## 2. 述語の単一定義(**定義はここだけに置く。他の節は参照する**)

**同じ述語を各節で言い直すと伝播漏れが起きる。** 前タスク(製品データモデル設計)では、述語を集約する節を新設してもなお**残存を検出する機械検査が別に必要**だった(台帳 **H-78**・`docs/development/harness-evaluation.md:548`)。さらに、是正時に**正規語の文字列だけで走査して別名を取りこぼす**事故が繰り返し観測されている(台帳 **H-79**・同 `:555`・`:563`)。

したがって本節は **① 唯一の定義 ② 禁じる別名(残存検査の入力)③ 適用先** の 3 点を持つ。**以降の節は本節を参照し、定義を書き直さない**。

### 2-2. 「同期連番」が誤読されやすい点(**本書の中核**)

受け取り元の申し送りは「**同期連番が「到着順」であることを明記**し、論理順序を別に持つ前提を共有する」と書かれている(候補案 `docs/features/product-data-model-design/design.md:1774-1775`)。**この「到着順」を「サーバーが受信した順」と読んではならない。**

- 要件書は**イベント生成時にクライアントが採番**することを定めている(REQ:284)。採番は**キュー追記と不可分**である(REQ:288)
- **サーバー受信順は入れ替わり得る**(再送・並行送信・部分到達)。それを連番の意味に採ると、**prefix コミット**(REQ:286 = 欠落があればそれ以降を適用しない)が成立しない — 受信順で採番するなら定義上欠落が生じないため、欠番検知そのものが意味を失う
- したがって **D1 の「到着」はクライアント内のキューへの到着**を指す。**サーバー到着順という概念は本設計に存在しない**

### 2-3. 禁じる別名

**各述語について、本書で使ってはならない語**を列挙する。**「正規語だけを検索して別名を取りこぼす」型の事故**(H-79)を防ぐため、**検査の入力を人手の記憶ではなく表にする**。

**検査の除外区間**: **2-2 節・2-3 節・12 節は検査対象から外す** — 2-2 と 2-3 は**その語を禁じる理由を述べるために当該語を使い**、12 節は**検査が捕まえた語を記録するために当該語を使う**ため、検査すると必ず引っかかる。**除外を隠れた例外にしないよう、ここに明記する**(検査スクリプトはこの見出しを見て除外区間を決める)。**2-1 と 2-4、および 3 節以降は検査対象**。

**表を 2 つに分ける。** 初版では 1 つの表に混ぜていたが、**残存検査を実際に回したところ「再送」「応答」「空イベント」で誤検出が出た** — これらは**それ自体が正しい概念**であり、無条件に禁止できない。**機械検査にかけられるのは無条件の禁止語だけ**であり、文脈依存の語は**人間の逐行確認の対象**である(計画書 6 節が「意味の支持は人間レビューへ分離する」と定めている)。

## 4. イベント契約の骨格(論点 13・14・15)

### 4-1. 本節が決めることと、決めないこと

**同期側が決めるのは「意味上必須な値と、それらが満たすべき不変条件」まで**である。**列名・型・NULL 性・FK・索引・表分割は決めない** — それらは製品データモデルの正本化(TSK-250)の責務であり、本書は**構造上の帰結を 11 節の「データモデル影響差分」として渡す**([plan.md](../features/sync-protocol-design/plan.md) 2 節)。

**「必須」の意味**: その値が無いと**同期プロトコルの規則(5〜9 節)のどれかが成立しない**ということ。表示や分析の都合で欲しい値は含めない。

**「必須」は種別に依存しうる。** **V6(論理位置)と V8(状態差分)は種別ごとの条件付き**であり、**全イベントが持つわけではない**。初版は V6 を無条件の必須として書いていたが、**5-5 の参加区分表で「同期順のみ」「従属」とした種別は自身の D2 を持たない**ため矛盾していた(起草レビュー 1 周目 P1)。

### 4-2. 識別子は 5 種を混ぜない(論点 13)

候補案が既に 5 種を分離している(`docs/features/product-data-model-design/design.md:436-440`)。**本書はこれを再決定せず、同期側の述語 ID との対応を付けて引き継ぐ**。

| 識別子 | 本書の述語 | 生成者 | 一意性の範囲 | 同期側での役割 |
| --- | --- | --- | --- | --- |
| べき等キー | **D5** | クライアント | **テナント内で全試合・全世代にわたり再利用しない**(4-5 の推奨。照合キーは `(テナント, D5)`) | 再送の二重適用を防ぐ。「**同じ操作か**」の判定 |
| イベント連番 | **D1** | クライアント(**採番と追記が不可分**) | **(試合, 記録権世代)内で単調増加** | 「**順序と欠落**」の判定(prefix コミット) |
| 記録権世代 | **D4** | サーバー | 試合内 | 引き継ぎのたびに更新。**正史は世代の連結** |
| 一時 ID(その場登録) | — | クライアント(**UUID**) | グローバル | 断中の選手登録。**同期時に正式 ID へ置換**(4-4) |
| エンティティの内部 ID | — | サーバー | テーブル内 | 選手 ID は**不変・内部**。名前・背番号は表示用属性(REQ:344) |

**混ぜてはならない理由(同期側から見た形)**:

- **D5 と D1 は判定の目的が違う**。D5 は「同じ操作か」、D1 は「順序と欠落」。1 つにまとめると **D7 改訂**(**同じ D1 のまま新しい D5**)が表現できなくなる(REQ:290)
- **D1 を試合グローバルにしない**(**P-25**)。**D4 のスコープが正**であり、**D4 なしでは D1 が一意にならない**(REQ:301)
- **一時 ID と D5 を兼ねない**。一時 ID は**エンティティの仮の名前**、D5 は**操作の同一性**。兼ねると、同じ選手を参照する 2 つの操作が「同じ操作」と誤判定される

**サイドカー結合キーはこの 3 つの合成で成立する**: 付録D-1 が定める外部契約の結合キーは **(試合ID + 記録権世代 + イベント連番)** であり(REQ:1186 — 「連番は世代内スコープのため世代なしでは一意にならない。FR-013」)、**独立した新しい識別子を作らずに満たせる**。**新しいキーを増やさない**(**P-02** と同じ発想)。

### 4-3-A. オンラインの変更操作を履歴へどう入れるか(論点 13 — 起草レビュー 1 周目 P1)

**初版は断中に生成されるイベントだけを扱い、オンラインの変更操作を覆っていなかった。** FR-007 の**記録済みプレイの修正**(REQ:231 の全体・終了済み試合も対象 — REQ:237)・**プレイ行の削除**(REQ:239)、FR-011 の**交代イベントの修正**(REQ:276)は、**いずれも既存イベントを変える操作**であり、契約が要る。

**「変更操作」に含めないもの**(起草レビュー 3 周目 P1):

| 操作 | 扱い | 理由 |
| --- | --- | --- |
| **任意位置への挿入**(REQ:238) | **変更イベントではない。新規の毎球入力**(5-5 の #1)であり、**D1 を採番してキューに積む** | **既存イベントを変えるのではなく、記録し忘れたプレイを足す操作**である。「指定位置にプレイを挿入でき」(REQ:238)と書かれているとおり**プレイ自身**であり、**論理位置(D2)を自分で持つ** |
| **端末をまたぐ再開**(REQ:249) | **イベントを生成しない** | 「同期済みプレイまでが対象」(REQ:249)であり、**既存の記録を読み直すだけ**。**未同期キューが残る端末からの切替は FR-013(記録権)の領域** |

| # | 規則 | 理由 |
| --- | --- | --- |
| **W1** | **確定済みイベントの修正・削除は、新しい変更イベントとして追記する**。**既存イベントを書き換えない** | **物理削除しない**(REQ:145)/ **プレイ行の削除は論理削除**(REQ:239)。**追記型にすると「いつ・何を・どう直したか」が追跡できる**(旧システムはこれが無く、改善台帳が問題として記録している) |
| **W2** | **D6 墓標・D7 改訂を、確定済みイベントの修正・削除に流用しない** | **D6・D7 は「サーバーが内容起因で拒否したイベントの始末」**(REQ:290)であって、**受理済みの記録を直す手段ではない**。流用すると**「拒否されたのか、後から直したのか」が区別できなくなる** |
| **W3** | **変更イベントは V1(D5)・V5・V7・V10 を持つ。**論理位置(V6)は対象の D2 に従う**(従属 — 5-5)。**D1(V2)を持たない** | **変更操作はすべてオンライン専用**である(進行中は REQ:240・REQ:242、終了後も REQ:242)。**D1 は断中のキューのための順序値**(REQ:284)であり、**断中に生成されない種別に持たせる理由が無い**。**持たせると害がある** — 終了後修正は記録権の条件の外なので(W4)、**複数端末が同じ次番号を採番して衝突し、楽観ロックでは修復できない**(起草レビュー 2 周目 P1) |
| **W3-a** | **変更イベントは V11 = 「対象の期待版」を持つ**。サーバーは**対象の現在の確定版と一致するときだけ受理**し、**受理と同時に対象の確定版を進める**(**楽観ロック** — REQ:234) | **D1 も自身の D2 も持たないと、DB から再生したときにどれが最終版か決まらない**(起草レビュー 3 周目 P1)。**期待版と確定版の連鎖が、変更イベント間の順序そのもの**になる |
| **W3-b** | **この「変更版順」は D1・D2 のどちらでもない別の順序であり、論理再生順に使わない** | **論理再生順は D2 だけで決まる**(5-5 の O1〜O4)。**変更版順は「同じ対象への変更を何番目に適用したか」だけを表す** |
| **W3-c** | **変更イベントは prefix コミットの対象にならない**。**オンライン専用なので欠番検知が要らない**(送信と応答が 1 往復で閉じる) | D1 を持たないため |
| **W4** | **変更操作は「オンライン・記録権保持・未同期キューが空」を前提とする**(進行中試合)。**終了後修正は記録権の外**で、**楽観ロック**が競合を扱う(REQ:234・REQ:237) | 5-3 の実行前提と同じ |

**「削除」は 2 つある。** **プレイ行の論理削除**(W1 — 受理済みの記録を消す)と、**墓標**(D6 — 内容起因で拒否され、破棄を選んだ D1 を消費する)は**別物**であり、**同じ経路にしない**。

### 4-4. 一時 ID → 正式 ID の置換契約(論点 13)

断中の選手のその場登録は「**クライアント生成の一時 ID(UUID)で記録され、同期時にサーバーが正式 ID を確定・参照を置換する**」(REQ:343)。**置換は「参照の置換」であって行の作り直しではない**。同期側は次の 4 点を契約とする。

| # | 契約 | なぜ必要か |
| --- | --- | --- |
| **C1** | **選手登録イベントへの応答で、一時 ID → 正式 ID の写像を返す** | クライアントが以後どの ID を使うかを決められない。**ACK(D9)の保証内容に写像を含める**(7 節) |
| **C2** | **後続イベントの参照が、同じ正式 ID へ決定的に解決される** | 断中に登録した選手を、同じ断中の後続イベントが**一時 ID で参照**している。**prefix コミット(6 節)が「欠落があればそれ以降を適用しない」ことを保証するため、登録イベントは必ず先に適用される** — この順序保証があるから解決できる |
| **C3** | **ACK 消失後の再送でも、別の正式 ID を重複生成しない** | 再送は **D5 で同一視**される(REQ:286)。サーバーは**新規作成ではなく既存の写像を返す**。これを守らないと、**同じ選手が 2 人分登録される** |
| **C4** | **写像が確定するまで、当該イベントを「同期済み」として扱わない** | 「未送信 / 同期済み」の判定に依存する分岐は置かない規律(REQ:228)と同根。**写像未確定のまま同期済みにすると、一時 ID のまま残った参照が解決不能になる** |

**置換の記録を残す**(どの一時 ID がどの正式 ID に解決されたか)。これは FR-035 の「**統合前の帰属を復元できる情報を保持する**」(REQ:721)と同型の要求であり、**同じ構造で扱える**。

### 4-5. べき等キーの再利用禁止範囲と衝突時の扱い(論点 14)

要件書は「クライアント生成」とだけ定める(REQ:284)。**生成アルゴリズムと長さは (B) 論点 17** に送るが、**再利用の可否と衝突時の扱いはプロトコルの意味規則**なのでここで決める。

#### 一意性の範囲 = **テナント内で再利用しない**

**(試合, 世代) 内一意では足りない。** 退避イベントの取り込みは「**現行世代の連番として採番し直す**」(REQ:307)ため、**同じ内容のイベントが別の世代・別の連番で再登場する**。このとき原本の D5 を流用すると、サーバーは**重複と判定して取り込みを無視する**。

したがって:

- **D5 は「テナント内で、全試合・全世代にわたって再利用しない」**。**照合キーは `(テナント, D5)`**

  > **初版は「グローバル一意」とし、選択を TSK-250 へ送っていた。これは撤回する**(起草レビュー 2 周目 P1)。**再利用禁止範囲は (A) 論点 14** であり(計画書 4 節)、**意味規則を物理モデル側へ委ねられない**。また初版の根拠(「テナント内一意にすると衝突検出のために先にテナントを解決する経路ができ、6-2 の段階順と衝突する」)は**誤りだった** — **認可は段階 ③、D5 の照合は段階 ⑥** なので、**認可後に `(テナント, D5)` を照合すれば段階順と矛盾しない**。
  >
  > **テナント内一意で本節の規則はすべて成立する**(退避取り込み・改訂・再送の同一視はいずれもテナント内で閉じる)。**DB 全体での一意制約を置くかは物理の判断**だが、**置く場合でも「他テナントの同一 D5 を重複として扱わない」「保存結果を返さない」ことが必要**(6-5 の非開示規則)。**物理表現は (B) 論点 17 / TSK-250**
- **退避イベントの取り込みは、新しい D5 を持つ新しいイベント**として扱う(原本はそのまま残る — 9 節)
- **D7 改訂も新しい D5 を持つ**(REQ:290)。**同じ D1・違う D5** という組み合わせが改訂の表現そのもの

#### 衝突時の扱い(**fail-closed**)

| 状況 | 扱い | 根拠 |
| --- | --- | --- |
| 既存と**同じ D5・同じ内容** | **無害な重複**。適用済みとして扱い、D3 は動かさない | REQ:286(「再送が重複到達しても二重適用されず」) |
| 既存と**同じ D5・異なる内容**(**FR-012 のキューに載る D1 付きイベント**) | **規約違反**。**先着を正とし、後着を恒久的な内容起因の拒否**とする(**B3**)。**再開は 6-4 の 2 択**(改訂 / 墓標) | べき等の定義上、同じキーの 2 回目は同じ操作でなければならない。**後着で上書きすると、確定済みの記録が黙って書き換わる**(REQ:147「黙殺しない」に反する) |
| 既存と**同じ D5・異なる内容**(**D1 を持たない変更イベント**) | **オンライン要求として fail-closed で拒否**する。**B3 の 2 択は使えない**(同一 D1 の改訂も墓標も、D1 が無いので成立しない)。**操作者は新しい D5 で操作をやり直す** | **B3 の再開手段は D1 を前提にしている**(起草レビュー 3 周目 P1)。**同じ D5 での再試行は「同じ操作の再送」としてのみ許す**(内容が同じなら重複として吸収) |
| **内容の同一性を判定できない** | **先着を正とし、後着を拒否する**(判定不能を「同じ」と見なさない) | 設計書 6.3 の「**判定に迷うものは含む側に倒す**(fail-closed)」と同じ発想。**誤って拒否する方が、誤って二重適用するより安全** |

**内容の同一性をどう判定するか(全フィールド比較 / ハッシュ)は (B) 論点 17** に送る。**意味規則は「同じ D5 で異なる内容は拒否する」**であり、判定手段はそれを実現できるものであればよい。

### 4-6. FR-040(状態補正)の条件付き扱い(論点 15)

**FR-040 は Should** であり、断中操作の完全列挙は「**Must の 6 種 + 状態補正(採用した場合のみ第 7 の種別)**」と定められている(REQ:119・REQ:166)。**採用を前提に構造へ焼き込んではならない**(**P-58**)。

本書は次の形で扱う:

1. **V5 のイベント種別の集合を「Must 6 種 ∪ (採用時のみ) 状態補正」と定義する**。採用状態は**集合の要素の有無**で表し、**種別ごとの分岐を構造の前提にしない**
2. **取消可能な操作の集合も同様**: 「確定プレイ ∪ (採用時のみ) 状態補正」。**採用しない場合、履歴文脈(V8)は確定プレイだけで構成される**(ADR-003 **D-6** `:255` — 「採用しない場合は『状態補正』イベント種別そのものが存在しない」)
3. **不採用の場合は、外した事実を宣言する経路がある**: ADR-003 **D-6**(`:255`)は「**当該イベント種別と補正関連 case を契約から外し、外した事実をマニフェストの `vectors[]` に宣言する**(**宣言のない除外は fail**)」と定める。**これは NFR-019 側の経路**なので、同期側は「**イベント種別の集合が FR-040 の採用状態に依存する**」ことを記録し、**受け取り先を 11 節の申し送りに書く**
4. **補正・undo は「イベント種別で表現し、別の対象計算にしない**」(ADR-003 **D-6** `:255`)。**同期側でも別経路を作らない** — 状態補正は他の操作イベントと同じ D1・D5・D3 の規律に従う

## 5. 順序の 2 系統と射程(論点 1・2・3・4)

**D1(同期連番)と D2(論理順序)の定義は 2-1 節が唯一の定義**である。本節は**定義を書き直さず、両者が並存して矛盾しないことを示す**。

### 5-1. 受け取り元の是正を正として引き継ぐ

候補案は 3 周目に「論理順序も出場区間の境界も再計算の起点も**イベント連番へ**」と一元化し、**4 周目に差し戻された**。差し戻しの理由は「**イベント連番は同期の到着順であり、過去位置への挿入や退避イベントの取り込みでは末尾に付く。そのまま論理順序に使うと挿入したプレイが末尾に再生される**」であり、結論は「**境界と再計算の起点は「論理順序」側を使う。同期連番は同期と undo に限る**」(`docs/features/product-data-model-design/design.md:407-411`)。

> **候補案 `docs/features/product-data-model-design/design.md:404-405` の用途対応表には、是正前の文言(「出場区間の境界 = イベント連番 / 再計算の起点 = イベント連番」)が残っている。** 同じ節の `:411` と食い違うため、**本書は `:411` を正として起草する**。**表の是正は TSK-250 へ申し送る**(11 節)。

### 5-2. 論理順序の表現方式(論点 2)

#### 前提を絞り込む — 並行挿入は「起きない」のではなく「直列化される」

方式の選定に効くのは**どこまでの同時性を支える必要があるか**である。要件から次が導かれる:

- **進行中試合の修正・挿入は「オンライン・記録権保持・未同期キューが空」でしか実行できない**(REQ:240・REQ:242)。したがって**断中に挿入は起きない**
- **同一試合の入力は 1 端末**(REQ:979)であり、**複数書き手の並行受け入れ・自動 3-way マージは Won't**(REQ:82)
- **ただし終了後修正は記録権の条件の外にある**。FR-007 は「終了済み試合 / 過去プレイを修正 / 終了状態のまま修正でき、再集計が自動で走る」(REQ:237)を認め、**旧 FR-007 から「幻の得点/アウトの禁止・差分プレビュー・楽観ロック」を継承する**(REQ:234)。**つまり並行更新は「存在しない」のではなく、楽観ロックで検出・直列化する前提が要件側に既にある**

> **初版は「2 人が同時に同じ位置へ挿入する状況は存在しない」と書いていた。** これは**進行中試合の条件だけを見た誤り**であり、**終了後修正を覆っていなかった**(起草レビュー 1 周目 P1)。

**したがって前提は「並行挿入が存在しない」ではなく「並行挿入は楽観ロックで直列化される」である。** 方式の選定には**これで十分**である — **衝突を自動マージで解く必要がない**(Won't)以上、**衝突耐性を持つ順序ラベル(LexoRank・無限精度の有理数)は支える必要のない性質にコストを払う**ことになる。

#### 候補と選定

| 方式 | 採否 | 理由 |
| --- | --- | --- |
| **整数の間隔(gap)** — 隙間を空けて採番し、挿入は隙間へ。隙間が尽きたら局所再採番 | **推奨** | 並行更新は**楽観ロックで直列化**するので**衝突耐性が要らない**。整数は比較・範囲指定・索引が素直で、**DB 側絞り込み**(REQ:797 — NFR-005)と相性がよい。再採番は起こるが**局所**に閉じる |
| **有理数(分数)** — 2 点の中間を取る | 却下 | 中間を取り続けると**分母が指数的に伸びる**。これを避ける再正規化は結局 gap 方式の再採番と同じ手間で、**得るものが無い**(直列化される以上、無限に割れる性質が要らない) |
| **LexoRank 等の文字列ラベル** | 却下 | **並行編集の衝突回避**が目的の方式。本製品は単一書き手(REQ:979)で、**Won't が明示的に自動マージを外している**(REQ:82)。**支えない性質のために文字列長の増大と比較コストを負う** |
| **相対参照(前後のイベントを指す連結リスト)** | 却下 | **範囲指定の集計ができない**。NFR-005 は「DB 側絞り込み・集計」を基本規律とし**全件読み込み型の集計を禁じる**(REQ:797)が、連結リストは**順序で絞り込むために全件たどる**ことになる |

**具体パラメータ(初期間隔・再採番の閾値・数値型)は (B) 論点 26** に送る。**実クエリが 1 本も無い段階で定数を確定させない**。

### 5-3. 挿入時の再採番の可否と、実行前提(論点 3)

#### 再採番の規則

| 場面 | D2(論理順序) | D1(同期連番) |
| --- | --- | --- |
| **通常の追記** | 末尾に採番 | 末尾に採番 |
| **任意位置への挿入**(FR-007) | **指定位置の隙間へ採番**。隙間が尽きたときのみ**局所再採番** | **末尾に採番**(キュー追記順 — REQ:284) |
| **退避イベントの取り込み**(FR-013) | **操作者が指定した位置**へ採番 | **現行世代で採番し直す**(REQ:307) |

**再採番が D2 側で起きても D1 は動かない。** これが 2 系統に分ける効用そのものであり、**D1 を動かさないので prefix 水位・べき等キー・既に確定した同期の判定はいずれも影響を受けない**。

**退避イベントの取り込みは通常の挿入とは別経路**である。取り込みは **D1 を採番し直す**が、通常の挿入は **D1 を末尾に採番するだけで振り直さない**。**末尾への機械的な追加はしない**(**P-31**)。詳細は 9 節。

#### 実行前提と、前提未達時の拒否

FR-007 は進行中試合の修正を「**記録権を保持する端末のみ**が実行でき、かつ**未同期キューが空であること**を前提条件とする」と定め(REQ:240)、補足で「**修正はオンライン前提**」とする(REQ:242)。

| 前提 | 未達時の扱い | どこで止まるか |
| --- | --- | --- |
| **オンライン** | 挿入操作を**提供しない** | クライアント |
| **記録権を保持** | **サーバーが拒否**する(REQ:308 — 現世代のない端末のイベントは適用しない)。**記録権起因の拒否は内容の編集で解決できない**ため退避へ誘導(6 節) | サーバー |
| **未同期キューが空** | **クライアントが実行を止める**。加えて**サーバー側にも防壁が立つ**(下記) | クライアント + サーバー |

**サーバー側で証明できるのは「サーバー側に gap がない」ことだけである。**

初版は「挿入イベントの D1 が D3 + 1 であることを見れば、キューが空だと分かる」と書いていた。**これは成立しない**(起草レビュー 1 周目 P1)。**ACK が失われた場合、端末は `D1=5` を未送信と認識したままサーバーの D3 は 5 まで進んでいる**。このとき次の挿入は `D1=6` で、**D3 + 1 の検査を通ってしまう** — **端末のキューは空でないのに**。

**したがって前提の担保は 2 段にする**:

| 段 | 何を保証するか | 誰が |
| --- | --- | --- |
| **前段** | **挿入の前に、キュー内の全イベントについて ACK 照合を完了する**(再送 → `(D4, D1, D5)` ごとの結果を受け取る — 7-1)。**未確定が 1 件でも残っていれば挿入を開始しない** | クライアント |
| **後段** | **挿入イベントの D1 が D3 + 1 であること**を確かめる。**これは「サーバー側に gap がない」ことの確認**であって、**端末のキューが空であることの証明ではない** | サーバー |

**後段だけでは足りない**ことを明示しておく。**前段を省くと、ACK 消失時に未確定のイベントを残したまま挿入が走る**。

### 5-4. REQ:238 と REQ:284 の両立(論点 1・2・3 の接続)

**任意位置挿入**(REQ:238)と**生成時のクライアント採番**(REQ:284)は、**D1 を末尾・D2 を過去位置に置く**ことで両立する。手順は次のとおり。

1. **前提を確認**(5-3)— オンライン ∧ 記録権保持 ∧ 未同期キューが空
2. **操作者が挿入位置を指定**する(前後のイベントの間)
3. **イベントを生成**する — **D1 は末尾**に採番し、キュー追記と不可分に永続化する(REQ:284・REQ:288)。**D2 は指定位置の隙間**に採番する
4. **送信**する — サーバーは **D1 の順**に prefix コミットで適用する(REQ:286)
5. **サーバーは D2 の順で再生・再計算**する。**下流再計算・差分プレビュー・幻の得点/アウトの禁止**が適用される(REQ:238)

**この手順の要点は 5 が 4 と別の順序で動くことである。** D1 順に「受け取り」、D2 順に「再生する」。**候補案が差し戻された「挿入したプレイが末尾に再生される」事故は、この分離によって起こらない**。

#### 規則が破綻しない 2 例

| 例 | 起きること | なぜ破綻しないか |
| --- | --- | --- |
| **`D1=3` が `D1=2` より先に到着** | サーバーの D3 は 1 のまま。`D1=3` は**適用しない**(**受け取ってはいるが確定させない**)。`D1=2` が到着した時点で 2 → 3 の順に適用し、D3 は 3 へ進む | **D1 の欠落判定は D2 と無関係**。**未確定のイベントがある間も、確定済みの D2 の並びは変わらない**。REQ:286 の規則がそのまま働く |
| **後から生成したイベントが過去の論理位置へ入る** | `D1` は末尾(例: 51)だが `D2` は 12 番目と 13 番目の間。適用は D1 順、再生は D2 順 | **D1 は「いつ受け取ったか」、D2 は「どこに位置するか」**を表す別の値であり、**一方が他方の意味を上書きしない** |

> **ACK 消失後の再送**については、ACK(D9)が何を保証するかを決めてからでないと検証できないため、**7 節で扱う**。

### 5-5. 論理順序の射程と同位置の扱い(論点 4)

#### イベント種別ごとの参加区分

要件書の断中操作の完全列挙は「**毎球入力・undo・選手交代・タイブレーク開始・試合終了宣言・選手のその場登録(Must の 6 種)＋状態補正(FR-040 — 採用した場合のみ第 7 の種別)**」である(REQ:119・REQ:166)。**この列挙は利用者の操作だけを覆っており、同期プロトコル自身が生成する墓標・改訂版を含まない**。したがって**両方を表に載せる**。

**区分の定義**: **論理位置を持つ** = 自身の D2 を持ちプレイ列に投影される / **同期順のみ** = D1 だけを持ち D2 を持たない / **従属** = 自身の D2 を持たず**他のイベントの D2 に従う**。

**表は 2 群に分ける**(起草レビュー 2 周目 P1): **断中に生成されうる種別**(要件書の完全列挙 — REQ:119)と、**オンライン専用の種別**(同期プロトコルが生成するもの + 4-3-A の変更イベント)。**初版は前者しか載せておらず、変更イベントが参加区分表から漏れていた**。

| # | イベント種別 | 区分 | 根拠 |
| --- | --- | --- | --- |
| 1 | **毎球入力** | **論理位置を持つ** | プレイ列の本体。任意位置挿入の対象(REQ:238) |
| 2 | **undo** | **従属**(取り消す対象の D2 に従う) | undo は「**直前の取消可能な操作 1 件**」を取り消す操作であり、プレイ列に**自身の場所を持たない**。ただし**下流再計算の起点は対象の D2** になるため、位置を完全に持たないわけではない(REQ:229) |
| 3 | **選手交代** | **論理位置を持つ** | 「**何回・どのプレイ時点で誰→誰**」が追跡でき、**交代はイベントとして永続化**される(REQ:274)。**出場区間の境界そのもの**であり、下流再計算でも「**交代イベントの時点が保持される**」(REQ:236) |
| 4 | **タイブレーク開始** | **論理位置を持つ** | 以降の状態遷移の起点。**どのプレイの後から適用されるか**が意味を持つ |
| 5 | **試合終了宣言** | **論理位置を持つ** | **論理順序上の末尾**に位置する。**検知(FR-005)とは分離**され、宣言はイベントとして積まれる(REQ:216・**P-29**) |
| 6 | **選手のその場登録** | **同期順のみ** | **マスタへの登録**であってプレイ列に投影されない。ただし**後続イベントが一時 ID で参照する**ため、**D1 で先行している必要がある**(4-4 の C2) |
| 7 | **状態補正**(採用時のみ) | **論理位置を持つ** | 「**絶対状態の設定**」(ADR-003 **D-6** `:255`)であり、**以降の再計算の起点**になる。**採用しない場合はこの行が存在しない**(4-6・**P-58**) |
| 8 | **墓標**(同期が生成) | **同期順のみ** | **D1 を消費して D3 を前進させる**ためだけに存在し(REQ:290)、**プレイ列に投影されない** |
| 9 | **改訂版**(同期が生成) | **元イベントの参加区分を継承する** — 元が**論理位置を持つ**なら有効版として選ばれた後に**元の D2 を引き継ぎ**、元が**同期順のみ**(選手のその場登録など)なら**D2 を持たないまま**にする | **同じ D1 のまま内容を作り直したもの**(REQ:290)であり、**位置は変わらない**。引き継がないと、**内容を直しただけでプレイの並びが動く**。**一律「従属」とすると、元が D2 を持たない種別を表せない**(起草レビュー 3 周目 P1) |
| 10 | **プレイの修正**(オンライン専用 — 4-3-A) | **従属**(対象の D2) | **確定済みイベントを追記型の変更イベントで直す**(W1)。**自身はプレイ列に投影されない** |
| 11 | **プレイ行の論理削除**(オンライン専用) | **従属**(対象の D2) | **論理削除**(REQ:239)。**削除された対象の D2 は投影から外れる**が、**変更イベント自身は位置を持たない** |
| 12 | **交代イベントの修正**(オンライン専用) | **従属**(対象の D2) | REQ:276。**交代の時点(対象の D2)は保持される**(REQ:236) |

#### 同位置を作らない(**tie-break に D1・D4 を使わない**)

**初版は同位置の順序を `(D2, D4, D1)` の辞書式で決めていた。これは撤回する。** **D1 を論理再生順の決定に使うと、2-1 が定めた「D1 は同期と undo に限る」を破り、D1 と D2 を再結合してしまう**(起草レビュー 1 周目 P1)。**分離を主題とする本書が、tie-break の一点で分離を崩していた**。

**代わりに「同位置を作らない」を規則とする。**

| # | 規則 | 理由 |
| --- | --- | --- |
| **O1** | **D2 の採番・再採番は、楽観ロックを伴う原子的な操作として直列化する** | 要件は FR-007 に**楽観ロックを継承させている**(REQ:234)。**採番を直列化すれば、同じ D2 が 2 件生じない** |
| **O2** | **隙間が尽きたときは、採番と同じ原子的操作の中で局所再採番する** | 「隙間が無いまま同値で入れる」経路を作らない |
| **O3** | **退避イベントの取り込みで既存と同じ位置を指定されたときも、O1 の操作の中で隙間を作る** | 取り込みは**明示的な操作**(REQ:307)なので、採番と同じ経路に載せられる |
| **O4** | **それでも同値が観測されたら、それは不変条件の破れとして扱う** — 順序を推測で決めず、**検出して是正する**(扱いは下表) | **推測で順序を決める規則を置くと、破れが隠れて残る** |

**D2 の一意性の射程**: 不変条件は「**同時に有効で、かつ自身の D2 を持つイベントの間で D2 が一意**」である。**従属・同期順のみの種別は対象外**(自身の D2 を持たない)。**置換された旧版も対象外**(有効でない)。

**O4 で検出したときの扱い**(起草レビュー 2 周目 P2):

| 検出の場面 | 扱い | 境界結果 |
| --- | --- | --- |
| **採番時に楽観ロックが競合した** | **隙間を取り直して自動再試行**する。操作者には見せない | **B7 相当**(一時障害と同じ扱い。再試行で解ける) |
| **永続化済みのデータに同値が見つかった** | **fail-closed** — **投影と再計算を止め、管理者へ顕在化する**(REQ:851)。**DB の返却順に依存した順序で再生しない** | **B3 相当**(操作者の再送では解けない) |

**この形なら順序の決定は D2 だけで完結する。** **D1・D4 は再生順に現れない**。

**O1 の実現方式((試合, D4) 単位のロックか、行単位の版番号か)は (B) 論点 26** に送る。**本書が決めるのは「採番が直列化されること」まで**である。

## 6. prefix コミットと、拒否・再開の決定表(論点 5・6)

### 6-1. D3(prefix 水位)の規則(論点 5)

**D3 の定義は 2-1 節が唯一の定義**である。本節は**前進と据え置きの規則**だけを定める。

| 規則 | 内容 | 典拠 |
| --- | --- | --- |
| **R1 スコープ** | **D3 は (試合, D4) ごとに持つ**。D1 が世代内スコープであるため、世代が変われば水位も別 | REQ:301 |
| **R2 欠落での停止** | **D1 に欠落があれば、それ以降を適用しない**。欠落の直前で止まる | REQ:286 |
| **R3 前進の契機** | **確定イベントの適用**、または**墓標の適用**で前進する。「**prefix は確定イベントまたは墓標を越えて前進する**」 | REQ:290 |
| **R4 単調性** | **D3 は後退しない**。改訂(D7)は**同一 D1 の内容を置換する**だけで、水位を戻さない | REQ:290 |
| **R5 行の存在は拒否しない** | **下位番号の欠番・重複それ自体を拒否する規則ではない**。R2 は「適用しない」であって「保存を拒む」ではない | 候補案 `docs/features/product-data-model-design/design.md:539` |

**R3 と R2 の関係**: R2 だけだと、**破棄したいイベントが 1 件あるだけで以降が永久に止まる**。R3 が墓標を前進の契機に含めることでこれを解く(REQ:290 の「破棄で後続が永久停止しない」)。**D6 墓標はこのためだけに存在する**。

**改訂(D7)が水位を戻さない理由**: 改訂は**同じ D1・新しい D5**(REQ:290)であり、**位置ではなく内容を差し替える操作**である。仮に水位を戻すと、**既に確定した後続イベントが未確定へ逆戻りし、確定記録が揺れる**。**墓標と改訂の論理順序上の扱いは 5-5 節が正**(墓標 = 同期順のみ / 改訂版 = **元イベントの参加区分を継承**)。

### 6-2. 決定表を 2 軸で表す(論点 6)

**「最初の未適用イベントの停止理由」という 1 軸では、全件適用できた場合と全件が重複だった場合を分類できない**(そもそも「最初の未適用イベント」が存在しない)。また「適用済み / 重複」は**停止理由ではなくイベント 1 件ごとの処理結果**である。したがって**2 軸で表す**。

| 軸 | 何を表すか | 値 |
| --- | --- | --- |
| **第 1 軸: ACK 済みの D3** | この要求で**水位がどこまで前進したか** | 整数(前進しない場合は元の値) |

**1 要求は単一の `(試合, D4)` に限る**(起草レビュー 2 周目 P2)。**D3 は `(試合, D4)` ごとに持つ**(6-1 の R1)ため、**複数の試合・世代を 1 要求に混ぜると「第 1 軸の D3」が一意に定まらない**。混在を許す形は**要求と ACK の形を作り直す必要があり、得るものが無い**。
| **第 2 軸: 境界結果** | **どこで、なぜ処理が終わったか** | 下の 7 種 |

**イベント 1 件ごとの処理結果**(新規適用 / 重複 / 未適用)は**第 1 軸の内訳**として ACK に載せる。**第 2 軸には置かない**。

#### 網羅性の根拠 — 処理段階の列挙

境界結果の 7 種は思いつきの列挙ではなく、**サーバーが 1 要求を処理する段階の列挙**から導く。**各段階で止まりうる**ので、段階の数だけ境界結果がある。

| 段階 | 何を確かめるか | ここで止まったときの境界結果 |
| --- | --- | --- |
| ① トランスポート・処理系 | 要求が届き、処理が完了したか | **B7 一時障害** |
| ② 認証 | 呼び出し元が認証されているか | **B5 認証失効** |
| ③ 認可(テナント) | その試合が**自テナントのものか** | **B6 認可・テナント不一致** |
| ④ 記録権(D4) | **現世代の端末からのイベントか** | **B4 旧記録権世代** |
| ⑤ 連番(D1)の連続性 | **D3 + 1 から欠落なく続くか** | **B2 gap** |
| ⑥ 内容の検証 | イベントの内容が受理できるか | **B3 恒久的な内容拒否** |
| ⑦ 完了 | 最後まで処理し切ったか | **B1 要求終端** |

**段階の順序は入れ替えられない。** ③ 認可は ④ 以降より**必ず先**でなければならない — 後に置くと、**記録権の状態や連番の状態が応答に現れることで、他テナントの試合の存在が漏れる**(REQ:825「**内容・存在を含め参照できない**」・REQ:583「**内容・存在が応答から判別できない**」)。

| **B5** | **認証失効** | なし(② で止まる) | **失われない**(REQ:293) | **再ログイン後に同期が再開される**(REQ:293) | **再ログインを促す**。**キューが保持されていることを併せて示す**(操作者が「消えた」と誤解して再入力するのを防ぐ) |
| **B6** | **認可・テナント不一致** | なし(③ で止まる) | **保持する**(破棄しない) | **同じ認証状態での自動再送は止める**。**正しいテナントで再認証すれば同じキューから同期を再開できる**。加えて**管理者対応**と**ローカル書き出し**(7-7)の経路を残す | **6-5 の非開示規則に従う** |

| **全件が重複の再送**(ACK 消失後など) | **前進しない**(既に最後の D1 まで進んでいる) | **B1** | 内訳は「新規適用 0 件 / 重複 n 件」。**「何も起きなかった」ではなく「終端まで処理して重複だった」**と表せる |
| **前進した後で停止** | 途中まで前進 | **B2 または B3** | **第 1 軸と第 2 軸が独立**なので「ここまでは確定した + ここで止まった」を同時に表せる。**B4 は含めない** — 記録権の照合は段階 ④ で **D1 の処理より前**に行われるため、**B4 では D3 が前進しない**(6-3) |

### 6-4. B3(恒久的な内容拒否)からの再開 — 2 択

要件書は、**B3(恒久的な内容拒否)からの再開だけ**を **2 択に限定**する(REQ:290)。この 2 択を B2(gap)や B4(旧記録権世代)へ流用しない。

| 選択 | 何を送るか | サーバーの扱い | D3 |
| --- | --- | --- | --- |
| **(a) 編集して再送** | **D7 改訂版** — **同一の D1**・**新しい D5**(4-5) | **旧版を置換する** | 改訂版の適用で**前進する** |
| **(b) 破棄** | **D6 墓標** — 内容起因で拒否された当該 D1 を正式に消費する空イベント | 内容を持たないまま**当該 D1 を消費** | **墓標を越えて前進する**(R3) |

**破棄・改訂の事実は記録される**。**破棄時は、後続イベントへのサーバー補正の内容が通知される**(REQ:290)— 破棄したイベントに依存していた後続の状態が変わるため、**黙って直さない**(REQ:147・NFR-015)。

**記録権起因の拒否(B4)はこの 2 択に含めない。** 「**記録権拒否は内容の編集では解決できないため別カテゴリとして扱い、退避へ誘導する**」(REQ:290)。**B3 と B4 を同じ画面・同じ導線に載せると、操作者が「編集すれば通る」と誤解する**。

#### 原本のない B2(gap)の扱い

**B2 の gap は、通常はクライアントに当該イベントが残っているので再送で解ける。** しかし**端末故障で未送信分の一部が失われた場合**(9 章 R-2 の受容済みリスク — `docs/requirements/requirements-pitchlog-2026-07-22.md:1019`)、**再送する原本が存在しない**ため gap が解けず、**以降が永久に前進しない**。

**v0.1 では原本のない B2(gap)は前進不能であり、本書の保証および射程の外である。** 現行要件 FR-012 の墓標は**内容起因で拒否された場合**に限定されるため、原本喪失 gap を前進させる新しい遷移を本書で発明しない。受け取り先は、**要件書 v2.5 と本正本 v0.2 を同一の確定ゲートで一括検証する後続タスク**とする(11-4 の U-1)。

### 6-5. B6(認可・テナント不一致)の非開示規則

要件書は「**それ以外の他チームのデータ資源は内容・存在を含め参照できない**」(REQ:825 — NFR-010)、「**404 または拒否となり、内容・存在が応答から判別できない**」(REQ:583 — FR-034)と定める。**同期の応答も出力経路の 1 つ**であり、この規則の対象になる。

| 対象 | 規則 |
| --- | --- |
| **応答コード** | **自テナントに存在しない試合と同じ応答**にする。「権限がない」と「存在しない」を**応答から区別できてはならない** |
| **応答の本文** | **理由コードを返さない**。B4(旧記録権世代)や B2(gap)のような**内部状態を含めない** — 含めると、その試合が存在することが分かる |
| **利用者への通知** | **内部原因を露出しない**。「**別テナントの試合です**」「**記録権が他チームにあります**」はいずれも**不可** |
| **監査** | **サーバー側のログには記録する**。管理者は追跡できる(FR-035 の管理者操作ログ)。**非開示は利用者向けの応答に対する規則であって、記録しないことではない** |

**この規則は 6-2 の段階順(③ 認可を ④ 以降より先に置く)と一体である。** 順序を入れ替えると、**規則をどれだけ書いても応答の差から存在が漏れる**。

**非開示は「記録を捨てること」ではない。** **B6 でもキューは保持する**(6-3)。**間違ったテナントのアカウントでログインしていただけなら、正しいテナントで再認証すれば同じキューから同期を再開できる** — **この経路を塞ぐと、操作者の設定間違いで 1 試合分の記録が永久に取り出せなくなる**(起草レビュー 1 周目 P1)。**再認証を促す文言は、当該試合の存在を示唆しない一般的なものにする**(「この端末には送信できていない記録があります。アカウントを確認してください」等)。

## 7. ACK とキューの状態遷移・クライアント規律・undo・非常口(論点 7・8・9・16)

### 7-1. ACK(D9)が保証するもの(論点 7)

**D9 の定義は 2-1 節が唯一の定義**である。本節は**何を保証し、何を保証しないか**を定める。

| # | ACK が保証すること | 根拠 |
| --- | --- | --- |
| **A1** | **受理され連続 prefix に入ったイベントについて、当該経路で適用されるすべての T 要素が原子的に確定した**(**経路別の適用表は 8-1**)。**ACK が返す D3 は、その条件を満たしてコミット済みの連続 prefix の上限**である。**要求(バッチ)全体の原子性は保証しない**。**拒否・退避・未処理のイベントには A1 が掛からない**(起草レビュー 2 周目 P1) | REQ:287・8-1 |
| **A2** | **D3 以下のイベントは、以後の再送で二重適用されない** | REQ:286 |
| **A3** | **境界結果(6-3)がどれか**。ただし **ACK が返るのは B1〜B4 の場合に限る** — **B5(認証失効)・B6(認可)・B7(一時障害)では ACK 自体が返らない**(6-2 の段階 ①〜③ で止まるため) | 6 節 |
| **A5** | **要求に含めた各イベントについて、`(D4, D1, D5)` ごとの結果**(**受理 / 重複 / 拒否 / 退避 / 未処理**)。**「未処理」は B2・B3 で処理が止まった以降のイベント**を表す。**「重複」は保存済みの確定結果が「受理」だった場合に限る** — **拒否・退避・未処理だったものは、保存済みの結果をそのまま再掲する**(**保存済みだが未適用のものを「重複」と返すと、クライアントが未適用のイベントを同期済みへ移してしまう** — 起草レビュー 3 周目 P1)。**選手登録イベントについては、A4 の写像が返っていることが「受理 / 重複」の成立条件** | **D1 ≤ D3 だけで同期済みへ移すと、同じ `(D4, D1)` で異なる D5 のイベント(改訂の途中など)を取り違える**。**「未処理」が無いと、止まった以降のイベントを表現できない**(起草レビュー 2 周目 P1) |
| **A4** | **一時 ID → 正式 ID の写像**(当該要求に選手登録イベントが含まれる場合) | REQ:343・4-4 の C1 |

**ACK の内容は再送しても同じものが返る。** **D5 ごとに確定結果(A4 の写像・補正の差分・退避の結果)を保存し、重複再送でも同じ結果を返す**。**これを保証しないと、応答が失われたときに NFR-015 が求める通知が永久に失われる** — 再送は B1 の「重複」になり、**最初の補正内容が二度と流れない**(起草レビュー 1 周目 P1)。

**ACK が保証しないこと**:

- **サーバーの再計算結果がクライアントの表示と一致すること**。差異は**補正として別に通知される**(REQ:289・8 節)。**ACK は「受け取って確定した」であって「あなたの計算が正しかった」ではない**
- **D3 より先のイベントの帰結**。B2/B3 で止まった場合、**それ以降は未確定**である

**ACK の必須要素は「前進後の D3」である。** 件数だけを返すと、**部分成功のときにクライアントがどこまで確定したかを特定できない**。

### 7-2. キューの状態遷移(論点 7)

| 状態 | 意味 | 典拠 |
| --- | --- | --- |
| **未送信** | 端末内キューに積まれ、まだ確定していない | REQ:283 |
| **要操作**(改訂待ち / 墓標待ち) | **内容起因で拒否された**(B3)。**操作者の判断を待つ**あいだ、自動再送の対象から外す | REQ:290 |
| **同期済み(24 時間保持)** | 確定した。**DB 障害時の再送出所**として端末に残す | REQ:292 |
| **退避済み** | **旧世代として退避された**(B4)。破棄されていない | REQ:305 |

**遷移条件**:

| 遷移 | 条件 |
| --- | --- |
| **(なし)→ 未送信** | 操作の確定と同時。**追記と D1 の採番は不可分に永続化される**(REQ:288) |
| **未送信 → 同期済み** | **ACK の A5 が、当該イベントの `(D4, D1, D5)` について「受理」または「重複」を返したこと**。**D1 ≤ D3 だけでは不足**(同じ `(D4, D1)` で異なる D5 を取り違えるため — 起草レビュー 1 周目 P1) |
| **未送信 → 要操作**(**改訂待ち / 墓標待ち**) | ACK の A5 が当該イベントについて**拒否**を返したこと(**B3**)。**操作者の 2 択(6-4)を待つ状態**であり、**自動再送の対象から外す** |
| **要操作 → 未送信** | 操作者が**改訂版または墓標を生成**したこと |
| **未送信 → 退避済み** | ACK の境界結果が **B4** であること |
| **同期済み → (破棄)** | **確定から 24 時間の経過**(REQ:292)。破棄トリガの実装は (B) 論点 25 |

**キュー遷移の根拠は A5 だけである。** **D3 は遷移の判定に使わない** — **D3 の役割は「連続 prefix の整合確認」と「再送範囲の決定」に限る**(起草レビュー 2 周目 P1)。

**なぜ件数や「送った/送っていない」で判定しないか**: **ACK が消失したときに、実際は確定しているイベントを未送信と誤判定する**。**A5 は次回の要求で必ず取り直せる**ため、**判定の根拠を端末の記憶ではなくサーバーの応答に置ける**。

**写像が確定するまで同期済みにしない**(4-4 の C4)— A4 の写像を受け取っていない選手登録イベントは、**D1 が D3 以下でも同期済みへ移さない**。

### 7-3. ACK 消失後の再送(論点 7)

**ACK が失われても規則は破綻しない。** 手順は次のとおり。

1. クライアントは**未送信のまま**の先頭から再送する(**D3 を知らないので、自分が知る最後の同期済み以降を送る**)
2. サーバーは **D5(べき等キー)で重複を判定**し、**二重適用しない**(REQ:286)
3. サーバーは **現在の D3 を ACK で返す**。境界結果は **B1**(内訳は「新規適用 0 件 / 重複 n 件」)
4. クライアントは**返ってきた A5 で状態遷移を判定**し、「重複」と返った分を「同期済み」へ移す(**D3 は再送範囲の決定に使う**)

**規則が破綻しない理由**: **D3 が単調で後退しない**(6-1 の R4)ため、**再送が何回起きても最終的な状態が同じ**になる。**クライアントの記憶が欠けても、サーバーの D3 が真値**である。

**これが REQ:228 の「クライアントの『未送信/同期済み』判定に依存する分岐を置かない」と同じ根**である。要件は undo について書いているが、**理由(ACK 消失時の誤判定)は同期全体に効く**。したがって本設計は**「同期済みか」を分岐条件にする箇所を作らず、必要なときは D3 と突き合わせる**。

### 7-5. 試合終了に固有の経路(論点 8)

FR-010 は終了時の同期について 2 つの受入基準を持つ。**通常の同期規律とは別に明示する**。

| 場面 | 規則 | 典拠 |
| --- | --- | --- |
| **未同期プレイがある状態で試合終了** | **同期が実行され、失敗があれば件数と理由が明示される**(**黙って欠損しない**) | REQ:263 |
| **通信断中の試合終了宣言** | **終了宣言イベントがキューに積まれ、復帰後に同期・確定される**。あわせて**未送信である旨の警告**と**試合一覧の未送信バッジ**が表示される | REQ:264 |

**「失敗があれば件数と理由」は 6-3 の境界結果へ写す**: 終了時同期の失敗は **B2〜B7 のいずれか**であり、**理由の提示は境界結果の提示**である。**終了固有の新しい失敗分類を作らない**。

**未送信バッジは Q4(未送信件数の常時表示)とは別の要求**である。Q4 は**記録画面**、バッジは**試合一覧**。**正常フローのまま記録が端末に置き去りになる事故の防止**が目的(REQ:264)であり、**試合を離れた後も見える場所に出す**必要がある。

### 7-6. undo の同期上の表現(論点 9)

| # | 規則 | 典拠 |
| --- | --- | --- |
| **U1** | **常に取り消しイベントがキューに積まれる**。**同期済み・未送信を問わない** | REQ:226 |
| **U2** | サーバー側で**べき等に適用される**。**対象の操作が未着なら相殺する** | REQ:226 |
| **U3** | **画面は即時に 1 つ前の状態に戻る**(サーバー往復を待たない — NFR-001) | REQ:226・REQ:777 |
| **U4** | **取消可能な操作が 1 件も無いとき**は、**状態を変えず、取り消す対象が無いことを利用者へ示す** | REQ:227 |
| **U5** | **「未送信/同期済み」判定に依存する分岐を置かない** | REQ:228 |
| **U6** | **undo 自身は取消可能な操作としない**(undo を undo しない) | REQ:229 |

**undo は対象を `(試合, 対象の D4, 対象の D1)` で名指す**(V10)。**D1 だけで名指してはならない** — **D1 は世代内でしか一意でない**(REQ:301)ため、**世代を跨いだ最初の undo が同番号の別イベントを取り消す**(起草レビュー 1 周目 P1)。**履歴文脈も「世代の連結 + 世代内 D1」で導出する**(REQ:301 の「正史は世代の連結」)。

**U2 の「相殺」が成り立つ条件**: undo イベントは**対象を V10 で名指す**。**prefix コミットが順序を保証する**(6-1 の R2)ため、**undo が対象より先に確定することはない**。

**相殺は要求の境界を越える。** 初版は「同一要求内での打ち消し」に限定していたが、**これは誤りだった**(起草レビュー 2 周目 P1)。**R5 は gap より先のイベントを拒まず保存する**(6-1)ため、**undo が先の要求で保存され、対象が後の要求で到着する経路が実在する**。FR-006 の「**対象の操作が未着なら相殺**」(REQ:226)はこの経路を含む。

| # | 規則 |
| --- | --- |
| **U2-a** | **欠番が埋まったら、保存済みのイベントを D1 順に連続 prefix として適用し切る**(drain)。**要求の境界で止めない** |
| **U2-b** | **drain の途中で undo が対象に追いついたら、その場で相殺する**。**対象を適用してから undo で取り消す**のではなく、**両者が同一トランザクションで打ち消し合う**(REQ:226 の「相殺」) |
| **U2-c** | **drain の結果も D5 ごとの確定結果として保存する**(7-1)。**undo を再送されても同じ結果を返す** |

**U4 と同期の関係**: 空履歴の undo は**イベントを生成しない**。**生成しないので D1 も消費しない**。**「何もしないイベント」を積むと、墓標(D6)と紛らわしい列ができる**ため、**積まない**ことを明示する。

**U6 と 5-5 の関係**: undo は**従属**(取り消す対象の D2 に従う)であり、**自身の論理位置を持たない**。**undo を undo しない**ため、**undo を対象とする undo イベントは生成され得ない**。

### 7-7. キューのローカル書き出しと復旧後取り込み(論点 16)

要件書は「**端末内キューのローカル書き出し(ファイル保存)と復旧後取り込み**」を **Should** とし、**保証範囲を「同一端末・同一ブラウザ」**に限定する(REQ:295)。**キュー上限でのブロックを廃止したことに伴い、キュー肥大時の非常口として重要度が上がった**という経緯を持つ。

**同期上の規則**(ファイル形式は (B) 論点 19):

| # | 規則 | 理由 |
| --- | --- | --- |
| **X1** | **書き出しは D1・D4・D5 を含むイベントの原形を保つ**。書き出しの時点で採番し直さない | 取り込み後に**同じイベントとして同期できる**ようにするため |
| **X2** | **取り込みで生じる重複は D5(べき等キー)で吸収する**。既に確定していれば **B1 の「重複」**として扱われ、二重適用されない | REQ:286。**取り込み専用の重複判定を作らない** |
| **X3** | **取り込めるのは同一の D4(記録権世代)のイベントに限る**。世代が変わっていれば、同期しても **B4(旧記録権世代)**になり退避される | REQ:308。**退避経由で現行世代へ取り込む**のが正しい経路(9 節)であり、**ローカル取り込みでそれを迂回しない** |
| **X4** | **保証範囲は同一端末・同一ブラウザ**。別端末への持ち込みは**保証しない** | REQ:295 |

**X3 が重要な理由**: ローカル書き出しは**非常口**であって、**記録権の引き継ぎを迂回する裏口ではない**。世代が進んでいるのに取り込みを成功させると、**D1 の衝突と正史の破壊**が起きる。**迂回できない形にしておく**。

## 8. サーバー適用の原子性・再計算・補正通知(論点 10)

### 8-1. 単一トランザクションの構成要素と境界

要件書は 4 つの要素が**単一の DB トランザクションで確定する**ことを求める(REQ:287 — 「**途中クラッシュでプレイが消える/二重適用される事故の防止**」)。**本書はこれに T5(D2 の採番・再採番)を加える** — 要件が名指してはいないが、**同じ「途中クラッシュ」の事故が D2 側でも起きる**ため。

| # | 要素 | 本書の述語 | 欠けるとどうなるか |
| --- | --- | --- | --- |
| **T1** | **べき等キーの記録** | **D5** | 再送で**二重適用**される(REQ:286 が守れない) |
| **T2** | **イベント保存** | — | **プレイが消える** |
| **T3** | **prefix 更新** | **D3** | 適用済みなのに水位が戻り、**再送で二重適用**されるか、**永久に前進しない** |

| **T5** | **D2 の版検査・隙間の確保・対象範囲の局所再採番**(5-5 の O1・O2) | **D2** | **再採番だけが確定して新しいイベントの保存が確定しないと、「既存イベントだけが動いた」「D2 が重複した」状態が残る**(起草レビュー 2 周目 P1) |

**境界の決め方(本書の判断)**:

| 判断 | 内容 | 根拠 |
| --- | --- | --- |
| **単位は「1 要求」ではなく「連続して適用できた範囲」** | 要求に 10 件含まれ 7 件目で B3(内容拒否)になったら、**1〜6 件目を確定させて 7 件目以降は確定させない**。1 要求を丸ごと 1 トランザクションにすると、**1 件の拒否で確定できたはずの 6 件が失われる** | REQ:286(欠落があればそれ以降を適用しない = **それ以前は適用してよい**)・6-3 の第 1 軸 |

**まとめ方((1 件ずつ / 連続範囲を 1 つに)は性能の都合であり、意味規則ではない**。どちらでも上表の判断を満たせる。**選択は (B) 論点 18(バッチ単位)へ送る**。

#### 経路別の適用表(起草レビュー 3 周目 P1)

**すべてのイベントに T1〜T5 が掛かるわけではない。** **D1 を持たない変更イベント(4-3-A)には T3(prefix 更新)が存在しない**。

| 経路 | 適用される T 要素 |
| --- | --- |
| **FR-012 のキューに載る D1 付きイベント**(毎球入力・undo・交代・タイブレーク開始・終了宣言・その場登録・状態補正・墓標・改訂) | **T1・T2・T3・T4** |

**ACK の A1 が保証するのは「当該経路で適用されるすべての T 要素の確定」**である(7-1)。

### 8-2. サーバー再計算が正(論点 10)

| # | 規則 | 典拠 |
| --- | --- | --- |
| **S1** | **正本は DB の 1 系統のみ**。断中のクライアント計算は**暫定**であり、**復帰同期時のサーバー再計算が確定記録** | REQ:149 |
| **S2** | サーバーは**イベント列を入力順に再計算・検証**する | REQ:289 |
| **S3** | **サーバー結果が確定記録**となる | REQ:289 |
| **S4** | クライアント表示と差異があれば**補正し、操作者に通知する**(**黙って直さない**) | REQ:289・REQ:851(NFR-015) |

**「入力順」とは D2(論理順序)の順である。** **D1 は受け取りの順**であって再生の順ではない(5-4)。**ここを取り違えると、任意位置へ挿入したプレイが末尾に再生される** — 候補案が差し戻された事故そのものである。

**再計算の起点は、変更されたイベントの D2 とそれ以降**である(**下流再計算** — REQ:238)。**全件を毎回引き直す必要はない**が、**どこから引き直すかは D2 で決まる**。

**再計算の粒度(全リプレイ / 増分 / チェックポイント)は (B) 論点 21** に送る。**本書が決めるのは「何を正とするか」と「どこから引き直すか」まで**であり、**引き直し方は実データの規模で決まる**。

### 8-3. 補正の通知(論点 10)

**S4 の「黙って直さない」は、同期の全経路に効く。** NFR-015 は「**データ保存・同期・バックアップ・出力の失敗、スキップ、自動補正**は、利用者または管理者に顕在化する」と定める(REQ:851)。

| 通知すべき場面 | 何を伝えるか | 典拠 |
| --- | --- | --- |
| **再計算でクライアント表示と差異が出た** | **補正した内容** | REQ:289 |
| **墓標で破棄した** | **後続イベントへのサーバー補正の内容**(破棄したイベントに依存していた状態が変わるため) | REQ:290・6-4 |
| **同期が境界結果 B2〜B7 で止まった** | **どこで止まったか**(6-3 の通知欄) | REQ:290 |
| **試合終了時の同期に失敗があった** | **件数と理由** | REQ:263・7-5 |

**通知の宛先は「利用者または管理者」である**(REQ:851)。**B6(認可・テナント不一致)だけは利用者への通知内容が制限される**(6-5 の非開示規則)が、**管理者側のログには残す**。**非開示と黙殺は別物**である。

### 8-4. サーバーが状態を持たないこと

**サーバーはステートレス**であり、**プロセス内に試合状態を持たない**(REQ:977)。**再計算はプロセスのメモリではなく DB のイベント列を入力とする**。

**この制約は 8-1 の T4(状態遷移)と両立する**: T4 が更新するのは **DB 上の状態**であって**プロセス内のキャッシュではない**。**プロセス内に状態を置くと、複数プロセス構成で「どのプロセスが正か」が決まらず、S1(正本は DB の 1 系統のみ)が崩れる**。

### 8-5. 復帰同期と事前集計の無効化

要件書は無効化トリガーの列挙に**復帰同期**を含める(REQ:957 — 「無効化→再計算のトリガーは次のすべての変更操作を含む——**復帰同期**・プレイ修正・undo・…」)。

**同期側の責務はここまでである**: **復帰同期の完了が無効化のトリガーになる**ことを保証する。**対象範囲の決め方と無効化マトリクスそのものは候補案が持っており**(`docs/features/product-data-model-design/design.md:1350`)、**正本化は TSK-250 の領域**。**本書は「トリガーを発火させる側の契約」だけを持つ**。

**発火の条件**: **D3 が前進したこと**。件数や要求の成否ではなく **D3 の前進**を条件にすると、**B1 の全件重複(前進なし)で無駄な無効化が起きない**。

## 9. 記録権との境界表、退避と取り込み(論点 12・11)

### 9-1. 境界表の作り方(論点 12)

ハーネス設計書 6.3 は**両領域の重複帰属を明示的に認めている**:

- 同期プロトコル行: 「…**記録権世代・連番を扱うコードは「記録権」と重複帰属し得る**」(`docs/development/dev-harness-design-2026-08-07.md:353`)

**「重複帰属し得る」はレビューの掛かり方の話であって、決定主体の話ではない。** 項目に「共同」とだけ書いても、**どちらが決めるのかが決まらず、二重定義か空白のどちらかになる**。

### 9-3. 引き継ぎ照合の「確定水位」= D3(論点 12)

通常引き継ぎは「**元端末の凍結 → 最終同期の完了確認 → 権移動**の順で行われ、(**保持端末・世代・確定水位**)の照合を伴う**アトミックな操作**として成立する。**照合に失敗した(古い状態からの)引き継ぎ要求は失敗する**」(REQ:303)。

**この「確定水位」は D3(prefix 水位)である。** 同期側はこの接続だけを保証する:

| 照合項目 | 同期側が提供するもの |
| --- | --- |
| 保持端末 | — (記録権側) |
| 世代 | — (記録権側。**D4**) |
| **確定水位** | **当該 (試合, D4) の D3** |

**「最終同期の完了確認」= D3 が元端末の最後の D1 に追いついていること**である。**追いついていなければ通常引き継ぎは成立しない** — 未確定のイベントを残したまま権を移すと、それらが次の世代で **B4(旧記録権世代)**になり退避へ回る。

**緊急引き継ぎはこの確認を経ない**(元端末が断中・故障・応答不能のため)。だからこそ「**元端末の未送信記録は自動では取り込まれない**」旨の明示的な警告と確認が要求され(REQ:304)、**未確定分は退避経路へ回る**(REQ:305)。**同時に複数の緊急引き継ぎ要求があった場合、後発は失敗する**(世代が二重に進まない)。

### 9-4. 退避と取り込み(論点 11)

#### 退避の位置づけ

| # | 規則 | 典拠 |
| --- | --- | --- |
| **E1** | 旧世代のイベントは**適用されないが破棄されず退避される** | REQ:305 |
| **E2** | 退避イベントは**閲覧・書き出しができる**(**Must**)。「**黙って捨てないこと自体が NFR-015 の要求**」 | REQ:306 |
| **E3** | 取り込みは **Should**。**操作者が挿入位置を指定**した上で、**現行世代の連番として採番し直し**、**下流再計算を伴う明示的な操作**として行う | REQ:307 |
| **E4** | **旧世代の連番のまま挿入しない。末尾への機械的な追加はしない** — 「退避イベントは緊急引き継ぎ以前の実プレイであり、**末尾に置くと得点・アウト・走者の再現に失敗する**」 | REQ:307 |
| **E5** | 取り込み結果は**差分プレビューで確認できる** | REQ:307 |

#### 取り込みの手順

1. **操作者が挿入位置を指定する**(例:「◯回×アウトの後」に相当するプレイ番号)
2. **D2 を指定位置の隙間に採番する**(5-3)
3. **D1 を現行世代で採番し直す**(REQ:307)
4. **新しい D5 を付ける**(4-5 — 原本の D5 を流用すると重複と判定されて取り込みが無視される)
5. **下流再計算**を行い、**差分プレビュー**を出す(REQ:307)
6. **原本は退避側に残る**(E1)。取り込みは**複製であって移動ではない**

**通常の任意位置挿入(5-3)との違い**は **3 と 6** である。通常の挿入は **D1 を末尾に採番するだけで振り直さず**、原本という概念も無い。**この 2 つを同じ経路にしない**。

#### 保持期間と破棄可否(論点 11)

| 対象 | 保持期間 | 破棄 | 典拠 |
| --- | --- | --- | --- |
| **同期済みイベント(端末内)** | **24 時間** | **自動破棄**。破棄トリガの実装は (B) 論点 25 | REQ:292 |
| **退避イベント(サーバー)** | **要件書に定めがない** | **本書は「破棄しない」を既定とする** | E1・E2 |

**退避イベントの保持期間は要件書が定めていない。** E2 が閲覧・書き出しを **Must** とし、その理由を「**黙って捨てないこと自体が NFR-015 の要求**」としている以上、**期限を切って自動破棄する設計は要求と衝突する**。したがって**本書は「破棄しない」を既定とする**。

**ただし無期限保持は保存容量の問題を持つ**(6.1 のデータ保持方針は種別ごとに期間を定めている — `docs/requirements/requirements-pitchlog-2026-07-22.md:952` 近傍)。**退避イベントの保持期間は要件書に行が無いため、要件の確認事項として 11 節の申し送りへ送る**。**本書が勝手に期限を決めない**。

### 9-5. 復元後の全世代フェンスと 24 時間保持分の回収

NFR-009 は「**復元後の手順**」として、「バックアップからの復元 = サーバーが過去に戻るため、**復元後は全試合の記録権世代を無効化(フェンス)して新世代を発行**し、**端末の同期済み 24 時間保持分(FR-012)の回収・突合を復旧手順に含める**(端末側が「同期済み」と認識しているイベントがサーバーから消えている「**世界線ズレ**」の解消)」と定める(`docs/requirements/requirements-pitchlog-2026-07-22.md:821`)。

**同期側から見た接続**:

| 段階 | 同期側で起きること |
| --- | --- |
| **フェンス** | **全試合の D4 が更新される**。以後、旧世代の端末からのイベントは **B4(旧記録権世代)**になる(6-3・REQ:308) |
| **回収** | 端末の**同期済み(24 時間保持)**分が回収対象。**7-2 の「同期済み」は破棄されるまで再送の出所になる**ため、この保持が回収を可能にしている |
| **突合** | 回収したイベントを**新世代へ取り込む**。経路は **9-4 の取り込み**(挿入位置の指定 → 現行世代で再採番 → 下流再計算) |

**24 時間の保持が「DB 障害時の再送出所」として定められている**(REQ:292)理由がここで効く。**復元は 24 時間以内に行われる前提**であり、**それを超えると回収できる範囲が狭まる**。**この前提が運用上成立するかは運用手順側の問題**なので、**11 節の申し送りで NFR-009 の復旧手順へ接続する**。

**フェンス後に端末が同期を試みると B4 になる** — このとき **6-3 の B4 の通知**(記録権が移っていること・退避されたこと・破棄されていないこと)が出る。**復元直後は全端末がこの状態になる**ため、**通知の文面が「他の人に権を取られた」と読めてはならない**。**通知の文面は本書の範囲外**だが、**B4 が復元起因でも発生することを 11 節で申し送る**。

### 10-2. NFR-019(c)(d) の観点

要件書は CI に含めるテストとして **(c) 主要分岐の E2E テスト**と **(d) 同期プロトコルの故障系テスト**を挙げる(REQ:909)。

- **(c)**: 「タイブレーク・コールド・引き分け・終了後修正→再集計・交代フルセット・**通信断→復帰同期**・**記録権の通常/緊急引き継ぎと退避経路**」
- **(d)**: 「**墓標/改訂の適用**・**サーバー適用の原子性(クラッシュ注入)**・**複数タブの単一書き手競合**」

#### (c) と (d) の分担

| | (c) 主要分岐の E2E | (d) 同期プロトコルの故障系 |
| --- | --- | --- |
| **何を確かめるか** | **正常な経路が通ること**。断が起きても復帰して確定に至る | **故障が起きたときに不変条件が壊れないこと** |
| **本書のどこに対応するか** | 7-2 の状態遷移・9-3 の引き継ぎ・9-4 の取り込み | 6-1 の D3 の規則・8-1 の原子性・7-4 の Q2 |
| **失敗の見え方** | **経路が完走しない** | **完走するが不変条件が壊れている**(二重適用・水位の後退・D1 の衝突) |

**(d) は「壊れないこと」を確かめるので、故障を注入しないと何も検出しない。** これが (c) と分ける理由である。

#### (d) の 3 観点 — 実行可能なシナリオ

| 観点 | シナリオ | 期待する不変条件 |
| --- | --- | --- |
| **墓標の適用** | `D1=1..7` を送る。`D1=5` をサーバーが内容起因で拒否する(B3)。操作者が `D1=5` の**墓標**を送る | **D3 が 4 → 7 まで前進する**(墓標を越えて前進 — 6-1 の R3)。`D1=5` の位置には**プレイが投影されない**(5-5 の #8)。**破棄の事実が記録され、後続への補正が通知される**(REQ:290) |
| **改訂の適用** | 同上で `D1=5` を拒否させ、**同一 D1・新しい D5** の改訂版を送る | **旧版が置換される**。**D3 は 5 → 7 へ前進**する。**D2 は元の位置を保つ**(5-5 の #9)ため、**プレイの並びが変わらない** |
| **原子性(クラッシュ注入)** | `D1=5` の適用中、**当該経路の T 要素の各境界でプロセスを落とす**(D1 付きイベントなら T1〜T4、D2 の採番を伴うなら T5 も)。再起動後にクライアントが再送する | **どの注入点でも、T1〜T5 が全部確定しているか全部確定していないかのどちらか**(REQ:287・8-1)。再送で**二重適用されない**(D5 で吸収)。**D3 が後退しない**(6-1 の R4) |
| **D2 の再採番の原子性** | **隙間が尽きた位置へ挿入**し、**局所再採番(T5)と新イベント保存(T2)の境界でプロセスを落とす** | 「**既存イベントだけが動いた**」「**D2 が重複した**」状態が観測されない(起草レビュー 2 周目 P1) |
| **複数タブの単一書き手** | 同一ブラウザで**同じ試合の記録画面を 2 タブ開く**。両方から確定操作を行う | **記録できるのは 1 タブのみ**(7-4 の Q2-a)。**D1 の重複が発生しない**。**読み取り専用になったタブにはその旨と記録中タブへの導線が示される**(Q2-b) |
| **退避と B4 応答の原子性** | 旧世代の端末からイベントを送る。**退避の保存と B4 の応答の境界でプロセスを落とす** | **「退避が保存されている」か「B4 を返していない」かのどちらか**(9-2)。**B4 を返したのに退避が無い状態が観測されない**(REQ:305) |

**シナリオを「実行可能」にするために必要なもの**: **クラッシュ注入点(当該経路の T 要素の境界)がテストから指定できること**。これは**実装側の設計制約**であり、**8-1 のトランザクション境界を実装が任意に変えられると注入点が定義できない**。**11 節のデータモデル影響差分へ送る**。

### 10-3. 正解ベクタの発効ゲートは (d) に及ばない

**NFR-018 は正解ベクタについて「完成をもって発効する」という強い規律を持つ**(REQ:896 — 「**完成をもって正解ベクタとして発効する。完成前に NFR-019(a) を合格と判定してはならない**」)。

**この発効ゲートは (d) の故障系テスト資産には掛からない。** 同条は対象を**明示的に限定している**:

> **発効ゲートの対象は対象計算に紐づくベクタ契約であり、対象計算に紐づかない参照データ契約〔付録B-6 領域シード〕は対象外**(REQ:896 — 逐語)

**(d) の故障系テストは「対象計算」ではない。** 対象計算は NFR-018 が列挙する**ドメイン計算**(状況判定・終了判定・座標変換・捕球選手推定・成績集計の前処理など)であり、**同期プロトコルの故障時の不変条件はそこに含まれない**。

**したがって本書は「発効規則が要件書に存在しない」とは書かない。** 正しくは「**発効ゲートは存在するが、その対象は対象計算に紐づくベクタ契約に限られており、(d) には及ばない**」である。

**本書は (d) のテスト資産の版付け・置き場・契約を定める。** 具体的な固定方法は 11 節の U-6 で受け取り先を名指しする。


## 11. 性能の構造表 + データモデル影響差分 + 未解決・申し送り

### 11-1. 性能の構造表

**文書だけで p95 の達成は証明できない。** 本節が示すのは「**設計が構造的に妨げていないこと**」までであり、「**実測で達成すること**」とは別物である。**両者を混同しない**。

#### 同期のクリティカルパス

**入力応答(NFR-001)のクリティカルパスに、サーバー往復は含まれない。** 要件書は「確定操作 → 次の球の入力開始可能まで p95 で 1 秒以内(**クライアント計算・サーバー往復を待たない**)」と定める(REQ:777)。

| 段階 | 入力を待たせるか | I/O | 根拠 |
| --- | --- | --- | --- |
| 状況計算(クライアント側の暫定) | **待たせる** | なし(メモリ) | 断中も同じ経路(REQ:167) |
| **キューへの追記 + D1 の採番** | **待たせる** | **端末内の永続ストレージへ 1 回**(**不可分**) | REQ:288。**ここだけが同期側でクリティカルパスに乗る** |
| 画面の更新 | **待たせる** | なし | REQ:226(undo は即時に 1 つ前へ戻る) |
| 送信・ACK・サーバー再計算 | **待たせない** | ネットワーク + DB | REQ:777(往復を待たない)・REQ:782(同期は非同期・入力を妨げない) |

**構造的に妨げていないと言える根拠**: **同期側が入力応答に追加する待ち時間は「端末内キューへの不可分な 1 回の永続化処理」だけ**である。**送信は待たせない**(REQ:782 が「非同期・入力を妨げない」と明示)。

**p95 1 秒は端末内書き込みだけの話ではない。** 上表のとおり**状況計算と画面更新も待ち時間に含まれる**ので、**実測は「計算 + 永続化 + 描画」の総時間で行う**(起草レビュー 1 周目 P2)。**同期側が言えるのは「1 回の永続化処理しか足していない」ことまで**である。

**「不可分な 1 回」は論理的な永続化処理の回数**であって、**物理 I/O が 1 回であることを意味しない**(永続ストレージ API の実装により複数回になり得る)。

#### 実測の条件と受け取り先

**NFR-001・NFR-002 の p95 は、NFR-005 が定める前提負荷で測る。** 「性能目標(NFR-001〜004)の前提負荷は『**1 テナントあたり同時 3 試合(各試合 = 入力 1 端末 + 閲覧 10 端末)+ 分析利用の並行**』とし、**15 万プレイ蓄積まで維持する**」(REQ:797)。

**単一試合・空のデータベースで測っても達成にならない。**

| 指標 | 目標 | 前提負荷 | 受け取り先 |
| --- | --- | --- | --- |
| **NFR-001** 確定 → 次の入力可能 | **p95 1 秒**(REQ:777) | REQ:797 | 実装計画 + 実戦リハーサル(REQ:1002) |
| **NFR-002** サーバー同期 | **p95 5 秒**(REQ:782) | REQ:797 | 同上 |
| **NFR-006** 閲覧端末への反映 | **10 秒以内 — Should**(REQ:803) | REQ:797 | 実装計画。**方式は (B) 論点 22** |

**NFR-006 の Must は反映時間ではない。** 同条の優先度は「**Should(鮮度表示は Must)**」であり(REQ:802)、**Must なのは鮮度表示** — 「**閲覧画面には最終反映時刻を表示し、入力端末がオフラインの間はその旨を明示する**」(REQ:803)である。**10 秒を外しても鮮度表示は外せない**。

### 11-3. 要件の全数割り当て

**語彙による走査だけでは網羅を保証できない**(**NFR-001 は「サーバー往復を待たない」という直接の同期制約だが同期語彙に 1 つも当たらない**)。したがって**全数割り当て**で担保する。

**抽出規則**: 要件書を **FR/NFR 65 条**と、**その外側の Markdown 要素 375 単位**(見出し / 段落 / 箇条書き / 番号付き / 表のデータ行 / 入れ子項目)に分け、**規範性を事前判定せず全件**に安定 ID(`R<行番号>`)を付ける。

| 区分 | 件数 | 意味 |
| --- | --- | --- |
| **同期側で決める** | **27** | 本書のどこかが決定を書いている |
| **境界として参照** | **23** | 決めないが規則の入力になる |
| **対象外** | **313** | 本書が決定を書かない |
| **非規範** | **77** | 見出し単体・変更履歴表の行など、規範を持たない単位 |
| **合計** | **440** | **抽出 ID 集合 = 割り当て ID 集合 / 重複 0 / 未割り当て 0**(機械検算 — 12 節) |
