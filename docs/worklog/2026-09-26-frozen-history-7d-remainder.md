## 実装の敵対レビュー 1 周目 — 新種 2 件・P0 0 件・P1 2 件

### P1-1 記録が実際の HEAD と一致しない(**本タスクのテーマが自分に返ってきた**)

**`#83` の記録の `change.after` が、ステップ 5 の中途状態で凍結されていた。**

```
記録が指す検査器: 119d04e2...
実体(HEAD):      8607fa7c...
```

**原因**: ステップ 5 で、**検査器を編集し終える前に記録を生成し、その後さらに編集した**。検査器の sha256 は `a58a5383`(ステップ 5)以降ずっと `8607fa7c` で一貫しており、ステップ 6・7 は触っていない。

**なぜ気づかなかったか**: **不変量モードは `after.external_snapshots` を実ファイルと突き合わせない。** **ローカルの検査器は exit 0 を返していた。** **PR 受理モード(= CI)でのみ落ちる。**

**委任元がステップ 5 で確認した 3 つ(本番検査器 exit 0 / 9 件すべて参照されている / 孤児 29 件のまま)はどれも真であり、それでも記録は間違っていた。** **見ていない面があった。**

### 委任元の切り分けの誤り(**レビューの正しい指摘を誤った実測で覆した**)

レビューは「**7 資産の `after.asset_snapshots` もすべて不一致**」と指摘した。**委任元はこれを「自己参照ゆえの仕様」と判断して却下し、委任先へ「資産側を触るな」と指示した。** **誤りだった。**

**誤りの原因**: 資産 snapshot を **`sha256(資産ファイルの生バイト)`** と比べていた。**正しくは `sha256(frozen_projection_content(資産, 外部ファイルの実内容))`** である(`_asset_projection_snapshots`)。**射影には外部ファイルの中身が入るので、中途版の検査器が 7 資産すべての射影に焼き込まれていた。**

**TSK-440 の記録と比べて「440 も資産側は不一致だから仕様」と結論したが、440 についても同じ誤った比較をしていた。** **2 つの誤った観測が一致したので、正しいと思い込んだ。**

**委任先が実測で反証して停止・報告し、委任元が確かめ直して撤回した。** **全ステップの委任プロンプトへ「設計と実物が食い違ったら、勝手に実装を実物へ合わせず、報告して止まれ」を入れていたことが、委任元自身の誤指示を止めた。**

**TSK-440 が同じ構造を報告している**(委任先が実測で押し返し、指示を撤回した)。**指示が誤っていても機械は従うので、「止まってよい」と明示的に許可しておくことに意味がある。**

## 決定

### 射程 — 退去(削除)機構を外した(人間の判断 2026-09-26)

**敵対レビュー 2 周目の P0 を原典で確認した。** `check_tenant_boundary_bypass.py` の `load_contract` は **`FROZEN_BASELINE_ASSETS` の 7 資産すべてを無条件に `_read_json` する必須入力**である。**資産ファイルを削除すると、退去の記録を検査する前にここで落ちる。**

**したがって「非 authority 資産なら削除できる」は成立しない — 7 資産のどれ 1 つも削除できない。** `load_contract` を一律に条件付きへ変えると、検査入力を退去記録だけで外せる経路ができる(空洞化)。**「実行不能か空洞化の二択」**であり、7D の残りという射程では安全に閉じられない。

**448 が実装するのは D4(履歴アーカイブの規律)・D5(実装の隔離)だけ。** **退去の仕様は [design.md](../features/frozen-history-7d-remainder/design.md) 3 節に契約として書き、TSK-461(新設提案)へ送る。**
