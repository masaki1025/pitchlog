### 訂正 1: **レビューの是正案 B-1 をそのまま条文化するとリポジトリが凍結する**

> **移行状態はリポジトリ全体の状態であって、PR ごとの許可ではありません。** (b)③ は「宣言集合と実在入口集合の差」で
> fail するので、**その PR が何を触ったかと無関係に fail します**。未宣言の入口が 1 つでも残っている限り、
> **文書 PR でも ORM の PR でも赤くなる** — これが 2 周目 P0-1 の「三すくみ」の実体です。

→ 「移行状態を利用する PR」= **事実上すべての PR**。全 PR に `未達数＋債務数` の厳密減少を課すと
**TSK-343 の ORM 作業も本タスクの文書 PR も TSK-317 の認可検証も止まる**。**paths filter でも切れない**
(失敗が PR の触った paths と無関係に起きるため)。

**代案(採用 — §4-9 論点 B の B-1')**: ①厳密減少は**段階 2 の PR にのみ**課す(段階 2 の PR は定義上
ちょうど 1 対象を登録し未達が 1 減るため空振りしない)②停滞は「時間」ではなく**「マージ本数」**で測る
(移行状態が有効なあいだのマージ累計が N 本に達し、そのあいだに `未達数＋債務数` が 1 件も減っていなければ失効)。
**日付を書かず・機械判定可能・凍結しない。** `N` の値は**人間の裁定事項**(TSK-235 側は段階 2 のタスクが
未起票のため決められないと回答)。

> 私が merge-base と言ったのは **core-guard の「他領域 byte-for-byte 不変」の文脈**からの類推でした。
> …**`bootstrapDebt` は「開始時点の集合と比べて増えていないこと」を見る**ので、**比較元は動いてはいけません**。
> merge-base は base が進むと動くので、**この用途には不適**です。

### 確認できた点

- **移行状態は段階 1 と段階 2 にまたがる**(状態ベースの定義が正しい)。

**`N` = 50 の根拠(実測)**: develop へのマージは**直近 3 週間で 1.6 本/日**
(2026-08-19〜09-10 で 37 本。通算 63 本 / 50 日)。**50 本 ≒ 1 ヶ月**。

**設計の意図**: 段階 1 のあいだは**構造的に未達も債務も減らない**ため、`N` をどう置いても
**段階 1 の途中で必ず失効する**。これは欠陥ではなく**意図した設計** — `N` は異常検知の閾値ではなく
「**どのくらいの頻度で PO に再確認を求めるか**」のパラメータであり、無期限の緩和を防ぐ本質は
期限そのものではなく「**人間が定期的に意識して延長する**」ことにある。
