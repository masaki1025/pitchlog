## 2. 何が壊れるか — 原典で確認した

### 2-1. 反対側の原理

```

**実装主体が Claude になった時点で、反対側は構造的に不在になる。**
**Claude が書いたものを Claude が見ても、原理の側が満たされない。**

### 2-2. 条文を変える経路は循環する

```

        (敵対レビュー → 人間承認)を通す

**6.3 の表(レビュー主体)を変えるには確定ゲートが要り、確定ゲートには停止中の
委任先が要る。** **循環する。**

**前例がある** — #119 で「必須チェックが構造的に満たせなくなった場合の正規の経路が、
どの正本にも無い」(台帳の対応案 (d))に突き当たり、**正本を変えず、保護設定の

## 4. master の判定 — 3 件

### 4-1. 【未確定】3-1 と 3-2 でマージ条件が食い違う

```
3-1   PR 段階の敵対レビューは 10-21 以降   → マージは 10/21 の後
3-2 (b)  代替 + 逐行確認でマージ可         → マージは今日からできる
```

**同じ山田さんの裁定だが、3-2 のほうが広い。** **どちらが後に出たものか、
master は判定できない。**

**実害の所在**: **open の 3 本(#131・#132・#137)はすべてコア領域**なので、
**(a) が適用される PR は現時点で存在しない。** 食い違うのは (b) だけで、
**3 本のマージ時期がこの 1 点で変わる。**

**【2026-10-15 07:02Z の実測 — 3-2 (b) の形で着地した】**

**#131(TSK-538・コア領域)がマージされた**(マージコミット `e2e78cfb`・squash ではない)。
**PR 段階の敵対レビューは 10/21 以降に行う**として、**マージを先に済ませている**。

```
着地した形   代替レビュー + 山田さんの逐行確認 → マージ → 10/21 以降に追認
            = 3-2 (b) そのもの
```

**したがって 3-1 と 3-2 の食い違いは、3-2 (b) を採る向きで解消した。**
**master は以後 3-2 で各タブへ案内する。**

**残る義務は追認**: **10/21 以降の敵対レビューで P0 が出たら fix PR を出す。**
**マージ済みなので、取り消しではなく前進で直すことになる。**
**追認を実施したかどうかを追跡する機構は無い** — **人の記憶に載っている。**
**この追跡の不在は台帳の候補へ対応案 (f) として記録した。**

### 4-2. 【支持】代替レビュアのモデルを変えること

**原理の側から正しい。** 設計書 :166 の「自己批准の禁止」は主体の分離を要求していて、
**同一モデルの別文脈は主体の分離になっていない。**

**実測の裏づけが両側にある。公平に両方を置く**:

```
反対材料  2026-10-15・#137 の同じ差分
         外部の敵対レビュー 1 周目 = P0 2 件(うち「2 契約の期待値を壊しても検査が通る」)
         Claude の spec-checker   = この P0 を出していない(出したのは条文の参照先誤り・軸が違う)

賛成材料  2026-10-15・#131 の直接実装分
         Claude サブエージェントの敵対レビューが P1 を 1 件検出
         取り込みで test_core_guard を自ブランチ版で解消し #133 の表明を落としていた
         (登録 PR 後始末の型の再発。実害があった)
```

**代替は「何も出さない」のではなく「軸が偏る」。** **だから軸を変える = モデルを
変えるのは、効く方向の手当てである。**

**ただし費用の制約を無視できない** — CLAUDE.md は **「Fable 5.1 は常用しない
(Max では週次上限の 50% までで消費も速い)」**と定めている。**6 日間すべての
レビューを Fable で回すと、Fable 側が先に止まる。**

**master の提案(裁定ではない)**:

```
コア領域の PR          Fable 5.1(軸を変える価値が費用に見合う)
非コア領域の PR         Opus の別文脈のサブエージェント(軸は偏るが、落ちる重大度も低い)
枠を使い切ったとき      Opus の別文脈へ落とし、その旨を PR 本文へ明記する
```

### 4-3. 【別項】台帳は #119 の (d) と分ける

```
#119 の (d)   必須チェックが構造的に満たせなくなった場合の正規の経路が、どの正本にも無い
              原因 = 検査器の規則そのものの穴(core_guard)
              解いた手 = 保護設定の一時解除

本件           レビュー主体が利用不能になったときの正規の経路が、どの正本にも無い
              原因 = 外部サービスの可用性(条文にも検査器にも穴は無い)
              解いた手 = PO の期限付き裁定
```

**原因も解き方も違うので別項が妥当。** **ただし上位型は同じ**(「ゲートを満たせなく
なったときに、正本が経路を持っていない」)**なので、相互参照を両方へ置く。**
