## 計画レビューと実装(2026-08-14〜15)

**計画レビュー(敵対)6 周で収束**。指摘 22 件を全件採用・不採用 0 件。6 周目は P0/P1 ともに 0 件で「承認可」。**PO 承認 2026-08-15**。

### P0 が 1〜4 周目に連続で出た — すべて同じ型

| 周 | P0 | 共通点 |
| --- | --- | --- |
| 1 | 台帳の**運用規則**に追記しようとした | 版繰り上げ + 確定ゲートが必要 |
| 2 | ADR 免除を**恒久的な運用規則**へ格上げしていた | 設計書 7.1-3 の改訂が必要 |
| 3 | 免除を**正本の編集経路**として使っていた | 履歴を残さず approved を書き換える |
| 4 | 3 周目の是正が**運用側の制約に逃げ**ていた | 機構で強制していない |

**本タスクは「規約と機構の差分を埋める」ものなので、差分を埋めようとするたびに規約そのものを動かしたくなる構造的な誘惑がある。** かつ 2〜4 周目は**前の周の修正が新しい違反を作った**もの(H-42 の再現)。

最終形では免除を**パス → 内容の SHA-256** に固定し、内容が変われば免除が失効して fail-closed になる。**ダイジェスト値の更新は禁止**で、正規化するなら履歴表を新設して同じ PR で免除エントリを削除する — この非対称を書かないと、次に触る人が「不一致になったから値を更新する」という**安全性が逆転する対処**をしてしまう。

### 合格条件が実効性を持たない指摘も繰り返し出た

- `grep` で「旧番号表記 0 件」→ **残すべき歴史記録の削除を誘発**(要件書の「v1.0 当時の決定範囲」・設計書の「v1.4 で旧上限を撤去した」)
- 「`## 候補` は 4 件」→ **既に 4 件あるので何もしなくても成立**
- テスト件数がステップ表に追随していない(2 箇所)
- 見出し破損検査が**自分の計画書のコードフェンスを誤検知**する

→ DoD に**実効性の 4 条件**を明示して対処した。

### 呼び出し方の誤り 1 件

`codex_run.py implement` を `review` と同じ `- `(標準入力)だけで呼んで `exit=2` になった。正しくは **`implement <plan.md> [-]`** で計画書パスが必須(ラッパーが `status: active` と `承認: 済` を機構検証するため)。
