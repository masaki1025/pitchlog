### 候補 A: `feature_status.py` の allowlist が `merge_allowed` を落とす(分類漏れ)

- **分類**: 機構の穴
- **検出日**: 2026-09-10(TSK-343 が発見・TSK-235 と TSK-317 が独立に原典追認)
- **事象**: `scripts/feature_status.py` は 2 親マージを **`merge_allowed`**(develop 取り込み)と
  **`merge_unknown`** に分類する(`:878-881`)。**`merge_unknown` を名指しで弾く専用分岐がある**

- **非対称の追加根拠**: **3 つの `unknown` 経路のうち `merge_allowed` 経由だけ `note` が付かない** —
  `:986-991` は `note="許可されないマージコミット混在"`、`:993-997` は `note="無記法の実装コミット"`、

## ステップ 16 の残余リスク記録(`[手動・外部]` 条件・申し送り先 = TSK-217)

**実機で確認した残余リスク**(2026-09-10・`tests/db/test_authz_trust_boundary.py` 1 passed)。
**隠さず、期待値として試験に持たせた。**

### 事象

**アプリ用ロール(`app_role`)自身で認証した実接続から、
`pg_catalog.set_config('app.tenant_id', <任意の値>, true)` が成功する。**
設定値は `current_setting` で読み戻せ、**その文脈で共有関数を呼ぶと当該テナントの行が返る。**

### 射程(3 文脈を実測して境界を確定した)

| # | 文脈 | 要求元テナントの付与 | 返却 |
| --- | --- | --- | --- |
| 1 | **本来の文脈**(`requester_tenant_id`) | なし | **空集合** |
| 2 | **偽装文脈**(付与あり) | あり | **対象行を exact-set で取得** |
| 3 | **偽装文脈**(付与なし・参加のみ) | なし | **空集合** |

→ **危険なのは「GUC を設定できること」ではなく「1 では届かない行が 2 では届くこと」**である。
文脈 1 を測っていなければ、**対象行がどの文脈からも返る壊れ方でも試験は green のまま**だった
(一次レビューの差し戻しで追加した — 当初は `marker` と `expected_invocation_ids` による
**構成での宣言**でしかなく、測定ではなかった)。

→ 文脈 3 により、**リスクの射程は「GUC だけで何でも取得できる」ではなく
「参加と付与を持つ別テナントへの成りすまし」**に絞られる。
**DB 層の認可(参加・付与)は迂回されていない。**迂回されているのは
**「接続主体とテナント文脈の対応」だけ**である。

### DB 層で塞げない理由

`app.tenant_id` は **GUC(実行時パラメータ)であり、接続主体との対応を DB が検証しない。**
`set_config` の実行権限はロールに紐づかず、**アプリ用ロールが自分の接続で自由に設定できる。**
これを DB 側で塞ぐには「テナント文脈を GUC ではなくロール自身から導く」設計が必要で、
**凍結資産の構成(1 アプリロール + GUC)を変えることになる**ため本タスクの射程外。

### 申し送り先: **TSK-217**

**理由**: 本計画 2 節「やらないこと」が **HTTP 経路の判定を TSK-217 の所有**と定めており、

**この残余リスクが実害になるのは「アプリの接続に任意のテナント ID を注入できる経路が
HTTP 層に存在する場合」**であり、**その判定は HTTP 層でしかできない。**

1. **アプリの実接続へ渡す `app.tenant_id` が、認証済みの主体から一意に導出されること**を
   HTTP 層で検査する(リクエストのパラメータ・ヘッダ・ボディから来ない)
2. **`set_config` を呼ぶ経路がアプリコード内で 1 箇所に限られること**を機械で検査する

   **本試験の期待値は変わらない**(「設定できてしまう」が正しいまま)。
   TSK-217 側が足すのは「**HTTP 層からは注入できない**」という別の試験である
