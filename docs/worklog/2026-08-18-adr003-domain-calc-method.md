## 調査で判明した重要事項

- **(b)② の成立は「実装」の語の解釈にかかる** — アーキテクチャ完全性検査としてなら実現可能。「同じ計算を別の書き方で再実装した任意のコード断片」の検出としては**実現不能**(プログラム同値性は決定不能)。閉域が壊れる条件も原典で確認(esbuild は非解析 import を verbatim で残す / ESLint `no-eval` は間接 eval を検出できない)
- **実現手段は制約 DSL / 宣言モデルからの生成が最も適合**(Codex 評価)。Pyodide は未圧縮で WASM 約 9MB + 標準ライブラリ約 2.4MB + JS 約 1MB の固定費がテーブル駆動の状態遷移に対して過大。**状態テーブルを両言語の手書き interpreter で読むだけだと interpreter が二実装と見なされる**
- **旧システムに「複数実装が同じ値を返すことを固定する機構」は存在しない** — 実在したのは構造の実装横断固定(SQLite DDL と PG DDL の突合)・定義の固定(語彙・分母)・単一実装内のリプレイ恒等式の 3 種
- **ADR が触ると 2 ゲート化する境界を特定** — 共有実装コード / 生成物を `contracts/` に置くと設計書 4 章の限定文と衝突する
- **要件側の条文上のギャップ 2 件** — NFR-018(b) の機械検査が 8 章 DoD② のリリース判定の列挙に無い / (β) の担保を CI 必須とする明文が無い

### 論点が動いた要所

- **(b)② の実現不能の確定(1・4 周目)** — 計画レビュー 1 周目 P0 で方針が覆った経緯(要件書:867 の括弧書きが名指しする失敗モードそのものを見逃す検査になる)を受け、ADR 側でも「アーキテクチャ完全性検査で穴を受容する」案を採らず、**v2.1 の (b)② は実現不能**と結論した
- **3 つの防御案がレビューで順に破られた** — ①残余の明示 = 透明性であって防御ではない ②結果型の構築点の限定 = object spread で brand を持ち回れる・`any` 流入・import-linter は構築点を見ない ③sink 閉包 = 正規の結果 A・B のどちらを出すかを手書きの条件で選ぶ制御フローを止められない。**いずれも任意コードの意味判定に帰着する**
- **目的の再定義(人間裁定)** — 「再実装が存在しないことの証明」から「**差分が必ず検出されること**」へ。レビューはこれを**正当な再定義**と認め、以降は「必ず」の強さ(保証の対象・入力範囲・強さ・範囲外)を閉じる作業になった
- **経路一致検査の新設(8 周目 P0)** — 3 層は**製品経路が正本以外の実装を使っていても、その別実装が期待値と一致する限り全層を通過し得る**。(b)③ の構成検査が本来これを構成的に排除するが、解析の及ばない経路には空振りするため、**値の面で直接突き合わせる層**を独立した合否条件として追加した
- **FIP の非負矛盾(9 周目)** — 新設した不変条件「集計は非負」が、付録A の FIP 定義(3 回 9 奪三振・被本塁打 0 なら −2.90)を拒否していた。指標ごとの成立条件へ分解した
- **undo の履歴(15〜21 周目)** — 深さ 1 → 深さ 2 → **スタック(各要素が種別と差分)**へ。最終的に**履歴文脈は有限にならない対象**と整理し、境界値・等価分割で保証範囲を閉じた。**`D` は検査の保証範囲の上限であって実行時の上限ではない**(FR-006 の連鎖はスタックが空になるまで続く)
- **表示名の正本境界(16〜21 周目)** — 写像テーブルへ焼き込む案は 4.0-3 の保全規律(改名は ID 経由で全履歴表示へ反映)と衝突。**語彙スナップショットを対象計算の入力に含める**ことで、改名を入力の差し替えとして反映し、FR-022 の結果表示名を完成した表示値のまま比較面に載せられるようにした
