### ステップ 1 の是正: 要件書への行番号引用が自分の編集で全部 1 行ずれた

要件書の変更履歴表は**古い順**なので、起案行は**表の末尾**に入る。その結果
**以降の全行が +1 ずれた**。実測: `NFR-018` の正解ベクタ条項 `:915` → **`:916`** /
`NFR-010` の測定方法 `:846` → **`:847`** / 8 章のリリース判定基準 2 `:1035` → **`:1036`**。

**自分がステップ 1 で書いた 4 箇所の引用が、書いた直後に古くなっていた**
(`docs/README.md` の要件書行 / 要件書の起案行 2 箇所 / `data-model.md` の起案行)。
**行番号を条項名 + 逐語の参照へ置き換えて是正した** — `NFR-018` の**正解ベクタ**条項 /
`NFR-010` の**測定方法**条項(逐語「API直叩き含む」)。

**これは本改訂の全体に効く制約である。** 本ゲートは要件書と `data-model.md` を
同時に改訂するので、**以後も行番号は編集のたびにずれる**。したがって
**正本の本文へ書く要件書参照には行番号を使わない**(条項名 + 逐語 + アンカー)。
行番号は worklog・research のような**日付つきの記録**にだけ残す。
`data-model.md` が v0.1 で**行番号引用 296 件を安定 ID 参照へ貼り替えた**のと同じ理由である。

**既存の feature 文書・worklog の要件書行番号引用も現時点で 1 ずれている**が、
**過去記録は書き換えない**(TSK-348 の PO 裁定)。**本 feature の
`research.md` は本ゲートの依頼文が参照する生きた文書**なので、
**ステップ 6 の ADR 本文で典拠を引くときに条項名 + 逐語で引き直す**。

### ステップ 2: 12-4 のゲート表に裁定 A・B を条文化する

ゲート表へ **2 行を新設し 3 行を改訂**した。

| 行 | 何をしたか |
| --- | --- |
| **適用単位**(新設) | 裁定 A。**当該 PR が開く経路ごとに判定する**。**開いていない経路を理由に不合格と判定しない** |
| **通過条件** | ② の末尾へ**括弧参照**を足した(「②の green は本表の「適用単位」の範囲で判定する」) |
| **最低要求 4 件と測定経路の関係**(新設) | **4 件はすべて DB ロール・関数 ACL・`search_path` への要求で HTTP 経路への要求を 1 件も含まない**。**測定経路の充足条件は 4 件に足す別の要求**である |
| **測定経路** | 裁定 B の**充足条件**を追記。**HTTP 経路を開かない PR には空の要求として掛かる** |
| **判定の記録** | **どの経路について判定したか**を記録項目へ足した |

**「判定」と「成立」を別の語で使い分けた**。**判定** = 本ゲートを通す/通さないを決める行為(**PR ごと**)。
**成立** = `NFR-019(b)` の網羅が完成した状態。**網羅がいつ成立していなければならないかは
要件書 8 章のリリース判定基準 2 が定める**と書き、**本節では判定時点を新設しなかった**。
`NFR-021` はこの 2 語の混同で `P0` を 2 回踏んでいる(台帳 `H-79`)。

**最低要求 4 件の文言は 1 文字も変えていない**(`git diff` で当該行が差分に出ないことで確認)。
**12-7 (1) が実機確定タスクへの要求として同じ 4 件を列挙している**ためで、実測すると
**両者の差は 12-4 側の ② が「越境関数」・12-7 側が「関数」の 1 語だけ**である(既存の差・本改訂では触らない)。

**計画の 4 項目に対し「判定の記録」行の改訂を 1 件足した**。適用単位を経路ごとにした以上、
**記録に経路が残らないと何を判定したのかが後から分からない**ためで、裁定 A の直接の帰結である。
**射程の追加としてここに記録する**。

### ステップ 3: 「経路」と「経路を開く」を 12-4 で定義する

**12-4 へ「経路の定義」の項を新設**し(non-serving 宣言より前 — **定義してから使う**)、
**1-1 の定義の所在表へ 1 行足した**。

- **経路** = **製品の外からの要求が DB のデータへ到達する、識別子を持った 1 本の入口**。
  **識別子の正は `contracts/authz/http-route-matrix.json` の `route_id`**
- **「開く」の述語**は **3 条件の同時成立**(入口が存在する / 外から到達できる / DB のデータを読むか書く)
  の **閉から開への遷移**として定義した
- **境界例を 6 件表にした**(読み取りのみ = 開く / 内部経路 = 開かない / バッチ = 開かないが最低要求 4 件は掛かる /
  ハンドラだけで未登録 = 開かない / `/health` のように DB へ到達しない = 開かない / 既存経路の変更 = 開かない)

**書きかけを実測で潰した 1 件**: 最初 `route_id` の書式を **`ROUTE:FR-nnn` と
`ROUTE:SHARED:...` の 2 系統と書いた**。実測すると **49 件中 12 件が
`ROUTE:CONTROL:*` / `ROUTE:MANAGEMENT:*`** で、**列挙が最初から不完全だった**。
**列挙をやめて「集合も体系も同ファイルが正・本節は列挙しない」へ書き換え**、
**書式は網羅でない例示として 4 件**だけ残した(4 件はいずれも同ファイルに実在することを確認済み)。
**台帳が繰り返し記録している「母集団を人が列挙する検査は射程が動くと黙って古くなる」型**を、
**書いている最中に自分で踏んだ**ということである。

**射程の境界**: **機械判定(CI での検出)は送る**(ADR-004 の射程宣言・ステップ 6 で実 ID)。
**意味定義は本改訂で置いた** — 所在を指すだけで終わらせない(計画レビュー `P0-2`)。
**同ファイルに識別子が無い入口を開く PR は同一 PR で `route_id` を与える**という要求を 1 つ置いた。
**識別子が無いと「どの経路について判定したか」が記録できず適用単位が定まらない**ためである。
