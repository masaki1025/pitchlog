## 計画レビューの経過

- **1 周目(sol xhigh)= 否決**。P0 9 件・P1 12 件。全件を採用または人間裁定で処置し、25 → 30 ステップへ再構成した。
  - 最も重い発見: `scripts/check_design_propagation.py:432`-`:573` は **欠陥 ID ごとの手書き分岐**で機械検出しており、
    JSON の `invariant` を汎用に解釈する機構が無い(Claude が原典で確認)。「機械検査に全部載せる」は
    77 件分の判定を手書きするか DSL を作るかの規模で、**当初の見積もりが実態より小さかった**
  - 自分の検算で **`DM-SY-C08` の割当漏れ**を 1 件発見し、ステップ 11 へ追加した
- **2 周目(sol xhigh)= 否決**。P0 8 件・P1 6 件。**指摘の多くは 1 周目の是正が生んだ新しい欠陥**:
  - WAIT 台帳を作った → `WAIT-03`・`WAIT-05`・`WAIT-08` の所有ステップが無い(ゲートを開始できない)
  - FORB 台帳を作った → **`FORB-01` と AUTH 実装範囲が矛盾**。候補案 8-2-B の管理関数クラス (c) に
    「**退避イベントの取り込み(挿入位置指定)**」が含まれており(Claude が原典で確認)、
    これを DDL 化すると同期正本が TSK-267 へ送った射程外構造を作ることになる
  - AUTH 対応表を作った → **AUTH 主張の母集合が無い**ので、主張を落とせば「テストの無い主張 0 件」が green になる
  - 新規: **ORM・ドライバの具体値が計画で固定されていない**(ステップ 27 の実装者がアーキテクチャを決める構造)
- **2 周連続で「是正起因の P0」が増えた**。これは前タスク(TSK-248)が 3 周続けて打ち切った状態と同型であり、
  計画へ入れた停止条件が実際に発火した形。**射程の切り出しを人間へ諮り、裁定を得た**(2026-08-31)
- **3 周目(sol xhigh)= 否決**(P0 3・P1 3)。**ただし「さらにタスクを切る必要はない」**と明示された —
  残る指摘は**受け渡し資産の形式**に集中しており、切り出しの境界そのものは妥当と判定された
  - P0: **B・C の成果が機械可読で固定されていない**(スキーマ版・安定 ID・共通正規化 ID・元 commit・
    blob digest)/ **入力主張母集合に B・C 由来の物理関係を含めていない**(後段で持ち込むと母集合を壊す)/
    **`AUTH-*` の exact-set は「B を正確に転記した」ことしか証明しない** — B が要件を 1 件落として
    カタログ・DDL・テストを同じ欠落状態で作れば、本タスクは検出できずそのまま正本化してしまう
  - **設計書 5.1 の版繰り上げを不採用とした件は「欠陥は残らない」と明示された** —
    ハーネス自身が「版番号では内容を一意に識別できない」ため blob SHA で拘束すると定めており
    (設計書 `:657`)、固定した 3 値と 5.1 差分を敵対レビュー・人間承認へ含める限り未検証成果物は生じない
  - 判定者依存が残るのはステップ 16・17・23 と指摘され、**digest 照合と不採用構成表との突合**へ置き換えた

- **4 周目(sol xhigh)= 未収束だが新規 P0 は 0 件**(P1 3 件)。いずれも「機械判定へ落とす最後の接続」:

  発火しない**(負例を 7 件の個別ファイル名で固定。**AUTH–FORB 衝突の負例が抜けていた**のを 7 件目として追加)/
  **C の 88 列 JSON に共通正規化 ID が無い**(B にだけ要求していて非対称。無いと TSK-250 側が安定 ID から
  物理要素 ID を補うことになり「写像のみ・再解釈しない」を機械保証できない)
- **5 周目(sol xhigh)= 収束**。新規 P0 0・P1 0・P2 なし。
