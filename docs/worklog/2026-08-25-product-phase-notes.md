## 論点(次タスクで決めること)

### 論点 A: Phase の切り方

要件書のブロックをそのまま Phase にするか、依存順に組み替えるか。

**検討材料**:
- **ブロック 7(認証・マルチテナント)は他の全機能の前提**。テナント分離を後付けすると FR-034 の所有権制御を全経路へ適用し直すことになる(H-79 の大規模版)
- **ブロック 1 は 15 件でコア領域を 3 つ含む**。1 Phase としては大きい。同期プロトコル(FR-012)・記録権(FR-013)は互いに依存し、状況計算(FR-003/005/040)はクライアント/サーバー一致が要る(NFR-018・ADR-003)
- ブロック 3(リアルタイム成績)は状況計算に依存し、ブロック 4・5 は 3 に依存する
- **ブロック 8 のデータ移行(FR-038)は旧システムの 88 列が入力**。移行先スキーマが確定してからでないと着手できない

### 論点 B: 1 タスクの粒度

現行の規約は「**1 タスク = 1 成果物 ≒ 1 PR**」「実装は**ステップ単位**で 1 委任 = 1 ステップ = 1 コミット」。

FR 1 件 = 1 タスクだと 42 タスク。ブロック単位だと 8 タスクだが、ブロック 1 は 15 件で 1 PR に収まらない。**中間の単位**(機能群 / 画面 / データモデルの単位)を決める必要がある。

### 論点 C: 確定ゲートの打ち切り基準(台帳 H-68)

本タスクで、設計書のゲート **6・7 周目は「私が変更履歴へ書き足したメタ主張の正確性」に終始**した。最終的に主張自体を削除して輪を断った。

**H-68(閉じた輪)の判定を、周回数や指摘の性質でどう機械化するか**は未定。設計書 v1.8 のゲートでも「4 周目に閉じた輪に入ったと判定して以後は範囲を狭める方向に限定した」前例がある(**判定は人間の裁量**)。

### 論点 D: 前提となる設計作業

製品実装の前に、以下が済んでいる必要がある(いずれも既に着手済みまたは approved):

| 前提 | 状態(2026-08-25 実測) |
| --- | --- |
| **ADR-003**(ドメイン計算の実現方式と契約化) | **approved** |
| **製品データモデル設計** | 計画は**承認済み**(2026-08-21・山田正輝)・`status: in-review`(**PR 段階**) |
| **`contracts/` のゴールデンベクタ**(クライアント/サーバー一致の正 — NFR-018) | **雛形段階**。`README.md` と `display_geometry_263_v1.json` のみ |
| **`.claude/core-areas.json` の `paths`** | **全 5 領域が空**(実測。台帳 H-12) |

**論点 D で最も重いのは `core-areas.json` の空**である。

- `paths` が空だと **`core_guard` が発火しない**。つまり 6.3 が定めた「コア領域 PR は人間の逐行確認を必須とする」という統制が、**機構としては働かない**
- しかし**製品コードが存在しないため、いま埋めることもできない**(パスが無い)
- したがって **製品実装の最初の PR は、コア領域の統制が空回りしている状態で作られる**。ブロック 1(同期プロトコル・記録権・状況計算)や ブロック 7(テナント分離)から始めると、**最もリスクの高い領域を統制なしで書く**ことになる

**この順序問題は次タスクで必ず扱うこと。** 選択肢としては、①最初に統制の効かない小さな領域から始めて `core-areas.json` を埋める ②コア領域に着手する PR で同時に `paths` を埋める(ただし同一 PR 内では自身の検査を無効化できる — 設計書 10.2 の循環参照と同型)③別途 paths だけを先に定義する、等が考えられる。**いずれも本メモでは決めない。**
