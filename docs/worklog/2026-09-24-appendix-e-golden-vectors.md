第3アウトと得点が同じプレイで起きたとき、得点の可否は**本塁到達が第3アウト成立より
前だったか**で決まる。これは**プレイ結果からは一意に推定できない現場の観測**であり、
次のように決めた:

- **記録者が生還候補走者ごとに入力する**(`home-before-third-out` / `not-before-third-out`)
- **自動推定しない。既定値も置かない**
- **必要な走者の入力が 1 人分でも欠けていればプレイを確定できない**(FR-003 の受け入れ基準)

**根拠**: 既定値を置くと、未観測の前後関係から得点と打点を黙って決めてしまう。
記録の正確性を優先した。

**PO に見てほしい点**: **最頻の操作経路(毎球入力)に確定のブロッカーが 1 つ増える**。
発生頻度は低い(第3アウトと生還が同一プレイ、かつ `OUT3-01`〜`03` の例外に当たらない場合のみ)が、
**その場面で入力を止める**設計になっている。運用上許容できるかは人間の判断。

## 反映 9 周目 — 線の決定元を宣言へ一元化した

### 線の判定規則(`freezeBaseline.scope.selectionRule`)

**凍結基準に入るのは、次をすべて満たす比較である**:
**左辺が descriptor の JSON 値に由来** / **演算子が等値・非等値・所属・部分集合のいずれか** /
**右辺が検査器のソースリテラルまたはモジュール定数**。
**これらは実行時に宣言から読み込む形でなければならない。**

**線の外に置くものは 7 つの役割で列挙した** —
ナビゲーション用のメンバ名 / 汎用バリデータが使う JSON Schema 語彙 /
識別子・書式の文法 / パス・ファイル名の文法 / 実行時の型・制御番兵 /
現在の資産値だけから導く関係 / 診断文。

### `sourceLiteralAudit` — 検査器のリテラルを全件宣言する

**`scripts/state_transition_freeze.py` が `ast` で 4 つの検査器ソースを実際に構文解析し、
文字列リテラルを抽出して、資産側の役割別 allowlist と exact-set で突合する。**

**作成者が独立に変異させて確認した。** 宣言に無いリテラル比較を検査器へ密輸したところ:

```
ERROR: 凍結基準受理履歴が不正: 比較literalが資産側の線引き宣言とexact-set不一致:
scripts/check_input_axes_descriptor.py: missing=[]; unexpected=['ruleFieldCombination', 'smuggled-undeclared-expectation']
```

**密輸した 2 つを名指しで検出した。復元後は緑に戻る。**

**なお検出するのは 3 点突合の検査器であり、ソースを改竄された descriptor 検査器自身は
緑のままである。** **CI は `pytest tests/`(ci.yml:89)経由で 3 点突合のリポジトリテストを
走らせるため、CI では赤になる。**

### 基準集合の宣言化

**`scope.criterionOrder` / `criterionBindings` / `criteria` を exact-set で拘束し、
`scope` 自体を `freezeDefinition` として独立に hash 化した。**
**集合・対応・線の定義そのものの変更も受理記録を要する。**
**`CRITERIA_SECTIONS` は実装から消え、`forbiddenImplementationSetNames` に
「置き直してはならない名前」として宣言されている。**

### 受入変異 5 種はすべて赤

game-end 組合せ規則の同時変更 / `schemaRetention` の同時変更 /
実装側への criterion 部分集合の再設置 / 宣言側からの criterion 削除 /
反映 7 周目の 7 変異。**負例 13 ケース、関連テスト 82 件が緑。**
