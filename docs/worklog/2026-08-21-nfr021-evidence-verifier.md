### 方針転換 1 件(2 周目で入れて 3 周目で撤回)

**`push` イベントの事後検査**。2 周目に「非 PR イベントのスキップは検査の穴」(ブランチ保護が未適用のため直接 push が塞がれていない)と指摘されて追加したが、3 周目に「赤くしても統合は止まらない・統制が未定義」「`main` 宛 PR で正当なマージが落ちる」と指摘され、正本を読み直して撤回した。

**根拠**: 10.1 `:640`(残余リスク)が同じ問題を既に処理していた — 「ブランチ保護が未導入…なので**人間管理の排他区間**を置く」「**これは機構による強制ではなく運用規律であり、所有者・他メンバーの UI / API 操作を防げない残余リスクが残る**」「マージ後の第 1 親・第 2 親・ツリー検査は**事後検出**であり…手遅れになりうる」。**正本は事後検出を対策として位置づけておらず、この穴を残余リスクとして受容済み**だった。

**教訓**: レビューの指摘に反応して機構を足す前に、**正本が既にその穴をどう扱っているかを確認する**。2 周目の P0 は「穴がある」という事実としては正しかったが、「4-5 が塞ぐべき穴」ではなかった。

### 不採用にした 2 件(理由を残す)

1. **(e-4) を `max + 1` に狭める** — 設計書 `:640` が回復規則を「**既存のすべての予約より厳密に大きい**」と明文で定めている。`:637` の「再実施のたびに +1」は採番の一般的な意図の説明で、`:640` は欠番・重複が既に存在しうる回復場面を想定した意図的な一般化。`max + 1` は**正本より厳しい**。品質 2 周目のレビュア自身も「反論なし」と認めた
2. **PR 内で既存証跡を改変して元へ戻す経路**(品質 2 周目で**この不採用を覆した**)— 当初「復元後はバイト単位で同一だから監査記録は損なわれていない」としたが誤り。同じ 10.1 節の `:644` が失効判定で各コミットの和集合を使う理由として「**変更後に元へ戻されたパスが 2 点差分には現れない**」と明記しており、**このリポジトリは「中間コミットは見ない」原則を採っていない**。`:638`「追記のみ(既存を書き換えない)」も**行為を禁じる書き方**である

### 変異テスト

**通算 21 変異を PR 作成者が再現**(台帳 H-49)。うち **2 件は自分の変異が無効だった**:

- `git log T C`(2 リビジョン)は 2 点差分ではないためパスが落ちない → `git diff T C` へ修正して初めてテストが落ちた
- `REASON_X and None or REASON_Y` は常に `REASON_Y` に評価されるので**何も変えていなかった**(`641 passed` のまま)→ `if False:` へ書き直して 2 テストが落ちた

**教訓**: 変異は「本当に挙動が変わったか」を先に確かめる。落ちない場合の切り分けは ① 変異が無効 ② テストが弱い ③ **その分岐が冗長**、の 3 通り。

また、`-z` を外す変異はパーサごと壊れて無関係なテストが大量に落ち**何も証明しない**ため、**新テストを修正前の実装へ当てる**方法へ切り替えた。
