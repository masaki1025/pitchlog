## 事象と原因(実測 2026-10-03)

```
tests/test_step_history_audit.py::test_real_repository_artifacts_exist_at_each_completed_step_commit
AuditViolation: 実装ステップコミットを第一親履歴から取得できない   (:500)
```

検査は `git log --first-parent origin/develop..HEAD` でステップコミットを集め、
**0 件なら違反**とする(`:500` の `if not records`)。

**develop 上では HEAD == origin/develop なので範囲が空**になり、必ず 0 件になる。

| | 実測 |
| --- | --- |
| develop の第一親履歴のステップコミット | **0 件** |
| 全履歴なら | **816 件** |

**feature ブランチにいることを前提にした検査を、全ブランチに課していた。**
PR では緑で、**マージした瞬間に真偽が反転する**。
TSK-440(census の merge-base)/ TSK-460 と**同じ型**。

## 影響の確定

  `consistency` と `mutation` は含まれない — u-x1 master が実測、こちらでも確認)

- `docs/development/github-setup.md:124` の Ruleset JSON には `consistency` が書かれており、
  **文書と実機が食い違っている**(別件。その食い違いが今回は偶然セーフティネットになった)

## 方針(計画段階)

**範囲が空のときを違反にしない。** 検査の目的は「このブランチが申告したステップの成果物が、
その時点のコミットに在るか」であり、**審査対象が存在しない状況(develop 上・計画段階のブランチ)を
違反と呼ぶのが誤り**。緩和ではなく前提の明示。

**落ちてはいけないもの**: 申告したステップがあるのに成果物が無い / ステップ番号の重複 /
`/N` の総数不一致 — これらは従来どおり赤であること。

**P0 は 3 周とも 0 件。P1 は 2 → 3 → 1 と減って収束した。**
**初版の方針は 2 度作り直している。どちらも根拠の確認不足だった。**

| 2 | P1 3 / P2 2 | ①**`branch:` を書き換えるだけで監査を無効化できた** — 同じ PR で変えられる値を判定基準にしていた ②「無記法の実装コミットは赤」は過大 — 1 件以上ある後の無記法は**従来から通り抜ける** ③ステップ記法を外す判断は AGENTS.md と衝突し、かつ不要 |
| 3 | P1 1 | 文言が 2 箇所だけ古いまま。設計は「**通り抜け無し**」で確認 |

**最終形**:

```
declared_base = origin/develop 側の domain-calc-dsl 計画書の branch:
declared_head = HEAD 側の同じ欄
current       = PR の head.ref(PR 外は現在ブランチ名)

declared_head != declared_base  → 違反(書き換えそのものを赤にする)
current == declared_base        → 監査する(従来どおり全判定・0 件も赤のまま)
それ以外                         → 対象外
```

**比較元側を読むので PR からは変えられず、食い違い自体が赤になる。**

### ハーネス運用評価台帳への追記の判断

**該当する。ただし本 PR では追記しない。**

本件は既存候補「**検査が、そのタスクに無関係な PR を巻き込んで赤にする**」の **6 例目**である。
**`444 344 393` セッションが 1〜6 例を母集団としてまとめて記録する段取り**になっており、
**TSK-476 を参照先として控えてある**(2026-10-03 のセッション間連絡で合意)。
**こちらから重複して起票すると、同じ事象が 2 行になる。**

あわせて、当該セッションへ**分類の細分化**を提案し合意を得た。

| | 中身 | 直し方 |
| --- | --- | --- |
| (a) 比較元が動く | 可変参照を比較元にし、マージで差分が空になる | **比較元の固定** |
| **(b) 母集団が空になる** | 比較元は固定なのに、その上に立つと範囲が空(**本件**) | **「対象が無い」と「対象があるのに不足」を分ける** |

**TSK-460 で (a) を直した直後に (b) を入れた**という経緯が、分類を分ける必要性そのものの
証拠になる。当該セッションが台帳行へ引用する。
