## ステップ 3 — 発効条件 (ii) の条文化(2026-10-11)

**射影規則そのものには触れない**(射程宣言)— **`projectionRules[]` は descriptor の凍結基準

### 丸めの所在を決めた — SQL の外に置く

**本条件が決める分岐点である**(TSK-510 で「(iii) が決めるべき分岐点」と整理した件の決着)。

**(β)①〜⑤ の生成物の構成「SQL 式 + 型付き受け口 + 表示 formatter」は発効後も変えない。**
**SQL 式は構造化値(`NumericValue`)を返し、丸めは formatter が行う。**

**理由を条文に書いた**:

- **丸めを SQL 側へ寄せると、丸めの規則が DB 製品の実装に依存する**
- **D-14-e は丸めを整数対の剰余で定め**(`2r ≥ |d|`)、**浮動小数の乗除を経由しないことを要求している**。
  **SQL の `ROUND()` は engine 依存かつ浮動小数を経由し得るため、この規則を満たさない**
- **SQL 側で整数対の算術を組むことは可能だが、同じ規則の実装が 2 箇所(formatter と SQL 生成器)に増える** —
  **NFR-018 (a) の「人手保守する実装は 1 系統」に照らして不利**

**帰結**: **D-14-e の規律は formatter に掛かり、SQL 式には掛からない**(SQL 式は丸めない)。

**TSK-510 で撤回した主張との関係**: あのとき撤回したのは「**D-14-e が SQL に及ぶから `ROUND()` は使えない**」という
**条文の射程を越えた延長**だった。**今回は条文の射程を越えたのではなく、(iii) が決めるべき分岐点を決めた**。
**結論の向きは似ているが、根拠が違う** — **前者は「D-14-e がそう言っている」(誤)、
後者は「D-14-e の規律を 2 箇所で実装したくないから丸めを SQL へ寄せない」(本条件の決定)**。

**実測**: `check_docs_status` 緑(18 文書・違反 0)。
