### 罠 1 — DSN のスキームが DB 必須テスト 102 件を全滅させていた

`tests/db` が **102 件すべて setup error** になっていた。原因は環境変数
`PITCHLOG_TEST_ADMIN_DSN` / `PITCHLOG_TEST_ROLE_DSN` のスキームが `postgresql+psycopg://` で、
これは **SQLAlchemy の URL 形式であり libpq の conninfo ではない**こと。psycopg の

| 4 | **`--cov` は実行開始時にデータファイルを消し、終了時に書く** |

**`--exclude-standard` は `.gitignore` を尊重するが、追跡済みファイルには効かない。**
だから `.gitignore` へ `.coverage` を足しても `git ls-files --cached --others` は列挙し続ける
(TSK-317 が実験で確認: `.gitignore` 追加後も列挙数 1・ファイルを退避しても列挙数 1)。
**必要なのは `git rm --cached backend/.coverage` で、`.gitignore` は再発防止にすぎない。**

**そして「列挙されるが実行中は存在しない」のは競合状態ではなく決定的**である。
CI の 3 run すべてで同一の 1 件だけが落ちたことと、私の手元で 1 回で再現したことの両方が
これで説明できる。

#### 本タスク自身が同じ混入をしていた

TSK-317 から「`--cov` を回すと `backend/.coverage` が変更済みとして出る。それをコミットしないでほしい」
という警告を受けて自分の履歴を確認したところ、**既に混入していた**:

```
71c3d86 build: ORM スタックを標準として確定し依存と機械検査を追随させる (ステップ 1)
  backend/.coverage   Bin 53248 -> 69632 bytes
```

**`.coverage` に触ったコミットは史上 2 件だけで、`c104789` と本タスクの `71c3d86` である**
(`git log --all -- backend/.coverage` で確認)。**私は 2 件目をやった。**

**`70d553a` で `origin/develop` の blob(`67fa046`・53248 bytes)へ戻した。**
`71c3d86~1` の blob と同一なので、**本ブランチの純差分から当該バイナリが消えた**(確認済み)。

`.gitignore` への追加と `git rm --cached` は行わない — **`S-11` の後続タスクの射程**であり、
本タスクの計画には無い(AGENTS.md 絶対規則 5)。

#### 運用ルール(以後守る)

- **`--cov` を回した後は `git checkout -- backend/.coverage` で戻す**
- **`git add -A` や `git add backend/` のような広い add を使わない。add 対象を明示列挙する**

#### 台帳候補としての形

**3 段構造になっている**:

1. **`c104789`** — `docs:` 型のクローズ処理コミットで **53 KB のバイナリが正本リポジトリへ入った**。
   **その時点では何も壊れなかった**
2. **`71c3d86`**(本タスク・3 週間後) — **追跡済みになった生成物の churn が、
   広い add で黙ってコミットされた**。**これも何も壊さなかった**
3. **PR #52 が新設した文言走査が初めて踏んだ** — `--cov` を付ける経路で
   `FileNotFoundError` になり、**CI が red になった**

**「追跡されてしまった生成物は、その後のすべての広い add に黙って乗る」**のが 2 段目の型で、
**1 段目と 3 段目の間が 3 週間空いている**ため、**原因と症状が結び付かない**。

**帰属**: 候補 2 件を TSK-317 が後続タスクのクローズ処理で提出する。
**「検証コマンドを人が選ぶと CI が走らせるコマンドとの差分が黙って残る」の本文は本タスクが起草**する
(実測が本タスクのものなので二次情報として出るのを避ける)。
**「クローズ処理の一括 add が生成物を取り込み 3 週間後に別の検査の母集団に入って壊れた」は TSK-317 が書く。**

#### push 状態の確認と、履歴を書き換えない判断(2026-09-11)

TSK-317 が「`71c3d86` は push 済みなので 69632 bytes の blob はリポジトリの履歴に残る」と
補足してきたが、**これは事実誤認だった**。実測:

- `git ls-remote --heads origin feature/orm-schema-migration` → **空**(リモートに同名ブランチが無い)
- `git branch -r --contains 71c3d86` → **0 件**(リモートのどのブランチからも到達しない)

**本ブランチは一度も push していない**ので、**当該 blob は現時点でローカル履歴にのみ存在する**。

**それでも履歴の書き換えは行わない。** 理由:

1. **純差分は空**で実害が無い(`git diff origin/develop -- backend/.coverage` が空)
2. **`plan.md` と worklog が `71c3d86`・`f8b0992`・`9595f68`・`bda3f7f`・`7153693`・`70d553a` 等の
   SHA を典拠として引いている**。書き換えると**自らの記録の典拠が全部無効になる**
3. `bda3f7f`(develop 取り込みマージ)が間に挟まっており、**マージを越える rebase は
   衝突解決をやり直すことになる**

**push 時に当該 blob はリモート履歴へ入る**が、**PR の「Files changed」には現れない**。
**逐行確認(`D12`)ではコミット単位で `71c3d86` の `Bin 53248 -> 69632 bytes` が見えるので、
`71c3d86` と `70d553a` の両コミットメッセージが経緯を説明している**形にした。

TSK-317 の運用提案(**各ステップのコミット前に `git status` で `backend/.coverage` が
出ていないかを見る**)は採った。同タブの混入 `c104789` も「クローズ処理でまとめて add した」
ときに起きているので、**add の広さだけでなく確認の手順としても入れる**。

#### 対策を意志に置くと、意志を緩める文脈が対策の外にある(TSK-317 の指摘・2026-09-11)

TSK-317 と `.coverage` 混入の対策を突き合わせた結果、いちばん効いた観点。

私は当初「**広い add を使わない**」だけを対策にしていた。TSK-317 の指摘:

> `c104789` は「広い add をしないつもりだった人」が起こしたのではなく、
> **クローズ処理という「まとめて締める」文脈が広い add を自然にした**結果である。
> **意志ではなく文脈が決めている**ので、意志を対策に置くと同じ文脈で再発する。

**本タスクの `/pr` はまさにその文脈**である — クローズ処理は **worklog・計画書・台帳・索引を
同時に締める**ので、`git add -A` が最も自然な操作になる。

→ **`/pr` のクローズ処理では add 対象を明示列挙し、コミット前に `git status` を確認する**。
**`S-11` の運用ルールに追記した。**

**一般化すると「対策を意志に置くと、その意志を緩める文脈が対策の外にある」**という形で、
これは**機構で閉じるか否かの判断基準**になる。台帳候補②へ TSK-317 がこの観点を入れる。
