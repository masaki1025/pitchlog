# 作業ログ: 2026-09-13 製品機能の実装単位を分割する

   **`data-model.md` 12-4 が「マージ条件」であって「着手条件」ではない**ことを確定した

3. **詳細設計**(`design.md`)— **3 周目に帰属の導出を分離**(PO 裁定)。

## 決定

### PO 裁定 1 — **13 章の射程宣言との衝突**(2026-09-13・山田正輝)

**設計書 13 章は「実装単位の数・名称・境界・PR 分割・着手順・見積もり」を各実装単位のタスクへ残している。**
**しかし各実装単位のタスクを作るには先に単位を決めねばならず、循環する。**
**裁定: カードを優先する。正本は改訂しない。本タスクが確定するのは「最初の 1 回」の単位定義だけ。**
**着手順は非拘束の推奨として書く。**

### PO 裁定 2 — **帰属表を `design.md` へ分離**(同日)

**3 周とも `P0` が 3 件以上出て、3 周目の `P0` 2 件は「非起因」**
(**設計に元からあった穴が新しく見つかった**)。**根本原因は、計画書の中で
「42 FR の帰属が完全であることの証明」を書こうとしていたこと。**
**判定は 42 FR × 5 領域 = 210 セルあり、目視で当てると取りこぼす(3 周で 5 件取りこぼした)。**

**TSK-317 の裁定 `D-19` と同じ手を採った** — **計画書は契約 5 件を持ち、帰属の導出は `design.md` が持つ**。
**収束の機構は「完全性を TSK-363 が証明しない」と認めること**(`design.md` 2 節)。
**各単位の計画書が、自分が主所有する FR について 5 領域すべてに当てた結果を書く。**

## 3 周目の処理(P0 3 / P1 5 / P2 1)

| 指摘 | 処理 |
| --- | --- |
| 面切り失敗時の手順が境界を再定義する | **採用** — 手順から「本書の表を更新する」を外し、**再定義の権限を当該単位の計画書へ戻した** |
| `U-X1` が重複帰属に未列挙 | **採用** — **重複帰属を 3 件 → 5 件**(`U-X1` game-state × sync-protocol / `U-R1` recording-rights × sync-protocol を追加) |
| `FR-041` の共有集計の計算面が未帰属 | **採用** — **`U-X2` の分担**とした(2 領域に収まり 3 領域目にはならない)。**帰結として `U-C1` は `FR-041` を閉じられない**ので **`部分充足`** の状態をカードに持たせた |
| 35 ファイル閾値が実測と不一致 | **採用** — **閾値を撤回**(`PR #50` = 12 ファイル 13,795 行 / `PR #52` = 89 ファイル 22,895 行 — **相関しない**)。**「分割の検討を起動する条件」3 つ**へ置き換えた |
| 帯 2 の Notion 状態が閉じない | **採用** — **起票時のカード値を (ii) 既定で一意に埋める規則**を置いた(`コア判定` = コア(fail-closed)/ `レビュー経路` / `降格条件`)。**未確定を理由に空欄にしない** |
| 5 条件が `grep` 述語でない | **一部採用** — **検索式の表**を書いたが、**「候補」と明示**した。**`backend/src` に製品コードが 0 行で語彙の実測ができない**ため、**本書が拘束するのは「一致 0 を要求する検索式を計画書へ書く」という形式だけ** |
| 帯 4 の凍結典拠が単位ごとに違う | **採用** — **`U-X1` / `U-X2` / `U-X5` = ADR-003** / **`U-X3` = 正本不在**(`data-model.md` 12-5 が `送`)/ **`U-X4` = `U-X2` 依存**。**「帯 4 = ADR-003 で凍結」は不正確**だった |
| 検証の作業ディレクトリが両立しない | **採用** — **worktree ルートに統一**し、`WT=` を撤去。**検証 1 を `design.md` の表から実測する形**にした(表の写しを二重に持たない) |
| 節の重複 | **採用** — 「経路契約が無い FR-001〜019 の扱い」を 1 つへ統合 |
