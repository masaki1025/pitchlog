## 1-2. `frontend/src/lib/sync/` は何なのか(**最大の既存資産**)

**同期プロトコル設計 v0.3(approved)の実装層**。UI ではなく、**クライアント側の記録・送信の中核**。
本体 9,572 行 + テスト 13,372 行の 30 モジュール。**製品コードの大半がこれ。**

### 平たく言うと

**「球場のタブレットで 1 球ずつ入力した記録を、電波が切れても失わず、二重にも欠けもさせずに
サーバーへ届ける取り決め」** の実装。1 試合で数百球の入力があり、球場は電波が悪い。
それでも記録は止められないので「繋がっている前提」では作れない。

| 起きうる事故 | 防ぐ仕組み | 正本の呼び名 / 実装 |
| --- | --- | --- |
| 圏外の間の入力が消える | 端末内に**永続キュー**を持ち、まず端末へ確実に書いてから送る | 断中記録 / `durableQueue.ts`(IndexedDB) |
| 再送でスコアが二重に増える | 1 件ごとに**使い回さない鍵**を付け、同じ鍵は 1 回しか適用しない | **D5 べき等キー** / `idempotencyCollision.ts` |
| 途中の 1 球が抜けたまま後ろだけ適用される | **欠番があればそこから先を適用しない**(prefix コミット) | **D1 同期連番** / **D3 prefix 水位** |
| 2 人が同じ試合を同時に記録して壊れる | 記録できる端末を**世代で切り替える**。古い世代の書き込みは弾く | **D4 記録権世代** |
| 同じ人がタブを 2 つ開いて二重に書く | ブラウザのロックで**書き手を 1 つに絞る** | 単一書き手 / `singleWriter.ts`(`navigator.locks`) |
| 取り消しで番号に穴が空く | 穴を**「ここは取り消し」の印**で埋める | **D6 墓標** / `k5Tombstone.ts` |
| 後から直したとき正しい歴史が分からなくなる | **改訂版**として上書きし正史を 1 本に決める | **D7 改訂** |
| 適用できない記録を黙って捨てる | **退避**して人に見せる(黙殺しない) | **D8 退避** |

### 最重要の設計判断(**素朴に作ると必ず間違えるところ**)

正本が「**本書の中核**」と自ら書いている 1 点:

> **同期連番の順は、クライアントが操作を受理して端末内の永続キューへ新規追記した順である。
> サーバーが受信した順ではない。**

理由: **サーバー受信順で番号を振ると定義上「欠落」が起こらなくなり、欠番検知そのものが意味を失う**。
そのため「**サーバー到着順という概念は本設計に存在しない**」と宣言し、
禁止語として**機械検査までかけている**(`scripts/check_design_propagation.py`)。

### 正本からコードまでが 1 本の鎖になっている

```
docs/design/sync-protocol.md              ← approved v0.3(正本)
      ↓ 節・規則 ID(V1〜V12 / Q1〜Q7 / A3 / W4 …)を機械可読へ
scripts/design_relations/sync-protocol.json
      ↓ @design-relations エイリアス(vite.config.ts / tsconfig.app.json)
canonOracle.ts(1,350 行)                 ← 正本語彙の読み取り(パーサ)
      ↓ 語彙を供給
各同期モジュール + それぞれの spec
```

**各ファイルの 1 行目が正本の該当節を名指ししている。** 例:

- `durableQueue.ts:1` 「この永続化境界は `sync-protocol.md` **7-4 の Q1 の実装**である」
- `eventFieldRules.ts:1` 「この表と条件写像は **4-3(V1〜V12)と 4-3-A の写し**である」
- `canonOracle.ts:2` 「射程は正本語彙と構造の読み取りに限り、**値の変更は正本の改訂ゲートを通す**」

→ **コードが勝手に仕様を決められない構造**。語彙を変えたければ正本を改訂するしかない。
**この規律を壊さないこと**(コード側に語彙を直書きすると `check_design_propagation.py` が落ちる)。

## 2. クリティカルパス — backend を 1 行でも書くために通る唯一の経路

**データモデルが未確定なので、バックエンドの実装は構造的に開始できない。** その連鎖:

```
TSK-271  88 列と旧資料矛盾の調査           ← 進行中(計画承認済み 2026-09-08・ステップ 1/5)
   │
   ├─ TSK-337  要件書改訂: 負値座標のセンチネル条件      ← 移行実装のブロッカ(TSK-271 の依存ではない)
   │            付録 B-5 のクランプ vs FR-038 の x<=0 が矛盾。確定ゲート必須
   ▼
TSK-334  裁定セッション(判定 22 件の採否)
   │       ※ DM-LX-03/04 で「非 data-layer.md 側」を採るなら
   │         → 要件書 precedence の改訂を新規起票し確定ゲートを通す(さらに 1 段増える)
   ▼
TSK-335  TSK-250 の計画改訂(受け渡し契約の内部矛盾の解消)
   │       敵対レビュー収束 + 人間再承認の完了までが DoD
   ▼
TSK-250  データモデル設計の正本化(docs/design/data-model.md 新設・確定ゲート・実機検証)
   │       ※ 開始条件に TSK-317(PostgreSQL 認可構成の実機検証 第2/第3群)も含まれる
   ▼
backend の実装(モデル・マイグレーション・API)   ← ここまで来て初めて可能
```

### この連鎖が生まれた理由(1 行ずつ)

- **TSK-250 が 2 度否決された** — 「1 タスクに独立した確定単位が複数入っており、後段が前段の成果を壊す」。
  人間の裁定(2026-08-31)で先行タスク A(TSK-269・**マージ済み**)/ B(TSK-317)/ C(TSK-271)へ分割
- **TSK-271 の受け渡し契約が内部矛盾していた** — TSK-250 の射程表は C を「**88列の行き先表**」と呼ぶ一方、
  契約の 4 項目(`保存元 / 変換 / 欠損時規則 / 逆変換可能性`)に**行き先を含まない**。かつステップ 18 が
  「本文の記述のうち C の JSON に無い値が 0 件」を機械検査する。
  → **C が行き先を持たなければ TSK-250 が落ち、持たせれば C が TSK-250 の物理スキーマに依存して循環する**
- **TSK-271 の中身が正本の権限を超えていた** — 承認済み要件が `data-layer.md` を
  「**移行仕様の事実の正本**」(88 列の実際の意味・センチネル値・列名の罠)と指定しているため、
  調査が `data-layer.md` を他 7 資料から「誤り」と判定した 2 件の**採否を裁定するには
  要件書 precedence の改訂が必要**だった

### 重要な是正(2026-09-08 追記)— **上の連鎖は「正本の要求」ではなく自分で課した順序だった**

**上の図を「backend を書くために通る唯一の経路」と書いたのは誤り。** 正本を読み直すと、
**ハーネス設計書 13 章「製品機能の実装(v1.13・approved)」が製品実装の開始条件を定めていない。**

| 典拠 | 逐語 |
| --- | --- |
| 設計書 13 章 | 「**要件書の FR が定める製品機能の実装は、本章の Phase の対象外とする。**」 |
| 同 | 「**本章は製品実装の開始条件を定めない** — **着手可否は 6.1 の実装計画書ゲート(人間承認)で判断する**」 |
| 同 | 「**本節は製品機能の実装について順序・群・段階を定めない**。どの FR から着手するかは各実装計画書(6.1)の判断とする」 |
| ADR-003 | 「**対象横断の正解ベクタが未完成であることは「適合と判定しない」を意味するのみで、実装を禁じるものではない**」 |
| 人間の裁定 2026-09-02(TSK-279 確定ゲート 2 周目) | 開始条件の明記を**射程から落とした**。「13 章は開始条件を定めない」 |

→ **「TSK-250 の完了まで backend は構造的に開始できない」は正本の要求ではない。**
実際の拘束は次の 2 つだけである。

1. **6.1 の実装計画書ゲート**(承認済み計画 → ステップ単位 → PR)
2. **`NFR-018` の対象計算に触れる実装は ADR-003 の導入順序に従う** — 「検査基盤(生成器・
   マニフェスト・収集器・CI 配線)+ ベクタ schema + 独立に確認した期待値の**先行確定**」→
   対象 1 件ごとに 3 層検査を**同一の変更**として追加 → 当該対象の全緑がマージ条件。
   **「検査基盤の未整備を理由に対象計算のコードを先に追加することはできない」**

### では何が本当に backend を止めているのか(実測)

| 前提 | 状態 | 所有 | backend の何を止めるか |
| --- | --- | --- | --- |
| **DB スキーマ**(`docs/design/data-model.md`) | **存在しない** | TSK-250 | models・マイグレーション・データを触る API の**すべて** |
| **ORM の確定** | **未確定** — 設計書 5.1 が Alembic を「**SQLAlchemy 前提。設計フェーズで最終確定**」と留保。backend の依存は `fastapi` + `psycopg` のみで SQLAlchemy 無し | TSK-250(5.1 の留保解除) | models を書く言語そのもの |
| **ADR-003 検査基盤** | **未着手**(`domain-calc-dsl` は計画段階・承認待ち・計画レビュー 1 周) | TSK-235 | **状況判定・座標変換・捕球選手推定・成績集計の前処理のコード全部**(ADR-003 が先行を要求) |
| **wire / API スキーマ** | **未決**(「要件書に要求が一切無く、置き場も未決」) | **TSK-331**(起票済み) | API の入口の形 |
| **故障系契約とシナリオ資産 10 件** | 未着手 | **TSK-332**(起票済み) | `NFR-019(d)` の担保 |
| **同期サーバー適用の実装** | 未着手・**開始条件が「TSK-250 の完了」と書かれている** | **TSK-330**(起票済み) | 同期の適用経路 `P1`〜`P5` |
| **PostgreSQL 認可構成** | 未着手 | TSK-317 | テナント分離の DDL(TSK-250 ステップ 6 で要る) |

**ここで分かる 2 つの見落とし**:

1. **ADR-003 検査基盤(TSK-235)は第 2 のクリティカルパスであり、TSK-250 とは独立**。
   スキーマが出た後にドメイン計算のコードを書こうとすると、ここで止まる。**いま並行で始めるべき**
2. **TSK-331(wire / API スキーマ)・TSK-332(故障系契約)も TSK-250 非依存**。
   TSK-330(backend 実装)の前提だが、TSK-250 を待つ理由がない

**なお同期キューの状態遷移は `NFR-018` の対象計算の列挙に無い**(要件書 NFR-018 の「対象」欄)。
→ **同期の適用ロジックは ADR-003 のゲート下にない**。止めているのは永続化 = スキーマだけである。

### TSK-250 の 28 ステップの内訳(実測 — 最大の短縮余地)

TSK-250 が新設する資産は約 24 件だが、**backend が必要とするのは `docs/design/data-model.md` 1 本**で、
**残り約 20 件は `scripts/design_relations/*` の文書検査機構**(プロファイル・不変条件・主張母集合・
関係マニフェスト・欠陥台帳・digest・負例 fixture 10 件)である。

→ **13 章が「実装は文書の approved を前提にしない」と定めている**のだから、
**スキーマと ORM の確定を先に小さく凍結し、文書検査機構は並行/後追いで載せられる。**
**品質は落ちない** — 切り出したスキーマ確定に**同じコア領域の統制**(敵対レビュー + 人間の逐行確認)を通す。
これは **TSK-335 の既存 DoD「ステップ 6・18 の入力と合格条件を再設計する」の射程内**である。

### PO 裁定(2026-09-08)— **backend への最短路**

**裁定 1: TSK-250 から「スキーマ + ORM の確定」を切り出す。** 設計と起票は **TSK-335** が持つ。

| **先行(切り出す)** | ① `docs/design/data-model.md` の**スキーマ本体** ② **設計書 5.1 の ORM 留保の解除**(SQLAlchemy 2.x / psycopg 3 / Alembic) | **backend が必要とするのはここだけ**。コア領域として敵対レビュー + 人間の逐行確認 + 7.3 の確定ゲート |

### 短縮判断(2026-09-08)— この連鎖は 4 段から縮められる

上の図は**タスク単位の直列**で書いてある。**依存を実測すると、直列である必要のない箇所が 3 つある。**

| # | 判断 | 実測した根拠 | 状態 |
| --- | --- | --- | --- |
| ② | **TSK-317(B)を TSK-271 と並行で今すぐ始める** | TSK-317 は 88 列にも `data-migration` にも触らない(`contracts/authz/**` と `tenant-isolation`)。**TSK-271 への依存は無い**。`未着手`・優先度 `高` | **記録済み**(TSK-317 のカードへ追記) |
| ⑤ | **TSK-340(設計書 6.1 = 計画レビューの終端条件)を TSK-250 の前に置く** | TSK-250 は **28 ステップのコア領域タスク**。終端条件なしに計画レビューへ入ると TSK-271 と同じ輪(9 周)に入る。条文が先にあれば TSK-250 の計画レビュー自体が短くなる。**ブロッカではなく順序の推奨** | **記録済み**(TSK-340 のカードへ追記) |
| ① | **TSK-250 の開始条件をタスク単位からステップ単位へ緩める** | **人間の裁定 2026-08-31 の変更に当たるため裁定が必要**。裁定材料と追加 DoD を TSK-335 へ記録した | **人間の裁定待ち** |

**① の実測(TSK-250 の実装ステップ表 28 件)— ここが直感と違う**:

- **ステップ 1〜5**: B も C も要らない → **今すぐ着手できる**
- **ステップ 6**(入力主張母集合・独立資産・受け渡し digest の固定): **B の DDL 要素表と C の 88 列写像の両方**を
  和集合の要素として要求する。**28 ステップ中もっとも早い依存点**
- **ステップ 7〜17・20〜28**: B・C への直接の依存語は無いが、**ステップ 6 が固定した母集合を後段が
  exact-set で照合する**構造なので、実務上はステップ 6 が通らないと進めない
- **ステップ 18** = C / **ステップ 19** = B

→ **「B・C に依存するのは 2 ステップだけ」という読みは誤り。** タスク単位 → ステップ単位に緩めるだけでは
**ステップ 1〜5 しか前倒しできない**。実質的な短縮は **ステップ 6 の母集合固定を出所ごとに分割**し、
B・C 由来の部分を後から追加できる形にすることで得られる。これは **TSK-335 の既存 DoD
「ステップ 6・18 の入力と合格条件を再設計する」の射程内**であり、新規タスクは要らない。

**この実測の限界**: 依存の判定はステップ表の記述に対する語句照合であり、**暗黙の依存を取り切れていない
可能性がある**。順序を緩める判断は人間が行う(だから ① は裁定待ちにしてある)。

## 8. プロセス上の既知の弱点(共同開発で顕在化しやすい)

- **計画レビューに終端条件が無い** — 確定ゲート(7.3)には収束規則があるが、
  計画レビュー(6.1)には無い。**TSK-271 で 7 周を要し、受理範囲を限定して初めて指摘が局所化した**。
  運用評価台帳の候補として記録済みで、**昇格条件が成立したため TSK-340 を起票**した
- **是正が構造を追加し続ける輪** — 「構造が薄い」という指摘に応えて構造を足すと、
  足した構造そのものが要件先取りとして次の P0 を生む。**縮小方向の是正**でしか抜けられない場合がある
  (TSK-248・TSK-250・ADR-003・TSK-271 で 4 例)
- **強制終了** — 長時間実行の敵対レビューが通算 23 回強制終了している(台帳の実測)。
  **判定条件は未特定**でセッション種別とは無相関
- **タスク本文の陳腐化** — 解消済みの前提が本文に残る。**着手前に本文の前提を実測で検証すること。**
  実例 2 件:
  - **TSK-235**: ブロッカに「Phase 4-2(backend 骨格)が未着手 — `backend/` が存在しない」と書かれているが
    **`backend/` は実在し Phase 4 は完了**している(3 節)
  - **TSK-275**: 「画面受入タスクは未起票」と書かれているが **TSK-307 が同日に起票済み**だった。
    **2026-09-08 にこの記述を信じて TSK-341 を重複起票し取り下げた**(訂正済み)。
    → **起票の前に必ず Notion をタスク名で検索する。他タスクの本文を典拠にしない**
