`VerifiedDeviceContext(tenant_id: UUID, device_id: UUID, credential: str)` は認証側が発行・検証する不透明な文脈の候補。任意のDTOをこの名前で新設して検証済みと呼ばない。tenant IDだけの `TenantContext` やwire自己申告で代用しない。

### C. commit完了までの外部fenceとロック順

現 `gate.py:gated_writer` の `finally: writer._close()` は業務scopeの `__exit__` によるcommitより先に実行される。writer失効は維持し、これを外部fenceの解放点へ流用しない。

```python
# U-R1が提供する候補。leaseを呼出側が捏造できないことを別に検査する。
def hold_write_fence(
    verified_device: VerifiedDeviceContext,
) -> AbstractContextManager[WriteFenceLease]: ...

with hold_write_fence(verified_device) as lease:
    with tenant_transaction_scope(context) as scope:
        # lease検証 → 端末資格共有ロック → 既存の業務ロック
        with gated_writer(scope, rights) as gated:
            ...  # T2〜T9、⑧
    # 業務DBのcommit/rollback終了。結果不明なら解決プロトコルへ移る。
# 通常終了の場合だけ共有fenceを解放
```

順序候補は **認可・RG1非ロック事前確認 → 外部epoch共有fence → 同一業務scopeの端末資格FOR SHARE → 試合FOR UPDATE → 記録権世代FOR UPDATE → RG1 FOR SHARE NOWAIT → commit/rollback完了 → 外部fence解放**。③-aは既存どおりD5照合・業務ロックより前にも行い、⑧は書込分岐のcommit直前に行う。T8/T9も書込として同じfenceの対象。バッチ全体ではなく各書込transactionが必ず保持する形を推奨する。preflightは端末を同じ文脈で照合し、書込transactionで権利とfenceを再確認する。

U-G1のチーム/選手/U-M2記憶行、V12配達行との相対順は実経路照合待ち。試合→世代の既受理順を変えない。資格失効側は資格行を保持したまま試合/世代へ進まない。復元開始側はRG1だけを閉じてcommitした後に外部epoch排他更新へ進み、外部排他を待ちながらRG1ロックを保持しない。

**要判断の障害境界**: 外部接続喪失で共有ロックが消えた場合、単なるcontextmanagerの解放抑止では安全性を保証できない。commit結果不明も通常のfinallyで安全に解放できるとは限らない。推奨は、U-R1が「業務transactionの確定/取消の権威ある解決までepoch切替を許さない」耐久的な調整契約を提供するまで実接続を閉じること。再接続・再取得だけで成功扱いしない。耐久方式・提供主体・外部台帳配置は今回未決であり、この疑似コードだけで解決済みとはしない。
