### 既存資産の欠陥を発見(TSK-509 の射程外・別途報告)

**生成される Python formatter と TypeScript formatter が、同じ入力に別の値を返す**(本タスクが実測):

```
入力        scale   Python(Decimal)   TypeScript(float64)
1.005       2       1.01              1.00
0.285       2       0.29              0.28
-0.0001     3       -0.000            0.000
```

Python は `Decimal` + `ROUND_HALF_UP`、TS は `Number(...)` と `Math.floor(abs*10**scale + 0.5)`
(`backend/src/pitchlog/domaingen/formatter.py:190-195`・`:347-356`)。

**検査が拾わなかった理由も確認した**: 生成された TS formatter を node で実行する試験は
`tests/domain/gen/test_formatter.py:333` の **1 件だけ**で、`"1.3"` という**単一の値**を突き合わせている。
要件書 `:949` が 3 層担保の 2 層目として求める「**正本から生成した各実行体どうしの等価性**」が、
**1 つの値の突合に縮退していた**。

**現時点では潜在**(生成器がスタブ・参照実装は製品経路から切り離されている)。
ただし**段階 2 で対象計算を載せ始めると、この穴の上に実データが乗る**。

**TSK-509 への含意**: この食い違いは **D-1 が 2 言語に別々のコードを生成する方式だから**生じている。
D-2 はこの種のずれを構造的に消すが、**代わりに JS に decimal 型が無い問題を背負う**。
**どちらの方式も数値意味論の問題を持ち、形が違うだけ**である。四観点の「同一由来性」は、この実測を踏まえて評価する。

## ステップ 1 — 整数符号化の許否と `ADR-003:103` の射程の裁定(2026-10-09)

**裁定(PO・山田正輝 2026-10-09)**: **案 B** — **整数符号化は許さない。代わりにガードによる分岐の道を開ける。**
検査器とガードの実装は段階 2 へ送り、本改訂は条文として置く。

### 1-1. 射程の裁定 — 「条件分岐は書けない」は表示規則に掛かる

`ADR-003:103` の逐語:

> **条件分岐・部分文字列操作・③の宣言の外の数値整形ロジックは引き続き書けない**

**DSL 全体に条件分岐を禁じたものではない。** 根拠は原典の形である。

**v0.1 承認行(`ADR-003:34`)の逐語** — 禁止が「**許すのは 2 種**」の括弧の中にある:

> 表示規則を正本の射程へ取り込み、対象計算は「構造化値」と「表示値」の両方を返すことに確定
> (…**許すのは enum→表示名の写像テーブルと、プレースホルダ差し込みだけの宣言的テンプレートの 2 種で、
> 条件分岐・部分文字列操作・数値整形は書けない。**…)

**v0.2(`:103`)でも位置は同じ**。直前は表示規則の射程の限定、直後は①の写像テーブルの規定であり、
**「③の宣言の外の数値整形ロジック」という文言自体が表示規則 3 類(①②③)を指している**。
**「引き続き書けない」は v0.1 からの継続**を意味する語である。

**補強(内的整合 — master タブが独立に到達・本タスクも支持)**:
D-1 の射程行は「状態 / イベント / **ガード** / 次状態」を含む。
**禁止の文も射程行も同じ表のセルの中にある。**
したがって「DSL 全体で条件分岐が書けない」と読むと、**同じセルの中で自己矛盾する**。

**これは文脈の読みより強い**。前後関係の解釈ではなく、**矛盾しない読みが 1 つしかない**という形で言える。

### 1-2. ただし、状態遷移の層で分岐する道は実装上ふさがっている(本ステップの発見)

```
ADR の射程行        「状態 / イベント / ガード / 次状態」を明示          ADR-003:103
model.schema.json   GuardRule / guardRefs を必須フィールドとして定義    :424-443 / :451・:464
実装                guardRefs を読むコードが 0 行                      全言語で走査
pregen_checks       1 イベントに遷移 2 本 → 無条件で「決定的でない」    pregen_checks.py:163-170
```

`_check_transitions` は `del schemas` のうえ `eventRef` で遷移を数えるだけで、
**`guardRefs` を一切参照しない**。`count > 1` で違反を立てる:

```python
elif count > 1:
    violations.append(_violation(CheckId.TRANSITIONS, ..., "複数の遷移が成立し決定的でない"))
```

**`guardRefs` の出現箇所は、schema・合成フィクスチャ・`[]` や文字列リテラルを渡すテストだけ**である
(`tests/domain/gen/{test_pregen,test_formatter,test_backends,test_core}.py` / `tests/domain/test_model_schema.py` /
`backend/tests/domain/fixtures/synthetic_dsl/model.json`)。**製品側で読む実装は存在しない。**

**したがって整数符号化が必要だったのは、ガードによる正規の分岐が検査で塞がれているからである。**
回避策が先にあったのではなく、**道が無いので算術で畳んでいた**という順序だった。

**これは本リポジトリで繰り返し出ている型の新しい面である**:
**検査が、条文や機構の契約より厳しい条件を独自に課している。**
#108 で直した 3 件(テスト側)と同根だが、**本件は生成前検査(製品側の機構)**であり面が違う。

### 1-3. 裁定の理由

**整数符号化を許さない理由**:

- **D-1 の正当化が崩れる**。`ADR-003:507` は「射程を『状態遷移 + 有限の算術』に限れば**生成器は小さく保て、
  生成物の検査を生成時に機械化できる**」として D-1 を選んだ。整数符号化は
  **状態とイベントをすべて整数で符号化する**ことを要求するため、**enum・boolean という射程の型が使えなくなり、
  型による検査が効かなくなる**。「型で機械検査できる」という選択理由そのものを損なう
- **式が巨大化する**。第 3 アウトの攻守交代(C1)だけで 3 フィールド・十数ノード
  (`ux1-game-state-core/evidence/expressible_models.out.md`)。付録E の全行に広げた規模は未測
- **回避策の追認になる**。ガードが射程にありながら実装が無く、検査がそれを塞いでいる状態を、
  回避策を正式化することで**固定してしまう**

**ガードの道を開ける理由**:

- **ADR が既に射程へ入れている**。新しい能力の追加ではなく、**宣言済みの射程を実装が満たしていない**
- **schema も既に持っている**(`GuardRule` / `guardRefs` が必須フィールド)
- **検査の是正だけで足りる**(ガードの排他性を判定し、排他なら複数遷移を受理する)

### 1-4. ステップ 3 への入力

**D-1 拡張の評価は「ガードが使える前提」で行う。** 整数符号化には依らない。

**判定が変わるもの**: 状態の層で書けた 10 件のうち、整数符号化に依っていた **7 件**
(C1・C2・C9・C14・C16・C17・C27)は、**ガードが使えるなら素直に書ける見込み**である。
**ステップ 3 で確かめる。**

**判定が変わらないもの**: **表現不能 5 件(C3・C4・C10・C12・C13)はガードとは無関係**である。
C3 は出力の値を定める記述が schema に無いこと、C4 は履歴スタックを読む式が無いこと、
C10・C12 は配列型が無いこと、C13 は語彙スナップショットを引く式が無いことが根拠であり、
**いずれも分岐の問題ではない**。発火の根拠は不変。

### 1-5. 段階 2 へ送るもの

- **ガードの実装**(`guardRefs` を読む生成器)
- **生成前検査の是正**(排他なガードによる複数遷移を受理する。`_check_transitions` の `count > 1`)
- **排他性の判定方法**(機械で判定できる形に限るか、宣言で与えるか)

**本改訂では条文として「ガードによる分岐が射程であること」を明示し、実装は段階 2 の射程とする。**

## ステップ 2 — NFR-018 (b)③ と D-2 の関係(第 1 関門)(2026-10-09)

**判定: ② 抵触しない(条件つき)。** D-2 は選択肢として残る。**PO 裁定へは上げない。**

### 2-1. 条文が禁じているもの(要件書 `:952` 逐語)

> **③ 宣言された構成の完全性**: **入口の全列挙**(本番に到達可能な実行入口を宣言し、**宣言外の入口を拒否する**。
> Web Worker・Service Worker・別HTML・静的配信配下を含む)／**構成の照合**(本番に含まれるモジュール・
> 生成物の集合が宣言と一致すること。**サーバー側も同等に閉じる**)／**動的機構の禁止**
> (**動的コード生成・非リテラルな動的読み込み・外部スクリプトの実行**を禁止し、違反を検出する。
> 単一の検査手段では漏れるため複数を重ね、**実行時の制限も併用する**)

**禁止は 3 つの機構を名指ししている。** D-2 の artifact がどれに当たるかで決まる。

| 禁止 | D-2 の artifact | 判定 |
| --- | --- | --- |
| **動的コード生成** | **build 時に生成**した固定ファイル。実行時に組み立てない | **当たらない** |
| **非リテラルな動的読み込み** | **宣言済みのリテラルなパス**から読む(実装でそう定める) | **当たらない** |
| **外部スクリプトの実行** | **本リポジトリの build 生成物**であり、宣言され hash で固定される | **当たらない** |

**③ 全体の趣旨は「宣言外のものを拒否する」である**(入口の全列挙が「宣言外の入口を拒否する」と書き、
構成の照合が「宣言と一致すること」と書く)。**判定基準は「JS かどうか」ではなく「宣言された構成に入っているか」**。

**先例が既にある**: 現行設計は **build 時生成の TS を `frontend/src/lib/generated/` へ置き、
`generated/wrappers/` 経由の静的 import に限定**している(`frontend/.dependency-cruiser.cjs` が強制)。
**同じ形**であり、D-2 が変えるのは「**同じ artifact をサーバーでも動かす**」ところだけである。

### 2-2. ただし運用定義に「サーバーで JS を実行する」行が無い(本ステップの発見)

ADR-003 `:259` の運用定義は**言語ごとの 2 行しかない**:

> **動的機構の禁止** | **TypeScript 側** = dependency-cruiser で dynamic / exotic / unknown・undetermined
> dependency を error + lint で動的コード生成(`eval` 相当・`Function` 構築)と非リテラル読み込みを禁止
> + 実行時の CSP。**Python 側** = `importlib` による動的 import・`getattr` による動的解決・
> entry point 経由のプラグイン読み込みを禁止し静的検査で検出。単一手段では漏れるため層を重ねる

**「サーバーで JS を実行する」場合の行が存在しない。** 条文(`:952`)には抵触しないが、
**運用定義が D-2 を想定していない**。

**D-2 を採る場合、本改訂でこの行を足す必要がある**(ステップ 5 の棚卸しの対象。ADR-003 の 1 正本内なので
射程宣言は保たれる)。足すべき内容:

- 埋め込みエンジンで **`eval` / `Function` 構築 / 動的 import を禁止**する
- **実行時の制限**(メモリ上限・時間上限)を併用する(`:952` の「実行時の制限も併用する」)
- **構成の照合を JS artifact まで広げる**(「サーバー側も同等に閉じる」)
- **artifact の hash を起動時に照合**する

### 2-3. 入口の全列挙(クライアント側)

**artifact の読み込み方で宣言が変わる。**

| 読み込み方 | 入口の全列挙への影響 |
| --- | --- |
| **メインバンドルへ同梱** | 現行と同じ。追加の宣言は不要 |
| **Worker 化** | **入口の追加**として宣言が要る(`:952` が Web Worker を名指し) |
| **別配信** | 同じく宣言が要る(「静的配信配下を含む」) |

**最も安いのはバンドル同梱**であり、現行の `generated/wrappers/` 経由の静的 import と同じ形で済む。
**ステップ 5 の棚卸しで、どの形を採るかを条文に書く。**

### 2-4. 7.1 の 2 条文

**技術スタック(`:1059`)**:

> 技術スタック: Python / FastAPI + Vue.js + TypeScript / PostgreSQL…**変更には承認を要する**
> (v1.8: フロントエンドを React から Vue.js へ変更 — 決定は ADR-002)

**「変更には承認を要する」であって禁止ではない。** 先例の ADR-002(React → Vue)と同じ形で、
**本改訂の確定ゲート + PO 承認がその承認にあたる**。**関門にはならない。**

**ステートレス(`:1060`)**:

> サーバーはステートレス(**プロセス内に試合状態を持たない**)。レート制限カウンタ等の横断状態もプロセス外に置く

**条文が禁じているのは「試合状態をプロセス内に持つこと」**であり、常駐プロセスそのものではない。
ただし **D-2 の形によって難度が変わる**:

- **インプロセスの QuickJS** — 要求ごとに評価して返すだけで、試合状態を保持しない。**整合しやすい**
- **常駐 Node のサイドカー** — 持続プロセスなので、**試合状態を持たない設計規律を別に要する**。
  さらに **U-S1 のポート規則と当たる可能性**がある(`feature/us1-sync-apply-core` の design.md が
  ポートの登録モジュールの推移的 import に threading・asyncio・multiprocessing を禁じている —
  **TSK-405 の報告・本タスクは未追試**。当該ブランチは未マージ)

**→ D-2 を採るなら、インプロセスの QuickJS のほうが条文との摩擦が小さい。** ステップ 4・6 の材料とする。

### 2-5. 判定の理由(なぜ PO 裁定へ上げないか)

計画のステップ 2 は「**要件書の解釈が割れる場合**は停止して PO 裁定」と定めている。**割れていない。**

- 条文は**禁止する機構を 3 つ名指し**しており、D-2 の artifact は**いずれにも当たらない**
- ③ 全体の趣旨が「**宣言外のものを拒否する**」であることは、入口の全列挙・構成の照合の文面から一意に読める
- **同じ形の先例が現行設計に既にある**(build 時生成物の静的 import)

**残るのは条文の解釈ではなく、ADR 側の運用定義の不足**であり、**それは本改訂の射程そのもの**である。

### 2-6. ステップ 3 以降への入力

- **D-2 は選択肢として残る。** 費用の検討(ステップ 4)へ進む条件を満たした
- **D-2 を採る場合に本改訂で足すもの**: (b)③ の運用定義へ「サーバーで JS を実行する場合」の行
  (ステップ 5 の棚卸しに含める)
- **D-2 の形**: インプロセスの QuickJS を基本線とする。常駐 Node は条文との摩擦が大きい
- **技術スタックの変更の承認**は確定ゲートで取る(関門ではない)

## ステップ 3 — D-1 拡張(案 B)で表現不能 5 件を書けるか(2026-10-09)

**ステップ 1 の裁定により、ガードが使える前提で評価する。**

**結論: 5 件は 2 つの問題に還元される。** 一方は安く、他方は D-1 の正当化を失う。

```
問題 I   出力の導出規則が無い            C3            → 書ける。正当化を失わない
問題 II  可変長の出力を持てない          C10・C12
                                        C13 の集計部分
                                        C4 のスタック全体出力  → 書けるが正当化を失う
```

### 3-1. schema の実測(根拠)

```
OutputField          7 キー(fieldId / type / nullable / range / unit / scale / visibility)
                     additionalProperties: false — 導出式のキーが無い
FieldType            6 型(IntegerType / BooleanType / EnumType / NumericValueType /
                     VocabularySnapshotType / HistoryStackType)— 汎用の配列型が無い
ReferenceExpression  kind + fieldRef だけ — 添字も長さも射影も無い
```

**上限が無いことの条文上の根拠**:

- **延長上限は「なし」が許される**(要件書 付録F-1 `:1632`「整数または**なし**」/ `DRAW-07` `:1670`
  「延長上限が`なし`で終了宣言イベントが未適用なら…**同点なら次の回を継続する**」)
  → **イニング数に上限が無い** → C10・C12 の出力長に上限が無い
- **履歴スタックに上限を置かない**(`ADR-003:312`「**実行時のスタックの長さに上限は置かない**
  — FR-006 の連鎖はスタックが空になるまで続くため」)→ C4

### 3-2. 件ごとの判定

| 件 | 要るもの | 判定 |
| --- | --- | --- |
| **C3** 出力の導出式 | `OutputField` に式を束ねるキー(または出力規則の `kind`)。**式の語は既にある**(8 種) | **書ける。正当化を失わない** |
| **C4** 履歴の読み出し | **2 つに割れる**(下記 3-3) | **計算は書ける。全体出力は問題 II** |
| **C10** 可変長の出力 | **上限の無い配列型** | **書けるが正当化を失う** |
| **C12** 行リストの出力 | 同上 | **書けるが正当化を失う** |
| **C13** 閉じない列挙 | **入力側**: `VocabularySnapshotType` を引く式(型は既にある)<br>**出力側**: 球種ごとの集計 = 上限の無い写像 | **入力側は書ける。出力側は問題 II** |

### 3-3. C4 は 2 つに割れる(本ステップの発見)

**undo の計算そのものは、上限の無い添字を要しない。**

取消可能な操作は**確定プレイと状態補正の 2 種**(`ADR-003` D-6 / 要件書 FR-006 `:261`)。
**種別ごとに逆遷移を宣言すれば**、undo は「**スタック先頭の種別を読み、その逆遷移を適用する**」で足りる。
先頭の要素は**種別(有限な enum)+ 状態の形をした差分**なので、**汎用のリスト操作は要らない**。
**これはガードが使えれば素直に書ける形である**(種別でガードし、種別ごとの逆遷移へ分ける)。

**しかし出力側が壁になる。** NFR-019(a)(`:971`)は比較面に

> **遷移後の履歴文脈(取消可能な操作のスタック全体 — 各要素は種別と差分。先頭1件だけではない)**

を要求する。**スタック全体を出力に持つ**ため、**上限の無い配列を出力できないと満たせない**。

**→ C4 の難所は undo の計算ではなく、スタック全体の出力である。問題 II と同じ。**

### 3-4. 問題 I(出力の導出規則)は安い

**現状、遷移は状態にしか代入できず、出力の値を状態から定める規則が schema に無い。**
これは**射程の拡張というより、宣言モデルの欠けた半分**である。

- **式の語は既に揃っている**(`Expression` 8 種・四則・比較・min/max・丸め)
- 追加するのは**出力と式の束縛**だけ
- **有限・型付き・宣言時固定**という性質は変わらない
- **生成時に機械検査できる**(型・範囲・scale は `OutputField` が既に持つ)

**`ADR-003:507` の正当化**(「射程を『状態遷移 + 有限の算術』に限れば**生成器は小さく保て、
生成物の検査を生成時に機械化できる**」)**を損なわない。**

**なお、これはステップ 1 で見つけた「ガードが射程にあるのに実装が無い」と同じ形である** —
**条文が意図した能力が、schema と実装に落ちていない。**

### 3-5. 問題 II(可変長の出力)は正当化を失う

**上限の無い配列型を入れると、D-1 を選んだ理由そのものが崩れる。**

1. **「有限の算術」でなくなる。** `ADR-003:507` の「**射程を限れば**」の射程が、上限の無い列を含む
2. **生成時の機械検査が効かなくなる。** `OutputField` の `range` / `scale` / `unit` は
   **1 つの値に対する制約**であり、長さの定まらない列には当てはまらない
3. **ゴールデンベクタが出力空間を列挙できない。** 要件書 `:947-950` の 3 層担保のうち
   網羅的な正解ベクタが、**長さの上限が無い出力に対して「網羅」を主張できない**
4. **変異テストの非等価変異の生存 0** も、可変長の出力に対する等価判定が重くなる

**つまり D-1 拡張で C10・C12・C13 の集計・C4 の全体出力を書くには、
「制約された宣言モデル」という D-1 の性格そのものを変える必要がある。**

### 3-6. ステップ 4・6 への入力

**D-1 拡張(案 B)の射程は、2 段階に分かれる。**

| 段階 | 中身 | 費用 | 正当化 |
| --- | --- | --- | --- |
| **B-1** | 出力の導出式(C3)+ ガードの実装(ステップ 1)+ 語彙を引く式(C13 の入力側) | **小** | **保てる** |
| **B-2** | 上限の無い配列型(C10・C12・C13 の出力側・C4 の全体出力) | **大** | **失う** |

**B-1 だけでは表現不能 5 件のうち C3 しか閉じない。** 残る 4 件は B-2 を要する。

**したがって「D-1 拡張で 5 件すべてを書けるか」の答えは「書けるが、そのとき D-1 は
制約された宣言モデルではなくなる」である。** DoD 第 3 項の分岐判定では、
**③(D-1 拡張が 5 件を書けない)ではなく、「書けるが正当化を失う」**として扱う。

**この結果は D-2 との比較を単純にする。**

- **D-1 は、可変長の出力を型システムへ入れる必要がある**(上限が無いので「最大 N」で閉じられない)
- **D-2 は、JS の配列をそのまま使える** — 型システムの拡張ではなく実装の問題になる

**ただし D-2 にも固有の壁がある**(厳密な小数・有理数 — TSK-405 が調査中)。**ステップ 6 の四観点で並べる。**

### 3-7. 未確定 16 件への波及(ステップ 1 からの持ち越し)

**整数符号化に依っていた 7 件(C1・C2・C9・C14・C16・C17・C27)は、ガードが使えるなら素直に書ける見込み。**
ただし**本ステップでは個別に確かめていない**(表現不能 5 件の判定に必要なかったため)。

**これは本タスクの射程外とする** — 未確定の内訳は TSK-405 の判定の更新であり、
**本改訂が依存するのは表現不能 5 件だけ**だからである(計画 1 節)。
**TSK-405 へ「ガードが使える前提での再判定」を申し送る。**

## ステップ 4 — D-2 の費用の扱いの決定(2026-10-09)

**決定: ②「未実測」と明示して判定する。スパイクは費用には使わない。**

ステップ 2 が②(抵触しない)、ステップ 3 で D-1 拡張が 4 件を正当化なしでしか書けないため、
計画の実施条件を満たしたうえでの決定である。

### 4-1. なぜ測らないか

**費用の実測は採否を変えない。** 理由は 3 つ。

**① D-1 側の「安さ」の根拠が、ステップ 3 で消えた。**
v0.2 が D-2 を見送った理由 1 は「**数値書式のためだけに払うコストではない**」という
**便益との対比**だった([research.md](../features/adr003-d2-switch/research.md) 6 節)。
いま便益は「数値書式」ではなく「**要件が求める 5 件の計算が書けるかどうか**」である。
しかも D-1 拡張は**上限の無い配列型を入れねばならず、「制約された宣言モデル」でなくなる**(ステップ 3)。
**対比の片側が変わった以上、D-2 の費用を単体で測っても判定は決まらない。**

**② D-1 側の費用も未実測である。**
**生成器 3 言語は固定スタブ**で、遷移も式も評価していない([research.md](../features/adr003-d2-switch/research.md) 1 節)。
**D-1 を採っても実行経路はこれから作る。** つまり比較は「**どちらも未実装・どちらも作る**」であり、
**D-2 の費用だけを測れば、測った側だけが高く見える。** 片側の実測は比較を歪める。

**③ 適合性の差のほうが方式の性質に直結する。**
費用は実装量の見積りだが、**可変長の出力**(D-1 の壁)と**厳密な小数・有理数**(D-2 の壁)は
**方式を選んだ時点で決まる性質**である。**判定を分けるのはこちらである。**

### 4-2. 「未実測」をどう扱うか

**条文に明示する。** v0.2 の理由 1 は費用を列挙しただけで実測を伴っていなかったが、
**そうとは書かれていなかった**。同じ空洞を繰り返さないため、本改訂では次を書く。

- D-2 の費用(**バックエンドの JS ランタイム・境界の直列化・timeout・クラッシュ処理・デプロイ依存**)は
  **本改訂の時点で実測されていない**
- **D-1 の費用も実測されていない**(生成器が未実装のため見積りの基礎が無い)
- **採否は費用ではなく適合性で判定した**(何を根拠にしたかを明記する)

**再評価の契機は既にある** — 見直しトリガー「**対象技術の世代交代** — Pyodide / WASM / JS ランタイムの
運用コストが大きく変わり、D-2 の却下理由が成立しなくなった場合」(`ADR-003:546`)。
**費用が判定を分ける局面になったら、この条で戻れる。**

### 4-3. スパイクの扱い

**PO がスパイクを承認している**(2026-10-09)。**費用には使わない**が、**適合性の検証には使う余地を残す。**

**いま最も判定を分ける未確認は「厳密な小数・有理数を JS で満たせるか」である。**

- 要件書は**投球回を 1/3 回単位の混合分数**(`:1174`)、**球種割合を百分率・整数・四捨五入**(`:1193`)と、
  **丸めの正確さを条文で要求**している
- ADR の型領域は `NumericValue` = **整数・decimal・有理数(分子/分母)**(`:103`)
- **JS の数値は float64 で decimal 型も有理数型も無い**
- **既存の生成 TS formatter は実際にずれている**(Python `1.01` / TS `1.00` ほか — 別タスクで起票済み)

**これは費用ではなく適合性の問題**であり、**満たせないなら D-2 は NFR-018 (b)② を満たせない。**

**TSK-405 が同じ軸を調査中**(2026-10-09 の分担合意)。**その結果で足りるならスパイクは打たない。**
**足りなければステップ 6 の前にスパイクを打つ。**

### 4-4. ステップ 5・6 への入力

- **費用は「未実測」のまま判定へ進む。** 条文に明示する
- **判定の根拠は適合性に置く**(可変長の出力 / 厳密な小数・有理数)
- **四観点のうち「費用」は、両方式とも未実測であることを記録して並べる**
  (D-2 だけ未実測と書くと、D-1 が測られているように読める)
- **スパイクは適合性の検証に温存する**
