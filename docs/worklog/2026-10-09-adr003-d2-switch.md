**判定を左右する報告は、すべて本タスクが原典で追試した。** 結果は [research.md](../features/adr003-d2-switch/research.md)。

**下調べで判定の形が変わった点**:

1. **D-1 の実行経路は存在しない**(追試済み)。生成器 3 言語がすべて固定スタブで、遷移も式も評価していない
   (`backends/python.py` 48 行 / `typescript.py` 42 行 / `sql.py` 38 行)。
   比較は「完成した D-1 vs 新規の D-2」ではなく「**未完成の D-1(+拡張)vs D-2**」である
2. **v0.2 が D-2 を見送った 3 理由は、D-2 の否定ではない**(逐語で確認)。理由 1 は「**数値書式のためだけに**」、

   **D-2 の表の行は「代替案として保持」、見直しトリガー第 1 項は「次点は D-2」と名指ししている**
3. **NFR-018 (b)③ の動的機構の禁止**(要件書 `:952`)が D-2 と緊張しうる。**ADR はこの点を検討していない**。
   **費用ではなく適合性の問題**なので、計画の第 1 関門に置いた

### 既存資産の欠陥を発見(TSK-509 の射程外・別途報告)

**生成される Python formatter と TypeScript formatter が、同じ入力に別の値を返す**(本タスクが実測):

```
入力        scale   Python(Decimal)   TypeScript(float64)
1.005       2       1.01              1.00
0.285       2       0.29              0.28
-0.0001     3       -0.000            0.000
```

Python は `Decimal` + `ROUND_HALF_UP`、TS は `Number(...)` と `Math.floor(abs*10**scale + 0.5)`
(`backend/src/pitchlog/domaingen/formatter.py:190-195`・`:347-356`)。

**検査が拾わなかった理由も確認した**: 生成された TS formatter を node で実行する試験は
`tests/domain/gen/test_formatter.py:333` の **1 件だけ**で、`"1.3"` という**単一の値**を突き合わせている。
要件書 `:949` が 3 層担保の 2 層目として求める「**正本から生成した各実行体どうしの等価性**」が、
**1 つの値の突合に縮退していた**。

**現時点では潜在**(生成器がスタブ・参照実装は製品経路から切り離されている)。
ただし**段階 2 で対象計算を載せ始めると、この穴の上に実データが乗る**。

**TSK-509 への含意**: この食い違いは **D-1 が 2 言語に別々のコードを生成する方式だから**生じている。
D-2 はこの種のずれを構造的に消すが、**代わりに JS に decimal 型が無い問題を背負う**。
**どちらの方式も数値意味論の問題を持ち、形が違うだけ**である。四観点の「同一由来性」は、この実測を踏まえて評価する。

### 計画レビュー(敵対・3 周)— 採否記録

**全 15 件を採用。不採用 0 件。** 回数は設計書 6.3 の上限どおり
(基本枠 2 回〔全文 1 + 差分 1〕+ 2 回目に P0 が残ったため P0 限定の 3 回目が自動追加)。

| 周 | 指摘 | 内訳 | 採否 |

**周を追うごとに起因の比率が上がった**(非起因 8 → 起因 5 → 起因 2)。
**是正が次の穴を生む輪**であり、台帳が記録している型と同じ。

**1 周目の主な指摘**(非起因 — 元の計画の欠陥):

- **条件付きの射程は成立しない**。「方式が決まってから射程を確定する」という組み立てが 3 経路で破綻した:
  ① D-2 を採ると要件書 `:1169` と矛盾したまま approved になる(後送できない)
  ② 3 節の条件付き宣言は `check_plan_docs_sync` を通らない(**検査器は「反映なし」を含む物理行を丸ごと非反映宣言として扱う**)
  ③ D-2 を採ると ADR 内の D-3・D-11・D-1-d が同一文書内で食い違う
- ステップ 1 が「PO 裁定が要る」で**完了扱いになる**
- ステップ 2 が 3 の結果に依存するのに**順序が逆**
- 「測ってから判定する」を選ぶと、**測定が射程外なので本タスク内に結果が無い**

**解き方**: **「決定」と「発効」を分ける**(先例 = 要件書 `BOOT-ACTIVATION`「**本書が approved となることは発効ではない**」)。
D-2 の採用は要件書の規範追随が完了するまで発効せず、発効までは D-1 が現行である。
**レビューは「ADR で同型の先例は確認できなかったが、禁じる規定も無い」と判定した**(3 周目)。

**2〜3 周目の起因 P0**(是正が生んだもの):

- 発効を分けると書いたが、**発効前に D-1 が有効であることを条文に残す**指示が抜けていた
- 棚卸しの範囲を D-3・D-11・D-1-d に絞ったが、**D-8 と帰結の実装順序も D-1 依存**だった
- **`active` の間は `check_plan_docs_sync` が警告止まりで exit 0 を返す** — **`active` での緑は合格の証拠にならない**
- **棚卸しを採否より後に置いた**ため、成立しない経路が見つかっても**採否に戻る先が無い**(順序を入れ替えた)
- **`in-review` 化後の再実行は実装ステップの中で判定できない**(`/pr` の受入条件へ移した)

**最終形**: ステップ **16**・DoD **16 項目**(全項目に担当ステップを対応)。
**DoD 第 3 項は適合性の 4 分岐**(両方可 / D-2 脱落 / D-1 不可 / **両方不適合 = 停止して PO 裁定**)。
