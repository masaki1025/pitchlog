## 3. 語彙 — **免除の根拠は列挙のみ**(射程縮小により全面改稿)

> **⚠ 本節は PO スコープ裁定(射程縮小・2026-09-13)により書き直した。**
> **縮小前は「未達 / 違反 / 既知債務 / 判定不能」の 4 型を定義し、性質による分類で免除範囲を決めていた。**
> **この形が確定ゲート 3 周で別々の穴を開けたため、分類を免除の判定から外した。**

### 3-1. 採った形

**免除の根拠は `BOOT-SEAL`(封印集合への列挙)のみ**である:

> **本規定が免除するのは封印集合に列挙された事項に限る。**
> **列挙されていないものは、宣言の欠落・宣言と実体の食い違い・判定不能のいずれであるかを問わず一切免除しない。**

**「未履行か違反か」を問う必要がない。** 列挙されているか否かだけで決まる。

### 3-2. 3 周で何が起きたか(記録)

| 周 | 論点 | 是正 | 次周の指摘 |
| --- | --- | --- | --- |
| 初周 | **既知債務が「違反」にも該当**し、債務を登録した基盤 PR 自身が違反になる | 分類の優先順位を追加 | 封印が**対象単位**なので別種の違反まで免除 |
| 2 周目 | **封印された対象の生成物が手編集されても免除**される | **宣言の有無**で切り分け | **「宣言外の入口」は `entrypoints[]` 宣言が無いので未履行にも該当** |
| 3 周目 | **振り出し** — 分類が排他的でない | **PO 裁定へ** | — |

**条文は 2204 字 → 4024 字へ膨らみ、条項は 12 → 14 件へ増えていた。**
**塞ぎ方が複雑になるほど条項間の相互作用が増え、是正が次の穴を開けた。**

### 3-3. 報告の語彙としては残る

**免除の判定には使わないが、`BOOT-REPORT` が要求する未解消レポートは
「何が残っているか」を人へ示す必要がある。** そのための記述語として
「宣言が無い」「宣言はあるが実体と食い違う」等を用いることを妨げない。
**ただしそれは報告の語彙であり、免除判定の基準ではない**(`TSK-235` も同じ扱いとした — 2026-09-13)。

### 3-4. **`TSK-379` が導入した「未発効」との衝突**(縮小後も有効)

**要件書 v2.8(`TSK-379`)が `NFR-019(b)` へ発効条項を置き、「未発効」を
「対象経路が実装されていない状態」の意味で導入した。**

**本改訂では「未発効」を使わず「未接続」を用いる**(`BOOT-ACTIVATION` の接続前の状態)。

**向きの非対称を引くときは非対称ごと引く**(`TSK-379` からの助言):

| --- | --- |

## 4. 移行状態の二軸

### 4-1. なぜ二軸か

**同じ状態に 2 つの終了条件を持たせない**(plan.md 3 周目 P1-4)。
「未達 0 かつ債務 0 で終わる」と「停滞したら失効する」は**別の事象**であり、
1 つの状態に両方を持たせると**どちらで終わったのかが判定できない**。

| 軸 | 名称 | 何を表すか | 終了 |
| --- | --- | --- | --- |
| ① | **移行プログラム** | **検査基盤の整備が完了していない**という事実 | **封印集合の未解消 0 件**の成立で**必須ゲートへ自動かつ不可逆に昇格** |
| ② | **緩和されたマージ授権** | **その事実を理由にマージを止めない**という授権 | **有効 → 失効 → 人間の明示的な再承認**を遷移する |

**①が終了すれば②も終了する。②が失効しても①は継続する**(失効中も未解消件数は計上され続ける)。

### 4-2. 軸①: 移行プログラム

| 項目 | 定義 |
| --- | --- |
| **開始** | **移行開始を承認したコミット**(固定 SHA)。§6-1 で定義する |
| **継続条件** | **封印集合の未解消要素が 1 件以上ある** |
| **終了** | **未解消 0 件**の成立をもって**自動的に**終了し、**必須ゲートへ昇格**する |
| **不可逆性** | **昇格後に再び移行状態へ戻る経路を設けない**。戻すには**正本の改訂**を要する |
| **失効との関係** | **②が失効しても①は継続する**。未達・債務の計上は止まらない |

**「自動かつ不可逆」の理由**: 昇格を人間の操作にすると、**未達 0 になっても昇格されないまま
授権が残り続ける**経路ができる。**条件の成立と昇格を同一にする**ことで、この経路を塞ぐ。

### 4-3. 軸②: 緩和されたマージ授権

| 状態 | 定義 | 遷移先 |
| --- | --- | --- |
| **有効** | 停滞エポック内にあり、かつ①が継続中 | **失効**(停滞)/ **終了**(①の昇格) |
| **失効** | 停滞エポック内で**未解消件数**が 1 度も減少しないまま **N マージ**が経過した | **有効**(人間の明示的な再承認) |
| **終了** | ①が昇格した | — |

**`N = 50`**(PO 裁定 B-1'・2026-09-11)。

**失効中の扱い**: **既存の fail-closed が無条件に復帰する。**
移行状態を理由としたマージ可否の別判定は行われず、`NFR-018`(b)・`NFR-019`(a) の
判定どおりにマージ不可となる。

**「無期限の緩和にしない」の担保**(plan.md 射程④): **停滞を時間ではなくマージ本数で測る。**
時間で測ると**作業していない期間も経過する**ため、「進んでいないこと」の測定にならない。

## 5. 機械条件 `M-1`〜`M-5`

plan.md §4-10 が「**design.md が答えを出さなければならない**」と定めた 5 論点。
**各論点に「必須命題・正例・負例・不成立条件」を書く**(「決める」と書いただけの回答を認めない —
plan.md §4-10 の機構 1)。

> **⚠ 射程縮小(PO 裁定 2026-09-13)により、本節の位置づけが変わった。**
>
> **確定ゲートで起因過半が 2 周連続**(7.3-6)。**3 周かけて「未履行と違反の切り分け」を 3 度書き直し、
> そのたびに別の穴が開いた**(初周: 既知債務が違反にも該当 → 優先順位を追加 / 2 周目: 封印が対象単位で
> 別種の違反まで免除 → 宣言の有無で切り分け / 3 周目: 「宣言外の入口」は `entrypoints[]` 宣言が無いので
> 未履行にも該当 → **振り出し**)。
>
> → **正本は「性質による分類」を免除の判定に用いるのをやめ、`BOOT-SEAL`(封印集合への列挙)のみで決める。**
> **本節の `M-1`〜`M-5` は、正本が確定する機械条件ではなく、`TSK-235` が実装で満たすべき要求**となる。
> **正本は充足すべき条件を定め、判定方法を実装へ委ねる**(要件書 `NFR-018` (e) の末尾「本規定が実装へ委ねる事項」)。
>
> **本節の内容は破棄しない** — **委任先が満たすべき条件(必須命題・正例・負例・不成立条件)として `TSK-235` へ渡す。**
> **空手形にしないための材料である**(plan.md §4-10 の機構 1)。

**用語**: 以下で「**対象**」は要件書 `NFR-018` の「対象」欄が列挙する対象計算を指し、
「**段階**」は `ADR-003` 帰結 1 の着手順序 4 段階を指す。

### 5-1. `M-1`: 段階 2 の PR の判定方法

**問題**(plan.md 2 周目 P0-1): **paths 接触では判定できない。**
発効原子性を満たす段階 1 の基盤 PR は必然的にマニフェストと債務台帳へ触れるため、
paths 判定だと**発効 PR 自身が段階 2 と誤判定され、厳密減少に失敗して発効できない**。

#### 必須命題

> **`M-1-a`** 段階 2 の PR とは、**base から head へのあいだに、安定した対象 ID が
> ちょうど 1 件、実在集合へ新規に加わった** PR をいう。
>
> **`M-1-b`** 「実在集合へ加わった」とは、当該対象について
> **①宣言モデルの正本 ②生成物 ③製品経路の呼び出し部 ④その対象の 3 層検査**
> の **4 つがすべて同一の PR に揃っている**ことをいう(`ADR-003` 帰結 1 の段階 2 の逐語
> 「対象計算 1 件ごとに、宣言モデルの正本・生成物・製品経路の呼び出し部・その対象の 3 層検査を
> 『同一の変更』として追加する」)。
>
> **`M-1-c`** 判定は **paths ではなく意味差分**で行う。**マニフェスト・債務台帳・検査器への
> 接触は判定に用いない。**
>
> **`M-1-d`** **2 件以上が同時に加わった PR は段階 2 ではない**(段階 2 は「1 件ごと」を要求する)。
> この場合は **fail** とし、PR の分割を求める。

#### 正例

| # | PR の内容 | 判定 |
| --- | --- | --- |
| 正-1 | 対象「終了判定」について ①〜④ を揃えて追加。他の対象に触れない | **段階 2** |
| 正-2 | 正-1 と同じ内容に加え、当該対象の債務 ID を解消済み集合へ移す | **段階 2**(債務の解消は段階 2 に付随する) |

#### 負例(**段階 2 に分類されてはならないもの**)

| # | PR の内容 | 判定 | 理由 |
| --- | --- | --- | --- |
| 負-1 | **発効 PR** — 判定器・未解消レポート・観測機構・負例を CI へ接続する。対象は 1 件も加わらない | **段階 2 ではない** | 実在集合の差が 0。**paths ではマニフェストに触れるため誤判定される** |
| 負-2 | **台帳保守** — 債務台帳の書式・コメントを整える。対象は加わらない | **段階 2 ではない** | 実在集合の差が 0 |
| 負-3 | **reseal** — 封印資産の digest を追随させる | **段階 2 ではない** | 実在集合の差が 0 |
| 負-4 | **宣言だけの変更** — マニフェストに対象を宣言するが、生成物・呼び出し部・3 層検査が無い | **段階 2 ではない**(かつ **fail**) | `M-1-b` の 4 点が揃っていない。**宣言だけで未解消件数を減らせる経路を塞ぐ** |
| 負-5 | 対象を 2 件同時に追加 | **段階 2 ではない**(かつ **fail**) | `M-1-d` |

#### 不成立条件(**この条件下では `M-1` の判定自体が成立しない → fail-closed**)

- **安定した対象 ID の体系が存在しない**(§8 の ID 規約が未確定)
- **base と head のいずれかで実在集合が算出できない**(マニフェストの解析に失敗する)
- **base が移行開始の固定 SHA の祖先でない**(履歴が繋がらない)

→ **いずれも「判定不能」として扱い、`ADR-003` D-11 の既定どおり合格としない**(§3-1 の型 4)。

### 5-2. `M-2`: 停滞エポックの定義と「1 マージ」の母集合

**問題**(plan.md 2 周目 P0-2・3 周目 P1-3): 「連続 50 マージで減少 0 なら失効」を測るには、
**何を 1 マージと数えるか**と**いつエポックが始まるか**を一意に決める必要がある。

#### 必須命題

> **`M-2-a`(エポックの開始)** 停滞エポックは次の 3 時点で開始(リセット)する:
> **①移行状態の発効時**(= 判定機構が CI の必須経路へ接続された時点。**正本の approved 時点ではない**)
> **②**未解消件数** が減少した時点** **③失効後の正当な再承認が成立した時点**。
>
> **`M-2-b`(1 マージの母集合)** 「1 マージ」は **`develop` の第一親をたどった列に現れる
> PR 統合コミット**を数える。**feature 側が `develop` を取り込むマージコミットは数えない。**
>
> **`M-2-c`(候補 PR の評価)** 判定対象の PR は、**固定された base に対する次の 1 本**として
> 評価する。**base が評価中に前進した場合は再評価する。**
>
> **`M-2-d`(観測の開始時点)** **観測は移行状態の開始と同時に始まる。**
> ②の失効判定は①の昇格判定より**先に必要になる** — ①の昇格(未達 0 かつ債務 0)は遠い先だが、
> **②の 50 マージのカウントは開始直後から走る**ため。
>
> **`M-2-e`(履歴の保持場所)** **未解消件数** の履歴は **CI が生成する機械可読な未解消レポート**(`BOOT-REPORT`)に
> 記録し、**エポック開始時点の値と現在値の比較**で減少を判定する。
>
> **`M-2-f`(優先順位)** **50 本目のマージと「前進」または「自動昇格」が同一の変更で成立した場合、
> 前進・昇格を優先する**(失効させない)。**減少が起きている以上、停滞ではないため。**

#### 正例

| # | 状況 | 判定 |
| --- | --- | --- |
| 正-1 | エポック開始から 49 マージ経過、50 本目で未達が 1 減った | **失効しない**。エポックが②でリセットされる |
| 正-2 | 50 本目のマージで最後の未達と債務が同時に 0 になった | **失効しない。①が昇格して終了する**(`M-2-f`) |

#### 負例

| # | 状況 | 判定 | 理由 |
| --- | --- | --- | --- |
| 負-1 | 50 マージのあいだ、宣言だけを増やして未解消件数を見かけ上減らした | **減少に数えない → 失効する** | `BOOT-PROGRAM` が「生の検査結果で示す」ことを要求する |
| 負-2 | feature ブランチが `develop` を 10 回取り込み、それを 10 マージと数える | **数えない** | `M-2-b` |
| 負-3 | 移行状態が**正本で approved になった時点**からカウントを始める | **誤り** | `M-2-a` ①は**発効時**。approved は発効ではない(§7) |

#### 不成立条件

- **履歴が不足している**(エポック開始時点のレポートが存在しない)
- **base が前進していて固定できない**
- **`develop` の第一親をたどれない**(履歴の書き換え等)

→ **いずれも fail-closed**。**停滞していないことを示せない場合は失効扱いとする**
(「測れないから継続」にしない)。

### 5-3. `M-3`: 固定 SHA と再承認エポックの分離

**問題**(plan.md 2 周目 P0-3・3 周目 P0-1): 再承認で固定 SHA を更新できると、
**それまでに追加・再導入・復活した債務を新しい開始集合へ吸収でき、比較から消せる。**

#### 必須命題

> **`M-3-a`** **2 つの基準を分離する**:
>
> | 基準 | 用途 | 更新可能性 |
> | --- | --- | --- |
> | **初回開始 SHA** | **債務比較の基準** | **不変**。更新には**正本の改訂**を要する |
> | **再承認エポック** | **50 マージを数える起点** | **再承認で更新できる** |
>
> **`M-3-b`** **再承認が更新できるのは再承認エポックのみ**であり、**初回開始 SHA・初回対象集合・
> 初回債務 ID 集合には触れられない。**
>
> **`M-3-c`** **解消済み債務 ID 集合は追加のみ可能な単調集合**とする
> (**復活の検知に必要な履歴を保つため** — 削除を許すと「解消 → 復活 → 解消済みから削除」で
> 復活が見えなくなる)。
>
> **`M-3-d`** **初回開始 SHA を書き換える PR は無条件に fail** とする。

#### 正例

| # | 状況 | 判定 |
| --- | --- | --- |
| 正-1 | 失効後に人間が再承認し、再承認エポックが更新された。初回開始 SHA は不変 | **正しい** |
| 正-2 | 債務 A を解消し、解消済み集合へ A を追加した | **正しい**(単調に増える) |

#### 負例

| # | 状況 | 判定 | 理由 |
| --- | --- | --- | --- |
| 負-1 | 再承認と同時に初回開始 SHA を現在の `develop` へ更新した | **fail** | `M-3-b`・`M-3-d`。**増えた債務が吸収される** |
| 負-2 | 解消済み集合から ID を削除した | **fail** | `M-3-c`。復活が検知できなくなる |
| 負-3 | 債務 A を解消済みにしたあと、再び A が未宣言になった | **fail** | §6 の規律③(解消済みからの復活) |

#### 不成立条件

- **初回開始 SHA が到達不能**(履歴の書き換え・浅いクローン)
- **初回債務 ID 集合が読めない**

→ **fail-closed**。

### 5-4. `M-4`: 再承認の機械的経路

**問題**(plan.md 2 周目 P1-4): 失効後は既存 fail-closed が無条件復帰するため、
**再承認を反映する PR 自体が通常ならマージ不可**になる。

#### 必須命題

> **`M-4-a`(承認者)** **要件書 8 章の判定者**(システム管理者 = プロダクトオーナー)に固定する。
> **既存の承認主体を流用し、本改訂で新しいロールを作らない。**
>
> **`M-4-b`(記録場所)** 再承認は**移行状態の宣言ファイル**に記録する
> (**ファイル名・スキーマ・フィールド名は本改訂で決めない** — `TSK-235` の射程。plan.md「やらないこと」)。
>
> **`M-4-c`(単回性)** **1 回の再承認は 1 つの再承認エポックのみを開始する。**
> 同一の承認記録で 2 度エポックを開始できない。
>
> **`M-4-d`(失効中に許される変更範囲)** **失効中にマージできるのは、次のいずれかに限る**:
> **①**未解消件数** を減少させる変更** **②再承認そのものを記録する変更**
> **③移行状態と無関係な変更**(`NFR-018` の対象計算・検査基盤に一切触れない PR)。
>
> **`M-4-e`(再承認 PR の扱い)** **②の PR は、移行状態の授権ではなく `M-4-d` ②の規定によって
> マージ可能となる。** この経路は**再承認の記録のみを含む PR に限る**(他の変更を同梱した PR は
> この経路を使えない)。
>
> **`M-4-f`(自動昇格後の禁止)** **①が昇格した後の再承認は受け付けない**(fail)。
>
> **`M-4-g`(有効期限)** **再承認エポックに時間的な期限は設けない。**
> 期限は `M-2` のマージ本数で測る(§4-3 の「時間で測らない」理由と同じ)。

#### 正例

| # | PR | 判定 |
| --- | --- | --- |
| 正-1 | 再承認の記録のみを含む PR | **マージ可**(`M-4-d` ②・`M-4-e`) |
| 正-2 | 失効中に、対象を 1 件実在させて未達を減らす PR | **マージ可**(`M-4-d` ①) |
| 正-3 | 失効中に、フロントエンドの表示文言を直す PR(検査基盤に触れない) | **マージ可**(`M-4-d` ③) |

#### 負例

| # | PR | 判定 | 理由 |
| --- | --- | --- | --- |
| 負-1 | 再承認の記録と、検査器の変更を同梱した PR | **マージ不可** | `M-4-e`。**再承認を口実に他の変更を通す経路を塞ぐ** |
| 負-2 | 昇格後に再承認を記録する PR | **fail** | `M-4-f` |
| 負-3 | 同じ承認記録を参照して 2 度目のエポックを開始する | **fail** | `M-4-c` |

#### 不成立条件

- **承認記録が機械的に読めない**(自由記述のみ)
- **承認者が要件書 8 章の判定者と一致しない**

→ **fail-closed**。

### 5-5. `M-5`: 未解消件数の原子単位(委任 ①・要件書 (e) の拘束③が対応)

**問題**(plan.md 2 周目 P1-5): 行の統合・ワイルドカード化・改名・分類変更で
**対象計算を整備せずに値を減らせる。**

#### 必須命題

> **`M-5-a`(原子単位)** **未解消件数は封印集合の要素の単位で数える。**
> **要素は D-11 が要求する宣言の 1 件、または (b) が要求する事項の 1 件に対応する**(包括要素を置かない — 要件書 (e) `BOOT-SEAL` の拘束③)。**行・表・ファイルの単位では数えない。**
>
> **`M-5-b`(実測との差分)** **未解消件数は、封印集合から解消済み集合を引いた差**である。
> **宣言集合ではなく実在集合を引く**(plan.md §4-2 の契約 5 — 宣言と実測を別語で呼ぶ)。
>
> **`M-5-c`(実在の条件)** ある対象が実在集合に属するのは、
> **`M-1-b` の 4 点が揃い、かつその対象の 3 層検査が緑である**ときに限る。
>
> **`M-5-d`(行構造の変更は減少に数えない)** 対象 ID の**統合・ワイルドカード化・改名・分類変更**は
> **減少に数えない**。改名は §8 の ID 規約で**禁止**する。
>
> **`M-5-e`(減少の要件)** 減少を主張するには、**独立して実測した入口集合と、必要層の充足**を
> 示さなければならない。**宣言の更新だけでは減少しない**(`M-1` 負-4 と対)。
>
> **`M-5-f`(解消の成立)** **解消は、当該事項が実際に充足されたことを、本規定による免除を適用しない生の検査結果で示したときに成立する**(要件書 (e) `BOOT-PROGRAM`)。**宣言の更新のみをもって解消としてはならない。**

#### 正例

| # | 状況 | **未解消件数** の変化 |
| --- | --- | --- |
| 正-1 | 対象「捕球選手推定」について 4 点を揃え、3 層検査が緑になった | **当該対象に係る封印要素が解消** |
| 正-2 | 封印要素を 1 件解消した | **未解消件数 −1**(**二重に数えない** — 単一の集合で測るため) |

#### 負例

| # | 状況 | **未解消件数** の変化 | 理由 |
| --- | --- | --- | --- |
| 負-1 | 対象 A と対象 B を 1 行に統合した | **変化なし** | `M-5-a`・`M-5-d`。ID の単位で数えるため |
| 負-2 | 対象欄の記述をワイルドカード(「座標変換一般」)へ変えた | **変化なし** かつ **fail** | `M-5-d`。要件書の対象欄の改訂は本改訂の射程外(plan.md「やらないこと」) |
| 負-3 | マニフェストに対象 C を宣言したが、生成物と呼び出し部が無い | **変化なし** | `M-5-c`・`M-5-e` |
| 負-4 | 3 層検査のうち変異層だけが緑で、他の 2 層が無い | **変化なし** | `M-5-c`。`NFR-018` (b)②「いずれか 1 層でも欠ければ満たさない」 |

#### 不成立条件

- **対象 ID の体系が無い**(§8 未確定)
- **実在集合が算出できない**
- **3 層検査の結果が読めない**

→ **fail-closed**。

## 6. 封印集合の規律(射程縮小後は 3 規律 + 範囲の要求)

**債務 = 移行開始時点で既に未宣言であった対象を、全件列挙して封印したもの。**
**封印は「増やさないこと」と引き換えに授権を与える機構**である。

### 6-1〜6-3. 封印の 3 規律(**条文は正本が正** — 本節は要旨と根拠のみ)

> **⚠ 逐語の引き写しをやめた**(2026-09-13)。**縮小前は 3 規律の条文を全文で持っていたが、
> 正本の改訂のたびに追随を要し、実際に漏れた**(確定ゲート 2・3・4 周目で 3 周連続の指摘)。
> **`TSK-235` も同じ構造を持っていたことを実測で確認した**(先方の `BOOT-` 参照 28 箇所・
> うち複数が逐語 — 2026-09-13)。

| 条項 | 要旨 | なぜその形か |
| --- | --- | --- |
| **`BOOT-SEAL-BASE`** | 比較元は**移行開始を承認したコミットの完全な commit OID**。**merge-base は不可** | **merge-base は base が進むと動く**ため、「開始時点の集合と比べて増えていないこと」を見る用途に適さない(`TSK-235` から訂正を受領 — 1 周目 P0-6) |
| **`BOOT-SEAL-IMMUTABLE`** | 比較元は**当該 PR から変更できない**。更新には**正本の改訂**を要し、**再承認では更新できない** | 更新できると、**それまでに追加・再発した事項を新しい開始集合へ吸収して比較から消せる**(`M-3` の吸収) |
| **`BOOT-SEAL-MONOTONE`** | **追加・再発・削除**のいずれも不合格。**解消済みの記録は追加のみ可能** | **削除を許すと「解消 → 再発 → 解消済みから削除」で再発が見えなくなる**(3 周目 P0-1) |

**粒度の拘束 3 つ**(識別子の安定性 / 封印後の範囲変更の禁止 / 包括要素の禁止)は
**`BOOT-SEAL` 本体が持つ**(4 周目 指摘 1 で追加 — §6-4)。

### 6-4. 封印集合の範囲(射程縮小により `BOOT-SEAL-SCOPE` は撤去)

**縮小前は `BOOT-SEAL-SCOPE` として「D-11 が要求する宣言のうち未宣言であったものすべて・
実行入口に限定しない」と定めていた。**

**射程縮小により、範囲の定義は `BOOT-SEAL` 本体へ統合された**:

> **移行開始時点で本項の達成条件 (b) および `ADR-003` D-11 が要求していながら充足されていなかった事項**

**「宣言のうち未宣言のもの」から「要求されていながら充足されていなかった事項」へ広がっている** —
**宣言の有無を問わないため、実行入口に限定されないことは自明になった**(別条項で述べる必要がない)。

**要素の粒度についての拘束は `BOOT-SEAL` が持つ**(確定ゲート 4 周目 指摘 1 で追加):
**①識別子の安定性 ②封印後に要素の内容・適用範囲を変更しない ③包括要素を置かない**。

### 6-5. 封印の自己点検 — **片側検査になっていないか**

plan.md §4-2 の契約 5 が要求する自己点検を、本節自身に当てる。

| 検査 | 宣言側 | 実測側 | 両側にあるか |
| --- | --- | --- | --- |
| 封印集合の重複拒否 | ✅ 封印集合の要素は一意 | ✅ 実在集合の要素も一意 | **両側** |
| 追加の検出 | ✅ 封印集合に無い | ✅ 実測で未宣言 | **両側** |
| 復活の検出 | ✅ 解消済み集合に在る | ✅ 実測で未宣言 | **両側** |

**`TSK-317` が踏んだ型**(`check_authz_catalog.py` は `sealed_assets` 側に重複拒否があるのに
`input_assets` 側に無かった)を、**本改訂の封印では両側に置く**。

## 7. 発効原子性

### 7-1. 何が揃ったときに発効するか

**要旨**(**条文は正本が正**): **本規定の各条項を機械的に判定する機構**と、
**各条項が不合格とする事象がいずれも不合格となることを示す負例**とが、
**すべて同一の変更(= `develop` へ統合される 1 つの PR)で CI の必須経路へ接続された時点**をもって発効する。
**接続前は「定義済みだが未接続」であり、既存の fail-closed が維持される。**

**正本が課す 3 要求**(機構と負例の具体的な構成は `TSK-235` が定める):

| # | 要求 |
| --- | --- |
| ① | **本規定のすべての条項について、その違背を検出する機構が存在すること** |
| ② | **各条項が不合格とする事象について、それが実際に不合格となることを示す負例が存在すること** |
| ③ | **軸①の自動昇格および軸②の失効が、実際にその条件で成立することを示す正例が存在すること** |

**当初 7 点を列挙し、2 周目で 10 点へ拡張したが、3 周目で「列挙が閉包でない」と指摘された**
(自動昇格を「不合格とする負例」へ誤って入れていた — **残務 0 での昇格は成功させるべき正遷移**。
また⑩が「違反・判定不能を免除しない」検査なのに負例は違反だけで判定不能を捕捉していなかった)。

→ **射程縮小により、点の列挙をやめ「全条項に機構と負例がある」という要求へ置き換えた。**
**列挙は条項が増減するたびに追随を要し、追随漏れが構造的に生じる。**

**7 点では閉じていなかった**(初周 指摘 5): 当初の 7 点は**判定器の責務を二軸判定に限定**しており、
**`BOOT-SEAL-*`・`BOOT-NO-CLAIM`・`BOOT-REAPPROVAL` を検査する機構も負例も発効条件に無かった。**
→ **7 点を形式上満たしながら、債務の追加や充足の誤表示を止める検査が未実装のまま発効できた。**

**「未接続」の語については §3-4 を参照する**(`TSK-379` の「未発効」と区別する)。

### 7-2. なぜ観測機構(4)を同一変更に含めるか

**②の失効判定は①の昇格判定より先に必要になる** — ①の昇格(未達 0 かつ債務 0)は遠い先だが、
**②の 50 マージのカウントは開始直後から走る**。**発効時に観測機構が動いていなければ
失効判定が成立しない**ため、両者を同一変更に含めることを条文で要求する
(`TSK-235` からの指摘 — **先方の実装順序が一意に決まる**)。

### 7-3. 発効と approved の区別

| 時点 | 何が起きるか | 移行状態 |
| --- | --- | --- |
| 3 正本が **approved** になる | **条文が確定する** | **定義済み・未接続**。**既存の fail-closed が維持される** |
| **10 点 + 必須の負例**が CI の必須経路へ接続される | **発効する** | **有効**。停滞エポックの観測が開始する(`M-2-a` ①) |

**approved は発効ではない。** この区別を条文に明記する(§5-2 負-3 が塞ぐ経路)。

### 7-4. コードは本改訂で書かない

**10 点と必須の負例の実装は `TSK-235` の射程**である(plan.md「やらないこと」)。
**本改訂が拘束するのは「揃っていなければ発効しない」という条件のみ**であり、
**ファイル名・スキーマ・フィールド名は正本に書かない。**

### 7-5. 自己点検 — **全条項に「不合格とする事象」があるか**(2026-09-13・5 周目の依頼で実施)

**`BOOT-ACTIVATION` の①「違背を検出する機構が存在すること」は性質表明である**
(**機構が存在するだけでは、それが動くことを示さない**)。**②の負例が①の実効性を担保する構造**にしてあるが、
**②が成立するのは当該条項が「不合格とする事象」を持つ場合に限る。**

→ **12 条項を機械的に点検した**(否定表現 `不合格` / `してはならない` / `妨げない` /
`受け付けない` / `数えない` / `用いてはならない` / `みなさない` / `できない` / `適用しない` の有無):

| 結果 | 条項 |
| --- | --- |
| **不合格とする事象を持つ(11 件)** | `BOOT-SEAL` / `-PROGRAM` / `-GRANT` / `-REAPPROVAL` / `-NO-CLAIM` / `-REPORT` / `-SEAL-BASE` / `-SEAL-IMMUTABLE` / `-SEAL-MONOTONE` / `-STALL` / `-ACTIVATION` |
| **持たない(1 件)** | **`BOOT-STATE`** — 逐語「検査基盤の導入期を**移行状態**と呼び、次の二軸で定める。**同じ状態に 2 つの終了条件を持たせない**」 |

**`BOOT-STATE` は定義のみで規範を持たない。** **②の負例では担保されず、性質表明のまま残る。**

→ **`kind` を `補足` へ是正した**(§12)。**`TSK-235` はこの ID に依拠してはならない** —
**依拠すると「授権が実在する」という照合が、規範でないものに対して成立してしまう**(空振り)。
**依拠先は軸ごとの実体条項**(`BOOT-PROGRAM` / `BOOT-GRANT`)である。

**この点検は `TSK-235` の担当セッションが示した 3 類型**(**負例 / 正例 / 性質表明**)**を道具として行った**
(2026-09-13)。**先方は自分の 29 ステップを数えようとして「2 分類では数えられない」ことに気づき、
第 3 の類型を見つけた。** **性質表明は「動く機構が無くても成立する」ため、負例より危ない場合がある。**

## 8. 条項 ID の体系

### 8-1. 名前空間 — **`BOOT-` を採る**

**既存 ID との衝突を実測した**(2026-09-13・`docs/**/*.md`・`docs/legacy/` 除外):

| 候補接頭辞 | 既存の出現 |
| --- | --- |
| **`BOOT-`** | **0 件** |
| `TRANS-` | 0 件 |
| `MIGR-` | 0 件 |
| `BT-` / `MG-` / `TR-` | 0 件 |

**既存の主要接頭辞**(3 件以上の実測・上位): `TSK`(4883)/ `FR`(4223)/ `NFR`(2994)/
`P1`(1543)/ `REQ`(1307)/ `ADR`(1015)/ `P0`(676)/ `P2`(407)/ `DL`(319)/ `SP`(259)/
`AUTH`(41)/ `CATALOG`(18)/ `REJ`(23)/ `PROP`(50)ほか。

→ **`BOOT-` を採る**(bootstrap = 導入期。**2 文字略号は将来の衝突余地が大きい**ため 4 文字を採る)。

### 8-2. ID の規約(`TSK-235` の 4 要求を受け入れる)

| # | 規約 | 根拠 |
| --- | --- | --- |
| 1 | **粒度は条項単位**(節単位にしない) | 節単位だと、単調性だけに依拠するステップが「移行状態の定義」全体を指すことになり、**単調性の条文が消えても実在検査が通ってしまう** |
| 2 | **意味的な安定 ID**(節番号を含めない) | 番号ベースは**改訂で節が動いた瞬間に照合が全滅**する |
| 3 | **一度付けた ID は改訂で改名しない**(追加は自由) | 改名は**偽の発火**をする(授権は生きているのに「実在しない」と判定する) |
| 4 | **削除・失効時は ID を消してよい** | その場合の発火は**正しい発火**(依拠していた授権が撤回されたなら `TSK-235` は止まるべき) |

**非対称は 3 段**(`TSK-235` が §12-1-b-1 で確定した照合方式):
**改名 = 偽発火 → 条文側が禁止** / **削除 = 真発火 → 停止** / **内容変化 = 再確認 → 停止しない**。

### 8-3. digest 計算前の正規化規約

> **`BOOT-ID-NORMALIZE`** 条項 digest の計算前に、**空白の連続を単一空白へ畳み、
> 行末空白と改行を正規化する。それ以外は無加工。**

**理由**: 正本は日本語 Markdown で**行を手で折り返している**ため、**折り返し位置を変えるだけ(reflow)で
生テキストの digest が変わる**が**規範は変わっていない**。そのままでは `TSK-235` の②が
**偽の再確認を大量に出す**。この正規化により **reflow では発火せず、語句の変更では発火する**。

> **混同注意**: `TSK-235` の §7-3 に「**比較器は正規化しない**」という規約があるが、
> **あれは表示値の比較**(`ADR-003` の lossless 原則)で**別物**。**両者を別の名前で呼ぶ** —
> **表示値比較 = lossless / 条項 digest = 正規化あり**。

### 8-4. 条項 ID 対応表の必須列

| 列 | 用途 |
| --- | --- |
| **条項 ID** | 実在照合の鍵 |
| **規範の所在**(正本と条項名) | 人間の追跡 |
| **範囲の切り出し規則** | digest の対象範囲。**表形式の条項では「規範を担うセル」に限る**(行全体だと列を 1 つ足すだけで全条項が一斉に再確認になる) |
| **版と `status`**(**行ごと**) | 「依拠先は `approved` 版に限る」検査の入力。**表全体で 1 つでは不足** |
| **`superseded_by`** | **「撤回」と「分割・統合」の区別**。分割・統合を②の再確認(停止しない)へ落とす |
| **`kind`**(規範 / 補足) | 「依拠先が `規範` でない行なら fail」の機械検査 |
| 一行の要旨 | **人間向け。本機構の検査の入力にはしない**(表に明記する) |

**対応表そのものの不変条件**: **条項 ID の重複を許さない**(`TSK-235` からの要求・2026-09-12)。
**対応表の生成時に一意性を機械検査する** — §4-2 の契約 5 の自己点検を**本タスク自身の成果物にも当てる**。

## 10. `D-xx` の配置決定と選定理由

### 10-1. 規範をどこへ置くか

### 10-2. `ADR-003` に規範を置かない原則との関係

`TSK-379` が ADR-004 で確立した原則(**ADR は争点・決定・理由・却下案を持ち、規範は持たない**)と、
本改訂の **D-13 新設**は矛盾しないか。

**矛盾しない。** D-13 が置くのは**位置づけの決定**であり、**適用条件・合格述語・量化子を持たない**。
**規範は要件書 `NFR-018` (e) 側にあり、D-13 はそれを参照する。**

**検証可能な境界**(ADR-004 の型を借りる): **D-13 から条項参照(`NFR-018` (e))を外すと、
規範として読めなくなること。** 読めてしまうなら規範を持っている。

### 10-3. `BOOT-ID-NORMALIZE` を正本へ置かない理由

**条項 digest の正規化規約は、`TSK-235` の照合機構の実装詳細**である。
**正本へ置くと、先方の実装方式が変わるたびに正本の改訂が要る。**

→ **本書に置き、`TSK-235` へ申し送る。** ただし **`TSK-235` は本書の記述に依拠できない**
(design.md はゲート対象外)ため、**先方が自身の design.md で確定する**。
**本改訂が保証するのは「条項 ID の安定」のみ**である(plan.md §4-10 の合意どおり)。
