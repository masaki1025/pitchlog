## 1. 背景・目的

**Notion タスク**: [TSK-355](https://app.notion.com/p/3d693b75e68781b3b9f8d441f1d1cde5)(高 / 5pt)

TSK-235(ドメイン計算の宣言モデル・生成器・検査基盤)の**敵対レビュー 3 周目 P0-1** により発生したブロッカ。
TSK-235 は停止中で、本タスクの完了を待っている。

### 1-1. 矛盾の実体

TSK-235 は「検査基盤の導入期は、未整備を **未達**(exit 0)と **既知債務**(承認時点の既知債務・封印済み・
exit 0)として扱い、債務が空になったら必須ゲートへ自動かつ不可逆に昇格する」という移行状態を設計した。
**この移行状態が正本に授権を持たない。**

| 正本 | 逐語 |
| --- | --- |
| 要件書 `NFR-018` 達成条件 (b) の fail-closed 行 | 「**未分類・判定不能は合格としない**(fail-closed)。**正解ベクタが未整備の間、変異テストの生存率が閾値を超える間は、いずれも不合格として扱う**」 |
| `ADR-003` D-7 実行契機表 (b)③ 行 | 「**(b)③ 構成の完全性**(D-11)| **PR 必須** | … | **マージ不可**」 |

`(b)③` は「宣言集合と実在入口集合の差で fail」するため、**対象計算が未登録のあいだは必ず差が出て
マージ経路が無くなる**。

### 1-2. 本改訂の位置づけ — **明示的な経過規定**(1 周目 P0-1 で改めた)

**当初案(「fail-closed への例外ではなく、未定義の空枠を埋める」)は撤回した。** 計画レビュー 1 周目が
これを**成立しない**と判定し、原典で確認した結果**その判定が正しかった**。

> `ADR-003` の段階 1 は**作業順序を定めているだけ**で、既存の一般的なマージ条件を解除していない。
> 段階 3 の「当該対象の全緑」は段階 2 の変更に追加される対象単位条件であり、
> 段階 1 を D-7 や `NFR-018` の適用外にする文言ではない。

したがって**段階 1 にも「未整備は不合格」と「PR 必須・マージ不可」が既に適用されている**。
本改訂は「例外の不在」を埋めるのではなく、**充足判定の fail-closed を維持したまま、
閉じた移行状態に限りマージ可否を別判定する経過規定を新設する**改訂である。

**「例外ではない」と書いてはならない** — 書くと**優先関係が定義されないまま**になる。条文は次を明示する:

1. **優先関係**(移行状態の条項が `NFR-018` 達成条件 (b)・`NFR-019` 柱書・D-7・D-11 のどれに対して
   どう優先するか)
2. **移行プログラムの開始・終了条件**と、**緩和されたマージ授権の発効・失効・再承認条件**
3. **緩和されたマージ授権が有効でない間は既存規則が無条件に戻ること**

**fail-closed の由来**(要件書 v2.1・人間裁定 2026-08-17 — 旧 NFR-011 の文言のまま**多重実装が 1 年以上
解消しなかった**事故を二度と起こさない意図)を条文の根拠節に引用し、**経過規定がその意図を損なわないこと**を
示す。**`fail-closed` に経過措置を認めた前例は全数確認で 1 件も無い**(research.md §7-4)。

**「空枠か例外か」は主観では判別しにくい — 同一原典から同じ誤読が 2 回生じている**
(2026-09-11・TSK-235 と共有。**条文の根拠節でこの事実を引く。ただし下記の限定を必ず添える**):

| # | 誰が | いつ | 何を | 結果 |
| --- | --- | --- | --- | --- |
| 1 | **TSK-235** | 2026-09-01〜09-10 | `bootstrapDebt` を「**もともと空いていた枠を埋めるもの**」と認識して設計を続行 | 敵対レビュー 3 周目 P0-1 で「**正本の授権が無い**」と否決 |
| 2 | **TSK-355(本タスク)** | 2026-09-10 | 同じ発明を見て「**fail-closed の例外ではなく未定義の空枠を埋める**」と立てた | 計画レビュー 1 周目 P0-1 で「**段階 1 は作業順序を定めているだけで既存のマージ条件を解除していない**」と否決 |

**交絡(先に明示する)**: **2 件とも同じ発明(`bootstrapDebt`)を見ている。** 本タスクの 1 周目は
TSK-235 の設計を読んだうえでの立論であり、**完全に独立した 2 標本ではない。**

**それでも証拠として成立する理由**: ①担当・タスク・レビュアがすべて別 ②**本タスクは原典
(`ADR-003` 帰結 1 の段階 3 の括弧書き「未完成のあいだ適合と判定しないであって、実装を禁じるもの
ではない」)を自分で読んだうえで同じ結論に達している** — **先方の結論を鵜呑みにしたのではなく、
同一原典から同じ誤読をしている**。

**示せること / 示せないこと**:

| | 内容 |
| --- | --- |
| **示せる** | 「注意すれば気づける」類の失敗ではない。**同一原典を読んでも同じ側へ倒れる** |
| **示せない** | 誤読の**発生率** / **設計を見ていない第三者でも同じ誤読をするか** |

→ 本改訂が「経過規定の新設」として書かれなければならない理由の**限定つきの裏づけ**であり、
**同時に TSK-235 の見直しトリガー 16(改)が要る理由**でもある(先方の design.md §12-1-b に
同じ事実を同じ限定つきで記録)。**両者が同じ交絡を負うため、限定の書き方を揃えてある** —
片方が限定なしで書くと、そちらが崩れた際に連鎖して弱くなるため。

## 2. スコープ

### やること

1. **移行状態の定義** — **状態ベース**で定める(1 周目 P0-2 で改めた。**段階で限定しない**)。
   **二軸で定義する**(3 周目 P1-4 — 同じ状態に 2 つの終了条件を持たせない):

   | 軸 | 名称 | 継続条件 | 終了 |
   | --- | --- | --- | --- |
   | ① | **移行プログラム** | 「**未達 0 かつ債務 0**」が成立するまで継続 | 成立時に**必須ゲートへ自動かつ不可逆に昇格**して終了 |
   | ② | **緩和されたマージ授権** | 停滞エポック内で有効 | **有効 → 失効 → 人間の明示的な再承認により有効** を遷移する。**①が終了すれば②も終了する** |

   **失効するのは②だけで、①は継続する**(失効中も未達・債務は計上され続ける)。
   これは `ADR-003` 帰結 1 の**段階 1 と段階 2 にまたがる**(全 13 対象の登録完了は段階 4 の直前)。
   **条文の根拠は段階 3 の括弧書きに置く** — 逐語「(要件書 NFR-018 の「正解ベクタは完成をもって発効する」=
   **未完成のあいだ適合と判定しないであって、実装を禁じるものではない**)」。
   **移行状態の授権はこの一文の延長線上にある**(TSK-235 からの指摘)
2. **移行プログラムの開始・終了条件**と、**緩和されたマージ授権の発効・失効・再承認条件**を、
   それぞれ機械判定可能に定める(**発効原子性**を含む — §4-4)
3. **「未達」「違反」「債務」を正本の語彙に置く**(既存の「判定不能」との切り分けを含む — §4-4)
4. **既知債務の授権** — 全件列挙・封印・**比較元の固定**・追加/再導入/降格の禁止・不可逆昇格(§4-4)
5. **「無期限の緩和にしない」ことの担保**(**方法は裁定済み = B-1'** — §4-9 論点 B)
6. **fail-closed 原則との関係の明示** — **優先関係・移行状態外での復帰**、および
   **`NFR-018(b)②` / `NFR-019(a)` を満たしたと判定することは移行状態では絶対にできない**こと
7. **全強制点への追随**(§4-3 の exact-set 表。**固定数を先に置かない**)
8. **`ADR-003` の見直しトリガーに「移行状態が機能しない場合」を追加**
9. **母集合の追随**(§4-6。要件書の変更で機械的に発生する **7 段の連鎖**)

### 4-6. 母集合の追随 — **7 段の連鎖**(1 周目 P0-5 で 3 段から改めた)

**実測**(2026-09-10・`4ed54fc` 起点): 要件書に試験行を 1 行挿入すると

先に走るため到達しない**。`reseal_catalog` は `claims[].decision_digest` と decision lock しか更新せず
**`input_manifest` には触らない**。

**当初の「3 段」は誤りであった。** 評価台帳 **H-85**(「oracle の入力凍結が、正本の 1 文字の変更を
**8 資産 + ハーネステストの更新へ拡大する**」)が正で、その候補①に

**資産の一覧は固定しない**: `contracts/authz/` の資産は TSK-317 の PR で増減する
(2026-09-11 の PR #1 で 4 資産が新設された)。**着手時のリベース後に実測して確定する。**

**既知の穴**(2026-09-12・TSK-317 から共有): **`check_authz_catalog.py` は `input_assets` の重複行を通す**
(先方が `validate_oracle_seal` を直接呼んで実測 — 正常 8 行も、重複行を足した 9 行も green)。

同じ穴の上を通る**。→ **ステップ 7 の着手時に「この穴が塞がれているか」を実測で確認し、
塞がれていなければ `input_assets` の重複が無いことを自前で確かめる**(合格条件へ反映)。

**7 段**:

1. 母集合の `input_manifest` と、**変更・追加・位置移動したすべての `claims`** を更新
   (`source_id` が**位置依存**のため「足した行だけ」では足りない)。

   reseal 経路が無いため手作業 — 2 周目 P1-8)
2. `--reseal --skip-derived --skip-oracle`
3. 派生 3 資産と各 lock の入力 digest を更新
4. `--reseal-derived --skip-oracle`
5. **入力確定コミット**
6. oracle 6 資産と seal の `oracle_commit` を **そのコミット** へ更新し **人間査読**
7. `--reseal-oracle`

→ **ステップ 7 を 2 ステップに分割する**(前段 = 入力確定コミット / 後段 = oracle 更新と人間査読)。

**「7 段階」と「2 段コミット」は矛盾しない — 粒度が違い、7 段階が 2 コミットに収まる**(TSK-317 との
突き合わせで確認)。**ステップ 7 = 段 1〜5(入力確定コミット)/ ステップ 8 = 段 6〜7**(oracle)。

**人間査読の位置は「`oracle_commit` の差し替え」と「`--reseal-oracle`」のあいだ**である
(H-85 の TSK-278 実測の逐語: 「入力確定コミット → 6 資産と seal の `oracle_commit` 差し替え
〔**7 ファイル × 1 行**〕→ **人間確認**〔`reseal_policy.human_review_required`〕→ `--reseal-oracle` →
2 本目のコミット」)。**差し替えてから査読し、査読後に reseal する**(順序を入れ替えない)。

### 4-9. PO 裁定(2026-09-11・山田正輝)— **裁定済み**

#### 論点 A: 設計書 10.1 の扱い → **A-1(射程に加える)**

**事実**(1 周目 P0-4): 設計書 10.1 は `consistency` ジョブを「**ゴールデンベクタ一致性テスト
(NFR-019a: 同一入力列 → クライアント/サーバー同一状況)**」と定義している。移行状態は
**`consistency` 系の exit 0 が `NFR-019(a)` の合格を意味しない状態**を新設するため、
**ジョブ名・個数が不変でもジョブ状態の意味が変わる**。「確認のみ」では閉じない。

**裁定**: **設計書 10.1 を本タスクの射程に加え、3 正本(要件書・`ADR-003`・設計書)の
単一確定ゲートで一括検証する。**

- **裁定の理由**(提示した根拠): ①A-2(別タスク)は**ブロッカがブロッカを生み**、TSK-355 の目的
  (TSK-235 のブロッカ解消)を達成しない ②TSK-278 が 2 正本の単一ゲートを実際に回した前例がある
  ③10.1 の変更はジョブ名・個数を変えず関係を定義するだけで条文量が小さい
- **帰結**: **射程が変わったため計画レビュー 2 周目は全文**(**7.3-4 を準用** — **7.3 は「正本確定ゲート」の
  規範であり `/plan` を拘束しない**。全文へ戻す判断は同条の趣旨を準用したものであって、
  規定の適用ではない。**2026-09-11 に引用の射程を訂正**)。設計書は **v1.13 → v1.14**。
  **TSK-343(設計書 10.1 の追随を所有)へ連絡が必要**(TSK-317 は 10.1 に触らないため無関係と確認済み)

#### 論点 B:「無期限の緩和にしない」の実現方法 → **B-1'(`N` = 50)**

**裁定**: **厳密減少は段階 2 の PR にのみ課し、停滞は「マージ本数」で測る。`N` = 50。**

**条文に書く 2 つの規律(骨子 — 機械条件の細部は §4-10 で design.md へ送る)**:

1. **厳密減少は段階 2 の PR に課す。** `ADR-003` 帰結 1 の段階 2 は「**対象計算 1 件ごとに…同一の変更として
   追加**」と定義されているため、**段階 2 の PR は定義上ちょうど 1 対象を登録し未達が 1 減る**。
   ここに「`未達数＋債務数` が厳密減少」を課すのは自然で**空振りしない**。
   **全 PR には課さない** — **無関係な PR は移行指標を減らす責務を負わず、厳密減少を満たせないため
   一律に落ちてリポジトリが凍結する**(2 周目 P2-10 の訂正を反映。
   「(b)③ が PR 内容と無関係に fail するから」という当初の説明は**理由として不正確**であった —
   移行状態が発効していれば (b)③ 自体は緑になる)。
2. **停滞は「時間」ではなく「マージ本数」で測る。**

   > **緩和されたマージ授権が有効なあいだ、直近の「前進」から数えて連続 50 本のマージで
   > `未達数＋債務数` が 1 件も減っていなければ、**緩和されたマージ授権は失効し**、
   > 継続には人間の明示的な再承認を要する。**(**失効するのは授権だけで、移行プログラムは継続する**)

   **「移行状態中の累計 50 本」ではない**(2 周目 P0-2)。累計で書くと**一度でも減った時点で失効条件が
   二度と成立しない**。**エポック**(発効時・各前進時・正当な再承認時に数え直す)として定義する。

**`N` = 50 の根拠**(実測): develop へのマージは**直近 3 週間で 1.6 本/日**
(2026-08-19〜09-10 で 37 本。通算 63 本 / 50 日)。**50 本 ≒ 1 ヶ月**。

**授権失効中にゼロ到達した場合**(4 周目 P1-2): **移行プログラムが自動昇格して終了し、授権も終了する。
以後の再承認はできない**(①が終われば②も終わる — §2 の二軸表)。

**エポックの起点は「発効時点」であり、「正本が approved になった時点」ではない**
(2026-09-11・TSK-235 からの照会に対する明確化)。§4-4 論点 3 の**発効原子性**により、
**移行判定器・未達レポート・観測機構・負例が同一変更で CI の必須経路へ接続されるまで
移行状態は「定義済みだが未接続」**である(**改称の経緯は §4-4 論点 3**)。したがって:

- **正本が approved になっただけでは 50 マージのカウントは走らない**
- **カウントが始まるのは検査基盤の PR がマージされ、機構が動き出した時点**
- **その時点で `未達数＋債務数` と債務台帳が初めて存在する**(それ以前は**存在しない量の減少を
  判定することになり成立しない**)
- **封印の比較元「移行開始を承認した既存コミットの固定 SHA」は、この発効コミットを指す**

→ **検査基盤を作る PR 自身が失効に巻き込まれることはない。** 失効が起こり得るのは
**発効後**(段階 1 の後半〜段階 2)である。

**設計の意図(条文の根拠節に書く)**: **段階 1 のあいだは構造的に未達も債務も減らない**
(TSK-235 は検査基盤、TSK-236〜239 はベクタ契約で、対象計算の登録は段階 2 から)。
したがって `N` をどう置いても**段階 1 の途中で必ず失効する**。これは欠陥ではなく**意図した設計**である —
`N` は異常検知の閾値ではなく「**どのくらいの頻度で PO に再確認を求めるか**」のパラメータであり、
無期限の緩和を防ぐ本質は期限そのものではなく「**人間が定期的に意識して延長する**」ことにある。

**失効と自動昇格は衝突しない**(向きが違う):

| 遷移 | 向き | 扱い |
| --- | --- | --- |
| **昇格**(①移行プログラムの終了) | **厳しくなる** | **自動かつ不可逆。人が止められない**。①が終わると②も終わる |
| **失効**(②授権のみ無効化) | **厳しくなる** | **自動。昇格と同じ向きなので衝突しない**。**①は継続する**(未達・債務は計上され続ける) |
| **再承認**(②を再び有効化) | **緩くなる** | **人間の明示承認を必須とする。自動延長にしない**。**更新できるのは停滞エポックだけ**で、初回 SHA・初回対象集合・初回債務 ID 集合は変更できない(3 周目 P0-1) |

### 4-10. **design.md で確定する機械条件**(本計画書では決めない — H-68 型の回避)

**design.md が答えを出さなければならない論点**(2 周目の指摘に対応。**ステップ 2 の合格条件**):

| # | 論点 | 何が問題か | 由来 |

**条文の側の要求(2026-09-11・TSK-235 からの提案を受けて)**: 本改訂で新設・改訂する条項には
**安定した条項 ID** を与える。TSK-235 が「**当該ステップが依拠する授権の条項 ID が正本に実在するかを
着手前に照合する**」機構(文言存在型・機械判定)を持つ予定であり、**条項 ID が安定していないと
その照合が成立しない**。あわせて**行番号参照 0 件**の方針(本書冒頭の参照規約)とも整合する。
**ID の粒度は design.md で確定する。TSK-235 から次の 4 点の要求を受領済み**(2026-09-11):

| # | 要求 | 理由(先方) |
| --- | --- | --- |
| 1 | **粒度は条項単位**(節単位は粗すぎる) | 節単位だと、たとえば単調性だけに依拠するステップが「移行状態の定義」全体を指すことになり、**単調性の条文が消えても実在検査が通ってしまう** |
| 2 | **意味的な安定 ID**(節番号を含めない) | 番号ベースだと**改訂で節が動いた瞬間に照合が全滅**する(3 周目 P1-8 の「行番号 18 件全滅」と同じ壊れ方)。既存の書き方(`NFR-018 (b)②` / `AUTH-*` / `H-12`)に揃えて**意味的な接頭辞 + 識別子** |
| 3 | **一度付けた ID は改訂で改名しない**(追加は自由) | 改名すると**偽の発火**をする(授権は生きているのに「実在しない」と判定する) |
| 4 | **削除・失効時は ID を消してよい** | その場合の発火は**正しい発火**(依拠していた授権が撤回されたなら TSK-235 は止まるべき) |

→ **「改名で偽発火・削除で真発火」の非対称が保てれば機構として成立する**(先方の整理)。
**4 点とも受け入れる方針**だが、確定は design.md(ステップ 2)で行う。

**照合方式は先方が確定した**(2026-09-11・design.md §12-1-b-1)。私が指摘した
「ID だけでは内容変更を見逃し、逐語照合だと確定ゲートの表現調整のたびに偽発火する」という
トレードオフは、**依拠先を `approved` 版に限ることで解消された**:

| 層 | 検出 | 判定 | 扱い |
| --- | --- | --- | --- |
| ① | 依拠する条項 ID が正本に無い(最初から無い / 撤回された) | **機械** | **発火 = 停止** |
| ② | ID は在るが内容 digest が pin と違う | 機械が検出・**人間が判断** | `[手動]` の再確認。**停止しない** |

- **`in-review` の条文には依拠しない** → **本タスクの確定ゲート中(表現調整が何度も入る)は
  検査対象にならず、先方の検査は赤くならない**
- **`approved` になった時点で digest を pin する** → 以後の変更は改訂ゲート(7.6 の決定表)を通るため
  頻度が低く、②の検出は**正しい動作**

→ **非対称は 3 段**: **改名 = 偽発火 → 条文側が禁止**(本タスクの負担)/ **削除 = 真発火 → 停止** /
**内容変化 = 再確認 → 停止しない**。

**本タスクの負担は「条項 ID の安定」のみ**(digest の pin は先方が行う)。**追加の負担は無い。**

**成果物の形**(2026-09-11 に先方と合意): ステップ 2 で **条文そのものと、条項 ID の対応表の両方**を出す。
**対応表があると先方の依拠宣言が機械生成できる**。**列は次を必須とする**(design.md で最終確定):

| 列 | 用途 | 必須の理由 |
| --- | --- | --- |
| **条項 ID** | ①の実在照合の鍵 | — |
| **規範の所在**(正本と条項名) | 人間の追跡 | — |
| **範囲の切り出し規則** | **②(内容 digest)の対象範囲**。「表の 1 行」「見出し X から次の見出しまで」「箇条書きの 1 項」など**機械的に一意へ切り出せる規則**。**表形式の条項では「行全体」ではなく「規範を担うセル」に限れる形を検討する** | **これが無いと digest を計算できず、②が成立しない**(①だけの弱い機構になる)。**セル単位にできれば表への列追加に耐える** — 行全体だと**列を 1 つ足すだけで全条項が一斉に再確認**になる(本タスクは計画レビュー 6 周のあいだに表へ何度も列を足しており、**条文でも起きる**) |
| **版と `status`**(**行ごと**) | 「**依拠先は `approved` 版に限る**」検査の入力 | **表全体で 1 つでは不足**。改訂で**一部の条項だけ `in-review` に戻る**ことがあり、行ごとに持たないと**改訂中の条項への誤依拠を検出できない** |
| **`superseded_by`** | **「撤回」と「分割・統合」の区別** | **改名の禁止だけでは分割を扱えない**。1 条項が 2 条項へ分割されると先方からは「旧 ID の削除 + 新 ID の追加」に見え、**削除 = 真発火(停止)**の規則により**規範が生きているのに停止する**(偽発火)。`superseded_by` があれば**分割・統合は②の再確認(停止しない)へ落とせる**。**本タスクの確定ゲートは 27 周の前例があり、条項の分割・統合は高い確度で起きるため必須列とする** |
| **`kind`**(規範 / 補足) | **「依拠先が `規範` でない行なら fail」**の機械検査 | **本タスクは §4-12 を「規範」と「経緯(記録)」に割っており、条文でも同じ区別が生じる**。先方が**補足・経緯の行へ依拠すると「授権でないものを授権として扱う」**ことになり、**これは 3 周目 P0-1 の再発そのもの**(先方の指摘) |
| 一行の要旨 | **人間向け** | **本機構の検査の入力にはしない**ことを**表に明記する**(要旨方式は先方が §12-1-b-1 で却下済み — 更新が気づき依存になるため。**明記が無いと後から誰かが検査へ配線して同じ問題が戻る**) |

**対応表そのものの不変条件**(2026-09-12・TSK-235 からの要求): **条項 ID の重複を許さない。**
先方の依拠条項リストは**同じ条項 ID を 2 回宣言できてしまう**リスクを持ち、**対応表側でも重複を
拒否すれば両側で塞げる**(先方は同型の欠陥を自分のマニフェスト schema に見つけて是正済み —
「ベクタ側には重複拒否があるが宣言側に無かった」)。
→ **対応表の生成時に条項 ID の一意性を機械検査する**(§4-2 の契約 5 の自己点検を、
**本タスク自身の成果物にも当てる**)。

**規約 2 件**(表ではなく規約として design.md に置く)。

**規約① digest 計算前の正規化**: 正本は日本語 Markdown で**行を手で折り返している**ため、
**折り返し位置を変えるだけ(reflow)で生テキストの digest が変わる**が**規範は変わっていない**。
そのままでは先方の②が**偽の再確認を大量に出す**。→ **digest の計算前に、空白の連続を単一空白へ畳み、
行末空白と改行を正規化する。それ以外は無加工。** これで **reflow では発火せず、語句の変更では発火する**。

> **混同注意**(先方からの警告): 先方の §7-3 に「**比較器は正規化しない**」という規約があるが、
> **あれは表示値の比較**(`ADR-003` の lossless 原則)で**別物**。**両者を別の名前で呼ぶ** —
> **表示値比較 = lossless / 条項 digest = 正規化あり**。**同じ文書に「正規化する」「正規化しない」が
> 並ぶため、本タスク側でも取り違えないこと。**

**規約② ID の名前空間**: 既存の `NFR-018 (b)②` / `AUTH-*` /
`CATALOG:*` / `D-7` / `H-12` / `P-01` / `I-4` / `FR-*` と**衝突しない接頭辞**を定める。
**先方の検査は正本横断で ID を引く**ため、衝突すると誤った条項を指す。**ステップ 2 で既存 ID を実測し、
衝突しないことを確認したうえで確定する。**

**送り先を空手形にしないための 3 つの機構**(3 周目 P1-2 — `design.md` はゲート対象外であり、
「答えが存在すること」だけを検査しても形式的な回答で通ってしまう):

1. **ステップ 2 で逐項検証する** — 各 `M-*` について**必須命題・正例・負例・不成立条件**を書く
   (「決める」と書いただけの回答を認めない)

### 4-12. 並行タスクとの取り合い(2 周目 P1-8 / P1-9・3 周目 P1-6・4 周目 P1-4)

**以下は規範記述である**(経緯は本節末尾の「経緯(記録)」へ隔離した — 5 周目 P1-3)。

**開始条件**: **`TSK-317 PR #2`(改訂 3 第 2 弾 = 再封印)と `TSK-343` の両方がマージされた後に
リベースしてからステップ 1 を開始する。**

**確定した総順序**(2026-09-11 決着。**各タスクの既存の制約から機械的に決まり、循環しない**):

```
TSK-348(済) → TSK-317 PR #1(済) → TSK-343(済) → TSK-317 PR #2
  → TSK-355(本タスク) → TSK-317 PR #3 → TSK-235
```

**`TSK-317 PR #3` の位置は PO 裁定で確定した**(2026-09-12・山田正輝 — **案 A**)。
PR #3 は 2026-09-12 の裁定 `D-14` / `D-15` で新設され、**2026-09-11 に合意した総順序より後に
生まれたため席が無かった**。**新しい席を作る決定であり、既存の決定からは導けない**ため裁定を仰いだ。

**衝突の実体**: PR #3 は `auth-catalog.json`(入力資産)を変えて `oracle_commit` を前進させ、
本タスクは要件書を変えて `requirement-claims.json`(同じく入力資産)の digest を動かす。
**同じ seal の入力側を両方が触る**ため、**後になったほうが再封印を 1 回余分に払う**。

**案 A(本タスクが先)を採った理由**:

| # | 根拠 |
| --- | --- |
| 1 | **最長区間を前倒しできる**。本タスクの**確定ゲート**は同型の前例(TSK-278)で **27 周**かかっており、残り作業の中で圧倒的に長い。**案 A なら本タスクの確定ゲート中に PR #3 が計画・実装を進められる**(PR #3 は「マージだけ」待つ)。**案 B では 2 つの長い作業が直列**になる |
| 2 | **PR #3 はまだ 1 行も書いていない**。後に回っても**計画時点で本タスクのマージ後の状態を織り込める**ため追加費用がほぼ出ない。一方**本タスクは計画が承認済み**で、後に回るとステップ 7・8 の基準コミットが変わり、**承認済み計画の改訂と再承認(人間の手番が 1 回増える)**が必要になる |

### コア領域の PR で CI が完走しない構造(**本タスクは必ず踏む**)

**TSK-317 からの申し送り**(2026-09-11・PR #52 / #53 / #54 の **3 件連続で踏んだ**実例つき):

- `ci.yml` の `concurrency` が **`cancel-in-progress: true`** — **PR 本文の編集が `edited` イベントで
  新 run を起こし、前の run を打ち切る**
- **`core-guard` は逐行確認のチェックが入るまで red**(`core_guard.py` が
  `- [x] <REQUIRED_CHECK_TEXT>` を機械検査する)
- → **「全ジョブ green」が成立し得るのはチェック後の run だけ**。かつ**チェックを入れる行為自体が
  それまでの run を無効化する**

**したがって順序が一本に決まる**:

```
push → PR 作成 →(この時点で確認できるのは core-guard 以外)
  → 人間の逐行確認 → PR 本文のチェックと実施記録の記入
  → edited で起きた新 run の完走を待つ → 全ジョブ green を確認 → マージ
```

**「push 後に green を確認した」だけでは足りない。**

CI のコマンドで確認する。**
