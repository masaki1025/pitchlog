# 調査メモ: 検査基盤の導入期の移行状態を条文化する(TSK-355)

## 問い

TSK-235 の敵対レビュー 3 周目 P0-1 が指摘した「移行状態が正本に授権を持たない」を解消するため、
PO 裁定(2026-09-10・山田正輝)の甲案 = 正本(要件書 `NFR-018` + `ADR-003`)への移行状態の明記を
設計するのに必要な事実を実測する。具体的には次の 6 点:

1. 移行状態の開始・終了を機械判定可能に定めるために、**何が観測可能か**
2. 「未達」「違反」「債務」の 3 型を正本の語彙に置くとき、**既存の語彙と衝突しないか**
3. `bootstrapDebt` の授権(全件列挙・封印・追加/再導入/降格の禁止・不可逆昇格)を**どの条文形式で書くか**
4. 許容期間または昇格条件を「無期限の緩和にしない」形で書く方法
5. fail-closed 原則と充足宣言(`NFR-018(b)②` / `NFR-019(a)`)との関係の書き方
6. `ADR-003` D-7 実行契機表 (b)③ 行への併記の形

## 結論(要約)

1. **矛盾の実体は「例外の不在」ではなく「段階 1 のマージ条件が未定義」である。** ADR-003 は既に着手順序の
   4 段階を持ち、段階 3 が「**当該対象の全緑をマージ条件**」と**対象単位で**マージ条件を切っている(§7-3)。
   対象が 0 件である段階 1 のマージ条件だけが書かれていない。**移行状態は「例外の新設」ではなく
   「未定義の空枠を埋める」立て方で書くのが、fail-closed の由来(§7-4)と最も衝突しにくい。**
2. **触るべきアンカーは 6 つで、1 ステップで同時に触らないと必ず追随漏れになる**(§7-9 の警告)。
   要件書 = `NFR-018` 達成条件 (b) の fail-closed 行 / 正解ベクタ欄の発効条件 / 10 章の未決事項行、
   ADR-003 = D-7 の (b)③ 行 / D-11 ③ の入口全列挙 / D-11 の判定不能の扱い。
   TSK-278 の 27 周で最頻だった欠陥型が「追随漏れ」(7 回)であり、同型を踏む構造が既にある。
3. **本タスクは fail-closed に導入期の例外を初めて設ける改訂**(§7-4 — 前例は全数確認で無い)。
   したがって**援用できる型を既存条文から借りる**必要がある。最も近いのは要件書 `NFR-018 (c)` 例外表
   (成立条件・失効条件・判定者・状態を 1 表に閉じ、「**検証テストが無い行の例外は成立しない**」と
   不成立側を明示する型 — §6-6 の手本 A)。
4. **「無期限の緩和にしない」は日付なしで満たせる。** 上限は既存条文が持っている —
   要件書 8 章 DoD ② と NFR-021 リリース候補時が「**NFR-018(b) の機械検査が成功していること**」を
   要求しており、**移行状態はリリース判定に到達する前に必ず終端する**(§6-5)。これに TSK-235 の
   単調性 4 条件(債務の追加禁止・再導入禁止・降格経路なし・自動不可逆昇格 — §5-3)を組み合わせる。
5. **必ず突かれる論点が 2 つある。**(a)「**対象範囲の縮小で満たしたことにはできない**」(要件書 v2.1 由来)と
   債務台帳の関係 — D-4 が同じ論法で v2.1 の (b)② を実現不能と結論した経緯がある(§7-9 P0 級 #7)。
   (b)「exit 0 で緑」が**緑の意味を空洞化していないか**(§7-9 P1 級 #17 — 3 周目 P0-1 の指摘そのもの)。
   **条文はこの 2 点への答えを内蔵していなければならない。**
6. **語彙は新語を作らず既存語に寄せる。** 「充足宣言」は正本に 0 件で、既存は
   「**満たした / 合格と判定してはならない**」という否定形(§6-4)。「違反」は `NFR-018 (c)` に既に
   「**その状態は本要件の違反として扱う**」の用例がある(§6-6 手本 A)。**宣言集合と実測集合は
   別語で呼び分ける**(§5-6 制約 (6))。

### 3. 設計書 13 章「製品機能の実装」(v1.13)に既存の導入順序がある — **重要**

`docs/development/dev-harness-design-2026-08-07.md:872`(逐語引用):

> **適合判定との関係**: **対象横断の正解ベクタが未完成であること**は「**適合と判定しない**」を意味するのみで、
> 実装を禁じるものではない([ADR-003](../adr/ADR-003-domain-calc-method.md))。**ただし `NFR-018` の対象計算に
> 触れる実装は ADR-003 が定める導入順序に従う** — 検査基盤(生成器・マニフェスト・収集器・CI 配線)とベクタ
> schema・独立に確認した期待値の先行確定 → 対象計算 1 件ごとに宣言モデルの正本・生成物・製品経路の呼び出し部・
> その対象の 3 層検査を同一の変更として追加 → 当該対象について全検査が緑であることをマージの条件とする。
> **検査基盤の未整備を理由に対象計算のコードを先に追加することはできない**

**含意**(3 件):

1. **「検査基盤を先行確定させる期間」の存在は設計書 v1.13 が既に前提にしている。** 移行状態は新概念の
   発明ではなく、この導入順序の第 1 段階に**授権を与える**位置づけで書ける。
2. 同条文は「**対象横断の正解ベクタが未完成であること**は『**適合と判定しない**』を意味するのみ」と
   既に区別している。これは TSK-355 が要求する「**未達 ≠ 違反**」の区別と**同型の区別が設計書側に既にある**
   ことを意味する(語彙は異なる)。条文設計はこの既存区別に接続させるのが自然。
3. **矛盾リスク**: 同条文の末尾「検査基盤の未整備を理由に対象計算のコードを先に追加することはできない」は
   移行状態と両立するか要検証。移行状態は「検査基盤の PR 自身がマージできること」を授権するもので、
   「対象計算を先に追加すること」を授権するものではない — **この差を条文で明示的に切り分ける必要がある**。
   切り分けに失敗すると設計書 13 章との矛盾になり、**射程拡大(設計書も対象に加える)の PO 裁定が必要になる**。

#### 5-1. P0-1 の閉じ条件(最小要件 5 件)

| # | 要求 | 理由(回答の要旨) |
| --- | --- | --- |
| (a) | **要件書 `NFR-018` の fail-closed 行そのものに例外を書く** | ADR だけ直すと、要件書が「不合格」と言い続けるため**両者の矛盾**として再指摘される |
| (b) | **`ADR-003` D-7 (b)③ 行の「マージ不可」に移行状態での扱いを併記** | 2 本目の支持条文。片方だけでは同じことが起きる |
| (c) | **移行状態でも充足宣言はできないことを明記** | **例外が原則を飲み込むのを防ぐ唯一の歯止め**。無いと「exit 0 なんだから合格では」と読める形が残る |

#### 5-2. 終了条件は **連言**(私の質問の前提が誤っていた点の訂正)

回答の逐語: 「design.md §3-2 に書いたのは「**未達レポートと債務台帳の両方が空になった時点で昇格**」です。
**未達 0 かつ 債務 0** の連言です。」

- **未達 0** = 要件由来の対象集合(α5 + β①〜⑧)が**全件マニフェストに登録され、各層の実行集合に現れる**
- **債務 0** = 承認時点で封印した既知の未宣言入口が**全件解消**
- **これ以外の終了条件は想定していない**(期限・登録率・別タスク完了を終了条件に置く設計はしていない)

#### 5-3. 許容期間 — **条文に日付を書かない**(単調性で閉じる)

回答の要旨:

- **見通し**: 未達 0 = 13 対象すべて登録済み。TSK-236〜239(ベクタ)+ **ADR-003 の着手順序の段階 2**
  (対象計算 1 件ごとの追加)が全 13 件終わる必要がある。**TSK-235〜239 では終わらない**。
  段階 4(対象横断の判定)の直前まで続く。**段階 2 のタスクは未起票のため期間は見積もれない**
- **日付を書くと** ①正当に未完のまま期限切れ → また正本改訂が必要 ②守られない期限として形骸化
- **代案**: PO 裁定のスコープ 4 は「許容期間**または**昇格条件」なので**昇格条件だけで要件を満たせる**。
  「無期限の緩和にしない」は**期限ではなく単調性で閉じる** — 次の 4 つが揃えば移行状態は単調に縮小するのみ:
  1. **債務は増やせない**(台帳への追加を禁止)
  2. **一度解消した債務は再導入できない**
  3. **「違反」を「債務」へ降格する経路が存在しない**
  4. **昇格は自動かつ不可逆**(手動の再有効化フラグを持たない)

→ **本タスクの方針判断が必要な論点**。PO 裁定は「または」で選択を許しているため昇格条件のみで
裁定の範囲内だが、「無期限の緩和にしない」の充足を単調性で説明する構成になる。**計画書に明記して
人間の承認を仰ぐ**(私が勝手に確定しない)。

#### 5-4. (b)③ の「実在入口集合」は**宣言から独立に採取**する — 語彙の呼び分けが必須

回答の逐語(要旨): 「**レジストリやデコレータから採ると (b)③ が無意味になります。** (b)③ は
「宣言が実態と合っているか」を見る検査なので、**比較する 2 つの集合のうち片方は宣言から独立して
いなければならない**」

採取元(回答が示した所在 = design.md §10-1・§10-2):

- **frontend**: Vite の全 input・Web Worker・Service Worker・別 HTML・静的配信配下の**入口全列挙**
  + `dependency-cruiser` の import グラフ + **production build の実物**を直接読む統合テスト
- **backend**: Python の **import グラフ** + `importlib` / `getattr` / entry point 経由の読み込みの禁止

実測値(回答が引用した TSK-235 側 research.md §6-3・2026-09-10 時点):

- `vite.config.ts` に `build` セクションが無いため input は既定の `index.html` **1 本のみ**
- Web Worker **0 件**、Service Worker **0 件**
- 既存の手書き座標変換への到達 = `index.html` → `main.ts` → `App.vue` → `StrikeZoneCompareHost.vue`
  → `StrikeZone.vue` の**静的 import 4 ホップ**

→ **開始・終了は機械判定可能**(build 設定と import グラフから計算できる)。

**注意(v0.2 の新設事項)**: (b)③ に **4 つ目の不変条件「表外既定の表示対応の突合」**が増えている
(ADR-003 D-7 (b)③ 行・v0.2 新設)。こちらの実在集合は「**製品表示呼出箇所**」を静的解析で実測したもの。
**入口だけでなくこちらも移行状態の対象**。→ 制約 (5) に直結。

#### 5-5. 封印は blob digest **だけでは足りない** — 比較元の不変性が要件

- 既存機構は `sha1(b"blob {len}\0" + data)`(回答が引用した TSK-235 側 research.md §6-5)
- **不足の理由**: 敵対レビュー 3 周目 P1-4 が同型の指摘 —
  **比較元が PR head のリテラルだと、同じ PR で台帳・digest・検査の 3 点を同時に書き換えれば通る**
- 是正案(回答): 「**base 側 commit アンカーに一本化し、比較元を PR head から変更不能な
  merge-base blob にする**」。想定は「承認コミット SHA を台帳に持ち、比較元を merge-base の blob にして
  CI で差分検査」
- **条文への要求**: 正本には実装ではなく規律を書くが、機構が成立するには
  **「比較元が当該 PR で変更可能であってはならない」**という一文が必要

#### 5-6. 「正本にこう書かれると TSK-235 の設計が壊れる」6 件(回答の逐語見出し)

| # | 禁止事項 | 理由 |
| --- | --- | --- |
| (1) | **「未達」と「違反」を 1 つにまとめない** | 3 型(未達・違反・債務)の区別が exit 契約の中核。まとめると「違反も exit 0」へ滑る |
| (2) | **昇格を手動フラグにしない** | 「自動かつ不可逆」が設計。手動だと**昇格忘れが永続化**し検出できない(design.md §3-2 は「未達 0 かつ債務 0 なのにゲート未昇格なら fail」というテストを置く前提) |
| (3) | **移行状態でも充足宣言はできない、を必ず入れる** | (1-c) と同じ |
| (4) | **条文に日付を書かない** | §5-3 の理由 |
| (5) | **`bootstrapDebt` の対象を「入口」だけに限定しない** | v0.2 が新設した (b)③ の 4 つ目(表外既定の表示対応の突合)も同じ規律で扱う想定。「未宣言の入口」だけに限定すると**表示対応が未宣言の表外既定項目を扱えず、もう 1 系統の常時 fail 源が残る**。「**(b)③ が要求する宣言のうち、承認時点で未宣言のもの**」という一般形にすれば両方を覆える |
| (6) | **実在集合を「宣言から採る」形に書かない** | §5-4 の理由。条文で「**マニフェストに宣言された入口の集合**」と「**実測した入口の集合**」を**別の語**で呼び分ける |

### 7. ADR-003 側の実測と決定の経緯(decision-tracer)

#### 7-1. **D-7 実行契機表に「(b)② 行」は存在しない**(前提の訂正 — 重要)

D-7 の表は **6 行**で、`(b)` ラベルを持つのは **① と ③ の 2 行だけ**。**(b)② は上 4 行(網羅ベクタ・
差分テスト・プロパティテスト・変異テスト)が分担して担う**構造(D-11 が対応の正)。

→ **「(b)①(b)②(b)③ の 3 行の整合」という枠組みでは表を読めない。**
Notion タスクのスコープ 6 は「(b)③ 行への併記」なので影響しないが、**条文を書くときに
「(b)② 行」を参照してはならない**。

**D-7 の 6 行の「失敗時の扱い」**(ADR3:309-314):

| 行 | 検証機構 | 実行契機 | 失敗時の扱い |
| --- | --- | --- | --- |
| 1 | 網羅的な正解ベクタ(D-6 の①契約の全行) | PR 必須 | **マージ不可** |
| 2 | 差分テスト(両実行系の出力突合) | PR 必須 | **マージ不可** |
| 3 | プロパティテスト | PR 必須(seed 固定)+ 夜間(拡大) | PR = **マージ不可** / **夜間 = 失敗を起票して追跡** |
| 4 | 変異テスト | PR 必須(差分 10 分 / 全面 30 分) | **マージ不可**(非等価変異が 1 件でも生存したら失敗・上限超過はタイムアウト = fail) |
| 5 | **(b)① 乖離検出** | **PR 必須** | **マージ不可** |
| 6 | **(b)③ 構成の完全性(D-11)** | **PR 必須** | **マージ不可**。これをもって要件書 v2.1 の (b)② を満たしたとはしない |

**柱書 ADR3:305** 逐語: 「**夜間のみの検査を Must の唯一の担保にしない。** NFR-019 は PR ごとの CI・
全グリーンを要求するため、**NFR-018(b) と NFR-019(a) の必須判定には PR 必須の基線を置く**。
夜間枠は補助検査に限る。」

→ **6 行のうち 5 行が「マージ不可」を明記**し、例外は 3 行目の**夜間枠のみ**。
**PR 必須側に「未整備なら通す」層は 1 行も無い。**

#### 7-2. D-11 ③「構成の完全性」の 4 不変条件(ADR3:234-241)

3 列表 `| 不変条件 | 採用する方式(決定) | 判定不能時 |` の **4 行すべてが「判定不能時 = fail」**。

**① 入口の全列挙**(ADR3:238)逐語の核心部:

> **実在入口 = ラッパーの利用箇所の静的列挙 + フレームワークの route / API ハンドラ登録の列挙**とし、
> **この集合と `entrypoints[]` の差が 1 件でもあれば fail**

→ **これが P0-1 の直接の衝突点**。

**判定不能の扱い**(ADR3:253)逐語:

> 解析器が「解析できない」と報告した箇所は**合格にしない**。解析不能な構文は動的機構の禁止規則で先に落ちるため、
> **残る判定不能は解析器の限界を意味し、CI を失敗させて人が判断する**。

→ **「未達」型を新設すると、未達と「判定不能」の区別が条文上必要になる**(スコープ 2 の 3 型に
**第 4 の型「判定不能」**が既に存在する、という認識が要る)。

#### 7-3. **最も有力な接続点 — ADR-003 帰結 1 の 4 段階(ADR3:387-391, 401)**

ADR-003 は既に**着手順序の 4 段階**を持ち、その **③ が段階的マージを授権している**:

1. 検査基盤とベクタ schema を先に確定(**この段階では対象計算のコードを追加しない**)
2. 対象 1 件ごとに正本・生成物・呼び出し部・3 層検査を同一変更として追加
3. **当該対象の全緑をマージ条件**とする
4. 対象横断の判定は全契約完成後

→ **移行状態は「段階 1 に対応する条文が欠けている」ことの補完として書ける。**
段階 3 が「**当該対象の**全緑」と対象単位でマージ条件を切っている以上、
**「対象が 0 件のときのマージ条件」が未定義**というのが矛盾の正体。**これが最も整合的な接続点**。

なお設計書 13 章(§3)はこの 4 段階を引き写したもの。`pitchlog-89` の実測報告(2026-09-10)により
**13 章の禁止の主語は「対象計算のコード」に限定**されており、「検査基盤の PR 自身のマージ」は
13 章が禁じる対象に入らない、と読める。→ **設計書は無変更で済む見込みが強まった**(要確認は残す)。

#### 7-4. **fail-closed に経過措置を認めた前例は「無い」**(全数確認の結論)

decision-tracer の結論(逐語): 「**fail-closed に対する経過措置・時限的例外の前例は無い**(不明ではなく、
要件書 NFR-018 全文・ADR-003 全文・設計書 6.3/7.x の全数確認で無い)。**TSK-355 は「fail-closed に
導入期の例外を初めて設ける改訂」になる**」

近い型は 4 件あるがいずれも別物:

#### 8-4. 3 型の exit 契約(`design235:125-140` §3-2 全文)

> ### 3-2. 「未達」「違反」「債務」の 3 型
>
> 段階的 CI 状態モデルの中核。`consistency` を paths filter なしの必須ジョブにして未整備を常に exit 1 に
> すると、**本 PR 以後の全 PR が赤になりマージ経路が無くなる**(要件書 `NFR-019` / `github-setup.md` 2 章)。
>
> | 型 | 意味 | exit |
> | --- | --- | --- |
> | **未達** | まだ登録されていない(想定内) | **0**(機械可読な未達レポートを出力) |
> | **違反** | 登録されているのに食い違う・宣言外の入口がある | **1** |
> | **債務** | **承認時点で既知の未宣言入口**。封印された全件列挙の中にあるもの | **0**(§4 の規律下でのみ) |
>
> **基盤の自己テスト**(検査器・runner・生成器が仕様どおり動くこと)は **exit 0 = 緑**で**必須ジョブ**。
> **全体適合判定**は未達レポートを出して exit 0、**適合も exit 0・違反は exit 1**。

**4 集合の定義**(`design235:106-123` §3-1)— 移行状態の機械判定はこの 4 集合の上で書ける:

| # | 集合 | 出所 |
| --- | --- | --- |
| 1 | **要件由来の対象集合** | 要件書 NFR-018 対象欄。**(α)5 + (β)①〜⑧ で閉じている** |
| 2 | **マニフェスト登録集合** | `backend/domain/manifest.json` |
| 3 | **本番から独立採取した実在入口集合** | Vite の全 input・Web Worker・Service Worker・別 HTML・静的配信配下 + Python の import グラフ |
| 4 | **各検査層の実行集合** | ベクタ / プロパティ / 変異のランナー証跡 |

→ **§5-4 の「宣言から独立に採取」は集合 3 の定義そのもの**。条文で集合 2 と集合 3 を別語で呼び分ける
必要がある(制約 (6))。
