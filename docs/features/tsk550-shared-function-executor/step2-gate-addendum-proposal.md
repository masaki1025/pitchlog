## 実PR番号を得るための先行操作

7.7のv2履歴は`owner/repository#number`形式の実受理IDを要求し、PR受理検査はGitHub eventの番号・develop向け2親mergeと一致させる。従って**コード着手前に、既存の文書のみのfeature HEADをpushし、同じAブランチでDraft PRを作って実番号を取得する**順序を推奨する。これは通常の6.1の`/pr`順序に対するA限定の番号取得例外であり、計画frontmatterは`status: active`のまま維持する。正式受理後のステップ2コミット・ローカル最終HEAD検査を終えた時点で通常の`/pr`手順へ移り、worklogの締めと`status: in-review`化を行う。この先行操作はステップ2完了や7.7受理ではない。人間が別途push・Draft PR作成を許可したときだけ行う。現指示では禁止されているので実施しない。

この順序なら2A/2Bを同一worktreeで連続実行し、正式受理後にコード・資産・履歴を**1つのステップ2コミット**へまとめられる。候補差分は受理前にコミットせず、新規ファイルへ`git add -N`を適用した`git diff`と`git status --short`の全数照合を証跡として提示する。正式受理時に候補との差分があれば再提示する。正式受理後に単一ステップコミットを作成し、**そのコミットのHEAD**でローカル検査を実行する。ローカル検査が失敗した場合はpushせず、修正差分とdigest・前後射影の変化を提示する。受理対象が変わる場合は再受理を得た後、未pushコミットを`git commit --amend`して同じステップtokenを1個だけ維持し、HEAD検査をやり直す。ローカル全緑後にDraft PRへpushし、PR CIの実merge refによる検査を確認する。**push後**のCI・敵対レビューで修正が必要なら、差分を人間へ再提示して停止する。履歴を書き換えるforce pushや追加コードコミットは自動では行わず、6.1との整合を含む個別判断を求める。最終headのCIと人間逐行確認が成立するまでマージしない。

**残る時間順の論点**: 7.7 v2履歴の`approved_by`・`approved_on`は正式受理の後にしか書けず、最終コミット・CIはその後に生じる。従って「正式受理」を**実値/前後射影の人間受理**と「最終head/CIのマージ前確認」に分け、前者だけで最終CIを済ませたとは主張しない。7.7規範は変えないが、計画DoDにはこの2つの判断点を明記する必要がある。もし人間がCI緑を7.7正式受理の前提とするなら、v2履歴の未承認値を禁じる現行資産と循環するため、本案は適用できない。その場合は別の資産ゲート設計と正本審査を要する。
