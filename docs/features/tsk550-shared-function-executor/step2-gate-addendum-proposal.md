## 実PR番号を得るための先行操作

7.7のv2履歴は`owner/repository#number`形式の実受理IDを要求し、PR受理検査はGitHub eventの番号・develop向け2親mergeと一致させる。従って**コード着手前に、既存の文書のみのfeature HEADをpushし、同じAブランチでDraft PRを作って実番号を取得する**順序を推奨する。この先行操作はステップ2完了や7.7受理ではない。人間が別途push・Draft PR作成を許可したときだけ行う。現指示では禁止されているので実施しない。

この順序なら2A/2Bを同一worktreeで連続実行し、正式受理後にコード・資産・履歴を**1つのステップ2コミット**へまとめられる。候補差分は受理前にコミットせず、レビュー可能な`git diff`と証跡として提示する。正式受理時に候補との差分があれば再提示する。最終コミット後にDraft PRへpushし、PR CIの実merge refによる検査を確認する。CI結果または敵対レビューで修正が生じた場合は、修正差分を人間確認へ戻す。最終headのCIと人間逐行確認が成立するまでマージしない。

**残る時間順の論点**: 7.7 v2履歴の`approved_by`・`approved_on`は正式受理の後にしか書けず、最終コミット・CIはその後に生じる。従って「正式受理」を**実値/前後射影の人間受理**と「最終head/CIのマージ前確認」に分け、前者だけで最終CIを済ませたとは主張しない。7.7規範は変えないが、計画DoDにはこの2つの判断点を明記する必要がある。もし人間がCI緑を7.7正式受理の前提とするなら、v2履歴の未承認値を禁じる現行資産と循環するため、本案は適用できない。その場合は別の資産ゲート設計と正本審査を要する。

## レビューと承認

6.1の計画レビュー受理範囲は「正本違反／ステップが緑にできない／DoDと成果物の不対応」。A計画の基本2周は使用済み。6.3により追加の独立敵対レビューは**PO裁定1回と対象範囲指定**が先に必要。推奨裁定は「追加レビュー1回、対象は本追補全文と元計画のステップ表・6.1コミット規律・7.7履歴手順への影響節」。計画レビュー重大度はP0=正本・ゲート破綻または実行不能、P1=一意でない/規約矛盾、P2=表現・記録。レビュー指摘の採否と最終反映差分を人間承認対象にする。今回の方針支持は追加レビューの範囲裁定や追補の最終承認として扱わない。
