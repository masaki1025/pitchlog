### 4. 確定ゲートの機構と進行順序の制約

- `/finalize-doc` の手順: ① 変更履歴表/frontmatter を `in-review` へ → ② `codex_run.py review adversarial`(sol xhigh)→ ③ 採用/不採用に分類して反映 → ④ 収束まで反復(**反映周ごとに 1 コミット・件名に `反映<r>周目`・実装ステップ番号を付けない**・`plan.md` の `確定ゲート周回` を +1)→ ⑤ 人間の承認 → **⑥ approved 化・版数確定・変更履歴追記・索引の現行化** → ⑦ worklog(典拠: `.claude/skills/finalize-doc/SKILL.md:13-21`)
- 「**敵対レビューを経ずに approved にする経路は存在しない**」(典拠: 同 `:9`)
- 反映周コミットは `{1..確定ゲート周回}` と機械突合される(典拠: `docs/development/dev-harness-design-2026-08-07.md:295-316`)
- **`check_docs_status.py` の 3 検査を同一コミットで揃える**(典拠: `scripts/check_docs_status.py:694`・`:705`・`:830`):
  - frontmatter の `status` ≡ 索引の状態セル(セルは最初の `(` 以降を切り捨てて正規化)
  - 索引の版 ≡ 変更履歴表の**最大版**(版セルは `2.3` 形式。**`v2.3` は不正**)
  - 索引の最終更新 ≥ 変更履歴表の最大日付
  - → **要件書と設計書を別コミットで進めた瞬間に赤**。この検査は `docs-lint` だけでなく `tests/test_check_docs_status.py:976` が実リポジトリに対して走るので **`/check`(pytest)でも落ちる**
- **要件書・設計書の approved を不変条件にするテストは存在しない**(実測)。**H-84 が発火するのは onboarding を触る場合だけ** — `tests/test_verify_nfr021_evidence.py:2403 test_real_repository_onboarding_is_approved` は HEAD の blob が `approved` であることを要求するため、**同書の確定ゲート中は必ず赤**。`/pr` は `/check` 成功を要求するので **approved 化まで PR を出せない順序が機構的に強制される**(典拠: `docs/development/harness-evaluation.md:610-619`)
