# 調査メモ: PostgreSQL 認可構成の実機検証

**◎印** = 調査サブエージェントの報告のうち **Claude が原典を直接確認したもの**。
**◆印** = **Claude が実 PostgreSQL(17.11)で実行して確認した事実**(4 節)。
略記: `REQ` = `docs/requirements/requirements-pitchlog-2026-07-22.md` /
`CAND` = `docs/features/product-data-model-design/design.md`(候補案) /
`HARNESS` = `docs/development/dev-harness-design-2026-08-07.md`。

## 問い

候補案 3 章・8 章が提案した認可構成は「**形を提案し検証はしていない**」と自己申告されている(`CAND:1789`)。
本タスクはこれを実 PostgreSQL で検証し、**通った構成だけ**を確定して TSK-250 へ引き渡す。

1. 候補案が提案する構成は**実際に動くか**。前タスクが誤った 2 点は本当に誤りか
2. **要件は何を要求しているか**。AUTH カタログの母集合をどこから作るか
3. 過去の決定が構成に課す**制約**は何か
4. 越境テストの**合否をどう定義するか**

## 結論(要約)

1. **前タスクの 2 つの誤りは、いずれも実機で再現した**(◆)。加えて **`search_path` 乗っ取りの成立も再現**した。
   候補案が挙げた 4 件の ACL 契約は**すべて load-bearing**(1 つでも欠くと越境する)。
2. **越境テストの方法論に重大な落とし穴がある**(◆・**本調査で新たに判明**)。
   **`SET ROLE` の可否はセッションの認証ユーザーで判定される**ため、**superuser セッションから
   `SET ROLE` してロールを模しても検証にならない**(superuser は任意のロールになれる)。
   **テストは実際にそのロールで接続しなければならない。**
3. **要件書には「認可を DB 層で強制せよ」という条項が 1 件も無い**(◎)。RLS・DB ロール・GRANT・
   `SECURITY DEFINER` の記述はゼロで、NFR-010 の測定方法は「**API 直叩きを含む越境テスト(CI 常設)**」。
   → **AUTH カタログは要件の写像ではなく設計判断を含む**。この事実を計画に明記する必要がある。
4. **最強の拘束は `REQ:1004`「DB は標準 PostgreSQL の範囲で使用し、ホスティング固有機能に依存しない」**(◎)。
   RLS・`BYPASSRLS`・`FORCE RLS` はコア機能なので適合する。**懸念だった「Supabase 上で `BYPASSRLS` ロールを
   作れるか」は実機で検証し、成立した**(◆ 1-7 節)。ただし **`BYPASSRLS` ロールに何かを所有させる操作は
   実行者がそのロールへ `SET ROLE` できることを要求する**ため、**プロビジョニングは一時的な所属付与と
   その解除を含む 5 手順になる**(1-7-c)。**解除漏れの検査を必須にする**。
5. **NFR-018 との衝突リスク**(◎): `REQ:885` は共有集計を **(β) サーバー内で人手保守する実装が 1 系統**と
   定めている。**共有集計を DB 関数と Python の両方に書くと NFR-018 違反(P0)**。
6. **要件の「2 層」は 2 種類ある**(◎)。**(A) 相互性の 2 層**(対象側の付与 ∧ 要求元の付与)と
   **(B) 操作認可の 2 層**(テナント側権限 ∧ グループ内役割)。**1 つに潰すと必ず 1 件落ちる**。

## 詳細と典拠

### 1. 実機検証の結果(◆ — Claude が PostgreSQL 17.11 で実行)

環境: `postgres:17.11-bookworm` の使い捨てコンテナ(開発 DB と同じ版)。
組んだ構成は候補案 3-2 節どおり — テーブル所有者 / アプリ用 / 関数所有(`BYPASSRLS` あり・なしの 2 種)/ 無所属。
`play(tenant_id, note)` に A・B の 2 行を置き、`tenant_id = current_setting('app.tenant_id', true)` の
RLS ポリシーを貼った。

#### 1-1. RLS の基本(候補案 3-1・3-3 節の確認)

| # | 検証 | 結果 |
| --- | --- | --- |
| A | アプリ用ロール + トランザクション内で `set_config('app.tenant_id','A',true)` | **1 行**(自テナントのみ) |
| B | 同一トランザクションで文脈なし | **0 行**(default-deny) |
| C | **autocommit で `set_config` と本クエリを別文にする** | **0 行** — 候補案 3-3 節の警告(`CAND:191`-`:196`)が**実機で再現**した |
| D | テーブル所有者(FORCE 前) | **2 行**(所有者は RLS をバイパスする) |

**C が意味すること**: `set_config(..., true)` はトランザクションローカルなので、
**接続直後の 1 文で設定して次の文で読む形は成立しない**。テストとアプリの両方で
「1 トランザクションの先頭で設定する」ことを**機構で強制**する必要がある。

#### 1-2. 前タスクの誤り①の再現 — `SECURITY DEFINER` だけでは RLS をバイパスしない

同一の関数本体(`SELECT count(*) FROM public.play`)を `SECURITY DEFINER` で 2 つ作り、
**所有者だけを変えた**:

| 関数所有者 | 関数が見た行数 |
| --- | --- |
| `BYPASSRLS` **なし** | **1**(= RLS が適用され、呼び出し元の文脈で絞られた) |
| `BYPASSRLS` **あり** | **2**(= 全テナント) |

→ **`SECURITY DEFINER` は RLS をバイパスしない。バイパスするのは所有ロールの `BYPASSRLS` 属性である。**
候補案 3-2 節の是正(`CAND:128`-`:133`)は正しい。

**切り分けの注意**(◆): 最初の試行では `permission denied for table play` で止まった。
これは RLS ではなく **`SELECT` 権限**の不足である。**「0 行」と「権限エラー」は別の失敗**であり、
テストは両者を区別して判定しなければならない(混同すると壊れた構成が green になる)。

#### 1-3. 前タスクの誤り②の再現 — 新規関数の `EXECUTE` は既定で `PUBLIC` に付く

| 検証 | 結果 |
| --- | --- |
| 新規関数の `proacl` | **NULL** |
| 同じ関数に対する `has_function_privilege('public', ..., 'EXECUTE')` | **true** |
| **無所属ロールから越境関数を実行** | **成功。2 行(全テナント)が返った** |
| `REVOKE ALL ON FUNCTION ... FROM PUBLIC` 後: `PUBLIC` / 無所属 / アプリ用 | **false / false / true** |

→ **`proacl IS NULL` は「権限なし」ではなく「既定 ACL」を意味する。**
既定では **`PUBLIC` が実行できる**ため、**`REVOKE` を欠くと無所属ロールから越境できる**(実際に読めた)。
候補案の ACL 契約(`CAND:153`-`:158`)は**必須**。

#### 1-4-A. **`pg_temp` による乗っ取り — 本タスク最大の発見**(◆ 2 周目の実機検証)

**計画レビュー 1 周目の指摘を受けて再検証したところ、1-4 節の結論が不十分だったことが判明した。**
`CREATE` 権限を一切持たないロールでも、**一時表だけで `SECURITY DEFINER` 関数を乗っ取れる**。

実測(アプリ用ロールで実接続。`public` への `CREATE` = false / DB への `CREATE` = false /
**DB への `TEMPORARY` = true**〔PUBLIC への既定付与〕):

| 関数の設定 | 返した行数(本物 2 行 / 偽の一時表 4 行) |
| --- | --- |
| `search_path` **未設定** | **4 — 乗っ取り成立** |
| **`SET search_path = pg_catalog, public`** | **4 — 明示しても乗っ取り成立** |
| **`SET search_path = pg_catalog, public, pg_temp`** | **2 — 守れた** |

**一時スキーマは `search_path` に列挙しなくても、relation の名前解決で暗黙に最初に検索される。**
したがって **`pg_temp` を明示的に最後へ置かない限り、`SET search_path` を設定していても防げない。**

**候補案の記述は誤りである**(`CAND:158`): ACL 契約は
「**書き込み可能スキーマ・一時スキーマを `search_path` から外す**」としているが、
**「外す」ことはできない**(列挙しなければ先頭に来る)。**正しくは「`pg_temp` を最後に明示する」。**
**この字面どおりに実装すると脆弱な構成になる** — 本タスクが存在する理由そのものの実例。

**攻撃の成立に必要なもの**: ① `TEMPORARY`(**既定で PUBLIC に付く**)② 一時表への `SELECT` を
関数所有者へ与えること(**攻撃者が一時表の所有者なので自分で `GRANT` できる**)。
**通常スキーマへの `CREATE` 権限は不要。**

→ **1-4 節の「成立には関数所有者が攻撃側スキーマへ `USAGE` を持つ必要がある」は、
通常スキーマ経由の場合の条件であって、一時スキーマ経由には当てはまらない。**

→ **検査項目**: `proconfig` に `search_path` があることだけでは不十分。
**`pg_temp` が明示され、かつ最後にあること**を検査する。あわせて **DB への `TEMPORARY` 権限**も
検査対象に含める(剥奪するか、`pg_temp` の明示で無効化するかを決める)。

#### 1-4. `search_path` 乗っ取りの成立(◆ — **1-4-A の限定的なケース**)

`SET search_path` を**持たない** `SECURITY DEFINER` 関数と、**持つ**関数を並べ、
呼び出し側が偽の `play` テーブル(3 行)を置いたスキーマを `search_path` の先頭に入れた:

| 関数 | 返した行数 |
| --- | --- |
| `SET search_path` **なし** | **3**(= **偽テーブルを読んだ**) |
| `SET search_path` **あり** | **2**(= 本物) |

**成立条件**(◆ — 一度失敗してから判明した): **関数所有者が攻撃側スキーマへ `USAGE` を持つ**必要がある。
最初の試行では乗っ取りが効かなかったが、それは `SET search_path` の効果ではなく
**所有者が当該スキーマを見られなかったから**だった。攻撃者は自分の作ったスキーマへ
`GRANT USAGE ... TO PUBLIC` できるため、**この条件は攻撃者側で満たせる**。

→ **検査は「`search_path` の文字列が正しいこと」だけでは足りない。**
**列挙スキーマへの `CREATE` 権限**と、**アプリ用ロールがスキーマを作れるか**まで見る必要がある。

#### 1-5. **方法論上の落とし穴(本調査で新たに判明)**(◆)

`SET ROLE` の可否は **セッションの認証ユーザー**で判定される。**superuser セッションでは任意のロールへ
`SET ROLE` できる**ため、superuser で接続したテストから `SET ROLE app_role` して権限を確かめても、
**ロール到達性の検証にはならない**。

実測(所属関係は `pg_auth_members` で 0 行であることを確認したうえで):

| 接続方法 | `SET ROLE fn_owner_bypass` |
| --- | --- |
| superuser セッションから `SET ROLE app_role` した状態 | **成功してしまう** |
| **アプリ用ロールで実接続** | **`permission denied to set role` で拒否**(期待どおり) |

同様に、**アプリ用ロールで実接続**したときの結果は次のとおりで、いずれも設計意図と一致した:

| 実接続したロール | 操作 | 結果 |
| --- | --- | --- |
| アプリ用 | 越境関数の実行 | 成功(明示的に `GRANT` 済み) |
| 無所属 | 越境関数の実行(`REVOKE` 後) | **拒否** |
| 無所属 | テーブルの直接読み取り | **拒否** |

→ **越境テストは「そのロールで実際に接続する」形で書く。`SET ROLE` による模擬は不可。**
これは計画の DoD に入れる。

#### 1-6. `NOLOGIN` が担っている役割の再評価(◆)

候補案は「`NOLOGIN` + 誰にも `GRANT` しない」で到達経路を限定するとしている(`CAND:141`)。
実機で確かめた限り、**到達を実際に止めているのは「所属を与えない」ことであり、`NOLOGIN` 自体ではない**
(所属を与えれば `SET ROLE` で到達でき、テーブルを直接読めた)。
→ **`NOLOGIN` は「パスワード認証でログインできない」だけを保証する。**
**ロール所属の検査(`pg_auth_members` の推移的な閉包)を検査項目に入れる必要がある。**

#### 1-7. **Supabase(マネージド環境)での実機検証**(◆ — 人間が 2026-08-31 に実行・Claude が手順を設計)

**結論: 候補案の認可構成は Supabase 上でも成立する。** ただし**構築手順に追加の制約がある**(下記 (c))。

環境: 使い捨ての Supabase プロジェクト。**Data API / 新規表の自動公開 / 自動 RLS をすべて OFF** で作成。
検証後にプロジェクトごと削除する前提。**接続情報・パスワードは Claude に共有していない**(NFR-014)。
結果は SQL エディタの出力のみを受け取った。

##### (a) 前提条件 — `BYPASSRLS` ロールを作れるか

| 確認項目 | 結果 |
| --- | --- |
| `postgres` の `rolsuper` | **`false`** — Supabase の `postgres` は superuser ではない |
| `postgres` の `rolcreaterole` | `true` |
| `postgres` の `rolbypassrls` | **`true`** |
| `CREATE ROLE … NOLOGIN BYPASSRLS` | **成功** |
| RLS + `FORCE ROW LEVEL SECURITY` + `POLICY` | **成功** |

→ **候補案の構成が成立する前提条件は満たされている**。`REQ:1004`(ホスティング固有機能に依存しない)の
懸念だった「マネージド環境で `BYPASSRLS` ロールを作れないのではないか」は**否定された**。
`postgres` 自身が `rolbypassrls = true` を持つため、`CREATE ROLE … BYPASSRLS` が許される
(PostgreSQL は `BYPASSRLS` の付与に superuser ではなく**付与側が同属性を持つこと**を要求する)。

##### (b) ロール所属の既定 — **恒久的な到達経路は存在しない**

`CREATE ROLE` 直後の `pg_auth_members` を確認したところ、Supabase は**作成者へ自動的に所属を与えていた**が、
その内容が重要だった。

| roleid | member | grantor | `admin_option` | `inherit_option` | `set_option` |
| --- | --- | --- | --- | --- | --- |
| `probe_fn_owner_bypass` | `postgres` | `supabase_admin` | **true** | **false** | **false** |

→ **`postgres` は既定では `BYPASSRLS` ロールへ `SET ROLE` できず、権限も継承しない**。
`REVOKE` 後に再確認しても `pg_has_role('postgres', …, 'SET') = false` /
`pg_has_role('postgres', …, 'USAGE') = false` で、**常時開いた到達経路は存在しない**ことを実測した。

**ただし `admin_option = true`** である。**`postgres` の資格情報を持つ者はいつでも
`GRANT … WITH SET TRUE` で経路を開ける**。したがって**統制対象は「経路の存在」ではなく
「`postgres` の資格情報の管理」**である(残余リスクとして記録 — 5-1 節)。

> **Docker(superuser)環境からの一般化は誤りだった。** 1-5 節で「superuser セッションから `SET ROLE` しても
> 検証にならない」という方法論上の落とし穴を見つけたが、**同じ落とし穴が「経路が恒久的に 1 本残る」という
> 見立てそのものにも効いていた**。Docker の `postgres` は superuser なので任意のロールになれるが、
> Supabase の `postgres` は superuser ではなく、**既定では `SET ROLE` できない**。
> → **実機検証でしか出ない差の 3 件目**(① `SECURITY DEFINER` と RLS ② `NOLOGIN` の役割 ③ 本件)。

##### (c) **構築手順の制約 — 所有させる操作は `SET ROLE` 可能であることを要求する**

`CREATE SCHEMA … AUTHORIZATION <role>` と `ALTER FUNCTION … OWNER TO <role>` は**いずれも失敗した**
(`ERROR: 42501: must be able to SET ROLE "probe_fn_owner_bypass"`)。
**`BYPASSRLS` ロールに何かを所有させる操作は、実行者がそのロールへ `SET ROLE` できることを要求する。**
また `ALTER FUNCTION … OWNER TO` は**新所有者が当該スキーマへ `CREATE` 権限を持つこと**も要求する。

→ **プロビジョニング手順が確定した**(そのまま DDL 適用器の実装契約になる — ステップ 4):

1. `CREATE ROLE <fn_owner> NOLOGIN BYPASSRLS`
2. **一時的に** `GRANT <fn_owner> TO <provisioner> WITH SET TRUE`
3. `CREATE SCHEMA … AUTHORIZATION <fn_owner>` → `CREATE FUNCTION` → `ALTER FUNCTION … OWNER TO <fn_owner>`
4. `REVOKE ALL ON FUNCTION … FROM PUBLIC` + アプリ用ロールへ限定 `GRANT EXECUTE`
5. **`REVOKE <fn_owner> FROM <provisioner>`** で経路を閉じる

**手順 5 を忘れると恒久的な到達経路が残る**。カタログ検査(ステップ 5)は
**適用完了後に `pg_has_role(<provisioner>, <fn_owner>, 'SET') = false`** を検査項目に含める必要がある。

##### (d) ACL と越境の成立

| 確認項目 | 結果 |
| --- | --- |
| `REVOKE ALL … FROM PUBLIC` 後の `has_function_privilege('public', …, 'EXECUTE')` | **`false`** |
| 同 `has_function_privilege('probe_app', …, 'EXECUTE')` | **`true`** |
| `SET LOCAL ROLE probe_app` + `set_config('app.tenant_id','A',true)` での**関数経由**の件数 | **`2`**(全テナント) |
| 同一トランザクション・同一ロールでの**直読み**の件数 | **`1`**(自テナントのみ) |

→ **同一トランザクション・同一ロールで、関数経由なら越境でき、直読みなら RLS が効く**。
**「関数だけが越境できる」という設計の中核が Supabase 上でも成立する**ことを実測した。
FORCE RLS 下でも関数所有者の `BYPASSRLS` が効いている。

##### (e) 副次的に判明したこと(検証の実務に効く)

- **Supabase の SQL エディタの文分割はドル引用符を解さない**。`DO $$ … $$` ブロックは
  `unterminated dollar-quoted string` / `syntax error at or near "DECLARE"` で落ちる。
  **`--` コメント中のアポストロフィも分割を壊す**。→ **人間に実行させる検証 SQL は平文 SQL で書き、
  ドル引用符とアポストロフィを使わない**(TSK-250 以降の検証スクリプトにも同じ制約が効く)。
- **新規プロジェクトの既定は「新規表の自動公開」が ON**。これを ON のまま本番運用すると
  **設計した認可経路の外側に公開経路ができる**。→ 残余リスクとして記録(5-1 節)。

### 2. 要件が要求していること(◎)

#### 2-1. **「DB 層で認可を強制せよ」という要件は存在しない**

要件書に **RLS・DB ロール・スキーマ分離・`SECURITY DEFINER`・GRANT 設計・関数シグネチャの記述は一切ない**。
DB に関する規範は次の 3 つだけ:

- `REQ:1002` PostgreSQL(本番 = Supabase、開発 = WSL2 から完結して利用)
- **`REQ:1004`「DB は標準 PostgreSQL の範囲で使用し、ホスティング固有機能に依存しない(可搬性)」**
- `REQ:809` 集計は DB 側絞り込み(NFR-005)

そして **NFR-010 の測定方法は `REQ:841`「越境アクセスの自動テスト(API 直叩き含む。CI に常設)」**。

→ **本タスクが作る AUTH カタログは「要件の写像」ではなく設計判断を含む。**
TSK-250 へ渡すとき、**どこまでが要件由来でどこからが設計判断かを区別して渡す**必要がある。

#### 2-2. 認可行列 — 許可リストと常時 404

**許可リスト(これがすべて)**(`REQ:601`-`:608`): ① FR-041 の共有画面 ② 共有集計エクスポート
③ 制御資源の読み取り ④ 制御資源への操作(7 操作)。
柱書 `REQ:599`「**それ以外のすべての資源・すべての経路は既定で拒否される(404)**」。

**常に 404 になる資源**(`REQ:630`-`:634`): 1 球単位の生記録(88 列 CSV を含む)/ カルテの所見 /
第三者として記録した対戦相手データ / 身体プロフィールの分布 / グループ指定なしの単一テナント名指し。

**既定拒否の射程は「FR-041 が新設する経路」に限られる**(`REQ:599`)。
**FR-035・FR-037 の管理経路は射程外**で現行維持 — **許可リストを全域と読むと管理経路を誤って閉じる**。

#### 2-3. **「2 層」が 2 種類ある**(落としやすい)

| 呼称 | 定義 | 適用対象 | 典拠 |
| --- | --- | --- | --- |
| **(A) 相互性の 2 層** | 対象側の付与 ∧ 要求元の同一粒度の付与 | **共有データ資源**(成績・選手個別・概要・エクスポート) | `REQ:625`-`:629`・前提 4(`REQ:617`) |
| **(B) 操作認可の 2 層** | テナント側の権限 ∧ グループ内の役割 | **制御資源への 7 操作** | `REQ:502` |

**前提条件も 2 セットある**: 共有データ資源の **6 前提**(`REQ:612`-`:619`)と、
制御資源の **3 共通前提**(`REQ:666`-`:670`)。混同禁止。

**7 操作の切り分け**(`REQ:502` と `REQ:923` が完全一致): **2 層を要する 3 操作** = 招待の発行・失効 /
役割の変更 / グループの終了。**テナント側の権限のみの 4 操作** = 作成 / 参加 / 付与変更 / 離脱。

#### 2-4. 越境テストの合否と、DB で判定できる範囲

**合否の定義**(`REQ:923`・`REQ:1027` が再掲): 「越境が 1 件でもあれば fail」ではなく
**「FR-034 の認可行列どおりに通り、行列外はすべて 404」**。

`REQ:923` が列挙する組合せは **13 束**。うち:

- **DB レベル(0 行 / 権限拒否)で判定できる**: 10 束(付与 3 種 × 相互性 / 状態遷移後 /
  複数グループ同時参加 / 制御資源の読み取り①② / 7 操作 / 再有効化 / **参加上限の同時受諾(直列化)** /
  自テナント特例 / 在籍区分変更後)
- **HTTP 404・400 でしか判定できない**: 6 束(常時 404 資源の陰性証明 / 非参加テナントの 404 /
  既定拒否の全経路 / グループ指定なしの直接アクセス / **同時比較上限超過の 400** / 上限計数)
- **アプリ層(キャッシュ)**: 2 束

→ **本タスクの射程は前者。後者は Phase 4 の API テストへ明示送付する**(束が両側にまたがるものがあるため、
「13 束のうち何束」ではなく**束を分割して**数える)。
