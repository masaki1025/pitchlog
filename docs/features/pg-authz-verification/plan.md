## 2. スコープ

### やること

**第 1 群(契約と前提の凍結)**

1. **要件主張母集合** — **全数採取 → 分類**(選択しない)。安定 ID・抽出規則・source-text digest
2. **Supabase の実機確認**(**使い捨てプロジェクト必須**)。`BYPASSRLS` の可否が**構成の前提条件**
3. **DB テスト基盤** — CI へ postgres サービス。**psycopg 3 は製品依存**。**使い捨てクラスタ**を起こす
   フィクスチャと**ロールごとの実接続**

   **7 操作は認可契約のみ**(実副作用は含めない)
5. **oracle の凍結** — 候補 DDL manifest / 既知の不採用構成 / mutant 対応表 / 攻撃木と cut set / 境界案

**第 2 群・第 3 群 — 本計画の承認範囲外。計画改訂 2 で確定する**(人間の裁定 2026-08-31)

probe 検証(DDL と適用器・カタログ検査・越境テスト・mutation・管理経路の probe)と
引き渡し(3 資産・`core-areas.json`・設計書 10.1 の追随)は、**第 1 群の実測を踏まえて改訂 2 で確定**する。
**改訂 2 が満たすべき要件は 4 節の `R-1`〜`R-7`**(3 周分のレビューで確定した実質的な指摘)。

### DDL の位置づけ — **使い捨てクラスタでの構成検証**(レビュー P0-11・P0-2 を採用)

当初は「制御資源 4 表を製品 DDL として作る」としていたが、これは
**TSK-250 の物理モデル(主キー・列型・状態表現・制約・履歴・招待の一回消費・最後の `admin`・
同時受諾の直列化)を先取りする**。候補案自身が物理 DDL を未決としている(`CAND:216`)。

したがって **DDL は probe 構成の検証**とし、**製品資産として確定しない**。
**TSK-250 が実スキーマを適用したあとに同じテストを再実行するゲートを、TSK-250 の完了条件に置く**。

**隔離の単位は「スキーマ」でも「DB」でもなく「クラスタ」である**(レビュー P0-2):
**PostgreSQL のロールはクラスタ全域に存在し、スキーマにも個別 DB にも属さない**。
DB への `TEMPORARY` 権限も同様。したがって
**ロール属性・ロール所属・default ACL を変える変異は、別 DB にしても他の変異へ漏れる**。
→ **これらの変異は使い捨てのコンテナ(新規クラスタ)で実行する**。
**Supabase の検証も本番プロジェクトではなく使い捨てプロジェクトを必須とする。**

## 4. 実装方針

### 重さ分類の根拠 — **コア領域**

成果物は**テナント境界の認可判定そのもの**で、設計書 6.3 の境界定義表に該当する。
→ **sol xhigh・敵対レビュー必須・人間の逐行確認必須**。**design.md は作らない**。

### 信頼境界 — **DB 単体では成りすましを防げない**(レビュー P0-3 を採用)

`current_setting('app.tenant_id')` は**認証されたテナント ID ではない**。
**アプリ用 DB ロール自身が `set_config()` で任意の値を設定できる**(本タスクの検証でも実際にそうしている)。
したがって「要求元を引数に取らなければ成りすませない」は**誤り**である。

**本タスクの立場を明示する**: **`app.tenant_id` は認証済み API サーバーだけが設定する信頼入力**であり、
**DB 接続を攻撃者へ渡さない**ことを前提とする。**この前提を AUTH カタログの残余リスクとして明記**し、
**トークン → GUC の結合の検証は TSK-217 の必須テストへ送る**。
あわせて**アプリ用実接続から他テナント ID を設定できてしまう試験を置き、結果を残余リスクとして記録する**
(隠さない)。

### 認可の軸 — **経路レジストリ + 3 軸**(レビュー P0-2 → P0-1 → P1-7 の 3 周で確定)

当初の 4 値 enum(`成績`/`概要`/`選手個別`/`書き出し`)は**要件の認可軸を表現できない**。
**付与粒度は 3 種**(`成績` / `選手個別` / `書き出し` — `REQ:493`)で、**`概要` は独立した粒度ではなく
`成績` で開く**。また**書き出しは `書き出し ∧ 当該データ種別の付与`** を要する(`REQ:625`-`:629`)。

**2 周目でさらに 1 軸足りないと判明した**(レビュー P0-1): `resource_kind × channel` では
**許可された共有集計 CSV と禁止された FR-032 分析 PDF を区別できない**(どちらも
`team_metrics × export` になる)。FR-034 が許可する**経路**は
**「FR-041 共有画面」と「共有集計エクスポート」の 2 つだけ**で、既存の分析 PDF・スコアカード・
カルテ PDF は同じ媒体でも共有不可である(`REQ:599`-`:650`)。

したがって軸を **3 つ**に分ける:

- **`route_kind`** = `shared_screen` / `shared_aggregate_export`(**許可値はこの 2 つだけ**)。
  **既存経路(FR-020〜032)は明示的な拒否行として保持する**
- **`resource_kind`** = `team_metrics` / `team_summary` / `player_metrics`
- **`channel`** = `screen` / `export`

**直積から必要な付与を機械表で導出**し、**許可セル・拒否セルを全数テストする**。
**常に 404 の 4 資源(生記録・カルテ所見・第三者データ・身体プロフィール分布)は
`resource_kind` の値域に存在しない**。ただし **`pg_enum` のラベル数は「別経路が存在しないこと」を
証明しない**(レビュー P0-1)ため、**予期しない `SECURITY DEFINER` 関数・view が増えていないことを
カタログ検査の exact-set で別に担保する**。

**3 周目でさらに構造の不足が判明した**(レビュー P1-7): `route_kind` の許可値が 2 種しかないのに、
**FR-020〜032 を同じ直積の拒否行として表現するスキーマが無い**。したがって:

- **`route_id` の閉じたレジストリを別に置く** — **FR-020〜032・制御資源の読み取り・7 操作を含む
  全論理経路**を列挙する
- **`route_class`** で許可 2 種(`shared_screen` / `shared_aggregate_export`)を表す
- **経路レジストリと HTTP 行列を exact-set で結ぶ**

**DB で判定する資源行列**と、**TSK-217 が判定する HTTP 経路行列**を**別表**にし、
**後者にも本タスクで安定 ID と必須テスト ID を割り当てる**(送りっぱなしにしない)。
**テスト参照は `planned` と `implemented` を分け、`implemented` は収集結果との実在照合を必須にする**
(将来のテスト ID 文字列を置くだけで「テストの無い主張 0 件」と数えられるのを防ぐ — レビュー P1-11)。

### 関数の責務と、業務行での実証(レビュー P0-1 を採用)

**認可済みテナント ID を返すだけでは、FR-041 の業務データ経路は実証されない**
(アプリ用ロールがその ID で業務表を読もうとしても RLS に遮断される)。

したがって **越境関数は「許可された業務行」を返す**形にし、
**`tenant_id` / 所有種別(`kind = self` か第三者か)/ 在籍状態 / 資源種別**を持つ
**代表的な probe 業務行**に対して、**許可された行だけが返る**ことを試験する。

**集計は関数に書かない** — 関数が返した行に対して **ADR-003 由来の生成 SQL 式**を適用する形とする
(手書き部分 = 認可と行フィルタ / 生成部分 = 集計式 / 製品入口 = 両方を 1 クエリで実行)。

**ただし「製品入口と直接呼び出しの一致」は本タスクでは実行できない**(人間の裁定 2026-08-31・
レビュー P0-6 を採用): ADR-003 D-1/D-11 が要求する**生成基盤(TSK-235)が未実装**であり、
**手書きで模した生成 SQL 式で一致を見ても生成基盤の検証にはならない**。したがって

- **本タスクは「境界案」を機械可読資産として記録するに留める**
  (型付き行投影・関数 signature・生成 SQL への入力方法の案)
- **確定と NFR-018 適合判定は TSK-235 の所有とする**
- **実行できない一致検査を本タスクの合格条件にしない**

### 管理経路 — **代表 probe 操作 1 件に狭める**(人間の裁定 2026-08-31・レビュー P0-3 を採用)

`can_operate(...) RETURNS boolean` は**認可の助言であって操作を強制しない**(管理ロールに基表 DML が
あれば boolean を無視でき、無ければ true でも操作できない)。したがって
**認可と副作用は同一の `SECURITY DEFINER` 関数・同一トランザクション**に置く必要がある。

**ただし 7 操作の実副作用を本タスクで実装すると TSK-250 の物理モデルを先取りする** —
作成時の初期 `admin`・招待の一回消費・同時受諾の直列化・最後の `admin`・無効化時の自動終了・
再有効化・操作ログは**物理状態遷移そのもの**である。probe 上の簡略版では製品経路を証明せず、
正しく実装すれば TSK-250 の territory に入る。

**本タスクの射程**:

- **代表 probe 操作 1 件**で「**呼び出しロールに基表 DML が無い**」「**関数内で認可と副作用が原子的**」
  を実証する。**それ以上の操作は実装しない**
- **7 操作は機械可読な「コマンド・認可契約」として固定する**(閉じた enum・操作別の前提条件・
  テナント側権限とグループ内役割の要否)。**実副作用と競合試験(同時受諾・最後の `admin`・再有効化)は
  TSK-250 の実スキーマ適用へ送る**
- 参照系は**ページング済みの行を返す関数**としてクラス別に**契約だけ**定義する

### 読み取りだけでなく書き込みを検証する(レビュー P0-5・P1-9 を採用)

FR-033 は他テナントへの**操作**を禁じ、共有付与は**参照だけ**を許す(`REQ:585`)。
RLS は **`USING` が既存行の SELECT/UPDATE/DELETE を、`WITH CHECK` が INSERT/UPDATE 後の行を支配**し、
**permissive policy は OR 結合**される。**`TRUNCATE` と `REFERENCES` は RLS の対象外**。

→ **全 probe 表について、ロール × 次の実行行列**を正負で置く:
**SELECT / INSERT / UPDATE(対象行)/ UPDATE(後の行)/ DELETE / TRUNCATE / REFERENCES**。
**共有行は SELECT のみ正例、全 DML は拒否**とする。

→ **ACL は表に適用可能な全権限**(`SELECT`/`INSERT`/`UPDATE`/`DELETE`/`TRUNCATE`/`REFERENCES`/
**`TRIGGER`**/**`MAINTAIN`**)**と列 ACL**を exact-set 比較する。
**`TRIGGER`・`MAINTAIN` の予期しない付与も red にする**。
**`pg_policy` の `polcmd` / `polroles` / `polpermissive` / `polqual` / `polwithcheck` を正規化して exact 比較**する。

### 母集合は「全数採取 → 分類」で作る(レビュー P0-4 を採用)

**`抽出集合 == 母集合` は循環 oracle になる** — 抽出器と母集合を同じ選択規則から作れば、
**両方に同じ欠落が入っても green** になる。「既知の 1 箇条を削除する」負例も、
**抽出規則が最初から拾っていない条項**を検出しない。

したがって:

- **対象節の全見出し・箇条書き・表行をまず構造的に全数採取する**(選択しない)
- **各行を「AUTH 主張」または「対象外 + 理由」のどちらかへ必ず分類する**(未分類を許さない)
- **負例は 3 種**: ① 既知条項の削除 ② **未登録の認可条項の挿入** ③ **表行の追加** ④ **層の追加**
- **`decidable_at` は配列(または claim-layer の中間表)**とし、
  **DB / HTTP / cache それぞれに所有テスト ID を要求する**(単数形で扱わない)

### カタログ検査は「越境経路が関数だけ」を証明する形にする(レビュー P0-7 を採用)

relation 集合を exact-set にするだけでは足りない。**予期しない `SECURITY DEFINER` 関数・別スキーマの
関数・view・列 ACL・`BYPASSRLS` 所有ロールへの `SET ROLE` 経路**が残り得る。

- **`BYPASSRLS` ロールが所有する全 object**・**全 `SECURITY DEFINER` routine**・
  **全 routine の ACL と `proconfig` と依存 relation**を exact-set にする
- **`pg_auth_members` は `set_option` / `inherit_option` / `admin_option` 込みで
  2 種類の到達閉包**(継承による到達 / `SET ROLE` による到達)を検査する
  — **`SET` は既定で true** なので単純な所属グラフでは到達性を判定できない
- **表 ACL に加えて列 ACL・schema ACL・default ACL**(`ALTER DEFAULT PRIVILEGES`)を検査する
  — **新規 object は既定で PUBLIC EXECUTE を持つ**ため、将来 object の既定も閉じる必要がある
- **採用構成外の関数が 1 件増える負例**を置く

### `search_path` は `pg_temp` を最後に明示する(◆ 実測)

**`SET search_path` を設定しても `pg_temp` を明示しなければ乗っ取られる**(1 節)。
**検査は「`search_path` がある」ことではなく「`pg_temp` が明示され、かつ最後にある」こと**を見る。
あわせて **DB への `TEMPORARY` 権限**・**列挙スキーマの所有者と `CREATE` 権限**を別々に検査する。

### プロビジョニング手順 — **所有させる操作は `SET ROLE` 可能であることを要求する**(◆ Supabase 実測)

Supabase の実機検証(research.md 1-7-c)で、**`CREATE SCHEMA … AUTHORIZATION <role>` と
`ALTER FUNCTION … OWNER TO <role>` はいずれも「実行者がそのロールへ `SET ROLE` できること」を要求する**
ことが判明した(`ERROR: 42501: must be able to SET ROLE`)。
さらに `ALTER FUNCTION … OWNER TO` は**新所有者が当該スキーマへ `CREATE` 権限を持つこと**も要求する。

Supabase の `postgres` は `rolsuper = false` で、`CREATE ROLE … BYPASSRLS` の直後に自動付与される所属は
**`admin_option = true` / `inherit_option = false` / `set_option = false`** — つまり
**既定では `SET ROLE` できない**。したがって**一時的に経路を開き、使い終わったら閉じる**必要がある。

**DDL 適用器(第 2 群のステップ)の実装契約**:

| # | 操作 | 検査 |
| --- | --- | --- |
| 1 | `CREATE ROLE <fn_owner> NOLOGIN BYPASSRLS` | `rolbypassrls` / `rolcanlogin` |
| 2 | **一時的に** `GRANT <fn_owner> TO <provisioner> WITH SET TRUE` | — |
| 3 | `CREATE SCHEMA … AUTHORIZATION <fn_owner>` → `CREATE FUNCTION` → `ALTER FUNCTION … OWNER TO <fn_owner>` | `pg_proc.proowner` / `pg_namespace.nspowner` |
| 4 | `REVOKE ALL ON FUNCTION … FROM PUBLIC` + アプリ用ロールへ限定 `GRANT EXECUTE` | 全オーバーロードで `has_function_privilege('public', …, 'EXECUTE') = false` |
| 5 | **`REVOKE <fn_owner> FROM <provisioner>`** で経路を閉じる | **`pg_has_role(<provisioner>, <fn_owner>, 'SET') = false`** かつ **`… 'USAGE') = false`** |

**手順 5 の検査はカタログ検査の必須項目**とする(research.md `RES-02`)。
**手順 2 を後回しにすると手順 3 が落ちる**ため、**適用器は手順の順序自体を契約として持つ**
(順序を入れ替える変異を mutation の対象に含める — 改訂 2 の `R-8`)。

**DB 層で塞げないもの**(research.md 5-1-R):

- **`RES-01`**: `<provisioner>` は `admin_option = true` を持つため、**その資格情報を持つ者はいつでも
  手順 2 を再実行して経路を開ける**。カタログ検査が示せるのは**「適用完了時点で閉じていること」**だけで、
  **「開けられないこと」は示せない**。→ **`<provisioner>` の資格情報管理は運用統制へ送る**(申し送り 7 節)
- **`RES-03`**: Supabase の**新規プロジェクト既定「新規表の自動公開」が ON**。ON のままだと
  **設計した認可経路の外側に公開経路ができる**。**`pg_catalog` に現れないためカタログ検査では検出できない**。
  → **明示的に本タスクの射程外**とし、**本番プロジェクトの作成手順へ送る**(申し送り 7 節)

### mutation は 2 系統に分ける(レビュー P0-4・P1-8 を採用)

| 系統 | 内容 |
| --- | --- |
| **構成軸** | 所有者の `BYPASSRLS` 除去 / 所有者の入れ替え / `REVOKE` の省略 / **`pg_temp` の除去** / `FORCE RLS` の解除 / ロール所属の付与 / アプリ用ロールへの `CREATE`・`TEMPORARY` 付与 / 管理関数の `EXECUTE` をアプリ用ロールへ / **`WITH CHECK` の削除** / **`USING (true)` の permissive policy 追加** / **`TRUNCATE`・`REFERENCES` の付与** |
| **認可述語軸**(**新設**) | **要件主張 1 件につき最低 1 変異**。グループ `active` 条件の削除 / 参加条件の片側削除 / 有効条件の片側削除 / 指定外グループの付与を参照 / 自テナント例外の過剰適用 / `kind = self` または在籍 `active` の削除 / 書き出しの下位付与の削除 / 制御資源の 3 共通前提の削除 / 7 操作のテナント側権限または `admin` 条件の削除 / 最後の `admin` 不変条件の削除 |

**単独変異だけでは足りない**(2 周目 レビュー P0-5): **防御が重なっている箇所は、片方を壊しただけでは
攻撃が成立しない**(例: `pg_temp` の末尾固定と `TEMPORARY` の剥奪を併用した場合、両方を壊したときだけ
成立する)。全単独変異に kill を要求すると、**防御を重ねた構成を誤って不合格にするか、
複合故障を一度も試さないか**のどちらかになる。

したがって:

- **構成を攻撃木(fault tree)にし、攻撃成立に必要な最小 cut set を列挙する**
- **単独変異に加え、全 2 因子の相互作用と既知の cut set を実行する**
- **認可述語は AND だけでなく OR・NOT・CASE を含む決定単位で MC/DC を生成する**
  (自テナント例外・permissive policy の OR・操作別条件は AND 限定では覆えない)
- **「カタログ差分による drift 検出」と「実際の越境成立による kill」を別の合否として記録する**

**許可セルごとに正例**を置く。

**kill の判定を厳密にする**(レビュー P1-8): 「red になった」だけでは変異適用失敗・fixture エラー・
接続不能でも kill と誤認する。**① 変異後のカタログが狙った属性だけ変化した ② テストが
skip/xfail/error でなく実行された ③ 期待した assertion か SQLSTATE で失敗した
④ setup/teardown 失敗を kill に数えない ⑤ ロール属性・所属・default ACL の変異は使い捨てクラスタで実行する**
を機械確認する。

### 実接続の行列(レビュー P1-7 を採用)

**`NOLOGIN` の関数所有ロールは実接続できない**ため実行行列に入れられない。行列は
**テーブル所有者(LOGIN) / アプリ用(LOGIN) / 管理呼び出し用(LOGIN) / 無所属 outsider(LOGIN)** の 4 本。
関数所有ロールは**カタログ検査の対象**とし、実行は `SECURITY DEFINER` 経由だけ。
**テーブル所有者を行列に入れることで `FORCE RLS` 解除が越境テストでも検出できる**。

**各テストの冒頭で `session_user` / `current_user` を照合する**(ソースの grep を合格根拠にしない —
レビュー P1-9)。

### 冪等性 — `CREATE OR REPLACE` + ACL 正規化(レビュー P1-22 を採用)

当初は「`CREATE OR REPLACE` は ACL を保存するので `DROP`+`CREATE`」としたが、
**`DROP`/再作成は OID が変わり、依存する view・trigger 等を壊す**。
**`CREATE OR REPLACE` + `ALTER OWNER` + ACL の全正規化**(`REVOKE ALL` → 限定 `GRANT`)で
宣言状態へ収束させる。**signature/戻り型の変更は versioned migration として依存を明示処理する**。
**mutation は製品適用器を巻き戻し装置にせず、変異ごとに新しい DB を作る**。

| # | 要件 | 由来 |
| --- | --- | --- |
| R-1 | **関数 body の改変を捕捉する** — `pg_depend` の依存 relation 検査では、**既存 `SECURITY DEFINER` 関数の本体に禁止 relation への参照を後から足す改変**を捕捉できない(文字列 body・PL/pgSQL では依存が完全には追跡されない)。**正規化した `pg_get_functiondef` / owner / language / security / volatility / leakproof / strict / parallel / `proconfig` / ACL の digest を oracle 化**する。読み取り関数は可能なら **`LANGUAGE SQL BEGIN ATOMIC`** に限定し、PL/pgSQL では**動的 SQL を禁止・検査**する。**負例: 既存関数の body へ禁止 relation の SELECT/DML を追加** | 3 周目 P0-2 |

| R-3 | **TOCTOU を検証する** — 失敗注入の rollback は「部分 commit が残らない」ことしか示さない。**認可 SELECT と副作用 DML の間に別トランザクションが認可状態を変える**競合は未検証。副作用を持つ関数は `VOLATILE` で**内部クエリごとに新しい snapshot** を取るため、同一関数・同一トランザクションでは閉じない。**認可確認直後に barrier を置く 2 接続試験**を追加し、**認可行を lock するか、認可条件を副作用 DML の同一文へ埋め込む**ことで **linearization point が一意**であることを実証する | 3 周目 P0-4 |
| R-4 | **TSK-250 への受取契約を登録して read-back する** — 申し送りの箇条書きでは受け手の完了条件にならない。**TSK-250 の DoD へ、7 操作の全状態遷移・招待の一回消費・同時受諾・最後の `admin` の離脱/降格・無効化時の終了・再有効化・cache・通知/操作ログを安定テスト ID 付きで登録**し、**相互リンク後に read-back で exact 照合**する。**probe テストを「移植可能な claim テスト」と「probe 固有の catalog テスト」に分け**、TSK-250 は**製品 adapter と製品 manifest を実装前に凍結して前者を再実行**する | 3 周目 P0-5 |
| R-5 | **適用原子性の失敗点を固定する** — 「失敗注入」の範囲が未定義だと**最初の文より前に失敗させるだけで合格**できる。失敗点を **ロール作成後 / policy 変更後 / body 置換後 / owner 変更後 / ACL 正規化途中**に固定し、比較対象に**全対象 catalog・membership・default ACL・fixture data** を含める。**古い直接 GRANT は 1 回目と 2 回目の双方で消えている**ことを要求する | 3 周目 P1-9 |
| R-6 | **表権限は PostgreSQL 17 の 8 種**(`SELECT`/`INSERT`/`UPDATE`/`DELETE`/`TRUNCATE`/`REFERENCES`/**`TRIGGER`**/**`MAINTAIN`**)を**単一の機械可読集合から**カタログ検査・実行行列・mutation へ生成する。**「6 権限」という記述を残さない**(`MAINTAIN` は VACUUM・ANALYZE・REFRESH MATERIALIZED VIEW・LOCK を許す実効権限) | 3 周目 P1-13 |
| R-7 | **claim を `probe_executable` と `contract_only` に分ける** — HTTP/cache と実装しない 6 操作には**本タスク内の実越境 kill 経路が無い**ため、「全 claim に runtime kill」は不可能か、**契約 lint を実副作用 kill として数える抜け道**になる。前者だけ runtime kill を必須にし、**後者は schema-drift kill + 受取タスクの runtime テスト ID** を必須にする | 3 周目 P1-8 |
| R-8 | **プロビジョニング手順の順序と解除漏れを検査する**(◆ Supabase 実測 — 4 節「プロビジョニング手順」)。`BYPASSRLS` ロールに何かを所有させる操作は実行者の `SET ROLE` 可能性を要求するため、**適用器は「一時的に開く → 所有させる → 閉じる」の順序を契約として持つ**。**カタログ検査に `pg_has_role(<provisioner>, <fn_owner>, 'SET') = false` / `'USAGE') = false` を必須項目**として入れ、**mutation に「手順 5 の `REVOKE` を省略」と「手順 2 を手順 3 の後ろへ移す」の 2 件**を加える(前者は red、後者は適用そのものが失敗することを期待値とする)。**`RES-01`(`admin_option = true` により経路は再度開ける)は DB 層で塞げない**ため、検査対象は「適用完了時点で閉じていること」に限ると明記する | Supabase 実機検証 2026-08-31(`RES-01`・`RES-02`) |

## 7. TSK-250 への申し送り

- **`search_path` の扱いを是正した** — 候補案 3-2 節「一時スキーマを `search_path` から外す」は**誤り**。
  **`pg_temp` を最後に明示する**が正しい。**不採用構成表に記録済み**
- **NFR-018 との関係**: 集計は **ADR-003 由来の生成 SQL 式**を DB で実行する(手書きしない)。
  **本タスクは境界案を記録するに留め、確定と適合判定は TSK-235 の所有**(人間の裁定 2026-08-31)
- **DDL は probe 構成の検証**であり製品スキーマではない。
  **TSK-250 の完了条件に「実スキーマで同じテストを再実行する」を置く**
- **管理経路の 7 操作の実副作用と競合試験**(同時受諾の直列化・最後の `admin`・再有効化・
  招待の一回消費・無効化時の自動終了・操作ログ)は **TSK-250 の実スキーマ適用へ送る**。
  本タスクは**認可契約として機械可読に固定するだけ**
- **隔離の単位はクラスタ** — ロールはクラスタ全域に存在するため、TSK-250 が同じテストを再実行するときも
  **ロール変異は使い捨てクラスタで行う**必要がある
- **DB 単体では成りすましを防げない**(`app.tenant_id` は信頼入力)。残余リスクとして引き渡す
- **要件書には「認可を DB 層で強制せよ」という条項が無い**。カタログは**設計判断を含む**
- **NFR-019(b) のうち HTTP でしか判定できない束**は TSK-217 へ
- **Supabase(本番想定のマネージド環境)で構成が成立することを実測した**(research.md 1-7 節・
  `probe/supabase-managed.sql`)。**`REQ:1004` の懸念は解消**。ただし**構築手順に制約がある**ため、
  **4 節「プロビジョニング手順」の 5 手順をそのまま TSK-250 の実スキーマ適用へ引き渡す**
- **運用統制へ送るもの**(DB 層で塞げない — research.md 5-1-R):
  - **`RES-01`**: `<provisioner>`(Supabase では `postgres`)は `BYPASSRLS` ロールへ `admin_option = true` を
    持つため、**その資格情報を持つ者はいつでも到達経路を開ける**。**統制対象は資格情報の管理**であり、
    カタログ検査が示せるのは「適用完了時点で閉じていること」だけ
  - **`RES-03`**: Supabase の**新規プロジェクト既定「新規表の自動公開」が ON**。
    **`pg_catalog` に現れないためカタログ検査では検出できない**。**本番プロジェクトの作成手順**へ送る
    (作成時に Data API / 新規表の自動公開 / 自動 RLS を OFF にする)
- **人間に実行させる検証 SQL の書き方**: Supabase の SQL エディタの**文分割はドル引用符を解さず、
  `--` コメント中のアポストロフィも分割を壊す**。**`DO` ブロックを使わず平文 SQL で書く**
  (TSK-250 以降の検証スクリプトにも同じ制約が効く)
