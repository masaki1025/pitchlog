# 固定関数実行器 A/B/C 分割案（承認前）

2026-10-15。Claude調整役の照会に対するTSK-550担当案。既受理契約、計画、正本、凍結資産をこの文書だけで改訂しない。独立レビューとPOの計画追補承認を経るまで実装しない。

## 採否案と境界

**条件付き採用を推奨する。** Aは共有実行器だけを先行統合し、製品関数の登録は0件とする。その後、BはTSK-550段階A resolverを1件、CはU-R1 RG1専用関数を2件、それぞれA統合済みdevelopを基線に別PRで進める。BとCには実行時の相互依存を置かない。ただし**現行受理文言のままならCはBの登録を待つ**。CをBより先に統合可能にするには「最初の登録対象はresolver1件」の順序制約をPOが明示的に変更し、両計画・受理記録へ反映する必要がある。どちらが先に統合されても後続PRは最新の凍結契約revision、digest、7.7 before/afterを取り直し、同じ共有JSON・registryへの差分を再基線化する。この**統合上の直列化**はBの製品機能をCの実行時依存にする理由ではない。

| 単位 | 所有・差分 | 合格境界とゲート |
| --- | --- | --- |
| A：共有実行器 | TSK-550担当が共有`FunctionOperationRegistration`、同一`_TenantTransaction.run_function`、固定registryの空集合を定義。既存DML登録/`run`を維持し、製品関数・SQL・関数ACLの登録は0件 | 空集合のまま未登録tokenを拒否する。**試験専用の閉じた登録入力**で正常な固定関数1件と変異例を通し、DML横断のID/型衝突、固定SQL構造、bind/decoder、tenant/contextの実行直前照合、偽造token、失効scope、任意SQL、repository入口への直接Session注入を拒否する。試験用登録を製品registryや公開資産へ混入させない。共有repository/capability/allowlistの実差分を7.7へ出し、独立レビュー・PO承認後に別PRとして実装・統合。空registryで動くことと、本番の規則解決/試合作成成功を混同しない |
| B：段階A resolver | TSK-550担当の後続PRで`StageAResolveRuleToken`と固定`public.resolve_stage_a_rule(text,text,boolean)`の**1件だけ**を登録 | 承認済み入力/4失敗・同一scope、規則出所、5値の単一相関検査、F-2配置、関数owner/RLS/EXECUTE/GUC、正本・認可・凍結7.7、2接続/故障試験を個別ゲートで満たす。未整備なら保存成功を返さない。現行ステップ3/4/5の範囲・順序の変更は最小計画追補へ明記 |
| C：RG1専用 | U-R1担当の別PRでRG1事前・コミット直前のexact token/固定関数**2件だけ**を登録 | U-R1の物理状態・起動時閉鎖・権限/凍結資産・競合試験の個別承認を要する。U-S1 PortWriter実接合は同担当の後続ステップ。D4外部台帳の未承認は維持。Aへの共有実行器変更が必要ならA/Bへ混ぜず、契約差分を再レビューする |

**「resolver 1件限定」との関係**: [PO代替受理済み契約](step1-contract-acceptance.md)は「最初の登録対象は段階A解決関数1件だけ」と書き、登録型とresolverの1対1も定める。Aの0件は「まだ製品関数を登録しない」構成だが、同時実装の読みを残すため、**空集合の許容を計画・受理シートへ明示する追補が必要**。さらに現行文言のままCをBより先に統合すると、最初の登録がRG1の2件となり衝突する。Cを先行可能にするPO判断案は、「Aの登録0件を許す。TSK-550が登録する製品関数はBのresolver1件だけとする。U-R1は独立受理と個別資産ゲートを経てCのRG1専用2件を登録でき、B/Cの統合順を固定しない。管理/汎用登録は開かない」と**初回登録順序だけを改訂**するもの。POがこの順序変更を承認しなければ、A→B→Cで統合する。既受理の入力、tenant、SQL/decoder、DML非緩和は変更しない。これは**提案**であり、現行PO代替受理の上書きではない。

## 最小計画追補と統合条件

現行[計画](plan.md)の1 PR・ステップ3→4順序から、Aを先行PRへ切り出す点だけを計画追補する。Aはステップ4の共通実行器部分を前倒しするため、ステップ番号/コミット現在地・PR単位・core-guard登録と7.7の受理単位を明示し、承認済みステップ2の成果を変更しない。**A専用ブランチは統合済み最新develop起点の別worktreeで作り、現在のTSK-550本体ブランチのcodec/未承認正本候補をAの差分へ混入させない**。Bはステップ3の関数/配置・認可とステップ4のresolver登録を既存の正式ゲート成立後に進める。CはA統合を待つ。Bより先の統合は上記の順序変更承認後に限る。BとCが同じ凍結資産に触れるため、先に統合した側の正本/資産基線と受理済み履歴を保持し、後続側は追加集合だけを新しい7.7単位で審査する。中間コミットや古いrevision/digestを受理済みとしない。

Aの具体的な公開型・空registryの表現・固定SQL検査・拒否試験、core-guard宣言/登録、**固定関数ID欄・生成契約・検査器・fixtureを含む共有repository-contract/allowlist/runtime authzの所有**とbefore/afterは、**独立のコア計画レビュー後にPOが追補を承認し、個別7.7で具体資産を承認してから**実装する。A単体で関数ownerや製品関数の認可を増やさない。Aの「Session拒否」はrepository入口へSessionを渡す経路を作らない意味であり、B/CでアプリDBロールに関数EXECUTEを与えた後の**DB直接呼出しを阻止する保証ではない**。後者は各関数のGUC・実効ACL・直呼出し負例を個別に検証する。Bのdata-model/認可正本の7.3人間承認、配置/権限の個別ゲートとFR-014/DRAW-04裁定、CのU-R1固有ゲートは残る。U-R1の関数identityは旧`authz_private`ではなく後発の`rg1_api`**候補**を認可担当が確定してから登録する。A統合後もB/Cの製品経路は各ゲートと実試験まで閉じる。

U-R1側の[先行統合追補案](../ur1-recording-rights/shared-function-executor-addendum-proposal.md)はAにresolver1件を含める旧候補を明記しており、今回のA=0案とは一致しない。U-R1担当に今回の分割への差分採否を求め、旧案を黙って受理済みとして扱わない。
