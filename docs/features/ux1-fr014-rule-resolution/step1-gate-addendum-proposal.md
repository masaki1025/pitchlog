# TSK-550 ステップ1ゲートの最小追補案（未承認）

2026-10-14、Codex D の `24566d72` 差分受理を受けた**PO判断用**の案。承認済み9ステップ計画の製品範囲や正本/スキーマ/認可/凍結資産を、この文書だけで変更しない。段階A（全体既定のみ）を先行し、大会割当があれば拒否する意味と段階B後続を維持する。

## 循環と現行計画との差

現行ステップ1は関数・型・失敗・同一scopeとゲートを担当受理してから製品コードへ進む。一方、差分受理は**実関数を通る2接続 PostgreSQL 証跡**も不足とした。この実測をステップ1の条件と読むと、制限関数（ステップ3）、登録（4）、公開resolver（5）、2接続試験（6）が未実装なので循環する。契約の受理と実装後の検証を分ける必要がある。

また現行ステップ2は `rule_sets` 帰属列のmigrationを必須とする。Codex Dは、段階Aに限り、既定表経由・閉じた管理書込・直接ACL拒否で帰属を証明する案を条件付き採用した。帰属列を独断で追加するのも、受理なしにステップ2を飛ばすのも計画と一致しない。`games.applied_rules` のID専用列も追加理由はない。

## PO選択

| 選択 | 内容 | 影響 |
| --- | --- | --- |
| **A（推奨）** | 段階Aだけに9ステップを限定し、ステップ1は実装前の契約/必要な正式ゲートの受理、ステップ2は既存 JSONB と凍結5値schemaを使う strict codec/旧行拒否の実装と試験へ置換。帰属列・大会割当解決・試合上書きは段階Bの別計画/個別ゲート。ステップ3〜6で実関数、固定operation、resolver、2接続/故障注入を順に実測 | 最短で U-G1 の安全な作成側契約へ接続可能。ただし管理/割当の書込入口を本PRへ含めるか、存在しない期間は書込を閉じて後続受理するかを別途明示する。実際の全入口並行安全性はその入口が実装されるまで完了扱い不可 |
| B | 現行ステップ2の帰属列migrationと、後続の全FR-014優先順位を維持。全管理・割当書込入口も本PR内で実装し、実測までTSK-550を閉じない | 既存計画に近いが、個別のschema/認可/凍結ゲートと実装範囲が増え、U-G1 preparing作成を待たせる |

**Aの追加境界（推奨）**: 段階Aでは、`pitchlog_app` の3規則表への直接書込を拒否し、まだ存在しない規則管理・大会割当の製品書込関数を「実装済み」としない。出所を証明できない既存規則行は成功へ使用しない。全体既定の設定に必要な実値・入口が未着地なら、作成は `rule_not_available` で失敗し、仮規則や仮operationによる保存成功を返さない。将来の書込入口は親→割当→既定→規則の順を守る受理/実測を経て有効化する。**Aだけでは初期規則が存在しない環境の製品作成成功は成立しない**。POがMVP内で管理書込を必須と判断する場合は、Aに**管理者専用の最小 RuleSet・既定対応書込関数**を追加する明示追補が必要。大会割当書込は段階Aの解決対象外だが、有効化時には同じ親行直列化を必須にする。
