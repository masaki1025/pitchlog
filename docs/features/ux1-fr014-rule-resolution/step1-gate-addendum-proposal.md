# TSK-550 段階Aの最小計画追補（範囲選択済・最終承認待ち）

2026-10-14、Codex D の `24566d72` 差分受理を受け、POは**Aの範囲を選択**した。これは最終計画承認でも、個別の正本/スキーマ/認可/凍結資産変更の承認でもない。実装前契約をステップ1、実関数の2接続/故障注入をステップ3〜6、U-G1の実HTTP・RG1・全取消をTSK-395ステップ2で検証する。段階A（安全な全体既定の解決、ID+5値の保存、U-G1との同一transaction接続）と段階B後続の区別を維持する。

## 循環と現行計画との差

現行ステップ1は関数・型・失敗・同一scopeとゲートを担当受理してから製品コードへ進む。一方、差分受理は**実関数を通る2接続 PostgreSQL 証跡**も不足とした。この実測をステップ1の条件と読むと、制限関数（ステップ3）、登録（4）、公開resolver（5）、2接続試験（6）が未実装なので循環する。契約の受理と実装後の検証を分ける必要がある。

また現行ステップ2は `rule_sets` 帰属列のmigrationを必須とする。Codex Dは、段階Aに限り、既定表経由・閉じた管理書込・直接ACL拒否で帰属を証明する案を条件付き採用した。帰属列を独断で追加するのも、受理なしにステップ2を飛ばすのも計画と一致しない。`games.applied_rules` のID専用列も追加理由はない。

## PO選択

| 選択 | 内容 | 影響 |
| --- | --- | --- |
| **A（推奨）** | 段階Aだけに9ステップを限定し、ステップ1は実装前の契約/必要な正式ゲートの受理、ステップ2は既存 JSONB と凍結5値schemaを使う strict codec/旧行拒否の実装と試験へ置換。帰属列・大会割当解決・試合上書きは段階Bの別計画/個別ゲート。ステップ3〜6で実関数、固定operation、resolver、2接続/故障注入を順に実測 | 最短で U-G1 の安全な作成側契約へ接続可能。ただし管理/割当の書込入口を本PRへ含めるか、存在しない期間は書込を閉じて後続受理するかを別途明示する。実際の全入口並行安全性はその入口が実装されるまで完了扱い不可 |
| B | 現行ステップ2の帰属列migrationと、後続の全FR-014優先順位を維持。全管理・割当書込入口も本PR内で実装し、実測までTSK-550を閉じない | 既存計画に近いが、個別のschema/認可/凍結ゲートと実装範囲が増え、U-G1 preparing作成を待たせる |

**Aの供給境界と作成までの依存**: 要件書付録F-2の5区分の規則値は2026-07-22確定済み。`pitchlog_app` では `rule_sets`・`tournament_rule_assignments` の直接SELECT/書込を拒否し、`game_type_rule_defaults` の既存SELECTを保持して書込を拒否する。まだ存在しない製品用管理書込関数を実装済みとしない。段階Aの推奨供給は、F-2値/ID/出所を検証可能にする**個別審査済みデータ配置migration（ステップ3）**。値を再裁定せず、曖昧な既存行の採用や衝突上書きもしない。将来の管理書込は認証/権限・所有ロール・EXECUTE対象・監査・既定行→規則行の競合保護を別ゲートで受理する。後続の大会割当書込を有効化する場合は大会親行→割当→既定→規則行の全順序を受理・実測する。データ配置が未着地なら `rule_not_available` 等で全取消し、U-G1は試合作成成功を返さない。**Aのresolverだけでは実データ配置とRG1実operationがない環境の製品作成成功に届かない**。D4は別裁定のまま。

## Aを採る場合の計画差分候補

| 箇所 | 差分候補 | 実施/証跡時点 |
| --- | --- | --- |
| ステップ1合格条件 | 「関数名/型/4 literal、6-key snapshot、全入口の権限・ロック順、同一scope、親不在/無効化/解除の意味、旧行拒否、必要な正式正本ゲート、7.7対象/担当/受理手順について、U-X1・U-G1・認可面・tenant境界が実装前契約を受理」と明確化。**2接続実測は含めない** | 受理記録と正本ゲートの結果。未受理ならステップ2不可 |
| ステップ2 | 帰属列migrationを段階Aの必須から外し、`applied_rules` の `ruleSetId` + 既存5値schema、strict decoder/encoder、旧 `{}` 拒否、round-trip/値域・相関試験へ置換 | 製品コード・pytest。帰属列/曖昧な旧行の推定移行は段階B個別ゲート |
| ステップ3 | 段階A制限関数のDDL/ACL/owner/search_pathと、権限拒否・親/規則行lockの実DB試験。管理書込入口をこの段階で入れるかはPOの明示判断 | 実DB/認可・7.7。割当書込を入れない場合、その並行製品経路は未検証と表示 |
| ステップ4 | 固定 function operation の専用登録型、tenant scope束縛、exact引数/戻り decoder、任意SQL・偽造token拒否。repository-contract変更は担当受理と7.7 | 凍結基線、bypass負例、pytest |
| ステップ5 | 段階Aの全体既定だけのresolver、4 failure、割当あり/上書きあり拒否。FR-014の後続優先順位は段階B | pytest。仮の既定値を持たない |
| ステップ6 | 実関数・実scopeを通る隔離DB二接続。実装済みの書込入口との両順序、rollback、更新競合、故障注入を測定 | HEADを結び付けた試験コード/DBログ。U-G1の実HTTP・game INSERT・RG1は TSK-395 ステップ2の接続試験 |

ステップ7〜9のguard登録・最終検査・申し送り、コア領域敵対レビューと人間逐行確認は維持する。9ステップの数・既存宣言と登録の別コミットも維持する。計画の意味とステップ2/5を変えるため、**承認済み範囲の自動拡張とは扱わず**、本追補の差分を規約の計画レビュー対象として人間承認へ出す。正本の構造変更はハーネス7.6に従い、該当部分だけ7.3の敵対レビューと人間承認を通す。認可/凍結資産の個別差分と7.7受理は別ゲートであり、この追補の承認で代替しない。

1. POのA範囲選択を受け、U-X1独立担当 Codex D、U-G1、認可面、tenant境界へ、6-key shape・4 literal・閉じた入口/ロック順・固定operation・実規則データ供給と未整備時拒否を**実装前契約**として採否確認する。
