## 3. FR-014 の規則関数の切り出し案(PO 判断事項)

- **事実**: 規則読み取り関数・大会へ規則を結ぶ関数・`rule_sets` の帰属列は NFR-018 の対象計算ではない(`req:931`)。`ADR3:929` の「対象計算のコードを追加しない」は掛からない
- **事実**: 単位分割計画書は U-X1 を単位ごと「条文凍結」としている(`product-impl-unit-split/plan.md:367`・`:386`)。根拠は「主所有 FR が丸ごと対象計算」(同 `:396`)
- **事実**: TSK-424 の申し送りで、U-G1(スナップショット)・U-P1(プリフェッチ)の規則の読み取りはこの関数を待つ(Notion TSK-405 カード「TSK-424 からの申し送り」節・`docs/features/product-authz-surface/design.md` 1-6)
- **提案**: この 3 点を **U-X1 から切り出した別タスク**(凍結なし・コア領域 = テナント分離)として先行させる。**裁定するのは PO**。切り出しが通ったら、単位分割計画書の凍結の記述を是正する送り先も同じ裁定で決める
- 本計画書は切り出しの結果に関わらず、**PR-1 のステップに FR-014 の関数を含めない**

## 5. PR-1 の変更構成

### 5-1. 「同一の変更」とコミットの分け方

- `ADR3:930`: 対象計算 1 件ごとに **正本・生成物(派生物)・製品経路の呼び出し部・3 層検査** を「同一の変更」として追加する(**片側だけのコミットを作らない**)
- `req:962`(BOOT-ACTIVATION): 「同一の変更」= develop へ統合される 1 つの PR。**PR 内のコミットの分割は妨げない**
- `req:962` の定義は「**本規定における**」— BOOT 規定の局所定義であり、ADR3 `:930` の読みには使わない
- **本計画の採る形: 1 対象 = 1 コミット**(1 周目 P0-2 で初稿の解釈〔正本と派生物だけを先に入れ、呼び出し部・検査層を後続コミットに分ける〕を撤回)。理由: ①「片側」を正本と派生物に限る根拠が条文に無い ②マニフェストは対象計算ごとに `vectors[]` / `properties[]` / `mutation` の空を許さない(`ADR3:267`)ので、正本だけを登録したコミットはそれ自体が検査に落ちる
- したがって**ステップ 1 = T1 の全部・ステップ 2 = T2 の全部**になる。1 ステップが大きいので、**/implement の委任文は本書 §6 の層ごとの小見出しで作業順を指示する**(コミットは 1 つ)

### 5-2. T1/T2のD-14-m方式と配置

D-14-mのT1/T2対象別開始後は、PR-1に限り**TS正本→再現ビルドした同一JS artifact**が正で、ブラウザと常駐Nodeが同一hashを実行する。TS正本・生成器・artifactの具体パスはTSK-538の承認済み基盤契約を照合し、実T1/T2のsource/generated/entrypoint識別値は対象追加PRのmanifestに置く。D-1-bの`contracts/`外配置と(β)のDB集計は維持する。他対象はD-2全体発効までD-1のままで、段階①全体の完了を装わない。
