## 4. 実装方針

**前提となる調査**: [調査メモ](research.md)。特に **E 節「実行順序の制約」**・**D 節「境界」**・**G 節「既知のリスク」** は本節の方針を規定する(内容は複製せず参照する — 設計書 7.1-1)。

### 重さ分類の根拠 = 通常

- **コア領域に触れない。** CLAUDE.md が列挙する 5 領域(同期プロトコル / 状況計算 / 記録権 / テナント分離 / データ移行)のいずれにも該当しない。プロダクトのドメイン計算・認可・同期のコードを 1 行も変更しない
- **`.claude/core-areas.json` の `guard_paths` にも触れない。** 同ファイルが列挙するのは `core-areas.json` / `ci.yml` / `core_guard.py` / PR テンプレ / `/pr`・`/release`・`/task-done` の各 SKILL.md であり、**本 PR の変更対象はいずれも含まれない**。`ci.yml` を触らない判断(2 節「やらないこと」1)がここでも効く
- **軽微ではない。** 正本の版繰り上げ + 確定ゲートを含み、Phase 4 の完了を確定させる判定を伴う

### 順序制約(本タスク固有 — 機構では守られない)

失効判定は `T` → `E` の**各コミットの変更パスの和集合**に対して行われ、allowlist は `docs/ops/nfr021-acceptance/`・`docs/worklog/`・`docs/features/` の 3 つだけである。**設計書・台帳・`docs/README.md` はいずれも失効対象**(`default: "invalidating"`)。また **`E` の後にコミットを積めない**(マージが `--match-head-commit <E>` のため)。

```
ステップ1(設計書 v1.10 起案 + 索引を in-review/1.10 へ — 同一コミット)
  → /finalize-doc(確定ゲート — 反映周コミットは複数。ステップ記法を付けない)
     └ 承認後: 設計書を approved 化・変更履歴追記・索引を approved/日付へ現行化(手順 6)
  → ステップ2(台帳 follow-up + 索引の台帳行の日付)
  → 【初回公開】git push -u origin feature/phase4-6-acceptance  ← 宛先を明示する
  → 【T = push 済みの HEAD(= ステップ 2 のコミット)の完全 40 桁 OID を固定】
     └ remote の同ブランチ SHA が T と一致することを確認してから次へ進む
  → 【人間ゲート: 受入の実施(PO)— コミットを伴わない】
  → 結果証跡を作成し、3 節の別枠へ実パスを追記(未コミット)
  → /pr(クローズ処理コミット = 【E】→ push → PR 作成)
  → PR head = E を確認・E に対する CI(success 必須 7 本)を確認
  → 検証器を candidate_sha = E で実行 → 判定者の合格判定
  → 排他区間の開始 → phase4_base_sha 固定 → head/base 再照合 → マージ
  → マージ後検査 → PR へ 4 項目を記録 → 排他解除
```

#### `/pr` のクローズ処理コミットを `E` にする(計画レビュー 1 周目 P0 の反映)

当初案は「`/pr` を `E` より前に実行する」だったが、**成立しない**。`/pr` のクローズ処理は plan status・worklog をコミットして push するため、`T` の後・`E` の前に HEAD が動き、**受入環境が取得する HEAD が `T` と一致しなくなる**。したがって次のとおりにする。

- **`/pr` は受入完走後に 1 回だけ実行する。** そのクローズ処理コミットが `E` である(証跡 + worklog の締め + plan status + 3 節の実パス追記を 1 コミットに含める)
- **`/pr` のクローズ処理で台帳・索引を追加更新しない。** `/pr` SKILL 1-3 は台帳追記時に `docs/README.md` の索引日付も更新するが、**索引は allowlist 外**であり `T`→`E` に入ると**証跡が失効する**。台帳・索引の更新はステップ 2 で済ませ、`/pr` 実行時は **worklog に「台帳への追記なし(ステップ 2 で実施済み)」と記録**して 1-3 を満たす
- **`E` を push し、PR の remote head が `E` であることを確認する。** `--match-head-commit <E>` は remote head が `E` でなければ失敗する
- **CI は `E` に対して判定する**(`/pr` 時点ではなく `E` に対して)。判定の契約は下記「マージ統制の実行順」手順 2 が正 — 文書のみの変更では `frontend`・`backend` が skipped になるため「全ジョブ緑」は成立しない

#### 受入の実施(コミットを伴わない人間ゲート)

判定者(PO)が受入プロファイル上の新規環境で `onboarding.md` v1.0 の 0〜8 章を完走する。Claude は操作補助と記録の起草のみ(設計書 `:638`)。合格項目 5 は sandbox でソケット bind ができず Codex へ委任できない(台帳 H-69 (c))ため、**委任計画を立てない**。人手必須箇所は research.md B-5(7 系統 17 件)。

**受入対象のツリーの取得方法**(計画レビュー 1 周目 P0・2 周目 P2・**3 周目 P0** の反映)。

`onboarding.md` 2 章の develop 切り替えをそのまま行うと、**`develop` には本 PR の変更が入っておらず `T` を試験したことにならない**。同章の注記が排除しているのは `main` のみであり(`onboarding.md:206`)、受入 README `:191` は「**予約を含む候補ツリー**で完走」と定める(research.md F-1 の裁定)。

**ただし detached checkout は採れない**(3 周目 P0)。`onboarding.md` 6 章 項目 5 は **`develop` 上で git_guard が拒否すること**を合格条件とするが(`onboarding.md:300`)、`git_guard.py` の `current_branch` は `git rev-parse --abbrev-ref HEAD` を使うため、**detached HEAD では文字列 `HEAD` が返り、`PROTECTED` にも「解決不能」にも該当せずガードが発火しない**(`git_guard.py:467-473`)。結果として**受入項目そのものが落ちる**。

**したがって「`T` を指すローカル `develop` ブランチ」で試験する。** 候補ツリーの固定と 6 章の成立を両立させる唯一の形である。

| onboarding 2 章の行 | 受入時に代わりに実行する |
| --- | --- |
| clone 直後の切り替え | **`origin` から feature ブランチを明示的に fetch したうえで、ローカル `develop` を `T` の位置へ強制的に作り直して切り替える**(`git fetch origin feature/phase4-6-acceptance` → `git switch -C develop <T>` 相当)。**これはローカル ref だけを変え、`origin/develop` は更新しない** |
| `develop` であることを確認する行 | **逐語どおり実施**(`git branch --show-current` が `develop` であること)**に加えて、`git rev-parse HEAD` の出力が `T` と完全一致することを確認する** |

これにより **① 現在ブランチ名 = `develop`**(6 章 項目 5 の git_guard 試験が成立する)**② ツリー = `T`**(候補ツリーを試験している)の両方が満たされる。**3 章以降は逐語どおり実施する。**

**この置換は approved な手順の逐語からの逸脱**であり、**判定者の了解事項として本書に記録する**。証跡の「実行コマンドと終了コード」欄にも置換後の実コマンドを、「各合格項目の期待値と実測値」欄に `git rev-parse HEAD` の実測値を記録する。

#### `E` を作った後に不合格になった場合の復帰経路(計画レビュー 2 周目 P1 の反映)

「`E` の後にコミットを積めない」は**マージへ進む成功時だけの不変条件**である。`E` はまだ `develop` へ統合されておらず、append-only の統合時検査も未通過なので、**統合前なら作り直せる**。CI・検証器・判定者のいずれかで不合格になった場合は、原因によって 2 分岐する。

| 原因 | 対処 | `T` の扱い |
| --- | --- | --- |
| **allowlist 配下だけで直せる**(証跡の記入漏れ・プレースホルダの残り・欄名の不一致・ファイル名の誤りなど) | `/pr` の「差し戻しが発生したら」手順で計画書を `in-review` → `active` へ戻し、証跡を修正して**新しいクローズ処理コミット `E′`** を作り、push して `E′` を候補にする | **維持できる**(`T`→`E′` の差分が allowlist 配下に収まるため) |
| **失効対象パスを直す必要がある**(設計書・台帳・索引・`onboarding.md` などの誤り) | 直すと `T`→`E` に失効対象が入り証跡が失効する。**下記「受入が不合格だった場合の経路」と同じ扱い**にする — 失敗閉塞 → 新規予約 → 新しい `T` → 再受入 | **採り直す** |

#### 受入が不合格だった場合の経路(計画レビュー 1 周目 P0 の反映)

**`/task-done` は使えない。** 同スキルは `gh pr view` で PR が **MERGED** であることを前提とし、その 4-6 分岐は**マージ後検査**の合否を扱う。受入そのものが不合格なら 4-6 PR はマージできないため、この経路には入れない。設計書 `:643` ⑤ に従い次のとおりにする。

1. **不合格の結果証跡を 4-6 ブランチへコミットしない。** コミットするとマージできない PR の中に閉じ込められ、予約を閉じられない
2. **別ブランチで「結果証跡だけを運ぶ監査 PR」**を作り、`result: failed` の証跡で予約 `phase4-001-20260819T142916Z` を閉じて `develop` へ統合する(Phase 4 の実装を含めない)
3. **次の試行を予約する**(`attempt_seq` = 2 の予約レコードを別の監査 PR で `develop` へ統合)
4. **4-6 ブランチへ `develop` を取り込み、新しい `T` を採り直して再実施する**(検証器の合格条件 ⑧⑨ は、候補ツリーに当該ゲートキーの予約がすべて閉じた状態で存在することを要求するため)
5. **Notion タスクは `進行中` のまま**とし、経緯をコメントで記録する(`/task-done` へは進まない)
