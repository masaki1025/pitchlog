## 4. 実装方針

### 重さ分類 = 通常(根拠)

CLAUDE.md が列挙する**コア領域 5 つ(同期プロトコル / 状況計算 / 記録権 / テナント分離 / データ移行)のいずれにも触れない**。`.claude/core-areas.json` の `areas[].paths` に該当 0 件。

**ただし `guard_paths` には該当する**(4 周目 P1 でスコープに `.claude/skills/pr/SKILL.md` が入ったため)。同ファイルのトップレベル `guard_paths` は `core-areas.json` / `ci.yml` / `core_guard.py` / `pull_request_template.md` / **`pr/SKILL.md`** の 5 件で、最後の 1 件に触れる。したがって **CI の core-guard が発火し、PR 本文の逐行確認チェックが必須**になる(コア領域そのものではないので敵対レビュー項目は不要 — `/pr` の判定表)。

**ただし設計書の版繰り上げにより `/finalize-doc` の確定ゲート(敵対レビュー + 人間承認)が乗る。** レビュー負荷は「通常」の想定を超えるため、計画レビューにも敵対レビューを適用する。

### 設計書の改訂内容(A-1〜A-3)

**A-1: ステップ検出書式の厳密文法**

現在 `設計書:252` は `(ステップ <k>[/<N>][ 付記])` という表記だけを示している。次を追記する(いずれも実装が既に行っている検査であり、**実装追随の明文化**):

- 開き括弧と閉じ括弧は**同種で一致**すること(`（ステップ 7)` は不整合)
- **`k = 0` は不正**
- `/<N>` を書く場合、**ステップ表の総数 N と一致**すること
- 数値の直後に許される文字を**列挙**する(1 周目 P2 — 「境界文字」では句読点等を含む一般的な単語境界とも読める)。実装が許すのは **`/`(総数の区切り)/ 同種の閉じ括弧 / 空白** の 3 つで、それ以外は不正(`(ステップ 2abc)` は不正)
- **括弧のない文言は不算入**(`docs: ステップ 2 の補足` はステップコミットと見なされない)
- 1 件名に**2 個以上のトークンがあれば不整合**

**A-2: `確定ゲート周回` の反映周コミット規定**

現在の規定(`設計書:272`)は「指摘反映を伴う 1 周ごとに +1」だけで、コミットを要求していない。次を追記する:

- **指摘反映を伴う 1 周ごとに 1 コミットを作る。** 件名に **`反映<r>周目`** を**必ず含める**(`<r>` は 1 始まりの周回番号)
- **実装ステップ表の番号は割り当てない。** 件名にステップ記法を用いず `反映<r>周目` だけを含める(例 `docs: 確定ゲート 反映3周目 — 指摘 4 件を反映`)
  - **理由**(確定ゲート 1 周目 P1): 反映周は複数コミットになるため、ステップ記法を付けると**同一ステップ番号のコミットが複数本**生まれ、`implement/SKILL.md:33`・`plan-template.md:42`・`CLAUDE.md:45` が規定する「**1 ステップ = 1 コミット**」と衝突する。**番号を割り当てなければ衝突しない**ため、この 3 箇所への例外追記は不要になる(当初案の 2 運用併記を廃した)
- **突合は件数ではなく集合で行う** — 抽出した `<r>` の集合が **`{1..確定ゲート周回}`** と一致するかを検証する(1 周目 P1 — 件数比較だと `反映1周目` を重複させても通ってしまう)
- **`確定ゲート` を含むだけの件名は反映周コミットとみなさない** — 実在の履歴には `確定ゲート通過`(approved 化)・`確定ゲートが5周で収束`(記録)があり、反映コミットと区別できない(1 周目 P1)
- **カウンタと証跡の乖離は機構が警告する**が、**コミットの作成自体は強制しない**(台帳 H-41 の対応案に従う)
- **適用境界は plan frontmatter の明示キー `反映周コミット` で決める**(4 周目 P1・PO 裁定 2026-08-15)
  - 値は **`適用` と `規約制定前` の 2 値**。`docs/development/templates/plan-template.md` が `適用` を持つため、**以後に作られる計画書は自動的に適用対象**になる
  - **既定値を持たない必須キー**とし、**欠落は `未取得(反映周コミット 未記載)` で縮退**する(5 周目 P1)。**`規約制定前` とは区別する** — 欠落を対象外の既定にすると、**手書き・旧計画書のコピー・テンプレ適用漏れによる記入漏れが正常系に紛れ**、カウンタだけ進んでも警告が出ない状態を作る。「削除は差分に現れる」という論拠も**最初からキーを書かなかった新規ファイルには成立しない**
  - **v1.5 以前の計画書 8 件へ `規約制定前` を明示移行する**(確定ゲート 5 周目で実施済み)
  - `適用`・`規約制定前` 以外の値は **`未取得(反映周コミット 不正値)`**
  - **git の履歴から着手時期を機械判定する方式は採らない**(1〜3 周目で採っていたが 4 周目 P1 で廃止)。理由は 2 つ。① 着手時点は Git に痕跡を持たない(`/task-start` は**未コミットの** plan.md を作るだけ)② 確定コミットを定数で持つ方式は**その定数を埋める PR 自身では成立しない**(approved 化コミットはマージ前まで `origin/develop` の祖先にならない)。周回ごとに穴が増えたため方式ごと差し替えた
  - **明示キーを `規約制定前` に書き換えれば回避できる**が、**書き換えは PR の差分に現れる**うえ本機構は警告のみであり、機構で防ぐ対象ではない(祖先関係方式でも `created` の書き換えは防げなかった)。**ただし「書かない」ことによる回避は塞ぐ** — 欠落は縮退表示になる(5 周目 P1)
- **突合の履歴範囲**: **`merge-base(origin/develop, HEAD)..HEAD`**(`feature_status.py:510` の既存定義と同一)
- **判定順序を先勝ちで固定する**(4 周目 P1 — 複数条件が同時成立しうるため、順序を決めないと表示が一意にならない)。上から順に最初に成立したものだけを表示する:
  1. **`plan.md` が HEAD に記録されていない** → **`対象外(計画書 未コミット)`**(`/task-start` 直後。**マージ済みと区別するため最初に判定する** — 4 周目 P1: `base..HEAD` が空という条件だけでは両者を区別できなかった)
  2. **HEAD が `origin/develop` の祖先** → **`対象外(develop へマージ済み)`**
  3. **`反映周コミット` が未記載** → **`未取得(反映周コミット 未記載)`**(記入漏れを対象外に紛れさせない)
  4. **`反映周コミット` が `規約制定前`** → **`対象外(規約制定前)`**
  5. **`反映周コミット` がそれ以外の値** → **`未取得(反映周コミット 不正値)`**
  6. **`確定ゲート周回` が不正値**(非整数・負値・キー重複)→ **`未取得(確定ゲート周回 不正値)`**
  7. いずれにも当たらなければ**突合を実行する**
- **突合結果は段階表示とは別の行に出す**(4 周目 P1)。`FeatureResult` の縮退欄は単一値(`feature_status.py:173`)で、A-3 の `未取得(承認履歴取得失敗)` と同時成立しうるため、**段階表示の縮退欄を奪わない独立行**とする。あわせて **`status: in-review`・`実行方式: fast`・未承認でも表示する** — 段階表示は これらで早期 return する(`feature_status.py:1072`・`:1084`・`:1094`)ので、**その前に評価する**
- **`確定ゲート周回` の不正値は既存経路の改修を伴う**(4 周目 P1)。非整数・負値は現在 `None` になり(`feature_status.py:276`・`:329`)段階表示から無言で省かれる(`:796`)。**キー重複は `Frontmatter` 自体が `None` になり既存の `未取得(frontmatter 解析失敗)` に落ちる**(`:316`・`:1245`)ため、**解析結果に重複の原因を保持する変更**が要る。縮退経路を足すだけでは区別できない
- **`確定ゲート周回` が `0` でも突合する**(3 周目 P1)。**空集合と比較**し、`反映<r>周目` が 1 件でもあれば不一致として警告する。`0` を免除条件にすると**カウンタを更新しないだけで回避できる**

**A-3: 「計画系/文書系のみ → known 0」の例外**

現在の規定は「②③のみ → known k = 0(実装前)」と断定している。次を追記する:

- **ステップ表に N ≥ 1 があり、かつ有効トークンが 0 件のとき**は、known 0 と判定したうえで「**ステップ記法のコミットなし(書式未一致の可能性)**」を**併記**する
- **判定自体は変えない**(承認直後の正常な経路を `実装前` と導出する目的は維持する)。変えるのは**注記の有無**だけである
- **承認直後は注記を出さない**(1 周目 P1 — 当初「区別できないので常時注記」としたが**過大だった**)。`承認` が初めて `済` になったコミット以降に**追加コミットが 0 件**なら、それは承認直後の正常な状態であり注記しない。`feature_status.py` は既に**各コミット時点の frontmatter を読む機構を持つ**(`fs.py:524`・`:541`)ので実装できる
- **承認履歴を取得・解析できないときは縮退する**(2 周目 P2)— 現在の実装は**スナップショットの frontmatter 解析失敗を無視する**(`fs.py:541`)。新しい判定で同じ扱いをすると「承認コミットを特定できない」を通常状態として扱ってしまう。**`未取得(承認履歴取得失敗)` へ縮退**し、そのテストを置く
- **残る副作用を明記する** — 承認後に文書系コミットを重ねたが有効トークンが 0 件、という状態では両者を区別できず注記が出る。ただし**主要な正常時ノイズ(承認直後)は除去される**

### 実装方針(C-5〜C-8)

**再利用**: 既存の `Progress`(`note` フィールドを持つ)・`format_progress`・`violation` 相当の表示系。**新しい表示形式を作らない** — 既存の `不明(理由)` と同じ `種別(理由)` の形に揃える。

  - **ただし承認直後は注記しない**(3 周目 P1 — C-5 が旧仕様のままだった)。`承認` が初めて `済` になったコミット以降に**追加コミットが 0 件**なら出さない
  - **承認履歴を取得・解析できないときは `未取得(承認履歴取得失敗)` へ縮退**する(2 周目 P2)
- **C-6(worktree の無言除外)**: `collect_features` の glob 例外(`fs.py:1237-1241`)とブランチ名不一致(`fs.py:1252-1254`)で `continue` せず、**`未取得(理由)` の結果を 1 行返す**。理由は「docs/features を読めない」「ブランチ名が feature/<slug>・fix/<slug> に一致しない」
- **C-7(`inconsistent` の理由)**: `fs.py:698`・`:709`・`:716`・`:728` の **4 経路すべて**で `Progress.note` を設定し、`format_progress` を `不整合(理由)` へ。**`unknown` 側と扱いを揃える**

- **C-8(H-41 の突合)**: **適用判定を先に行う** — **先勝ち 7 経路**(計画書未コミット / マージ済み / `反映周コミット` 未記載〔縮退〕 / 同 `規約制定前`〔対象外〕 / 同 不正値 / `確定ゲート周回` 不正値 / 突合実行 — 4 周目 P1 + 5 周目 P1)を上から順に評価し、最初に成立したものだけを表示する。**突合結果は段階表示と別行**に出し、`in-review`・`fast`・未承認でも表示する。突合を実行する場合は、`merge-base(origin/develop, HEAD)..HEAD` から A-2 が規定する反映周コミットの **`<r>` を抽出**し、次の **3 条件すべて**を検証する(計画レビュー 2 周目 P1 — 実装方針が件数比較へ戻っていた)。**`確定ゲート周回` が `0` でも空集合と比較する**。**exit code は変えない**(表示専用スクリプト)
  1. **`<r>` の集合が `{1..確定ゲート周回}` と一致**する
  2. **各反映コミットのマーカーはちょうど 1 個**(1 件名に `反映1周目 反映2周目` と複数書けば通ってしまうため)
