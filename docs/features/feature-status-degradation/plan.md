## 4. 実装方針

### 重さ分類 = 通常(根拠)

CLAUDE.md が列挙する**コア領域 5 つ(同期プロトコル / 状況計算 / 記録権 / テナント分離 / データ移行)のいずれにも触れない**。`.claude/core-areas.json` の `areas[].paths` に該当 0 件。

**`guard_paths` にも該当しない** — 同ファイルのトップレベル `guard_paths` は `core-areas.json` / `ci.yml` / `core_guard.py` / `pull_request_template.md` / `pr/SKILL.md` の 5 件で、本タスクはいずれにも触れない。したがって **CI の core-guard は発火しない**。

**ただし設計書の版繰り上げにより `/finalize-doc` の確定ゲート(敵対レビュー + 人間承認)が乗る。** レビュー負荷は「通常」の想定を超えるため、計画レビューにも敵対レビューを適用する。

### 設計書の改訂内容(A-1〜A-3)

**A-1: ステップ検出書式の厳密文法**

現在 `設計書:252` は `(ステップ <k>[/<N>][ 付記])` という表記だけを示している。次を追記する(いずれも実装が既に行っている検査であり、**実装追随の明文化**):

- 開き括弧と閉じ括弧は**同種で一致**すること(`（ステップ 7)` は不整合)
- **`k = 0` は不正**
- `/<N>` を書く場合、**ステップ表の総数 N と一致**すること
- 数値の直後に許される文字を**列挙**する(1 周目 P2 — 「境界文字」では句読点等を含む一般的な単語境界とも読める)。実装が許すのは **`/`(総数の区切り)/ 同種の閉じ括弧 / 空白** の 3 つで、それ以外は不正(`(ステップ 2abc)` は不正)
- **括弧のない文言は不算入**(`docs: ステップ 2 の補足` はステップコミットと見なされない)
- 1 件名に**2 個以上のトークンがあれば不整合**

**A-2: `確定ゲート周回` の反映周コミット規定**

現在の規定(`設計書:272`)は「指摘反映を伴う 1 周ごとに +1」だけで、コミットを要求していない。次を追記する:

- **指摘反映を伴う 1 周ごとに 1 コミットを作る。** 件名に **`反映<r>周目`** を**必ず含める**(`<r>` は 1 始まりの周回番号)
- **ステップ表に番号を割り当てる運用**では、ステップ記法の付記として書く(例 `(ステップ 6 反映3周目)`)
- **番号付きステップを割り当てない運用**では、ステップ記法なしで `反映<r>周目` だけを含める(例 `docs: 確定ゲート 反映3周目 — 指摘 4 件を反映`)
  - **「ステップ外」は実行時期ではなく「番号付きステップを割り当てない場合」と定義する**(1 周目 P1 — 「全ステップ完了後」だと本計画自身のゲートが当てはまらない)
- **突合は件数ではなく集合で行う** — 抽出した `<r>` の集合が **`{1..確定ゲート周回}`** と一致するかを検証する(1 周目 P1 — 件数比較だと `反映1周目` を重複させても通ってしまう)
- **`確定ゲート` を含むだけの件名は反映周コミットとみなさない** — 実在の履歴には `確定ゲート通過`(approved 化)・`確定ゲートが5周で収束`(記録)があり、反映コミットと区別できない(1 周目 P1)
- **カウンタと証跡の乖離は機構が警告する**が、**コミットの作成自体は強制しない**(台帳 H-41 の対応案に従う)
- **適用開始条件**(2 周目 P1・PO 裁定 2026-08-15): **本規定は設計書 v1.5 の確定日以降に着手したタスクにのみ適用する。** 計画書 frontmatter の **`created` が v1.5 の確定日より前の feature には突合を行わない**。規則制定前の行為を違反扱いしないため
  - **実在の 4 前例のうち 3 件が新規則に適合しない**([research.md](research.md) §5)。うち `harness-evaluation` の 1〜5 周集約は**当時 PO が明示的に裁定した逸脱**であり、遡及適用は不当である
  - 判定に使うのは **`base..HEAD` の最初の plan スナップショットの `created`**(3 周目 P1 — **現在値だけで判定すると、着手後に日付を古く書き換えるだけで警告も縮退もなく突合を回避できる**。`/task-start` は初期値を設定するだけで不変性を保証しない)
  - **初回スナップショットの `created` と現在値が食い違う場合は縮退**する(**`未取得(created 不一致)`**)。書き換え自体は止められないが**黙って回避されることは防ぐ**
  - **`created` を読めない / スナップショットを取得できない場合も縮退**する(**`未取得(created 取得失敗)`**)。突合を無言でスキップしない

**A-3: 「計画系/文書系のみ → known 0」の例外**

現在の規定は「②③のみ → known k = 0(実装前)」と断定している。次を追記する:

- **ステップ表に N ≥ 1 があり、かつ有効トークンが 0 件のとき**は、known 0 と判定したうえで「**ステップ記法のコミットなし(書式未一致の可能性)**」を**併記**する
- **判定自体は変えない**(承認直後の正常な経路を `実装前` と導出する目的は維持する)。変えるのは**注記の有無**だけである
- **承認直後は注記を出さない**(1 周目 P1 — 当初「区別できないので常時注記」としたが**過大だった**)。`承認` が初めて `済` になったコミット以降に**追加コミットが 0 件**なら、それは承認直後の正常な状態であり注記しない。`feature_status.py` は既に**各コミット時点の frontmatter を読む機構を持つ**(`fs.py:524`・`:541`)ので実装できる
- **承認履歴を取得・解析できないときは縮退する**(2 周目 P2)— 現在の実装は**スナップショットの frontmatter 解析失敗を無視する**(`fs.py:541`)。新しい判定で同じ扱いをすると「承認コミットを特定できない」を通常状態として扱ってしまう。**`未取得(承認履歴取得失敗)` へ縮退**し、そのテストを置く
- **残る副作用を明記する** — 承認後に文書系コミットを重ねたが有効トークンが 0 件、という状態では両者を区別できず注記が出る。ただし**主要な正常時ノイズ(承認直後)は除去される**

### 実装方針(C-5〜C-8)

**再利用**: 既存の `Progress`(`note` フィールドを持つ)・`format_progress`・`violation` 相当の表示系。**新しい表示形式を作らない** — 既存の `不明(理由)` と同じ `種別(理由)` の形に揃える。

- **C-5(縮退の明示)**: `derive_progress` の known 0 経路(`fs.py:767-769`)で、`table.total >= 1` かつ有効トークン 0 件のとき `Progress.note` を設定する。`format_progress` と段階表示の両方に反映する
  - **ただし承認直後は注記しない**(3 周目 P1 — C-5 が旧仕様のままだった)。`承認` が初めて `済` になったコミット以降に**追加コミットが 0 件**なら出さない
  - **承認履歴を取得・解析できないときは `未取得(承認履歴取得失敗)` へ縮退**する(2 周目 P2)
- **C-6(worktree の無言除外)**: `collect_features` の glob 例外(`fs.py:1237-1241`)とブランチ名不一致(`fs.py:1252-1254`)で `continue` せず、**`未取得(理由)` の結果を 1 行返す**。理由は「docs/features を読めない」「ブランチ名が feature/<slug>・fix/<slug> に一致しない」
- **C-7(`inconsistent` の理由)**: `fs.py:698`・`:709`・`:716`・`:728` の **4 経路すべて**で `Progress.note` を設定し、`format_progress` を `不整合(理由)` へ。**`unknown` 側と扱いを揃える**
  - 4 経路の内訳: ① **ステップ表が不正**(表なし / 番号の欠番・重複 / 空セル)② **不正形トークン or 1 件名に 2 トークン** ③ **`k > N`** ④ **完了集合の欠番**
  - **① は `StepTable` が現在 理由を保持していない**ため、**`StepTable` 側にも理由フィールドを足す実装変更が要る**(1 周目 P1)
- **C-8(H-41 の突合)**: **適用判定を先に行う** — `base..HEAD` の最初の plan スナップショットの `created` を読み、**① 読めない/取得失敗 → `未取得(created 取得失敗)` で縮退** **② 現在値と食い違う → `未取得(created 不一致)` で縮退** **③ v1.5 の確定日より前 → 突合をスキップ**(縮退ではなく対象外)。適用対象かつ `確定ゲート周回 > 0` のとき、`base..HEAD` から A-2 が規定する反映周コミットの **`<r>` を抽出**し、次の **3 条件すべて**を検証する(2 周目 P1 — 実装方針が件数比較へ戻っていた)。**exit code は変えない**(表示専用スクリプト)
  1. **`<r>` の集合が `{1..確定ゲート周回}` と一致**する
  2. **各反映コミットのマーカーはちょうど 1 個**(1 件名に `反映1周目 反映2周目` と複数書けば通ってしまうため)
  3. **各 `r` の出現コミット数は 1**(同じ周を複数コミットに分けたものを通さない)
  - **件数比較にしてはならない** — 実在の `req-v1-9-nfr021-wsl2` はカウンタ 12・完全形マーカーも 12 件だが**番号は 1〜4 が各 2 件で集合は `{1..8}`**。件数比較だと誤って通る
