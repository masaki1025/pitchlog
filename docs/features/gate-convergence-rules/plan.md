## 4. 実装方針

**重さ分類 = 通常の根拠**: コア領域 5 領域(同期プロトコル・状況計算・記録権・テナント分離・データ移行)のプロダクト実装・設計内容に触れない(文書の手続き節・スキル手順・PR テンプレ・guard_paths 登録のみ)。ただし guard_paths 該当ファイルに触れるため、6.3 の「検査経路の変更」として **PR に人間の逐行確認チェックが必要**(core-guard が機械強制)。実装は文書改訂のため設計書 3 章の役割分担どおり Claude が直接編集し(Codex への実装委任なし)、レビューはラッパー経由(計画 = review normal / 確定ゲート = review adversarial)。

**前提作業(コミットしない)**: origin/develop が本計画の起票後に進んでいる(24adeb2 → PR #33 ほか。設計書 10.1 の節更新を含むが 7.3/6.3 とは非衝突 — 実測済み)。**ステップ 1 着手前に worktree ブランチを最新 origin/develop へ rebase する**。

**新規則の自己適用の扱い**: v1.12 の確定ゲートは v1.12 承認前に走るため、新規則をそのまま適用すると循環する(レビュー 1 周目 P1)。恒久の解決は **D-5a 適用版の原則**(その時点で approved の 7.3 規則を適用 — 7.3 条文へ条文化)で、本ゲートはこれにより**現行 7.3(収束するまで反復)で運用**される。あわせて**本タスク限りのシャドー観測(D-5b — 正本・スキルへは書かない)**として、各周で「新規則ならどう判定されたか」を D-5b の固定様式で worklog に並記記録し、v1.12 の実効性の初期データとする。

**機構強制しないことの残余リスク(レビュー 1 周目 P1 への回答)**: B2 記録行・判定行・6 周警告・2 周連続過半検知は core_guard 等で検証されないため、**記録や判定行が欠けていても CI は green になる**。これを許容する理由: (1) 逐行確認チェック自体(canonical 行)の機械強制は従来どおり維持される、(2) ゲート中に機構を足すことが収束を壊す実測(research.md §4 パターン i)があり、まず運用で規則の形を安定させる、(3) 機構化の要否は運用実績 3 ゲート分を台帳で評価してから別タスクで判断する(申し送り)。この残余リスクは 7.3 v1.12 の本文にも明記する。
