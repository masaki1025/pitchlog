# 調査メモ: U-F8 試合記録・再開・修正(TSK-523)

## 問い

5 画面・16,000 行強を製品へ作り直すにあたり、**何をどこまで作るのか**(範囲)、**どう分けるのか**(PR 分割)、**何を他単位から受け取るのか**(境界)を決めるための材料を集める。

## 結論(要約)

1. **旧実装はクライアントで状況計算をしていない。** サーバーが計算し、画面は応答の `state` で置き換えるだけ(`screens/GameScreen.tsx:1239` ほか 10 箇所)。クライアント計算は楽観カウント(`:1188-1196`)と修正中の得点警告(`:2267-2269`)の 2 つだけ。**要件書 4.0-4 が求める「断中のクライアント計算」は、新システムで初めて作るものである。**
2. **U-F8 は計算を持てない。** `ADR-003` D-14(D-2 方式)は決定済み・**未発効**で、PO 裁定は「発効前は実行基盤まで、対象計算の追加は発効後」。一方 **U-X1 の第 1 PR の着手条件 P-7 は「U-F8 の 1 球確定の入口が実在すること」**で、状態は「U-F8 は未計画」。**相互に待つ形になっている。**
3. **PR 分割は本単位の計画書が決める。** 「`GameScreen` は単独タスク」は PO 裁定ではなく申し送りの一文で、根拠は行数のみ。しかも古いコミット(`0423851`・1,423 行)で測った値。
4. **カードの範囲記述は 3 点で実態とずれる。** `api/liveInput.ts` は 8 行の GET で確定経路に関与しない / FR 列挙が帰属の正(`design.md` 6.3)より狭い / 再開処理は `ScoreCardScreen` にもある。
5. **「4 区分」は正本に無い。** 正本にあるのは同期プロトコル 6-3 の境界結果 `B1`〜`B7` と P3 の `B8`〜`B14`。4 区分を B へ写す作業が計画の範囲になる。
