### 4-1'. 確定の経路と順序(**P0 是正・2026-10-16**)

**確定先は E-1 `POST /games/{game_id}/sync/events`**(`docs/features/sync-wire-schema/design.md:163`)。旧経路 `POST /games/{id}/plays` ではない。要求本文は `recording_right_proof` と `events[]`(`d5`・`d1`・`d4`・`game_id`・`event_kind`・`d2`・`payload`・`state_diff`)(`:173`)。**1 要求は単一の `(試合, D4)` に限る**(正本 6-2)。

**1 球の記録は P2 経路**(D2 の採番を伴う。master の訂正・2026-10-16)。経路の判定はクライアントが選ばず、正本 8-1 の経路表と 6-2 に従う。

**順序は次のとおり。当初の設計(送信 → 失敗したらキューへ)は受理境界を壊すので採らない。**

```
1. 単一書き手の排他を取る(runAsSingleWriter — singleWriter.ts:106)
2. D1 を採番し、端末の永続キューへ不可分に追記する
3. 【追記が成立した時点で「操作の受理」】 ← 要件書 :329 の E0・sync-protocol.md:1095 の Q1
4. 画面に受理を表示する
5. E-1 へ送る
6. ACK を parseAckBoundaryResult で分類し、A5 と拒否理由を【既存スロットへ適用】する
```

**`B3`(恒久的な内容拒否)は「送信が失敗したこと」ではなく「拒否を含む ACK が返ったこと」である**(`sync-protocol.md:764`)。`queueTransition.ts:127, 478` が、既存スロットに対応する A5 拒否と B3 分類を受けて `要操作` へ遷移させる。**ACK が返らない場合は `未送信` のままで、自動再送の対象。**

**`NFR-007`/`E4` の「追記不成立を受理成功として見せない」は、この順序でしか満たせない。**

### 4-2. 「4 区分」と境界結果の対応(**本計画では決めない**)

master から渡された 4 区分(前提違反 / 内容拒否 / 一時的 DB 障害 / 結果未確認)は**正本に無い**([research.md 5](./research.md))。正本は `B1`〜`B7`(`sync-protocol.md:688-702`)と `B8`〜`B14`(`:785-794`)。

**U-F8 は `B` 区分で受け取る。** 4 区分を `B` へ写すのは U-F7・U-S1・TSK-506 の仕事。画面は `boundaryResults.ts` が返す型だけを見る。

**恒久エラーを無限再送しないこと**(山田さんの指示)は、**`B3`(恒久的な内容拒否)で「未送信 → 要操作」へ落ち、自動再送の対象から外れる**という正本の規定(`sync-protocol.md:760-768`)で満たされる。U-F8 は `要操作` を画面に出す責務を負う。

| **(i)** | **待機中の非所有タブの確定が、ロックの解放後に実行される** —— Web Locks の既定はブロッキングで、前の書き手が解放した瞬間に追記・送信される。資産は `appendCount: 0` / `d1.consumed: false` を要求する | 要件書 `:332` の `E2`・`sync-protocol.md:1690`・`waiting-input-not-accepted_v2.json` | **U-F8 の射程内。是正済み** |

| **(iii)** | **排他の保持単位が「1 球ごと」で、資産が前提とする「セッション保持」と食い違う** —— 資産の `input.lock` は `heldDuringFreeze: true`。後からセッション保持を入れると、その内側の確定が同名ロックを再取得して待ち続ける(Web Locks は再入不可) | `sync-protocol.md:1689`・`leader-freeze-reelection_v2.json` | **設計判断。封鎖解除の前提条件として残す** |

**封鎖を外す前に、(iii) を決めること。** (i)(ii) は是正したが、**是正の中身は「待たない管理機構を既定にする」ことなので、確定の経路を画面へ繋ぐときに既定が上書きされていないかを必ず確かめる。**

### (i)(ii) の是正 —— `lib/sync` を変えずに解けた

**当初これらを「`singleWriter.ts` の変更が要るので U-F7 の所有」として申し送ったが、誤りだった。** `runAsSingleWriter` は `lockManager` を**公開の注入点**として持ち、鍵が取れないときにコールバックが `null` を受けると**追記せずに** `LOCK_REQUEST_FAILED` で戻る。したがって `ifAvailable: true` を使う管理機構を呼出側から渡せば、**`lib/sync` の差分 0 行のまま**契約を満たせる。

実装は [`GameScreenSingleWriter.ts`](../../../frontend/src/screens/GameScreenSingleWriter.ts)。`createNonBlockingLockManager` が待たない管理機構を作り、`describeNonOwnerInput` が `LOCK_REQUEST_FAILED` を `rejectNonOwnerInput()`(`Q2-b`)へ写す。`commitPitchEvent` の結果に `nonOwner` として載る。

**実体を作るだけでは足りない。** `runAsSingleWriter` は `lockManager` を省略するとブラウザ既定(ブロッキング)を使うので、呼出元が渡し忘れると契約が破れる。**`withNonBlockingSingleWriter` が既定を機構として固定**し、`commitPitchEvent` と `acceptPitchEvent` の両方がこれを通す。契約資産 `waiting-input-not-accepted_v2.json` の期待(追記 0 件・D1 を消費しない・`Q2-b`)は `GameScreenSingleWriter.spec.ts` が固定している。

**一度、実体だけ作って接続せずに「是正済み」と書き、封鎖解除の歯止めを外しかけた。** 新しい既定を入れるときは、**既定が実際に通る経路を試験で押さえてから**是正と呼ぶこと。

**所有の割り当てを誤ったまま文書とコードへ固定しかけた。** 注入点の有無を確かめずに「ライブラリの変更が要る」と判断したのが原因で、同種の判断では**まず公開 API の注入点を探す**こと。

### (iii) が残る理由

**排他を「1 球ごと」に取るか「記録セッションとして保持」するかは、U-F7 の再送規則と U-F8 の画面の寿命の両方に掛かる設計判断である。** セッション保持へ寄せる場合、確定の経路は「排他を取る版」と「排他の中で動く版」に割る必要がある(`appendPitchEventUnderLock` と同じ分け方)。**第 1 期は確定を塞いでいるので決めない。** 封鎖を外す PR で決めること。

## 7. 試験の方針

| 種別 | 第 1 期 | 第 2 期 |
| --- | --- | --- |
| 単体(Vitest) | 入力の組み立て・キューへの受け渡し・表示の導出 | — |
