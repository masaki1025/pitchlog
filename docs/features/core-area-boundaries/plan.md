## 4. 実装方針

- **重さ分類 = 通常** の根拠: 全変更が文書とハーネス設定(JSON への文言追加)であり、コア領域の実装コードは存在せず触れない。機械的複写ではない(境界文言の起案は判断を伴う)。
- **コア領域判定**: 実装コードには触れない。ただし **guard_paths の `.claude/core-areas.json` に触れる** — CI の core-guard が発火し、PR 本文に必須チェック文言(`scripts/core_guard.py` の REQUIRED_CHECK_TEXT と完全一致)の `- [x]` が要る。**本タスクが初の発火ケース**になる見込み(/pr で対応)。
- **実行主体**: 全ステップ文書・設定変更のため Claude が直接編集・コミット(役割分担 — 設計書 3 章)。品質は本計画書のレビュー(review normal)+ **確定ゲートの敵対レビュー(review adversarial・sol xhigh — /finalize-doc が自動適用)** + /pr レビューで担保。
- **ゲート判定**: 設計書は版繰り上げ = **finalize-doc 必須**(6.3 の境界定義は強化レビューの適用範囲を定める構造的変更 — 7.6-3 後段)。台帳・索引・ハーネス設定は節更新・追随(7.6-3 前段)。
- **6.3 の書き方**(ステップ 2 の起案方針 — 詳細文言は確定ゲートで磨く): 領域ごとに「含む」「含めない(理由と代替統制)」の両側を書く表形式。要件の定義(4.0-4・FR-012 等)は**参照**し内容を複製しない(7.1-1)。paths 充填(Phase 4)は「本定義への当てはめ」と位置づけ、H-12 の承認手続の残余を注記する。
- **core-areas.json の互換性**: `description` キーの追加が core_guard・ハーネステストのスキーマ検証と互換であることをステップ 3 の pytest で確認する(非互換ならテスト側の修正は行わず、キー名・置き場を変える方向で回避 — コード変更をスコープに入れない)。
- **反映周コミット**: 確定ゲートの指摘反映は 1 周 = 1 コミット・件名に `反映<r>周目`・ステップ記法なし(設計書 6.1 — frontmatter `反映周コミット: 適用`)。
- design.md は**作成しない**(境界文言は 6.3 本文そのものが成果物であり、方針は本節と worklog 決定節で足りる)。
