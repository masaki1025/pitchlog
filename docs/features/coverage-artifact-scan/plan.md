## 4. 実装方針

### 重さ分類 = コア領域(根拠)

**`backend/tests/db/test_authz_table_privileges.py` が `.claude/core-areas.json` の
`tenant-isolation.paths` に該当する**(実測 — `areas=['tenant-isolation']`)。
**したがって設計書 6.3 により sol xhigh・敵対レビュー必須・人間の逐行確認必須**(**確認者は PR 作成者以外**)。

**意味範囲としてはテナント分離の判定そのものではない**(文言走査は表権限の記述を見る検査)。
**しかし 6.3 の paths は完全一致・`fnmatch` で機械判定されるので、
「意味的には軽い」という理由で軽く扱わない**(**`H-12` の型 = paths 該当と意味範囲の乖離**)。
**core-guard は発火する**ので PR 本文のチェックも必要になる。

`.gitignore` と `tests/**` と `backend/.coverage` は **areas・guard_paths のいずれにも該当しない**(実測)。

### 設計判断 1: 追跡の解除は「削除」ではない

**`git rm --cached` は index からの除去で、worktree のファイルは残る。**
**要件書 4.0-2 の「物理削除しない」は業務データの論理削除の規律であり、
生成物の追跡解除とは無関係**である(念のため明記する — 敵対レビューで論点になり得るため)。

**`.coverage` は追跡解除後、`.gitignore` により `git status` に現れない。**

### 設計判断 2: 母集団の絞り方(**「広く取る」と「原則で絞る」の向き**)

**PR #53 で確立した形は「候補は広く取り、同一性は厳格に主張する」だった**が、
**本件は逆向きである** — **走査は「読んで内容を検査する」ので、読めないものを母集団に入れてはならない。**

**したがって次の 2 段にする**:

1. **母集団を原則で絞る** — **「テキストの成果物」であることを条件にする**
   (拡張子の allowlist ではなく、**追跡状態 + テキストであることの判定**を推奨する。
   **allowlist は人が列挙する母集団になり、台帳候補の型を踏む**)
2. **絞った母集団の中で読めなかったパスは、黙って飛ばさず明示的に扱う** —
   **「読めなかった」ことを違反として報告する**か、**理由付きで除外集合に入れる**

**どちらを採るかは実装判断に委ねるが、次を満たすこと**:

- **`.coverage` のような生成物が母集団に入らない**
- **母集団に入ったのに読めないパスがあったとき、黙って通らない**
- **人が拡張子やパスを列挙する形を新たに作らない**

### 設計判断 3: 恒久検査の置き場所

**`tests/test_repository_artifacts.py`(新設・ルート)** に置く。理由:

- **ルート `tests/` は `harness` ジョブが `uv run pytest -c pyproject.toml tests/` で回す**(`ci.yml:88`)。
  **DB を要さないので、DB 不通の環境でも検査が生きる**
- **`backend/tests/` に置くと `backend` ジョブだけの検査になり、`--cov` 経路に依存する**
- **`test_ci_wiring.py` には入れない** — 同ファイルの射程は CI の配線で、**リポジトリの内容ではない**

**検査内容**: **追跡済みファイルに、`.gitignore` が無視すると宣言しているものが含まれないこと。**

**生成物の条件は `.gitignore` を単一の正本とし、その解釈は git 自身に行わせる**(計画レビュー 1 周目 `P1-4` の是正 —**当初『`.gitignore` 導出か独自条件か』を実装判断へ委ねたが、それでは `.coverage` を名指しして負例 1 件だけを通す実装が排除できない**):

- **母集団** = `git ls-files`(**追跡済み全件**。件数を定数で持たない)
- **述語** = **git 自身の ignore 判定**。ただし次の 2 点を固定する(2 周目 `P1-2` の是正 — **当初「`git check-ignore` 相当」としか書かず、意味が一意でなかった**):
  - **追跡済みでも「未追跡と見なして」判定する** — **`--no-index` 相当が必須**。
    **実測**: 追跡済みの `backend/.coverage` に対し `git check-ignore -v` は **rc=1・出力なし**(`.gitignore` に `.coverage` を足しても同じ)。**`--no-index` を付けると rc=0 で `.gitignore:29:.coverage` を返す**。
    **したがって通常形で書くと、この検査は追跡済みファイルを永久に検出できず空洞になる。**
  - **権威は「リポジトリが管理する `.gitignore`」に限る** — **`.git/info/exclude` と `core.excludesFile` は権威にしない**(**開発者ごとのローカル設定で判定が変わってはならない**)。**`-v` の出力は `<出典>:<行>:<パターン>` を返すので、出典が追跡済みの `.gitignore` であることを要求できる**
- **検査コード側でパターンを解釈しない・拡張子や名前を列挙しない**
- **検査は `.coverage` を名指ししない**

- **評価環境を固定する**(3 周目 `P1-1` の是正 — **出力の事後選別だけではローカル設定の影響を排除できない**。**未追跡の下位 `.gitignore` の否定パターンが追跡済み `.gitignore` の一致を覆すため、`-v` の出典名を見るだけの実装では防げない**):
  - **index の内容を展開した一時リポジトリで評価する**(**`git checkout-index -a --prefix=<tmp>/` 相当** → **そこに存在する `.gitignore` は index にあるものだけ**・**`.git/info/exclude` は空**)
    **`HEAD` から取り出してはならない**(4 周目 `P1-1` の是正 — **母集団は index(`git ls-files`)なのに述語を `HEAD` で評価すると時点が混ざり、staged された `.gitignore` の追加・変更が述語へ反映されず、同時に staged された生成物を見逃す**。**まさに本タスクのステップ 1 のコミット前がその場面である**)
  - **`core.excludesFile` を無効化して実行する**(`-c core.excludesFile=/dev/null` 相当)
  - **母集団(追跡済み全件)は実リポジトリの `git ls-files` から取り、述語の評価だけを一時リポジトリで行う**

**この形なら `.gitignore` へ新しいパターンを足すだけで検査が追随し、ローカル設定は結果に影響しない**(**二重管理も、環境差も構造的に起きない**)。**負例でそれを固定する。**

### 設計判断 4: 検証は CI と同一コマンドで行う

**本欠陥は `--cov` の有無で分岐する。** したがって
