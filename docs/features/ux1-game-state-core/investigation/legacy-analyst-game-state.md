## TSK-405 調査報告: 旧システムの状況判定は宣言モデル(DSL)で書けるか

### 結論
- 旧システムの状況計算核(`update_list`)は**手続き型の単一関数**でした。ただし**ループなし・if の入れ子は最大 3 段・参照するのは直前 1 行だけ**です。

- 「表で書けない形」は旧システムに実在します。ただし核の外側にあります。逐次上書き、状態に応じたイベントの書き換え(UI 層にある)、全履歴の集計、最近傍推定、反実仮想(新しい旧版のみ)、プレイ内の順序情報の欠落の 6 点です(2 章末)。

### 1. 状況判定の実装の形(確認済みの事実)

**処理の流れ**: サジェスト → 人間の上書き → 確定 → スコアボード加算 → `update_list` の順です(`domain-logic.md:105-118`、`input-screen.md:137`)。

| 部品 | 形 | 入れ子の深さ(旧コード) |
|---|---|---|
| `update_list`(`domain/game_state.py:148-425`) | 手続き型。ローカル変数の逐次代入で、ループなし | **最大 3 段**(`:208→216→219`、`:246→256→257`、`:322→327→328`) |
| `suggest_runner_states`(`domain/runner_advancement.py:71-243`) | **上から先勝ちの決定リスト**(14 規則 + 既定値)。規則ごとに、塁の占有の述語から状況ラベルを決める | 最大 3 段(`:195→197→199`、try を含む) |
| `should_finish_game`(`domain/game_end_rules.py:12-50`) | 早期 return の決定リスト | 2 段(`:44-48`) |
| `scoring_rules`(`domain/scoring_rules.py:40-97`) | **警告のみ**で状態は変えない | 1〜2 段 |
| `apply_scoreboard_event`(`domain/scoreboard.py:38-85`) | 加減算。`direction=±1` で確定と取消を兼用 | 1 段 |
| カウントの自動昇格 `_resolve_continue_batting_result` | **UI 層**にある(`app/pages/game_input_helpers.py:41-51`) | 2 段 |
| 打席の継続/完了の決定 | **UI 層**にある(`app/pages/game_input.py:1149-1152`) | 1 段 |

**履歴への依存**
- `update_list` が読むのは「直前 1 行 + 両軍の出場選手配列 + スコア配列」だけです(`game_state.py:148`)。試合再開も最終行から導出します(`services-shell.md:126`)。
- 履歴は状態の列に折り畳まれています。例は、チーム別の打順ポインタ「先攻打順」「後攻打順」(`game_state.py:184-185, 351-352, 360`)と累積スコア配列です。
- 直前 1 行では足りない箇所が 4 つあります。
  - **球数**: 全履歴を集計した結果から `stats[24]+1` で得ていました(`game_input.py:403-404`)。`update_list` は 0 に戻します(`game_state.py:410`)。
  - **取消(undo)**: 逆演算で戻しますが、完全な逆写像ではありません。0 点が `""`(未消化)に戻ってしまいます(`scoreboard.py:35`、`domain-logic.md:177`)。
  - **UI の上書き保持**: 入力シグネチャを比較して、人間の上書きを保持していました(`input-screen.md:169, 191`、`services-shell.md:86`)。
  - **状況変更・タイブレーク**: メモリ上の現在状態行(data_list)だけを変え、DB には書きません(`services-shell.md:158, 206`)。
    - 推論: このため、保存済みの行を前の行からの `update_list` で再現できない区間ができるはずです。

補足(事実):

- 併殺打とライナー併殺: 別の入力欄である打球タイプにも G や L を書き込む(`:155-174`)。
- 捕手牽制: 「1塁牽制」という表記で `牽制の種類` を上書きする(`input-screen.md:57, 273`)。サジェストは「一塁牽制」しか一致判定しない(`runner_advancement.py:119`)。推論: 捕手牽制のアウトは自動サジェストされません。

**「表で書けない形」の実例(推論による整理)**
1. 順序に依存する逐次上書き(`game_state.py:268-298`)
2. 状態に応じたイベントの書き換え(UI 層。`helpers:41-51`)
3. 全履歴の集計に依存する値(球数。`game_input.py:404`)
4. 最近傍の argmin(`helpers:85-88`)
5. 反実仮想(自責点。dd03160 のみ)
6. プレイ内の順序情報がないため決まらない判定(タイムプレー・サヨナラ)

一方、`update_list`・サジェスト・終了判定の本体は、平坦な有限の決定表に落とせる形でした。
