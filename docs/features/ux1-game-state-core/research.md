# 調査メモ: U-X1(状況計算核)を宣言モデルで書けるか — ADR-003 見直しトリガー 1 への反例集

## 問い

**`ADR-003` の見直しトリガー 1**(`../domain-calc-dsl/design.md:1497`)の発火条件は逐語で
「**履歴スタック・規則配列・語彙 snapshot map・スコアボード全欄・`NumericValue` / `DisplayAtom` の型語彙で
表現できない**」構成が「**反例が 1 件でも成立**」すること。

**本調査の問いは 1 つ** — **`U-X1` が主所有する 13 の FR のうち、現行の宣言モデルで書けないものがあるか。**

本書は実装計画の下調べではない。**トリガー 1 の裁定(非発火・2026-09-19)を再評価するための反例集**である。

## 結論(要約)

1. **反例の候補が 6 件ある。** 現行 schema に**条件分岐・論理演算・履歴の読み出し・出力値の導出式**を
   書く場所が無いことは実測で確定している(§3)。**ただし各候補が「DSL で表現不能」と確定したかは
   本書では判定していない** — 判定は計画書のステップ 2 で、候補ごとに行う(**2 周目 `P1-2` の是正**。
   初稿は「反例は成立する」「少なくとも 6 件が受け皿を持たない」と断定していた)。
2. **それ以前に、宣言の `rules` / `outputs` から実行コードを生成する経路が存在しない。**
   中間表現に入るのは `displayRules` だけで、3 言語 backend は宣言を読まない固定スタブである。
3. **これは `TSK-235`(PR #74)の欠陥ではない。** 同タスクの射程は `ADR-003` 段階 1 の②(検査基盤)であり、
   生成は段階 2 に属する。**ただし段階 2 の生成経路を所有するタスクは現時点で存在しない。**
4. **トリガー 1 の裁定は合成 DSL fixture に対して行われており、実 FR で検証されていない。**
   裁定自身が限界を記録している(「**置き場がある**」までで「**書き切れる**」ではない)。
5. **この再浮上は予告されていた** — `../domain-calc-dsl/design.md:1863-1881` の PO 裁定(2026-09-18)が
   「**`U-X1`(状況計算核)が結果表示名を実装する時点で必ず再浮上する**」と明記している
   (**ただし同節はトリガー 2 についてのもの** — §6 を参照)。
6. **候補の行き先は `ADR-003` の見直しトリガー第 1 項**(「DSL の射程で表せないドメイン計算が現れたとき」)。
   **`TSK-235` のトリガー 1 は無関係であり、同 PR を停止させる話ではない**(§5 の再是正)。

### 3. 反例 — 現行 schema に書く場所が無いもの

**測定対象**: `origin/feature/domain-calc-dsl` の `backend/domain/model.schema.json`(`$defs` 35 件)。
**測り方**: schema を JSON として読み、`$defs` の `required` / `properties` / `additionalProperties` を機械で列挙した。
以下はすべて 2026-10-03 の実測である。

#### 反例 1 — 条件分岐そのものが書けない

| 事実 | 実測 |
| --- | --- |
| `Expression` の分岐は **8 種** | `NumericLiteralExpression` / `BooleanLiteralExpression` / `EnumLiteralExpression` / `ReferenceExpression` / `ArithmeticExpression` / `ComparisonExpression` / `ExtremumExpression` / `RoundingExpression`(**`$defs` 上の名前をそのまま書く** — 略称では grep で引けない) |
| **条件ノード(if / case / 三項)が無い** | 上記 8 種に該当なし |
| **同一イベントに遷移を 2 本書くと拒否される** | `backend/src/pitchlog/domaingen/pregen_checks.py` — `count > 1` で逐語「**複数の遷移が成立し決定的でない**」 |

→ **「ガードで分ける」ことはできるが、「同じイベントで状況により別の結果へ行く」ことが表現できない。**
FR-003(打撃結果による状況の自動更新)・FR-005(スコア・アウト・イニング)は本質的にこの形である。

#### 反例 2 — 論理演算(AND / OR / NOT)が書けない

| 事実 | 実測 |
| --- | --- |
| `GuardRule.required = ['kind','ruleId','expression']`・`additionalProperties: false` | schema |
| **`GuardRule.expression` は `ComparisonExpression` に固定**(`Expression` ではない) | schema |
| `ComparisonExpression.operator` は **6 比較のみ**(`equal` / `not-equal` / `less-than` / `less-than-or-equal` / `greater-than` / `greater-than-or-equal`) | schema |
| `TransitionRule.guardRefs` は配列だが、**連言か選言かを定めたコードが無い** | `git grep guardRefs -- backend/src` が **0 件** |

→ **1 ガード = 1 比較。** 複合条件は `guardRefs` の配列に託されているが、**その配列をどう結合するかを読む実装が存在しない。**

#### 反例 3 — 出力値の導出式を書く場所が無い

| 事実 | 実測 |
| --- | --- |
| `OutputField.required` = `fieldId` / `type` / `nullable` / `range` / `unit` / `scale` / `visibility` の **7 キー** | schema |
| `additionalProperties: false` | schema |
| **`expression` も `derivedFrom` も無い** | 上記 7 キーに該当なし |

→ **出力の「型・範囲・単位」は宣言できるが、「値がどう決まるか」を宣言する場所が無い。**
FR-020〜023(スコアボード・投手成績・打者成績・球種分布)はいずれも導出値の表示である。

#### 反例 4 — `HistoryStack` を持てるが読めない

| 事実 | 実測 |
| --- | --- |
| `FieldType` の分岐に `HistoryStackType` が**ある** | schema |
| `ReferenceExpression` は `kind` + **`fieldRef` 1 個のみ**・`additionalProperties: false` | schema |
| **添字・長さ・pop に相当する式が無い** | `Expression` 8 種に該当なし |

→ **履歴を「置く」ことはできるが「読む」ことができない。**
**FR-006(undo)は履歴の最上位要素を読んで差分を戻す操作であり、書けない。**

#### 反例 5 — 最小・最大が「どれか」を返せない

| 事実 | 実測 |
| --- | --- |
| `ExtremumExpression.operator` は `min` / `max` のみ | schema |
| `operands` は `Expression` の配列で、**返るのは値** | schema |

→ **argmin / argmax(= 最小値を与えた候補の識別)が表現できない。**

> ### ⚠ 【2026-10-03 是正】**この候補は要件と突き合わせていない**
>
> 初稿は「`FR-004` の捕球選手推定は『座標に最も近い守備位置はどれか』であり argmin が要る」と書いた。
> **これは旧システムの挙動(legacy-analyst の報告・当方未確認)から立てた推定であり、要件を読んでいない。**
>
> **要件 付録B-6 第 6 項**(`../../requirements/requirements-pitchlog-2026-07-22.md:1208`・逐語):
>
> > **フィールド領域のシード**: 捕球選手の自動推定(`FR-004`)と打球方向バケット(A-3)に使う
> > 守備位置領域・方向区分は、**座標多角形のシードデータ**としてリポジトリに収載する
> > (**境界線上の点の帰属は「先に定義された領域が優先」**)
>
> **要件が定めているのは「点がどの多角形領域に入るか」(順序つきの優先規則つき)であって、
> 距離の argmin ではない。** したがって**本候補は「要件に不要」に落ちる可能性が高い。**
> **判定は計画書のステップ 2〜3 で行う。**
>
> **ただし 5a を「要件に不要」としても、要件が求める推定は残る**(**計画レビュー 4 周目 `P1-1`**)。
> `FR-004`(`../../requirements/requirements-pitchlog-2026-07-22.md:224`)は
> 「**座標からの自動推定**・推定領域は付録B-6 のシードデータ・**ドメインロジック単一実装 NFR-018**」を要求し、
> **`NFR-019`(同 `:930`)は「捕球選手推定＝打球位置座標→守備番号(付録B-6)」を独立した対象計算として挙げている。**
>
> **→ 候補 5b(多角形領域への帰属判定 + 境界の優先規則)を新たな候補とする。**
> 「点がどの多角形に入るか」を **8 種の `Expression` と現行の入力型(配列型は `HistoryStack` のみ)**で
> 書けるかは**未確認**である。
>
> **`ADR-003` D-6 が付録B-6 領域シードを②参照データ契約に分類している点**が 5b の判定に効く可能性がある
> (対象計算の生成物とは扱いが異なりうる)。**これも未確認。**
>
> **本件は計画レビュー 3 周目(gpt-6-sol xhigh)が `P1` として指摘した。**

#### 反例 6 — 集計の初期値が定数に固定されている

| 事実 | 実測 |
| --- | --- |
| `ReducerRule.required` = `kind` / `ruleId` / `sourceRef` / `maximumItems` / `initial` / `expression` | schema |
| **`initial` は `NumericValue` 1 個**(状態参照ではない) | schema |

→ 状態に依存した初期値を持つ畳み込みが書けない。

#### 演算子の全量(参考)

| 種別 | 全量 |
| --- | --- |
| 算術 | `add` / `subtract` / `multiply` / `divide`(**剰余なし**) |
| 比較 | 6 種(上記) |
| 極値 | `min` / `max` |

**`ADR-003` D-1 の射程行**(`../../adr/ADR-003-domain-calc-method.md`)が挙げるのは
「状態 / イベント / ガード / 次状態 / 整数・boolean・enum / 四則・比較・min・max / 明示的な丸め / 有限の reducer」であり、
**論理演算・条件式・ループ・関数呼び出しは一覧に無い。** schema は条文に忠実である。
**つまり不足は実装の漏れではなく、条文が定めた射程そのものにある。**

### 4. より深い発見 — 生成経路が存在しない

**反例 1〜6 は「宣言に書けるか」の話だが、その前段が成立していない。**

| 事実 | 実測(`origin/feature/domain-calc-dsl`) |
| --- | --- |
| `domaingen/core.py` が中間表現へ入れるのは **`displayRules` のみ** | `rules` / `states` / `events` / `outputs` が中間表現に現れない |
| `backends/python.py` は **48 行**で、`rules` / `outputs` / `expression` の語が **0 件** | 固定の `_pitchlog_generated` スタブを出力するだけ |
| `backends/typescript.py` も同様に **0 件** | 同上 |
| `backends/sql.py` は `COALESCE(SUM(:pitchlog_value), 0)` の**固定文字列** | 宣言を読んでいない |
| `backend/domain/model.json` / `manifest.json` は**存在しない** | 本物の宣言が 0 件 |

**これは `TSK-235` の欠陥ではない。** 同計画書の「やらないこと」が逐語で
**「対象別の DSL 正本・製品生成物を作らない」=「`ADR-003` 段階 2」** と宣言している(`../domain-calc-dsl/plan.md:136`)。

**`TSK-235` が完了しても状況は変わらない。** ブランチ先端は **ステップ 52/57** で、
残るステップ 53〜57 は **CI ジョブ配線 / 依存と lock / 発効の文書同期 / `core-guard` 基線 / `core-areas.json` 登録**であり、
**計算コードの生成を作るステップは 1 つも無い**(同 `plan.md` のステップ表)。

**→ 段階 2 の生成経路を所有するタスクは、現時点で存在しない。**(2026-10-03 時点の実測。
`TSK-236`〜`239` はベクタ契約であって生成器ではない。)

> **記録した限界**: ①**表現できる形が用意されたことは示せたが、実際に全項目を書き切ったわけではない**

#### 【2026-10-03 是正】**ステップ 30 での再評価は実施されていた**

**初稿は「再評価されたか確定できない」と書いたが、これは誤りである。** `../domain-calc-dsl/design.md:1532-1544` に
PO 裁定が明記されている(逐語):

> **◎ 期限到達時の再評価(PO・2026-09-19・ステップ 30 完了時点)— 非発火で確定。**
> **延ばした理由だった実証が出た。** 合成 DSL で**全区分の宣言モデルを実際に書き、
> 生成前検査から formatter まで通した**。5 項目すべてが**表現できた** …… **反例 0 件。**
> **上の限界①は解消した**(書き切れることを実測した)。

**誤りの原因**: 当方と `TSK-235` 担当の**双方**が、`review-trigger-evidence.json` のコミット履歴
(記録が `f6a0aa85`〔2026-09-23〕でまとめて書かれたこと)だけを根拠に「実施の形跡が無い」と結論し、
**裁定が実際に書かれている設計書を読まなかった。** **1 つの置き場所に無いことを、行為が無かったことの
証拠として扱った。** 本計画書への敵対レビュー(gpt-6-sol xhigh)が **P0** として指摘して判明した。

**→ 「再評価の欠落」は論点ではない。** `evidenceDigest` が `model.schema.json` を指したままである点も、
**裁定が合成 DSL fixture の実証を根拠にしていることと矛盾しない**(証拠の所在の記録であって判定時点の記録ではない)。

#### 【2026-10-03 再是正】**受け皿は存在する。「閉じ方の帰結」も撤回する**

**本書は一時「限界②の受け皿として指された前提ゲート①の射程が合っておらず、戻る評価地点が無い」と
書いていた。これも誤りである。** 計画書への敵対レビュー 2 周目が `P1` として指摘し、原典で確認した。

**誤り 1 — 条項の混同。** `../../adr/ADR-003-domain-calc-method.md` の「見直しトリガー」節の**第 1 項**(逐語):

> **DSL の射程で表せないドメイン計算が現れたとき** — D-1 の正本の射程(状態遷移 + 有限の算術)に
> 収まらない計算が要件に入った場合。次点は D-2 の「TS 正本 → 同一 JS artifact を QuickJS / 常駐 Node で実行」

**`ADR-003` 自身が、表現力不足のための見直しトリガーを持っている。次点の方式まで指定されている。**
**`TSK-235` の実装ゲートである「トリガー 1」と、`ADR-003` 自身の「見直しトリガー」は別の条項である。**
前者が評価地点を使い切って閉じていることは、**後者の経路に影響しない。**

**誤り 2 — 限界②の引用が 1 文目で切れていた。** 全文(`d825b2c9` の `design.md:1541-1542`・逐語):

> **限界②は残る**: **これは合成 DSL での確認であり、製品データではない。**

**→ 本書が確認した論点(再評価の有無・閉じ方・限界②の受け皿)の範囲では、`TSK-235` に瑕疵は見つかっていない。** 本書 §3 の候補 6 件の行き先は

### 6. 予告されていた再浮上

`../domain-calc-dsl/design.md:1863-1881`(PO 裁定 2026-09-18)の逐語:

> **つまり前提ゲート 3 の発火は、同時に見直しトリガー 2 の発火を意味する。
> 停止先は要件書の改訂ゲート … と `ADR-003` の改訂ゲート … の両方**

> **段階 2 への申し送り: `U-X1`(状況計算核)が結果表示名を実装する時点で必ず再浮上する。**

**ただしこの予告はトリガー 2(結果表示名の 3 類への不適合)についてのものであり、本書が扱うトリガー 1(型語彙の表現力)とは別の条項である。**
**2 つを同一視しない。** 本書が引く意味は次の 2 点に限る:

1. **同じ `U-X1` の実装着手が、両トリガーの再評価点になる**と PO が既に認識していたこと
2. **停止先が「要件書の改訂ゲートと `ADR-003` の改訂ゲートの両方」になる**という形が、既に 1 件確定していること

**トリガー 1 の発火判定そのものは、本書 §3 の反例によって独立に行われる。**
