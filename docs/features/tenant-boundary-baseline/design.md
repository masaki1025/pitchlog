## 1. D1 — 単一検査・1 記録(5 周目 `P0-1` の是正・**PO 裁定 2026-09-24**)

### 4 周目案の撤回

4 周目は「7 資産へ `check_id` を置いて別検査として宣言する」としたが、**それはラベル付けであって検査の分割ではない**と判定された:

> 現行の `load_contract` / `check_repository` は **7 資産を組み合わせて単一の合否を返します**。`check_id` の追加と既存記録の独立性は、検査の分割ではなく既存構造へのラベル付けです。**既存 7 記録は適否を争っている対象なので、別検査であることの根拠にもできません。**

**根拠が循環していた。撤回する。**

### 採る形 — 単一検査として扱う

**tenant_boundary の 7 資産は 1 つの検査である。** 7.7-2 の「同一の検査について、1 回の受理が実際に作った遷移につき 1 記録」に従い、**1 受理につき 1 記録**とする。

| | |
| --- | --- |
| **記録の置き場** | **`base-allowlist.json` の `baseline_control.history`**(単一検査の履歴の authority) |
| **他 6 資産** | `baseline_control` へ **`history_authority: false`** を宣言し、**以後の追記先にしない**。既存の v1 prefix は不変のまま保持する |
| **記録の中身** | **7 資産すべての新旧識別値**を持つ(`previous_baseline_identifiers` / `new_baseline_identifiers` が 7 資産分) |

**`history_authority` は機械可読な宣言であり、`true` がちょうど 1 資産であることを検査する。**

### 既存 7 記録との関係

**既存の 7 記録(v1)は、資産ごとの prefix としてそのまま残す。** 移動も書き換えもしない(7.7-2 の追記専用)。**本 PR 以後、追記されるのは authority 資産だけである。**

## 2. D2 — 版付き record schema

| 版 | `change.before/after` | 許される位置 |
| --- | --- | --- |
| **v1** | `{state, frozen_projection_sha256}` | **比較元から継承した論理履歴 prefix の中だけ** |
| **v2** | 3 節のとおり | **prefix 以後の追記はすべて v2 のみ**(authority 資産のみ) |

**prefix 以後の版キー欠落・明示的な v1・未知の版は、いずれも拒否する。**

### prefix の同一性

**`N = 比較元の history 件数`** とし、**HEAD の先頭 N 件が比較元の生 JSON 値と deep-equal である場合だけ**、その N 件を v1 として受理する。**変更・削除・並べ替え・同位置置換はいずれも拒否する。**

## 3. D3 — v2 が保存する内容(5 周目 `P0-2` の是正)

### 4 周目案の撤回

4 周目は `external_anchors` を `{path, sha256}` だけにし、**「外部実装の旧内容は復元できない」を保証範囲外へ逃がした**。**これは 7.7-2 第 3 項の明示要求を外すこと**と判定された。撤回する。

### 採る形 — content-addressed snapshot を追記専用で置く

| キー | 中身 |
| --- | --- |
| `aspect` | **実差分から機械導出**し、申告値との **exact-set 一致**を検査する(5 周目 `P0-2`) |
| `declaration` | 当該時点の `baseline_declaration` の正規化 JSON(**内容そのもの**) |
| `movement_policy` | 同上 |
| `external_snapshots` | `{path, sha256, snapshot_ref}` の順序固定列 |

**`snapshot_ref`** は **`contracts/tenant_boundary/history-snapshots/<sha256>`** を指す。**同ディレクトリは追記専用**とし、**既存ファイルの変更・削除を受理しない**。

**これにより「変更前後の内容」が履歴から必ず解決できる。** digest だけの参照ではない。

**`movement_fact` / `reason` / 新旧識別値は v2 でも必須。**

## 4. D4 — 評価の役割分担とモードの強制(5 周目 `P0-4` の是正)

### 役割分担

| 判定 | 使うもの |
| --- | --- |
| **movement 判定・対象集合** | **比較元の宣言** |
| **`before`** | **比較元の定義と比較元の実装** |
| **`after`** | **HEAD の定義と HEAD の実体から導出** |

**HEAD 定義の変更自体は、比較元宣言と 7.7-1 の普遍下限によって必ず movement になる。**

### モードは検査器が強制する(4 周目案の撤回)

4 周目は「CI workflow の改変は射影で観測しない」を保証範囲外へ逃がしたが、**workflow を変えて不変量モードだけを実行させれば遷移と `acceptance_id` を検査せず green にできる**ため、**7.7-3 が禁じる「判定の省略」**と判定された。撤回する。

**採る形**:

1. **PR コンテキストでは検査器自身が PR 受理モードを強制する。** `GITHUB_EVENT_NAME == "pull_request"` を検査器が見て判定し、**必要なイベント情報が無ければ不合格**にする(workflow の指定に従わない)
2. **モード結線を担う `.github/workflows/ci.yml` を 7 資産の `external_files` へ含める**

**PR 受理モードで検査すること**: `base.ref == develop` / HEAD が 2 親 / 第一親 == `base.sha` / 第二親 == `head.sha` / 遷移と記録 / `acceptance_id` の照合。

**不変量モード**(`push` / `workflow_dispatch` / ローカル): 不変量だけ(資産の構造・履歴の内部整合・prefix の deep-equal)。

### `acceptance_id`

```
acceptance_id = f"{repository.full_name}#{pull_request.number}"
```

**同一 PR の再実行・reopen は同値。新しい PR は別値。** **PR 番号は記録を作る前に確定させる**([plan.md](plan.md) ステップ 1 で draft PR を作る)。

## 5. D5 — 普遍下限と 7D の最小限(5 周目 `P0-3` の是正)

### 条文の 5 軸と宣言 token の対応

| 7.7-1 の事実(逐語) | 宣言 token |
| --- | --- |
| 基準の**集合** | `baseline_set` |
| 基準の**値** | `baseline_value` |
| 基準の**置き場** | `declaration_location` |
| **凍結対象との対応** | `frozen_target_mapping` |
| **同一性の粒度や識別値の解釈** | `identity_granularity` と `identifier_interpretation` |
| (下限外の追加分) | `pass_fail_mapping` ほか — **比較元の宣言から取得する** |

### 負例は字面ではなく実状態を動かす(4 周目案の是正)

4 周目は「6 token の欠落 6 + 置換 6」としたが、**それが証明するのは宣言 token の exact schema だけ**で、**各軸の事実変化が movement になることを証明しない**と判定された。

**採る形 — 6 token それぞれについて、対応する実状態を変異させ、movement と記録要求が発生することを試験する。**

### 7D の最小限を本 PR へ戻す

**`baseline_set` と `declaration_location` は、資産の移動・削除と `FROZEN_BASELINE_ASSETS` の変更を同時に行うと HEAD 側走査から消える**(5 周目 `P0-3`)。**走査が HEAD 側だけでは、この 2 軸の下限を実装したと判定できない。**

**したがって「比較元側 ∪ HEAD 側の資産集合を走査する」ところまでを本 PR へ戻す。** 削除記録の置き場・履歴アーカイブ・安定した履歴 ID は**送り出したまま**とし、**本 PR では「比較元にあって HEAD に無い資産」を検出したら不合格にする**(記録の形は決めない)。

## 6. D6 — 実装の隔離

**検査器は `base-allowlist.json` の `external_files` に入っているので、1 バイトでも編集すると射影が動き、記録が無い時点で red になる。**

1. **準備の実装は新規 `scripts/frozen_history.py` へ置く**(検査器を触らない・未結線)
2. **最終コミットで同時に行う**: 結線 / 7 資産の `external_files` へ検査器・helper・`ci.yml` を入れる / `history_authority` の宣言 / **authority 資産へ v2 の記録 1 件と識別値の更新**

## 8. 主張しない範囲(**番号付き exact-set** — 5 周目 `P1` の是正)

**[plan.md](plan.md) ステップ 10 と DoD は本節を参照し、この 5 項目をそのまま PR 本文へ転記する。**

1. **「7.7 へ完全に適合した」とは主張しない。** 7D の残り(削除記録の置き場・履歴アーカイブ・安定した履歴 ID)・7E・センチネル 7 件は未解決のまま残る
2. **合否写像だけを変えて凍結を無効にする経路は塞がない**(7.7-4 が明示的に非保証)。**7B は「宣言した trigger を射影が観測する」ところまでである**
3. **HEAD 実装が比較元宣言をどう解釈したかは機械で保証しない。** 信頼根は人間の逐行確認である
4. **記録された承認者が実際に承認したことは保証しない**(7.7-4 が既に明示)。**保証するのは予約値のまま素通りしないことまで**
5. **比較元 prefix の真正性は検証しない。** **`base.sha` の履歴を信頼根とし、それ以前に入った改竄や不正な v1 記録はそのまま継承する**。過去改竄の検出には署名済みまたはリポジトリ外の不変アンカーが要る(**送り出す**)

**4 周目に保証範囲外へ置いた 2 件(外部実装の旧内容・CI workflow の改変)は、いずれも条文の要求を外すと判定されたため撤回し、3 節・4 節で実体を作った。**
