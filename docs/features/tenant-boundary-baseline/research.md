# 調査メモ: 凍結基準の更新経路(設計書 7.7)への適合 — tenant_boundary 資産(TSK-431)

## 問い

TSK-431 が持ち越した 7B / 7C / 7D / 7E を、**設計書 7.7 のどの項に照らして・どういう順で・どの方式で**直すか。とくにカードが「個別の穴を塞ぐより先に要る可能性がある」と書いた **「基準の値」と「検査の手続き」の線引き**について、既存の決定があるかを確かめる。

調査は `/investigate` で 3 並列(decision-tracer / spec-checker / Explore)に委任し、**エージェント間の食い違いは本セッションが原典で裁定した**(6-3 節)。

## 結論(要約)

1. **線引きには既に先例がある。** 7A の是正(2026-09-21)で「**比較元は基準の値ではなく検査の手続きに属する**」が採られ、**条文ではなく機構**(検査器ソースへ凍結した既定値を置き、検査器自身を凍結射影の対象にする)で解かれている。コードにコメントとして残っている(`scripts/check_tenant_boundary_bypass.py:33-36`)。**本タスクは新しい線を引くのではなく、この先例を 7D へ適用できるかを判断する。**
2. **条文の正面の違反は 7C と 7D の 2 件だけ。** 7B と 7E は **7.7-4 が各資産へ委任した領域の不履行**であって、7.7 が命じたことへの違反ではない。とくに **7B が主題とする「合否写像だけを変えて凍結を無効にする経路」は、7.7-4 が明示的に「本節はこれを塞がない」と書いた経路**である(`dev-harness-design-2026-08-07.md:640-643`)。
3. **7D は自己矛盾を抱えている。** 検査器のコメント(`:46-47`)が「資産の場所だけは bootstrap・第二の決定元にはしない」と自己申告する一方、実挙動(`:3749`)は保護対象の集合そのものを決めている。**申告と実挙動が食い違う。**
4. **TSK-421(PR #73)の概念部品は流用しうるが、台帳への移設対象ではない。** tenant_boundary は「検査器ソースへの直書き」を持たないので `frozen-baselines.json` の母集団に属さない。一方 7C が解く問題は TSK-421 が `changes[]` + fold で解いた問題と同一である。
5. **カードに無い 5 件目がある。** 全 7 資産の `approved_by` / `approved_on` が `"未承認(PR #72 のレビュー待ち)"` のまま、`source_commit` が `"PENDING_ACCEPTANCE"` のままで、**PR #72 は 2026-09-23 にマージ済み**。7.7-2 第 4 項の不履行が現に存在する。
6. **本タスク自身が全 7 資産の射影を動かす。** 検査器を触る以上 `base-allowlist.json` の射影が動き、資産 JSON を触る以上その資産の射影も動く。**履歴 1 件ずつの追加と識別値の更新が自己適用で必要**。DoD に未記載。

#### 3-1. 7B — 条文が「塞がない」と明示した経路である

7 資産すべてが `movement_triggers` に `pass_fail_mapping` を宣言しているが、合否写像を実装する `scripts/check_tenant_boundary_bypass.py` を `external_files` に射影しているのは **`base-allowlist.json` の 1 資産だけ**(実測 — 他 6 資産は `"external_files": []`)。検査器はこの非対称を検証しない(`:387` は型検査のみ)。

**ただし 7.7-4 `:640-643` は、この経路をまさに「本節が塞がない経路」として名指ししている**:

> **塞がらない経路の例**: **基準・値・置き場・対応・粒度をすべて維持したまま、比較の結果を検査の合否へ写す規則だけを変えて凍結を無効にする経路**(**確定ゲート 8 周目 `P1`**)。**本節はこれを塞がない**

したがって **7B は「7.7 が命じたことを守っていない」型ではない**。根拠にできるのは 7.7-4 `:637-638`:

> **行為の対象となる基準の集合は、7.7-1 の事実による下限と、直前の宣言が定める下限外の追加分との和とする。** **宣言は下限を縮小できない**

資産が `pass_fail_mapping` を宣言した以上、それは「下限外の追加分」として対象集合に入る。**その追加分を射影が実装していないことが、`:621` の委任の不履行にあたる。**

**選択肢が 2 つあり、計画書が裁定する必要がある**:

- (a) **射影に含める**(6 資産の `external_files` に検査器を足す)
- (b) **宣言から `pass_fail_mapping` を落とす**(下限外の追加分の撤回)

`pass_fail_mapping` は **7.7-1 `:535-536` の 5 軸(集合・値・置き場・対応・粒度)に含まれない**ので、(b) も条文上は禁じられていない。ただし (b) は検査器の `required_triggers`(`:420`)の変更を伴い、それ自体が 7.7-1 `:566-567`(粒度・解釈の変更)に近い行為になる。

**付随する不整合**: 検査器が `required_triggers` として **7 要素**を強制している(`:420-435`)が、**7.7-1 の事実の列は 5 軸**。実装が条文の下限を 2 要素超えて要求している。`:627-628` の許す上乗せだが、**下限を決めているのが実装側の定数である**点は 7.7-4 `:629-630`(決定元は宣言 1 つ・実装は決定元にしない)と同じ形の問題を抱える。

#### 3-2. 7C — 7.7-2 第 3 項の正面の違反。射程はカードより広い

7.7-2 `:593-595`(逐語):

> 3. **何を変えたか** — **変えた事柄と、その変更前後の内容**(**同一性の粒度・識別値の解釈を変えたときは、旧定義と新定義の双方**。**新旧の識別値が同じでも変更は起こりうるので、これが無いと履歴から復元できない**)

実装は `change` の許容キーを `{subject, before, after}` に、`before`/`after` の許容キーを `{state, frozen_projection_sha256}` に **exact-set で固定**(`:490-506`)。`state` は `{NO_BASELINE, PRESENT}` の 2 値、digest は 64 hex を強制(`:515-520`)。**内容を書く場所が構造上存在しない。**

`_history_snapshot`(`:619-629`)が返すのは **`(state, frozen_projection_sha256)` の 2 要素 tuple のみ**で、`subject` / `movement_fact` / `reason` は**読まない**。呼び出しは 4 箇所(`:670` / `:672` / `:716` / `:718`)、すべてタプル等値比較。

**カードは「変更前後の実内容を記録できない」までしか書いていないが、`:594` の「同一性の粒度・識別値の解釈を変えたときは旧定義と新定義の双方」も書けない。** 7C の射程はこちらまで及ぶ。

#### 3-3. 7D — 3 本の条文に抵触し、コード内に反論が記録されている

**(i) 7.7-3 違反(最も強い)**: `:607-609` は「履歴の取得に失敗した等」で「**判定の保留・省略・中立の結果では満たさない**」と定める。`_validate_repository_histories`(`:3749`)は **HEAD 側定数だけ**を反復する。**資産の削除・移動と定数からの除去を同一差分で行うと、旧パスの履歴は走査対象から落ち、検査は不合格にならずに通る** = 条文が名指しで禁じた「**省略**」。

7.7-4 `:615` が「**7.7-3 は検査の結果に掛かる**(**現存の検査にも掛かる**)」と明記しており、「既存実装だから対象外」という逃げ道は無い。

**穴は「資産ファイルと定数を同時に消す」場合に限られる**(資産だけ消せば `_read_json`(`:190-193`)が `ContractError` を上げて fail-closed する)。

**(ii) 7.7-4 の決定元規則への抵触**: `:629-630`「**決定元は機械可読な宣言 1 つとする**(**実装は決定元にしない**)」、`:631-633`「**その行為の直前に有効だった宣言で判定する**」。実装の定数が集合を決めており、しかも **HEAD 側**(行為の直後)で判定している。

**コード内に反論が記録されている** — `:46-47`:

```python
# 資産の場所だけは、その宣言を読む前に必要になる bootstrap なので残す。
# 基準値・合否写像は各資産から読み、この一覧を第二の決定元にはしない。
```

**この自己申告と `:3749` の実挙動(集合そのものを決めている)が食い違う。TSK-431 の中心論点はここ。**

**(iii) 7.7-1 の削除遷移を表現できない**: `:546-548` と `:574-577` は「凍結対象が 1 つも残らなくなったら宣言から取り除く」遷移を**正当なものとして定めている**のに、現行実装はそれを通せない(定数に残せば `_read_json` が落ち、消せば黙って通る)。

#### 3-4. 7E — 条文違反ではないが、修正が 7.7-1/7.7-2 の義務を発生させる

比較元は `_run_git`(`:3705-3718`・`text=True` → ロケール既定でデコード + universal newlines による `\r\n`→`\n` 変換)の戻り値を `.encode("utf-8")`(`:3764`)。現側は `read_bytes()`(`:3768`)。射影は両者を同じ `hashlib.sha256` に掛ける(`:600`)。

**資産 JSON 側には差が伝播しない** — `_frozen_projection_sha256`(`:555-616`)は Python オブジェクトを `json.dumps(..., sort_keys=True, separators=(",",":")).encode("utf-8")` で再正規化してから取る。**外部凍結対象だけが生バイトのまま入る**(`:603`)。ここが唯一の非対称点。

**現時点で差は出ていない**(実測: 両側とも `dadd3e86…`・160273 バイト・CRLF 0 件・`.gitattributes` はリポジトリに無い)。

**7.7-3 の射程外**: 7E が生む誤りは「確かめられない」ではなく「**誤った同値判定**」。`:607-608` の列挙は「参照先が解決できない、比較元を読めない、履歴の取得に失敗した等」に限る。**条文は誤答型の欠陥に fail-closed を要求していない。**「7.7-3 で守られているから軽い」という論法は使えない。

**修正が発生させる義務**: 7.7-1 `:566-567`「**「値の変更」には、一度定めた同一性の粒度・識別値の解釈を変えることを含む**」。比較のバイト規則を変えることはこれに当たり、**7.7-1 の宣言義務 + 7.7-2 `:594` の旧新双方の記録義務が発生する**。DoD に未記載。

**副次的な欠陥**: `_run_git` が `encoding=` を指定していないため、ASCII ロケールでは `UnicodeDecodeError`(= `ValueError` 派生)になり、`:588-593` の `except (OSError, ContractError)` に捕まらず伝播する。**ただし結果は検査器の異常終了 = CI が red なので fail-closed の側**で、穴ではない。UTF-8 以外のロケールで CI が壊れる運用上の脆さ。

### 4. 決定史 — 線引きには既に先例がある

#### 4-1. 決定A「比較元は検査の手続きに属する」(2026-09-21・山田正輝の判断)

`docs/worklog/2026-09-17-tenant-boundary-enforcement.md:190-195`(逐語):

# 比較元は基準の値ではなく検査の手続きに属するため、検査対象の資産には置かない。
