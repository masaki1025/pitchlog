## 2. スコープ

### やること

**`_validate_receiving_task_repository_change_closure` に 1 つのゲートを入れる。**

**分岐に入る前に、基準版と HEAD の両方が次を満たすことを確かめる**(**満たさなければ red**):

- `claims` が**存在し・配列で・空でなく・要素がオブジェクト**
- **全行**が `receiving_task_id` を持ち、**非空文字列**

そのうえで分岐する。

| 基準版の状態 | 挙動 |
| --- | --- |
| **プレースホルダ行が 1 件以上ある**(置換が進行中) | **現行の 4 段をそのまま走らせる**(挙動を変えない) |
| **プレースホルダ行が 0 件**(置換が済んでいる) | **基準版の全行が最終文法に一致すること**と **HEAD にも 0 件であること**の**両方**を確認して**素通りする**。どちらかが崩れていれば **red** |

**「0 件なら HEAD も 0 件だけ確認して素通り」では閉じない**(**5 周目 `P1`**)—
**`claims: []` / 全行 `""` / 全行 `"xyz"` がいずれも素通り対象になる**。

> **条件の正は 4 節の ①②③ である。** **本節の表は読み手が最初に見る要約であり、
> 条件を改訂するときは 4 節を直してから本表を合わせる。** **他の節では条件を書き直さない**
> (**6 周目 `P1` — 条件を複数箇所に書いたことが 5 周連続の追随漏れの原因**)。

**ゲートは閉包の入口に置く。** 段ごとに分岐を足すのではなく、**4 段まとめて掛ける**
(段 1 だけ通して段 2 で落ちる、のような中途半端な状態を作らない)。

### やらないこと

| やらないこと | 理由 |
| --- | --- |
| **`contracts/` を 1 バイトも変えない** | 本件は検査器の欠陥であり、資産は正しい |
| **固定 SHA の基準を検査器へ置かない** | **基準の固定は `TSK-421` の射程**。ここで置くと**移設対象が 1 つ増えるだけ**。**加えて `TSK-420` の草案 `7.7-1`(基準を新たに置くときは資産側の宣言へ)が統合された場合には、直書きがその規則に触れる**(**develop `4b46c03` の設計書は 7.6 までで 7.7 節は存在しない** — 実測。**3 周目 `P0` で草案扱いへ是正**) |
| **段 2〜4 の中身を変えない** | 置換が進行中のときの挙動は正しい。**変えるのは「いつ走るか」だけ** |
| **受取先の検査 4 層(層①〜④)を変えない** | 文法・参照整合・owner 単位の一致は常時有効でよい。**落ちているのは閉包だけ** |
| **`backend/` を触らない** | 凍結オラクル検査は別系統で、本件と無関係 |

### **この修正は緩和であって除去ではない**(**`420` セッションの指摘**)

**「基準版に対象行 0 件」は 2 つの状態を区別できない。**

1. **置換が完了した正常な状態**
2. **基準が、プレースホルダがそもそも存在しなかったコミットへずれた異常な状態**

**「HEAD にも 0 件」を足しても完全には分かれない** — **2 の場合も両方 0 件で通る。**

**完全に断つには基準の固定が要り、それは `TSK-421` の射程**(凍結基準を台帳へ移す)。
**本修正は `TSK-421` が「対象行が無いときの分岐がある前提」で受け取れる形にする**ことまでを負う。
**この限界を docstring と PR 本文の両方へ書く。**

### **`TSK-420` が起案中の `7.7` は、現行条文ではない**(**2 周目 `P0` で是正**)

**develop(`4b46c03`)のハーネス設計書は 7.6 までで、7.7 節は存在しない**(実測)。
**当初これを現行条文として引いたが、読んでいたのは `feature/frozen-baseline-clause` の草案だった。**
**本 fix は `TSK-420` より先にマージする**(7 節)ので、**現行条文としては引けない。**

**そのうえで、草案の整理は本修正の設計と矛盾しない**(`420` セッションの指摘):

- 草案 `7.7-3` が掛かるのは「**基準の妥当性を確かめられないとき**」。
  **いまの red は「確かめた結果、前提が崩れていた」**ので、**通常の検査失敗**である
- **本修正は「確かめずに通す」のではなく「別の性質を確かめて通す」**形なので、**草案が入っても衝突しない**。
  **確かめる内容は 4 節の ①②③ が正**(**本節では条件を書き直さない** — **6 周目 `P1`。条件を複数箇所に書いたことが 5 周連続の追随漏れの原因**)

**本修正が「確かめられないときは red」を置くのは、条文の帰結ではなく本計画書の設計判断である。**

## 4. 実装方針

### 重さ分類 = **コア領域**

**`scripts/check_authz_catalog.py` は `tenant-isolation` の `paths` に明示登録されている**
(`.claude/core-areas.json:291` 付近 — **実測**)。**`guard_paths` のみではない**(**1 周目 `P1` で是正**)。

→ **PR 本文では敵対レビューと逐行確認の両方のチェックを有効化する**(`pr/SKILL.md:44`)。
**レビューも敵対で回す。**

### 設計

**閉包の入口で 1 度だけ判定する。**

```
① 基準版と HEAD の claims が「存在する・配列である・空でない・要素がオブジェクトである」
② 基準版と HEAD の 全行 が receiving_task_id を持ち、非空文字列である
     ①② のいずれかが確かめられない → red(判定を保留・省略・中立にしない)
③ 基準版に receiving_task_id == "TSK-270-GROUP-2" の行があるか
     ある  → 4 段をそのまま走らせる(現行の挙動)
     無い  → 次の 2 つを確かめて素通りする
              (a) 基準版の全行が最終文法に一致する
                  TSK-nnn | PENDING:FR-nnn | PENDING:NFR-nnn
                  既存の _validate_receiving_task_id_syntax を再利用する
                  (層① は現行資産、(a) は基準版を見るので役割が重複せず、
                   文法の二重定義にもならない — 5 周目レビューで確認)
              (b) HEAD にも対象行が 1 件も無い
             どちらかが崩れていれば red
```

**① が要る理由(1 周目 `P1`)**: 現行の段 2 は `_expect_object_list` で
「`claims` が欠落・非配列」を red にする。**入口で形状を見ずに「対象行 0 件」と誤認して return すると、
その検査を迂回できる。**

**② が要る理由(2 周目 `P0`)**: **分岐は `claim_row.get("receiving_task_id")` に依存する。**
**基準版の同フィールドが欠落・非文字列だと、その行は「対象でない」と数えられる。**
**全行がそうなら「対象行 0 件」になり、HEAD も 0 件なら 4 段すべてを迂回できる。**
**①(要素がオブジェクト)だけでは閉じない。**

**「空でない」と「非空文字列」と (a) が要る理由(4 周目 `P0` — 同型の 3 度目)**:

| 迂回の手口 | どこで落とすか |
| --- | --- |
| **基準版を `claims: []` にする** | **①(空でない)**。`_expect_object_list` は空配列を許すので、ここで足す必要がある |
| **基準版の全行を `receiving_task_id: ""` にする** | **②(非空文字列)**。`""` も「文字列」なので型検査だけでは通る |
| **基準版の全行を文法外の文字列(`"xyz"` など)にする** | **③ (a)**。型も非空も満たすので、**最終文法への一致まで見ないと閉じない** |

**いずれも「基準版を壊して HEAD を正常にすれば 4 段を素通りできる」という同じ形。**
**ゲートの入力領域を最初に列挙していれば 1 周で閉じられた。**

**この「確かめられないときは不合格にする」という置き方は、本計画書の設計判断である**
(**2 周目 `P0` で是正** — 当初ハーネス設計書 `7.7-3` を根拠として名指したが、
**develop(`4b46c03`)の設計書は 7.6 までで 7.7 節は存在しない**〔実測〕。
**7.7 は `TSK-420` が起案中の草案**であり、**本 fix は `TSK-420` より先にマージする**〔7 節〕ので、
**現行条文としては引けない**)。

**素通りしても資産は無防備にならない。ただし守りの役割は層ごとに違う**(**1 周目 `P2` で正確化**)。

| 層 | 何を守るか | 守らないこと |
| --- | --- | --- |
| `oracle-seal.lock.json` の `canonical_sha256`(`:5250` 付近) | **現行資産と現行 seal の整合** | **資産と seal を同時に更新されたら止まらない** |
| **backend の凍結オラクル意味本文検査**(`mutation_composition.py:1144` 付近) | **固定基準 `099a8fa…` との意味本文の一致** — **意味凍結を担うのはここ** | — |

**本閉包は PR 限定の上乗せだった。** **意味凍結は backend 側が持つ。**
