## 4. 実装方針

### 重さ分類の根拠 — 「通常」

`.claude/core-areas.json` の `areas`(同期プロトコル / 状況計算 / 記録権 / テナント分離 / データ移行)の paths に、本タスクが触るファイルは**1 つも含まれない**(実測)。意味範囲(設計書 6.3 境界定義表)でも変更対象は開発プロセスの運用文書であり製品ドメインに当たらない。→ **コア領域ではない**。

**ただし `guard_paths`(検査経路・42 件)に `.claude/skills/release/SKILL.md` が含まれる**ため、`core-guard` が発火し PR に逐行確認のチェックが要る。これはコア領域の敵対レビュー要求とは別物で、分類を上げる根拠にはならない。

**`release/SKILL.md` を別 PR へ切り出さない理由**: 設計書 10.1 残余リスクと `release/SKILL.md` の当該記述は**同じ事実を述べる対**であり、片方だけ動かすと不整合が残る(台帳 H-79 型)。

### 実装の主体 — Codex へ委任しない

CLAUDE.md の役割分担は「**Git 操作・PR・ドキュメントは Claude の役割**」。本タスクは全ステップが正本・運用文書・設定ファイルの編集で製品コードを 1 行も含まないため、**`/implement` を使わず Claude が直接実装する**。ステップ表・ステップ記法・1 ステップ 1 コミットの規律は従来どおり適用する(設計書 6.1)。

### ゲート区分 — 計画時点で固定する(レビュー P1 で是正)

当初は「前段で起案し、覆ったら `/finalize-doc` へ切り替える」としていたが、**撤回する**。理由は 2 つ:

1. **解除手続は新規規範である。** 本書自身が「明文が存在しないため定める」としており、7.6-3 前段の「実装追随の節更新」には当たらない。
2. **H-19(前段判定が 6 件覆った)は、意図的に前段へ置く根拠にならない。** 「レビューが毎回捕捉している」は事後の救済であって、計画時点で正しい区分を選ばない理由にはならない。

したがって**計画時点でゲートを固定する**:

| 変更 | ゲート | 根拠 |
| --- | --- | --- |
| `github-setup.md` 2 章 手続 5 の終了 | **前段** | 同書が「strict policy 適用で終了できる」と**条件付きで既に approved** |

### 公開の根拠の記録方針(レビュー P2 で是正)

**個人を特定する情報を書かない。** 記録の目的は**許諾範囲の明確化**であり、それは個人情報なしで達成できる。

**旧由来物の許諾と、公開実施の判断を混ぜない**(レビュー P2):

> **公開の根拠(2026-09-19)**: 公開対象は 2026-09-19 時点の本リポジトリ。**旧リポジトリ由来物の公開許諾は口頭で確認済み**(範囲 = リポジトリ全体)。**公開の実施は PO 指示による。**
> 本記録は**許諾範囲を明確にする**ことを目的とする — `docs/worklog/2026-08-13-req-v2-legacy-parity.md` が記録する許諾は**別リポジトリへの private ミラー**が対象であり、本件には及ばない。

**条件・期限は停止分岐を持つ**(レビュー 2 周目 P1): 「有無だけ確認」では、条件が**有る**場合に許諾範囲を検証できない。

- **条件・期限がともに無い** → **その不在を記録**して続行
- **いずれかが有る / 確認不能** → **タスクを `blocked` にする。** 記録・追随を停止し、**ステップ 4 以降・PR 作成・マージをすべて禁止**する。PO 判断を得て、**許諾範囲が本件を覆うことを確認した記録を残してから再開**する(内容を public 文書へ書かない方針とは両立する — 書くのは「条件あり・PO 判断済み」までで、内容は書かない)

**同じ規律をステップ 6 にも適用する**: **TSK-202 を実在カードへ置換できない場合、「特定不能とした根拠」の記録だけで通過しない。** タスクを `blocked` にし、PO 判断を得て**実在カードへの置換を記録してから再開**する。

### Ruleset の現況化は全現値を照合する(レビュー 2 周目 P1)

**正本の JSON と実設定が一致していない。** `github-setup.md` 3 章の Ruleset JSON には **`require_extra_approval_for_unattributed_changes` のキーが存在しない**(実測)。GitHub は省略時 `false` 扱いのため、**正本の JSON をそのまま再適用すると実設定の `true` が失われる**。

→ 3 章の JSON を**実設定の全現値へ合わせる**。**「ほか」では検査できない**ので、照合する投影を固定する:

| 照合対象 | 備考 |
| --- | --- |
| `name` / `target` / `enforcement` | |
| `conditions.ref_name.include` / `.exclude` | **空配列も比較対象**(省略と区別する) |
| `bypass_actors` | 空配列であること |
| **rule type の集合** | `deletion` / `non_fast_forward` / `pull_request` / `required_status_checks` の 4 種が過不足なく存在 |
| `pull_request` の全パラメータ | `allowed_merge_methods` / `required_approving_review_count` / **`require_extra_approval_for_unattributed_changes`** / `dismiss_stale_reviews_on_push` / `require_code_owner_review` / `require_last_push_approval` / `required_review_thread_resolution` / `required_reviewers` |
| `required_status_checks` の全パラメータ | `strict_required_status_checks_policy` / **`do_not_enforce_on_create`** / 各 check の **`(context, integration_id)` の対**(9 件) |

**`null`・省略・空配列はいずれも比較対象として区別する**(省略を既定値と同一視しない — 本件の `require_extra_approval_for_unattributed_changes` がまさにその事故)。**サーバー管理項目**(`id`・`created_at`・`updated_at`・`_links` 等)は照合から除外し、除外したことを明記する。

あわせて **1 章「現状の制約」の public 行**と **2 章「暫定運用」の見出し・導入文**は現状と**事実が逆**である。一般論として残す部分は条件付きの一般論へ直し、**本リポジトリについての誤った前提は残さない**。
