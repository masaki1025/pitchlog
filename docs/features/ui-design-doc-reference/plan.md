## 4. 実装方針

### 重さ分類 = **通常**

- **コア領域に当たらない。** 変更するのは `docs/` 配下の文書のみ。同期プロトコル / 状況計算 / 記録権 / テナント分離 / データ移行のいずれの意味範囲にも当たらず、
  `.claude/core-areas.json` の `paths`・`guard_paths` にも当たらない(**着手時点の実測。`/pr` で base 側へ再突合する**)
- **軽微ではない。** 設計書 6.1 の fast path は 3 条件すべてを要するが、**③「正本への影響なし」を満たさない**
- **機械的軽作業ではない。** 条文の判断を伴う

### ゲートの判定 — **7.6-3 後段(版繰り上げ + 7.3 の確定ゲート)**

**判定基準は「判断内容を変えるか」である。** 先例が 2 件ある:

| 先例 | 扱い |
| --- | --- |
| `ADR-003:15`(2026-09-01) | 「**D-12 の判断内容を変えない追随更新であり、版は上げない**(7.6-3 前段 — 実装追随の節更新)」 |
| `ADR-002:10`(2026-08-17) | 「様式の正規化(**決定内容の変更なし**)」— 版は 1.0 のまま |
| `ADR-001:12`(2026-09-27) | 決定表の再設計 → **v1.0 → v1.1**・確定ゲート |

**本改訂は `:36` の委任先という規範の所在を変え、`:34` に新しい判定を足す。** いずれも**判断内容の変更**であり、
**先例が前段に留めた「判断内容を変えない追随」には当たらない**。したがって **v1.0 → v1.1・7.3 の確定ゲート**を通す。

### 確定ゲートの適用版(7.3-1)

**設計書 7.3-1 は「適用版の原則」を定める** — ゲートの運用規則は**初回敵対レビュー時点で approved の版**に従う
(先例 `ADR-003:78`「適用版 = **v1.12**〔7.3-1 — 初回敵対レビュー時点で approved の版〕」)。
**ステップ 1 の変更履歴行に適用版を記録する**(着手時点の実測では設計書の approved は **v1.19**。
**初回レビュー時点で再測する** — 並行タブの改訂で動きうる)。

**ゲート中は frontmatter と索引を `in-review` にする。** `/finalize-doc` 手順 1 が
「**対象の変更履歴表/frontmatter を `in-review` に更新し**」と定め、設計書 7.1-4 の
「**現在状態の唯一の正は frontmatter**」とも整合する。**承認後に手順 6 で `approved` へ戻す。**

**【是正 2026-10-10】** 本節は当初「`approved` のまま据え置く」とし、計画レビュー 2 回目の `P0` を
その理由で不採用にしていた。**根拠にした「先例 3 件」は誤りだった** — 挙げた 3 件(設計書 v1.19 /
`ADR-001` v1.1 / `ADR-003` v0.3・v0.2)は**いずれも `in-review` 行の下に `approved` 行があり、
ゲート通過後の状態**である。**ゲート中の状態を示していない。**
develop の全正本 8 件を走査しても**ゲート中のものは 1 件も無く**、反証にも証拠にもならなかった。
**レビューの指摘が正しく、作成者の不採用判断が誤っていた。**

### `H-68` の扱い

**`H-68` の発火条件は「検査・検証の対象になる実体(検証器・生成物・ベクタ)が存在しない段階で、その実体のフィールド設計まで文書で閉じようとした」こと**
(`docs/development/harness-evaluation.md:1359`)。**14 単位の部品はまだ 1 つも無い。**

**本改訂はこの型を避ける設計を採る** — **コンポーネント設計規約そのものを書かず、定める主体と確定の経路だけを書く**。
これは `H-68` の対応案「**実装時確定への送り出し**」(`:1362` の未実施分)そのものである。

**ただし「細部設計をしない」という自己申告では避けられない**(`:1366`)。
**有効なのは「隣接規範を引き込む要求を 1 つも書かない」という具体的な制約**であり、**射程宣言(7.3-7)に「何を要求として書かないか」を含めること**である。

**2 節「やらないこと」は〈このタスクが編集しない対象〉の宣言であって、〈新条文が課さない要求〉の制約ではない。**
**両者は別物であり、`H-68` が求めるのは後者である。** したがって射程宣言には、**新条文が課さない要求**を次の 4 項として明記する:

| # | 本改訂の条文が要求しないこと |
| --- | --- |
| 1 | **`U-F` 系の実装単位に対する着手条件・着手順・レビュー経路**を 1 つも要求しない |
| 2 | **コンポーネントの命名・ディレクトリ構成・props の約束・スタイルの当て方**を 1 つも定めない |
| 3 | **`porting-rules.md` の内容・置き場・正本性**について何も要求しない |
| 4 | **アクセシビリティ・国際化**について何も要求しない(**`NFR-022` が Won't** — `requirements-pitchlog-2026-07-22.md:1015-1016`) |

**4 項の 1 について**: 本改訂の条文は**規約の行き先**(`docs/design/` の正本)**を指す**。これは `H-68` が言う「細部設計」ではなく、
**委任先の所在の指定**である。`docs/design/` に置く設計書は設計書 `:432` により確定ゲートが必須なので、
**行き先を指すこと自体が確定ゲートという経路を含意する**。**この 1 点は意図して要求する。**
したがって 4 項の 1 は「**成果物の形式**」を含めない — **含めると条文自身と矛盾する**。

**4 項は機械の走査だけでは確かめられない**(ステップ 1 の (ii) は語の有無しか見ず、
「props を必須とする」のような語を使わない規約を検出しない)。**走査は必要条件にすぎず、十分条件は人間の逐語確認である。**

**「適用対象が現に存在するか」をエスカレーション時の確認項目にする**(`:1371`)
→ **`U-F1` は現に着手済み**(`feature/uf1-common-ui`)。**送り先は実在する。**

### 送り先が空手形にならない担保

**`ADR-002:36` の失敗の型は「誰も作る任を負っていない文書へ委任した」ことである。** 同じ型を繰り返さないため、
**正本化タスクを同一 PR で起票する**(台帳の候補 `:3606`)。

**ただし正本へ Notion の URL を書いてはならない** — 設計書 7.4 は相互参照を「**正本は Notion を参照しない(Git 単独で完結)**」と定め、
「**正本を Notion に置かない・複製しない**」としている。**担保は Git 側で閉じる**:

- **`ADR-002` の変更履歴行は本計画書のパス**(`../features/ui-design-doc-reference/plan.md`)**で閉じる**(先例 `ADR-003:10`)
- **本計画書(Git 側)が正本化タスクの URL を持ち**、そこから Notion へ辿れる
- **`ADR-002` の条文は、委任先を「文書名」ではなく「主体と経路」(`U-F1` が実測から定め `docs/design/` の正本として確定する)で書く** —
  **文書名を書かないので、再び空手形になりようがない**

### 実装ステップ(コミット単位 — 設計書 6.1 段階実装)

**ステップ 1 を分割できない理由**: `scripts/check_docs_status.py:693-713` は「**索引の版 = 変更履歴表の最大版**」と
「**索引の最終更新 >= 変更履歴表の最大日付**」を違反として検出する。
**`ADR-002` へ v1.1 行を足した時点で `docs/README.md` を同時に直さないと緑にできない。**
