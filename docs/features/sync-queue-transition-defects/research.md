# 調査メモ: 同期キュー遷移の矛盾 2 件(U-13・U-14)

調査方式: 調査サブエージェント 3 本(spec-checker / decision-tracer / Explore)を並列で実行し、
**計画を左右する主張は Claude が原典を再確認して裁定**した。表記:

- **[確認済]** = Claude が本メモ作成時に当該ファイルを読んで裏を取った事実
- **[報告]** = 調査エージェントの報告をそのまま採った事実(典拠は付いているが Claude は再確認していない)

> **引用規約の注意**: 正本 2-6「識別子参照規約」は「**可変文書の参照は識別子が変化しないもので行う…行番号では引かない**」と定める
> (`docs/design/sync-protocol.md` 2-6)**[確認済]**。本メモは調査記録(正本ではない)なので、**節 ID + 実測行番号**を併記する。
> **計画書・正本本文へ転記するときは節・キー付き表行の安定 ID で引く**こと。
> なお同規約は「**版固定アーカイブ `docs/legacy/` は行番号で引く**」と例外を置いている。

## 問い

TSK-329(正本 `docs/design/sync-protocol.md` v0.3 の 11-4 が送った `U-13`・`U-14`)を閉じるために:

1. 2 件は何を決めていないのか。**要件は方式を決めているか**
2. **既に決まっていて動かせないもの**は何か(機構が強制しているものを含む)
3. 直すとどこまで波及し、**どの機械検査が鳴るか / 鳴らないか**
4. `U-14` の (A) 方式判断に、人間が判断するための材料は揃うか

## 結論(要約)

1. **要件は 2 件とも方式を決めていない**。FR-012 / FR-013 / NFR-015 は保存側の帰結(適用しない・破棄しない・退避する・顕在化する)を定めるだけで、
   **応答分類・D3 の前進可否・通知の中身・端末側のキュー遷移条件を定めていない** **[報告・条文は確認済]**。
2. **しかし機構は片側を既に決めている**。機械検査される不変条件 **`SP-01`** が
   「**7-2 の遷移条件列は A5 の結果だけをキーとし、未送信から退避済みへの遷移は A5 の「退避」で条件づけられる**」を positive、
   「**ACK の境界結果が `B4` であること**」を forbidden として持つ(`scripts/design_relations/defects.json` の `SP-01`)**[確認済]**。
   → **`U-14` のうち「キュー遷移の条件」は既に決着済み(A5 のみ)**。残る未決は**サーバーの応答分類・`D3` の扱い・利用者通知**である。
   → **`U-13` の `B1` 限定文言は、この `SP-01` の positive と同じ節の中で衝突している**。
3. **実装は既に A5 のみで遷移している**。`frontend/src/lib/sync/queueTransition.ts` の `QT-02`(未送信→同期済み)・`QT-08`(未送信→退避済み)は
   A5 結果だけを条件に持ち、**`B1`・`B2`・`B4`・`D3`・`P4` の識別子はファイル中に 1 件も存在しない** **[報告]**。
   → **正本の `B1` 限定文言のほうが、実装からも `SP-01` からも浮いている**。
4. **`U-14` の未決が下流を実際に止めている** — `canonOracle.ts` / `idempotencyCollision.ts` が `DI5` を「U-14 未決」を理由に射程外にし、
   TSK-330 へ送っている **[報告]**。
5. **機械検査は薄い**。`element-coverage` は**正本側の完全性(exact set)を見ない**ため、正本に行を足しても鳴らない。
   3 規則は digest も行番号も持たない。**人間の逐行確認が唯一の担保**という 11-4 の警告は実装で裏が取れている **[報告]**。
   ただし **7-2 節から `B1` の識別子が全部消えると `element-coverage` が鳴る**(`R-BOUNDARY` が 7-2 に `B1`〜`B7` の存在を要求)**[確認済]**。

## 詳細と典拠

### 1. 2 件の原文(正本 11-4)

**`U-13`**(11-4 の表・実測 `docs/design/sync-protocol.md:2083`)**[報告]**

> **部分成功したイベントを同期済みへ遷移できない**。7-2 の遷移表は「未送信 → 同期済み」を**`B1` に限定**するが、
> 同じ 7-2 が「**D1 付きキュー遷移の根拠は A5 だけである**」と定める。**A5 はイベント単位の結果**であり
> `B2`/`B3` より前のイベントは確定できるため、**拒否より前のイベントが未送信のまま残る**
> → **再送量・同期件数の通知・キュー空判定の実装が一意にならない**

**`U-14`**(同 `:2084`)**[報告]**

> **保存済みの退避結果の再掲が `B1` と `B4` に分岐する**。6-3 と 7-2 は「保存済みの退避を A5 で再掲する **`B1`** のイベント」という
> 経路を明記するが、7-1・ACK 消失後の再送手順・故障系シナリオは一貫して「**保存済み P4 退避は同じ `B4` を返す**」と規定する。
> **バッチ構成等による選択規則がない**
> → **`B1` の同期件数通知**と**`B4` の記録権不一致通知・`D3` 扱い**の**どちらを実装するかが決まらない方式判断**

**当該の 2 行の現物**(7-2 遷移表・実測)**[確認済]**:

- 7-2 遷移表「未送信 → 同期済み」(`:1011`): 「**B1** で ACK の A5 が、当該イベントの `(D4, D1, D5)` について「受理」または「重複」を返したこと。**D1 ≤ D3 だけでは不足**(…起草レビュー 1 周目 P1)」
- 7-2 遷移表「未送信 → 退避済み」(`:1017`): 「ACK の A5 が当該イベントについて**退避**を返したこと。境界結果が B4 の場合に加え、保存済みの退避結果が **B1** で再掲された場合も含む」

### 3. **機構が既に決めていること — `SP-01`(本調査の最重要発見)** **[確認済]**

`scripts/design_relations/defects.json` の `SP-01` は次を持つ:

```json
{
  "id": "SP-01",
  "check": "condition-key",
  "invariant": {
    "positive": "7-2 の遷移条件列は直後の宣言どおり A5 の結果だけをキーとし、未送信から退避済みへの遷移は A5 の「退避」で条件づけられる。",
    "forbidden": ["ACK の境界結果が **B4** であること"],
    "scope": "6-3、7-1、7-2",
    "mapping": "A5 の「退避」が 6-3 の退避経路と 7-2 の未送信→退避済み遷移の双方に対応する。"
  }
}
```

**帰結**:

1. **`U-14` の「キュー遷移の条件」側は既に決着している** — 遷移条件は **A5 だけ**をキーにする。
   `B4` を遷移条件のキーにする書き方は **forbidden として機械検査される**。
   → **`U-14` の未決は「サーバーがどの境界結果を返すか」「`D3` を前進させるか」「利用者に何を通知するか」に限られる**。
   **クライアントのキュー遷移をどう書くかは未決ではない。**
2. **`U-13` の `B1` 限定文言は `SP-01` の positive と同じ節の中で衝突している** —
   positive は「7-2 の遷移条件列は A5 の結果**だけ**をキーとし」であり、`:1011` の「**B1** で ACK の A5 が…」は
   B1 を条件に持ち込んでいる。`forbidden` の文字列は `B4` の一件だけなので**機械は鳴っていない**が、
   **条文の意図としては `U-13` の是正方向(B1 限定を外す)が `SP-01` と整合する**。
3. `SP-01` の `scope` は **6-3・7-1・7-2** であり、`U-13`/`U-14` が触る節とちょうど一致する。

**あわせて確認した機構の制約**(`invariants/sync-protocol.json` の `SP-01` 宣言)**[報告]**:

- `row-selector` が 7-2 の「未送信」「退避済み」を含む**最初の行**を選ぶ仕様のため、
  **「未送信」「退避済み」を両方含む行を前に挿入すると選択対象がすり替わる**
- 選ばれた行には `A5` と `退避` の**両方のリテラルが必要**

### 4. 実装の既成事実 **[報告]**

`frontend/src/lib/sync/queueTransition.ts`(727 行):

- 遷移表 `QUEUE_TRANSITION_RULES` は正本 7-2 の 14 行に 1:1 対応(`QT-01`〜`QT-14`)
- **`QT-02`(未送信→同期済み)の条件は `{kind:'a5-result', a5ResultIds:[受理, 重複]}` のみ。`B1` への言及なし**
- **`QT-08`(未送信→退避済み)の条件は `a5ResultIds:[退避]` のみ。`B1`/`B4` への言及なし**
- **`B1`・`B2`・`B4`・`D3`・`P4` は grep で 1 件もヒットしない**

→ **実装は `SP-01` の positive どおりに書かれており、正本の `B1` 限定文言だけが浮いている。**

**下流のブロック** **[報告]**:

- `frontend/src/lib/sync/canonOracle.ts`: 「`DI5` を射程外とする。理由 = **U-14 の保存済み退避再掲を B1・B4 のどちらにするか未確定であり TSK-330 が受け取るため**」
- `frontend/src/lib/sync/idempotencyCollision.ts`: 「**DI5 は U-14 が未解決で**、B3a は T9 の永続化を伴うため TSK-330 の射程とする」
- `canonOracle.spec.ts` がこの理由文字列を機械検査している

→ **U-14 を閉じないと `DI5` の実装が開かない。**

**バックエンド**: 同期エンドポイント・ACK 生成・キュー遷移の実装は**存在しない**(ORM モデルのみ)**[報告]**。
→ **この 2 件の是正でバックエンド実装が壊れることはない。**

### 5. 経緯(decision-tracer)**[報告]**

### C(U-14 の応答分類)を人間が判断するための軸

**要件はどちらも許す**ので、判断材料は次の 3 点に整理できる(**本メモは推奨を書かない**):

1. **通知の質(NFR-015)** — B4 は「現記録権を保持していないこと・退避されたこと・破棄されていないこと」を明示する通知を持つ。
   B1 の通知欄は「同期件数を表示する」のみ。退避を同期件数に混ぜない設計は B1 側でも可能だが、**その分の設計を足す必要がある**
2. **`D3` の一貫性** — B4 は「D3 が前進しない」。受理済み再掲と退避再掲が同一要求に混ざる場合(7-3 が明示)、
   B4 だと D3 を返せず prefix 判定と接する
3. **既存記述の多数派** — B4 側が 3 箇所(7-1・7-3・10-2)、B1 側が 2 箇所(6-3 保持表・7-2 遷移表)。
   ただし **7-2 の遷移条件そのものは `SP-01` で A5 固定**なので、7-2 側の「B1 で再掲」は条件ではなく説明文である

### 実施順の制約(計画書のステップ割りに効く)

- **`U-13` と `U-14` を別コミットに割る場合、7-2 から `B1` を全部消す側のコミットで初めて `element-coverage` が赤くなる**
  → `R-BOUNDARY` の `expected_elements` と 2-5 宣言表を**同じコミットで**直す必要がある **[確認済]**
- **7-2 に行を増減すると 11-5 台帳の `7-2/r18` がずれる** → 台帳の追随を同コミットに含める
- **正本 md だけの変更では frontend ジョブが走らない** → `queueTransition.spec.ts` の期待表との整合は
  `sync-protocol.json` を触るコミットまで検証されない。**逐行確認で埋める**

### 本タスクの射程外

- `U-3`(退避済みイベントの保持期間)— 要件書に行がなく、別タスクへ送付済み。**`U-13`/`U-14` の決定が退避済み状態の量に影響する**ため関係を明記する
- `U-5`(B4 の通知文面)— 実装計画(フロントエンド)へ送付済み。**C で B4 を採ると射程が広がる**
- サーバー側実装 — バックエンドに同期実装はまだ無く、TSK-330 が受け取る
