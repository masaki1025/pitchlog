## 1. 背景・目的

### なぜやるか

**`T250P` の受け渡し契約が内部で矛盾しており、TSK-250 が自分の機械検査で落ちる。** 1 節の射程表 C 行は
先行タスク C を「**88 列の行き先表**」と呼ぶ一方、契約の 4 項目(`保存元 / 変換 / 欠損時規則 /
逆変換可能性`)に**行き先を含まない**。ステップ 18 は「本文の記述のうち C の JSON に無い値が 0 件」を
機械検査する。→ **C が行き先を持たなければ TSK-250 が本文に足す行き先は必然的に「C に無い値」になり、
持たせれば C が TSK-250 の物理スキーマに依存して循環する**(TSK-271 計画レビュー 4 周目 `P0-1`・`P0-2`)。

**あわせて PO 裁定(2026-09-08)により、TSK-250 から「スキーマ + ORM の確定」を先行タスクへ切り出す。**
目的は **backend の処理を最短で書ける状態にすること**。根拠は**ハーネス設計書 13 章
「製品機能の実装(v1.13・approved)」が製品実装の開始条件を定めていない**こと(逐語「**本章は製品実装の
開始条件を定めない** — 着手可否は 6.1 の実装計画書ゲート〔人間承認〕で判断する」)。

## 4. 実装方針

### 重さ分類の根拠 — **コア領域**

**コード変更 0 行の文書タスクだが、意味範囲としてコア領域に該当する。** 切り出しの線引きが
**データ移行**(88 列の受け渡し契約・隔離領域・センチネル規則)と**テナント分離**
(RLS を防御層とする設計判断を先行に含めるか)の両方を決めるため、設計書 6.3 の境界定義表に照らして
**含む側に倒す**(同 6.3「判定に迷う場合は含む側に倒す(fail-closed)」)。
→ **敵対レビュー必須・人間の逐行確認必須。**

### 機構が発火しない点と代替統制 3 点

**`data-migration.paths`(5 件)・`tenant-isolation.paths`(21 件)のいずれも本タスクが触るパスを
1 件も含まないため、CI の core-guard は構造的に発火しない**(台帳 **H-12 の 5 件目**。前例は
`legacy-frontend-coverage` / `decision-sheet-ruling` / `legacy-column-mapping`)。代替統制を 3 点置く:

1. **計画・成果物の両方を敵対レビューに掛ける** — 計画書(本書)と、ステップ 8 での**改訂後の `T250P`
   全体**。**受理範囲を 5 種に限定して依頼する**(TSK-271 の成果物レビューが 5 周で閉じた方式 —
   台帳の実測)。**指摘反映後に収束確認周を回す**
2. **人間の逐行確認** — 対象は **① 改訂した `T250P` の全差分** ② **切り出しの線引き表**
   ③ **起票した先行タスク 1 本の DoD**(裁定 `R-2`)④ **4 節の `[手動・外部]` 表 7 項目**
   (**機械検査を 3 本へ絞った代価** — 3 周目の裁定)。実施記録を worklog へ残す。
   **逐行確認は PR 作成者以外**が行う
3. **必須チェック行の手動付与** — core-guard が発火しないため PR テンプレの必須チェック行は自動付与
   されない。**手動で必須チェック行**(文言の正 = `scripts/core_guard.py` の `REQUIRED_CHECK_TEXT`)を
   PR 本文へ置き、直後に設計書 6.3 の実施記録行を置く

### `T250P` が本ブランチに無い問題への対処(**ステップ 1**)

**実測**: `docs/features/data-model-canonical/plan.md` は **develop に存在しない**。
`feature/data-model-canonical` は develop に無いコミットを **6 件**持ち、**develop から 147 コミット
遅れている**。差分ファイルは **4 件のみ**(`T250P` / 同 `research.md` / worklog 2 本)で、
**すべて `docs/features/` と `docs/worklog/`**(一時作業域・記録)。

**採る方法**: **4 文書の内容を通常のステップコミットとして本ブランチへ移送する**(マージしない)。

**当初は「`feature/data-model-canonical` をマージする」と書いたが、これは正本に反する**
(計画レビュー 1 周目 `P0-2`)。設計書 6.1 は**記法なしで許されるマージを「第 2 親が `origin/develop`
系統の develop 取り込み」に限定**し、**side branch マージは進捗表示を「不明」に落とす**と定める。
実機で確認した(レビュアの実行結果):

```text
donor_sha=d3bf60da86a6a285ed4eda66531a1ec6392790fd
classification=merge_unknown      # (ステップ 1) を付けた仮想マージでも不許可分類
ancestor_rc=1                     # donor は origin/develop の祖先ではない
```

→ **マージすると `scripts/feature_status.py` の現在地導出が必ず「不明」になる。**

| 方法 | 採否 | 理由 |
| --- | --- | --- |
| **内容移送**(採る) | ◎ | **通常のステップコミット**なので `merge_unknown` にならない。対象は `docs/features/**` と `docs/worklog/**` の 4 件のみ(文書系) |
| `feature/data-model-canonical` をマージ | × | **`merge_unknown`**(上記の実測) |
| 同ブランチからブランチを切る | × | **develop の 147 コミットが無くなり、参照する TSK-271 の `research.md`(develop 上)が読めない** |
| TSK-250 のブランチで直接作業 | × | **1 タスク = 1 ブランチ = 1 worktree に反する** |
| 先に別 PR で donor を develop へ統合 | × | **計画書を持たない PR** になり 6.1 の実装計画書ゲートを通らない |

**帰結として明示すること**(内容移送でも避けられない): 本 PR のマージにより **TSK-250 の計画書・
