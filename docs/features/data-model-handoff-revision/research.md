## 結論(要約)

1. **要件は authz DDL を要求も禁止もしていない。** 要件書・改善台帳・同期プロトコル正本の全文を
   `RLS` / `ROW LEVEL` / `search_path` / `GRANT` / `関数 ACL` / `DB ロール` で走査して**ヒット 0 件**。
   `FR-034` が拘束するのは **① 応答の内容**(404・**内容・存在が応答から判別できない**・理由コードを
   返さない)**② 経路の全域性**(許可リスト外はすべて既定拒否)**③ セッションの射程**(`FR-033`)の
   3 点で、**実現レイヤを指定していない**。分離手段を名指ししているのは**改善台帳 `I-2` の
   「`team_id` による分離」だけ**で、RLS もロールも書かれていない(`team_id` という語も要件書に無い)。
   → **(A)/(B) は「要件を満たすか」ではなく「候補案の設計判断を先行タスクへ引き継ぐか」の選択である。**
2. **ただしテーブル制約の形は RLS の挙動から導出されている。** 候補案 3-4 節は PostgreSQL 公式の
   「**一意制約と外部キーは常に row security を貫通する**」を根拠に「一意制約は `tenant_id` を先頭に
   含める / テナント内 FK は複合参照にする」を導いている(理由は「**制約違反エラーが他テナントの行の
   存在を漏らす**」)。→ **「authz DDL を外してテーブルだけ決める」と、複合 FK とテナント内一意制約を
   選ぶ根拠が消える。** 継ぎ目は「含める/外す」ではなく **①設計判断(残す)/ ②DDL の実機確定(TSK-317)**
   の間にある。
3. **切り出しを阻害する事実が 3 件ある**(いずれも本調査で新規に検出):
   **(a) 正本と機械検査が「ORM を入れない」と定めている** — 設計書 10.1 の実装追随箇条(2026-08-31・

   「**変更は相対リンクの解決のみ**」で `docs/design/data-model.md` へ移送する設計だが、照合可能な
   54 件のうち**現行要件書の同一行に逐語があるものは 0 件**。貼り替えは**ステップ 22**(20 ステップ後)。
   **(c) 候補案 3-2 節が移行バッチの書き込み経路について内部矛盾している** — 「マイグレーション用

### 3. テーブル制約の形は RLS の挙動から導出されている

候補案 3-4 節の逐語:

> **動かせない事実**(PostgreSQL 公式 `https://www.postgresql.org/docs/17/ddl-rowsecurity.html`):
> 「Referential integrity checks, such as unique or primary key constraints and foreign key references,
> **always bypass row security** to ensure that data integrity is maintained.」
> つまり**一意制約と外部キーは RLS を必ず貫通する**。要件書が「**内容・存在を含め参照できない**」を
> 要求しているため、素直に設計すると**制約違反エラーが他テナントの行の存在を漏らす**。

そこから候補案が導く規則(3-4 節・**候補案・正本外**):
- **規則 1**: 一意制約は `tenant_id` を先頭に含める(グローバル一意制約を置かない)
- **規則 2**: FK は禁止しない。**テナント内 FK は複合参照**にする
  (`FOREIGN KEY (tenant_id, game_id) REFERENCES game (tenant_id, id)`)

→ **RLS を防御層に採るという前提を外すと、この 2 規則の根拠が消える。** テーブル構造と RLS は
候補案の設計上分離できない。

**継ぎ目の所在(本調査の判定)**: 論点は 3 つに分かれる。

| # | 要素 | 状態 |
| --- | --- | --- |
| ① | **RLS を防御層とする設計判断**(候補案 3-1)+ そこから導出されるテーブル制約(3-4・3-5) | **候補案にあり・正本化されていない** |
| ② | **DDL の一意な実機確定**(`BYPASSRLS` / `NOLOGIN` / 関数 ACL / `search_path` / `FORCE ROW LEVEL SECURITY` の組合せ) | **TSK-317 の所有**。`contracts/authz/ddl-elements.json` は `status: candidate_probe_only` / `product_schema: false` / `second_group_approval_required: true` |
| ③ | **移行バッチの書き込み経路** | **決定が存在しない**(§6) |

### 4. 【阻害要因 (a)】正本と機械検査が「ORM を入れない」と定めている

#### 11-4. 旧 `team` の 2 役の分解

**旧側の事実**: 旧 `team` は**名前がグローバル UNIQUE**、列は id / 名前 / password_hash のみ
(`DL:24`-`:29`)。**テナント境界は `game.owner_team_id` だけ**(`DL:55`・`SS:108`)。
`DB:313` は「**password_hash を持つ team=テナント、他=相手レコードとして振り分け**」と書くが、
**これは `DB` にしかなく `DL` precedence の射程外**(`C` 7-2 節)。

**構造として課されるもの**:
1. テナントとチームレコードは**別単位**で、チームレコードは `tenant_id` を持つ
2. **チーム名にグローバル一意制約を置けない**(同一実世界チームがテナント数だけ別レコードになる)+
   `FR-039`「類似名のチームが既に存在 / 登録 / **警告**される(意図的なら登録可)」
3. **自テナント側の識別が必要**(共有対象が「自テナント所有かつ在籍中の選手」に限られる —
   `FR-039` 補足・`FR-034`)
4. **旧 `stamem` の帰属**: 旧 `stamem` は `team` への FK しか持たず password_hash 有無に限定されない
   (`DL:41`-`:45`)→ password なし旧チームの `stamem` の行き先が問題になる
5. **カルテ 4 系統の対象参照は文字列**(`DL:103`・`DL:107`・`DL:372`「チーム名変更・選手名変更で
   孤児化する」)→ 移行では owner 側テナント配下のチームレコード + 選手 ID へ解決が必要

**候補案のファンアウト 5 手順(`CAND` 7-1 節)は正本外。** 同節は敵対レビュー `P1-3` の是正として
「**ある旧チーム行は『自身のテナント』であると同時に、別の所有テナントの試合では『対戦相手』として
参照され得る**」を記録し、`P0-1` の是正として「**`tenant_id` の比較では自他を判別できない**」を記録している。

#### 11-6. 隔離領域は先行スキーマの射程に含まれるか

**要件上、移行の 1 回目の実行時点で存在していなければ `FR-038` の受入基準を満たせない。**

- `FR-038`「Given 新スキーマの制約(参照整合等)を満たせず取り込めない行 / When 移行 / Then
  黙って落とさず**隔離領域に原本のまま保全**し、解決レポートで人が対処できる」
- `FR-038`「Given 旧データの不整合行 / When 移行 / Then **無検閲で取り込み保全され、警告レポートで
  可視化される(弾かない)**」+ 要件書 4.0 節「黙殺しない」+ 禁止事項 `P-46`「不整合行を弾く」
- 要件書 8 章 DoD⑤: 移行完了は FR-038 の検証がすべて一致し、**警告レポートの棚卸し**が完了していること

**本体スキーマの制約体系の外側にある**: 要件は「**原本のまま**」を要求。かつ
**所有テナント不明行の唯一の受け皿が隔離領域**である(`C` 6-4 節「帰属不明行(`owner_team_id` NULL)の
受け皿は `FR-038` の隔離領域のみで、**『帰属不明のまま新スキーマへ通す』行き先は認められていない**」)
→ **テナント列を NOT NULL にできない単位が 1 つある。**

**「先行スキーマ切り出しの射程に含める」と決めた決定は存在しない(不明)。**
