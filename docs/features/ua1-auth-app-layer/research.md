# 調査メモ: U-A1 γ 認証のアプリ層(署名と検証・TenantContext の生成)— TSK-469

## 問い

TSK-469 の射程(署名と検証 / `TenantContext` の生成 / 署名鍵の環境変数 / DB 接続の TLS 検証 / ログ非出力)について、
**① 要件のどこに根拠があるか ② 過去のどの決定に縛られるか ③ 旧システムに先例と移行制約があるか**を確かめ、
**計画書が決めなければならない論点**を洗い出す。

## 結論(要約)

1. **γ の射程の 4 項目は要件書に根拠が無く、設計正本 `data-model.md` 8-3 節だけが根拠**である
   (鍵 256 ビット以上と起動拒否 / 署名未照合の ID を渡さない / DB 接続の TLS 限定 / `TenantContext`・`allowed_symbols`・TB002)。
2. **NFR-014 の「JWT署名鍵」は旧実装の語彙**である。**旧システムは実際に JWT(HS256)を使っていた**。
   新設計は HMAC-SHA256 を選んでおり、**条文の文言が実装に追随していない**。
3. **γ が `allowed_product_modules` を開けることは、U-T1 が置いた禁止と正面から当たる可能性がある。**
   さらに **TSK-457(封じ込め)が未着手・無主**で、同カード自身が「製品の入口が開く時点で本タスクの機構が要る」と書いている。
   **計画段階で裁定が要る最大の論点。**
4. **DoD の「`core-areas.json` への paths 登録」は、置き場の選び方で不要にできる**(当方実測)。
5. **移行の制約は「本番データを実測しないと決まらない」**(旧 bcrypt のコスト・名前の正規化重複)。**不明を不明のまま書く。**

### 4. 機構の現況(当方の直接実測)

**① 検査器が「製品モジュールは 0 件」をハードエラーで強制している**

`scripts/check_tenant_boundary_bypass.py`(`_load_tenant_context_contract` 内)逐語:

```python

    raise ContractError("U-A1 / TSK-217 が未導入のため製品モジュールの生成経路は 0 件が必要")
```

資産側は `contracts/tenant_boundary/tenant-context-allowlist.json:94` が `"allowed_product_modules": []`。
**γ は資産と検査器の両方を変える。**

**② 資産は凍結基準である**

`tenant-context-allowlist.json` は `baseline_control` を持つ(`identity.scheme = integer_revision_field` / `current_identifiers = ["contract_revision:10"]`)。
`frozen_projection.external_files` に **`scripts/check_tenant_boundary_bypass.py` 自身**が含まれる。
→ **設計書 7.7 の更新記録(7.7-2)が要る。** 検査器を変えるだけでも凍結の射程に入る。

**③ `source_digest` は自己封印**

資産から `source_digest` を除いた正規化 JSON(`json-sort-keys-utf8-v1`)の SHA-256 を自分自身に書く。
**外部ファイルの digest ではない。資産を 1 文字でも変えたら自分で取り直す。**

**④ `TenantContext` の現況**

`backend/src/pitchlog/repositories/context.py:19`(**`db/repositories/` ではない** — U-M1 計画書 `:111` と封じ込めカードの引用はパスが誤っている)。
`__init__` は**公開のまま**(`:32`)。docstring 逐語: 「**この型は値の真正性を検査しない。テナント ID が認証済み主体のものであることは引き続き API 層(TSK-217 / U-A1)の責務である**」。
プロセス内の発行証跡 `_TENANT_CONTEXT_SECRET = secrets.token_bytes(32)`(`:9`)は **HMAC の署名鍵とは別物**。

### 5. 旧システムの事実(legacy-analyst。旧リポ `main`・`04238518`)

**旧は JWT(HS256)を使っていた。** 署名鍵は環境変数で与え、鍵が無いと発行・検証の時点で RuntimeError(`auth.py:14-18`)。
→ **NFR-014 の「JWT署名鍵」は旧実装の語彙**であり、新設計が HMAC を選んだことによるずれである。

| | 旧の事実 | γ への含み | 典拠(旧リポ) |
| --- | --- | --- | --- |
| 失効の機構 | `password_version` = **bcrypt ハッシュ文字列の SHA-256**。API 側が毎回 DB から再計算して比較 | 新の「世代」の先例。**ただし比較が定数時間でない** | `auth.py:34-36` / `api/deps.py:69-87`(`:81`) |
| ログアウト | **サーバ側のログアウトも失効機構も存在しない**(`auth` ルートは register / login / me / password の 4 つだけ) | **γ が新設する。先例なし** | `api/routers/auth.py:1-109` |
| クッキーの穴 | Streamlit のクッキー JWT は `password_version` を**入れていない**。**PW を変えても旧クッキーが失効しない** | **旧要件書が既知ギャップとして記載**。FR-036 が直そうとしている穴 | `app/main.py:162` / `docs/legacy/requirements-tsukuba-pss-v0.2.md:326` |

**移行の制約(いずれも「本番データを実測しないと決まらない」)**:
- **旧 bcrypt のコストとプレフィックスは不明**。`gensalt()` が引数なしで、コストを明示した箇所がリポ全体に 1 件もない(`auth.py:21-23`)
- **Streamlit 経路はパスワード長を検査していない**(空でないことだけ)。**8 文字未満や 72 バイト超が存在しうる**(API 経路は 8〜128 文字・72 バイト以内)
- **`team` の名前は生文字列の UNIQUE のみで、正規化が 1 箇所も無い**(`db/schema.py:645-648`)。**正規化すると重複が出るかは本番データ次第**
- **Basic 認証で入っていたチームは保存ハッシュが NULL のことがあり得る**

**ログ**: 旧でパスワード・トークン・ハッシュをログや画面に出すコードは**見つからなかった**(探索条件は legacy-analyst 報告のとおり)。
ただし **Streamlit は「PW 未設定」と「誤り」を区別して表示**し、**ログイン画面が PW を持つチーム名を一覧表示**する(`app/main.py:196-214`)。
→ FR-033 `:595`「失敗理由からチーム名の存在…が推測できない」が直そうとしている挙動(**応答側は δ**)。
