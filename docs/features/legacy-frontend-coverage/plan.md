## 4. 実装方針

### 重さ分類の根拠 — コア領域

**コア領域 5 つすべてに触れる**(設計書 6.3 境界定義表):

| コア領域 | 本タスクとの関係 |
| --- | --- |
| **同期プロトコル** | FR-012 の判定(旧 SPA は要件のオフライン記録継続セマンティクスを満たさない)。この結論が同期実装の移植元の有無を決める |
| **状況計算** | FR-003・FR-005・FR-007・FR-011・FR-040 の判定と、座標変換(263 系・視点変換)・捕球選手推定の実査(設計書 6.3 が状況計算領域と明記) |
| **記録権** | FR-013 の判定(記録権の意味要素に対応する実装が見つからない) |
| **テナント分離** | FR-034 の判定(404/403 の使い分け = 存在秘匿の要件に反する)+ FR-033/035/037/041/042 と**全出力経路**(FR-029/030/031/032 の帳票・CSV)の実査 |
| **データ移行** | FR-038 の判定(88 列 CSV 取り込みの契約と範囲)+ FR-031/**付録 D** の 88 列互換出力の実査 |

**「文書タスクだから」「コードを書かないから」は重さ分類を落とす根拠にならない。** 判定軸は内容が意味範囲に触れるかであり、作成主体ではない(先例: `docs/features/sync-protocol-design/plan.md:198-206`)。判定に迷うものは**含む側に倒す**(設計書 6.3。先例: `docs/features/product-data-model-design/plan.md:91-97`)。

**機構が発火しない点と代替統制**: `.claude/core-areas.json` の `paths` は同期プロトコル・状況計算・記録権・テナント分離の 4 領域が同期設計正本と要件書、**データ移行は空**であり、本タスクはいずれのパスも変更しないため **CI の core-guard は発火しない**。代替統制は次の 4 点:

1. **計画・成果物の両方を敵対レビューに掛ける** — 計画書(本書)と、ステップ 7 での **`research.md` 全体(結論要約・§0 を含む確定版)+ decision-sheet**。**指摘反映後に収束確認周を回し、最終周 P0/P1 = 0 で収束させる**
2. **人間の逐行確認** — 対象は**突合表のうち設計書 6.3 境界定義表の意味範囲に属する全行**(少なくとも FR-003〜005・007・011・012・013・019・029〜035・037・038・040〜042 と、付録 B/D 関連の座標変換・捕球選手推定・88 列出力の判定)+ **画面 × FR 対応表** + **decision-sheet の全行**
3. **必須チェック行の手動付与** — core-guard が発火しないため PR テンプレの必須チェック行は自動付与されない。**手動で必須チェック行(文言の正 = scripts/core_guard.py の REQUIRED_CHECK_TEXT)を PR 本文へ置き**、その直後に設計書 6.3 の実施記録行(`対象=/範囲=/方法=` — 設計書 354 行)を置く
4. **典拠の全件照合可能化** — 42 行すべてに `LEGACY:<path>:<line>` を付け(× の行は検索式)、レビュー側が機械的に照合できる形にする
