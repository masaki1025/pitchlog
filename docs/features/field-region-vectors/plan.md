### 前提 — 承認で確定する 4 点

条文が答えを持たない箇所がある。**PO 承認で確定し、否認されれば射程とステップを組み替える。**

#### 前提 A: 打者相対の区分は **3 値**(ADR に従う)

| | 要件書 | ADR-003 |
| --- | --- | --- |
| 区分 | 「引っ張り/**流し**」`:1208` | 「引っ張り / **センター返し** / 流し」`:325` |
| 入力軸 | 記載なし | **打球種別の全列挙** `:231` |

**実測: 要件書に「センター返し」「打球種別」は 0 件。**

**本書の判断: ADR に従い 3 値・入力軸に打球種別を置く。** 理由 — ① ADR-003 は approved の正本で、D-6 の契約表が本タスクの成果物を直接定義している ② 物理方向が**等角 5 分割**(`:1208`)である以上、打者相対へ畳むとき**中央の 1 区分を引っ張り側か流し側へ恣意的に寄せることになる**(3 値なら 2:1:2 で自然に対応する) ③ 要件書の「引っ張り/流し」は区分の**列挙ではなく例示の語**であり、「2 値に限る」と読む根拠がない。

**要件書の文言を ADR に合わせる追随は本タスクの射程外**(5 節で申し送る)。

#### 前提 B: 内外角の境界は **要件書の改訂で定める**(同一 PR・確定ゲート)

付録B-3(`:1288`)は「**内角/外角は保存座標と打席左右の組み合わせから導出**する」としか書かず、**分かれ目・2 値か 3 値か・境界線上の帰属・両打ちの扱い**をどれも定めていない。**旧システムにも導出関数が存在しない**([research.md 5 節](./research.md))。

**境界を決めることは計算規則の新設であり、計画書の承認だけでは確定できない。**

> 3. **ゲートの使い分け**: 実装追随の節更新・変更履歴追記は PR レビューで足りる。**版繰り上げを伴う構造的変更**(アーキテクチャ・スキーマの変更、**要件改訂等**)はその部分だけ **7.3 の確定ゲート**(敵対レビュー → 人間承認)を通す
> — `dev-harness-design-2026-08-07.md:531`

**したがって本タスクは要件書 付録B-3 の改訂を含む。** 同書 `:530-2`「**同一 PR で運ぶ**」に従い、ベクタと同じ PR で運ぶ(ステップ 2 → `/finalize-doc`)。

**改善台帳 I-28 の「判断が割れる場合は実装計画書ゲートで PO へ判断を上げる」は本件に適用できない** — 同項は**旧実装の逐語移植**の衝突を対象としており(`:241`)、条文の空白を埋める規則の新設は射程外。

**改訂案(確定ゲートに掛ける内容)**:

- **2 値(内角 / 外角)** — 付録A-3 のような第 3 区分を要求する条文が無いため
- **分かれ目 = ストライクゾーンの水平中心**(`contracts/display_geometry_263_v1.json` の `strike_zone` の left と right の中点)— 付録B-4 が「ゾーン枠は座標値としてデータ保持」と定め、ゾーン枠が唯一のデータ化された横方向の基準であるため
- **境界線上は外角側** — 付録B-6 のタイブレーク規則(「先に定義された領域が優先」)と同じく**一意に決まる規則を置く**ことが目的であり、どちらへ倒すかは任意。**一意であることが要件**(`ADR-003:414`)
- **両打ちは入力に現れない** — 入力は「打席左右」であって打者の属性ではない(`:1288` が「打席左右の組み合わせから導出」とする)

**この案は確定ゲートの敵対レビューに掛ける。** PO が別の線を引く場合はその線で改訂する。**改訂が approved になるまでステップ 5(座標変換ベクタ)は実行しない** — 正解が未確定のままベクタを書くと、後で全件を書き直すことになる。

**版の扱い**: 付録B-3 への規則の追加は条文の新設であり、**要件書の版を繰り上げる**(`:531-3` の「版繰り上げを伴う構造的変更」)。

#### 前提 C: 座標系は要件書 B-1 / B-2 の定義に従う(**選択ではない**)

[research.md 7 節](./research.md)で「frontend が 263・左上原点を『保存座標』と呼び、DB は 0〜1・左下原点」という不整合を実測したが、**これは呼称のずれであってベクタの選択肢ではない**。

- **保存座標** = 0〜1 に正規化した実数ペア・**捕手視点の物理座標・原点は左下**(要件書 `:1286`・`:1287`)
- **画面座標** = 263 スケール・左上原点(`contracts/display_geometry_263_v1.json`・`courseInputView.ts`)
- **(α) の射程は「画面座標⇄保存座標の相互変換」**(`:932`)なので、**ベクタは両方の系を持ち、その対応そのものが期待値**になる

**`courseInputView.ts` が 263 系を「保存座標」と呼んでいる件は本タスクの射程外**(実装を変更しない)。5 節で申し送る。

#### 前提 D: **(β)⑦ を射程から切らない**

master からは「射程を切れるなら切ってください」という示唆があったが、**切っても U-X1 の待ちは解けない**。

段階① の完了条件は「**TSK-235 と TSK-236〜239 の合流**」(`domain-calc-dsl/plan.md:96`)であり、**(β)⑦ 打球方向導出ベクタの後続担当は ADR-003 の契約表で本タスク**(「領域シード作成タスク(と同時)」`:325`)。切れば別タスクへ移るだけで、**段階① は閉じず P-2 は解けない**。

**(β)⑦ がリハーサルに要るかという問いとは別である。** [research.md 8 節](./research.md)の実測では**要らない側**だが(記録が持つのは座標と捕球選手で打球方向は導出値 — `:234`・`:1579`)、**リハーサル 26 FR の全数が正本のどこにも無い**ため典拠で閉じない。いずれにせよ**段階① の完了には要る**ので、本タスクで作る。

## 4. 実装方針

### 重さ分類 = コア領域

設計書 6.3 の境界定義表(状況計算の行)が逐語で含めている:

> …+ **座標変換・捕球選手推定**(NFR-018・NFR-019(a) の対象 — 旧システムで 3 箇所コピー・「静かなデータ破壊」の事故前例〔改善台帳 I-4・I-17〕)
> — `dev-harness-design-2026-08-07.md:398`

**本タスクはこの 2 つの正解ベクタを定める。意味範囲でコア領域(状況計算)に該当する。**

**機械判定とのずれ**: `contracts/field-regions/`・`contracts/display-geometry/` は**どの領域の `paths` にも未登録**なので、`core-guard` は該当を出さない。**非コアの根拠を `paths` で取らないのと同じく、コアの根拠も意味範囲で取る**(CLAUDE.md が両者を分ける)。

**`.claude/core-areas.json` へ新ディレクトリを登録する。** 設計書の paths 落とし込み規則が逐語で要求している:

> ① コアの不変条件・強制点・**契約(ベクタ・スキーマ・テスト)**を**変え得る**ファイルを含める (…) ⑤ **paths の追加・削除・縮小は敵対レビュー + 人間承認の対象**(core-areas.json は guard_paths でもあるため PR 必須チェックが機械強制される)
> — `dev-harness-design-2026-08-07.md:404`

新設する 2 ディレクトリは**まさに「コアの契約(ベクタ)」そのもの**なので ① に当たる。⑤ の敵対レビュー + 人間承認は、**本 PR がコア領域 PR として両方を通す**ので別建てにならない。

**登録しないと、契約だけを変更する後続 PR をどの機構も検知できない。** 本 PR は CI 配線(`guard_paths`)を触るので逐行確認欄は発火するが、**それは偶然であって契約パスの保護ではない**。

→ **敵対レビュー必須 + 人間の逐行確認必須**(設計書 6.3・ADR-001 のコア領域行)。

### 詳細設計

### oracle の独立性をどう担保するか

## 6. テスト計画

`NFR-019` が課すテスト種別のうち、本タスクが足すのは **一致性((a))の土台**と**単体**である。**本タスクはベクタを作るので、一致性テスト本体を緑にするのは消費側(U-X1 の PR-2)**。

| 対象 | 種別 | 置き場 | 確認すること |
| --- | --- | --- | --- |
| 契約 schema | **単体** | `tests/` | schema 自身が妥当。required フィールドの欠落を reject する |
| 領域シード | **単体** | `tests/` | schema 検査 / **守備位置 9 領域と方向区分の双方が存在** / **各群の内部の重複が 0** / 元寸法の対応がある |
| 捕球選手推定ベクタ | **単体** | `tests/` + `frontend/src/**/*.spec.ts` | schema 検査 / **境界線上の点がタイブレーク規則で一意** / **両 runner が読める** |
| 座標変換ベクタ | **単体** | 同上 | schema 検査 / **打席左右の両方** / **往復変換が元の値へ戻る** / クランプ点 / 内外角がステップ 2 の条文どおり |
