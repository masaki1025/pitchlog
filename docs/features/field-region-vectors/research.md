# 調査メモ: TSK-238 領域シードと座標系ベクタ — 方式の影響・射程・oracle の典拠

## 問い

1. **ADR-003 の D-1 → D-2 切り替えで、カードの 4 契約の形は変わるか**(カードは 2026-08-19 作成)
2. **(β)⑦ 打球方向導出を射程から切れるか**
3. **正解ベクタの期待値を独立に確認する典拠は何か**(シードや正本実装から自動生成すると oracle が循環する)
4. **コア領域判定**

調査サブエージェント 3 本(decision-tracer / spec-checker / legacy-analyst)に並列委任し、**判定の分かれ目はすべて原典をこちらで読み直して裁定した**。裁定は本文に「**裁定**」として明示する。

## 結論(要約)

1. **方式は 4 契約の形に及ばない。そもそも D-2 はまだ発効していない。** ADR-003 D-14 は「決定済み・未発効」で**現在の正は D-1**。4 契約の区分・置き場・schema の骨格・消費規則は **D-14-g の分類 ④(方式非依存)**。
2. **ただしカードは 1 点古い** — 打球方向導出ベクタの `expected` に「**写像①を適用した表示名**」が要る(v0.2・2026-09-03 追加)。原因は D-2 ではなく v0.2 の未反映。
3. **ADR が要件書より広い語彙を使っている** — 「センター返し」「打球種別」は**要件書に 0 件**。区分数と入力軸が変わるので **PO 判断が要る**。
4. **正解を作るのに条文が足りない** — 付録B-3 は内外角の**分かれ目・2 値か 3 値か・境界の帰属・両打ち**をどれも定めていない。クランプの典拠も移行側(B-5)にしかない。
5. **旧システムは多角形も等角 5 分割も内外角の導出も持っていない。** 捕球選手推定は**矩形ルール 4 本 + 9 アンカー最近傍**(固定コミットで実測)。**oracle の典拠は旧ではなく条文から作るしかない。**
6. **コア領域(状況計算)に該当する。** 設計書 6.3 の境界定義表が「**座標変換・捕球選手推定**」を明示的に含めている。`paths` には当たらないので**意味範囲で取る**。
7. **(β)⑦ は切れる側だが、根拠が正本の外にある。** リハーサル 26 FR の全数は**リポジトリのどこにも無い**。

## 詳細と典拠

### 1. 方式(D-1 / D-2)の影響 — 4 契約の形は変わらない

**D-2 は「決定済み・未発効」である。**

> ただし本決定は即時には発効しない — `ADR-003:515`
> 発効まで: **D-1 の規定が現行である**。本改訂で失効する規定は無い — `:671`
> **記録が唯一の発効の印である** — `:681-682`

変更履歴に発効日の記録は無い。**裁定: 現在の正は D-1。** master の「D-1 から D-2 へ切り替わりました」は、**決定の成立と発効を区別していない**。カードが D-1 を前提にしていること自体は現時点で誤りではない。

**4 契約の形は方式非依存。** D-14-g の分類で、**D-6 のうち正規化規則を除く部分(契約の構造・ベクタの置き場・入力イベントの範囲)・D-12 は ④(方式非依存・発効後も変更しない)**(`ADR-003:701`・`:713`)。D-11(入力範囲)と D-8 は ②(読み替えあり)だが、**入力範囲の各行(`:228` 座標変換 / `:229` 捕球選手推定 / `:231` (β)⑦)に撤回・上書きは無い**。

**発効後に未確定なのは方式側**(プロパティテストの比較相手 (i)・入力軸 descriptor の突合 (ii)・正規化規則の置き換え先 (iii))で、**ベクタの形には及ばない**。

### 2. カードの陳腐化 — 1 点だけ

| 契約 | ADR の現行記載 | カード |
| --- | --- | --- |
| 打球方向導出ベクタ | `cases[]` = 座標・打球種別・打席左右 → ①物理方向と ②打者相対の区分の両方、**および各区分に写像①を適用した表示名**(expected は構造化区分と表示名の双方を持つ — v0.2)`ADR-003:325` | **表示名が欠けている** |

v0.2 は **2026-09-03(TSK-278)**で、カード作成日 2026-08-19 より後。**D-2 とは無関係。** 他の 3 契約は ADR と一致する。

### 3. 要件書と ADR の語彙の食い違い(PO 判断が要る)

| | 要件書 | ADR-003 |
| --- | --- | --- |
| 打者相対の区分 | 「物理方向で保存し、打者相対の「**引っ張り/流し**」は打席左右との組み合わせで導出」`:1208` | 「引っ張り / **センター返し** / 流し」`:325` |
| 入力軸 | 記載なし | **打球種別の全列挙** `:231` |

**実測: 要件書に「センター返し」「打球種別」は 0 件**(全文 grep)。

**裁定: ADR が要件書より広い。** 区分が 2 値か 3 値かでベクタの `cases[]` の数が変わる。ADR は approved の正本だが、**要件書の付録A-3 が区分の定義元**(`:1208`「区分角はB-6の領域シードで定義」)なので、**どちらに従うかは条文だけでは決まらない**。計画段階で PO へ上げる。

### 4. 正解を作るのに条文が足りない箇所

**付録B-3**(`:1288`)の逐語:

> 3. **打者左右による変換なし**: 保存値は打者の左右にかかわらず物理位置。表示時のみ打者側に応じた背景画像を切り替える。**内角/外角は保存座標と打席左右の組み合わせから導出**する(左打者をミラー保存しない)

**定めていないもの**(いずれも要件に記載なし):

- 内角と外角の**分かれ目がどこか**(ゾーン中心か本塁板中心か)
- **2 値か 3 値か**(真ん中を置くか)
- **境界線上の点の帰属**
- **両打ちの扱い**(`:1144` は集計の対左右分類だけを定める)

**付録B-4**(`:1289`)は「ストライクゾーンの枠(内側判定の境界)は座標値としてデータ保持し、コードにマジックナンバーを散らさない」という**規律**であって計算規則ではない。枠の具体値は無い。

**裁定: B-4 の「内側判定」を (α) の出力に加える根拠は無い。** `:932` が (α) を「画面座標⇄保存座標の相互変換、および**投球コースの内外角の導出**」に限っているため。B-4 が効くのは**内外角の境界をゾーン枠から取る場合の入力データとして**だけで、その取り方自体が未定。

**クランプの典拠は移行側(B-5 `:1290`)にしかない。** ADR は (α) のベクタにも「範囲外のクランプ点」を求める(`:228`)が、**B-1〜B-4 にクランプの規定は無い**。

**1 契約にまとめる根拠は 3 つある**(B-3 と B-4 は別物だが): 要件書 10 章 `:1129` が「付録B-3/B-4座標変換ベクタ」と 1 件で呼ぶ / `ADR-003:327` の契約表 / `:228`「付録B-3・B-4 から導出して固定する」。**ただし NFR-019(a) の比較面 `:973` は B-3 だけを挙げる。**

### 5. oracle の典拠 — 旧システムから引けるもの / 引けないもの

**期待値をシードや正本実装から自動生成しない**(`ADR-003:324`「期待値はシードから自動生成せず独立に確認する」)。独立の典拠を実測した。

#### 引けるもの

| 典拠 | 性質 |
| --- | --- |
| `contracts/display_geometry_263_v1.json` | **dd03160 の `shared/` 版とバイト等価を照合済み**(sha256 `e0c4d336…`・`porting-rules.md:142-146`)。座標系宣言・ゾーン枠・フィールド基準点を持つ |
| 要件書 付録B-5 `:1290` | 263 系 ⇄ 0〜1 系の変換式(`x/263`・`(263−y)/263`)。**移行用だが変換の算術は共通** |
| `dd03160:frontend/src/lib/fielder.ts` | 捕球選手推定の規則(下記) |

#### 引けないもの(**旧に存在しない**)

**① 守備位置の多角形** — 旧は多角形を一度も持っていない。`dd03160:frontend/src/lib/fielder.ts` を固定コミットから取り出して実測:

- **矩形ルール 4 本を上から順に評価**: `y>=205 → 2` / `x>=155 && y>=165 → 3` / `x<=75 && y>=165 → 5` / `x>=105 && x<145 && y>=140 && y<=190 → 1`
- **残りは 9 アンカーへの最近傍**: 8(116,66) / 7(56,101) / 9(174,101) / 6(88,144) / 4(152,144) / 5(66,174) / 3(166,174) / 1(123,164) / 2(123,232)
- **タイブレーク**: 距離の比較が厳密 `<` なので**アンカー列の先頭側が勝つ**
- **センチネル**: `x<=0 || y<=0` と非有限値は `null`

**裁定: 付録B-6 が要求する「座標多角形」は旧に無い。** 多角形は**新規に設計する**ことになる。旧の規則は**期待値の照合相手**として使えるが、**多角形そのものの典拠にはならない**(規則の形が違う)。

**② 等角 5 分割と引っ張り/流し** — 旧は **x だけの 3 分割**。`dd03160:reports/batter_karte_html_pdf.py:271` を実測:

```python
def direction_bucket(x: float) -> str:
    third = PLATE_SCALE / 3
    if x < third:   return "left"
    if x < third * 2: return "center"
    return "right"
```

角度を使わず、打席左右も見ない。**等角 5 分割は pitchlog が 2026-07-22 に新規確定した値**(要件書 `:1208`)。

**③ 内外角の導出** — 旧に導出関数が無い。旧の 3×3 ゾーンは**物理 x で列を決めており打席左右によるミラーが無い**。

### 6. ゾーン枠の数値の食い違い — 正体は旧システム内部の二系統

spec-checker が「文書間で一致しない」と報告した件を裁定する。

| 出典 | 値 |
| --- | --- |
| 改善台帳 I-17 `:156` | 旧ゾーン枠「53〜210」 |
| `contracts/display_geometry_263_v1.json:8-12` | left 80 / right 183 / top 68 / bottom 180 |
| 要件書 | **値を持たない**(B-4 は「データとして持つ」ことだけを定める) |

**裁定: 矛盾ではなく、旧システム内部に二系統あった。** 契約 JSON は SPA の raw 座標系(左上原点)、I-17 の 53〜210 は**集計側の Yadj 系**の値である。同じ食い違いは本塁位置にもある(SPA (123,224) vs 打球図 `_HOME=(130,48)` = raw y 215)。

**したがって「どちらが正か」ではなく「どの系で書くか」を決める問題。** 契約 JSON がバイト等価で固定されている以上、**ベクタは契約 JSON の系に揃える**のが筋。ただし**これは本調査の推論であり、PO 承認が要る**。

### 8. 射程 — (β)⑦ を切れるか

**要件書は判定③ の FR 集合を定めていない。** `:1085` に FR の列挙は無く、`ux1-state-calc/research.md:178` も「導出元 — 要件書 `:1085` に列挙なし」と認めている。

**リハーサル 26 FR の全数はリポジトリのどこにも無い。** リポジトリ内にあるのは:

- 条文の前提関係から導いた**下限**(`frontend-impl-units/research.md:91`)
- U-X1 が持つ **13 件**だけ(`adr003-d2-switch/plan.md:33,65`)

**26 件の内訳は、主セッションの auto-memory ファイルにしか存在しない**(「PO 裁定 2026-10-09」と記録)。**射程判断の根拠が正本の外にある。**

**条文から言えること**(spec-checker の実測):

- 判定③ の対象は「**フル記録**」の欠損・誤り。**記録が持つのは座標と捕球選手**(`:234` FR-004)で、**打球方向は持たない** — 「打球方向は結果IDと打球座標を入力とする。座標と方向区分を同値のフラグとして重複保持しない」(`:1579`)
- 打球方向を表示する条文は **FR-026・FR-041・付録A-3・A-3b・FR-028/029** で、**FR-020〜023(リハーサル側の表示)に打球方向は無い**(`:441-491`)
- 分析はオンライン前提(`:190`)

**裁定: 打球方向は含まれない側。** ただし**留保が 2 点**ある:

1. **FR-024 の Could**「対戦相手のカルテ一式も先読み」(`:499`)のカルテには付録A-3b により打球方向が含まれる(`:1230`)。ただし Could で、判定① は Must のみを対象とする(`:1083`)
2. **26 FR の全数が正本に無い**

**したがって「切れる」と判断する根拠はあるが、正本の典拠では閉じない。PO 判断が要る。**

## 未解決・申し送り

1. **【PO 判断】打者相対の区分は 2 値か 3 値か** — 要件書「引っ張り/流し」vs ADR「引っ張り / センター返し / 流し」。**入力軸に打球種別を置くか**も同じ(要件書に 0 件)
2. **【PO 判断】内外角の境界をどう決めるか** — 分かれ目・2 値/3 値・境界の帰属・両打ち。**どれも要件に無い**。決めないとベクタが書けない
3. **【PO 判断】座標系をどの系で書くか** — 契約 JSON の系(263・左上原点)か DB の系(0〜1・左下原点)か。**frontend は前者を「保存座標」と呼び、DB は後者**という不整合が現存する
