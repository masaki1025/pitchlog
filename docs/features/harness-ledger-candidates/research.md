# 調査メモ: 評価台帳へ候補 8 件を追記するための下調べ

## 問い

1. **追記予定の 8 件は、既存候補と重複していないか。** 重複していれば新規ではなく追記になる
2. **候補は何件あるのか。** 索引の「候補 90 件」が正しいか
3. **`H-*` の採番規則**。8 件に番号を与えるべきか
4. **追記の作法**(導線・書式・変更履歴・索引・機械的な落とし穴)

## 結論(要約)

- **8 件のうち、新規候補として立つのは実質 2〜3 件。残りは既存候補への追記**になる。とくに ①⑧ は追記先が確定している
- **「候補は何件か」は、定義を添えないと数えられない。** 索引の「候補 90 件」は**自分が併記した走査条件で再現しない**(その条件では 89)。接頭辞が 3 系統あり、節の外にも候補がある
- **`H-*` は「制御目的の典拠が示せるか」で決まる**(台帳 `:176`)。採番者を定めた条文は無く、先例は「自分で採番」と「PO 判断」の 2 系統。`H-91` 以降は未使用
- **挿入は行番号で指定する。** `## 候補` を文字列検索して挿入すると変更履歴表を割る事故の前例がある(`:76` `:85` が現に破損)
- **版は上げない**(7.6-3 前段)。変更履歴表の**先頭(`:9`)**へ 1 行、状態列は `候補`

## 詳細と典拠

本節の典拠はすべて `docs/development/harness-evaluation.md`(以下「台帳」)。
調査は Explore と decision-tracer の 2 本を並列で投げ、**結論に効く主張は当方が原典で再確認した**。

**数えられない理由**:

1. **接頭辞が 3 系統**(`(候補)` / `(N)` / なし)。どれも独立候補として機能し、見出しの形で判別できない
2. **`## 候補` 節の外に候補が 5 件**(`:76` `:85` `:149` `:153` `:157`)
3. **見出しでない候補が 2 件**(`:149` `:153`)
4. **`### (候補)` の中身が「既存候補への N 例目」のものがある**(例 `:1678`「既存候補『…』への **4 事例目**」)

**`(N)` 番号付き 15 件は独立候補**(全件が自前の `- **事象**:` と昇格条件を持ち、下位項目は 1 件も無い)。
ただし**番号体系が 2 つ混在**している — `(1)`/`(2)` は受け皿の種別マーカー(`:2090` が定義)、`(5)`〜`(13)` は通し番号(`:2166` が欠番 `(7)` を項目として参照)。

**索引の「候補 90 件」はどの走査条件でも再現しない。**
`docs/README.md:15` は走査条件を自分で併記している(「走査条件 = `^### (候補)` の見出し数。別に番号付き候補が 16 件ある」)が、
**その条件では 89**。90 の内訳として挙げている接頭辞なしの 4 件は、**その条件にマッチしない**。

### 3. `H-*` の採番規則

**判定表**(台帳 `:174-178`):

| 判定 | 条件 | 扱い |
| --- | --- | --- |
| **候補** | **① 制御目的の典拠なし**(② の評価ができない) | `## 候補` 節へ置き **`H-*` を与えない**。典拠が確認できた時点で昇格 |
| 高 | ① あり かつ ② あり | `H-*` を与える。`対応案` に F-ID + worklog リンク か PO 見送り裁定が必須 |

- **①の定義**(`:170`): 「その機構が『何を止める / 何を検査する』ことになっているかが、**リポジトリ内の記述**(docstring・スキル本文・規約・設計書)で示せる」
- **「実例が N 件たまったら」型の共通規則は無い**(典拠なし)。各候補が自分の昇格条件を個別に書いている
- **採番者を定めた条文は無い**(典拠なし)。先例は 2 系統 — 自分で採番(`:111` H-79 / TSK-448 の H-90)と PO 判断(`:14` `:15` `:127`)

- **H-90 二重予約の申し送りは実在**(`:14` と `:1653-1659`)。**裁定の記録はリポジトリ内に見つからない**
- **分類が `機構の穴` 以外は判定を適用しない**(`:140-141`「`プロセス設計` と `機能した点` は比較判定せず `通常` 固定」)

### 4. 追記の作法

- **主経路**(`:136`): 「`/pr` のクローズ処理。PR 作成者が、クローズ処理の最終コミットを作る前に追記の有無を判断する。該当するなら同一 PR で ① 計画書 3 節へ宣言を先に追記 → ② 本書へ追記 ③ 本書の変更履歴表に 1 行 ④ 索引の最終更新日を現行化(②〜④ は同一コミット)」
- **`/task-done` から編集しない**(`:137`)。本タスクは**その後段の経路**(`/task-done` 後に follow-up を起票し、次の `/task-start` で別 feature/PR)に当たる
- **版は上げない**(`:134`・7.6-3 前段 = 設計書 `:516`)。記載要素・運用規則・分類そのものを変えるときだけ版繰り上げ + 7.3 確定ゲート
- **変更履歴表**: `:7` ヘッダ / `:9`〜`:128` データ行。**最新行は先頭 `:9` に挿入**。状態列は候補の追記なら **`候補`**
- **索引**: `docs/README.md:15`。件数を更新し、直後に `〔<タスク ID> で N 件追記 — <要旨>〕` を**件数のすぐ後ろ(新しいものが前)**へ

#### 書式(代表 3 形式)

既存 87 件の最頻は**箇条書き様式**:

```
### (候補) <命題を 1 文で>

- **分類**: <機構の穴 / プロセス設計 / 検査設計 / 運用の穴 など>
- **検出日**: YYYY-MM-DD(<出所タスク・周回>)
- **事象**: …
- **なぜ問題か**: …
- **同型との関係**: …(既存候補・`H-*` との違いを名指しで)
- **観測の限界**: **1 タスク N 件**
- **候補である理由**: **制御目的の典拠が無い**(…)。**昇格条件**: …
- **対応案**: (a) …(実施済み) (b) …(**未実施** — 正本の改訂になるため別タスク)
```

**直近 4 件(`:4586` ほか)は散文様式**(太字段落 + `####` 小見出し、見出し末尾に日付)。
**どちらで書いても前例があるが、既存 87 件との整合を優先するなら箇条書き様式。**
