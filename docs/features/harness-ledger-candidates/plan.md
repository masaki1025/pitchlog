## 4. 実装方針

**重さ分類 = 通常**。根拠:

- **コア領域に当たらない** — `.claude/core-areas.json` に `docs/development` の言及が無い(実測)。触るのは `docs/development/harness-evaluation.md` / `docs/README.md` / `docs/features/*/research.md` のみで、**コードも contracts も触らない**
- **軽微ではない** — 8 件の追記は分量があり、**既存候補との同型判定という判断**を伴った(③⑤⑦ の帰属を決めるのに計画レビュー 3 周を要した — 4-3 節)
- **機械的軽作業でもない** — 置換や形式変換ではない

### 4-1. 追記の作法(台帳 `:136` に従う)

**同一 PR で ① 計画書 3 節へ宣言(本書で済)→ ② 台帳へ追記 ③ 変更履歴表に 1 行 ④ 索引を現行化。②〜④ は同一コミット。**

したがって**実装ステップは「台帳の一部 + 変更履歴 + 索引」を 1 コミットの単位**とする。
台帳だけ先に書いて後から履歴を足す形にはしない。

### 4-2. 書式 — 箇条書き様式に揃える

**既存の最頻形**([research.md](research.md) 4 節の代表 A)に合わせる。ここでいう **87 は「`## 候補`(`:1403`)以降の `^### (候補)` 見出し数」**であって候補の総数ではない(**2 周目 P2 の是正**。内訳は [research.md](research.md) 2 節)。

```
### (候補) <命題を 1 文で>

- **分類**: <機構の穴 / プロセス設計 / 検査設計 / 運用の穴 など>
- **検出日**: YYYY-MM-DD(<出所タスク・周回>)
- **事象**: …
- **なぜ問題か**: …
- **同型との関係**: …(既存候補・`H-*` との違いを名指しで)
- **観測の限界**: **N タスク M 件**
- **候補である理由**: …。**昇格条件**: …
- **対応案**: (a) …(実施済み) (b) …(**未実施**)
```

**直近 4 件(接頭辞なし見出し)は散文様式だが、接頭辞付き見出し 87 件との整合を優先して箇条書きを採る。**

**実装時の判断に委ねない**(**計画レビュー 1 周目 P1 の是正** — 委ねると最大 5 件を新設できてしまう)。
**下調べ([research.md](research.md) 1 節)は当初 ③⑤⑦ を「要判断」としていたが、本節で全件を確定し、同節も確定後の記述へ同期済みである。**

### 4-4. 件数の扱い — 規則は変えず、再現する値を書く

**索引の「候補 90 件」は、併記された走査条件(`^### (候補)` の見出し数)で再現しない**(その条件では 89)。

**本タスクは走査条件そのものを変えない**(= 運用規則の変更にあたるため・2 節)。代わりに:

1. **実測した走査条件と件数を、再現する形で索引へ書く。** **「候補総数」と読める表現を使わない**(**1 周目 P2 の是正** — `^### (候補)` の 89 には**変更履歴中の 2 件が入り**、番号付き 16・接頭辞なし 4・箇条書き 2 は入らない)。**各値に測定対象を付ける** — 例「接頭辞付き見出し数 N(うち変更履歴表中 2)/ 番号付き見出し M / 接頭辞なし見出し K」
2. **再現しない原因**(2026-09-30 以降の 4 件が接頭辞なし)を **`:3890` の実例として台帳へ記録する**
3. **様式の統一は別タスクとして起票**し、索引からそのタスクを指す
