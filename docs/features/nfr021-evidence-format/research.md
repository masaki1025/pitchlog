## 4. Web 技術調査(Codex `research`・2026-08-19 実施)の要点

**採否の姿勢**: 以下は Codex の報告であり、**4-1 の主張は Claude が本リポジトリの実履歴で追試済み**(3-2 節)。ライブラリの版・メンテ状況は 4-5 の実装時に再確認する。

### 4-1. 差分の取り方(最重要)

- `git diff T C` / `T..C` は**二つのツリーの最終状態の比較**であり「途中で一度でも変更されたか」ではない。変更して元に戻すと最終差分に現れない([git-diff](https://git-scm.com/docs/git-diff)・[gitrevisions](https://git-scm.com/docs/gitrevisions)、公表日不明)
- `T...C` は merge-base と C の比較。**T が祖先でない場合に「証跡以後」を意味しないため失効判定の基準にしない**
- 推奨形: **T が C の祖先であることを先に検証**(`merge-base --is-ancestor`)し、満たさなければ**判定不能 = 失効(fail-closed)**。そのうえで `rev-list T..C` の各コミットについて `diff-tree -r -m --name-status -z --no-renames` の**和集合**を取る
- `-m` が要る理由: **既定ではマージコミットの diff が出ない**。`-c` / `--cc` は「全親から変更されたファイルだけ」を出すため取りこぼしが許されない用途に不適([git-diff-tree](https://git-scm.com/docs/git-diff-tree)、2.55.0 / 2026-06-29 更新)
- `--no-renames` が要る理由: `-M`(既定閾値 50%)は削除+追加を `R old new` に圧縮し、**新パスだけ見る実装は旧パスを見落とす**。類似度判定は設定や規模で結果が変わるため失効検出に不適
- `-z` が要る理由: 空白・改行・引用符を含むパスの安全な解析
- サブモジュールはスーパープロジェクトからは gitlink 1 パスにしか見えない。内部を対象にするなら再帰検査が要る(本リポジトリにサブモジュールは無い)

### 4-2. パターン構文

| 方式 | `*` が `/` を跨ぐか | 評価 |
| --- | --- | --- |
| gitignore 形式(`pathspec`) | 跨がない | **推奨(制限付き)** |
| Git pathspec magic `:(top,glob)` | glob 指定時は跨がない | Git コマンド用。JSON 正本の照合言語には不向き |
| Python `fnmatch` | **跨ぐ**・`**` に特別扱い無し | **不適** |
| ディレクトリ接頭辞一致 | — | 対象が固定ディレクトリだけなら最も安全 |

- gitignore 形式でも**スラッシュを含まない `foo` は任意階層に一致**するため意図せず広くなる([gitignore](https://git-scm.com/docs/gitignore))
- 推奨運用: パターンは必ず `/` 始まり / ディレクトリ全体は `/backend/**` と明記(`backend/` や `backend` を許容しない)/ **`!` 否定は禁止**(失効規則に除外穴を作るアンチパターン)/ 各パターンの「一致すべき・しないパス」を fixture で固定
- `pathspec` は **1.1.1(2026-04-27 公開)**、Production/Stable、maintainer 1 名。`GitIgnoreSpec` が Git の edge case により近いが**完全同一の保証はない**([PyPI](https://pypi.org/project/pathspec/))→ **版を pin し Git との差分 fixture を CI で固定**する

### 4-3. append-only の CI 強制(4-5 向けだが README の運用記述に影響)

- `pull_request` の `GITHUB_SHA` は head ではなく**テスト用マージコミット**。`base.sha` は payload の不変 SHA として使える(ただし「実行時点の base tip」を意味する保証は**不明**)
- **限界**: PR で workflow・検査スクリプトを書き換えれば無効化できる。**ブランチ保護 / required check が無ければ CI は助言にすぎない**。force-push・履歴書換えは Git 内の append-only を破る
- → 本プロジェクトは**ブランチ保護がプラン制約で未導入**(`D:657` 10.2)。README には「CI 検査は補助であり、実効は人間の運用規律」と正直に書く材料になる

### 4-4. 証跡ファイルの形式

- **Markdown + YAML frontmatter・一ファイル完結を推奨**。GitHub Docs が frontmatter を schema 検証する実例([GitHub Docs frontmatter](https://docs.github.com/en/contributing/writing-for-github-docs/using-yaml-frontmatter))。Kubernetes KEP は `README.md` + `kep.yaml` のサイドカー方式
- **形式自体は改ざん検出を提供しない** — Git の SHA・署名・保護された履歴のいずれかが要る
- 既存標準(in-toto / SLSA / SPDX / CycloneDX / TAP / JUnit XML)は **1 名体制・人手判定・Markdown 記録には過剰**。将来 CI が増えたときに「添付 artifact」として参照する設計が現実的
