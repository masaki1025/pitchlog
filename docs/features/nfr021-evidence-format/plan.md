### 設計判断(裁定からの導出)

以下は D-1〜D-7 から機械的に導かれる具体化であり、**新しい方式決定ではない**。

#### (1) JSON の構造(D-2)

10.1「証跡の失効」が「失効しないのは明示 allowlist のみ / どちらにも該当しないパスは fail-closed(失効扱い)」と定めるため、三値を表現する:

- `syntax`: `"gitignore-root-relative-v1"`(構文の宣言。検証器はこの値を検査し、未知なら fail-closed)
- `default`: `"invalidating"`(既定 = 失効)
- `invalidating`: 10.1 の下限 15 件を**ルート相対の明示パス**で列挙 + **`/mise.toml` を追加**(Node 版の正本 — 設計書 5.2・CI も `mise.toml` を正本として解決。10.1 は「少なくとも」= 下限なので追加に改訂は不要)
- `allowlist`: 10.1 の 3 件のみ(**閉じた列挙**。増補は 10.1 の改訂を要する)
- **優先順位**: 両方に一致した場合は `invalidating` を採る(fail-closed)。加えて**両リストが文字列として交差しないことをテストで固定**する

ディレクトリ配下は `/backend/**` の形で書くため、`backend/pyproject.toml`・`frontend/package.json` 等は親ディレクトリのパターンで覆われる。ルート直下にのみ存在するもの(`/pyproject.toml`・`/uv.lock`・`/.python-version`)は個別に列挙する。**`default: invalidating` により未列挙パスも失効扱いになる**ので、列挙漏れは安全側に倒れる — 列挙の役割は 10.1 の下限充足の証明と意図の可読化である。

#### (2) 「差分」の定義(D-1)

設計書 10.1「証跡の失効」行へ次を追記する:

- **`tested_commit_sha`(T)が候補 SHA(C)の祖先でなければ判定不能 = 失効**(fail-closed)
- 失効判定の入力は **T から C までの各コミットの変更パスの和集合**とする。**2 点差分(T と C のツリー比較)を用いない** — 範囲内で作られて消えたパス・変更後に戻されたパスを報告しないため
- **マージコミットは全親との差分に現れる変更パスを和集合へ含める**(既定ではマージコミットの差分が出力されない実装があり、そのままでは「各コミットを見た」と称して空集合を返せてしまう — 計画レビュー 1 周目 P1)
- **リネーム・コピー検出を用いない**(削除+追加として扱う)。類似度判定は設定と規模で結果が変わり、旧パスの取りこぼしを生む
- 実装手段(コマンド・ライブラリ)は本節で固定しない — 検証器の実装(4-5)に委ねる。**4-5 のテストにマージ経由の負例を含めることを申し送る**

**根拠(実証)**: 本リポジトリの実履歴 `HEAD~25..HEAD` で 2 点差分 193 パスに対し和集合 194 パス。差の 1 件は `frontend/src/lib/display_geometry_263_v1.json`(4-1 `2152e78` で追加 → 4-3 `d21620b` で削除。両方が範囲内のため 2 点差分に現れない)。同ファイルは座標契約の逐語移植であり `contracts/` は失効対象そのもの(research.md 3-2)。

#### (3) レコード種別の閉じた命名文法(D-3・計画レビュー 1 周目 P1)

**「結果証跡 = それ以外」という開いた定義にしない** — `README.md` が結果証跡として解析される。README で次を**閉じた文法**として定める:

**すべて `docs/ops/nfr021-acceptance/` の直下ファイルに限る**(サブディレクトリ配下の `.md` は正規形に一致しない = 不正)。

| 種別 | 正規形 | 備考 |
| --- | --- | --- |
| 正本(除外集合) | `README.md` / `reservation-template.md` / `evidence-phase4-template.md` / `evidence-release-template.md` の **4 件のみ**(完全一致) | 索引必須。検証器の列挙対象から除外 |
| 予約レコード | `YYYY-MM-DDTHHMMSSZ-<gate_kind>-<phase4\|vX.Y.Z>-seq<NNN>-reservation.md` | `<NNN>` は `attempt_seq` の**最低 3 桁ゼロ詰め**(1000 以降は桁が増える — `attempt_seq` に上限はない) |
| 結果証跡 | `YYYY-MM-DDTHHMMSSZ-<gate_kind>-<phase4\|vX.Y.Z>-seq<NNN>-<short_sha>.md`(**10.1「保存先・命名」を改訂して `seq<NNN>` を追加** — 3 節) | `<short_sha>` は T の短縮形。`seq<NNN>` により**形式として衝突しない**(`attempt_seq` はゲートキー単位で一意) |
| 上記のいずれにも一致しない `.md`(サブディレクトリ配下を含む) | **fail-closed**(検証器は無視せず不合格にする) | 非正規名の証跡が最新試行の列挙から漏れることを防ぐ |

**字句規則**(計画レビュー 2 周目 P1):

| 要素 | 規則 |
| --- | --- |
| `YYYY-MM-DDTHHMMSSZ` | 秒精度の UTC。区切りは日付部のみハイフン、時刻部は区切りなし、末尾 `Z` 固定 |
| `<gate_kind>` と第 2 要素の組 | **`phase4-phase4` または `release-vX.Y.Z` のみ**(それ以外の組合せは不正) |
| `vX.Y.Z` | `v` + 数値 3 連(セマンティックバージョン) |
| `<short_sha>` | 小文字 16 進の短縮 commit OID |
| `seq<NNN>` | `seq` + 10 進数字 3 桁以上 |

**ファイル名と frontmatter の対応**(検証器が突き合わせる — 4-5 の負例に含める): ファイル名の `<gate_kind>` = frontmatter の `gate_kind` / 第 2 要素 = `phase4` なら `release_version` 不在・`vX.Y.Z` なら `release_version` と一致 / `seq<NNN>` = `attempt_seq` / `<short_sha>` = `tested_commit_sha` の短縮形。

**結果証跡名の一意性は形式で閉じる**(計画レビュー 2 周目 P1 → 3 周目 P1): 現行の 10.1「保存先・命名」が定める形は**秒精度の時刻・ゲート・T の短縮 SHA だけ**であり、**同一の(ゲートキー, T)について同じ秒に 2 件作ると衝突する**。同節は「同日に失敗 → 再実施しても名前が衝突しない**形にする**」と**形式**を要求しているため、**運用規則(未使用の秒を選ぶ)では要求を満たさない**。したがって **10.1 を改訂して結果証跡名に `seq<NNN>` を含める**(3 節)。`attempt_seq` は既存の必須キーでゲートキー単位に一意なので、**新しいフィールドを増やさずに形式として一意性が保証される**。

#### (4) テンプレートの構造(D-4・計画レビュー 1 周目 P1)

テンプレート自身が正本であることと、そこから複写する証跡が正本でないことを両立させる:

- テンプレートファイルの **frontmatter は正本ヘッダ**(`status:` のみのちょうど 3 行 — 7.1-5)、直後に**変更履歴表**を置く
- **複写する本文は「そのファイル内でただ 1 つの」フェンス付きコードブロックの中に丸ごと入れる**(証跡側の YAML frontmatter を含み、**フェンス内容の先頭が `---` で始まる frontmatter であること**)。フェンスを 1 つに限るのは、**テストがどのフェンスを契約とみなすかを一意にする**ため(計画レビュー 2 周目 P1 — 「キーが文字列として現れる」だけの検査は、コメント・表・別フェンスに置いても通ってしまう)。これにより:
  - テンプレートは正本の書式検査を通る
  - **テンプレート内のサンプル値が検証器の frontmatter 解析に拾われない**(コードブロック内のため)— 命名文法((3))と二重に閉じる
- **必須項目はテンプレート「3 枚合計」ではなく 1 枚ごとに満たす**(計画レビュー 1 周目 P1)。テンプレート別の固定対応表:

| テンプレート | 必須項目 |
| --- | --- |
| `reservation-template.md` | 10.1「試行の排他と採番」の **5 項目**(ゲートキー / `attempt_seq` / `attempt_id` / 開始日時 / 実施者) |
| `evidence-phase4-template.md` | 要件書 NFR-021 の**証跡 11 項目** + 機械検証キーのうち **6 個**(`gate_kind` / `tested_commit_sha` / `onboarding_blob_sha` / `result` / `attempt_seq` / `attempt_id`)。**`release_version` を含めない** + Phase 4 完了時の合格項目 **5 行** |
| `evidence-release-template.md` | 同 **11 項目** + 機械検証キー **7 個すべて**(`release_version` を含む)+ リリース候補時の合格項目 **8 行** |

- 機械検証キーは**証跡側の YAML frontmatter**、要件書 11 項目のうち記述が要るもの(実行コマンドと終了コード・期待値と実測値・ログ参照)は**本文の表**に置く
- **候補 SHA の欄を設けない**(10.1「保存先・命名」が本文にもファイル名にも書くことを禁じる)

#### (5) `attempt_id` の生成規則(D-3)

- `attempt_id` = `<ゲートキー>-<attempt_seq の最低 3 桁ゼロ詰め>-<発行時刻 YYYYMMDDTHHMMSSZ>`
  - ゲートキー = `phase4` または `release-vX.Y.Z`(10.1「証跡の必須項目」の定義)
  - 例: `phase4-001-20260819T101500Z`
  - **ゲートキーと `attempt_seq` が ID 自身に埋まる**ため、`attempt_id` とレコード本文の不一致を人間が目視で検出できる(2026-08-11 の申し送り①への対応 — research.md 2 節)
  - **発行主体は 8 章の判定者**(10.1「試行の排他と採番」の採番主体と一致させる)
  - **ゲートキーの表現は 1 つに固定する**: 予約レコード・結果証跡・`attempt_id` のいずれにおいても `phase4` または `release-vX.Y.Z`(別表記を許さない)

**レコード間の一致契約(計画レビュー 4 周目 P1)**: ファイル単体の整合(ファイル名 ↔ 自分の frontmatter)だけでは、**予約が `seq001`・結果が `seq002` なのに同じ `attempt_id` を持つ**組が各レコード単体で通ってしまう。10.1「検証器の契約」は**予約と結果が同じ `attempt_seq` を持つ前提で `attempt_id` により試行へ畳み込む**と定めており、不一致があると「どちらの連番を正とするか」が未定になり、**予約されていない試行を最新試行として扱う余地**が生まれる。したがって README に次を明記する:

> **同一の `attempt_id` を持つ予約レコードと結果証跡では、ゲートキー・`attempt_seq`・(`release` の場合は `release_version`)が**すべて一致しなければならない**。1 つでも食い違えば fail-closed(検証器は対応不能として不合格にする)。**

これは 2026-08-11 の申し送り①(「同一 `attempt_id` 間でゲートキー・`attempt_seq` も一致必須であることをスキーマ化する」)への対応でもある。**新しいキーは増やさない。**

#### (6) 索引の必須/除外集合の規範(D-7)

これは **10.1「文書分類」(個々の証跡は正本ではない = 索引に載せない)から導かれる docs-lint 実装の受入条件**であり、**新しい規範の移管ではない**(計画レビュー 3 周目 P2 — D-1 の限定を参照)。README に次を書き、**実装(`scripts/check_docs_status.py` の変更)は予約レコード監査 PR が行う**:

- `docs/ops/nfr021-acceptance/` 配下のうち、**(3) の正本 4 件は索引必須**
- **予約レコードと結果証跡は索引カバレッジ検査の対象外**(10.1「文書分類」が「個々の証跡は正本ではない」と定めるため)
- 除外は `docs/ops/nfr021-acceptance/` に限定し、`docs/ops/` 全体へは広げない(将来の別文書 — 台帳 H-56 — を巻き込まないため)
- **除外は接頭辞単位にしない**(計画レビュー 2 周目 P1): 現行機構は接頭辞一致で `continue` するため、当該接頭辞を足すだけだと `unexpected.md` や `subdir/foo.md` まで無条件に索引検査から消え、(3) の「正規形以外の `.md` は fail-closed」という規範に反する。**4-5 の検証器が存在しない間に不正な記録が develop へ入ると、後続で恒久的な fail-closed を招く**
- したがって規範は「**直下ファイルであり、かつ予約レコードまたは結果証跡の正規形に一致するものだけを除外する。正本 4 件・未知の `.md`・サブディレクトリ配下の `.md` は索引漏れとして落とす**」とする。**この正負両方のテストを監査 PR の受入条件に含める**ことを README に明記する

### 確定ゲートの扱い(実装ステップ表に含めない理由)

確定ゲート(`/finalize-doc`)の反映周コミットは、AGENTS.md と設計書 6.1 により **`反映<r>周目` だけを含め、ステップ記法を付けない**。したがってステップ表に確定ゲートの行を置くと、**その行に対応するステップコミットが永久に生まれず現在地導出が滞留する**(台帳 H-41・H-45 と同型)。本計画ではステップ表を**実装 4 ステップに限定**し、確定ゲートは表の外の工程として扱う(前例 `docs/features/harness-evaluation/plan.md` はステップに含めていたが、上記の理由で踏襲しない)。
