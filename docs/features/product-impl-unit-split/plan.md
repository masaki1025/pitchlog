# 実装計画書: 製品機能の実装単位を分割する(TSK-363)

## 1. 背景・目的

**Notion**: [製品機能の実装単位を分割する — コア領域に触れる面を小さく切る](https://app.notion.com/p/3d893b75e68781de948bfe5ef4679652)

**backend の製品コードを書く単位が定まっていない。** 実測(2026-09-13・develop `478a026`):
**`backend/src` に FR の振る舞いを実装したものは 0 件**、HTTP は `main.py` の `GET /health` 1 本のみ、
**DTO・バリデーション・エラー処理・ルータは 1 つも存在しない**。

**設計書 13 章**(`dev-harness-design-2026-08-07.md:892-898`)が
「**本節は製品機能の実装について順序・群・段階を定めない**」とし、
**実装単位の数・名称・境界・PR 分割・着手順・見積もり**を
「**実装時(各実装単位のタスク)で確定する範囲**」として保留している(同 `:64`)。**本書がその保留を埋める。**

**なぜ急ぐか**: **切り方が後続タスクの重さを決める**。backend の製品機能はほとんどが
コア領域([FR-034](../../requirements/requirements-pitchlog-2026-07-22.md#FR-034) のテナント分離・
[FR-012](../../requirements/requirements-pitchlog-2026-07-22.md#FR-012) の同期プロトコル・
[FR-013](../../requirements/requirements-pitchlog-2026-07-22.md#FR-013) の記録権・状況計算)に当たり、
**コア領域は敵対レビュー + 人間の逐行確認が必須**で、**逐行確認は並列化できない人的資源**である。
**実測: TSK-317 は計画 5 周 + 実装 6 周。大きく切ると全部がコア領域になり、1 本ごとに同じ周回がかかる。**

**下調べ**: [research.md](research.md)(264 行・全事実に典拠)。**本書へ内容を複製しない**(設計書 7.1-1)。

**最重要の発見**: **`data-model.md` 12-4 は「マージ条件」であって「着手条件」ではない**
(逐語は「**マージまたは有効化しない**」— `:2428`)。**着手を縛る条文は 6.1 の計画書ゲートと
ADR-003 の 4 段階の 2 本だけ**で、後者は **[NFR-018](../../requirements/requirements-pitchlog-2026-07-22.md#NFR-018)
の対象計算に触れる単位にのみ**掛かる。

## 4. 実装方針

### 重さ分類 = **通常**(コア領域ではない)

**根拠**: **成果物がコードでも正本でもない**。`docs/features/**` と `docs/worklog/**` しか変更せず、
これらは `/pr` の正本突合から除外される。**`.claude/core-areas.json` の機械判定にも当たらない**。
→ **敵対レビューも人間の逐行確認も掛からない。**

### 分割の軸 — **強制点(enforcement point)の数で測る**

**単位の大きさを FR の数で測らない。「その単位が新設するコア領域の強制点の数」で測る。**

- 強制点 **1** = **核**(敵対レビュー + 逐行確認 1 周)
- 強制点 **0** = **葉**(通常レビュー・並行可)

**不変条件: 1 単位が抱えるコア領域は 0 か 1。2 にしない。**

| 却下した軸 | 根拠 |
| --- | --- |
| **FR 単位(42 本)** | テナントデータを返す FR はすべて 6.3 テナント分離「含む」欄の**全出力経路の越境(API 直叩き)**に当たる。**逐行確認 42 周**になり本タスクの目的が消える |
| **機能ブロック単位** | ブロック 1(記録)だけで sync-protocol + recording-rights + game-state の**3 領域**に跨る |
| **レイヤ単位のみ** | 「全 FR の DTO」は大きすぎ、既存 ORM と混在した瞬間に 6.3-② の**混在ファイルはファイル全体を含む**でコア化 |

**採用**: **第 1 軸 = コア領域面 → 第 2 軸 = レイヤ → 第 3 軸 = FR 群**の混成。

### 非コアで通せる 4 条件

**U-00 / U-01 / U-M1 / U-M2 / U-G1 / U-G2 / U-D1 / U-P1 の 8 単位**(+ U-C2 は降格候補)。
**各単位の計画書の「やらないこと」に逐語で書き、U-T1 の迂回検査で機械化する**:

1. 新たな**認可判定**を追加しない(**U-T1 の束縛を必ず経由する**)
2. **同期セマンティクス**(べき等キー・連番・墓標/改訂)を扱わない
3. **`NFR-018` の対象計算**を 1 行も含まない
4. **キャッシュ無効化契約**に触れない

**残る留保**: 4 条件を満たしても**テナントデータは返る**。**U-T1 の PR で
「束縛を経由する読み書きは新たな越境面を作らない」ことを PO に一度だけ確定させる**
(個別 FR ごとに 8 回問わない)。**取れなければ帯 2 は全部コアになる。**

### 着手順

**直列資源は逐行確認者 1 人。「コア単位は同時に 1 本」が唯一の全順序制約。**

```
段0(並行)  U-00 ─┬─ U-01
                  └─ U-02
段1(直列)  U-T1 → U-S1 → U-R1
段2(並行)  U-M1 ─ U-M2 / U-G1 ─ U-P1 / U-G2 / U-D1   ← 逐行確認不要
段3(直列)  U-A1 → U-A2 → U-C1 → U-C2 → U-C3 → U-D2
段4(凍結)  U-X1 → U-X2 → U-X4 ; U-X3(文書先行) ; U-X5
```

- **並行できる**: 段 0 の 3 本 / 段 2 の 6 本 / **段 2 と段 3**(段 2 は通常レビューなので資源が衝突しない)
- **並行できない**: 段 1 内部・段 3 内部・**段 1 と段 3**(同じ逐行確認者)
- **着手と完了を分ける**: **12-4 はマージ条件**なので、U-T1 以降は**実装・レビューまで進めて
  「マージ待ち行列」に置く**。**待ち行列の深さが 3 に達したら新規葉の着手を止める**
