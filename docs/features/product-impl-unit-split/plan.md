# 実装計画書: 製品機能の実装単位を分割する(TSK-363)

## 1. 背景・目的

**Notion**: [製品機能の実装単位を分割する — コア領域に触れる面を小さく切る](https://app.notion.com/p/3d893b75e68781de948bfe5ef4679652)

**backend の製品コードを書く単位が定まっていない。** 実測(2026-09-13・develop `478a026`):
**`backend/src` に FR の振る舞いを実装したものは 0 件**、HTTP は `main.py` の `GET /health` 1 本のみ、
**DTO・バリデーション・エラー処理・ルータは 1 つも存在しない**。

**設計書 13 章**(`dev-harness-design-2026-08-07.md:892-898`)が
「**本節は製品機能の実装について順序・群・段階を定めない**」とし、
**実装単位の数・名称・境界・PR 分割・着手順・見積もり**を
「**実装時(各実装単位のタスク)で確定する範囲**」として保留している(同 `:64`)。**本書がその保留を埋める。**

**なぜ急ぐか**: **切り方が後続タスクの重さを決める**。backend の製品機能はほとんどが
コア領域([FR-034](../../requirements/requirements-pitchlog-2026-07-22.md#FR-034) のテナント分離・
[FR-012](../../requirements/requirements-pitchlog-2026-07-22.md#FR-012) の同期プロトコル・
[FR-013](../../requirements/requirements-pitchlog-2026-07-22.md#FR-013) の記録権・状況計算)に当たり、
**コア領域は敵対レビュー + 人間の逐行確認が必須**で、**逐行確認は並列化できない人的資源**である。
**実測: TSK-317 は計画 5 周 + 実装 6 周。大きく切ると全部がコア領域になり、1 本ごとに同じ周回がかかる。**

**下調べ**: [research.md](research.md)(264 行・全事実に典拠)。**本書へ内容を複製しない**(設計書 7.1-1)。

**最重要の発見**: **`data-model.md` 12-4 は「マージ条件」であって「着手条件」ではない**
(逐語は「**マージまたは有効化しない**」— `:2428`)。**着手を縛る条文は 6.1 の計画書ゲートと
ADR-003 の 4 段階の 2 本だけ**で、後者は **[NFR-018](../../requirements/requirements-pitchlog-2026-07-22.md#NFR-018)
の対象計算に触れる単位にのみ**掛かる。

## 4. 実装方針

### 重さ分類 = **通常**(コア領域ではない)

**根拠**: **成果物がコードでも正本でもない**。`docs/features/**` と `docs/worklog/**` しか変更せず、
これらは `/pr` の正本突合から除外される。**`.claude/core-areas.json` の機械判定にも当たらない**。
→ **敵対レビューも人間の逐行確認も掛からない。**

### PO 裁定 — **13 章の射程宣言との衝突**(2026-09-13・山田正輝)

**2 周続けて同じ `P0` が出た。直し方が計画書の中に存在しないため PO へ上げた。**

**衝突の中身**: 設計書 13 章の射程宣言は「**実装単位の数・名称・境界・PR 分割・着手順・見積もり**」を
「**実装時(各実装単位のタスク)で確定する範囲**」とする。**本タスクはメタタスクなので、
23 単位を確定しカードを起票する行為そのものが射程宣言に触れる。**

**厳密に読むと循環する** — **「各実装単位のタスク」は単位が定義されないと存在できない**のに、
**単位の定義が「各実装単位のタスク」の仕事**とされている。**誰も最初の 1 歩を踏めない。**

**裁定**: **カードを優先する。** **13 章の射程宣言は循環するので、
最初の 1 回だけメタタスクが単位を定義してよい。** **正本は改訂しない**(確定ゲートを払わない)。

**この裁定の射程**:

| 本タスクがやってよいこと | 本タスクがやらないこと |
| --- | --- |
| **単位の数・名称・境界を確定する** | **着手順を拘束力のある形で定める**(**非拘束の推奨に留める** — 1 周目 `P0-1`) |
| **コア領域判定を記録する** | **PR 分割を確定する**(**各単位の計画書が決める**) |
| **Notion カードを起票する** | **見積もりを確定する** |
| **依存関係を記録する** | **群・段階を正本へ書く** |

**衝突は記録として残す。** **13 章の改訂が要ると判断されたら、それは別タスクの確定ゲートである。**

### 分割の軸(**1 周目 `P0-4` で主張を差し替えた**)

**当初は「強制点の数で切ると FR 単位より面が小さくなる」と主張したが、これは成立しない。**
**実測(逐行確認の回数)**:

| 6.3 の読み | FR 単位 | 本案(23 単位) |
| --- | --- | --- |
| **A. 「全出力経路の越境」をそのまま読む**(強制点の再利用を認めない) | **42 回** | **23 回**(理由は単位数が少ないことだけ) |
| **B. U-T1 の強制点を経由すれば葉は非コア** | **9 回** | **10 回**(**本案のほうが多い**) |

**どちらの読みでも「強制点で切ると面が小さくなる」は言えない。**
**U-T1 の強制点を再利用できるなら、同じ理屈は FR 単位の分割にも使える**(1 周目 `P0-4` の指摘どおり)。

**したがって本案の根拠を次の 3 点へ置き換える。逐行確認の回数は根拠にしない。**

| # | 本案の実際の価値 | 典拠 |
| --- | --- | --- |
| **1** | **器を核から外す** — 機能丸ごと 1 タスクにすると**器も逐行確認の対象になる**。器は**現在 1 行も存在せず**(実測)、**新規作成の単位として独立に通せる** | カードの設計目標・`core-areas.json` の機械判定(`api/` は非コア) |
| **2** | **PR のサイズ**(**3 周目 `P1` で閾値を撤回し、起動条件へ置き換えた** — 下記) | `contracts/authz/route-registry.json`・develop のマージ実績 |
| **3** | **凍結境界の分離** — **付録 A・E が未整備でドメイン計算は実装開始が禁じられている**(要件書 `:891` の fail-closed)。**面を切らないと、FR-010 / 007 / 011 の非計算部分まで凍結側へ落ちる** | 要件書 `:891`・`:915`・ADR-003 `:388` |

#### PR サイズ(**3 周目 `P1` で閾値を撤回**)

**「35 ファイル」という閾値は実測と一致しなかった**(`PR #50` = **12 ファイル 13,795 行** /
`PR #52` = **89 ファイル 22,895 行** — **ファイル数と行数が相関しない**)。**単一の閾値は置かない。**

**代わりに「分割の検討を起動する条件」を置く** — **[design.md](design.md) 5 節が正**。
**本書は分割を確定しない**(**PR 分割は 13 章が各実装単位のタスクへ残した範囲**)。

**却下した軸と、その理由(1 周目の指摘を受けて書き直した)**:

| 軸 | 却下理由 |
| --- | --- |
| **FR 単位(42 本)** | **逐行確認の回数では優位が無い**(上表)。却下理由は **PR サイズ**である — **FR-041 を 1 単位にすると 3 種の経路(`management_operation` 8 / `control_read` 4 / `shared_data` 12)を 1 PR で抱え、[design.md](design.md) 5 節の起動条件 3 つすべてに掛かる**。**FR-038 も掛かる見込みだが、凍結中なので本書では分けない**(上記) |
| **機能ブロック単位** | ブロック 1(記録)だけで sync-protocol + recording-rights + game-state の**3 領域**に跨る。**1 単位 = 1 領域**(下記の不変条件)を破る |
| **レイヤ単位のみ** | 「全 FR の DTO」は大きすぎ、既存 ORM と混在した瞬間に 6.3-② の**混在ファイルはファイル全体を含む**でコア化 |

### 不変条件(**1 周目 `P0-3` で改めた**)

**1 単位が抱えるコア領域は 0 か 1。ただし設計書 6.3-③ が重複帰属を明記する範囲は例外とし、
本書で明示列挙する。**

**6.3-③ の逐語**: 「**領域間の paths 重複を許す**(重複帰属)」。
したがって**重複帰属そのものは違反ではない**。**違反は「重複を黙って持つこと」である。**

**現時点で 5 件**(`U-S1` / `U-R1` / `U-X1` / `U-X2` / `U-D2`)— **[design.md](design.md) 4-3 が正**。

**例外を増やさないための検査**(**2 周目 `P0-2` の再発防止**): **新しい単位を足すときは、
その単位が主所有する FR を 6.3 境界定義表の 5 領域すべてに当て、2 つ以上に該当したら
例外として明示列挙するか、単位を分ける。** **黙って 1 つに寄せない。**

### FR の帰属(**[design.md](design.md) が正** — PO 裁定 2026-09-13 で分離)

**計画レビューが 3 周とも `P0` を 3 件以上出し、3 周目の `P0` 2 件は「非起因」**
(**設計に元からあった穴が新しく見つかった**)。**根本原因は、計画書の中で
「42 FR の帰属が完全であることの証明」を書こうとしていたこと**である。
**判定は 42 FR × 5 領域 = 210 セル**あり、**目視で当てると取りこぼす**(**3 周で 5 件取りこぼした**)。

**TSK-317 の裁定 `D-19` と同じ手を採る** — **計画書は契約を持ち、帰属の導出は `design.md` が持つ**。

**本書に残す契約**:

| # | 契約 |
| --- | --- |
| **1** | **主所有は FR ごとにちょうど 1 単位**。**多重集合で検算する**(`set` では重複を検出できない) |
| **2** | **分担には面の名前を必ず書く**。**経路予約は所有と分離する** |
| **3** | **2 領域以上に帰属する単位は、例外として明示列挙する**(6.3-③ が重複帰属を許す)。**黙って 1 つに寄せない** |
| **4** | **完全性は TSK-363 が証明しない** — **各単位の計画書が、自分が主所有する FR について 5 領域すべてに当てた結果を書く** |
| **5** | **どの単位にも属さない横断要求**(物理削除しない・テナント分離を全機能に適用 ほか)**は、各単位の DoD へ「破っていない」として入れる** |

**現時点の帰属表・重複帰属 5 件・PR サイズの見積もり条件は [design.md](design.md) が正。**

### 1. FR の帰属が一意であること(**多重集合で数える** — 1 周目 `P0-2`)

**`design.md` 4-1 の表を読んで数える**(**表の写しを検証スクリプトへ二重に書かない** — 7.1-1)。

```bash
uv run python - <<'EOF'
import collections, pathlib, re
rows = [l for l in pathlib.Path("docs/features/product-impl-unit-split/design.md")
        .read_text(encoding="utf-8").splitlines() if re.match(r"^\|\s*`?U-", l)]
owned = []
for l in rows:                                   # | 単位 | 主所有 FR | ... |
    cells = [c.strip() for c in l.strip("|").split("|")]
    owned += re.findall(r"\b0(\d\d)\b", cells[1]) if len(cells) > 1 else []
c = collections.Counter(f"0{x}" for x in owned)
expected = {f"{n:03d}" for n in range(1, 43)}
assert set(c) == expected, sorted(expected ^ set(c))
assert max(c.values()) == 1, [k for k, v in c.items() if v > 1]
print(f"主所有 {sum(c.values())} 件・一意・欠番 0")
EOF
```

### 2. 単位ごとのコア領域数(**測る時点に注意** — 1 周目 `P1`)

**`core_guard.matched_paths` は領域 ID を返さない**(`CoreAreas` が 5 領域を 1 本の
`path_patterns` へ平坦化する)。**領域別に数えるには `core-areas.json` を直接読む。**

**さらに測る時点が 2 つある**:

| 時点 | 何が分かるか |
| --- | --- |
| **登録前**(現在の `core-areas.json`) | **新設パスはすべて非コア**。**器が非コアで通せることの確認**にはなる |
| **登録後**(各核単位が自 PR で登録したあと) | **不変条件(0 か 1)の確認**。**本タスクでは測れない** |

**したがって本タスクの機械検証は「登録前」だけで、不変条件は本書の表で担保する。**
**実際の検証は各核単位の PR(6.3 規則⑤ の敵対レビュー + 人間承認)が行う。**

```bash
# 登録前の確認 — 器と葉の代表パスが現時点で非コアであること
uv run python - <<'EOF'
import fnmatch, json, pathlib
cfg = json.loads(pathlib.Path(".claude/core-areas.json").read_text(encoding="utf-8"))
def areas_of(path):
    return [a["id"] for a in cfg["areas"]
            if any(fnmatch.fnmatchcase(path, p) for p in a["paths"])]
for p in ["backend/src/pitchlog/api/app.py", "backend/src/pitchlog/api/errors.py",
          "backend/src/pitchlog/api/schemas/base.py",
          "backend/src/pitchlog/api/routes/players.py",
          "backend/src/pitchlog/services/players.py"]:
    print(p, areas_of(p) or "非コア", "guard" if p in set(cfg["guard_paths"]) else "")
EOF
```

**実測(2026-09-13)**: 上記 5 パスはすべて**非コア・`guard_paths` 該当なし**。
