# 詳細設計: FR → 実装単位の帰属と、コア領域の判定

**計画書 4 節から参照される。本書が帰属の正である**(計画書へ内容を複製しない — 設計書 7.1-1)。

## 1. なぜ分離したか(**PO 裁定 2026-09-13・山田正輝**)

**計画レビューが 3 周とも `P0` を 3 件以上出し、しかも 3 周目の `P0` 2 件は「非起因」**
(**私が直した結果ではなく、設計に元からあった穴が新しく見つかった**)。

**根本原因**: **計画書の中で「42 FR の帰属が完全であることの証明」を書こうとしていた。**
**FR を単位へ写像するたびに、6.3 の 5 領域と `NFR-018` の (α)(β) との交差が新しく見つかる。**
**1 件潰すと次の交差が出る。**

**判定は 42 FR × 5 領域 = 210 セル**あり、**各セルは 6.3 の境界定義表の逐語を当てる判断**である。
**目視で当てると取りこぼす**(**実際 3 周で 5 件取りこぼした** — `U-D2` / `U-X2` / `U-S1` / `U-R1` / `U-X1`)。

**TSK-317 の裁定 `D-19` と同じ構造**なので、同じ手を採る:
**計画書は契約(単位の定義・地雷・非コアの条件)を持ち、帰属の導出は本書が持つ。**

## 2. 完全性を誰が示すか(**収束の機構**)

**TSK-363 が 210 セルすべてを証明しない。** **示せないことを認める。**

| 主体 | 示すこと |
| --- | --- |
| **本書(TSK-363)** | **判定の方法**と、**現時点の帰属表**、および**重複帰属として検出できたもの** |
| **各単位の計画書** | **自分が主所有する FR について、5 領域すべてに当てた結果**。**2 領域以上なら例外として明示列挙するか単位を分ける** |
| **各核単位の PR** | **`core-areas.json` への登録**(6.3 規則⑤ の敵対レビュー + 人間承認) |

**これにより、本書の帰属表が不完全でも後続で検出できる。**
**本書の役割は「方法を固定すること」であって「完全性を証明すること」ではない。**

## 3. 判定の方法(**目視で当てない**)

### 3-1. 入力

| 入力 | 何を決めるか |
| --- | --- |
| **設計書 6.3 の境界定義表** | **5 領域それぞれの「含む」「含めない」の逐語**。**意味範囲の正** |
| **要件書 `NFR-018` の対象列挙**(`:888-891`) | **(α)(β) の区分**。**どの FR がドメイン計算に触れるか** |
| **`data-model.md` 12-5**(`:2448-2495`) | **E / D / N / 送 の区分**。**永続化の有無** |
| **`contracts/authz/route-registry.json`** | **経路の実数**。**PR サイズの見積もりに使う** |
| **`.claude/core-areas.json`** | **機械判定**。**ただし新設パスは未登録なので「登録前」しか測れない** |

### 3-2. 手順(**1 FR につき 5 回当てる**)

1. **6.3 の 5 領域それぞれの「含む」欄に、その FR 番号または該当する概念が現れるか**を当てる
2. **現れたら、その領域へ帰属**する
3. **2 領域以上に帰属したら、重複帰属として明示列挙する**(6.3-③ が重複帰属を許す)
4. **「含めない」欄に該当する場合だけ、非コアの候補**とする
5. **迷ったら含む側に倒す**(6.3「**判定に迷うコードは含む側に倒す**」— fail-closed)

### 3-3. **目視で当てない**ための実行可能な形

**5 領域の「含む」欄から FR 番号を機械抽出し、突合する。**
**概念で書かれていて FR 番号が無い行**(例: 「全出力経路の越境」)**は、
その概念に該当する FR を人が判断し、判断の典拠を本書へ書く。**

**機械で取れる分と、人が判断した分を分けて記録する。**

## 5. PR サイズの見積もり(**閾値は置かない**)

**3 周目 `P1` で「35 ファイル」という閾値が実測と一致しないことが判明した。**
**実測をやり直した結果、ファイル数と行数が相関しない**:

| PR | ファイル | 行 |
| --- | --- | --- |
| #50 | **12** | **13,795** |
| #52 | **89** | **22,895** |
| #55 | **89** | **29,507** |
| #57 / #60 | 35 | 2,740〜3,962 |
| #59 | 16 | 5,393 |

**→ 単一の閾値は置けない。** **代わりに「分割の検討を起動する条件」を置く**:

| 条件 | 根拠 |
| --- | --- |
| **経路が 10 本を超える** | `U-C3` = 12 経路 / `U-C1` = 8 経路。**経路数は route-registry で機械的に数えられる** |
| **主所有 FR が 5 件を超える** | `U-X1` = 13 / `U-X2` = 6 |
| **越境テストの受取 owner が 20 を超える** | **`FR-041` は 74 owner**(TSK-367 実測・全体の 48.7%) |

**いずれかに当たったら、その単位の計画書が分割を検討する。**
**本書は分割を確定しない**(**PR 分割は 13 章が各実装単位のタスクへ残した範囲**)。

### 5-1. **`FR-041` の偏り**(TSK-367 実測)

**152 論理 ID のうち 74 件(48.7%)が `FR-041` へ行く。** 理由は 3 つ:

1. **`FR-034` の受け入れ基準 4 見出しがすべて `FR-041` の入口に掛かる**。
   要件書 `:602` が「**`FR-041` が新設する権限・経路によって得られるアクセスは、
   下の許可リストに明示的に列挙されたものだけである**」と射程を明示しており、
   **`FR-034` 自身は入口を持たない**。**`FR-034` の 51 owner のうち 48 が `FR-041` へ**
2. **SECTION-3 の用語定義群**(付与の単位・粒度 3 種・既定すべて非共有・参照のみ・同時比較の上限)が
   **`FR-041` の入口で執行される**
3. **APPENDIX-ITEM-A-5 の共有指標の列挙**も `FR-041`

**`route-registry.json` の 37 経路のうち 24 本が `FR-041` 系**(`SHARED` 12 / `CONTROL` 4 / `MANAGEMENT` 8)。

**`U-C1` / `U-C2` / `U-C3` の 3 分割では足りない可能性が高い。**
**TSK-367 が提示した分割の手がかり**(いずれも要件書の見出しに対応):

- 共有の認可(`FR-034` heading-001/002/003 由来)
- 制御資源の読み取り粒度(`FR-034` `:661` 由来)
- 共有集計エクスポートの出力契約(`FR-034` `:685` 由来)
- 撤回の経路と効果(`FR-034` `:703` 由来)
- 7 つの制御資源操作

**さらなる分割は `U-C1` の計画書が判断する。**
