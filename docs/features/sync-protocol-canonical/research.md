## 結論(要約)

**候補案は正本化の前に是正が要る。** 13-3 が「検証が薄い」と自己申告した 4 領域すべてに具体的な伝播漏れ・不整合が実在し、**表間突合だけで 20 件**を検出した(うち 10 件が「表 A の変更を表 B へ写していない」型 = 前タスクが検査を持たなかった型)。加えて**要件の射程を超える記述が 3 件**(D1 の用途・墓標の定義・NFR-019 の種別取り違え)あり、**放置すると approved 文書が要件を超える**。

**U-1 は「要件改訂が要る」で確定**した(要件書に原本喪失による gap の行は不在)。**U-6 は規定の「不在」を確認**(CI 配線のみ受け取り先が特定でき、台帳 H-57 が追跡中)。**U-9 は粒度が判明**し、要件書側で網羅を証明できるのは**条・章節・付録項番・条内小項**まで(受入基準は無採番)。

**手続き面は確定**。`docs/design/` は 7.2 で確定ゲート必須の置き場で、本タスクがその**初号**。新設は 7.6-3 後段 → **7.3 のフルゲート**。過去 16 件の実績は **2〜25 周**で、「収束しないまま approved にした前例は存在しない」。

**旧システムからの構造制約は無い**(同期・記録権・キュー・境界結果はいずれも旧に対応物なし)。ただし旧が実装で持っていた安全装置(再計算の対象範囲の限定)に、候補案が対応物を持たない。

### B. 要件との突合(Q1〜Q4)

#### B-1. U-1(墓標の用途)— **要件改訂が要る**(結論 (b))◎

要件書で「墓標」に相当する記述は **3 箇所のみ**:

| 行 | 位置づけ | 内容 |
| --- | --- | --- |
| 要件書 `:14` | 変更履歴 v1.4 行(**非規範**) | 「同期プロトコル厳密化(墓標・世代内連番・原子性)」 |
| 要件書 `:290` | **FR-012 受入基準 — 唯一の定義** | 「Given 途中の1件がサーバーに**内容起因で拒否された** / … (b) **破棄** — **墓標イベント**(当該連番を正式に消費する空イベント)として送信する」◎ |
| 要件書 `:909` | NFR-019(d) | CI の故障系テストに「墓標/改訂の適用」を含める、とだけ書く |

- 定義は `:290` の **1 箇所だけ**。その Given は「**内容起因で**拒否された」であり、**同じ行が記録権拒否を「内容の編集では解決できないため別カテゴリ」として明示的に墓標経路から外している** ◎ → **拒否の種類によって墓標が使えるか変わることが条文自体に書かれており、未送信原本の喪失という第三の事由は列挙外**
- FR-012 受入基準(要件書 `:283`-`:294` の 12 行・**無採番**)で gap に触れるのは 2 行のみ ◎ — `:286`「**連番に欠落があればそれ以降を適用しない**(prefixコミット)」= **停止のみを定め解消手段を書いていない**、`:290` = 上記
- 端末側喪失は 9 章 R-2(要件書 `:1019`)が「未同期キューは…**断中の端末故障・ブラウザデータ消去で失われ得る**／**受容**」と**受容済みリスク**として記録するにとどまり、**失われた後に prefix をどう前進させるかは書かれていない**

**最小改訂案**(採否は要件改訂ゲートの領分): FR-012 受入基準に 1 行追加 —「Given 未送信イベントの原本が端末から失われ、連番に恒久的な欠落が生じた / When 操作者または管理者が確認 / Then 当該連番を**墓標**として消費し prefix を前進させられる」。あわせて `:290` の墓標定義を「内容起因で拒否された」限定から切り離すか射程注記を足すかの選択が要る(**定義が 1 箇所しかないため、どちらかを触らないと二重定義になる**)。

**先回りリスク**: 候補案は既に **2-1 の D6 定義**(`design.md:46`)を「**拒否された**イベントの同期連番を正式に消費する空イベント」と書き、要件の「内容起因で」を落としている ◎。**U-1 は 6-4 の未解決事項に閉じておらず、定義節そのものに射程拡大が埋め込まれている**。

**`CI-*`(引用の意味ズレ・射程過大 11 件)と `LG-*`(旧システム 5 件 + 前タスク `research.md` の典拠不一致 3 件 = **8 件**)はすべて人間照合対象**である(計画レビュー 7 周目 P1-4・12 周目 P0-1)。**したがって全体は 39 件 = 機械 16 / 人間 23**(`SP-*` 4 + `CI-*` 11 + `LG-*` 8)。**引用が主張を支えているか**・**記述が旧システムの原典と一致するか**はいずれも意味の判断であり、機械では落ちない。

**人間照合対象を機械化できないこと(計画レビュー 9・10 周目)**: **アンカー文字列方式も構造化不変条件方式も成立しない**。「引用が主張を支えているか」「記述が原典と一致するか」は**意味の判断**であり、機械化するには**正しい文章を全文固定するしかなく、それは検査ではなく第二の正本になる**。また**是正の前に「是正後のアンカー」は書けない**(時系列の矛盾)。したがって **`CI-*` と `LG-*`、および `SP-04`・`SP-05`・`SP-15`・`SP-17` は機械検証の対象にしない** — **各是正ステップでの原典照合と、確定ゲートの人間の逐行確認が担保**である。**本節が正とするのは「機械 16 / 人間 23」の内訳だけ**であり、検証方式は計画書 4 節が正。

**⑧ の扱い(計画レビュー 6 周目 P0-2)**: **⑧ は「最初に人間が期待要素として発見するが、マニフェスト化後は機械回帰対象」**である。**「T 要素表にそもそも無い要素」を機械が自力で気づくことはできない**が、**外部マニフェストの要素 ID の期待全集合へ「べき等キーごとの確定結果と一時 ID 写像の保存」を載せた時点で、以後は機械が欠落を検出できる**。**D-5 が要素 ID の期待全集合を持たせる狙い(全表からの同時欠落を捕まえる)と両立させるには、⑧ を機械検出対象に数える**。したがって **fixture に対する機械検出の期待は 16 件**(①②③⑥⑦**⑧**⑨⑩⑪⑫⑬⑭⑯⑱⑲⑳)である。

**全体の内訳(計画レビュー 12・13 周目で確定)**: **39 件 = 機械 16(すべて `SP-*`)/ 人間照合 23(`SP-*` 4 + `CI-*` 11 + `LG-*` 8)**。`LG-*` は **C-3 の旧システム関連 5 件 + 前タスク `research.md` の典拠不一致 3 件**。

### F. Web 調査: 保証対象ブラウザで主タブの一意選出は常に成立するか(U-2)

**問い**: NFR-020 の保証対象(iPad Safari / Chrome / Edge の最新版)で、同一オリジンの複数タブから主タブを一意に選出する機構が**常に**利用可能か。成立するなら U-2 は保証対象外環境に限定され、要件の射程外になる。

**結論: 言い切れない。保証対象ブラウザ上に、選出が成立しない具体的な条件が実在する。**

| 条件 | 内容 | 典拠 |
| --- | --- | --- |
| **Safari の Lockdown Mode** | Apple は **Safari 17 の Lockdown Mode で Web Locks API を無効化した**と明記。Safari 26.6 までのリリースノートに**再有効化の記載を確認できない**(現行の実機動作は**不明**)。**一度明示的に無効化され、現行文書に利用保証がない**以上「常に使える」とは断定できない | [Safari 17 Release Notes](https://developer.apple.com/documentation/safari-release-notes/safari-17-release-notes?changes=latest_minor) |
| **通常モードとプライベートモードの併用** | **選出範囲(storage key / partition)が分かれる**ため、同じ試合を両モードで開くと**主タブが 2 つ立つ**。別プロファイル・ゲストプロファイルも同様 | [WHATWG Storage Standard](https://storage.spec.whatwg.org/) |
| **旧主タブのフリーズ**(終了ではない) | ロックが解放されず、待機側が記録を始められない。**Web Locks が「安全な排他」を維持した結果、NFR-007 側が止まる**。`steal` を使うと旧コードの実行が止まらないため FR-012 を破り得る | [MDN Web Locks API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API) |
| **非セキュアコンテキスト / opaque origin** | 仕様上 `request()` が `SecurityError` になる | [W3C Web Locks](https://w3c.github.io/web-locks/) |

**利用可能な範囲**(上記に当たらない場合): **Web Locks API は iPad Safari 15.4 以上・Chrome・Edge で利用可能**。**名前付き exclusive lock を正本とし、全タブを待機キューに入れる方式**で一意選出できる(`steal` は使わない)。

**代替機構は単独では成立しない**:

| 機構 | 判定 |
| --- | --- |
| **BroadcastChannel** | 通知には使えるが、**合意アルゴリズムが別途要る**(単独では一意選出にならない) |
| **SharedWorker** | **iOS Safari が未実装**。代替にできない |
| **localStorage のリース** | `storage` イベントは**自タブへ通知されず配送も非同期**。**バックグラウンドタブのタイマー停止でリースが期限切れになり split-brain** を起こす。**Must の排他保証には不十分** |
| **Service Worker の `clients.matchAll()`** | **その時点のスナップショット**であり原子的でない。初回ロード時は未制御・アイドル時に終了され状態を失う |

**調査が示した第 3 の道**: 「FR-012 が通常/プライベート・別プロファイル・partition 分離まで含む、またはフリーズ時にも NFR-007 を絶対維持するなら、**ブラウザ内選出だけでは不足**。その場合は**サーバー側の writer epoch / fencing token / 記録権検証を併用**しない限り、単一書き手と停止しないを同時に保証できない」。

**Claude の評価**: 本書は既に**記録権世代(D4)と世代内の連番一意性・退避**の機構を持つ。**サーバー側の裁定へ寄せる形は、その機構の延長線上にある**。ただし**同一世代内での二重書き手の裁定規則は候補案に無く、新規に設計する必要がある**(候補案は「D1 の衝突は正史を壊す」とだけ述べる)。**断中はサーバーが不在**のため、断中に選出が破れた場合の裁定は復帰同期の時点になる。
