候補案 13-4 が「**本節を読まずに本書の形を採ってはならない**」と明記している。起草の敵対レビューは **3 周で P1 が横ばい**となり、**各周で前周の是正が新しい不整合を生む構造**(台帳 **H-78** の型)が続いたため、**人間の判断(2026-08-28)で候補案として閉じた**。[research.md](research.md) の調査で、**13-3 が「検証が薄い」と自己申告した 4 領域すべてに具体的な伝播漏れが実在すること**が確認された。

#### 要件書 v2.4 の改訂範囲(**U-2 分のみ・3 変更束 / 4 本文箇所** — すべてステップ 2 で原子的に行う)

| # | 条 | 内容 |
| --- | --- | --- |
| ① | **FR-012** 受入基準 | **E0** 「操作の受理」とは、記録権を持つ主タブが端末内の永続キューへ同期連番とともに不可分に追記した時点をいう / **E1** 例外は「主タブが exclusive lock を保持したまま停止し、まだ終了していない間」に限る / **E2** その間、非所有タブは入力を**操作として受理しない** / **E3** 記録不能であることと旧タブを終了する導線を明示する |
| ② | **NFR-020** 動作環境 | **6 つの前提**を明記 — トップレベルの HTTPS 表示 / 同一ブラウザプロファイル / 同一ブラウジングモード / **同一 storage bucket(= 同一 private browsing session)** / サイトストレージ利用可 / **Lockdown Mode 非適用**。**Web Locks の lock manager は storage bucket 単位**であり、**仕様は private browsing session を別 user agent として扱う**ため、**「同一モード」だけでは同一 bucket を保証しない**(14 周目 P0-4)。**別 bucket では双方が exclusive lock を取得でき、キューも共有されない** |
| ③ | **NFR-019(d)** 故障系テスト | **E5** 「主タブのフリーズ → 旧タブ終了 → 再選出 → キューを保持したまま記録再開」/「待機中の入力非受理と、その顕在化」/「**主タブで永続追記が失敗したとき、受理成功として表示されず再入力可能な形で顕在化する**」 |
| ①-b | **NFR-007** | **E4** NFR-007 の保証は「**操作として受理されたもの**」に掛かることを明記し、E0〜E3 と整合させる |

**根拠**: Web 調査([research.md](research.md) F)で、**保証対象ブラウザ上に主タブの一意選出が成立しない条件が 3 つ実在**することが確認された(Safari の Lockdown Mode / 通常・プライベートモードの併用 / 旧主タブのフリーズ)。**例外を「操作の受理」の境界として書き、失敗結果で定義しない**。

**本書で規範化する回復契約**: ① **`steal` を使わない**(旧コードの実行停止を保証しないため)② **ロックはコンテキストの終了時に解放される**(仕様保証)③ **待機側はキューを失わない**(永続キューは NFR-020 が前提とする**同一 storage bucket** の範囲で保持される)④ **ロック取得後、記録を始める前に単一書き手であることを再検証する**。

#### P3(オンライン専用の変更イベント)は v0.1 に残す(**人間の判断 2026-08-30**)

確定ゲート 2 周目までの指摘 27 件のうち **7 件が `P3` 起因**であり、**射程外へ出せば一度に消える**。しかし **PO の「旧機能の全面踏襲」決定(2026-08-13・要件書 v2.0)に沿って残す**。

- **`P3` は旧システムの「✏️ 直前修正」「🔎 過去修正」に当たる**。外すと **v0.1 で使えるのは末尾から戻す `undo` だけ**になり、**任意の過去プレイのピンポイント修正が落ちる**
- **`D6` 墓標・`D7` 改訂は代わりにならない** — `W2` が「受理済みの記録を直す手段に流用しない」と禁じている
- **下流への影響が決め手**: 11-2 のデータモデル影響差分が TSK-250 への引き渡しであり、`P3` を外すと **`#10`・`#11`・`#12`・`K4` の 4 要素が落ちる**。TSK-250 が変更イベントを知らないまま設計すると、**最も手戻りの高いデータモデル層で作り直しになる**
- **`P3` 起因の指摘は閉じ方が見える型**(結果集合の完全列挙・`D8` の定義からの除外)であり、際限なく広がる性質ではない

#### 収束判定の基準(**人間の判断 2026-08-30**)

**3 周目の P0 の過半が「2 周目の是正が生んだもの」なら、そこで止めて射程の縮小を人間に諮る。** 前タスクは 16 周回してから縮小したため、同じ経過を繰り返さない。

#### U-1 は本タスクの射程外(**人間の判断 2026-08-28**)

**U-1**(端末から失われたイベントによる gap を墓標で前進させる経路)は、**射程を縮めても新規設計なしでは閉じない**:

- **墓標生成の唯一の入口は「既存イベントが内容起因で拒否されて `要操作` になった後」**である(候補案 7-2)
- **原本を失った同期連番にはキュー項目も `要操作` 状態も存在しない**
- **通常生成すれば新しい同期連番が付く**ため、**欠けた過去の連番を消費できない**

閉じるには **墓標がクライアントイベントかサーバー生成か / 対象連番または欠落範囲の指定と検証 / 既存イベント・既存墓標がある連番への要求の結果 / べき等キー・再送・ACK の同一応答契約 / キュー遷移と prefix 更新のトランザクション境界 / 監査レコードの主体と閲覧権**を決める必要がある。**同期プロトコルの意味規則であり、正本化タスクで行う新規設計になる**(台帳 H-68 の「閉じた輪」)。

**順序は「先行」ではなく「後続」**: 先行にすると **① 先行タスクが墓標経路を設計しても、その成果を書く先である同期正本は本タスクの成果物であり取り込み経路がない**(別の設計正本を作れば「1 テーマ 1 正本」に反し、feature 文書だけを作れば非正本)**② 先行が先に approved になれば要件書は v2.4 を取り、本タスクの v2.4 と衝突する**。

**後続タスク(新規起票)**: **要件書 v2.5**(FR-012 の墓標の射程拡大)と**本正本の改訂版 v0.2** を**同じ確定ゲートで一括検証**する。**7.3 が定める通常の改訂経路**(approved 済み正本の再変更は新しい版として同じゲート)。

**本書との関係**: **本書は現行要件(v2.4)の射程で閉じる**。**U-1 は「要件の射程がまだ及んでいない領域」として受け取り先つきで記録する**。**本書に穴があるのではなく、要件に限界がある**。

#### U-9 の母集合の粒度(**本計画で確定・抽出器より先に固定する**)

**FR/NFR 条(65)・章節・ブロック 1〜8・付録項番・ID 付き表(`G-*`・`R-*`)・キー列を持つ表(付録C の設定値名・6.1 のデータ種別・10 章の項目名・FR-034 の認可行列)・8 章 DoD 1〜8・条内小項((α)(β)①〜⑧・(a)〜(d)・**本タスクが FR-012 / NFR-007 / NFR-019(d) へ新設する `E0`〜`E5`**)**。**`E0`〜`E5` は要件書側の正式な条内安定 ID として起案する**。**参照は必ず文書修飾を付ける** — `FR-012/E0` / `NFR-007/E4` / `NFR-019(d)/E5`(**同期正本には別系統の `E1`〜`E5`〔退避・取り込みの手順〕が既にあり、付録 `E-1`・`E-2` とも紛れる**ため — 16 周目 P1-1)(15 周目 P0-3 — 計画ローカルの記号にすると、母集合と抽出器の双方から共通に落ちて green になり、ステップ 2 の「FR-012 に E0 がある」という条件も実文書に対して定義不能になる)。**受入基準の行単位は採らない**(要件書側が無採番で、行番号を捨てると再現できない — [research.md](research.md) B-3)。

### 進め方の設計

**(1) 素材を先に移送し、索引と fixture を同じコミットで固定する。** `check_docs_status.py` は索引にない正本・版と状態の不一致をいずれも fail させるため、索引の更新を分離できない。**fixture と SHA-256 も検出器より前に固定する**(検出器に都合よく加工された fixture を弾くため)。

**(2) 要件書を先に、本書を後に。** 要件書 v2.4 の **4 本文箇所を 1 コミット**で起案し、**次のコミットで本書側の記述を要件から導出**する。

**(3) 分割の単位は「欠陥 ID の互いに素な集合」。** 7 関係は伝播先の表を共有するため「1 ステップ = 1 関係」では所有が交差する。**合格条件は「当該 ID が解消し、それ以前に解消した全 ID も解消のまま」**。

**(4) 検査の oracle を実装より先に固定する。** ① **欠陥台帳**(ステップ 3)② **関係マニフェスト**(ステップ 5)③ **要件母集合**(ステップ 7)。同じ作業で作ると共通の取りこぼしが一致して通る。

**(5) 新規機構を発明しない。** ベースライン ratchet は 5 周目に廃止した。**セレクタと累積実行という単純な列挙**で閉じる。

**(6) 検出器のない是正には文書状態の逐語照合を課す。** 人間照合 23 件は**該当箇所を列挙して原典と突き合わせ、結果を worklog へ記録する**。
