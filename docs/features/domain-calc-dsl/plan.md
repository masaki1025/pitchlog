## 4. 実装方針

### (1) 重さ分類の根拠 — コア領域

`backend/domain/` は**状況計算の正本そのもの**。設計書 6.3 の境界定義表が「状況計算」の含む側に
「座標変換・捕球選手推定」を明記し、「**判定に迷うコードは含む側に倒す**」と定める。
**`ci.yml` が既に `guard_paths` にあるため、本 PR は自動的に core-guard の対象**になる。

### (2) ◎ 検査集合を 4 つに分離する(P0 是正)

| # | 集合 | 出所 |
| --- | --- | --- |
| 1 | **要件由来の対象集合** | 要件書 `:883-885`(α5 + β8 = **13 件で閉じている**) |
| 2 | **マニフェスト登録集合** | `backend/domain/manifest.json` |
| 3 | **本番から独立採取した実在入口集合** | Vite の全 input・Web Worker・Service Worker・別 HTML・静的配信配下 + Python の import グラフ |
| 4 | **各検査層の実行集合** | ベクタ / プロパティ / 変異のランナー証跡 |

**不合格理由は集合ごとに別々に出す**(「0 件」で丸めない)。
**ステップ 9 は実リポジトリから既存の手書き座標変換入口を検出する負例を持つ。**

### (3) ◎ 段階的 CI 状態モデル(人間の裁定 2026-09-01 — 案 A)

**P0**: `consistency` を paths filter なしの必須ジョブにして未整備を常に exit 1 にすると、
**本 PR 以後の全 PR が赤になり、マージ経路が無くなる**(`NFR-019:915` / `github-setup.md:38`)。

**裁定: 基盤の自己テストと全体適合判定を分離する。**

| コマンド | 責務 | exit | CI |
| --- | --- | --- | --- |
| **基盤の自己テスト** | 検査器・runner・生成器が**仕様どおり動くこと** | 0 = 緑 | **必須ジョブ**(本タスクで常設) |
| **全体適合判定** | 4 集合の突合結果 | **未達を機械可読な「未達レポート」として出力し exit 0**。**適合は exit 0・違反(未達ではない誤り)は exit 1** | **必須ジョブ(レポート生成)。ゲート昇格は最初の対象追加時** |

**「未達」と「違反」を型として分ける**。未達 = 「まだ登録されていない」(想定内)。
違反 = 「登録されているのに食い違う」「宣言外の入口がある」(即 fail)。

**昇格条件を機械可読に持つ**: 未達レポートが空になった時点で必須ゲートへ昇格する条件を資産に書き、
**昇格し忘れを検出するテスト**を置く(**未達 0 件なのにゲート未昇格なら fail**)。

→ **設計書 10.1 へ「段階的 CI 状態モデル」として追随する。**

### (4) ◎ `D` の導出(P0 是正 2 件)

**誤り 1**: `D ≥ 4` を **FR-040 を含む 3 case** から導いていた。
**FR-040 は Should で採否未決**であり、非採用時は ADR `:256` により補正 case が外れる → **下限 4 が残らない**。

**是正**: **FR-006 単独**で導く。FR-006 `:236` は
「**undo を適用した後は、取り消された操作の 1 つ前の取消可能な操作が次の対象になる**」と定める。
**取消可能な操作が確定プレイのみ(FR-040 非採用)でも**
**`プレイA → プレイB → undo → undo`** が成立し、**長さ 4 の必須 case** になる。

**誤り 2**: 「**`D` と `D+1` で出力が変わらない**」プロパティは**成立しない**。
`NFR-019(a):917` が出力に**遷移後の履歴スタック全体**を要求するため、深さが違えば出力も違う。
さらに `D+1` は保証範囲外なのに同値を要求すると**保証範囲を事実上拡張**する。

**是正**: 同値による収束判定を**削除**する。

> **`D` = max(必須シナリオ長, スタック種別の全等価分割を覆う最小深さ)** として**具体値を固定**する。
> **`D+1` では「拒否・切り詰めをせず実行できる」ことだけを検査し、出力同値は求めない。**

**深さ・構成・シナリオ長の全 case 集合を資産へ固定する**(要件書 `:893` の「集合を固定する」を満たすため、
下限のままにしない)。

### (5) 変異テストの実装(P0 是正 — 欠落していた)

**基盤として本タスクで作る**(レビュー結論: 後続送りにできない):

**変更対象 + 依存先の逆引き** / **全面発火条件** / **各 mutant の kill 要因** /

`timeout-minutes` とは別)/ **夜間の拡大プロパティ・全面変異** / **夜間失敗の起票と縮小 case 追跡**

### (10) 配置の確定(P1 是正 — package 混同)

**`backend/domain/manifest.json` が存在することは、`backend/domain/` を Python package 探索へ
追加すべきことを意味しない。** `packages.find where=["src"]` は src-layout の設定である。

| 種別 | 置き場 |
| --- | --- |
| **規範資産(JSON)** | `backend/domain/*.json` |
| **生成器・検査器の実装** | `backend/src/pitchlog/...` |
| **backend 生成コード** | `backend/src/pitchlog/generated/...` |
| **frontend 生成コード** | `frontend/src/lib/generated/`(ADR `:100`) |
| **テスト** | `backend/tests/...` |

**トップレベルに Python を置く理由がない限り `packages.find` は変更しない。**
資産を runtime で読むなら **package-data または明示パスの契約**を定め、
**実 wheel に含まれるファイル一覧のテスト**を置く。

### (11) テストの所有ジョブを分離する(P1 是正)

`check_authz_catalog.py` 型の全葉変異をルート `tests/` に置くと、**既に 283s の `harness` に常時加算**される。
`consistency` でも同じ検査を呼べば**二重実行**になる。

| 検査 | 所有ジョブ |
| --- | --- |
| 検査器の単体テスト(全葉変異を含む) | **`harness`** |
| 実リポジトリ適合検査(未達レポート) | **`consistency`** |
| 重い変異テスト | **`consistency` とは別ジョブ**(並列) |

**同一テストを二重実行しない。** `harness` / `consistency` 双方の実測予算を DoD に持つ。
