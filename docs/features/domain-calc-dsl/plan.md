### なぜやるか

**旧システムには「複数実装が同じ値を返すことを固定する機構が存在しなかった。」**
旧要件書 `requirements-tsukuba-pss-v0.2.md` が多重実装(**捕球選手推定の 3 実装**ほか)を
認識しながら、**測定方法を「コードレビューと共有モジュールのテスト」= 人手**と定めていた。
結果として**監査で「表示成績が信頼できない」状態から立て直す**事態になった(research.md §4-1)。

### 本タスクの位置づけ — 段階 1 の「うち基盤部分」

`ADR-003` の着手順序の段階 1 は **①ベクタの schema と独立に確認した期待値** と
**②検査基盤(生成器・マニフェスト・収集器・CI 配線)** の**両方**を含む。

**本タスクは②のみを担う。**①(ベクタ schema と対象別の期待値)は **TSK-236〜239**。
→ **「本タスクの完了 = 段階 1 の完了」ではない。** 段階 1 は **TSK-235 と TSK-236〜239 の合流**をもって完了する。

**②の外延は v0.2 で拡大した**(research.md §6-10)— composite 証跡 schema と値の連鎖検証を行う収集器 /
表示系変異演算子 / **表外既定の表示対応の突合を行う静的解析器** / 表示 primitive の生成と生成前検査 5 種。

### 「対象計算 0 件」は事実ではない

**要件上の対象集合は (α)5 件 +(β)①〜⑧ で既に閉じている**(要件書 `NFR-018 対象欄`。
**追加・削除には本書の改訂を要する**)。実コードにも **`frontend/src/lib/courseInputView.ts` の
`courseScreenXToStoredX` / `courseStoredXToScreenX` が存在**し、**`ADR-003` がこの既存座標変換を名指ししている**。
**呼び出し元は実測で `StrikeZone.vue` のみ・4 箇所**(research.md §6-3)。

**空なのは `backend/domain/` とマニフェスト登録**であって、対象集合でも本番入口集合でもない。
→ **検査集合を 4 つに分離する**(design.md §3-1)。正しい不合格理由は「0 件」ではなく
**「要件対象が未登録」「既存の手書き座標変換入口が未宣言」「ベクタ未整備」**である。
