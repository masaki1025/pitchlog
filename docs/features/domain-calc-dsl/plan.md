## 4. 実装方針

**詳細は [design.md](design.md) が正。**本節は契約と重さ分類の根拠に絞る。

### (1) 重さ分類の根拠 — コア領域

`backend/domain/` は**状況計算の正本そのもの**。設計書 6.3 の境界定義表が「状況計算」の含む側に
「座標変換・捕球選手推定」を明記し、「**判定に迷うコードは含む側に倒す**」と定める。
**`ci.yml` が既に `guard_paths` にあるため、本 PR は自動的に core-guard の対象**になる。
加えて設計書 6.3-⑤ により **`core-areas.json` の paths 追加は敵対レビュー + 人間承認の対象**(design.md §11-4)。

### (2) 契約として固定する 6 点

| # | 契約 | 詳細 |
| --- | --- | --- |
| 1 | **検査集合 4 分離** — 不合格理由を集合ごとに別々に出し「0 件」で丸めない | design.md §3-1 |
| 2 | **「未達 / 違反 / 債務」を型として分ける** — 未達と債務は exit 0・違反は exit 1。基盤の自己テストと全体適合判定を別コマンドにする | design.md §3-2 |
| 3 | **`bootstrapDebt`** — 承認時点の既知債務を封印し、追加・再導入・降格を禁止、空になったら自動かつ不可逆に昇格 | design.md §4 |
| 4 | **exact-set は 2 層**(per-calculation 10 + トップレベル)。**フラットな 11 件では凍結しない** | design.md §6-1 |
| 5 | **provenance は条項 ID**。資産に行番号参照を 0 件にする | design.md §2-1 |
| 6 | **恣意的迂回は保証範囲外として明示的に記録**し、「検出する」合格条件を書かない | design.md §7-4 |
