## 1. 型語彙と配置

### 1-1. D-1 v0.2 の表示規則は 3 類

`ADR-003 D-1 表示規則 3 類` が許すのは次の 3 類**だけ**であり、**条件分岐・部分文字列操作・③の宣言の外の
数値整形ロジックは書けない**。

| # | 類 | 内容 |
| --- | --- | --- |
| ① | **enum → 表示名の写像テーブル** | **管理者管理でない安定した enum に限る**。管理者管理語彙(要件書 4.0-3)は ID によるデータ参照で解決し、写像テーブルに持たない |
| ② | **宣言的テンプレート** | プレースホルダ差し込みのみ。**受理するのは `DisplayAtom` と ① の結果だけ** |
| ③ | **数値表示 primitive 4 種** | 固定小数(scale 0..3・丸め・先頭 0・符号)/ 百分率(scale 0..2・丸め・先頭 0・記号)/ 混合分数(分母・整数部の助数詞・剰余 0 の形・分数の体裁)/ null 代替(代替文字列。**値部分のみ**) |

**書式の実引数の正は要件書 付録A の「表示書式」列(binding)**であり、正本の宣言は binding の値を参照する
(`ADR-003 D-1 表示規則 3 類`)。**表示の都合ではなく要件として与えられる。**

→ **本タスクは binding を新設しない。** 参照と、宣言時パラメータの充足検査(`ADR-003 D-1 正本の射程行`)だけを作る。
research.md §6-11 は **付録A の書式が この 3 類 + 閉じた合成で表現できる**ことを確認している
(合成は 3 系統のみ: 単一 primitive / primitive + 固定小数(0) + ② の母数併記 / ② に別 primitive の
`DisplayAtom` を入れる入れ子〔WHIP・FIP〕)。

> **⚠ 件数「全 36 件」は失効**(research.md §7-5・2026-09-18)。**要件書に件数の記載は無く**、
> **本タスクの再計測では付録A で「表示書式」列を持つ表の行数は 32**(A-2 = 12 / A-2b = 4 / A-3 = 7 /
> A-4 = 1 / A-5 = 8)**で一致しなかった。** **複合行 4 件**(`最速・平均球速` / `勝 / 敗 / 分` /
> `得点 / 失点` / `イニング別得点・失点`)**を分解するかどうかで数が動く。**
> → **ステップ 1 は「数え方の規則」を資産に定義し、その規則で数えた件数を `assert` する**
> (**独立導出**)。**「表現できる」という結論は維持する** — **失効したのは件数だけ。**

### 1-2. 型語彙の閉包

`ADR-003 D-1 表示規則 3 類` の型領域に v0.2 で加わったもの:

- **`NumericValue`** — 整数 / exact decimal / 有理数(分子・分母)の 3 形 + **nullable**
- **`DisplayAtom`** — 不透明型。**言語既定の文字列化を禁止**し、②は `DisplayAtom` のみ受理
- **供給源 3 経路** — ③ primitive の出力 / ① 写像の出力 / 参照解決後の名称

**対象計算は「①構造化値」と「②表示値」の両方を返し、`expected` と比較面はその双方を持つ**(`ADR-003 D-1 表示規則 3 類`)。
**例外**: 付録A-1 の表外既定の数値は**状況判定ベクタの比較面に表示値を載せない**(§10-3)。

**単位は値に含めない** — 球速の `km/h` は画面側の見出し・軸ラベルの担当(PO 裁定 2026-09-03)。
**ビンラベルのみ template が明示的に単位を含む**(要件書 付録A-2b 球速分布行)。
→ **primitive のパラメータに単位を持たせない。**

## 2. 機械条件の判定方法(`[機械]` から意味判断を追い出す)

**背景**: 敵対レビュー 2 周目の P1「`[機械]` に意味判断が混入」。加えて
research.md §6-7 のとおり**旧計画書の行番号参照 18 件がすべて別行を指していた** — 行番号を検査対象にすると
版の更新で必ず腐る。

**解法は兄弟タスクが確立済み**(`docs/features/adr003-display-primitives/plan.md` 6 節・
worklog `2026-09-01-adr003-display-primitives.md`)。**その型をそのまま移植する。**

| 型 | 判定方法 |
| --- | --- |
| **節限定差分** | 指定した節の外に差分が無いことを構文木レベルで確認する |
| **同一コミット** | 2 つ以上のパスの変更が同一コミットに入っていることを履歴で確認する |
| **行番号参照 0 件** | 資産・文書に `:<数字>` 形式の正本参照が存在しないことを確認する |
| **母集合計測** | 列挙器が空でないことに加え、**`assert attempts == 期待件数`** で母集合の大きさを固定する |
| **文言存在** | 逐語の文言が正本に存在すること(**行番号ではなく条項 ID で位置を指定**)を確認する |

**本タスクで追加する型**:

| 型 | 判定方法 |
| --- | --- |
| **exit コード分離** | `subprocess` で exit 0 / 1 / 2 を直接 assert する(戻り値の意味を型として分ける) |
| **全葉変異** | 契約木の全葉に値変異と削除変異を適用し **escape 0** かつ **母集合計測**を満たす |
| **集合差** | 期待集合と実測集合の差が 1 件でも fail する(「0 件」で丸めない) |
| **独立導出** | 期待値をリテラルで持たず、規則の唯一の実装から導出して資産と突合する(§11-2) |
| **パス allowlist** | そのステップの差分が、宣言したパス集合に収まる(**「節限定差分」とは別の判定** — 節限定差分は 1 ファイル内の節、こちらはファイル集合。3 周目 P1-2 の是正) |
| **`history_precedes`** | あるパスの変更が、別のパスの変更より**履歴上先行する**(**「同一コミット」は共変更しか証明せず、時間的な先行を証明しない** — 3 周目 P1-3 の是正) |
| **`generated_provenance`** | その成果物が**生成物であって手書きでない**ことを、生成元と生成器の実行から確認する(既存 9 型のどれにも無かった — 3 周目 P1-3 の是正) |

### 2-1. provenance は条項 ID で持つ

**マニフェストと資産の `provenance` に行番号を書かない。** 位置指定は次の形に限る:

- 要件書: `NFR-018 (b)②` / `FR-006 補足` / `付録A-2 WHIP 行` / `付録E-1 成績計上フラグ行`
- ADR: `D-1 射程行` / `D-11 3 層表 プロパティ層` / `D-7 実行契機表 (b)③ 行`

**逐語の文言存在**で実在を検査する(**文言存在**型)。**行番号参照 0 件**型で、資産に `:<数字>` 形式の
正本参照が混入していないことを機械検査する。

## 3. 検査集合 4 分離と 3 つの型

### 3-1. 4 集合

| # | 集合 | 出所 |
| --- | --- | --- |
| 1 | **要件由来の対象集合** | 要件書 `NFR-018 対象欄`。**(α)5 + (β)①〜⑧ で閉じている**(追加・削除は要件書の改訂を要する) |
| 2 | **マニフェスト登録集合** | `backend/domain/manifest.json` |
| 3 | **本番から独立採取した実在入口集合** | Vite の全 input・Web Worker・Service Worker・別 HTML・静的配信配下 + Python の import グラフ |
| 4 | **各検査層の実行集合** | ベクタ / プロパティ / 変異のランナー証跡 |

**不合格理由は集合ごとに別々に出す。**「0 件」で丸めない。正しい不合格理由は
**「要件対象が未登録」「既存の手書き座標変換入口が未宣言」「ベクタ未整備」**である。

**「13」という数値は ADR・要件書のどこにも書かれていない**(research.md §6-9)。
`ADR-003 D-6` が「**(α)5 件・(β)①〜⑧ のすべてがちょうど 1 つの契約で発効する**ことを CI が検査する
(重複帰属・未帰属はいずれも fail)」と規則を定めているだけなので、**資産側は 13 をハードコードせず
要件書の対象欄から導出する**(**独立導出**型)。

### 3-2. 「未達」「違反」「債務」の 3 型 — ⚠️ **免除判定としては失効。報告の語彙としてのみ有効**

> ⚠️ **本節と §3-3 の一部は、TSK-355 の射程縮小(PO 裁定 2026-09-13)より前の記述を含む。**
> **免除の判定は §3-2-b の「封印集合に列挙された事項に限る」が正**であり、
> **性質による分類(未達 / 違反 / 債務)は免除判定に使わない。**
> **本節は未達レポートの語彙としてのみ読む。**
> **現行の条項一覧は §3-2-f。** 撤去された `BOOT-VOCAB` / `BOOT-COUNT` / `BOOT-SEAL-SCOPE` への
> 参照が本節以下に残っているが、**いずれも失効した経緯の記録**である。

段階的 CI 状態モデルの中核。`consistency` を paths filter なしの必須ジョブにして未整備を常に exit 1 に
すると、**本 PR 以後の全 PR が赤になりマージ経路が無くなる**(要件書 `NFR-019` / `github-setup.md` 2 章)。

| 型 | 意味 | exit |
| --- | --- | --- |
| **未達** | まだ登録されていない(想定内) | **0**(機械可読な未達レポートを出力) |
| **違反** | 登録されているのに食い違う・**封印集合に無い**宣言外の入口がある | **1** |
| **債務** | **承認時点で既知の未宣言入口**。封印された全件列挙の中にあるもの | **0**(§4 の規律下でのみ) |

**◎◎ 分類の切り口が変わった(確定ゲート 2 周目 指摘 2・2026-09-13)— 優先順位は不要になった**

**新しい切り分け**: **宣言の有無**で切る。

| 型 | 定義 |
| --- | --- |
| **未履行** | **宣言が存在しない** |
| **違反** | **宣言が存在するのに実体と食い違う** |

→ **2 つは定義上ばらばら(disjoint)になるので、優先順位が要らない。**
**封印の対象は未履行の義務に限り、違反は封印されない。**

**初周の「封印された対象」単位だと、その対象の生成物が手編集されても免除されていた**(指摘 2)。
**義務単位への統一(本タスクが提案)と同時に解決した** — **封印の単位を対象から義務へ移したことで、
対象単位の例外が別種の違反まで覆う経路も閉じた。**

**↓ 以下は初周の是正(優先順位による解決)。2 周目でより良い切り方へ置き換わったが、
「なぜ優先順位では不十分だったか」の記録として残す。**

**◎ 分類の優先順位(TSK-355 の確定ゲート初周からの転送・2026-09-13 に是正)**

初版は「違反 = 宣言外の入口がある」と書いていたため、**封印済みの既知債務が「違反」と「債務」の
両方に該当**していた。**正本 `BOOT-VOCAB` の優先順位に従う**:

> **既知債務として封印された対象については、宣言と実在の差をもって「違反」と分類しない**
> (当該対象は「未達」かつ「既知債務」として計上する)。**封印集合に無い対象の差は従来どおり「違反」である。**

**放置した場合の症状**: **債務を登録した基盤 PR 自身が違反判定を受けてマージできない** —
**本タスクが解こうとしたデッドロックの再現**。**優先順位が無いと分類が競合して両方に落ちる。**

**基盤の自己テスト**(検査器・runner・生成器が仕様どおり動くこと)は **exit 0 = 緑**で**必須ジョブ**。

**◎ 名称の分離(同上・`BOOT-NO-CLAIM` との衝突の是正)**

初版は「**全体適合判定**は未達レポートを出して exit 0、**適合も exit 0**」と書いていたが、
**「適合」という語が正本と衝突する**。`BOOT-NO-CLAIM` 逐語:

> 移行状態にあるあいだ、本項の達成条件 (b)② を満たしたと判定してはならない。また `NFR-019(a)` を
> 合格と判定してはならない。**これは軸②が有効であるか失効しているかを問わない。**
> 移行状態における CI の緑は「**移行状態の要求を満たしている**」ことのみを意味し、
> 本項または `NFR-019(a)` の充足を意味しない。

→ **マージ可否(exit code)と適合判定(充足の主張)を別の語・別の出力にする**:

| 名称 | 意味 | 出力 |
| --- | --- | --- |
| **移行状態の要求判定** | 未達・債務・違反の分類と、移行状態の規律(単調性・封印)を満たすか | exit 0 / 1 |
| ~~全体適合判定~~ → **充足判定** | `NFR-018(b)②` / `NFR-019(a)` を満たしたか | **移行状態のあいだは常に「未充足」を出力する。exit code では表現しない** |

**「exit 0 = 適合」という名前づけをしない。** 移行状態の緑は**移行状態の要求を満たしたことだけ**を意味する。

**昇格条件を機械可読に持つ**: 未達レポートと債務台帳の**両方が空になった時点で必須ゲートへ昇格する条件**を
資産に書き、**昇格し忘れを検出するテスト**を置く(**未達 0 件かつ債務 0 件なのにゲート未昇格なら fail**)。

### 3-2-a. TSK-355 の計画承認で固定された骨格(2026-09-11)

**注意 — 承認されたのは TSK-355 の「計画書」であって「正本」ではない。**
**本タスクのブロッカが解けるのは、`ADR-003` と要件書の改訂が approved になった時点。**
計画承認は「同タスクが着手してよい」ことを意味するにすぎず、しかも**着手自体が
`TSK-317 PR #2` と `TSK-343` のマージ待ち**である。

固定された骨格のうち本タスクに効くもの:

| # | 確定内容 |
| --- | --- |
| **立て方** | fail-closed の例外ではなく「**充足判定は従来どおり不合格のまま、閉じた移行状態に限りマージ可否を別判定する経過規定**」。→ **本タスクの §3-2 の 3 型は「マージ可否の別判定」の機構であって、充足判定を変えるものではない**。依拠条項を書くときはこの立て方に合わせる |
| **二軸** | ①移行プログラム(未達 0 かつ債務 0 で**自動かつ不可逆に昇格**)②緩和されたマージ授権(**直近の前進から連続 50 マージで前進 0 なら失効**・**再承認は人間の明示承認**) |
| **エポックの起点** | **発効時点**(正本の approved 時点ではない)→ **本タスクの PR 自身は失効に巻き込まれない**(§3-3) |
| **封印の 4 規律** | 固定 SHA / 当該 PR から変更不能 / 復活は fail / 対象は **D-11 が要求する宣言のうち開始時点で未宣言のものすべて**(入口に限定しない) |
| **発効原子性** | **観測機構を含む**。**観測は移行状態の開始と同時に始まる** → 失効の観測機構を `bootstrapDebt` と同じコミット群に置く(§3-3) |
| **条項 ID** | **安定した ID を与える。改名しない。削除は真発火**(§12-1-b-1 の非対称と整合) |
| `M-1`〜`M-5` | TSK-355 の**実装ステップ 2 の `design.md`** で確定。**そこで本タスクへ 4 点がまとめて渡される** |

### 3-2-b. ◎◎ PO 裁定で射程縮小(2026-09-13)— 分類が不要になり、4 件が本タスクへ委任された

**経緯**: `7.3-6` のエスカレーション条件が **2 周連続で成立**(起因 8/8 → 9/9)。
**「未履行と違反の切り分け」が 3 周とも振り出しに戻った**:

| 周 | 論点 | 是正 | 次周に起きたこと |
| --- | --- | --- | --- |
| 初周 | 既知債務が「違反」にも該当 | 優先順位を追加 | 封印が**対象単位**で別種の違反まで免除 |
| 2 周目 | 封印対象の生成物が**手編集**されても免除 | **宣言の有無**で切り分け | **「宣言外の入口」は `entrypoints[]` 宣言が無いので未履行にも該当** |
| 3 周目 | **振り出し** | **PO 裁定へ** | — |

条文は **2204 字 → 4024 字**へ膨らみ、**塞ぐほど条項間の相互作用が増えていた**。

**採られた解 — 分類をやめ、列挙で決める**:

> **本規定が免除するのは封印集合に列挙された事項に限る。**

**◎ 止まらない経路(先方の懸念はこちらでは成立しない)**

**発効前にはそもそも検査が存在しない**(`ci.yml` の現存 9 ジョブに `consistency` は無い — research.md §6-6)。
→ **fail する相手がいないので止まらない。** **機構とその免除が同一変更で生まれる**という
発効原子性の設計が、ここで効いている。

**◎◎ しかし本タスクの PR 自身の CI 実行が問題になる**

本タスクの PR は **`consistency` ジョブを新設する**。**`pull_request` イベントでは PR 側の
`ci.yml` が使われる**ので、**新設したジョブが自分の PR で実行される**。

**そのとき移行状態は発効しているか?**

| 読み | 帰結 |
| --- | --- |
| **ツリー基準**(当該ツリーに 10 点と封印台帳が揃っていれば発効) | **免除が効き、本タスクの PR は通る** |
| **マージ基準**(`develop` へ統合された時点で発効) | **PR 実行時はまだ未発効 → 免除なし → 自分の PR が落ちる** |

**マージ基準だと、本タスクの PR は自分が新設したジョブで落ちてマージできない。**
**候補 5(規律が正しく書かれているほど、その規律を実装する変更が自らに引っかかる)の 5 件目**になる。

**条文の該当語**: `BOOT-ACTIVATION` の「**同一の変更で CI の必須経路へ接続された時点**」。
**「接続された時点」がツリーかマージかを定義していない**
(**「同一の変更」= PR は定義されたが、**「接続された時点」は未定義)。

**✅ ツリー基準で確定(TSK-355 が実測・2026-09-14)。**

**決め手は「CI の必須経路」の実体**:

> **実装状況(2026-08-10・ci-foundation)**: 個人 Free プラン + private リポジトリでは
> **branch protection / Rulesets とも利用不可**(**rulesets API 403 を実測**)のため、
> **ブランチ保護は後送り**(PO 判断)

**`required_status_checks` はそもそも存在しない。** 運用は `github-setup.md` 2 章の管理手続:

> マージ前に、**PR の最新 HEAD SHA に対して CI の全ジョブが green** であることを確認する
> (古い green run で判断しない)

→ **「PR の最新 HEAD SHA に対して」= ツリー基準。**
**本タスクの PR が新設した `consistency` は本タスクのツリーで実行され、
そのツリーに 10 点と封印集合が揃っていれば移行状態は発効している。免除が効く。**

**TSK-355 が条文へ 1 文足す**(ブランチ保護が将来導入されたときに読みが動かないように)。
**量化先は 2026-09-14 に是正された**:

> ~~CI の**全ジョブ**に当該機構が含まれ実行される~~ → **誤り**
> (**backend・frontend・secrets・docs-lint すべてで同じ機構を実行する読み**になり、
> **未導入ジョブや不採用の win-setup まで含む**)
>
> **正**: **ジョブのうち少なくとも 1 つに配線され、当該ジョブが PR ごとに実行され、
> その失敗がマージを妨げる扱いであること。** 全ジョブへ重複して配線することを求めるものではない。
> **どのジョブへ配線するかは検査基盤の実装が定める。**

→ **委任事項④に「それらをどの CI ジョブへ配線するか」が追加された。**
**本タスクが `consistency` へ配線するか別ジョブを立てるかは本タスクの判断。**

**→ 本タスクの実装順序は変わらない。**

**◎ 副産物 — ステップ 55 の合格条件に限界がある**

本タスクのステップ 55 は「**必須 context が 9 → 11 になり `github-setup.md` の 3 分類と
Ruleset JSON が同期**(**集合差**)」を合格条件に持つ。

**しかし `required_status_checks` はリモートに存在しない**(上記)。
→ **この合格条件が検査できるのは「文書の同期」だけ**であり、
**「実際にそのジョブが必須として強制されている」ことは検査できない**。
**強制は人間の手続き**(`github-setup.md` 2 章)。

**合格条件の文言を「文書の同期」と明示する**(§16-3 — 示せることと示せないことを分ける)。
**「必須ジョブになっている」と書くと、検査できないことを検査したと称することになる。**

**§15-1-b(`cancel-in-progress` の罠)とも接続する** — **強制が人間の手続きである以上、
「最新 HEAD SHA の全ジョブ green」を人が確認する順序が守られないと成立しない。**

### 3-2-h. ✅ 委任①の決定 — 封印要素の粒度は **A(composite 1 件)**(2026-09-14)

**TSK-355 の 8 周目 指摘 1** が「粒度の導出規則を D-11 へ適用しても単位が一意に決まらない」とし、
**3 つの読み(A: composite 1 件 / B: composite + invocation + 連鎖 / C: 連鎖を辺ごと)**の選択が
**委任①として本タスクへ委ねられた**。

**◎ D-11 の原典を読んで A に決定。理由 4 つ。**

**(1) D-11 が明示的に「要素を 3 つに分けない」と書いている**(逐語):

> **証跡直積の軸は従来どおり `directTargetId` 単位**(**要素を 3 つに分けない** —
> 5 判定の証跡・経路一致検査の要求集合は不変)

**(2) B / C の単位は「独立に解消の成否を判定できる」を満たさない**(拘束③):

D-11 は **`components[]` の各構成生成物について hash 突合**し、**収集器が前段の出力と後段の入力の一致
(値の連鎖)を独立に検証する**と定める。**しかし**:

- **値の連鎖の検証には両端の実行結果が要り、それは `invocation` による composite の実行からしか得られない**
- **`invocation` は「宣言された全段を通す」ものなので、その充足は composite の実行そのもの**

→ **辺も `invocation` も、composite を通す実行なしには判定できない。**
**「独立に解消の成否を判定できる最小の単位」は composite 全体。**

**(3) 拘束④(同一の事項が 2 つ以上の要素として封印されてはならない)と整合する。**
**B / C は composite と `invocation` を別要素にするが、D-11 では両者が同じ `directTargets[]` 要素を
構成する**ので、**同一の事項を 2 要素として数えることになる。** A ならこの衝突が起きない。

**(4) ◎ そもそも封印集合では A/B/C が区別されない(先方の前提を崩す)**

**先方は「未解消件数と `BOOT-STALL` の失効時点が分岐する」としているが、分岐しない。**

**移行開始時点では対象計算が 1 件も登録されておらず、`directTargets[]` 自体が不在**である
(本タスクは対象別の生成物を作らない — §2 やらないこと)。
→ **封印される要素は「対象 A の `directTargets[]` が不在」の 1 件**であり、
**composite の内部構造は存在しないので A/B/C のどれでも同じ**。
**`BOOT-SEAL-MONOTONE` により後から要素を追加できない**ので、
**段階 2 で composite が実在しても封印集合は変わらない。**

→ **A/B/C の選択が観測可能になるのは「開始時点に composite が部分的に存在する」場合だけで、
本タスクではその状況が生じない。**

**◎ ただし解消判定には効く。** A の意味は「**composite 全体が生の検査結果で緑になった時点で解消**」。
**`invocation` や連鎖を個別に示す必要はない**(D-11 の検査がそれらを内包するため)。

**`BOOT-STALL` の粒度の懸念について**: 「束ねると測定が意味を失う」という条文の懸念は、
**本タスクでは生じない**。**封印要素は「宣言 1 種が不在」の粒度**であり、
**1 対象あたり 10 要素(§3-2-f の実測 136 件)**に分かれているため、
**composite を 1 要素とすることで粗くなるのは `directTargets[]` の 1 要素分だけ**である。

**D-11 の改訂は不要**と判断する(**別タスクの起票をしない**)。

### 3-3. ◎ 失効判定の機構も本タスクの射程に入る見込み — ⚠️ **一部が縮小前の記述**

> ⚠️ **本節の `未達数 ＋ 債務数` と「10 点構成」は縮小前の記述。**
> **現行は `BOOT-SEAL` の封印集合と、`BOOT-ACTIVATION` の「全条項に機構と負例と正例がある」。**
> **現行の条項一覧は §3-2-f。**(TSK-355 の条文が二軸になるため)

**TSK-355 の申し送り 2026-09-10**: 同タスクの条文は**二軸**になる。

| 軸 | 内容 | 判定できないときの発火 |
| --- | --- | --- |
| **① 移行プログラム** | 未達 0 かつ債務 0 | **昇格判定の不能** |
| **② 緩和されたマージ授権** | **停滞エポック** — **直近の前進から連続 50 マージで前進 0 なら失効**。**再承認は人間の明示承認**(TSK-355 の計画承認 2026-09-11 で確定) | **失効判定の不能** |

**②は本タスクが提案した「時間ではなくマージ本数で測る」形が採られたもの**(日付を書かず・機械判定可能・
リポジトリを凍結させない)。**`N = 50` は TSK-355 側で確定した値。**

**◎ 帰結 — 現行の設計は①しか持っていない。**
§3-2 と §4-1 は**昇格条件しか持たず、失効条件を持たない**。②が正本に入るなら、
**「マージ本数の累計」と「`未達数＋債務数` の履歴」を観測し、50 マージ無減少で失効させる機構**が要る。
これは本タスクの検査基盤の射程に入る見込みで、**ステップが 1 つ増える可能性がある**。

**◎ 解消 — エポックの起点は「発効時点」**(TSK-355 が 2026-09-10 に条文へ明記)

TSK-355 は「**段階 1 のあいだは構造的に前進しないので、本タスクの PR 期間中に失効が起きるのは想定内**」と
言っているが、**それが成り立つのは移行状態が本タスクのマージ前から有効な場合だけ**である。
起点の候補が 2 つあり、帰結が違う:

| 候補 | 起点 | 帰結 |
| --- | --- | --- |
| **(a)** TSK-355 の正本が approved になった時点 | 本タスクの開発期間もカウントに入る | **本タスクがマージされる前に失効し得る** → 再承認を経ないと本タスク自身がマージできない |
| **(b)** 本タスクの開始 PR がマージされた時点(封印された台帳が生まれた時) | カウントは本タスクのマージ後に始まる | 失効は段階 1 の後半〜段階 2 の初期に起きる |

**(b) が整合的**と考える。理由: **債務台帳も `未達数＋債務数` の観測機構も本タスクが作る**ので、
**マージ前は 2 つの数値が存在しない**。存在しない量の減少を判定できない。
また §4-1 の封印は「**移行開始を承認した既存コミットの固定 SHA**」を比較元に置くので、
**「移行開始」という点が特定のコミットとして存在する**ことを前提にしている。

**→ (b) で確定した。** TSK-355 が計画書 §4-9 と `M-2` の両方へ明記:

> **エポックの起点は「発効時点」であり、「正本が approved になった時点」ではない。**
> 正本が approved になっただけでは 50 マージのカウントは走らない。カウントが始まるのは
> **検査基盤の PR がマージされ、機構が動き出した時点**。

根拠は同タスク §4-4 の**発効原子性** — 「移行判定器・未達レポート・観測機構・負例が
**同一変更で CI の必須経路へ接続されたときにのみ**移行状態が発効する。それ以前は**定義済みだが未発効**」。

**帰結: 本タスクの PR 自身が失効に巻き込まれることはない。** 失効が起こり得るのは**発効後**
(段階 1 の後半〜段階 2)。**本タスクの実装順序を変える必要はない。**

**◎ カウンタの形(2026-09-11 に確定)— 累計ではなく「直近の前進からの連続」**

本節の初版は「**移行状態が有効なあいだにマージされた PR が 50 本**」と書いていたが、
確定した形は「**直近の前進から連続 50 マージで前進 0**」である。**リセット付きのカウンタ**であり、
**発効時点からの累計ではない**。

→ **観測機構は「最後に `未達数＋債務数` が減った時点」を保持し、そこからのマージ数を数える。**
**前進があるたびにカウンタが 0 へ戻る。** 発効時点からの通算本数を持つ実装では不正確になる。

**◎ 二重計上の是正と、残る粒度の問題(2026-09-13)**

**本タスクが指摘し、TSK-355 が検証して確定した**: **母集合は「別」でも「同一」でもなく、部分的に重なる。**

```
未達集合の母集合 = 要件書 NFR-018 の対象欄が列挙する対象計算
債務集合の母集合 = ADR-003 D-11 が要求する宣言のうち移行開始時点で未宣言のもの

重なる例   : 対象計算「捕球選手推定」が未宣言 → 未達でもあり債務でもある(同一オブジェクト)
重ならない例: 入口の全列挙の宣言が欠けている → 債務だが「対象計算の未達」ではない
```

**`BOOT-SEAL-SCOPE` が「入口に限定しない」と定めた結果、債務集合は対象計算より広く、かつ交わる。**

→ **`未達数 ＋ 債務数` の和は誤り。** TSK-355 が **`残務数 = |未達集合 ∪ 債務集合|`**(重なりは 1 回)へ改める。
**軸①の終了条件と軸②の停滞判定は、いずれも `残務数` で測る。**

**混入経路(先方の分析)**: `plan.md` の元の表現は「**未達 0 かつ債務 0**」(**連言**)だった。
`design.md` で `未達数 ＋ 債務数` という**和**に書き換えたのが混入経路。
**終了条件としては連言と和が同値(非負整数なので)だったため気づかず、停滞判定に使った時点で差が出た。**

**◎ 本タスクから返した残る問題 — 「同一 ID か」より前に粒度が違う**

先方は「和集合を取れるためには同一オブジェクトが同一 ID で表される必要がある」として
**名前空間の問題**として扱っているが、**その前に集合の粒度が違う**:

- **未達集合の要素 = 対象計算**(13 件の母集合)
- **債務集合の要素 = 宣言**(`entrypoints[]` / 表示対応 / 構成の照合 …)

**1 つの対象計算が未登録なら、その対象が要求する宣言はすべて欠けている。**
→ **対象計算 1 件に対し宣言が k 件**対応するので、**同じ粒度で union を取れない。**

**本タスクの提案**: **母集合を「履行義務(obligation)」の 1 粒度に統一する。**

```
残務集合 = 未履行の義務の集合
  - 未登録の対象計算 → その対象が要求する宣言の数だけ義務を生む
  - 単独で欠けている宣言(表示対応など)→ 義務 1 件
未達は導出される: 対象計算が未達 ⇔ その対象の義務が 1 件以上残っている
```

**利点**: ①写像が要らない(union が自明)②二重計上が構造的に起きない
③**停滞判定の目的(残作業量の測定)に合う** — 作業は義務単位で進むため。

**二次的な非対称も残る**: **債務集合は移行開始時点で封印される(固定)**が、
**未達集合は `対象 ID 集合 − 実在集合` で毎回計算される(ライブ)**。
**封印された集合とライブな集合の和集合**を取ることになるので、
**義務単位に統一すれば「開始時点に存在した義務」= 封印**として一貫する。

**✅ 決着(2026-09-13)— 義務単位が採られ、粒度は正本に入る。**

TSK-355 が条文へ次を書く:

> **「履行義務」とは、`ADR-003` D-11 が要求する宣言の 1 件をいう。対象計算が実在集合に属さない場合、
> 当該対象について D-11 が要求する宣言はすべて未履行の義務として数える。**

```
残務集合 = 未履行の義務の集合(単一の集合。和も重なりも考えない)
既知債務 = 移行開始時点で未履行であった義務を全件列挙して封印したもの
未達     = 導出概念(対象計算が未達 ⇔ その対象の義務が 1 件以上未履行)
```

**軸①の終了条件も軸②の停滞判定も `残務数` 一本。**

### 4-4. 委任② — 解消の判定方法(決定: 2026-09-12)

> **解消は二値である。「部分的に充足」という状態を作ってはならない。**

| 判定 | 条件 |
| --- | --- |
| **解消** | 当該要素が指す事項の充足が、**本規定による免除を適用しない生の検査結果**で示されたとき(`BOOT-PROGRAM` 逐語) |

>
> **未解消件数は `封印集合 − 解消済み集合` として導出する。** **毎回 生の検査を走らせて数え直さない。**
> **解消済み集合への追加は「免除を適用しない生の検査結果」で示したときに 1 度だけ行い、
> 以後その要素を再検査の結果で戻さない**(`BOOT-SEAL-MONOTONE` ②③)。

## 5. `D`(履歴文脈の検査上限)の導出

### 5-1. FR-006 単独で長さ 4 を導く

要件書 `FR-006 補足` 逐語(research.md §6-11 で実在確認済み。**行番号ではなく条項で指定する** — §2-1):

> undo を適用した後は、取り消された操作の 1 つ前の取消可能な操作が次の対象になる
> (例: 状態補正 → プレイ → undo は当該プレイを取り消し、続く undo は状態補正を取り消す)。
> 取消可能な操作は「確定プレイ」と、FR-040 を採用した場合の「状態補正」(**未採用なら確定プレイのみ**)とし、
> **undo 自身は取消可能な操作としない**

→ **FR-040 が Should で採否未決のままでも** `プレイA → プレイB → undo → undo` が成立し、
**長さ 4 の必須 case** になる。**FR-040 を含む case から下限を導いてはならない**
(非採用時に `ADR-003` の補正 case が外れ、下限が残らない)。

### 5-2. `D+1` に出力同値を課さない

要件書 `NFR-019(a)` が出力に**遷移後の履歴スタック全体**(各要素は種別と差分。先頭 1 件だけではない)を
要求するため、**深さが違えば出力も違う**。「`D` と `D+1` で出力が変わらない」プロパティは**原理的に不成立**で、
かつ `D+1` は保証範囲外なのに同値を要求すると**保証範囲を事実上拡張**する。

> **`D` = max(必須シナリオ長, スタック種別の全等価分割を覆う最小深さ)** として**具体値を固定**する。
> **`D+1` では「拒否・切り詰めをせず実行できる」ことだけを検査し、出力同値は求めない。**

**深さ・構成・シナリオ長の全 case 集合を資産へ固定する**(要件書 `NFR-018 (b)` の「集合を固定する」を
満たすため、下限のままにしない)。導出は **case → 長さ → 最大値の式**として機械可読にする。

### 5-3. 値域 schema

**主要フラグ 9 項目**(`ADR-003 D-11 ② 入力範囲表`)= 回・表裏・得点・S/B・アウト・打順・走者・タイブレーク中・試合終了済み。
v0.2 で**変わっていない**。

先頭 0 / 丸め / 分母 / 符号 / 代替文字列 / **オーバーフロー軸の整数範囲上限**。
`ADR-003 D-1 正本の射程行` が「**1 つでも欠けた宣言は fail**」を要求する。

丸めモードの正は要件書 `付録A-1 共通規則`: **四捨五入(round half up)。負値のちょうど中間値は

## 7. 経路一致検査

### 7-1. 不変の骨格

**5 判定**と**6 次元要求集合 `(calculation, vector, case, runner, entrypointId, directTargetId)`** は
v0.2 でも**不変**(`ADR-003 D-11 ③ 経路一致検査の理由`)。**証跡直積は崩さない**(`ADR-003 D-11 ③ 動的機構の禁止行`)。

### 7-2. 収集器の入力契約の拡張

`ADR-003 D-11 ③ 経路一致検査の理由` 逐語(要旨): 収集器はアダプタから**生の出力・実行した artifact の hash・
(β) では実際に発行された SQL 文または AST**、さらに **composite target では各段の入力と出力**
(SQL 結果集合・受け口の入力と型付き出力・〔3 段では〕formatter の入力と最終文字列)を受け取り、
**等値判定(composite では値の連鎖検証を含む)は収集器が計算する**。

`ADR-003 D-11 ③ 動的機構の禁止行` はこれを「**「収集器の入力契約」の共通契約の一部であり、composite を持つ対象計算では必須 —
局所規定ではない**」と明記。→ **アダプタの自己申告を排除する構造は維持したまま、段別 I/O を必須入力に加える。**

### 7-3. lossless — 表示値に正規化を置かない

`ADR-003 D-11 ③ 動的機構の禁止行` 末尾「**表示値の比較は文字列の完全一致**(comparison の lossless 原則のまま —
**表示値に正規化変換を置かない**)」。`ADR-003 D-8 比較面表 座標変換行` も「**比較器は正規化しない**」。

→ 比較器は**丸めない・正規化しない**。文字種(MINUS SIGN `U+2212`・半角/全角)・先頭 0・負号・
剰余表記まで一致対象。型統一は **scaled integer・exact decimal への情報保存変換に限る**。

### 7-4. 恣意的迂回は保証範囲外 — 「検出する」と書いてはならない

`ADR-003 D-11 ③ 動的機構の禁止行` の PO 裁定(2026-09-03)逐語:

> アダプタが**恣意的に整合する値と現行 hash を提出して中段・終段を迂回する場合の完全排除は保証範囲外**
> (残余リスクとして明示 — 任意コードの実行証明は意味判定に帰着するため保証しない)
> (hash は「宣言どおりの生成物か」・連鎖は「提出された値が宣言された全段の入出力として整合しているか」を
> それぞれ検証する — **迂回・自前整形の実装は連鎖の欠落・不一致と構成検査〔(b)③〕の差分で検出される**
> (分担は確定のとおり — **変異テストは formatter 等の生成物自体の実効性を担い、
> scale=0 では迂回が等価変異になり得るため迂回の検出手段には数えない**))

**敵対 fixture は 4 種 + 1 記録**:

| # | fixture | 期待 |
| --- | --- | --- |
| 1 | 偽 SQL | fail |
| 2 | **段別 hash 不一致**(段数分に多重化) | fail |
| 3 | 期待値直返し | fail |
| 4 | **値の連鎖不整合**(前段出力 ≠ 後段入力) | fail |
| 5 | **恣意的迂回**(整合する値と現行 hash を提出) | **保証範囲外として明示的に不検出であることを記録する** |

**「迂回を検出する」合格条件を書くと `ADR-003` の決定と矛盾する。**
かつ **アダプタが `true` を 5 個返すだけでは通らない**ことを示す。

**軸の組合せ要件**: **丸め境界(直前・一致・直後)× 符号(正・負)は直積で必須**とし、
**負値の丸め境界一致(負のちょうど中間値)を必ず含める**(片側の符号だけで境界軸を消費した false green を許さない)。

(丸め境界 `.3335` / 負の中間値 `-1.5` など)。**製品の対象計算ごとの実ベクタ case 値は TSK-236〜239 に残す。**
→ `ADR-003 D-11 ② 入力範囲表 状況判定行` の「具体ケース値は TSK-235 で確定」と `plan.md` §2 の「実ベクタの中身を作らない」は
この分界で両立する。

runner は **生値 → 生成済み正規化 → 正規化後値の照合 → 計算入力**の順を強制し、
**正規化を素通りさせた入力を fail** させる。**全 case 消費**・**未知 field / 重複 ID の拒否**も維持。

### 8-6. DB を使う runner の運用上の罠(TSK-317 からの申し送り 2026-09-10)

**(β) の SQL プロパティテストは実 PostgreSQL を使う**ため、TSK-317 が実測した 2 件が本タスクにも該当する。
**復旧手順はどの正本にも書かれていない**(TSK-317 が台帳候補として起票予定)。

**罠 1: `idle in transaction` の観測接続が DDL を永久に止める**

`ALTER TABLE ... OWNER TO` は ACCESS EXCLUSIVE を要求するため、**対象表へ触った接続が 1 つでも
`idle in transaction` で残っていると永久に待つ**(読み取りだけの接続でも同じ)。
TSK-317 は「1 点 10 分 48 秒」の処理時間だと思っていたものが**待ち時間**だったと確定している。

診断:

```sql
SELECT a.pid, a.state, pg_blocking_pids(a.pid), left(a.query, 70)
FROM pg_stat_activity a
WHERE a.datname IS NOT NULL AND a.pid <> pg_backend_pid()
ORDER BY a.query_start;
```

`pg_blocking_pids` が空でない行があれば因果が確定する。**`state = idle in transaction` の行が犯人。**

**罠 2: 強制終了で teardown が飛ぶと以後の全 DB テストが error になる**

使い捨てクラスタのコンテナと開発 DB の `pitchlog_test_role` が残り、**残存ロールを fixture が
fail-closed で弾く**ため。復旧:

```
docker ps -aq --filter 'name=pitchlog-authz' | xargs -r docker rm -f
DROP OWNED BY "<role>";   -- 先に打たないと次が依存で失敗する
DROP ROLE "<role>";
```

→ **本タスクの (β) runner は、DDL 適用前に観測接続を閉じる契約を持つ**((β) runner の合格条件へ)。

**是正の実測(TSK-317・2026-09-10)**: 修正は **観測後に `rollback()` を発行する 1 行だけ**だった。

| | 修正前 | 修正後 |
| --- | --- | --- |
| 1 点 | **10 分 48 秒で未完**(ロック待ち) | — |
| 6 件 | — | **27.67 秒** |
| DB テスト全体 | **28 分でタイムアウト** | **109 passed / 5 分 37 秒** |

**設計は正しく、トランザクションを閉じていなかっただけ**である点がこの型の怖いところ。
**「処理が重い」と誤診して最適化へ向かうと直らない** — 先に `pg_blocking_pids` で待ちか処理かを切り分ける。

## 11. core-guard の基線機構

### 11-1. 「他領域 byte-for-byte 不変」には基線が必要

**実測(research.md §6-5)**: 期待値は `tests/test_core_guard.py` の Python リテラル
`EXPECTED_AREA_PATHS` と `EXISTING_REAL_GUARD_PATHS` + `NEW_GUARD_PATHS`。
**「変更前の姿」を保持する機構が無い**(外部基線も封印 digest も無い)。

→ 「他領域が不変であること」は**同じコミットで編集可能なリテラルとの一致**としか表現できず、
**delta 検査になっていない**(トートロジー)。

**採る方式**: **`guard_paths` が既に採っている二層方式**(`EXISTING_REAL_GUARD_PATHS` = 据え置き /
`NEW_GUARD_PATHS` = 追加分)を **area paths にも導入する**。既存前例があり最小変更。
封印は §4 の債務台帳と機構を共有する。

**旧計画書の誤り 2 件**: 該当 2 箇所の行参照は失効(**行番号を引き写さない** — §2-1)。
「他 **4** 領域」は誤り — areas は 5 件・変更対象が 2 件なので **他 3 領域**。

### 11-2. 「自己作成の期待値で完全性を証明」からの脱出

develop の `03c41ca` が**同一コミット**で `.claude/core-areas.json` と `EXPECTED_AREA_PATHS` と
`NEW_GUARD_PATHS` に**同じ行**を追加した実例が残っている(research.md §6-5)。
既存の完全一致テストは**登録漏れを検出せず、登録者が期待値を同時に書き換えれば必ず green になる**。

**◎ 方式は base 側 commit アンカーに一本化する(3 周目 P1-4 の是正)。**

当初は「**独立導出または commit アンカー**」と選択式に書いていたが、**これは弱い**。
**独立導出を本 PR で新設すれば、JSON・規則・期待値を同時変更する新しい自己 oracle を作れる**ため、
`03c41ca` 型の負例を避けられない。

→ **比較元を PR head から、変更不能な merge-base の blob へ移す。**
**JSON・期待値・アンカーの 3 点を同時変更しても fail する**履歴 fixture を置く
(`03c41ca` 型の負例は JSON と期待値だけを変えるが、**導出規則やアンカーまで同時更新する攻撃**を
必須化していなかった)。

**リポジトリ内の前例**: `scripts/check_authz_catalog.py` の `_expected_cell_decision`
(規則の唯一の実装で資産と突合)/ commit アンカー型(research.md §5 に典拠)。
**独立導出は補助として併用してよいが、基線の正は commit アンカー**とする。

### 11-3. core-guard は領域を見ない

`scripts/core_guard.py` が**全領域の `paths` を 1 本の tuple へ平坦化**してから
`fnmatch.fnmatchcase` で判定する(`guard_paths` は完全一致・area paths は `fnmatch`)。

→ **「`game-state` と `data-migration` の両方へ登録した」ことを core-guard の発火では検証できない**
(片方だけでも等しく発火する)。**合格条件は「JSON の両 area 配列の包含」で書く**(**集合差**型)。

### 11-5. `areas[].paths` は完全列挙ではなく glob で足す(TSK-343 からの申し送り 2026-09-10)

**`fnmatch` の `*` は `/` を跨ぐ**ため、`areas[].paths` は glob で下位ディレクトリまで覆える。実測:

```
True   backend/domain/*      vs  backend/domain/sub/manifest.json
True   backend/*conftest.py  vs  backend/tests/db/conftest.py
```

**完全列挙は脆い** — 後から足したファイルが**黙って未登録**になり、台帳 `H-12`
(コードを入れたのに paths が未充填で非発火)の再発型になる。**glob なら自動で覆われる = fail-closed。**
設計書 6.3-④ が「**過剰包含は PR 単位の例外で外さず、モジュール分割で境界を切ってから paths を狭める**」と
定めていることとも整合する(過小包含より過剰包含に倒す)。

**同一ファイルに前例がある**(実測 2026-09-10):

| area | paths | glob | 完全列挙 |
| --- | --- | --- | --- |
| `game-state` | 27 | **0** | 27 |
| `data-migration` | 6 | **0** | 6 |
| **`tenant-isolation`** | 22 | **4**(`contracts/authz/*` / `tests/fixtures/authz_claims/*` / `backend/tests/db/*` ほか) | 18 |

**表記の注記**: `fnmatch` は `*` と `**` を**同じに扱う**(どちらも `.*` へ変換される)。
`sync-protocol` の `tests/fixtures/sync-protocol-failures/**` は表記上の区別にすぎず、意味は `*` と変わらない。
**`**` を書いても深さの制御はできない**ので、`*` に揃えるか `**` を「意図的に深く覆う」印として使うかは
表記の選択にすぎない(TSK-343 の実測 2026-09-10)。

→ **本タスクは `game-state` / `data-migration` へ glob で足す**(`backend/domain/*` /
`backend/src/pitchlog/generated/*` / `frontend/src/lib/generated/*` 等)。
**完全列挙が必要なのは `guard_paths` のみ**(完全一致の frozenset なので glob が効かない — §11-3)。

### 12-1-b. ◎ 「気づいた瞬間に止める」を機械条件で書く方法(P1-5 との衝突の解き方)

**TSK-355 が投げた未解決の論点**: 既存 15 件は「〜できない」という**判定の失敗**を条件にしているが、
16 件目が捉えるべきは「**判定できないことに気づいた時点**」であり、
**判定を試みて失敗するより前**かもしれない。これは P1-5(トリガーごとに
`evaluationMethod`・判定者・証拠資産・発火値を固定する)と正面からぶつかる。

**解き方 — 「気づく」を「着手前の前提照合」へ置き換える。**

`bootstrapDebt` を発明してしまったときに実際に起きたのは「正本に授権が無いと**気づいたのに設計で回避した**」
ではなく、「**そのステップが何に依拠しているかを、着手前に正本と突き合わせなかった**」である。
後者なら機械化できる:

> **トリガー 16(改)**: **当該ステップが依拠する授権の条項 ID が、正本に実在しない。**
>
> - `evaluationMethod`: **文言存在型**(§2 の型)。各ステップの資産に
>   「このステップが依拠する正本の条項 ID」を宣言させ、**逐語が正本に実在するかを照合する**
> - 判定者: **機械**(実在しなければ fail)
> - 証拠資産: ステップごとの依拠条項リスト
> - 発火値: **1 件でも実在しなければ発火**

**これで「気づいた瞬間」が「着手前の定例チェック」になり、気づきに依存しなくなる。**
既存 15 件と同じ不能形(「実在しない」)でもあり、文型も揃う。

**◎ このトリガーが必要である実証(次のレビューでの弁護材料)**:
**「空いている枠を埋めているのか / 例外を新設しているのか」は主観では判別できない。**
現に**同一原典から同じ誤読が 2 回生じている**:

1. **本タスク(2026-09-01〜09-10)**: `bootstrapDebt` を「もともと空いていた枠を埋めるもの」と認識して
   設計を続行 → 3 周目 P0-1 で「正本の授権が無い」と否決
2. **TSK-355 の 1 周目(2026-09-10)**: 同じ発明を見て「**fail-closed の例外ではなく未定義の空枠を埋める**」と
   立てて否決。「段階 1 は作業順序を定めているだけで既存のマージ条件を解除していない」が理由

**◎ 交絡の明示(TSK-355 の指摘 2026-09-10 — この弁護材料を使うときは必ず添える)**:
**2 件は完全に独立ではない。** TSK-355 の 1 周目は**本タスクの `bootstrapDebt` という既存の設計を読み、
その立て方を引き継いだ**結果である。

**それでも証拠として成立する理由**:

- **担当・タスク・レビュアはすべて別**
- **TSK-355 は原典(`ADR-003` 帰結 1 の段階 3 の括弧書き)を自分で読んだうえで同じ結論に達した** —
  本タスクの結論を鵜呑みにしたのではなく、**同じ原典から同じ誤読をしている**

→ 主張は「**完全に独立な 2 事象**」ではなく「**同一原典から独立に同じ誤読が生じた**」が正確。
この形なら交絡の指摘に耐える。**過大に主張すると次のレビューで潰される**ので、
**弁護材料として使うときは交絡を先に明示する。**

**示せること**: 「注意すれば気づける」類の失敗ではない。
**示せないこと**: 誤読の発生率や、設計を見ていない第三者でも同じ誤読をするか。

条項 ID の実在照合なら**その場で機械が答えを出す**ので、主観の判別に依存しなくなる。

**副産物**: この機構は §2-1(provenance を条項 ID で持つ)と同じ資産を使う。
**行番号参照の陳腐化対策と、授権の実在検査が同じ機構で閉じる。**

#### 12-1-b-1. 「ID は同じまま内容が変わる」への対処(TSK-355 の指摘 2026-09-10)

**限界の指摘**: ID の不在・削除は捕まえられるが、**ID が同じまま条文の内容が変わる**場合は捕まらない。
逐語照合にすると捕まるが、**表現の些細な調整でも発火する**(TSK-355 の確定ゲートは
TSK-278 の前例で 27 周・指摘 88 件なので、反映のたびに本タスクの検査が赤くなる)。

TSK-355 の折衷案は「**条文に規範の要旨を 1 行持たせ、ID + 要旨で照合**」だが、
**要旨を誰が更新するかという運用規律に戻る**ため採らない。**気づきに依存しない**という
本トリガーの設計方針と矛盾する(**提案者自身がその懸念を書いている**)。

**採る方式 — 2 層に分ける。依拠先を `approved` 版に限定する。**

| 層 | 検出 | 判定 | 扱い |
| --- | --- | --- | --- |
| **① ID の不在** | 依拠する条項 ID が正本に無い(最初から無い / 撤回された) | **機械** | **トリガー発火 = 停止**(§12-2) |
| **② 内容 digest の変化** | ID は在るが条項の内容 digest が pin と違う | **機械が検出・人間が判断** | **`[手動]` の再確認**(依拠が生きているかを見る)。**自動停止にしない** |

**確定ゲート中の偽発火は「依拠先を `approved` 版に限る」ことで消える**:

- **`in-review` の条文には依拠しない。** TSK-355 の確定ゲート中(27 周相当の表現調整)は
  **本タスクが依拠していない**ので、検査対象にならない → **赤くならない**
- **`approved` になった時点で digest を pin する。** 以後の変更は
  AGENTS.md 絶対規則 4 の改訂ゲート(7.6 の決定表)を通るため、**頻度が低い**。
  そのとき②が検出するのは**正しい**(正本が改訂されたら依拠を見直すべき)

**非対称の維持**: **改名 = 偽発火なので条文側が禁止**(TSK-355 が受諾済み)/
**削除 = 真発火なのでそのまま停止**(授権が撤回されたなら止まるべき)/
**内容変化 = 再確認**(停止まではしない)。

**帰結**: 本タスクの資産は、依拠ごとに **`{条項 ID, 依拠時点の版, 内容 digest}`** を持つ。
版が `approved` でないものを依拠先に書けないことも機械検査する。

#### 12-1-b-2. 条項 ID 対応表の形式(**2026-09-11 に TSK-355 と確定**)

**確定した列**:

```
条項 ID / 規範の所在 / 範囲の切り出し規則 / 版と status(行ごと)/
superseded_by / kind(規範・補足)/ 要旨(検査の入力ではない旨を明記)
```

**確定した規約 2 件**: ① digest 計算前の正規化 ② ID の名前空間(既存 ID の実測つき)

**不一致が出たときの負担の所在(相互合意)**:

- **実装してみて列が足りない** → **本タスクの見落とし。本タスクが吸収する**
- **条文を書いてみてこの形式で表現できない** → **TSK-355 の見落とし。TSK-355 が形式に合わせる**
- 理由: **形式のほうが後から動かしにくい**(本タスクの検査機構が依存するため)。**条文を曲げるほうが安い**

以下は確定に至った経緯と各列の根拠。

**当初の提示(2026-09-11)**

TSK-355 が条項 ID を**条文と対応表の両方の形**で出す。**本機構が成立するために必要な列**:

| 列 | 必須 | 用途 |
| --- | --- | --- |
| **条項 ID** | ✅ | 依拠宣言のキー |
| **規範の所在**(正本ファイル + 条項名) | ✅ | どの正本のどこか |
| **◎ 条項の範囲の切り出し方** | ✅ **追加要求** | **digest の対象範囲**。「表の 1 行」「見出し `X` から次の見出しまで」等、**機械的に一意へ切り出せる規則**。これが無いと **digest が定義できず②(内容変化の検出)が成立しない** |
| **◎ その条項の版と `status`** | ✅ **追加要求** | **依拠先を `approved` 版に限る**検査の入力。行ごとに持たないと、改訂中の条項へ誤って依拠しても検出できない |
| **◎ ID の名前空間規約** | ✅ **追加要求**(表ではなく規約として) | 既存の `NFR-018 (b)②` / `AUTH-*` / `CATALOG:*` / 台帳の `H-12`・`P-01` と**衝突しない接頭辞** |
| 一行の要旨 | — | **人間向け。本機構の入力にしない**(§12-1-b-1 で要旨方式を却下済み。**後から誰かが検査へ配線しないよう明記する**) |
| `superseded_by` | 任意 | **条項の分割・統合時**の追跡(下記) |

**条項の分割の扱い(解決 2026-09-11)**: 改名は禁止したが、**1 条項が 2 条項へ分割される**場合は
「旧 ID の削除 + 新 ID の追加」に見え、**削除 = 真発火(停止)**の規則では**規範が生きているのに停止する**。
→ **`superseded_by` を必須列にすることで解決**(TSK-355 が受諾)。「撤回」と「分割・統合」を区別し、
後者は**②の再確認**へ落とす。

#### 12-1-b-3. digest の安定性に要る 2 件(TSK-355 へ追加提示 2026-09-11)

**どちらも「規範は変わっていないのに digest が変わる」= 偽の再確認を大量に出す形。**
確定ゲート 27 周の前例があるので、**どちらも起きる前提で決めておく。**

**(1) digest 計算前の正規化規約**

正本は日本語 Markdown で**行を手で折り返している**。**折り返し位置を変えるだけ**(reflow)で
生テキストの digest は変わるが、**規範は変わっていない**。

→ **提案**: digest の計算前に **空白の連続を単一空白へ畳み、行末空白と改行を正規化**する。
それ以外は無加工。これで **reflow では発火せず、語句の変更では発火する**。

**注意**: §7-3 の「**比較器は正規化しない**」は**表示値の比較**の規約であって別物。
**混同しないよう、両者を別の名前で呼ぶ**(表示値比較 = lossless / 条項 digest = 正規化あり)。

**(2) 表形式の条項での digest 対象**

条項が「**表の 1 行**」の場合、**表に列が 1 つ追加されると全行の生テキストが変わる**ため、
**全条項が一斉に再確認になる**。→ **digest の対象を「行全体」ではなく「規範を担うセル」に
限れるか**を、範囲の切り出し規則の中で扱ってもらう。

**(3) `kind`(規範 / 補足)列 — 追加要求**

TSK-355 は計画書で **§4-12 を「規範」と「経緯」に割っている**。条文でも同じ区別が生じる。
**本タスクが「補足・経緯」の行へ依拠してしまうと、規範でないものを授権として扱う**ことになる。

→ **`kind` 列を持たせ、「依拠先が `規範` でない行なら fail」を機械検査する。**
これは **3 周目 P0-1 の再発防止そのもの**(授権でないものを授権として扱った失敗)。

### 14-1. 新設ジョブが DB を使うなら `services: postgres` が要る(暗黙結合)

**TSK-317 の実測 + 本タスクでの追認(2026-09-10)。** (β) の SQL プロパティテストは実 PostgreSQL を
使うため、**CI 配線ステップで踏む**。

**機構**: 使い捨てクラスタは `backend/tests/db/conftest.py` の **`--pull=never`** で起動する。
CI runner には image が無いはずなのに動くのは、**`ci.yml` の `services: postgres` が同じ image tag を
pull し、それが local の image cache に入る**ため。**`ci.yml` に `docker` の明示的な言及は 0 件**(実測)。

**既存の防波堤**: `tests/test_ci_wiring.py` が
**`backend.services.postgres.image` = `environment-expectations.json` の期待値 = `docker-compose.yml`** の
**3 者一致**を要求する。image tag を片方だけ変えると `--pull=never` が CI で落ちるので、この検査が守っている。

**◎ ただしこの検査は `backend` ジョブだけを見ている**(`_mapping_at(backend, ("services", "postgres"))`)。

→ **本タスクが新設する `consistency` / 変異ジョブが DB を使うなら、そのジョブにも同じ tag の
`services: postgres` が必要なのに、既存検査はそれを要求しない。** §14 の
「全葉変異の母集団が `backend` ジョブの `services`〜`defaults` 手前に限定」と**同じ穴が image 結合にもある**。

**CI 配線ステップの合格条件へ入れるもの**:

- **DB を使う全ジョブ**について `services: postgres` の image が 3 者一致すること(**`backend` に限定しない**)
- **新設ジョブに `services: postgres` を書き忘れると red になる**負例(現状は静かに `--pull=never` で落ちる)
- `services` を持たないジョブが DB テストを呼んでいないことの検査

**このステップは敵対レビュー 3 周目 P0-7 で「28 ステップのどこにも無い」と指摘されたもの**であり、
**2026-09-12 に計画書のステップ 53 として復元済み**。本節の 3 条件を合格条件へ入れた。

**所有の確定(TSK-317 の実測 2026-09-10)**: **3 者一致検査の一般化は本タスクが持つ。**
TSK-317 の計画書に **`ci.yml` / `.github` への言及は 0 件**(実測)で、**TSK-317 は `ci.yml` を一切変更しない**。
同タスクの `S-8` の `test_ci_wiring.py` 追記は**既存の配線が保たれることの固定**であってジョブの追加を伴わない。
→ **DB を使うジョブを新設するのは本タスクだけ**なので、一般化の動機も本タスクにしかない。
順序も合っている(本タスクは TSK-343 の後・TSK-317 の改訂 3 の前に入る)。
**TSK-317 の改訂 3 では「本タスクが一般化した検査を壊さないこと」だけを確認する。**

**負例が要る理由(TSK-317 の確定ゲートで 4 周繰り返した型)**: 「検査を足した」だけでは実効を持たない。
条件 2(**新設ジョブに `services: postgres` を書き忘れると red**)は、**書き忘れが実際に red になることを
負例で確かめる**まで満たしたことにしない。満たさないと**静かに `--pull=never` で落ちる**失敗モードが残る。

## 16. 再開時の自己点検(TSK-355 の確定ゲートで実証された 2 つの型)

### 16-1. 「送り先が空手形になる」型

TSK-355 は PO 裁定で機械条件を `design.md` へ送ったところ、3 周目に

2. 回答を「**正本へ条文化 / 実装へ明示委任**」へ**写像する表**を作り、**写像漏れを停止条件**にする

**言い換えの瞬間には検出できない。**

| **③ 停滞** | `BOOT-STALL`「**未解消件数が減少した時点**」でエポック開始 | **前回値との比較** |

**◎ ①は同値ではない。** **正本が要求するのは一覧であって件数ではない。**
**件数だけを出力する実装は `BOOT-REPORT` を満たさず、「出力のない緑は本規定の充足とみなさない」に当たる。**
→ **ステップ 19 の成果物は一覧を持ち、件数はそこからの導出とする**(既にそう書いてある。**本突合で裏が取れた**)。

**◎ ②と③は同値だが、算出方法を誤ると破れる。**

**`BOOT-SEAL-MONOTONE` ②が「一度解消した要素が再び未解消となること」を不合格とする**ため、
**未解消件数は単調非増加**である。したがって「減少した」と「0 になった」は矛盾しない。
**ただしこれは「解消済み集合(追加のみ可能な単調集合 — `BOOT-SEAL-MONOTONE`)から導出する」場合に限る。**

> **⚠ 毎回 生の検査を走らせて未解消件数を数え直す実装にすると、②と③が破れる。**
> **検査が不安定なら件数が増えうるが、増加は `BOOT-SEAL-MONOTONE` ②で不合格**になる。
> **fail-closed としては正しいが、「停滞の測定」が検査の安定性に依存する**ことになり、
> **`BOOT-STALL` の「マージ回数で測る」という設計意図(時間や外部要因で動かない)と衝突する。**

→ **委任②への追加の拘束**: **未解消件数は `封印集合 − 解消済み集合` として導出する。**
**解消済み集合への追加は「免除を適用しない生の検査結果」で示したときに 1 度だけ行い、
以後その要素を再検査の結果で戻さない**(`BOOT-SEAL-MONOTONE` ②③)。
**生の検査は「解消済みへ追加してよいか」の判定にのみ使い、件数の算出には使わない。**

**限界**: **本突合は「未解消件数」という語に限った**(§16-11 の追跡範囲の制限)。
**他の語(「実在集合」「対象」「発効」)の用途分岐は見ていない。**

#### 16-7-0. 派生: 実装側の可否判断でしか出ない穴(台帳候補・提出は TSK-355)

**§16-7 より射程が広い形。接続部でなくても起きる。**

> ~~**レビュアは条文を条文として読むため、この露出の仕方をしない。**~~ → **反証済み(2026-09-13)**
>
> **残る主張(弱い形)**: **実装側は「自分にできるか」という問いから読むため、この種の穴を見つける
> 経路を持つ。ただしレビュアも見つけうるので、代替ではなく重複した経路である。**

**◎ 反証のデータ点**: TSK-355 の確定ゲート **2 周目 指摘 8** が、**目的を与えていない通常の依頼文で、
同型の穴を自力で発見した**:

> **最終条項 `BOOT-ACTIVATION` の digest 終端が未定義。** 対応表は各条項を「次の `BOOT-` の直前まで」と
> するが、最終の `BOOT-ACTIVATION` には次の `BOOT-` がない。…**変更検知の実効性が確定しない**。

**これは「実装判断を妨げる未定義の語」そのもの**(本タスクの照合機構が digest を計算するとき
**どこで切るか決められない**)。**条文を条文として読んだレビュアが、実装が困ることを見つけた。**

→ **「実装側でないと見えない」は反証。** 「同一の変更」が 6 周 + 初周を通過して残ったのは事実だが、
**タイミングの問題だった可能性が高い。**

**実例(1 件)**: `BOOT-ACTIVATION` の「**同一の変更**」の単位が未定義だった件。

**◎ 限界(§16-3 の規律を自分の観察へ当てる)**:

| | 内容 |
| --- | --- |
| **示せること** | この 1 件は、6 周 + 初周のレビューでは出ず、実装側の可否判断で出た |
| **示せないこと(1)** | **n = 1。** 1 例では傾向と言えない |
| **示せないこと(2)** | 「**レビュアには見えない**」は示せていない。示せるのは「**6 周 + 初周では出なかった**」まで。**次の周で出た可能性は排除できない** |
| **示せないこと(3)・交絡** | **読む範囲と目的が違う。** 本タスクは `BOOT-ACTIVATION` の当該規定**だけ**を、**特定の目的**(自分のステップ分割の可否)で読んだ。レビュアは**全文**を**条文として**読む。→ **「実装側だから見えた」のか「狭く目的を持って読んだから見えた」のかが分離できていない** |

**(3) は対立仮説として強い。** もし後者なら、**規律は「実装側に読ませる」ではなく
「狭く目的を持って読ませる」**になり、**対処が変わる**(レビュアに「この規定に従って動けるか」という
目的を与えれば足りる)。

**◎ 実験は取りやめ(2026-09-13)** — **支持側のデータが先に取れてしまい、情報量が下がった**ため。当初の設計は次のとおりだった:

> 各 `BOOT-*` 条項について、「**この規定に従って実装する側が、自分の作業がこの規定を満たすか
> 判断できるか**」を問うこと。判断に必要な語が定義されていない箇所を挙げること。

**◎ ただし帰無結果が判別力を持たない(本タスクから指摘・結果の解釈に効く)**:

| 結果 | 解釈 |
| --- | --- |
| **穴が出る** | 「目的を与えればレビュアでも見える」を**支持する**(ただし下記の条件つき) |
| **穴が出ない** | **判別できない。** ①実装側でないと見えない ②**そもそも残っている穴が無い**(2 周のゲートと反映を経た後なので、条文が既に清潔な可能性)の**どちらか分からない** |

**→ 結果を「見つかったか」で読まない。「見つかったものの性質」で読む。**
**同型の穴**(実装判断を妨げる未定義の語)**が出たときだけ支持**とする。
別の種類の指摘が出ても、それは**観点を 1 つ足した効果**であって仮説の支持にはならない。

**本質的な限界**: **「同一の変更」の穴は既に発見済みで、un-find できない。**
**同じ条文で対照実験は組めない。** したがって**この実験は一回性で交絡を含む**。

**2 つの対処は排他ではない**(先方の指摘): 接続部の欠陥(先方の初周で出た 2 件)は
**目的を与えても条文だけ読むレビュアには見えない**。**別の穴なので、接続先を渡すのをやめる理由にはならない。**

**◎ 反証後の限界**: **n = 2**(発見側 1・反証側 1)。
**どちらが早いか・どちらが多く見つけるかは示せない。**

### 16-11. 依頼文の観点は「数」ではなく「1 つあたりの追跡範囲」が上限を決める

### 16-10. 一般形の条文と、特定タスクへの適用結果を分けて扱う(台帳候補・提出は TSK-355)

**本タスクが 2 度示した構造(2026-09-14)**:

| 場面 | 結論 |
| --- | --- |
| 封印要素数の実測(§3-2-f) | **不在の配列は展開できない** → 配列要素単位でも件数は増えない |
| 委任①の粒度決定(§3-2-h) | **不在の composite に内部構造は無い** → A/B/C のどれでも同じ |

**共通するのは「粒度の議論は、実在する構造に対してのみ意味を持つ」。**

**◎ ただし「粒度」で書くと射程が狭い。** 一段上の形で書く:

> **一般形の条文に対する指摘が正しくても、特定タスクへの適用結果では空振りすることがある。**
> **条文側は一般形を維持したまま、適用側が「自分の文脈では観測不能」と返せば、実装は一意に決まる。**

**実例**: TSK-355 の 8 周目 指摘 1(「粒度が一意に決まらない。未解消件数と失効時点が分岐する」)は
**条文の一般形に対しては正しい**が、**本タスクの文脈では成立しない**
(**開始時点で全対象が未登録なので、3 つの読みが同じ封印集合を与える**)。
→ **条文は変えず、実装側が A で確定**して解決した。**指摘は不採用にしない**(一般形には効くため)。

**なぜ有用か**: **条文側が「一意でないから直さねば」と一般形を歪めるのを防ぐ。**
**適用側が空振りを返せば、条文は一般的なまま、実装は一意になる。**

**限界(§16-3)**:

| | 内容 |
| --- | --- |
| **示せること** | 本件で条文を変えずに解決した。**2 度とも同じ構造**(不在のものに内部構造は無い) |
| **示せないこと(1)** | **n = 2、同一タスク対**。別の設計者・別の領域での再現は無い |
| **示せないこと(2)** | **本タスクは「開始時点で全対象が未登録」という特殊な状況**。**一般には粒度の議論は空転しない** |
| **示せないこと(3)** | **空振りの判定を適用側が誤ったとき、条文の欠陥が見逃される。** 本件では D-11 の逐語で裏を取ったが、**裏が取れない場合の扱いは示せていない** |

**それ以外は参照に留める**(条項 ID + 要旨)。**引き写した箇所には「引き写しである」ことを

### 16-6-a. 合格条件は 3 類型に分かれる — 「正例」の欠落を数えた(実測 2026-09-13)

**TSK-355 の指摘**:「**成功すべきものが成功することを確かめないと、全部 fail する実装が通る**」。
**本タスクの合格条件を全 29 ステップで計測した。**

**◎ 計測して分かったこと — 類型は 2 つではなく 3 つある**

当初「負例 / 正例」の 2 分類で数えようとしたが、**多数のステップが third category に落ちた**:

| 類型 | 内容 | 例 |
| --- | --- | --- |
| **負例** | **不正な入力で fail する** | 「未対応 1 件で fail」「重複 ID の拒否」「escape 0」 |
| **正例 A(例外的遷移)** | **成功すべき遷移が成功する** | 「昇格が成立する」「失効が成立する」 |
| **正例 B(通常動作)** | **機構が実際に機能する** | 「**正当なものを実際に通す**」「空入力で generator は exit 0」 |
| **性質表明** | **成果物がある性質を持つ**(機構の動作ではない) | 「語彙 schema の exact-set」「単位パラメータが存在しない」「差分がパス allowlist に収まる」 |

**◎ 正例を 2 つに割る必要がある(2026-09-14 に判明・TSK-355 の 5 周目から)**

当初は「正例」を 1 つの類型としていたが、**それでは deny-all 実装を排除できない**。

**先方の 5 周目の指摘(唯一の非起因 = 初周から欠けていた)**:

> `BOOT-ACTIVATION` が要求する正例は**自動昇格と失効だけ**。**正当な封印要素について実際にマージを
> 許す `BOOT-GRANT`、失効後の再承認で授権が回復する `BOOT-REAPPROVAL`、要求が揃ったとき実際に
> 発効する `BOOT-ACTIVATION` の正常系がない。**
> **すべての PR・再承認を拒否する実装でも負例と 2 つの正例を満たせる。**

→ **正例 A(例外的遷移)だけでは足りない。正例 B(通常動作)が要る。**
**先方は 4 周目に負例を直して正例を 2 つ足したが、「機能すること」の正例を足していなかった。**

**◎ 本タスクにそのまま当たる**: 私の合格条件は「〜で fail する」ばかりなので、
**すべてを拒否する実装が私の検査を全部通る**。**再開時の目視分類は 4 類型で行う。**

**「全部 fail する実装」を通すのは負例だけでなく性質表明も同じ** —
**成果物の形だけ見ていて、機構が動くことを見ていない**ため。

**実測(キーワード法・下記の限界あり)**:

```
「正しい入力で成功する」条件を明示的に持つステップ: 13・14・21・27・28・29 = 6 / 29
```

**目視の抜き取り(1・5・7・26)では、`0 / 0` と判定された 4 件はいずれも性質表明**だった
(負例すら無い)。→ **「負例のみ 23 件」ではなく「負例または性質表明が 23 件」が正確。**

**◎ 方法の限界(§16-3)**:

| | 内容 |
| --- | --- |
| **示せること** | **正例を明示的に持つステップは 6 / 29 で少数**。抜き取り 4 件はすべて性質表明 |
| **示せないこと(1)** | **キーワード法なので誤判定を含む。** 全 29 件の目視はしていない(抜き取り 4 件のみ)。**◎ とくに「列挙した語だけを見て全数と称する」罠がある** — 先方は `BOOT-STATE` の「**持たせない**」を検出語に入れておらず、**規範を補足と誤判定して撤回した**(§3-2-f)。**「fail する」「exit 1」だけを探すと、別の書き方をした負例を見落とす** |

| **示せないこと(3)** | **個人の癖か型かは分からない。** n = 1 タスク |

→ **再開時に全 29(30)ステップを目視で分類し、正例が要るのに無いものを特定する。**

**本タスクの実装で、同じ型の欠陥が 3 ステップ連続で出た。** いずれも Codex が書いたテストである。

| --- | --- | --- | --- |

**共通する誤り**: **「いま資産がどういう状態か」を不変条件として書いている。**

**◎ 個別に差し戻すのをやめ、恒常規則として渡した**(3 回目の時点):

> **実資産の可変フィールドの現在値を assert しない。**

**適用結果を 3 件集めるまで一般形に上げなかった。**

**恒常規則の実効は、以降のステップで同型が出ないことでしか測れない** — **測る。**
