# 調査メモ: NFR-018 実現方式 ADR(状況計算の配置 + 付録A 契約化)

調査方法: 調査サブエージェント 3 本(spec-checker / legacy-analyst / decision-tracer)を並列実行し、Web 技術調査を /research(Codex・read-only + live search)へ委任。**決定的な引用と、エージェント間で食い違った点は Claude が原典で再確認・裁定した**。行番号は develop = `28cc738` 時点。

## 問い

1. 要件は「状況計算をどこで実行するか」をどこまで確定させているか。ADR が動かせる範囲はどこか
2. 「単一実装」を Python(backend)と TypeScript(frontend)にまたいでどう実現できるか
3. この ADR は何を防ぐためのものか(旧システムで実際に何が起きたか)
4. ADR を書き始めるうえでの手続き上の障害はあるか

## 結論(要約)

- **「配置」は既に要件で決着している。ADR が決めるのは「実現方式」だけ。** 要件は断中のクライアント計算を受入基準で要求し(FR-005)、サーバー再計算を確定記録と定め(4.0-2)、**両側に計算が存在することを受容済みリスク R-3 として明記**している。「サーバー権威のみ」は要件違反。
- **ADR の核心は要件解釈の判断**: NFR-018 の文言「**単一の共有実装**」と R-3 の「**両方に存在する**」は緊張関係にある。NFR-018 自身がその解決を ADR に委ねているため、**「単一実装」を「1 つのコードベース」と読むか「単一の規範的契約 + 検証された 2 実行系」と読むか**を ADR が定義しなければならない。これは技術判断ではなく**要件解釈**であり、人間の承認が要る。
- **Web 調査の推奨は (a) 二重実装 + 契約検査**(共通ゴールデンベクタ・差分テスト・プロパティテスト・変異テストの 4 層)。Pyodide / Node サイドカー / Rust+WASM はこの計算規模では運用コストが勝つ。**ただし (a) は上記の解釈を後者に倒すことを前提にしている。**
- **⚠ 手続き上の障害が 1 件ある**: 台帳の候補 (7)「ADR 様式と 7.1-3 の免除区分が未決」の**昇格条件が文字どおり「次に ADR を新設するタイミングで PO 裁定を得る」= 今**。テンプレートのまま ADR-003 を作ると CI の `check_docs_status.py` が落ちる。
- **正本の記述誤りを 2 件検出した**(下記 §6)。いずれも ADR が根拠として引用する箇所なので、ADR より先に直す必要がある。

### 2. ADR が答えるべき核心の問い(要件解釈)

NFR-018 の原文(要件書 `:856`):

> ドメイン計算（状況判定・座標変換・捕球選手推定・成績集計の前処理・終了判定）は**単一の共有実装**とし、UI別・経路別のコピー実装を作らない（**クライアント/サーバー両方で必要な状況計算の配置と実現方式は、実装着手前に設計フェーズの ADR で確定する設計課題として申し送り**〔v1.8明文化〕。一致はNFR-019で担保）

**文言は「単一の共有実装」を要求しているが、同じ要件書の R-3 は「両方に存在する」ことを受容している。** この緊張を解く権限が、括弧内で ADR に委任されている。

したがって ADR は次を明示的に定義しなければならない:

> **「単一実装」とは何を満たせば達成されたとみなすのか。**
> (i) 文字どおり 1 つのコードベースが両側で動くこと、か
> (ii) 単一の規範的契約(ゴールデンベクタ)に対して検証された 2 つの実行系を持つこと、か

**(ii) を採るなら、それは要件文言の解釈変更にあたるため、ADR にその旨を明記し人間の承認を得る必要がある**(要件書の改訂までは不要という判断も、ADR が根拠を示して行う)。

**申し送りの起源**(decision-tracer): D-10(2026-07-20)`requirements-draft-pitchlog.md:94`「D-5 の単一実装原則と両立させる配置(**状況遷移ロジックを1箇所に書き両側から使う等**)は設計フェーズの必須課題として申し送る」。設計書 `:177` は選択肢を「**共有実装・生成・その他**」と列挙するのみ。**これ以上の選択肢の展開・比較はリポジトリ内のどこにも無い。**

### 3. 実現方式の選択肢(/research — Codex・Web)

| 方式 | 仕組み | この案件での評価 | 主な破綻点 |
| --- | --- | --- | --- |
| **(a) 二重実装 + 契約検査** | Python と TS で純粋 reducer を各々書き、同一イベント列→同一状態を CI で比較 | **推奨**。追加ランタイム・別言語・配布物を増やさず診断も容易。MCP Conformance・Wycheproof など複数実装の適合性試験は成熟した手法 | **同じ仕様誤解を両実装に入れると通る** |
| (b) 遷移表/DSL から両言語を生成 | 状態・イベント・ガード・更新規則を単一定義にし生成 | 部分的に有効。**Python + TS を高品質に両対応する既製品は確認できず**。段階的適用(enum・型・遷移網羅テストの雛形だけ生成)が現実的 | DSL の表現力不足 / 生成器が第三のプロダクト化 |
| (c) Pyodide(CPython を WASM) | Python 実装をブラウザでそのまま実行 | この計算規模に対し **10MB 級ランタイムを毎端末に常駐**させる費用が見合わない。iPad Safari では 0.27.1 で iOS wasm-gc 起因の動作不能、crash regression の実績(後続版で修正) | 初期ロード / iOS 実装差 / Service Worker 制約 |
| (d) TS core を Node サイドカーでサーバーでも | FastAPI が Node へ RPC | **FastAPI のトランザクション境界が分断される**。常駐プロセス・監視・同時デプロイが増える | サイドカー不在時の同期失敗 |
| (e) Rust core → WASM + Python 拡張 | 一度書いて両方へ配布 | 性能要件が無いため**得るものは「一実装」だけ**で、Rust・二系統ビルド・型境界の保守が増える。`rustwasm` org は 2025 に sunset 告知 | CI マトリクスの肥大 |
| (f) CEL/JsonLogic を両側の evaluator で解釈 | ルールを宣言的に持つ | **TS 側に公式 CEL 実装が無く** error semantics の差が明記されている実装もある。ガード・終了判定など小規模な外出しなら有効 | evaluator 間の意味差 |

**(a) を安全に運用する 4 層**(Codex 提案):

1. **例示ベクタ** — 入力列・途中状態・最終状態・拒否理由・**遷移 trace** を JSON で固定
2. **差分テスト** — 生成した合法イベント列を両実装へ同一投入し、イベントごとの canonical JSON を比較。失敗は seed と最小化列を回帰ベクタへ昇格
3. **プロパティ/モデルベーステスト** — Hypothesis(Python)・fast-check(TS)。範囲不変条件・再生の決定性・snapshot からの再生一致・終了後のイベント拒否
4. **変異テスト** — mutmut(Python)・StrykerJS(TS)。毎 PR でなく夜間 CI で可

**契約として固定すべき意味論**(言語差が事故になる箇所): JSON の canonical 化と `null`/省略の区別 / **TS `number` の安全整数範囲 `±(2^53-1)`** / 列挙値・イベント順・補正イベントの優先順位 / 不正イベントの扱い / ルールバージョン / 状態だけでなく**各イベント後の遷移 trace**。

**ベクタの網羅性の測り方**: 行カバレッジでは測れない。`event_kind × 現在局面` の到達数 / 遷移 edge の到達数 / 各終了理由・補正理由・拒否理由の到達数 / **両実装が発火した rule ID の集合差分**。各 reducer がテスト専用 trace として発火 rule ID を返せば、ベクタ不足を機械的に可視化できる。

**到達点の限界(重要)**: 差分テストは「両実装の乖離」を強く検出できるが、**両者が同じ誤った仕様を実装していることは証明できない**。

### 5. ⚠ 手続き上の障害(ADR を書く前に決着が要る)

**台帳の候補 (7)「ADR 様式と 7.1-3 の免除区分が未決」— 昇格条件が「次に ADR を新設するタイミングで PO 裁定を得る」**(台帳 `:807-811`)。

- ADR-001・ADR-002 は**変更履歴表を持たない**。`adr-template.md` 自体も持たない
- しかし規約(設計書 7.1-3・`.claude/rules/docs.md`)は「正本は変更履歴表を持つ」を**例外なく**要求する
- F2 タスクが既存 2 件を**内容ダイジェストで grandfather** した。`scripts/check_docs_status.py:56` のコメントが「**将来 ADR を標準テンプレート(変更履歴表を持たない)から作ると検査が落ちる**」と明記している(**意図した挙動** — その時点で判断を強制する設計)
- 選択肢は 2 つで、コストが違う:
  - **(A) ADR 種別を免除区分として設計書 7.1-3 に明記する** → 設計書の**版繰り上げ + 確定ゲート**が要る
  - **(B) ADR 様式に変更履歴表を導入する** → テンプレート改訂 + **既存 2 件の様式変更**を伴う
- 候補 (8)(要件対話の決定記録の `D-1〜D-37` 表記の是正)が**この決着に依存**している

**ADR の番号**: 明示的な採番規則は見つからない(**規定なし**)。事実として `ADR-<3桁>-<英小文字ハイフン slug>.md` の慣行があり、**`ADR-003` を「状況計算の配置・実現方式」に充てる前提の記述が 1 件ある**(非正本 — `docs/features/req-v1-9-nfr021-wsl2/plan.md:75`)。

**確定ゲートの手続き**(設計書 `:380-390`・`.claude/skills/finalize-doc/SKILL.md`): draft → in-review(`codex_run.py review adversarial` を収束まで反復)→ 人間承認 → approved(版数確定・変更履歴追記・索引更新)。**指摘反映を伴う 1 周ごとに `確定ゲート周回` を +1 し、反映周ごとに 1 コミット**(件名に `反映<r>周目`・ステップ記法は付けない)。

### 6. 正本の記述誤り 2 件(Claude が原典で裁定)

## 未解決・申し送り(/plan で扱う論点)

### 論点 A(最優先・着手前に決着が要る): ADR 様式の PO 裁定

台帳の候補 (7) の昇格条件が「次に ADR を新設するタイミング」= 今。**(A) 免除区分を設計書 7.1-3 に明記(設計書の版繰り上げ + 確定ゲートが要る)/ (B) ADR 様式に変更履歴表を導入(テンプレート改訂 + 既存 2 件の様式変更)** のどちらかを人間が裁定しないと、ADR-003 を作った時点で CI が落ちる。**(B) の方が本タスク内で完結しやすい**(設計書の版繰り上げを誘発しない)。

### 論点 B(核心): 「単一実装」の定義を ADR がどう置くか

§2 のとおり要件解釈の判断。**(i) 1 つのコードベース / (ii) 単一の規範的契約 + 検証された 2 実行系**。Web 調査の推奨 (a) は (ii) を前提とする。(ii) を採るなら、要件文言との関係(解釈で足りるのか、要件書の改訂が要るのか)を ADR で明示し、人間の承認を得る必要がある。

### 論点 C: ADR のスコープに付録A 契約化を含めるか

台帳 H-55 の対応案は「**必須項目として含める**」。含めないと H-55 が受け皿を失う。ただし要件書 `:501` が「チーム集計はサーバー側の集計であるため、**バックエンド集計の契約と単体テストを別建てで置く**」と既に切り分けているので、**付録A 契約の置き場と NFR-019(a) の射程の関係**を整理する必要がある。

### 論点 D: 正本の記述誤り 2 件をこのタスクで直すか

§6 の誤り①(I-2 → I-4)と誤り②(WHIP/FIP → 被打率・投球回)。いずれも**事実誤認の訂正であり構造的変更ではない**ため、設計書 7.6-3 前段「実装追随の節更新・変更履歴追記は PR レビューで足りる」に該当すると読める。ただし**設計書 6.3 は境界定義表の一部**なので、訂正が「境界規定の実質改訂」と解釈されないかの判断が要る。

### 論点 E: リプレイ整合性の恒等式を担保機構に組み込むか

旧システムの資産として移植価値が高いと評価されているが、**出力一致の検査であってコピー実装の検出ではない**。NFR-019(a) のゴールデンベクタとは別種の網として位置づけるか、採らないかを決める。

### 論点 F: ADR の番号

`ADR-003` を充てる前提の記述が非正本に 1 件あるのみで、採番規則は**規定なし**。ADR 内で採番規則を定めるかは別途。
