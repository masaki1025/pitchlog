# 調査メモ: 同期プロトコル 7-2 / 7-4 / 7-7 を frontend に実装するための下調べ

## 問い

`docs/design/sync-protocol.md`(approved v0.1)の **7-2(キューの状態遷移)/ 7-4(クライアント側の規律)/ 7-7(ローカル書き出しと復旧後取り込み)** + **`K5`** + **W4 のクライアント規律側**を実装するにあたり、
① 何が要件として掛かるか ② 正本のどこまでが「写すだけ」でどこからが裁量か ③ 旧システムから何が取れるか
④ 射程の切り方は成立するか ⑤ 前タスク(TSK-280)の資産と衝突しないか。

**方法**: 調査サブエージェント 3 本(spec-checker / legacy-analyst / decision-tracer)を並列 + **Claude による原典の直接確認**。
本メモで **◎** を付けた事実は Claude が原典を直接読んで確認したもの(設計書 8.5)。

## 結論(要約)

1. **正本の決定密度が TSK-280 より高い。** 7-2 は **4 状態 + 遷移 14 行 + `I6`**、7-4 は **`Q1`〜`Q7` + `Q2-a/b/c` + `Q2-r1`〜`Q2-r4`**、7-7 は **`X1`〜`X4` + `VF1`・`VF4`**。**実装者が選べる余地はほぼゼロ**で、裁量は (B) 論点 **19・20・25** の 3 件(+ `U-5` の文面)に限られる。
2. **`prohibitions.spec.ts` の U-2 語走査に `/採番/` があり、正本の必須語と正面衝突する(◎ 確認済み)。** 新ファイルを足せば**必ず red になる**。TSK-280 で私が作った検査の副作用であり、**着手前に対処方針を決める必要がある**。
3. **`I6` の帰属を裁定した記録が無い。** TSK-280 は 7-2 を丸ごと α へ送りながら、実装では `I6` を射程外 allow-list に置いた。**人間の裁定が要る論点**。
4. **W4 のクライアント規律側は、当初の射程の書き方が正本と整合しない。** `R-CHANGE-RULE` の伝播先に **7-2・7-4 が入っていない**ため、7-4 の Q 表へ W4 由来の行を足すと「本表に無い伝播をしない」に抵触する。
5. **`NFR-019(d)` の期待値は 7-4 ではなく 10-2 にあり、10-3 が `scenarioId` を 3 つ名指ししている。** 置き場 `tests/fixtures/sync-protocol-failures/` は**未作成**。
6. **旧システムからは状態機械が取れない。** 旧 outbox は「送信失敗のリトライ器」であって「オフライン記録の器」ではない。取れるのは**バックオフ方針・ロック名の粒度・quarantine の発想**まで。

## 詳細と典拠

### 1. 7-2 / 7-4 / 7-7 の実体(◎ Claude が直接確認)

#### 7-2 キューの状態遷移(`docs/design/sync-protocol.md:978-1032`)

**4 状態**(`:988-991`):

| 状態 | 意味 |
| --- | --- |
| **未送信** | 端末内キューに積まれ未確定。**A5 の結果で別状態へ移るまで破棄しない** |
| **要操作**(**改訂待ち / 墓標待ち / 管理者対応待ち**) | 内容起因の拒否(B3)、または **`O4`** の永続化済み D2 同値を検出。**自動再送・自動破棄の対象から外す** |
| **同期済み(24 時間保持)** | D1 付きイベントの確定、**または端末永続化まで成立した P3 の変更受理結果が `I6` として保持された** |
| **退避済み** | **D4 または V12 の記録権照合に失敗した D1 付きイベント**(B4)、または復元前に保持した P3 受理結果。**v0.1 では自動破棄しない** |

**遷移 14 行**(`:999-1014`)。うち **3 行が「遷移なし」**(未送信 →(破棄)/ 要操作 →(破棄)/ 退避済み →(破棄))。

**間違えやすい規則**:

- **未送信 → 同期済み**は **`(D4, D1, D5)` について A5 が「受理」または「重複」**を返したこと。**`D1 ≤ D3` だけでは不足**(同じ `(D4, D1)` で異なる D5 を取り違えるため — 起草レビュー 1 周目 P1)(`:1002`)
- **`D3` は遷移の判定に使わない** — 「D3 の役割は**連続 prefix の整合確認**と**再送範囲の決定**に限る」(起草レビュー 2 周目 P1)(`:1024`)
- **D1 付きキュー遷移の根拠は `A5` だけ**(`:1024`)
- **端末起動時は 24 時間の期限清掃より先に `RG1` を確認**。到達できず確認不能なら **fail-closed で清掃を保留**(`:1026`)
- **写像が確定するまで同期済みにしない**(`C4`)— 「D1 が D3 以下でも同期済みへ移さない」(`:1032`)

**`I6`**(`:993-995`): 端末永続化まで成立した**対象参照 + V11 の版 + D5 + 確定内容 + `accepted_at`** を起点に同期済みと同じ 24 時間保持。
**保存済み結果の再掲で延長しない**。**サーバー確定から端末永続化まで保護なし**。**RG1 中は自動破棄停止**。**復元規則なし**。

#### 7-4 クライアント側の規律(`:1055-1084`)

| ID | 内容 |
| --- | --- |
| **`Q1`** | 追記と D1 の採番は**不可分に永続化**。**主タブでこの追記が成立した時点を「操作の受理」**とし、追記が成立していない入力は受理されていない。D6・D7 は採番せず既存スロットを不可分置換 |
| **`Q2`** | 同一ブラウザの複数タブは**単一の書き手のみ**。**満たすべき条件はここまでで、実現機構は (B) 論点 20** |
| **`Q3`** | **警告閾値(既定 350 イベント)に達しても記録をブロックしない** |
| **`Q4`** | **未送信件数を常時表示する** |
| **`Q5`** | 同期成功でキューが空になったとき「**どの試合の何球分が送信されたか**」を通知 |
| **`Q6`** | **永続ストレージの要求が拒否されたら、キューが消され得る旨を警告** |
| **`Q7`** | **認証トークンが失効してもキューを失わない**。再ログイン後に同期が再開 |
| **`Q2-a`** | 選出は **NFR-020 の 6 前提をすべて満たす範囲**で行う |
| **`Q2-b`** | 非所有タブでは**記録できないことと、記録中のタブを終了する導線を明示** |
| **`Q2-c`** | 主タブが排他ロックを保持したまま停止し**まだ終了していない間**、非所有タブの入力を**「操作として受理しない」** |
| **`Q2-r1`** | **`steal` を使わない**(「`steal` は旧コードの実行停止を保証せず、単一書き手を破り得る」) |
| **`Q2-r2`** | ロックはコンテキストの終了時に解放される(仕様保証) |
| **`Q2-r3`** | **待機側はキューを失わない**(同一 storage bucket の範囲) |
| **`Q2-r4`** | **ロック取得後、記録を始める前に単一書き手であることを再検証** |

**`Q3` の根拠が正本に明記**(`:1067`): FR-012 の入力継続基準を優先する。**NFR-007/E4 の「受理済み操作を失わない」保証とは別契約**。
「**旧システムの別経路は『キューに未送信が残る間は次のプレイ確定がブロックされる』実装だった([I-8])。同じ形にしない**」。

#### 7-7 ローカル書き出しと復旧後取り込み(`:1126-1146`)

| ID | 内容 |
| --- | --- |
| **`X1`** | 書き出しは **D1・D4・D5 を含むイベントの原形を保つ**。書き出しの時点で**採番し直さない** |
| **`X2`** | 取り込みで生じる重複は **D5 で吸収**。既確定なら **B1 の「重複」**。**取り込み専用の重複判定を作らない** |
| **`X3`** | 取り込めるのは**同一の D4 で、かつ要求の V12 が現保持端末を証明するイベントに限る**。不成立なら **B4 で退避** |

**`X3` が重要な理由**(`:1146`): ローカル書き出しは**非常口**であって、**記録権の引き継ぎを迂回する裏口ではない**。

#### 2-2. 主要な受入基準(逐語・要件書 `docs/requirements/requirements-pitchlog-2026-07-22.md`)

- **`:298`**「**追記と連番の採番は不可分に永続化**され、**同一ブラウザの複数タブは単一の書き手のみが記録できる**」

- **`:300` E1**「主タブが排他ロックを保持したまま停止 / **まだ終了していない** / Then 入力継続基準の例外は**その間に限る**。**単一書き手の制約自体は緩和せず、NFR-007/E4 の保証にも例外を設けない**」
- **`:301` E2**「E1 の期間中に非所有タブで入力 / Then **その入力を「操作として受理しない」**。**受理済みの操作を喪失する例外ではなく、受理の境界**である」

- **`:305`**「警告閾値(**既定 350 イベント**)に達した / Then **記録は継続でき**、警告される(**記録をブロックしない**)」
- **`:308`**「**永続ストレージの要求を拒否** / Then **キューが消され得る旨の警告**」
- **`:825` E4**「**受理の成否はその追記時点で判定して、後の喪失結果から遡って変更しない**」

**クライアント側 4 項目** = 「複数タブの単一書き手競合」(`:926`)+ **E5 の 3 行**(`:928-930`)。
**期待値は 7-4 ではなく 10-2 にある**(`sync-protocol.md:1641`・`:1644`・`:1645`・`:1646`)。

**10-3 の契約**(`:1669-1678`):

- **版付き JSON `<scenarioId>_v<N>.json`**。入力・故障注入・期待結果・比較単位のいずれかを変えたら **`N` を上げて別ファイル**にし、**参照するテストが全て新版へ移るまで旧版を上書き・削除しない**(`:1673`)

- **比較単位 = `scenarioId × 観測点 × expected の全フィールド`**。欠落・未知フィールド・順序不一致・余分な永続化はいずれも不合格(`:1678`)

#### 2-4. 触れる NFR

### 3. 決定経緯(decision-tracer)

#### 3-1. 実装者が選んではいけない値

**キュー状態の決定経緯**:

| 要素 | 決定 |

| 4 状態名 | 候補案 7-2 で確定。**正本でも不変** |
| **要操作の下位ラベル** | 候補案は**2 つ**(改訂待ち / 墓標待ち)。正本で **`O4` 由来の「管理者対応待ち」が増えて 3 つ**(起草レビュー 2 周目 P2) |

| **退避済みに 24 時間を流用しない** | **正本化ステップ 10 の人間照合 `CI-02` で是正**。候補案由来の 6-3 B4 行が退避を 24 時間対象に含めており、FR-012 の Given(**同期完了済み**)を超えていた |

**`K5` の非対称性は 2-1 の述語定義由来**(実装が動かせない): **`D6` 自身**が「**オンラインで現記録権保持を確認した後だけ生成**」を持ち(`:30`)、**`D7` は生成前確認を持たない**(`:31`)。
理由(`:595`): 「**墓標だけを生成前確認へ限定するのは、非保持端末に『当該 D1 を内容なしで正式消費する』という不可逆な判断を許さないため**」。

#### 3-2. 実装の裁量((B) 論点)

**受け取り先が「実装計画(フロントエンド)」= α の中核は 3 件**:

| 論点 | 内容 |
| --- | --- |
| **19** | **端末内キューの永続化技術 + ローカル書き出し/取り込みのファイル形式** |
| **20** | **複数タブ単一書き手の実現機構**(Web Locks / BroadcastChannel / リーダー選出) |
| **25** | **24 時間保持の破棄トリガの実装**(起動時 / タイマー / 次回同期時)— 7-2 が `:1013` で名指し |

**共通の裁量宣言**(`:1546`): 「受け取り先が『実装計画』の 8 件は、いずれも**本書の意味規則を満たす限り自由**である。**意味規則を変える必要が出たら本書へ戻る**」。

**論点 19 で「自由」なのは技術選択と表現形式だけ**(`:1537`)。**自由でないもの**: `Q1` の不可分性 / `X1` の原形保持 / `X2` の D5 吸収と取り込み専用判定の禁止 / `X3` の二重条件 / `X4` の範囲 / `VF1`・`VF4` の適用。

**正本化計画書が引いた線**(`sync-protocol-canonical/plan.md:169`): 「**主タブ選出は「exclusive lock による選出・`steal` 不使用・コンテキスト終了で解放」までを本書が規範化し、実装詳細(ロック名の設計・再試行間隔・UI の導線の作り)を送る**」。

**`U-5`(B4 の通知文面)**も実装計画(フロントエンド)だが、**3 つの制約が正本側**: 「**復元直後は全端末が B4 になる**ため『**他の人に権を取られた**』と読める文面にしてはならない」(`:2060`)/ 通知に含める 3 要素は 6-3 が固定(`:747`)/ **6-5 の非開示規則**で内部原因を露出しない(`:880`)。
