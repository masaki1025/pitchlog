## 4. 実装方針

前提となる調査結果・未解決論点は [research.md](research.md) を参照(内容を複製しない)。**H-63 の規律を適用した** — 選択肢に「(推奨)」ラベルを付けずに人間へ提示し、「UI別・経路別のコピー実装を作らない」という禁止文言との突合を明示した(評価台帳 `../../development/harness-evaluation.md` H-63)。

### 重さ分類の根拠 = 通常

正本ドキュメントの改訂であり実装コードを書かない。**コア領域(設計書 6.3)のコードには触れない**が、**NFR-018 の達成条件はコア領域の境界の広狭に間接的に関わる**ため、下記の判定を明示する。

**設計書 6.3 の条件付き除外への影響 = なし(判定)**。research.md §8 が特定した 3 つの影響条件に照らすと:

| 影響条件 | 本改訂の該当 |
| --- | --- |
| ① 付録A 契約の**形**(固定ベクタ + CI 強制)を変える | **該当しない** — 契約の形に触れない |
| ② **発効判断の委任先**を ADR 以外に置く / ADR に条件を課す | **該当しない** — 委任先は ADR-003 のまま |
| ③ 「成績集計の前処理」を NFR-018 の対象から**外す** / 範囲を再定義する | **該当しない** — 対象から外さない。むしろ NFR-019(a) の一致性テスト対象に**加える**方向(検証を強める) |

**③ の補強**(レビュー 2 周目 P1-C)— (α)(β) は「実行の所在」で切る軸、6.3 は「入出力」で切る軸であり、**2 軸は直交する**。混同を避けるため交差を明示する:

| 入出力境界(6.3 の軸) | (α) クライアント・サーバー双方 | (β) サーバー専用 |
| --- | --- | --- |
| イベントへの状態遷移・成績帰属(付録E まで) | **常時コア**(6.3)/ 一致性テストの対象 | **常時コア**(6.3)/ 一致性テストの対象外 |
| 確定イベント後の指標算出(付録A) | **条件付き除外**(6.3)/ 一致性テストの対象 | **条件付き除外**(6.3)/ 一致性テストの対象外 |

→ **(α)(β) は NFR-019(a) の対象判定にのみ用い、6.3 の「含む/含めない」欄と発効条件は変えない**。この限定を要件文にも明記する。**設計書の版繰り上げは誘発しない**が、**この判定(2 軸の直交)自体を確定ゲートの検証観点に含める** — 成立しなければ設計書 6.3 の改訂をスコープへ追加する必要がある。

### 改訂の骨格(A 案)

対象は要件書 NFR-018(:854-857)と NFR-019(a)(:861)。骨格は次のとおり(逐語の最終形は実装ステップで確定し、確定ゲートに掛ける):

- **要件**: ドメイン計算(列挙は本項に一元化)は**単一の実装コード**とし、クライアント・サーバーの双方が**同一のコードに由来する実行体**を用いる。UI別・経路別のコピー実装を作らない
- **対象の区分**(レビュー 1 周目 P0-3)— **用途は「NFR-019(a) 一致性テストの対象判定」に限る**。コア領域の境界(設計書 6.3)には用いない(レビュー 2 周目 P1-C):
  - **(α) クライアント・サーバー双方で実行されるドメイン計算** — 状況判定・座標変換・捕球選手推定・終了判定 + **断中にクライアントで実行される成績計算**(FR-021:409 の当日成績・FR-023:423 の球種割合)。**一致性テストの対象**
  - **(β) サーバー専用の集計** — チーム集計(FR-042)等。**FR-042 補足:501 の限定を維持**し、担保は付録A 契約(固定ベクタ)+ バックエンド単体テストに置く。一致性テストの対象に**しない**
- **正解ベクタの帰属**(レビュー 2 周目 P1-D)— NFR-019(a) の正解ベクタは現行「付録E のゴールデンケース」のみ(要件書:861)。付録E は**状態遷移・成績計上フラグの規範**であり、**指標の定義の正は付録A**(要件書:1002)。したがって (α) に成績計算を加える改訂では、**指標算出に関わる部分の正解ベクタは付録A 契約(固定ベクタ)とする**ことを要件文に明記し、**その整備は ADR-003 のスコープ**(評価台帳 H-55)であることを申し送る。本タスクでは固定ベクタを作らない
- **達成条件**:
  - (a) 対象のドメイン計算ごとに、**人手で保守される実装が 1 系統であること**。他方の実行体は生成・変換・埋め込みによる**派生物**であり、人手で編集しない
  - (b) **宣言と全数検査**(レビュー 1 周目 P0-2)— 対象ごとに **正本(出所)・すべての実行入口・派生関係を機械可読に宣言**し、CI が次の 2 つを判定できること: ① 出所と派生物の**乖離の検出**(派生物が古い・手で直された状態)② **宣言に無い実装が混入していないこと**。②が無いと「未申告の手書き実装が、出力が偶然一致する間だけ通る」= 旧 NFR-011 の失敗モード(「定義は共有だがロジックは別コード」)をそのまま再許容する。**要件は「機械的に判定できること」までを求め、判定面(探索対象の閉域)・実行入口の定義・生成物の識別・動的ロード等の禁止規則・到達性検査の方式は ADR-003 が定める**(レビュー 2 周目 P0-B — 方式まで要件に書くと実装不能な Must になる。**ADR-003 がこれらを定義することを要件の申し送りに明記する**)
  - (c) **逐語移植対象の扱い**(H-61・レビュー 1 周目 P0-1 / 2 周目 P0-A)— 例外は**ファイル単位ではなく〈対象シンボル・対応する契約値・逐語性の受入条件の終了証跡〉の 3 点組**で、**要件書に閉じた一覧として列挙**する。現時点の該当は 1 件(`frontend/src/lib/courseInputView.ts` の `COURSE_COORDINATE_SIZE` ←→ `contracts/display_geometry_263_v1.json` 由来の座標系スケール 263)。**一覧への追加は要件改訂を要する**(実装判断で増やせない)。例外の間は「契約値との一致がテストで固定されていること」をもって (a) を満たすとみなす。**卒業条件 = 当該シンボルの逐語性の受入条件を解いた時点で例外は自動失効**し、以後 (a) を満たす。**発効判定は逐語性を解く PR のレビューで行い、終了証跡を一覧から削除する**
  - (d) 対象の**列挙は本項が正**とし、4.0-4・NFR-019(a)・改善台帳 I-4/I-8 は本項を参照する(現在 4 系統に割れている — research.md §2)
- **測定方法**: (b) の宣言に対する機械検査(乖離検出 + 未宣言経路の検出)+ NFR-019(a) の一致性テスト
- **NFR-019(a)**: 対象列挙を **(α) に限って** NFR-018 へ揃える。A 案では実装が単一でも**生成パイプラインの退行**は起こり得るため、一致性テストは二重の担保として残す

### 確定ゲートへ明示的に掛ける論点(隠さない)

**A 案は前タスクの Web 調査の評価と正面から対立する** — 同調査は「この計算規模では Pyodide / Node サイドカー / Rust+WASM は運用コストが勝つ」と結論している([nfr018-domain-calc-adr/research.md](../nfr018-domain-calc-adr/research.md) §3)。人間裁定は要件の文言(「UI別・経路別のコピー実装を作らない」Must)を優先して A 案を選んだが、**この対立を計画書に残さないまま確定させると ADR-003 で同じ議論が再燃する**。したがって確定ゲートの敵対レビューには次を明示的に掛ける:

1. **A 案の達成条件を満たす実現手段が実在するか**(1 名開発体制・タブレット実機・断中動作という制約下で)。実在しない場合、要件は「実装不能な Must」になる
2. **その場合の差し戻し経路を要件側に持つべきか** — 例: ADR-003 が全手段の不成立を典拠付きで示した場合に要件を再改訂する、という手続を要件書に書くか、書かずに運用に委ねるか
3. 達成条件 (c)(逐語移植対象の例外)が**抜け道にならないか** — 「逐語移植対象」の範囲が広がれば (a) が空文化する
