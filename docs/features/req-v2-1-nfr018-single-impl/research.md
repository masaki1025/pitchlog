## 問い

要件書 NFR-018「ドメイン計算は単一の共有実装とし、UI別・経路別のコピー実装を作らない」の**達成条件**を v2.1 で明示するにあたり、(1) 改訂はどこまで波及するか (2) 過去の決定のどこまでが既決で、何が空白か (3) 旧システムの実績から「何を防ぐ条件」を書けば足りるか (4) 版番号 v2.1 の繰り下げに実害はあるか。

## 結論(要約)

1. **NFR-018 は旧 NFR-011 のほぼ逐語継承**で、旧はこの文言で 1 年以上多重実装を解消できなかった。旧は共有モジュール(`out_statuses.py`・`batting_results.py`)と共有契約ファイル(`shared/display_geometry_263_v1.json`)を**実際に持っていた**にもかかわらず「定義は共有だがロジックは別コード」の状態が残った。→ **「共有実装を置く」は達成条件にならない**ことが実証済み。
2. **達成条件を決めた過去の決定は存在しない**(D-5 = 原則、D-10 = 「両立させる配置」の申し送り〔括弧内・「等」付きの例示〕、v1.8 = 「実現方式は ADR で確定」の明文化のみ)。v2.1 は**空白を埋める改訂**であり既決事項の蒸し返しではない。ただし Must・禁止文言を**弱める方向**は D-5 と v1.0 以来の文言の書き換えにあたり、H-63 が P0 で差し戻した論点そのもの。
3. **改訂は NFR-018 単体で閉じない**。対象の列挙が **4 系統に割れており**(4.0-4 / NFR-018 / NFR-019(a) / 改善台帳 I-8)、うち NFR-019(a) は「成績集計の前処理」を欠く一方で FR-021・FR-023 が断中の成績クライアント計算を **Must の受入基準で必須化**している = **一致性テストの対象外なのに二重実装が必須**という穴が原典に実在する。
4. **R-3 は「受容済みリスク」ではなく「リスク」**(原典で裁定)。対応方針欄が NFR-018 を参照しているため、R-3 を根拠に NFR-018 を弱めるのは参照方向が逆。
5. **版 v2.1 の繰り下げは規約上問題なし**(版番号の予約・順序の規約は正本に不在)。approved 正本の前方参照は**要件書 :484 の「次版」1 件のみ**で、本改訂の確定ゲート内で是正できる。

### 3. NFR-019(a) との非対称 — 原典で成立する

NFR-019(a) 逐語(要件書:861 該当部): 「クライアント/サーバー状況計算の一致性テスト（同一のプレイ入力列から同一状況を導く。**付録Eマトリクスのゴールデンケースを共通の正解ベクタとする**。断中に実行するドメイン計算＝状況判定・終了判定・**捕球選手推定・座標導出**を対象に含める）」

- **「成績集計の前処理」は NFR-018 の列挙にあり(要件書:856)、NFR-019(a) の列挙にない(要件書:861)** — 非対称は実在する。
- **にもかかわらずクライアント側の成績計算は Must で必須化されている**: FR-021「Given 通信断中 / When 表示 / Then **当日成績はクライアント計算で追従**」(要件書:409)、FR-023「Given 通信断中 / When 表示 / Then **クライアント計算で追従する**」(要件書:423 — 球種割合)。当日成績の中身は投球数・投球回・最速/平均球速・被安打・奪三振・与四球・失点(要件書:405)。
- 逆向きの明示的な限定が 1 箇所ある: FR-042 補足「**NFR-019(a) の一致性テストは拡張しない**。…チーム集計はサーバー側の集計であるため、バックエンド集計の契約と単体テストを別建てで置く」(要件書:501)。ただしこれは **FR-042 のチーム集計に限った限定**で、FR-021/FR-023 の断中クライアント成績計算については何も述べていない。
- → **「NFR-018 の対象だが一致性テストの対象外で、しかもクライアント実装が必須」という領域が原典に空いている**。v2.1 が達成条件を書くなら、この穴を閉じるか、閉じないことを明示的に選ぶ必要がある。

### 5. 決定の射程 — 何が既決で何が空白か

- **D-5**(決定記録:63-67): ① UI を 1 本にする ② スタック継承 ③ タブレット/PC 両対応 ④「ドメインロジック（状況判定・座標変換・集計等）は**単一実装に集約**（旧NFR-011の多重実装問題を**構造的に**解消）」。**実現方法・達成条件は一切書かれていない**。当時の診断は多重実装の原因を「2UI 併存」に置いており、**Python/TypeScript の言語境界が原因になり得るという認識は D-5 の文面に現れていない**(D-10 が後から持ち込む)。
- **D-10**(決定記録:94): 「…D-5の単一実装原則と両立させる配置（**状況遷移ロジックを1箇所に書き両側から使う等**）は設計フェーズの必須課題として**申し送る**」。**裁定**: 括弧内・末尾「等」付きの**例示**であり、文の述語は「申し送る」。→ **「1 箇所に書く」を決定したと読むのは誤り**。同時に、申し送られたのは「**両立させる配置**」であって「単一実装原則を見直すか否か」ではない(D-10 は D-5 を所与として扱う)ため、**「D-10 が緩和を許した」と読むのも誤り**。
- **D-13**(決定記録:109-112): サーバー権威・差異の補正と通知・一致性テストの CI 常設・「正本はDBの1系統のみ」。**実装の本数・配置には触れていない**。
- **改善台帳 I-8**(改善台帳:81・84): 「状況計算の配置は後から変えられない（作り直し級）ため、今決めるしかない」「**状況計算をクライアント側でも実行できるアーキテクチャを最初から採用する**」。→ **クライアント側でも実行できることは確定。実装本数・実現方式への言及はなし**(D-10 と同じ構造)。
- → **「達成条件」は空白**。v2.1 は蒸し返しではない。蒸し返しに当たり得るのは **Must / 「UI別・経路別のコピー実装を作らない」を緩める方向のみ**で、これは H-63(評価台帳:773-782)が P0 で差し戻した論点そのもの。

- → **R-3 は実装方式(2 実装)の許可条項ではない**。しかも R-3 は NFR-018 を**対策として参照している**ので、R-3 を根拠に NFR-018 を弱めるのは**参照方向が逆**になる。評価台帳 H-63:777 の切り分けは原典で裏付く。
