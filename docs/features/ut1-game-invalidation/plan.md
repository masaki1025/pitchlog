# 実装計画書: U-T1 後続・試合削除の5範囲無効化契約

> **計画承認記録（2026-10-13）**: 利用者が追加1回のP0限定レビューの可決と `edbef663` への追随を確認し、現行計画を承認した。同じ計画の追加レビューは不要。この承認は実装ステップ1の開始指示、保守用認可、B06正本改訂の7.3確定、凍結契約の7.7受理を含まない。

## 1. 背景・目的

[TSK-543](https://app.notion.com/p/3f893b75e68781938d77d0c9087dd326) は完了済み [TSK-390](https://app.notion.com/p/3da93b75e68781fc87d7f04a12ff6ad8) の後続である。[TSK-397/U-D1](https://app.notion.com/p/3da93b75e68781c7a7b0ef8c32d221af) が所有する [FR-019](../../requirements/requirements-pitchlog-2026-07-22.md#FR-019) の試合削除・復元を、[設計書11-2](../../design/data-model.md) B02/B06 が求める5範囲のキャッシュ無効化契約に接続する。現行の純粋生成器は5範囲の具体キーを要求し、選択子は在籍区分変更の共有集計だけに許可される。保存器も同トリガーの1行だけに対応する。U-D1 の仮の物理キーとNULLワイルドカードを避け、テナントに限定した明示的な選択子を確定する。

本Codexセッションが専用worktreeで計画起案を担当する。**この担当指定は製品・共有契約の即時変更許可ではない**。Notion人物担当は未設定である。

## 2. スコープ

### やること

- トリガー5 `game_delete_restore_or_resume` に、試合の具体キーと選手通算・チーム集計・共有集計・分析チャートの明示的なテナント限定選択子を追加する。テナント一致、対象範囲、混在・欠落・重複・余分な指定の拒否を契約化する。
- 選択子を既存の `invalidation_intents` に曖昧さなく保存する判別子と列組合せ、既存共有集計意図との互換・migration、配信側の一致条件を確定する。NULLを暗黙の全件指定にしない。
- 5範囲各1行と行識別子 `scope_id` は**U-D1が所有・受理するトリガー5の行規則**として正本B06へ反映する。U-T1はその入力に従う生成器・保存器の契約を作る。意図IDの骨格・操作IDは完了済みTSK-447を再利用する。U-D1の状態更新0行なら意図0行となる呼出し境界を定める。
- 期限到来の `trashed → hidden` は、削除時に5範囲から除外済みで集計値が変わらないため追加の5行意図を発火させない（2026-10-13・利用者の仕様方針裁定）。削除・復元時の5行は維持する。ゴミ箱一覧は期限ちょうどから別に非表示とし、サーバー復元拒否は一覧キャッシュ・5分周期の保守処理に依存させない。この方針をB06の7.3正式ゲートに掛ける。

### やらないこと

- U-D1 の試合状態変更、API、UI、ゴミ箱の移行例外や保守関数を実装しない。実際の状態変更・再送と5行意図の統合受入試験はU-D1のDoDに残す。TSK-390 の完了状態を戻さない。
- キャッシュ本体・配信器を新たに実装しない。設計書B06の配信担当境界を維持する。
- 正本・凍結契約の確定ゲート前に `contracts/tenant_boundary/` や製品コードを変更しない。本番・共有DBに migration を適用しない。

## 4. 実装方針

テナント分離と無効化の永続化は6.3のコア領域である。現行 `CacheInvalidationRequest` の5種の範囲照合を保持し、トリガー5に限り明示的選択子を追加する。`SharedAggregateTargetSelector` の現行利用は壊さない。現行保存器は `ROSTER_STATUS_CHANGE` と1行に閉じているため、U-D1の状態変更実装で勝手に汎用化しない。意図保存の骨格はTSK-447の `<trigger_id>:<operation_id>:<行識別子>` を使う。U-D1が受理した行規則では一括更新も1要求・1操作IDとし、行識別子に試合IDと範囲IDを含める。厳密な符号化はB06ゲートで確定する。期限保守更新では追加意図を作らず、ジョブへ意図INSERT権限を付与しない方針をB06の正式ゲートへ掛ける。保守用認可のP0 3件は別に未解決である。

独立した専用テストDBでは既知の旧意図行を投入し、migrationの往復・旧行の判別を検証する。対象アプリDBの既存行調査は未了であり、その互換性を合格済みと見なさない。revision head/番号の競合照合、旧行を使う専用DB試験、対象DBの読取調査と実DB適用可否判断は別々のゲートとする。B06改訂に伴う `contracts/db/schema-manifest.json` の正本全文digestと `contracts/authz/shared-preconditions.json` の正本Git blob digestは**ステップ1で同時に追随**し、ステップ1終了時に両検査を緑にする。確定ゲートの文書コミットへJSONを混ぜない。DDLに判別列を追加する場合の**表構造・列一覧**の追随はステップ2でORM、不変性検査、authz製品資産とともにTSK-424所有者と確定する。対象DBへのmigration適用はそのデータ調査・裁定まで保留する。
