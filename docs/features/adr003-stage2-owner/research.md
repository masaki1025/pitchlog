# 調査メモ: ADR-003 段階 2 の実行経路 — 起票するタスクの射程を決めるための材料

## 問い

TSK-510 の成果物は「**段階 2 の実行経路を作るタスクを起票し、所有者を決める**」ことだけである
(Notion カード本文「**ADR-003 の改訂が方式を決めるまで、中身の計画には入れない**」)。
**起票するタスクの射程を正確に書く**ために、次を確かめた。

1. 段階 1 / 段階 2 の線引きはどこで決まり、**段階 2 へ送られた事項は何件あるか**
2. 要件書が生成経路に課している要求は何か。**発効条件 (iv) の母集団はどう数えるか**
3. **既存資産に何が在り、何が無いか**(現況)

調査は 3 本を並列で実施した(decision-tracer / spec-checker / Explore)。
**legacy-analyst は投げていない** — 旧システムの実挙動に依存する論点が本タスクに無いため。

## 結論(要約)

- **段階 2 への送り先は 2 系統ある。(甲) 段階 2 の実行経路**(TSK-510 の持ち物)と、
  **(乙) 「段階 2 受取タスク」**(TSK-236 が引き渡し契約で指名した受け手。**S01〜S34 の 34 件**+ TSK-455 の残余)。
  **乙は未起票**で、契約 JSON の `receiverTaskId` は `null`。
  **甲と乙を同一とする記述はリポジトリに無い** — **起票時に決めるべき最大の論点**
- **現況は「枠だけが在る」**。IR 生成コア・生成前検査 5 系統・formatter・乖離検出・封印機構は実装済みだが、
  **言語 backend 3 本は宣言を読まない固定スタブ**、**宣言の正本 `model.json` / `manifest.json` は不在**、
  **生成物の出力先 2 箇所は空**、**QuickJS / Node の配線はコード・依存・CI に 1 行も無い**
- **発効条件 (iv) の射程が条文と要件書でずれている**。(iv) は「**要件書ブロック 4** が定める必須集計」と書くが、
  NFR-018 の (β) は**ブロック 3・5 にもまたがる**ため、**字句どおりに読むと ②③⑦ が判定の外へ落ちる**
- **「生成 SQL は `ROUND()` を使えない」は言い過ぎだった**(本調査で訂正)。
  **丸めは formatter の担当で SQL の外**。**発効条件 (iii) が決める分岐点**であって、確定した難所ではない

### 7. 丸めはどこにあるか — 先の報告を訂正する

**先に「生成 SQL は `ROUND()` を使えない」と報告したが、これは条文の射程を越えた延長だった。**

- 現行 D-1 では (β)①〜⑤ の生成物は **SQL 式 + Python の型付き受け口 + 表示 formatter(Python)** の 3 つ(`ADR:108`)。
  **丸めは formatter の担当で SQL の外**にある。SQL は構造化値を返せばよく(`NumericValue` は有理数の分子/分母を持つ
  — `ADR:107`)、**`ROUND()` の問題は原理的に起きない**
- **D-14-e は見出しが「D-2 の固有の条件」で、本文は JS の `number`・BigInt の規定**(`ADR:628-655`)。
  機械検査も `Math.round` / `Math.floor` 向け(`ADR:651-655`)。**SQL に及ぶとは書かれていない**
- **要件書は矛盾も裏付けもしていない** — 定めているのは丸めの意味だけ(`R:1169`)で、
  SQL にも浮動小数にも言及が無い(走査「SQL|ROUND|浮動小数|表示層|UI 層|画面側」)

**正しい整理**: **発効後に formatter が何になるかは発効条件 (iii) が未定**(`ADR:729-733`)。
そこで**丸めを SQL 側へ寄せる設計を採るなら**、`ROUND()` は D-14-e 3 の規則(整数対の剰余・`2r ≥ |d|`)を
満たさないので使えない。**確定した難所ではなく、(iii) が決めるべき分岐点である。**

**SQL 側で丸めるか表示層でよいかの線引きは、要件書に書かれていない**(spec-checker の走査結果)。
要件書が境界として書いているのは「**完成表示値**」と「**画面側・UI 層**」の間だけ(`R:1185`・`R:1192`)。
