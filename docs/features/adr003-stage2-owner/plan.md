## 4. 実装方針

### 重さ分類の根拠: 通常

- **コア領域に触れない。** `.claude/core-areas.json` の `paths` に該当するのは
  `docs/adr/ADR-003-domain-calc-method.md` / `backend/domain/*` / `backend/src/pitchlog/domain*` /
  `backend/src/pitchlog/generated/*` / `frontend/src/lib/generated/*` / `tests/domain/*` などだが、
  **本タスクはいずれにも差分を持たない**(2 節「やらないこと」)。`guard_paths` にも該当しない
- **軽微な修正ではない。** 甲と乙の線引きは**起票する新タスクの射程を決める判断**であり、
  誤ると**段階 2 全体の持ち主が割れる**
- **機械的軽作業ではない。** 機械的な置換や定型処理ではない

### 進め方

1. **判断の材料は [research.md](research.md) が正**。本節では内容を複製しない
2. **ステップ 1 の射程案は、必ず PO の裁定を得てから起票する。**
   **起票は外向きの行為であり、取り消しに手間がかかる**
3. **起票する新タスクの本文は、現況の事実を根拠つきで持たせる** —
   「枠だけが在る」状態(言語 backend 3 本が固定スタブ / 宣言の正本が不在 / QuickJS 配線ゼロ /
   実ベクタ 266 件が未接続)を**新タスクの着手時に測り直せる形**で書く
4. **行番号だけの典拠を新タスクへ書かない。** 節名・逐語を併記する
   (台帳の既存候補「行番号だけの典拠は自分の編集で古くなる」)

### 実装ステップ(コミット単位)

| # | 内容 | 完了条件 |
| --- | --- | --- |
| 1 | **甲と乙の射程案を作る** — 2 案(A: 1 タスクに統合 / B: 2 タスクに分割)を、**それぞれの DoD・所有者・先行条件・TSK-236 と TSK-455 への影響**つきで worklog に書き、**推奨を明示**する | worklog に 2 案と推奨があり、**各案が S01〜S34 の 34 件をどちらが引き取るかを明記している**こと |
| 2 | **PO 裁定を得る** — ステップ 1 の案を提示し、裁定と理由を worklog に記録する | worklog に**裁定・日付・裁定者**があること。**裁定なしでステップ 3 へ進まない** |
| 3 | **Notion へ起票し、所有者を設定する** — 裁定どおりのタスク(1 本または 2 本)を作り、**タスク名・DoD・射程・現況の事実・先行条件**を本文に持たせる | 起票したタスクの **URL と DoD が worklog にあり**、**担当者プロパティが設定されている**こと |
| 4 | **相互リンクを張り、`receiverTaskId` の送り先を決める** — TSK-510 ↔ 新タスク、および TSK-236 / TSK-455 の送り元へ、**コメントで**相互リンクする。**契約 JSON は本タスクでは更新しない**(2 節)ので、**どのタスクが更新するか**を決めて worklog と新タスクの本文に書く | 相互リンクが**両方向**にあり、`receiverTaskId` の**更新主体**が決まっていること。**本 PR の差分に `contracts/` が入っていないこと** |
| 5 | **U-X1 / U-X2 の解凍条件を確認し、カード DoD の扱いの裁定を得る**(カード DoD 2 行目)— 原典で確認したうえで、**調査の結論どおり「含まれていない」なら、カードの DoD が字句どおりには満たせないことを PO へ上げ、裁定を得る**。**選択肢と、それぞれで DoD がどう閉じるかを明示する** (2 周目 P0 — **送り先を決めるだけでは DoD は未達のままになる**):<br>**① カードの DoD を「確認した」へ改める** → **改訂をもって達成**<br>**② 解凍条件の側を是正する** → **是正の改訂が完了するまで本 DoD は未達**。**②単独では本タスクを閉じられない** — **①を併せて行うか、改訂の完了を待つ**<br>**③ 本タスクの射程を広げて是正まで行う** → **是正の完了をもって達成**(重さ分類の再判定が要る)。**あわせて「段階① の完了」と「方式決定を待つ」の 2 通りの書き方の扱い**も同じ裁定で決める | 確認結果と典拠(**節名 + 逐語**)が worklog にあり、**裁定・日付・裁定者**が記録されていること。**裁定なしで DoD を満たしたと書かない** |
| 6 | **起票に直接かかわる申し送り 3 件の送り先を決める** — [research.md](research.md)「未解決・申し送り」の **1(甲と乙の線引き)・2(射程宣言の食い違い)・6(解凍条件の 2 通りの書き方)**(計画レビュー 1 周目 P1 — **8 件すべてを完了条件にするのはカードの DoD を超える**)。**残り 5 件は worklog に一覧として残すだけ**にする | 3 件に送り先があり、**残り 5 件が worklog に一覧として残っている**こと |

**ステップ 1〜6 はいずれも文書と Notion の操作で、実装コードを伴わない。**
したがって **Codex への実装委任は行わない**(設計書 3 章の役割分担 — Git 操作・PR・ドキュメントは Claude)。

## 6. テスト計画

**NFR-019 のテスト種別(単体・一致性・越境・E2E・故障系)への追加は無い。**

**理由**: 本タスクは**実装コードを 1 行も追加しない**(2 節「やらないこと」・4 節ステップ表)。
NFR-019 が定めるのは実装に対するテストであり(`docs/requirements/requirements-pitchlog-2026-07-22.md:969`)、
**文書と Notion の操作に対応するテスト種別は NFR-019 に存在しない**。

**代わりに掛かる機械検査**(いずれも CI の既存ジョブ):

| 検査 | 何を見るか |
| --- | --- |
| `check_docs_status.py`(`docs-lint`) | frontmatter と変更履歴・索引の整合 |
| `check_plan_docs_sync.py`(`/pr` の受入条件) | **3 節の宣言と PR 差分の双方向突合** |
| `core_guard.py`(`core-guard`) | コア領域の paths に差分が無いこと(**本タスクは該当しない想定** — 該当した場合は分類の判定が誤っていたことになる) |
| `harness` の `pytest tests/` | 既存のハーネス試験に退行が無いこと |

**`contracts/` に差分を持たないことが前提である**(2 節)。
**`receiverTaskId` を本タスクで更新しないと確定した**ため、`consistency` ジョブと凍結基準の検査は
本 PR の射程に入らない(計画レビュー 1 周目 P0)。
**もし差分を持つ設計へ変わるなら、重さ分類が「コア領域」になり計画書の敵対レビューからやり直しになる。**
