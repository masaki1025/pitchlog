# 調査メモ: マージゲートの適用単位と測定経路の条文化

## 問い

TSK-378 の PO 裁定 A・B を **ADR-004 + `data-model.md` 12-4 の追随改訂**として条文にする。
**要件書を触る必要があるか / 12-4 に何をどう書くか / 何が壊れるか。**

裁定の中身は確定済み(`../merge-gate-api-cycle/design.md` 4 節)。本書は**条文化の設計**を扱う。

## 結論(要約)

1. **要件書 `NFR-019` の改訂は不要。** ただし**条件 2 つ**を守る場合に限る(2 節)
2. **TSK-378 が記録した典拠 `:957` は弱い。** 正しい主典拠は **8 章 `:1034`・`:1035`**(2-2)
3. **`data-model.md:246` が要件を誤引用している。** 「`NFR-010` の『API 直叩きを含む全経路』」の
   **「全経路」は要件書に存在しない**(3-4)
4. **12-4 を 1 バイト変えると 4 系統の検査が落ちる。** うち 1 つは
   **この PR では検出されず、次に backend を触る PR で赤くなる**(5 節)
5. **「軽量版」の定義は存在せず、実例も 0 件。** ADR-003 は v0.1 が **25 周**・v0.2 が **27 周**(6-2)

## 2. 要件書 `NFR-019` を触る必要があるか — **不要(条件つき)**

### 2-1. 「網羅の完成」は PR ごとのマージ条件になっていない

`NFR-019` 柱書(要件書 `:920`)は 3 文からなる。

1. テストランナーを標準化する
2. 「**PR ごとに CI で自動実行、全グリーンでないとマージ不可とする**」
3. 「CI には (a)…(b) 越境アクセステスト — 合否は…**網羅すべき組合せは**〔列挙〕…を含む」

**第 2 文の「全グリーン」は走ったテストの結果に対する述語**であり、
「未実装のテストがあるあいだマージ不可」と読める語は無い。
**第 3 文は CI の構成要件**で時点を持たない。
`NFR-019` 自身の測定方法は `:933`「**CI 構成の確認と実行履歴**」で、PR ごとの網羅度ではない。

**網羅を合否条件にしている条文は要件書に 1 箇所だけ** — **8 章 `:1035`(リリース判定基準 2)**:

> **CI全グリーン**: NFR-019 のテスト一式(…**(b)越境**…)がすべて成功。
> **(b) の合否は NFR-019(b) の定義に従う**(…**同項に列挙した組合せを網羅すること**)

**したがって網羅の判定時点は 8 章 = リリース判定**であり、PR ごとではない。

**補強**: 要件書 `:956`(`NFR-021`・Phase 4 完了時)が
「**一致性・越境・E2E・同期故障系は実装期のため対象外**」と、
**実装期に (b) が揃っていない状態を前提している**。

**マージを止める規範は要件書に `:920` の 1 本だけ**(`マージ` の全 4 出現を走査。
残る 3 件は変更履歴・Won't の「同時入力のマージ」・`NFR-021` のマージコミット)。

### 2-2. TSK-378 が記録した典拠は弱い — **`:957` ではなく 8 章**

TSK-378 の worklog が裁定 A を「リリース候補時の受入(**要件書 `:957`**)で行う」と記録した。
**`:957` は `NFR-021`(開発環境)の測定方法の 1 行で、`NFR-010` に一言も言及しない。**

| 用途 | `:957` は使えるか |
| --- | --- |
| 「対象横断の `(b)` 網羅の時点」の典拠 | **使える**(「(a)〜(d) がすべて成功」) |
| 「**`NFR-010` 適合の宣言**をここで行う」の典拠 | **使えない** — **要件に記載なし** |

**正しい主典拠は 8 章 `:1034`「Must 要件充足: 4 章・5 章の Must 要件がすべて受け入れ基準を満たす」**
(`NFR-010` は Must — `:843`)**+ `:1035`**。**`:957` は従に置く。**

**このまま ADR-004 へ写すと敵対レビューで落ちる。**

### 2-3. `NFR-018` との非対称 — ここが本論点の芯

| | `NFR-018` 系 | `NFR-010` / 12-4 系 |
| --- | --- | --- |
| 「PR ごと全グリーン」条項 | **持たない**。`NFR-019` 柱書 `:920` を共有 | 同じ `:920` を共有 |
| **未完成のあいだの扱い** | **要件書の条文に明記** — `:915`「**完成をもって正解ベクタとして発効する。完成前に NFR-019(a) を合格と判定してはならない**」+ **per-target 版**「**(α) の対象のベクタが未完成のあいだは、その対象について NFR-019(a) を合格と判定してはならない**」 | **無い**(要件に記載なし) |
| 実装禁止でないことの明記 | 設計書 `:897` | 同 `:897` は「**ただし `NFR-018` の対象計算に触れる実装は**」と**限定**している |

**このプロジェクトの approved 正本は、既に「`NFR-019` のサブ項目が不合格であること」と
「CI が全グリーンでないこと」を別物として運用している**(`NFR-018` 側)。
**それが「要件書を触らなくてよい」ことの条文上の裏付けである。**

**ただし裏付けの形は「`NFR-019` 柱書がその区別を書いている」ではなく、
「`NFR-018` 側が per-target の判定保留条項を持ち、それが `NFR-019(a)` の合否に作用している」**
という形であり、**`NFR-010` / `(b)` 側に対応条項が無いという非対称は残る。**

### 2-4. ADR-003 の先例の正確な形

`ADR-003:390` は per-target のマージ条件を
「**要件書 `NFR-018` の『正解ベクタは完成をもって発効する』の言い換え**」として位置づけている。
つまり **ADR は要件書の既存条項に接続しただけで、新しい規範を単独で作っていない。**

`ADR-003:387` が「同一の確定ゲートで要件書 v2.2 として改訂する」と言うのは
**(b)② の再定義**が理由であって、per-target 化そのものが理由ではない。

### 2-5. 条件 2 つ

**この 2 つを守らないと、要件書の改訂が必要な側へ倒れる。**

| 条件 | 内容 | 典拠 |
| --- | --- | --- |
| **A** | **網羅の判定時点を ADR-004 / 12-4 で「新設」しない。** 8 章 `:1035`(と `:957`)への**参照**で書く | `data-model.md:2764`「**要件書に行が無い。設計が単独で決めると要件の創出になる**」 |
| **B** | **「`NFR-019` の『全グリーン』は網羅の完成を要求しない」という `NFR-019` の解釈を ADR-004 の規範文として書かない。** 書いてよいのは **12-4 のゲート(= `data-model.md` 固有の規範)の適用単位**まで | 設計書 `:500`(7.6 柱書「同じ規則を別文書で再定義しない」)・`:406`(7.1-1) |

**条件を外して `NFR-019(b)` に `NFR-018:915` と同型の発効条項を置きたいなら、
そのときは要件書の改訂が要る。** 直す条文は `NFR-019(b)` の末尾(`:928`)。
**これは「要る/要らない」ではなく「どちらの設計を採るか」の分岐**である。

## 3. 12-4 に何をどう書くか

### 3-1. 裁定 A の置き場 — **「ゲートの対象」の直後に新行 + 通過条件②への参照**

裁定 A が決めるのは**量化子**であり、対象(PR の集合)でも述語(通過条件)でもない。
通過条件行に押し込むと 1 セルが 3 命題を持つ。

**ただし新行だけでは不足**。通過条件②の逐語「その実スキーマに対して越境テストが green である」は
単独で読むと対象横断に読める。**②に「(当該 PR が開く経路について — 適用単位の行)」の 1 参照**を
入れないと、片方だけ読む経路が残る。

→ **最小 = 新行 1 + ②への括弧参照 1。**

### 3-2. 裁定 B の置き場 — 既存「測定経路」行への**追記**

現行は禁止形。裁定 B は禁止を撤回せず**充足条件を与えて量化する**ので、書き換えでなく追記で足りる。

### 3-3. 最低要求 4 件との関係 — **明示しないと現行の曖昧さが残る**

最低要求 4 件(`:2441`)の主体は **① アプリ用ロール ② `PUBLIC` ③ `search_path` ④ 関数の返却契約**
= **全件 DB 層で HTTP への要求は 1 件も無い**。現行条文は**4 件と測定経路の関係を書いていない**。

**明示すべき区別**:

- **4 件は経路によらず掛かる下限**
- **HTTP 直叩きは経路を開く PR にのみ掛かる**

**波及 1 件**: `:2441` の 4 件は **`:2673-2675`(12-7 (1))にほぼ同文で再掲**されている。
**4 件の文言に手を入れるなら 12-7 (1) と食い違う**(手を入れなければ影響なし)。

### 3-4. `:246` の誤引用 — **要件書に「全経路」は存在しない**

`data-model.md:246` の逐語:

> 関数本体の正しさに関係なく越境できる(`NFR-010` の「**API 直叩きを含む全経路**」に反する)

**この鉤括弧内は `NFR-010` の逐語ではない。** 要件書 `:846` の逐語は
「越境アクセスの自動テスト(**API直叩き含む**。CIに常設 → NFR-019)」で、**「全経路」という語は無い。**

**実測**(要件書全文):

- `直叩き` の全出現 = **`:599`(FR-034 受入基準)と `:846` の 2 行のみ**
- `全経路` の全出現 = **`:751`(パスワード失効)と `:850`(認証トークン)の 2 行のみ。`NFR-010` とは無関係**

**これは TSK-378 で「対立案」として重く扱った読みの出所である。**
**対立案は正本の誤引用に立っていた。** 裁定 B がその読みを不採用にしたのは結果的に正しい。

**`:2442`(測定経路行)自身は正しく引用している**(「`NFR-010` の測定方法が『**API 直叩き含む**』と
定めるので」)。**割れているのは `:246` の 1 行だけ**(`直叩き`/`アプリ経路` を `docs/` 全数走査。
`data-model.md` 内の該当は `:161`・`:246`・`:259`・`:299`・`:2442` の 5 行で、
`:259`・`:299` は RLS の `FORCE` の文脈で無関係)。

**最小の是正**: 鉤括弧を `:846` の逐語へ寄せ、「全経路」を本文の主張として書き直す。

**`:161-163` は触らずに済む。** RLS を採る理由の記述であり、測定経路の充足条件を述べていない。
**注意**: TSK-378 の敵対レビュー `P1` が「**`:161-163` は読み ① を支持していない**」と是正済み。
**ADR-004 が「`:161-163` が裁定 B の根拠」と書くとその是正を巻き戻す。**

### 3-5. non-serving 宣言 2 項・3 項 — **参照へ寄せるのが条文上支持される**

2 項(`:2427-2428`)「RLS の DDL 適用と、実スキーマに対する越境テストが green になるまで、
DB を利用する製品機能を**マージまたは有効化しない**」は、
**ゲート表の通過条件①②を散文で言い換えた行**である(1 対 1 で対応)。

**これは `data-model.md` が確定ゲート 13 周・98 件是正し、なお打ち切った型そのもの**
(`:2778`「ある節が、定義節の持つ述語を散文で言い換えて持っている」/ `:42-44` の PO 裁定「定義の一本化」)。

| 直し方 | 評価 |
| --- | --- |
| (a) 2 項の述語自体に量化子を足す | **片方だけ直る事故を新規に 1 件作る**(`:42-44` が対象にした型) |
| (b) **2 項をゲート表の通過条件への参照に寄せる** | **述語の所在が 1 箇所になる。条文上こちらが支持される** |

**3 項(`:2429`)も同じ量化子の影響を受ける。** 「暫定的にアプリ層分離で先行する場合も、
**同じ越境テストの green を条件とする**」。**2 項だけ直して 3 項を残すと、
3 項が対象横断の読みを保持する。**

**1 項は影響を受けない**(初回 migration 固有の事実宣言)。

### 3-6. 定義の所在(`:49-64`)への行追加

`data-model.md:66` は「**この表に無い事項を後から複数節へ書くときは、
まず定義節を決めてこの表へ行を足す**」と定める。

**裁定 A は「経路」という語をゲートの量化子に据える。**
**「経路」は「製品機能」と同じく規範的定義を持たない語**である
(要件書 3 章の用語定義 **8 語**にも、`data-model.md` 1-1 節の定義の所在表 **13 行**にも無い。
12-4 内の既存用法: `:2425`「利用経路」・`:2439`「読み取りだけの経路」)。

**定義するなら 1-1 の表へ行を足す要求が発火する。定義しないなら「定義しない」ことを射程宣言に書く。**

## 6. 条文化の作法

### 6-1. 射程宣言の配置(設計書 `:478`)

> **配置**: **新設の正本 = 文書内の節として置く** / **既存正本の改訂 = 当該改訂の変更履歴行(in-review)に記載する**

→ **ADR-004(新設)= 節** / **`data-model.md`(既存正本の改訂)= 変更履歴行**。
**一括検証は単一ゲート**で、**適用版の記録はゲート単位で 1 件**(設計書 `:437`)。

### 6-2. ADR の作法と「軽量版」

**共通する節構成**(ADR-001/002/003 とテンプレートの全数比較):

`frontmatter → タイトル → 変更履歴表 → メタ表(状態/日付/決定者) → 文脈 → 決定 → 理由 → 帰結 → 参照`
(`理由` は ADR-002 のみ省略)

**ADR-003 が追加している型**(本件と同種の「争点を残す」ADR に有用):
決定に **`D-n` の連番 ID** / **却下した方式と理由の表** /
**帰結に「何が変わるか」「後続タスクへ送るもの」「見直しトリガー」の 3 小節**。

**「軽量版」の定義は存在しない。** リポジトリ全体を走査して出現は
**設計書 `:418` の表のその 1 行のみ**。**軽量版で通した ADR の実例も 0 件。**

| ADR | 周回 |
| --- | --- |
| ADR-001・ADR-002 | ハーネス設計書の確定ゲート(敵対レビュー 5 周)に**同梱** |
| **ADR-003 v0.1 + 要件書 v2.2** | **25 周**(P0 24 / P1 68 / P2 7 = 99 件・全件採用) |
| **ADR-003 v0.2 + 要件書 v2.6** | **27 周**(88 件・全件採用・P0 全周ゼロ) |

**「軽い」という期待は持てない。**

**ADR は 1 本も `core-areas.json` に登録されていない**(`docs/` 配下の登録は
`sync-protocol.md` / `data-model.md` / 要件書の 3 本のみ)。**ADR-004 の新設だけでは core 領域に
該当しないが、`data-model.md` を触る時点で本 PR はコア領域 PR になる。**

**採番**: `ADR-004` は未使用(存在するのは 001〜003 の 3 本・欠番なし)。
**採番規則の条文は見つからない**(走査したのは設計書 `:418`・テンプレート・索引・CLAUDE.md の 4 箇所)。

### 6-3. ADR + 正本改訂を同一ゲートで通す手順(**再現すべきは 2 件目**)

**1 件目(ADR-003 v0.1 + 要件書 v2.2・2026-08-19)は 7.3-1 の制定前**なので手本にできない
(設計書 v1.12 approved = 2026-09-01 で 7.3-1 が制定)。

**再現すべきは ADR-003 v0.2 + 要件書 v2.6(2026-09-03)。**

**ステップ 1(in-review 化)を独立した実装ステップとして最初に置く**:

- 両書の frontmatter を `approved → in-review`
- 両書の変更履歴へ **in-review 行**。**射程宣言は変更履歴行の中に書く**
- **版セルは暫定**と明記し、**版番号の確定は人間承認時の PO 裁定**とする
- `docs/README.md` 索引を **in-review 表記へ現行化**
- **同一コミットで適用版を暫定記録**(版数 + **条文コミット SHA = in-review 化コミットの第一親**)

**この順序は敵対レビューで確立された規範**である。TSK-278 の計画レビュー 2 周目 `P0-1` が
「**正本を編集した後で `approved → in-review` とする順序は 7.3 の状態遷移と逆**」と指摘し、
**① 両正本を先に in-review → ② 改訂と敵対レビュー → ③ 人間承認後に版・変更履歴・索引を確定 →
④ その最終コミットに対して派生資産を追随** が確定した。

**依頼文は 1 回で両正本を同時にレビューさせる**(2 回に分けない)。

### 6-4. 周回を伸ばさないために — 先例が明示的に残した対策

TSK-348(v0.2)は**レビュー 10 回のうち 6 周が「写し先の劣化」型**だった。
**2 つの PO 裁定が対策を確定している**:

| 裁定 | 内容 |
| --- | --- |
| 5 周目 | **worklog は遷移規則を再掲しない。** 遷移の正は設計書 7.3-2 と `/finalize-doc` スキルであり、worklog はそれを参照する |
| 7 周目 | **worklog は派生値(周回・指摘件数・P0 の連続・反映コミットの本数)を持たない。** 正は `plan.md` の frontmatter・採否記録の行・`git log`・`feature_status.py` であり、worklog はその所在だけを書く |

実装形が `docs/worklog/2026-09-09-data-model-v0-2.md:560-577` の「現在地」節
(**知りたいこと → 正の所在**の表)。**この型をそのまま使う。**

**そのほかの明示的な申し送り**:

- **是正の完全性を証明する機構を同一タスクの射程に入れない**(TSK-348 は機構を入れて
  計画レビュー 3 周・21 件を全部機構への指摘で消費した)
- **射程宣言は差分 hunk の全数と突合できる形で書く**(TSK-348 は最終全文確認周でここを
  `P1` で落とされ、hunk と射程宣言の対応表を worklog に全数記録して閉じた)
- **版繰り上げのタイミング**: `check_docs_status.py` が索引の版と変更履歴の最大版の一致を
  常時要求するため、**版繰り上げを確定ゲートまで遅らせられない**。
  **変更履歴の起案行が目標版を持ち、索引も同時にその版へ。確定ゲートでは状態だけが `approved` になる**

### 6-5. 設計上の注意 — **ADR に規範を置くと自分の論拠が返ってくる**

`data-model.md:2748`(12-8 第 14 項)が
「**越境テスト再実行ゲートの定義**(12-4 節)」を**本書の確定範囲**と宣言している。

**TSK-378 が案⑥(TSK-346 に畳む)を「射程侵犯」として却下した論拠は、
形式的には ADR-004 にも当たる。**

**解ける。** ADR-003 の先例が **「ADR に決定と理由、正本に規範」** という分担を取っている。
→ **ADR-004 = 争点・決定・理由・却下案 / 12-4 = 規範**、と切る。

### 6-6. 「適用単位で切った」条文の先例 — **`NFR-021` の書きぶりが最も近い**

要件書 `:954`(v2.3):

> **受入保証の範囲は、「現在の固定ディストリビューション版 × 受入を実施したアーキテクチャ ×
> 受入事象」の組に限る** … **その組で「正式受入」を経ていないアーキテクチャは
> 「互換性目標(未検証)」**として扱い、**保証対象とは呼ばない** … **持ち越さない**

**型**: 「**範囲は〈組〉に限る**」+「**組の識別子を定義**」+「**組の外は〈別の呼び名〉とし、
〜とは呼ばない**」+「**持ち越さない**」。

**確定の経緯**: 敵対レビュー 9 周。**2 周目で範囲を限定 → 3 周目で組を定義 →
4 周目で「受入時点」を追加 → 5 周目で「受入事象」へ精密化**。
**5・9 周目の P0 はいずれも「判定」と「正式受入の成立」の混同が根**で、台帳 `H-79` に登録されている。

**本件への含意**: 裁定 A は「判定の単位を〈組〉に落とす」同型。
**「判定」と「成立」を最初から分けて書かないと、`NFR-021` と同じ P0 を踏む。**

そのほかの先例: `NFR-018 (c)`(**閉じた表 + 成立条件を機械可読な述語 + 表の変更は改訂を要する**)/
`NFR-018 (b)②`(**対象・入力範囲・強さ・範囲外の 4 点セット**)/
設計書 `:951`(「判定の単位は `develop` の状態であり、feature ブランチの中間コミットではない」)/
`ADR-003:226`(「判定の単位 | 対象計算ごとに判定する(全体集約にしない)」)。
