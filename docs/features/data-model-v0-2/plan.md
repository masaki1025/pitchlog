## 4. 実装方針

### 重さ分類の根拠 — **コア領域**

`docs/design/data-model.md` は `.claude/core-areas.json` の **5 領域すべて**に登録済み。
**core-guard が発火する**ため**敵対レビュー + 人間の逐行確認(PR 作成者以外)が必須**。

### 版と索引の扱い(3 周目 `P1-1` の是正 — **TSK-342 の先例で確定**)

`scripts/check_docs_status.py:694` は **索引の版と変更履歴表の最大版の一致**を常時要求し、
`:704` 以降は**索引の最終更新が変更履歴の最大日付より前でないこと**を要求する
(`latest_version = max(versions)` — `:615`)。
したがって **`0.2` の行が変更履歴に 1 行でも出た瞬間、索引も `0.2` でなければ red** になる。
**版繰り上げを確定ゲートまで遅らせることはできない**(2 周目に私が書いた順序は成立しない)。

**TSK-342 の先例が正しい形を示している** — 同書の変更履歴は `in-review` / `draft` の周回中も
**目標版 `0.1` を持ち**、索引も `0.1` だった。**確定ゲートでは状態だけが `approved` になり、版は動かない**。

| 段 | 正本 frontmatter | 変更履歴の最大版 | 索引の状態 | 索引の版 |
| --- | --- | --- | --- | --- |
| **ステップ 1** | `in-review` | **`0.2`**(起案行) | **`in-review`** | **`0.2`** |

### `H-79` 対策は `[手動・外部]` に降ろす(PO 裁定)

**機械保証は TSK-353。** 本タスクでは次を `[手動・外部]` として行い、**worklog に記録する**:

1. **`search_path` / 一時スキーマ / `pg_temp` / 完全修飾 / 名前解決** の 5 語で全文走査し、
   **全出現行を worklog に列挙**する(実測の出現行は本計画 1 節に記録済み)
2. **各行を「是正済み / 要求側 / 無関係」に逐行で分類**し、判断理由を書く
3. **`要求側` に分類した行を変更していないこと**を `git diff` で確認する

**この 3 つを機械 green の一部として数えない。** 数えると「実効のない合格条件」(7.3-3 の P1)になる。

### 合格条件の書き方

**`[機械]`** と **`[手動・外部]`** に書き分け、**`[手動・外部]` を機械 green の一部として数えない**。
**「検査が green」ではなく「割り当てが正しい」に置く。**

**射程が正本 3 箇所・新設 0 件になったので 1〜2 周で閉じる見込み**である。
