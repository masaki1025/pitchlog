## 4. 実装方針

### 重さ分類の根拠 — **コア領域**

**意味上の根拠は 1 つ**(計画レビュー 1 周目 P2-2 を採用 — 当初「独立した根拠 2 つ」と書いたのは過大だった)。

**設計書 6.3 の境界定義表**が「状況計算」の**含む側**に
**「座標変換・捕球選手推定(`NFR-018`・`NFR-019(a)` の対象 — 旧システムで 3 箇所コピー・
『静かなデータ破壊』の事故前例〔改善台帳 `I-4`・`I-17`〕)」**を明記している。
**`COURSE_COORDINATE_SIZE` は座標変換の契約値**である。
同節は **「判定に迷うコードは含む側に倒す(fail-closed)」**とも定めている。

**機械上の理由(意味上の根拠とは別)**: `.claude/core-areas.json` は**要件書のパスを 4 領域に一括登録**
しており、本 PR が要件書を触るため **core-guard が発火する**。
**これは広い機械マッチであり、本件が 4 領域すべてを意味的に変更するわけではない。**

**逆に不足がある**: 6.3 はコアの契約・テストを変え得るファイルを含めるよう要求するが、
**`courseInputView.ts`・契約 JSON・新規テストは `game-state.paths` に未登録**である。
**充填は `TSK-228` / `H-12` の責務**で本タスクの射程外。**新規テストを候補パスとして引き渡す。**

→ **sol xhigh・敵対レビュー必須・人間の逐行確認必須。**
**製品コードは 1 行も変更しない**(テストの追加のみ)。**`fast path` は使えない**(正本影響があるため)。

**2pt はコア領域手続の免除条件ではない**(計画レビュー 1 周目の判定)。

### 射程から外した理由 — 要件書の 1 文字が 8 資産 + ハーネステストへ連鎖する(2026-09-01)

**ステップ 2 として要件書の例外表を更新したところ、`tests/test_check_authz_catalog.py` が red になった。**
TSK-270 の要件主張母集合が**要件書の blob digest を凍結**しているためで、**機構は正しく発火した**。

**追随しようとして連鎖が判明した**(Claude が実測):

| 資産 | 母集合への固定 |
| --- | --- |
| `contracts/authz/route-registry.json` | `requirement-claims.json` + `.lock.json` の blob digest |
| `contracts/authz/auth-catalog.json` | 同(40 桁 digest 179 件) |
| `contracts/authz/http-route-matrix.json` | 同 |
| `contracts/authz/oracle-seal.lock.json` | 同(**`oracle_commit` 上の blob と照合**) |
| **`tests/test_check_authz_catalog.py`** | **`total=1062 auth_claim=184 out_of_scope=878` を 4 箇所でハードコード** |

さらに `_verify_manifest_commit` が「**`commit` が指すコミットの blob が `source_blob_digest` と一致すること**」
を要求するため、**新しい blob を含むコミットが無いと母集合を更新できない**
(`oracle-seal` は同じ制約を **`oracle_commit`** でも課す)。

→ **TSK-270 の母集合修正へ合流させる。** 根拠:

- **母集合はどうせ直す** — マージ後の敵対レビューで **P0 7 件** + **インデント表の採取欠陥**(下記)
- **いま再封印すると誤った分類を 8 資産へ焼き直す**
- **あちらは要件書の追随が必須**なので、**例外表の 2 セルも一緒に更新すれば連鎖が 1 回で済む**

**形式上の残余(隠さない)**: 例外表は「有効化待ち」のままで**形式上は違反状態が続く**。
**ただし実リスクは解消済み** — 改善台帳 `I-17` の「座標系の二重管理による**静かなデータ破壊**」は
**ステップ 1 のテストで検出可能になった**(契約 JSON の `size` を変えれば必ず落ちる)。

**発見(TSK-270 の射程 — 本タスクでは直さない)**: **インデントされた表行が `paragraph` として採取される**。
例外表のデータ行は `NFR-018/paragraph-003` で、**`NFR-018` 配下に `table_row` が 0 件**
(heading 1 / list_item 28 / paragraph 3)。**TSK-270 の「表行の追加」負例が
インデント表を捕捉できない可能性**がある。

### ゲート区分 — **7.6-3 前段(実装追随・PR レビュー)で確定**

**条件分岐を置かない**(計画レビュー 1 周目 P2-1 を採用)。当初「レビューで覆るならステップ 2 を
確定ゲートの後に置く」と書いたが、**確定ゲート対象なら更新後の要件書がレビュー対象であり、
ステップ 2 の編集をゲート後には置けない**(順序として不成立)。

根拠:

- 要件書は **「下表への追加・削除・失効はいずれも本書の改訂を要する」**と**列挙**しており、
  **「有効化」は列挙されていない**
- **`NFR-018` (c) はテストの存在により例外成立を自動判定する**。状態欄は**その事実から導かれる従属値**
- 要件書 v2.1 の変更履歴も **「要件承認と実装適合は別」「テストは別タスク」**と明記している
- 台帳 **`H-19`** の 5 件は**線引き不調の観測**であり、**確定ゲートへ自動昇格させる規範ではない**

**仮に人間が確定ゲートへ覆す場合**は、**計画を再承認**し、順序を
**「テスト実装 → 要件書の候補差分作成 → `/finalize-doc` → 残りの台帳更新」**とする。
ゲートでは**例外範囲が拡大していないこと・テストが生の契約値を読むこと・
失効条件と判定者と終了証跡セルが不変であること**を検証する。

### テストの置き場と形(計画レビュー 1 周目 P1-4 を採用)

**新規ファイル `frontend/src/lib/courseCoordinateContract.spec.ts`。**

**契約 JSON を直接 import し、リテラル `263` を書かない。**

**`vitest/globals` は使えない**(計画レビュー 2 周目 P1-1 — `frontend/tsconfig.app.json` の
`types` は `["vite/client"]` だけで、既存 spec はすべて明示 import している。
globals 前提で書くと **`vue-tsc` が通らない**)。

**`COURSE_COORDINATE_SIZE` と `DISPLAY_COORD_SIZE` を別々の名前付きテストにする**
(変異の帰属を**完全テスト名**で固定するため)。

```ts
import { describe, expect, it } from 'vitest'
import geometry from '@contracts/display_geometry_263_v1.json'
import { COURSE_COORDINATE_SIZE } from './courseInputView'
import { DISPLAY_COORD_SIZE } from './displayGeometry'

describe('courseCoordinateContract', () => {
  it('COURSE_COORDINATE_SIZE が契約の size と一致する', () => {
    expect(COURSE_COORDINATE_SIZE).toBe(geometry.size)
  })

  it('DISPLAY_COORD_SIZE が契約の size と一致する', () => {
    expect(DISPLAY_COORD_SIZE).toBe(geometry.size)
  })
})
```

| ID | 完全テスト名 |
