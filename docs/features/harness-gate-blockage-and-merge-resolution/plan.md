# 実装計画書: 必須チェックの構造的失敗の経路と、core_guard / frozen_history を区別した競合解消手順

## 1. 背景・目的

- Notion: [TSK-559](https://app.notion.com/p/3fa93b75e6878141bc7ec3a428ebb69b)
- 対象の正本: ハーネス設計書 `docs/development/dev-harness-design-2026-08-07.md`(現行 v1.19・approved)
- 関連要件: NFR-019(テスト必須)・NFR-021(受入ゲート)を支える開発プロセスの規範。要件書そのものは変えない
- **穴 1**: 必須チェックが**構造的に**満たせない(失敗の原因が PR の差分の外にある)ときの正規の経路が、どの正本にも無い。#119(保護の一時解除)・#139 と #138(develop 赤 → 前進の別 PR を待つ)・レビュー主体の停止(PO の期限付き裁定)で、**採った手が毎回違う**
- **穴 2**: 取り込みの競合解消が検査器の意味論と対応していない。テキストとして解くと、**機械検査が緑のまま意味が壊れる**(#131 で `tests/test_core_guard.py` を自ブランチ版で解き、#133 の表明を落とした)。core_guard(merge-base との関係を各コミットで見る)と frozen_history(PR event の base との差を、追記専用の履歴と導出値で見る)は競合の意味が違うのに、正本は区別した手順を持たない
- 事実と典拠は [research.md](research.md) に置く(本書は契約だけを書く)

## 2. スコープ

### やること

1. 設計書に **6.5「必須チェックが構造的に満たせないときの経路」**を新設する
   - 判定基準: 「構造的失敗」= 失敗の原因が当該 PR の差分の外にあること。**判定の手順**(同じ検査を比較元〔base 側〕で走らせて同じ失敗が出るか / 失敗した規則が当該 PR の変更を見ているか)
   - 原因の 3 類型(①比較元〔develop〕自体が赤 ②検査規則が無害な変更まで止める ③外部主体〔レビュー委任先など〕が利用できない)と、**類型ごとに許す手段と序列**。手段は (a) 前進で直す別 PR / (b) 検査器の規則改訂 / (c) 保護設定の一時解除 / (d) PO の期限付き裁定
   - (c) の必須条件(#119 を原型): 事前の PO 承認・外す範囲(必須指定の該当 1 件だけ、`bypass_actors`・`enforcement` は不変)・時間・解除中にマージしてよい PR(当該 1 件のみ)・原本の sha256 の事前取得・復元後の独立照合・記録先・10.2 の再確認義務(TSK-432/433)との関係
   - (d) の様式: 対象・期限・期間中の代替・事後の追認・失効条件・記録先
   - 事後の追跡義務(誰が・いつ・どこへ記録するか)。**追認の実施を追跡する置き場**(W138 の台帳候補 対応案 (f) が指摘する穴)をどこに置くかもここで定める
   - 禁止形: 比較元に依存する免除で規則を緩めること(#135 の P0 の理由)/ 検査の抜け(2 コミット分割・マージコミット)を意図して使うこと
2. 設計書に **6.6「develop 取り込み時の競合解消」**を新設する。**core_guard と frozen_history を別項**にし、型ごとに「判断規則」「やってはいけない解き方」「確認コマンド」を置く
   - core_guard 項: ① `.claude/core-areas.json` の `paths`(回転式の窓口)— **片側採用でも和集合でもなく**、比較元の基線に、当該ブランチが宣言した追加層(`AREA_PATH_ADDITIONS`)を宣言の順で全件足した形へ**組み直す** ② 基線定義 paths(`scripts/core_guard.py`・`tests/test_core_guard.py`)— 両側の表明を内容で 3 方向に統合する(相手側の表明を落とさない)。同一コミット規則との関係(マージコミットは検査されないことを前提にしない)
   - frozen_history 項: ③ 単調な版数(`contract_revision` など)— 比較元の最新から採り直す ④ digest pin — 再計算して pin し直す(導出値はマージしない)⑤ 追記専用の受理履歴 — 比較元の履歴の後ろへ付け直し、受理 ID をその PR 番号にする(生成器で作り直す)
   - **手元で再現できない検査**を名指しして列挙し、push 前の再現手順を置く: frozen_history の PR 受理モード(2 親の合成マージ + event JSON + `GITHUB_EVENT_NAME=pull_request`)/ core_guard の PR イベント模擬 / **マージ後の develop の模擬**(clone で `origin/develop` を合成マージへ付け替える — #139 の教訓)
   - `/pr`・`/check` から機械的に警告できる範囲を**切り出して列挙する**(自動化そのものは別単位)
3. 事例 → 節の対応表を置く(#119・#131・#132・#138 を必須、#133・#139 を補足)
4. 変更履歴表へ in-review 行を追記し、`docs/README.md` の設計書の行を現行化する。確定ゲート(7.3)を通す

## 4. 実装方針

- **重さ分類 = 通常**: コア領域のコード・paths(`.claude/core-areas.json`)には触れない。設計書は `core-areas.json` の paths にも `guard_paths` にも無い(2026-10-15 実測で確認する — ステップ 1 の前提)。ただし**正本の構造的変更なので確定ゲートは必須**
- 文書の起案は Claude の役割(CLAUDE.md)。1 ステップ = 1 コミット
- **解き方の規則は、検査器の実装に照らして成立することを確かめてから書く**。6.6 の各規則には、規則どおりに解いたときに当該検査器が緑になり、片側採用・和集合で解いたときに赤になる(または緑のまま意味が壊れる)ことを、#132 の競合を素材にした使い捨ての clone で実演した結果を worklog に残す(本書・正本には実演の手順だけを置き、#132 のブランチは変更しない)
- **独立レビュー**: 自己レビュー(本セッションが起動するサブエージェントを含む)を独立レビューとして扱わない。計画レビューと確定ゲートの敵対レビューは、**本セッション以外の主体**に依頼する(候補と判断は「必要な承認」)
- 確定ゲートの手順は `/finalize-doc`。7.3-1 の適用版は、初回敵対レビューの実行時点で approved の 7.3 の版を記録する
- **in-review のまま develop へマージしない**(approved 前提の試験が赤になる型 — 台帳 H-84)。PR は確定ゲートの通過まで draft に留める
