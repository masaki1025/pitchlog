## 4. 実装方針

### 改訂後の確定文(この一文を実装の契約とする)

**NFR-021 要件**:

> 開発環境は **Windows 11 上の WSL2** で完結する(**Windows ネイティブでの開発は対象外**。PostgreSQL は **WSL2 内**にネイティブ導入するか Docker で立てる)。セットアップ・起動手順を **`docs/development/onboarding.md`** に整備する

**NFR-021 測定方法**:

> **WSL2 クリーン環境**でのセットアップ再現

**要件書 7.1(`:739`)の技術スタック行**:

> …PostgreSQL(本番=Supabase、開発=**WSL2 内のネイティブ導入 or Docker**)

**改善台帳(`:58`・I-6 の「pitchlog」欄)** — 文言の書き換えではなく**参照への置換**:

> **pitchlog**: 開発・本番ともPostgreSQL(本番はSupabase継承。**開発環境での配置は要件書 [NFR-021](requirements/requirements-pitchlog-2026-07-22.md) を正とする**)

**相対リンクのパス注意**: 改善台帳は `docs/` 直下にあるため、要件書への相対パスは **`requirements/requirements-pitchlog-2026-07-22.md`**(`../` を付けない)。`../requirements/...` はリポジトリ直下の存在しないディレクトリを指し、CI の `docs-lint`(lychee `--offline`・`ci.yml:48`)が落ちる(計画レビュー 6 周目 P1)。

理由: 現行の「開発は**Windows ネイティブ版** or Docker」は**要件書 NFR-021(`:689`)・7.1(`:739`)の内容をそのまま複製したもの**であり、docs 規約の第 1 項に反している。

> **1テーマ1正本**。他文書からは相対リンクで参照し、**内容を複製しない**(`.claude/rules/docs.md:8`・設計書 7.1-1)

I-6 の改善の核心は「**SQLite/PostgreSQL 二重運用をやめ PostgreSQL に一本化する**」であり、DB の設置場所はその付随記述にすぎない。参照へ置き換えることで I-6 の改善内容は不変のまま、規約違反の重複が解消し、今後 NFR-021 が変わっても台帳の追随が不要になる(人間の裁定 2026-08-11・計画レビュー 5 周目 P1)。

**この扱いを一般則にしないこと(6 周目レビューの限定)**: 「参照化すれば常に PR レビューで足りる」という論法は成立しない。7.6 は要件改訂などの構造的変更を確定ゲートへ送る。**今回 PR レビューで足りるのは、方針変更の本体を要件書 v1.9 の確定ゲートに載せたうえで、改善台帳からは非正本の配置記述を除去するだけ**という限定された条件によるものである。

**DB の設置場所は WSL2 内へ統一する**(人間の裁定 2026-08-11・計画レビュー 4 周目 P1-1)。「ネイティブ版または Docker」という**許容幅は要件レベルで維持**するが、**Windows ホスト側は排除**する。根拠 — 実装側の文書はすべて Docker 前提であり、Windows ホスト上の PostgreSQL はどこも採っていない:

### 裁定: Windows ネイティブ開発は認めない(WSL2 必須)

計画レビュー 3 周目 P1-2 で、WSL2 方針に関する記述の食い違いが指摘された。**人間の裁定(2026-08-11)により「WSL2 必須」に統一する。** 根拠:

| 典拠 | 内容 |
| --- | --- |
| 設計書 `:668` | 「実行環境は WSL2。**WSL1 非対応のため必ず WSL2**。`[windows] sandbox` 設定は不要」 |
| 設計書 `:710`(論点C) | 2026-08-07 の PO 決定で WSL2 へ移行 |
| `onboarding.md` 0 章 | 「開発環境は WSL2(Ubuntu 推奨)を**標準とする**」+ **「WSL2 であること」を必須項目**として `wsl -l -v` の確認を要求 |
| `onboarding.md:52` | 「WSL2 では …`[windows]` セクションは**不要**」 |
| 技術的制約 | Codex の Linux sandbox(bubblewrap)は WSL1 非対応 |

矛盾していたのは以下の 3 箇所で、いずれも**論点C 改訂(ネイティブ継続 → WSL2 移行)前の前提が残ったもの**と判断する。

- 設計書 `:418` — 「/setup-dev … Codex の trust・**Windows sandbox 推奨設定の確認**(onboarding.md 準拠)」← onboarding はもう設定させていない
- 設計書 `:517` — 「**onboarding で設定させる** trust・**Windows sandbox 設定**を自ら無効化してしまう」← 同上
- `setup-dev/SKILL.md:19` — 「**Windows ネイティブで例外的に使う場合のみ** `[windows] sandbox = "elevated"` を提案」← `:668` の「必ず WSL2」と非整合

いずれも「Windows sandbox 設定」への言及を除去し、**WSL2 単一経路**に揃える。NFR-021 の確定文「WSL2 を含む Windows 11 上で完結」はこの裁定と両立する(Windows 11 上の WSL2 で完結する、という構造)。

**除去対象ではないもの**: 設計書 `:525`(9.3)は「Codex CLI が Windows ネイティブを正式サポートしている」という **Codex 側の仕様の事実**を述べたうえで「実地の障害により WSL2 へ移行」と結論しており、裁定と整合する(→「更新しないリスト」に分類)。

**テストへの影響なし**: `tests/` が参照する skill は `pr/SKILL.md` のみ(`test_core_guard.py:19`・`:352` の `guard_paths` と三者一致検査)。**`setup-dev/SKILL.md` は検査対象外**のため、編集による回帰は生じない。

### 重さ分類の根拠 — 通常

- **コード変更なし**の文書タスクだが、**正本(要件書の Must 要件)の改訂を含む**ため fast path の 3 条件(非コア・小差分かつ**正本への影響なし**・typo/コメント類 — 設計書 6.1)を満たさない。よって `軽微` ではなく **`通常`**
- `機械的軽作業` でもない(文言の判断と敵対レビューの反映を伴う)

### コア領域・検査経路の判定 — 非該当

`.claude/core-areas.json` の 5 領域は `paths` が空(Phase 4 で定義予定)であり、本タスクはそれらのコードに触れない。**`guard_paths`(`core-areas.json` 自身・`ci.yml`・`core_guard.py`・`pull_request_template.md`・`pr/SKILL.md`)にも 1 つも触れない**ため、`core_guard.py` は該当なしで exit 0 となる。

なお `paths` が空であること自体は判定に影響しない — `core_guard.py:269-270` は「コア領域 paths 未定義」の**通知を出すだけ**で、実際の突合は `:272` の呼び出しで `matched_paths()`(定義 `:210`・判定式 `:223-224`)が `guard_paths` の完全一致 **∪** `path_patterns` の glob に対して行う。したがって「paths が空だから該当なし」ではなく「**どちらにも該当しないから該当なし**」が正しい根拠。よって PR の逐行確認チェック項目は不要。

### 確定ゲートを 2 回回す — 順序と索引の同期

要件書(v1.9)と設計書(v1.4)は**どちらも確定ゲート対象**なので、`/finalize-doc` を 2 回回す。

**順序の制約が 2 つある。**

1. **要件書 → 設計書**。設計書は「要件書 v1.9 は通過済み」と書くため、要件書の approved が先
2. **波及の追随(ADR-002・AGENTS.md・spec-checker.md・README.md)は設計書の確定ゲートより前**。設計書 `:442` は「spec-checker が参照する正本」を記述しているため、設計書だけ v1.9 に更新して実ファイルが v1.7 のままだと、敵対レビューに矛盾した状態を渡すことになる

**索引の status は frontmatter と同時に動かす。** `check_docs_status.py` は索引の状態セルと frontmatter の `status` の**不一致を失敗にする**(`:370-376`)。したがって設計書を `in-review` にするステップで**索引の設計書行も `in-review`(v1.4)へ**変更し、approved 化のステップで**両方を `approved` に戻す**。

**確定ゲートは指摘反映ループを含むため 1 ステップ 1 コミットの原則から外れる。** 既存の前例(`docs/features/harness-baseline-merge/plan.md:55`)と同様、**指摘反映を伴う周ごとに 1 コミット**とし、承認後の状態遷移を別ステップ・別コミットにする。

**停止境界**: `/finalize-doc` の手順は人間承認後の approved 化・索引更新まで一連だが(`finalize-doc/SKILL.md:13-19`)、本計画では**ステップ 2 と 6 は「人間の承認を求めた時点で停止」**し、承認を得てからステップ 3 / 7 へ進む。承認なしにステップ 3 / 7 を実行しない。

**コミット件名のトークン**: 各ステップのコミットには完全トークン `(ステップ <k>/7)` をちょうど 1 個含める(設計書 6.1)。確定ゲートの反映周コミットは**同じステップ番号**を使い、付記で周回を示す — 例 `(ステップ 2/7 反映1周目)`。承認取得・計画書起票のコミットには**付けない**。なお本タスクの全コミットは `docs/` 配下または `.md` のみに触れるため「文書系」として無記法でも正当だが、進捗導出を機能させるためトークンを付ける。
