# 調査メモ: Phase 4-5 NFR-021 証跡の機械検証器と append-only の CI 検査

## 問い

1. 要件書 NFR-021 が要求する証跡項目・判定条件は何か(合格条件 ⑩ の機械検査対象の正)
2. 検証器の設計で過去に却下・撤回された案は何か(再導入事故の防止)
3. 既存の harness スクリプト・テスト・CI の実装様式は何か
4. **10.1 が定める失効判定(変更パス集合の求め方)は、Git CLI の既定挙動で実現できるか** — 自分の実測

## 結論(要約)

1. **失効判定は Git の既定挙動では規範を満たさない**。`git log --format= --name-only -m --no-renames <T>..<C>` の 3 オプションを全部明示して初めて 10.1 ②③④ どおりになる。既定のままだと本リポジトリの実履歴で**失効対象 12 パスを取りこぼす**(4-2 節)。祖先判定は 0/1/**128** の 3 値で、`returncode != 0` の一括判定は「失効」と「判定不能」を混同する(4-4 節)
2. **4-5 の受入契約は「二段の機械検査を両方実装すること」**(`docs/ops/nfr021-acceptance/README.md:162`)。ゲート時の完全性検査 ⑩(名指しされた 1 件のみ)と統合時の受入検査(その PR の新規追加分のみ)は**別物で互いに代替しない**。**どちらも過去の証跡へ広げてはならない**(恒久閉塞するため)
3. **禁止事項が 30 件超あり、その多くは「素直に書くとそうなる」実装**(2 点差分・`--cc`・リネーム検出・`fnmatch`・全件 `passed` 要求・畳み込み前の最大値判定)。2-3 節のリストを実装前チェックリストとして使う
4. **13 章が送った宿題(マージ後検査の期待値をどの媒体へ置くか)は 4-4 で消化されておらず 4-5 が決める側**。ただし証跡ディレクトリは選択肢から除外済み、`phase4_base_sha` の証跡キー化は撤去済み案の復活にあたる(2-4 節)
5. **要件由来と設計由来の切り分けが必要**。append-only・fail-closed・`gate_kind`/`attempt_seq`/失効判定は**すべて設計書 10.1 由来**で、要件書には存在しない(1-4 節)。計画書で NFR 由来と書くと典拠の誤りになる
6. **実装様式は既存 4 スクリプトに確立済み**で、一時 git リポジトリを作るテストの雛形も 2 系統ある(3-2 / 3-4 節)。**judgment が必要な分岐点は 7 件**(3-11 節)

## 調査者の裁定(エージェント間の食い違い)

**論点**: 命名正規形の判定が `check_docs_status.py` に既に 1 実装あり、4-5 の命名文法検査が 2 箇所目になる。これは NFR-018(単一実装)違反か。

- Explore は分岐点 3 を「NFR-018 の思想」として提示
- decision-tracer は「NFR-018 は『ドメイン計算』に限定され、ハーネススクリプト間の重複を禁じる決定は**見つからない(不明)**」と報告

**原典で確認して裁定**: 要件書 `:867` は「**対象(本項の列挙を正とする)**: 状況判定・座標変換・捕球選手推定・成績集計の前処理・終了判定」と**閉じた列挙**であり、命名文法の判定は含まれない。spec-checker も NFR-018 は「該当なし」と独立に報告している。→ **NFR-018 違反ではない**。したがって分岐点 3 の既定は**リポジトリの既存慣行 (c)「同一リテラル + 相互参照コメント + 腐り検知テスト」**(`docs/worklog/2026-08-10-codex-plan-status-guard.md:25-27`)。

#### 2-3. **実装で再導入してはいけない禁止事項**(4-5 の中核制約)

**証跡の選択**

- **全件 `passed` を要求する / 1 件でも `passed` なら可とする** — 前者は 1 件の失敗記録で永久に合格不能、後者は後続の失敗を無視して古い合格で通る(`:637`、`docs/worklog/2026-08-11-req-v1-9-nfr021-wsl2.md:84`)
- **証跡を自動選択する**(`evidence_path` を必須入力にしない)(`:637`)
- **最新試行の判定(⑦)を省く** — 名指しだけでは「後発の `failed` を無視して古い `passed` を選ぶ」経路が閉じない(`:637`、同 worklog `:87`)
- **予約と結果を `attempt_id` で畳み込む前に最大値の一意性を数える** — 予約と結果は同じ `attempt_seq` を持つので**最大値が必ず 2 回現れ恒久 fail-closed になる**(`:637`、同 worklog `:97`・`:105`。**設計文の記述バグとして 8 周目に捕捉された**)
- **候補 SHA のツリー外・未コミットの証跡を対象にする**(`:637`)

**失効判定**

- **2 点差分を用いる**(`:641` ②)/ **`T...C`(merge-base 比較)を基準にする**(`docs/features/nfr021-evidence-format/research.md:170`)/ **祖先条件の検証を省く**(`:641` ①)
- **マージコミットの差分を含めない・`-c` / `--cc` で済ませる** — `-c`/`--cc` は「全親から変更されたファイルだけ」を出すため**取りこぼしが許されない用途に不適**(`:641` ③、同 research `:172`)。**4 節の実測(combined / dense-combined が 109 のまま)と一致**
- **リネーム・コピー検出を用いる**(`:641` ④)
- **`fnmatch` や素の接頭辞一致でパターン照合する** — `fnmatch` の `*` は `/` を跨ぎ `**` の特別扱いも無い(**不適**)。`syntax` が未知値なら fail-closed(同 research `:179-188`)
- **`allowlist` を検証器側で独自に増やす** — 10.1 の allowlist は「のみ」= 閉じた列挙。増補は 7.3 の確定ゲートを要する(`:641`)

**検査範囲**
