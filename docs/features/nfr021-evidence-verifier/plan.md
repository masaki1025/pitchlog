## 4. 実装方針

詳細設計は [design.md](design.md)(ファイル構成 / 正規形パーサの成分 / スキーマ適合 / ①〜⑩ の実装と負例の対応 / 失効判定 / (a)〜(d) / 自己同一性確認 / 宿題への結論)。調査は [research.md](research.md)。**本節はそれらを複製せず参照する**(設計書 7.1-1)。

### 重さ分類の根拠 = **通常**(`gpt-5.6-terra` / max)

ADR-001 は「重さの判定は**コア領域リスト(設計書 6.3)で決まる**」と定める(`docs/adr/ADR-001-codex-model-selection.md:32`)。本タスクの変更対象は `scripts/` 2 本・`tests/`・`.github/workflows/ci.yml`・`docs/` で、**コア領域(同期プロトコル / 状況計算 / 記録権 / テナント分離 / データ移行)のいずれにも属さない**(`.claude/core-areas.json` の 5 領域の `paths` はいずれも未充填で、意味範囲の正である設計書 6.3 の境界定義表にも該当しない)。よって **通常**。

**ただしレビュー強度は上げる**: `.github/workflows/ci.yml` は `.claude/core-areas.json` の `guard_paths` に含まれるため、**人間の逐行確認が必須**(設計書 6.3 / `/pr` が必須チェックを自動付与)。また誤りの帰結が「**ゲートの恒久閉塞**」または「**ゲートの迂回**」であるため、一次レビュー(`review normal`)の後に**敵対レビュー(`review adversarial`)を 1 周追加する**。

### 実装上の中核制約(禁止事項)

[research.md](research.md) 2-3 節の禁止事項リスト(30 件超)を**実装前チェックリストとして使う**。とくに事故になりやすい 5 件:

1. **予約と結果を `attempt_id` で畳み込む前に `attempt_seq` の最大値の一意性を数えない** — 予約と結果は同じ番号を持つため**最大値が必ず 2 回現れ恒久 fail-closed になる**(v1.4 確定ゲート 8 周目で設計文の記述バグとして捕捉された型)
2. **⑩ と統合時検査を過去の証跡へ広げない** — `failed` 1 件で恒久閉塞する
3. **失効判定に 2 点差分・`T...C`・`-c`/`--cc`・リネーム検出を使わない** — `git log --format= --name-only -m --no-renames <T>..<C>` を明示([research.md](research.md) 4 節で実測)
4. **`fnmatch` でパターン照合しない**(`*` が `/` を跨ぐ)。`syntax` 未知値は fail-closed
5. **`merge-base --is-ancestor` の終了コードを 0/1 の二値扱いにしない** — 128 は「解決不能 = 判定不能」(実測)

### 本タスクが塞がない残余リスク(記録)

- **直接 push・GitHub UI / API による `develop` の更新**は機構で塞がない。10.1 `:640` が残余リスクとして受容し、対策を「人間管理の排他区間」(運用規律)と定めている

- どちらも **ブランチ保護が適用可能になった時点で再検討**する。台帳へ follow-up として記録する(/task-done のクローズ処理)
