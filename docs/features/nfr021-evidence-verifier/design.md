# 詳細設計: NFR-021 証跡の機械検証器と append-only の統合時受入検査

典拠は [research.md](research.md)。本書は同メモと設計書 10.1 / `docs/ops/nfr021-acceptance/README.md` を複製せず参照する(設計書 7.1-1)。

## 1. ファイル構成と依存の向き

| ファイル | 責務 | 依存 |
| --- | --- | --- |
| `scripts/verify_nfr021_evidence.py` | **ゲート時の検証**(10.1「検証器の契約」①〜⑩ + 失効判定 + 自己同一性確認)。命名文法の正規形パーサ・スキーマ検査・失効判定の**実装をここに置く** | `core_guard.GuardError` を try/except import(既存の唯一の共有前例 — `scripts/check_plan_docs_sync.py:13-16`) |
| `scripts/check_nfr021_append_only.py` | **統合時の受入検査**(10.1「保持」(a)〜(d))。PR 差分で新規追加された予約・結果証跡だけを対象にする | `verify_nfr021_evidence` から**正規形パーサ・スキーマ検査・完全性検査を一方向 import**。`GuardError` も同経路 |

**2 ファイルに分ける理由**: README `:130` が「ゲート時の ⑩ と統合時の本検査は別物であり、互いに代替しない」と定めており、**呼び出し経路が別**(検証器 = 判定者が手で実行 / 統合時検査 = CI が PR ごとに実行)。1 ファイル + `--mode` にすると、CI の設定ミスでゲート側の経路が動いてしまう余地が生まれる。

**共通ロジックを検証器側に置く理由**: 依存の向きを一方向に固定できる(逆にすると「統合時検査のためのモジュール」をゲート時が読む形になり、README の「別物」の関係が実装で反転する)。第 3 のモジュールを新設しない(リポジトリに前例がなく、`sys.path` 操作も既存様式にない)。

**`scripts/check_docs_status.py` は触らない**。同ファイルの索引カバレッジ除外述語(`:151-194`)は **`.md` 限定・真偽値のみ・種別不問**で、本設計の正規形パーサ(**拡張子を問わず fail-closed**・種別と成分を返す)とは**同一の述語ではなく、片方が他方の部分集合にもならない**([research.md](research.md) の裁定)。共通化せず、**両者に相互参照コメントを置き、リテラル整合の腐り検知テスト**(前例 `tests/test_core_guard.py:344-350`)で縛る。

## 2. 正規形パーサが返す成分

`docs/ops/nfr021-acceptance/README.md:30-50` の閉じた命名文法を、**種別 + 成分**へ分解する。

| 種別 | 判定 | 返す成分 |
| --- | --- | --- |
| `canonical`(正本) | ファイル名が `README.md` / `reservation-template.md` / `evidence-phase4-template.md` / `evidence-release-template.md` の**完全一致 4 件** | 種別のみ(**検証器の列挙対象から除外** — `README.md:39`) |
| `reservation`(予約) | `YYYY-MM-DDTHHMMSSZ-<gate_kind>-<phase4\|vX.Y.Z>-seq<NNN>-reservation.md` | timestamp / gate_key(合成形)/ attempt_seq |
| `evidence`(結果証跡) | 同末尾が `-<short_sha>.md`(`<short_sha>` = **小文字 16 進 12 桁**) | timestamp / gate_kind / release_version(`phase4` なら None)/ attempt_seq / short_sha |
| `invalid` | 上記のいずれにも一致しない**すべてのツリー項目** | 不合格理由(**無視ではなく不合格** — `README.md:32-35`) |

字句規則(`README.md:44-50`):

- timestamp = `\d{4}-\d{2}-\d{2}T\d{6}Z` の `fullmatch` **かつ** `datetime.strptime(v, "%Y-%m-%dT%H%M%SZ")` が成功する**実在時刻**(既存前例 `scripts/check_docs_status.py:180` と同じ二段)
- ゲート組は **`phase4-phase4` または `release-vX.Y.Z` のみ**。`vX.Y.Z` = `v` + 数値 3 連
- `seq<NNN>` = **最低 3 桁ゼロ詰め**。`len >= 3` かつ ASCII 10 進かつ `int(v) >= 1` かつ `str(int(v)).zfill(3) == v`(`seq001` 正 / `seq0001`・`seq1`・`seq000` 不正 / `seq1000` 正)
- `<short_sha>` = **先頭 12 文字固定**(Git の動的な一意短縮に委ねない — `README.md:49`)

**`invalid` の対象に含めるもの**(`README.md:32-35` の原文): `.MD` などの大文字違い / `.yaml`・拡張子なし / **サブディレクトリとその配下の全項目**。走査は `docs/ops/nfr021-acceptance/` 配下の**全ツリー項目**(`.md` に絞らない)。

### 3-1. 入力の受理条件(すべて fail-closed)

**候補 SHA は可変参照を一切受理しない**(レビュー 1 周目 **P0**)。10.1「候補 SHA の固定」は「**開始時に `candidate_sha` と `base_sha` をいずれも完全な commit OID として固定**し、以降ブランチ名(可変)で参照しない」と定めている(`dev-harness-design-2026-08-07.md:639`)。検証器が `HEAD`・ブランチ名・タグ・短縮 SHA を受理すると、**固定すべき候補を可変参照で検証できてしまい**、検証した SHA と実際にマージされる SHA の一致が崩れる。

| 入力 | 受理条件 | 違反時 |
| --- | --- | --- |
| `--candidate-sha` | **完全な小文字 16 進 40 桁のみ**。字句検査を通した後、**`git cat-file -t <sha>` が `commit` を返すこと**を確認する。**`<sha>^{commit}` による解決では不十分**(レビュー 2 周目 P0)— `^{commit}` は**注釈付きタグを commit へ剥がす**ため、40 桁の**タグオブジェクトの OID** が通ってしまう。**生のオブジェクト種別が `commit` であること**を要求する | 入力エラー(fail-closed) |
| `--evidence-path` | **必須**。候補 SHA の Git ツリーに収録された `docs/ops/nfr021-acceptance/` **直下**のパス | 不合格 |
| `--gate-kind` | `phase4` / `release` のみ | 入力エラー |
| `--release-version` | `release` で**必須**・`phase4` では**渡された時点で入力エラー** | 入力エラー |
| ファイル名 ↔ frontmatter | 結果: `<gate_kind>` = `gate_kind` / 第 2 要素が `phase4` なら **`release_version` は不在**・`vX.Y.Z` なら一致 / `seq<NNN>` = `attempt_seq` の `zfill(3)` / `<short_sha>` = `tested_commit_sha[:12]`。予約: **単一キー `gate_key`** から組を導出(**予約は `gate_kind` と `release_version` をキーとして持たない**) | `README.md:52-65` |
| `attempt_id` の字句 | `<ゲートキー>-<attempt_seq の zfill(3)>-<YYYYMMDDTHHMMSSZ>`。**ファイル名側と時刻書式が違う**(ID 内は日付ハイフンなし)。ゲートキー部分は `phase4` / `release-vX.Y.Z` に固定し**別表記を許さない**。末尾時刻も実在時刻を検証 | `README.md:86-102` |
| レコード間の一致 | 同一 `attempt_id` の予約と結果で**ゲートキー・`attempt_seq`・(`release` なら `release_version`)がすべて一致**。1 つでも食い違えば fail-closed | `README.md:104-108` |
| 二重記録の一致 | 本文「commit SHA」= `tested_commit_sha` / 本文「onboarding blob SHA」= `onboarding_blob_sha`。**本文「onboarding 版」は機械照合しない** | `README.md:68-84` |

## 4. 合格条件 ①〜⑩ の実装と負例テストの対応

**すべて「`evidence_path` で名指しされた 1 ファイル」に対する判定**。判定不能はすべて fail-closed。

| # | 合格条件 | 実装の要点 | 負例テスト |
| --- | --- | --- | --- |
| ① | `gate_kind` が要求ゲート種別と一致 | 判別共用体入力。`phase4` に要求版を渡したら**入力エラー**で fail-closed | `phase4` 実行に `--release-version` を渡す |
| ② | `result: passed` | — | `failed` の証跡を名指し |
| ③ | `tested_commit_sha` が候補 SHA の**祖先** | `git merge-base --is-ancestor`。**終了コード 0 / 1 / それ以外(128 等)を区別**し、0 以外 1 以外は「解決不能 = 判定不能」 | 祖先でない T / 存在しない OID |
| ④ | `onboarding_blob_sha` が T 時点の `docs/development/onboarding.md` の blob と一致し、**その blob の frontmatter が `status: approved`** | `git rev-parse <T>:<path>` + `git show`。**現 develop は `status: draft`** なので実データで負例が作れる | blob 不一致 / `draft` の blob |
| ⑤ | `release` なら `release_version` が要求版と一致(`phase4` では**記載自体を不合格**) | — | `phase4` 証跡に `release_version` を書く |
| ⑥ | 失効判定に掛からない(5 節) | — | T→C 間に失効対象パスの変更を入れる |
| ⑦ | **`attempt_id` で畳み込んだ試行集合**の中で `attempt_seq` が最大かつ**最大値が一意** | **畳み込みを先に行う**。予約と結果は同じ `attempt_seq` を持つため、**畳み込む前に数えると最大値が必ず 2 回現れ恒久 fail-closed になる** | 後発の試行がある状態で古い証跡を名指し / 同じ `attempt_seq` の別 `attempt_id` が 2 件 |
| ⑧ | 同一ゲートキーの**予約がすべて結果証跡で閉じている** | 未閉塞が 1 件でもあれば fail-closed | 未閉塞の予約を残す |
| ⑨ | 名指しされた結果証跡に対応する予約が**ちょうど 1 件**存在し、**予約を持たない結果証跡が 1 件も無い** | — | 孤児の結果証跡 / 予約 2 件 |
| ⑩ | **証跡本文の完全性** — 要件書 NFR-021 の**証跡 11 項目がすべて欄として存在**し、**ゲート別の合格項目が「項目名まで」テンプレートと一致**し、**空欄と `<...>` 形のプレースホルダが 1 件も残っていない** | 欄名の正は要件書 `:923`、欄の形と**合格項目の名前の正はテンプレート**。**行数だけを見る実装は不十分**(**通常レビューの指摘** — 汎用ラベル 5 行でも通ってしまい、要件書 `:921` が名指しする「ハーネスの pytest / backend の pytest / frontend の Vitest / 開発 DB へ接続 / 起動して疎通確認」が記録された保証にならない)。**期待項目名はコードへ焼き込まず、候補 SHA のツリーにあるテンプレートから導出する**(リテラル腐りの回避 — テンプレート改訂時に検査が自動追随する)。**名指しされた 1 件のみ**が対象 | 欄の削除 / プレースホルダ残存 / 合格項目の行不足 / **項目名がテンプレートと違う** |

**下位番号の重複・欠番それ自体は不合格理由にしない**(append-only と組み合わさると恒久閉塞するため)。回復規則は 10.1(未閉塞予約を `failed` 閉塞記録で閉じてから、既存全予約より厳密に大きい番号で新規予約)。

**⑦⑧⑨ の列挙範囲**: 候補 SHA の Git ツリーに収録された `docs/ops/nfr021-acceptance/` 配下の**同一ゲートキー**のレコード。作業ツリーの未コミットファイルは対象にしない。

### 4-A. ⑩ をテンプレートから導出することの残余リスク(通常レビュー起点)

**期待する合格項目名を候補 SHA のツリーのテンプレートから導出する**ため、**テンプレートを弱めれば ⑩ の検査も弱まる**
(項目を削れば、その項目が記録されていなくても通る)。これを本タスクでは塞がない。理由:

- テンプレート 4 件は **approved v1.0 の正本**であり、改訂は設計書 7.6-3 のゲート(構造的変更なら 7.3 の確定ゲート)を通る。
  検査の弱体化は**文書改訂として可視化される**
- `docs/ops/nfr021-acceptance/**` は失効判定の **allowlist** にあるため、テンプレート改訂は既存証跡を失効させない。
  これは正本が意図した設計(10.1 `:644`)であり、ここで覆すと規範追加になる
- 代替案の **blob OID をコードへ固定**は、テンプレート改訂ごとに検証器の書き換えが必要になり**リテラル腐り**を生む
  (それを避けるために導出方式を採ったので、自己矛盾する)

**したがって「テンプレートを弱める改訂」は人間のレビューで止める前提とし、機構では止めない。**
これは 6-1 節で `push` 経路の事後検査を撤回したのと同じ型の判断(正本が受容している残余リスクを機構で塞ごうとしない)。

## 5. 失効判定

### 5-1. 変更パス集合の導出(実測済み — [research.md](research.md) 4 節)

```
git log --format= --name-only -m --no-renames <T>..<C>
```

- **`-m`(= `--diff-merges=separate`)必須** — 既定はマージコミットの差分を出さない。実測で **109 → 121 パス**、差の 12 件に `AGENTS.md`・`CLAUDE.md`・`.claude/agents/*` が含まれた。`--diff-merges=combined` / `dense-combined` / `remerge` は 109 のままで**取りこぼす**(`-c` / `--cc` と同じ理由 — 全親から変更されたパスだけを出す)
- **`--no-renames` 必須** — `diff.renames` の git 既定は true で、実測(`d21620b`)では `--name-only` から**旧パスが消えた**。旧パスが失効対象・新パスが allowlist の移動で失効判定が空振りする
- **2 点差分(`git diff T C`)を使わない** — 範囲内で作られて消えたパスが現れない(実測 0 件 vs `log` で 1 件)
- **`T...C`(merge-base 比較)を使わない**

**先に祖先条件**: `git merge-base --is-ancestor <T> <C>` が真でなければ**判定不能 = 失効**(fail-closed)。

### 5-2. パターン照合(`syntax: "gitignore-root-relative-v1"`)

- **`syntax` が未知値なら fail-closed**。`default: "invalidating"` = 既定は失効
- **`fnmatch` を使わない** — `*` が `/` を跨ぎ `**` の特別扱いも無い。ルート相対の `/` 区切りセグメント単位で自前照合する(`/backend/**` はディレクトリ配下すべて、`/docs/development/onboarding.md` は単一ファイル)
- `invalidating` と `allowlist` の**両方に一致したら `invalidating` を採る**(fail-closed)
- **`allowlist` を検証器側で増やさない**(10.1 の allowlist は閉じた列挙)
- **どちらにも一致しないパスは失効扱い**(`default`)

## 6. 統合時の受入検査(append-only) (a)〜(d)

**対象は「その PR で新規に追加された予約・結果証跡」だけ。過去の証跡を再検査してはならない**(`README.md:142-144`)。

| 項目 | 対象レコード種別 | 内容 |
| --- | --- | --- |
| (a) 完全性 | **結果証跡のみ** | ⑩ と同じ検査(証跡項目・ゲート別合格項目の存在、空欄・プレースホルダの不在)を**新規追加分に**適用 |
| (b) 命名文法への適合 | 予約 + 結果証跡 | 2 節の正規形・字句規則・**直下ファイル限定** |
| (c) スキーマ適合 | 予約 + 結果証跡 | 3 節(必須キーと型・ファイル名↔frontmatter・レコード間の一致契約) |
| (d) 孤児・多重対応の拒否 | 予約 + 結果証跡 | **結果証跡側**: 対応する予約が統合後のツリーに**ちょうど 1 件** / 同一 `attempt_id` の結果証跡が**2 件目にならない**。**予約側**: 統合後のツリーで `attempt_id` と (ゲートキー, `attempt_seq`) の組が**それぞれ一意**であり、同じ値を持つ予約が**2 件目にならない** |

**既存証跡の変更・削除の拒否**も併せて行う(10.1「保持」の本体 — 追加以外の状態変化を拒否する)。**`--name-status` の状態が `A` 以外のものはすべて拒否する**(レビュー 2 周目 P1)— `D`・`M`・`R` だけを列挙すると、通常ファイルから symlink 等への変更が返す **`T`(type change)** が通ってしまう。`T`・`C`・`U`・`X` を含め**非 `A` はすべて fail-closed**。

### 6-A. 採番・排他プロトコルの機械化(レビュー 2 周目 P0)

(a)〜(d) だけでは、10.1「試行の排他と採番」が定める規範が**機械的に強制されない**。次の 2 つが素通りする:

1. **予約と結果証跡を同一 PR で新規追加する** — (d) は「対応する予約が**統合後のツリー**に 1 件」を要求するだけなので、同一 PR に両方を入れれば成立してしまう。しかし 10.1 は「**① 予約を通常の PR で `develop` へ統合する(ここで番号が確定する)→ ② 受入を実施 → ③ 結果証跡で閉じる**」という順序を規範として定めている
2. **未閉塞の予約があるのに次の予約を追加する** — 一意性しか見ないため、`seq001` が未閉塞の現状でも `seq002` の予約が通る。10.1 は「**未閉塞の予約がある間は次の試行を開始しない**」と定めている

したがって次の 4 検査を足す:

**すべて base のツリーを基準に評価する**(レビュー 3 周目 P0 — 当初案は (e-2)(e-3) を「統合後のツリー」で評価していたが、それでは 10.1 の順序規範と等価にならない。同一 PR に「`failed` 閉塞 + 新規予約」を入れると通ってしまい、正本が求める「**閉塞記録を `develop` へ統合してから**新予約を取る」順序を機械化できていなかった)。

| 検査 | 対象 | 内容 |
| --- | --- | --- |
| (e-1) **予約の先行統合** | 新規の**結果証跡** | 対応する予約が **base のツリーに既に存在**していること(同一 PR 内で追加された予約では満たさない — 10.1「① 予約を統合する → ② 受入を実施 → ③ 結果証跡で閉じる」の機械化) |
| (e-2) **未閉塞予約の不在** | 新規の**予約** | 同一ゲートキーについて、**base のツリーに未閉塞の予約が 1 件も無い**こと(「未閉塞の予約がある間は次の試行を開始しない」の機械化) |
| (e-3) **逆順の禁止** | 新規の**予約** | 同一 `attempt_id` の**結果証跡が base に既存でない**こと(既存の孤児結果へ後から予約を足して対応関係を成立させる経路を塞ぐ — レビュー 3 周目 P0) |
| (e-4) **採番の起点と単調増加** | 新規の**予約** | base に同一ゲートキーの予約が **0 件なら `attempt_seq` は 1**(`seq001`)、**1 件以上なら base の全予約より厳密に大きい**こと(10.1「ゲートキー単位で 1 から始まる単調増加」+ 回復規則「既存のすべての予約より厳密に大きい」の機械化)。**既存レコード間の欠番・重複は依然として不合格理由にしない**(恒久閉塞の回避) |
| (e-5) **同一 PR 内の新規予約の一意性** | 新規の**予約** | 同一ゲートキーの新規予約が、**その PR の中で 2 件以上にならない**こと(**通常レビューの指摘で追加** — (e-1)〜(e-4) はいずれも新規レコードを *base* と 1 件ずつ突き合わせるため、base が閉塞済みなら `seq002` と `seq003` を**同一 PR に同時に入れると両方が通り**、マージ後に未閉塞の予約が 2 件並ぶ。10.1「**ゲートキー単位で同時に進行できる受入試行は 1 件だけ**」に反する。実測で素通りを確認済み)|

**(e-2) と (e-5) の合成が規範の全体**である: base の未閉塞予約が 0 件(e-2)**かつ**その PR が同一ゲートキーへ足す予約が 1 件以下(e-5)→ マージ後の未閉塞予約は 1 件以下。どちらか一方だけでは「同時に 1 件だけ」を機械化できない。

(d) の一意性検査は**統合後のツリー**で行ったまま残す(**競合検知**として機能する — base が古い 2 つの PR が同じ番号を別々に通した場合、後から入る側で落ちる)。

**10.1「試行の排他と採番」の 5 経路すべてを通せることを確認した**:

| 経路 | (e-1) | (e-2) | (e-3) | (e-4) |
| --- | --- | --- | --- | --- |
| 初回の予約(`seq001`・既に統合済み) | — | base に予約 0 件 ✓ | base に結果 0 件 ✓ | 0 件なので `1` ✓ |
| 4-6 の受入 PR(結果証跡 `seq001`) | base に予約 `seq001` 既存 ✓ | — | — | — |
| 失敗閉塞の監査 PR(結果証跡のみ) | 同上 ✓ | — | — | — |
| 閉塞後の再試行の予約(`seq002`) | — | `seq001` は閉塞済 ✓ | `seq002` の結果は無い ✓ | `2 > 1` ✓ |
| 複数予約の回復(すべて閉塞 → 新規予約) | — | 全件閉塞済 ✓ | ✓ | 最大 + 1 以上 ✓ |

**この 4 検査は既存規範(10.1「試行の排他と採番」)の機械化であり、新しい規範を作らない**。README `:146-155` の 4 項目の列挙を超えるため、**この判断は人間の確認を仰ぐ**(判断が否なら (a)〜(d) のみに戻す)。

### 6-B. 並行 PR の残余リスク(敵対レビュー起点 — 機構では塞がない)

**同じ base から作った 2 つの PR が、それぞれ同一ゲートキーの `seq002` 予約を足すと、どちらも個別には exit 0 になる。**
(e-5) は「その PR の中で 2 件以上か」を見るため各 PR 内では満たされ、(e-2) は各 PR の `base.sha`(= PR 作成・更新時点の
develop)を見るため未閉塞予約 0 件で通る。先行 PR をマージしても後続 PR の head SHA は変わらないので、**古い green のまま
マージすると同一ゲートキーに未閉塞の予約が 2 件並ぶ**。

**これを機構で塞がない。** 理由:

- **正本が既に解決策を定めている** — `github-setup.md` 3 章の Ruleset は `strict_required_status_checks_policy: true` を
  含んでおり、これが **base 最新化を必須にする**。現在それが未適用なのはブランチ保護のプラン制約による縮退であり、
  設計書 10.2 / `github-setup.md` 1 章が受容している残余リスクの範囲
- CI は PR イベントの `base.sha` しか持たない。「現在の develop」を別途取りに行くと、**検査対象が PR の差分でなくなり**
  (e-1)〜(e-5) の基準がぶれる。またマージ順序に依存して同じ PR の判定が揺れる
- **(d) の一意性検査が統合後ツリーで競合検知として働く**ことは設計どおりだが、それは base が最新化された再実行でのみ効く

**当面は `github-setup.md` 2 章の手続 5(予約 PR を直列に扱う)で担保する。**
これは 6-1 節で `push` 経路の事後検査を撤回したのと同じ型の判断(正本が受容している残余リスクを機構で塞ごうとしない)。

### 6-0. (a) を予約へ適用しない理由(レビュー 1 周目 P1)

README `:146-155` は 4 項目を列挙するだけで**レコード種別ごとの適用範囲を書いていない**。しかし (a) の検査内容は「**証跡項目**・**ゲート別合格項目**の存在」であり、**予約レコードにはそのどちらの欄も存在しない**(`reservation-template.md:13-26` は `gate_key` / `attempt_seq` / `attempt_id` / `started_at` / `operator` の 5 キーと注記 2 行のみで、証跡 11 欄も合格項目表も持たない)。

**(a) を予約へ適用すると、規範どおりに書かれた予約 PR が必ず落ち、以後どのゲートも新しい試行を開始できなくなる**(予約が入らない → 受入が開始できない)。したがって **(a) は結果証跡のみ**に適用する。

これは README の**解釈**であり規範の変更ではない(README は適用範囲を定めていないため、狭める側の解釈で恒久閉塞を避ける)。**解釈が正しいことを「規範どおりの新規予約だけを含む PR が exit 0 になる」正例テストで裏取りする**。

### 6-1. 差分の取り方

`scripts/core_guard.py:132-162` / `:179-195` の前例に倣う:

- CI では `GITHUB_EVENT_PATH` の `pull_request.base.sha` / `head.sha` を読む
- **検査対象は `develop` を base とする `pull_request` イベントのみ**(レビュー 3 周目 P0)。それ以外(**`main` を base とする PR** / `push` / `workflow_dispatch`)は `scripts/core_guard.py:256-258` の様式で **stdout** へ理由を出して **exit 0** とする
  - **`main` 宛 PR を検査すると `develop → main` の正当なマージが必ず落ちる** — `main` は証跡をまだ持たないため、`base...head` の三点差分に**既に develop で検査済みの全証跡が新規追加として現れ**、(e-1) が「base に予約が無い」として拒否する
  - **`push` の事後検査は 4-5 のスコープから外す**(レビュー 2 周目 P0 の再判断)。**根拠**: 直接 push・UI/API マージによる `develop` の更新は、10.1 が**残余リスクとして明示的に受容**している(`dev-harness-design-2026-08-07.md:640` — 「ブランチ保護が未導入…なので**人間管理の排他区間**を置く」「**これは機構による強制ではなく運用規律であり、所有者・他メンバーの UI / API 操作を防げない残余リスクが残る**」「ブランチ保護が利用可能になった時点で、この排他区間を保護設定へ置き換える」)。同じ行が「**マージ後の第 1 親・第 2 親・ツリー検査は事後検出であり…手遅れになりうる**」とも評価しており、**正本は事後検出を対策として位置づけていない**。したがって push 経路を赤くする機構は ① 正本が要求していない ② 統合を止められないため「赤の後に誰が何を止めるか」という統制の定義が別途必要になる(= 規範追加)③ `main` 経路で正当なマージを落とす副作用がある
  - **ブランチ保護が適用可能になった時点で push 経路の検査を再検討する**ことを台帳へ follow-up として記録する
- **PR イベントなのに `base`/`head` が読めない場合は fail-closed**(スキップと故障を区別する)
- 差分は **`git diff --name-status --no-renames <base>...<head>`(三点)**。新規追加は `A`、**それ以外の状態(`M`・`D`・`R`・`T`・`C`・`U`・`X`)は既存証跡への変更としてすべて拒否**する(レビュー 2 周目 P1・3 周目 P1 — 6 節本文と同一。`T` は通常ファイル → symlink 等の type change)
- **三点(merge-base)を使う理由と、失効判定で三点を禁じた理由は別**である。ここでの問いは「**この PR が加えた変更は何か**」であり merge-base 起点が正しい。失効判定の問いは「**T 以後に何が変わったか**」で、こちらは範囲内の作成→削除を落とさないために各コミットの和集合が必要。**この区別を実装コメントに明記する**(レビューで混同されやすい)
- `--base` / `--head` の CLI 上書きは**ローカル実行とテスト専用**。**`origin/develop` / `HEAD` への暗黙フォールバックは行わない**(レビュー 2 周目 P0 — `GITHUB_EVENT_PATH` があるのに読めない状態を上書き値で救済すると fail-closed 要求と矛盾する)

## 7. 検証器自身の自己同一性確認

10.1 は「置換後は**候補 SHA に収録された検証器・設定だけを隔離した checkout から実行**する(少なくとも**候補 SHA 内の blob と実行する検証器が一致しなければ中断**)」と定める(`dev-harness-design-2026-08-07.md:647`)。4-5 のスコープは**この確認の実装まで**(`:802`)。

- 実行中のファイル(`__file__`)の内容から blob OID を算出(`git hash-object` 相当 — `blob <len>\0` + 内容の SHA-1)し、**候補 SHA のツリーに収録された `scripts/verify_nfr021_evidence.py` の blob OID と一致**しなければ中断
- **同じ確認を `.claude/nfr021-invalidating-paths.json` にも行う**(「検証器・**設定**だけを隔離した」— 設定が候補 SHA 外なら失効判定の基準が候補と乖離する)
- **`/release` 手順 0 の置き換えは行わない**(`P4-後` の責務)。自己同一性確認は**検証器の内部機能として実装・テストするだけ**
