# 調査メモ: ADR-003 — 状況計算の実現方式と付録A 契約化

## 問い

(1) 要件が ADR に委任した範囲と、ADR が変えられない制約はどこまでか (2) **達成条件 (b)②「宣言外の実装が混入していないことを CI が機械的に判定できること」は実現可能か**(実現不能なら要件書を `in-review` へ戻す経路がある) (3) A 案の実現手段のうち 1 名体制で維持できるものはどれか (4) 付録A 固定ベクタ・付録E 全表・FR-022 列定義をどう作るか (5) ADR が触ると別の確定ゲートを誘発する範囲はどこか。

## 結論(要約)

1. **(b)② の成立は「実装」の語の解釈にかかっている**。**アーキテクチャ完全性検査**(宣言済みの正本・生成物・入口・禁止された動的機構に対する検査)としてなら**実現可能**。**「同じ計算を別の書き方で再実装した任意のコード断片」の検出**としては**実現不能**(プログラム同値性は決定不能)。**ADR-003 はこの限定を明記して成立させるか、実現不能と結論して要件を差し戻すかの二択**であり、**これが最大の人間裁定事項**。
2. **実現手段は「制約 DSL / 宣言モデルを正本にして Python・TS を生成する」が最も適合**(Codex 評価)。Pyodide は技術的に成立するが**未圧縮で WASM 約 9MB + 標準ライブラリ約 2.4MB + JS 約 1MB** の固定費がテーブル駆動の状態遷移に対して過大。Rust+WASM は成熟しているが 1 名で PyO3/maturin と wasm-bindgen の両輪を維持するコストが高い。
3. **旧システムに「複数実装が同じ値を返すことを固定する機構」は存在しない**。実在したのは ① 構造の実装横断固定(SQLite DDL と PG DDL の突合)② 定義の固定(語彙・分母)③ 単一実装内のリプレイ恒等式 の 3 種。**ADR が作ろうとしている一致性の担保は旧に前例がない**。
4. **ADR が触ると 2 ゲート化する境界が特定できた** — **共有実装コード / 生成物を `contracts/` に置くと決める**と設計書 4 章の限定文と正面衝突し、**設計書の版繰り上げ + 7.3 確定ゲート**が ADR 自身の確定ゲートに加わる。
5. **要件側に条文上のギャップが 2 件ある** — **NFR-018(b) の機械検査が 8 章 DoD② のリリース判定の列挙に入っていない** / **(β) の担保を CI 必須とする明文が無い**(pytest として書けば結果的に入る)。

### 2. (b)② の検査方式は実在するか(本 ADR の核心)

**Codex の Web 調査の結論**(URL は下記。**★ = 本メモの作成者が原典で確認済み**):

> **モジュール・生成物・実行入口を構造的に閉じ、「宣言外の経路」を fail-closed で拒否する検査は実在し、pitchlog でも構築可能**。ただし**任意の Python/TypeScript コードのどこかに、同じ計算を別の書き方で再実装していないことを意味解析で完全証明する一般手法は存在しない**(プログラム同値性は決定不能)。

**TypeScript / JavaScript 側で使える材料**:

| 手段 | 何が取れるか | 典拠 |
| --- | --- | --- |
| Rollup プラグイン API | 全モジュール ID(`getModuleIds()`)・`isIncluded`・static/dynamic import・exports。`generateBundle` で最終チャンクごとの `moduleIds`・`renderedExports`・`dynamicImports` | https://rollupjs.org/plugin-development/ (公表日記載なし・2026-08-18 閲覧) |
| Vite production manifest | エントリ・静的 import・dynamic import・生成ファイルを JSON 出力 | https://vite.dev/guide/backend-integration.html (同上) |
| esbuild metafile | 入力・出力・import 種別等の機械可読 JSON | https://esbuild.github.io/api/ (同上。**metafile のフィールド一覧は当該ページで確認できず — 未確認**) |
| dependency-cruiser | custom forbidden rule / dynamic dependency / **unknown・undetermined dependency を error にできる** | https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md (同上) |

**閉域が壊れる条件(原典で確認済み)**:

- **★ esbuild は非解析 import をバンドルせず、そのまま残す** — 「**Other forms of import paths are not bundled, and are instead preserved verbatim in the generated output**」(https://esbuild.github.io/api/ ・2026-08-18 閲覧。本メモ作成者が原典で確認)
- **★ ESLint `no-eval` は間接 eval を検出できない** — 「**This rule cannot catch renaming the global object.**」として `const foo = window; foo.eval("const a = 0");` を明記(https://eslint.org/docs/latest/rules/no-eval ・2026-08-18 閲覧。同上)

→ **単一のツールでは fail-closed にならない**。「動的コード生成・非リテラル import・外部スクリプトを**禁止して検出する**」検査を重ねて初めて閉域になる(Codex 評価)。

**Python 側**: import グラフ解析(grimp / import-linter の forbidden contract)で同型の検査が組めるが、`importlib`・`getattr`・エントリポイント経由のプラグイン読み込みは同様に閉域を破る(Codex 報告。**個別 URL の原典確認は未実施**)。

**pitchlog への含意(裁定が要る)**:

- **(b)② を「アーキテクチャ完全性検査」と定義すれば実現可能** — 宣言済みの正本・生成物・ファサード・入口の集合を閉じ、**宣言外のモジュール・入口・動的機構を fail-closed で拒否**する。要件の 3 不変条件(全域・fail-closed・範囲縮小の禁止)とも両立する
- **ただしこの解釈には穴が残る** — **宣言済みモジュールの内側に、同じ計算を手書きで再実装したコードが置かれた場合は検出できない**。これは旧システムが実際に陥った形(「定義は共有だがロジックは別コード」)そのもの。要件 :867 が (b)② を課した動機がまさにこれである以上、**この穴を許容するかどうかは人間裁定**
- 穴を狭める補助手段(ADR で設計しうるもの): ドメイン計算を**生成物からのみ到達可能**にする / 手書き実装を置けるディレクトリを限定し他所からの計算関数の import を禁止する / 生成物の hash 固定 + 乖離検出((b)①)と組み合わせる

### 3. 実現手段の運用コスト(2026-08-18 時点の再評価)

Codex の順位付け(**1 名運用の維持コスト**と**タブレット負担**で評価):

| 順位 | 方式 | 1 名運用 | タブレット負担 | 評価 |
| --- | --- | --- | --- | --- |
| 1 | **制約 DSL / 宣言モデル → Python・TS 生成** | 低〜中 | 小 | **最も適合** |
| 2 | TS 正本 → 同一 JS artifact を Browser と QuickJS/常駐 Node で実行 | 中 | 最小 | DSL で表せないロジックが増えた場合 |
| 3 | Python 正本 → Pyodide | 中 | **大** | 実機 spike 合格時のみ |
| 4 | Rust 正本 → PyO3 + WASM | **高** | 小 | 将来の性能要求が強い場合 |
| 非推奨 | 一般 Python ↔ TS トランスパイル | 高・不確実 | 不定 | **成熟した意味保存手段なし** |

根拠(いずれも Codex 報告の URL。**原典確認は未実施**):

- **Pyodide の固定費**: 現行 npm 配布物は**未圧縮で WASM 約 9MB + 標準ライブラリ約 2.4MB + JS 約 1MB**。「数 KB〜数十 KB になり得る pitchlog の計算に約十数 MB の実行環境を足す」
- **Rust の主コスト**は性能ではなく「第三言語・FFI 型変換・wheel matrix・WASM glue・エラー表現・リリース同期」。本番事例でも PyO3 用と wasm-bindgen 用の**変換・ラッパー差分**が報告されている(https://tweedegolf.nl/en/blog/136/rust-interop-in-practice-speaking-python-and-javascript/ ・2024-09-30 / https://blog.mathieu-leplatre.info/leveraging-rust-in-python-and-javascript.html ・2020-09-08)
- **単一宣言 → 複数言語生成の成熟例**は Kaitai Struct(YAML の形式記述から JS・Python 等の parser を生成。対象はバイナリ形式)。https://doc.kaitai.io/user_guide.html
- **状態機械 DSL のデファクト標準は 2026 年時点で確認できず** — W3C SCXML(https://www.w3.org/TR/scxml/ ・2015-09-01)は任意の script/データモデル式を許し、Python/TS 両方への標準コード生成を規定しない。Frame 等は多言語出力を掲げるが型・初期化式の一部を対象言語へ素通しする
- **QuickJS** は 2026-06-04 版で ES2025 対応・単純な executable 367KiB。Python wrapper `quickjs-ng` 0.16.0.1 は 2026-08-01 公開で CPython 3.10+ の abi3 wheel を提供(https://bellard.org/quickjs/ ・https://pypi.org/project/quickjs-ng/)

**重要な設計上の注意(Codex 評価)**: 「**状態テーブルを両言語の手書き interpreter で読むだけだと、interpreter が二実装と見なされる余地がある**。生成器から両方の実行コードを派生させる方が NFR-018 に対して説明しやすい」。

**前タスクの評価との関係**: [nfr018-domain-calc-adr/research.md](../nfr018-domain-calc-adr/research.md) §3 は「この計算規模では Pyodide / Node サイドカー / Rust+WASM は運用コストが勝つ」と結論していた。**今回の再評価はこれと矛盾しない** — 上位に来たのは当時の比較で主役だった 3 方式ではなく、**制約 DSL からの生成**である。

### 4. 正解ベクタ・契約テストの実務(付録A / 付録E の設計材料)

**言語横断ベクタの成熟例**(Codex 報告・URL は原典未確認):

- **JSON Schema Test Suite** — 仕様バージョンごとのディレクトリ、ケースごとの JSON、schema/input/expected validity。**runner は各言語側が実装**。optional/proposal を分離(https://github.com/json-schema-org/JSON-Schema-Test-Suite ・最終更新 2026-05-26)
- **Unicode 正規化** — `NormalizationTest.txt` を normative conformance data とし、入力と NFC/NFD/NFKC/NFKD の期待値を提供(UAX #15 Revision 57 ・2025-07-30)
- **NIST ACVTS** — Known Answer / Monte Carlo / multi-block / デバッグ用中間値と**粒度を使い分ける**(https://csrc.nist.gov/Projects/Cryptographic-Algorithm-Validation-Program ・最終更新 2026-04-13)

**Codex が推奨するベクタの三層**: ① 要件から人手で確定する代表例・境界例 ② 有限状態なら**状態 × イベント × 主要フラグの exhaustive vector** ③ seed 固定の property/fuzz + 失敗を縮小した回帰ケース。

**CI 側で検査すべきこと**(同): **適用対象の runner** が**同じファイルを全件消費したこと**まで検査し(ADR-003 D-6 で (α)=両 runner /(β)=pytest のみ と確定)、未対応 case・未知 field・重複 ID・schema 不一致を fail にする。**正本実装だけから期待値を自動生成すると oracle が循環する**ため、重要ベクタは要件・状態表から独立生成または人間確認する。

**数値差の吸収**(同): ECMAScript `number` は IEEE754 binary64・安全整数は ±(2^53−1)。Python `int` は任意精度。→ カウント・得点・アウトは狭い整数範囲に固定、座標は**固定小数点整数**(`x_milli` 等で単位と scale をフィールド名か schema に持たせる)、**NaN/Infinity/-0/暗黙丸めを禁止**、2^53−1 を超える値は decimal string。除算は「切り捨て / 0 方向 / 四捨五入 / ties-to-even」のどれかを明記。**JCS(RFC 8785)は生成物 hash や署名が要る場合のみ**。

### 7. ADR の様式(機械検査が要求するもの)
