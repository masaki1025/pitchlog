- **前提の 2 件は解消済み**(起票時のブロッカ):
  - **要件書 v2.1**(2026-08-18 approved・PR #18)で **NFR-018 の達成条件が確定**した — ADR が何を満たせばよいかが定まった
  - **ADR 様式の正規化**(TSK-227)で、テンプレート由来の ADR が `check_docs_status.py` を通ることが固定済み
- **要件側が ADR に委任した項目**(要件書 NFR-018 の申し送り + 10 章 未決事項表):
  1. **実現手段の選択**(共有ランタイム / WebAssembly / コード生成 等)
  2. **達成条件 (b)② の検査方式**(探索対象の閉域の具体化・実行入口の定義・生成物の識別・動的ロード等の禁止規則・到達性検査の方式)
  3. **正解ベクタと比較面の整備**(付録A 固定ベクタ〔台帳 H-55〕・付録E 全表・FR-022 の当日打席結果の列定義)
- **要件側が既に課している制約**(ADR で緩められない):
  - (α) = クライアント・サーバーの双方が**同一のコードに由来する実行体** / (β) = **サーバー内で人手保守 1 系統**
  - (b)② の不変条件 — **検査対象は本番に到達可能なソース・生成物・実行入口の全域** / **未分類・判定不能は fail-closed** / **ADR は方式を選べるが対象範囲を縮小して②を満たしたことにはできない**
  - **①または②が実現不能と結論した場合は、実装を開始せず要件書を `in-review` へ戻して再改訂する**(緩い側へ倒して着手しない)
  - **発火点** = 「要件書 v2.1 の承認後、対象コードを新規に追加または変更する最初の変更の前」。**既存の対象コード**(`frontend/src/lib/courseInputView.ts` の座標変換)は **ADR 確定まで現状維持のみ許容**
- **本 ADR の決定がコア領域の広狭を握る** — 設計書 6.3 が「付録A 契約の実装完了後に後段集計の除外を発効する。**発効判断は本 ADR**」と定めている
- **本タスクの着手前調査**: [research.md](research.md)(ADR の裁量境界・(b)② の実在性・実現手段の再評価・正解ベクタの実務・旧システムの先例・条文上のギャップ)
- 実現方式の選択肢比較は [nfr018-domain-calc-adr/research.md](../nfr018-domain-calc-adr/research.md) §3・§4 が正(**複製しない**)。ただし同調査は「この計算規模では Pyodide / Node サイドカー / Rust+WASM は**運用コストが勝つ**」と評価しており、**要件が確定した A 案と正面から対立する**。確定ゲートの敵対レビューは「**A 案に適合する技術が実在しないという指摘はない**(実在するが運用コストの問題)」と判定した — **この対立の解き方が本 ADR の核心**
- 典拠: 要件書 NFR-018 / NFR-019(a) / 10 章、設計書 4 章 / 6.3 / 13 章、評価台帳 H-55 / H-12 / H-61
