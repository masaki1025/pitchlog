# 調査メモ: 同期プロトコル設計の起草(イベント順序・断中記録・記録権の境界)

## 問い

1. 要件書が同期プロトコルについて**決めていること**と**設計側の自由度**はどこで切れるか
2. データモデル候補案 12-7 節 (2) から本タスクへ何が申し送られたか。3 周目に「イベント連番へ一元化」して 4 周目に差し戻された理由は何か
3. 旧システム Baseball_Scoring は記録の保存・順序・断線時にどう振る舞っていたか(= 何が新規設計か)
4. 記録権(FR-013)と同期プロトコルの境界はどう定まっているか
5. 再提案してはいけない案は何か

調査サブエージェント 3 本(spec-checker / legacy-analyst / decision-tracer)を並列で投げ、矛盾は原典で裁定した。

## 結論(要約)

- **本タスクの中核要求は 1 行に集約できる**: 「**同期連番が「到着順」であることを明記し、論理順序を別に持つ前提を共有すること。REQ:236(任意位置挿入)と REQ:282(再送)の両立をそちらで設計する**」(データモデル候補案 12-7 節 (2))。**この引用に含まれる `REQ:236` / `REQ:282` は歴史的表記**(`kind=historical` — 要件書 **v2.2** 時点の行番号)であり、**現行 v2.3 では `:238`(任意位置挿入)/ `:284`(生成時のべき等キー・連番付与)、および `:286`(再送の重複排除と prefix)**に対応する。**逐語引用のため本文は書き換えない**
- 要件書は**適用規則を厳密に決めている**(べき等キー・世代内連番・prefix コミット・単一トランザクション・墓標/改訂・undo の常時送信・退避と再採番)。**自由度があるのは表現と実装機構**(順序ラベル方式・prefix 水位の持ち方・API 形状・キュー永続化技術・単一書き手の実現機構・再計算の粒度・配信方式)
- **旧システムには記録権・べき等キー・イベント列・論理削除・多段 undo・交代イベントのいずれも存在しない**。順序の担い手は 88 列の `プレイの番号`(列 9)ただ 1 つで **UNIQUE 制約なし**、undo は `MAX(id)` の**物理削除**、訂正は**上書き UPDATE で履歴を残さない**
- 記録権との境界は設計書 6.3 が「**重複帰属し得る**」と明記済み。同期側は「連番と採番の不可分性・prefix・墓標/改訂・原子性・再計算/補正・複数タブ競合」、記録権側は「世代更新とフェンシング・引き継ぎの原子性・競合拒否・退避経路」
- **進め方の教訓(H-78 / H-79)**: 述語を 1 節へ集約し適用先を表で明示し、**反映後に古い表現の残存を機械検査**する。集約だけでは伝播漏れは直らないことが前タスクで実測済み(集約後の検査で 6 箇所検出・うち 3 件が本当の残存)

## 詳細と典拠

### 1. 要件書が決めていること(設計で変更できない)

- **断中可能な操作は完全列挙**: 「毎球入力・undo・選手交代・タイブレーク開始・試合終了宣言・選手のその場登録(Must の 6 種)**＋状態補正(FR-040 — Should。採用した場合のみ第 7 の種別)**。**列挙は閉じており、未採用の Should を実装したことにする根拠にはならない**」(典拠: `docs/requirements/requirements-pitchlog-2026-07-22.md:166`)
- **べき等キーと連番**: 「全操作イベント / 生成 / **クライアント生成のべき等キー**と**記録権世代内で単調増加の連番**が付与される」(典拠: 同 `:284`)
- **prefix コミット**: 「べき等キーにより再送が重複到達しても二重適用されず、**連番に欠落があればそれ以降を適用しない**(順序と欠落は べき等キーでは防げないため連番で保証する)」(典拠: 同 `:286`)
- **サーバー適用の原子性**: 「**べき等キーの記録・イベント保存・prefix更新・状態遷移が単一のDBトランザクションで確定する**」(典拠: 同 `:287`)
- **クライアント側の不可分性と単一書き手**: 「**追記と連番の採番は不可分に永続化**され、**同一ブラウザの複数タブは単一の書き手のみが記録できる**(タブ複製による連番衝突の防止)」(典拠: 同 `:288`)
- **拒否時の再開は 2 択**: (a) **同一連番の改訂版**(新しいべき等キー・サーバーは旧版を置換) (b) **墓標イベント**(当該連番を正式に消費する空イベント)。「**prefixは確定イベントまたは墓標を越えて前進する**(破棄で後続が永久停止しない)」。**記録権拒否は内容の編集では解決できないため別カテゴリ**として退避へ誘導(典拠: 同 `:290`)
- **サーバー再計算が正**: 「サーバーがイベント列を入力順に再計算・検証 / サーバー結果が確定記録となり、クライアント表示と差異があれば補正+操作者に通知される(**黙って直さない**)」(典拠: 同 `:289`)。「**正本はDBの1系統のみ**」(典拠: 同 `:149`)
- **undo の扱い**: 「**常に取り消しイベントがキューに積まれ**、サーバー側でべき等に適用される(対象の操作が未着なら相殺)」(典拠: 同 `:226`)/ 空履歴では「**状態を変えず、取り消す対象が無いことを利用者へ示す**」(典拠: 同 `:227`)/ 「**クライアントの「未送信/同期済み」判定に依存する分岐を置かない**(ACK消失時の誤判定で取り消したプレイが復活する事故の防止)」(典拠: 同 `:228`)/ 「**undo 自身は取消可能な操作としない**」(典拠: 同 `:229`)
- **キューの規律**: 警告閾値 350 イベントでも「**記録は継続でき**」ブロックしない(典拠: 同 `:291`)/ 同期済みイベントは端末に **24 時間保持**(DB 障害時の再送出所)(典拠: 同 `:292`)/ トークン失効・再ログインでキューは失われない(典拠: 同 `:293`)/ 永続ストレージ拒否時は警告(典拠: 同 `:294`)
- **終了判定と終了宣言の分離**: 「試合状態を自動で「終了」に遷移させない(**断中に自動終了するとキュー内の宣言イベントが拒否されて詰むため**)」(典拠: 同 `:216`)
- **連番の世代スコープ**: 「**連番(FR-012)は記録権世代ごとに採番され、試合の正史は「世代の連結」として定義される**」(典拠: 同 `:301`)。外部契約にも露出: サイドカーの結合キーは **(試合ID + 記録権世代 + イベント連番)**(典拠: 同 `:1186`)
- **退避と再採番**: 旧世代のイベントは「適用されないが**破棄されず退避され**」(典拠: 同 `:305`)、閲覧・書き出しは **Must**(典拠: 同 `:306`)、取り込みは「**操作者が挿入位置を指定**…現行世代の連番として採番し直し、下流再計算を伴う。**旧世代の連番のまま挿入しない。末尾への機械的な追加はしない**」(典拠: 同 `:307`)
- **性能規律**: 確定 → 次の入力可能 p95 1 秒(サーバー往復を待たない)(典拠: 同 `:777`)/ サーバー同期 p95 5 秒(典拠: 同 `:782`)/ 閲覧端末へ 10 秒以内反映 + 最終反映時刻の表示(典拠: 同 `:803`)/ 集計は DB 側絞り込み(典拠: 同 `:797`)
- **無停止保証**: 「試合開始後の通信断(**時間無制限・試合終了まで**)において、記録が 1 球も失われない」(典拠: 同 `:808`)
- **復元後のフェンス**: 「復元後は**全試合の記録権世代を無効化(フェンス)して新世代を発行**し、端末の同期済み 24 時間保持分の回収・突合を復旧手順に含める」(典拠: 同 `:821`)
- **テスト要求**: NFR-019(d) = 「**同期プロトコルの故障系テスト**(墓標/改訂の適用・サーバー適用の原子性〔クラッシュ注入〕・複数タブの単一書き手競合)」/ (c) = 「通信断→復帰同期・**記録権の通常/緊急引き継ぎと退避経路**」(典拠: 同 `:909`)
- **復帰同期は事前集計の無効化トリガに含まれる**(典拠: 同 `:957`)
- **ADR-003 の拘束**(approved): 契約単位は「1 遷移」(input = 事前状態 + 履歴文脈 + 次イベント 1 件)/ **履歴文脈は取消可能な操作のスタック(各要素が種別 + 差分)**・深さ上限 `D` は検査の保証範囲で実行時上限ではない / **補正・undo はイベント種別で表現し別の対象計算にしない** / 状況判定の出力に「操作結果の区分」を含める / FR-040 を採用しない場合は契約から外し**外した事実をマニフェストへ宣言**(典拠: `docs/adr/ADR-003-domain-calc-method.md:255`〔**D-6**。契約単位「1 遷移」・履歴文脈は種別 + 差分・`D` は検査の保証範囲であって実行時上限ではない・補正/undo はイベント種別で表現し別の対象計算にしない・FR-040 不採用時はマニフェストの `vectors[]` へ宣言(宣言のない除外は fail)〕/ 同 `:308`〔**D-8**。状況判定の出力に「操作結果」の区分を含める〕)

#### 3 周目に一元化して 4 周目に差し戻された理由

- 是正の逐語: 「**操作順と論理順序を同一にしてはならない**: 3 周目に「論理順序も出場区間の境界も再計算の起点も**イベント連番へ**」とまとめたが、**イベント連番は同期の到着順**(欠番検知のための単調増加)であり、**過去位置への挿入や退避イベントの取り込みでは末尾に付く**。そのまま論理順序に使うと**挿入したプレイが末尾に再生される**。REQ:236 は任意位置への挿入と下流再計算を要求している」(典拠: `docs/features/product-data-model-design/design.md:407-410`)。**`REQ:236` は歴史的表記**(`kind=historical` — 現行 v2.3 では `:238`)
- 「**境界と再計算の起点は「論理順序」側**を使う(出場区間の境界・状態補正の起点)。**同期連番は同期と undo に限る**」(典拠: 同 `:411`)
- 根本原因(worklog の総括): 「**計画書 2 節が既に「同期プロトコルの詳細設計は別文書の領域」と宣言していた**。3 周目に「イベント連番へ一元化」と決めて 4 周目に差し戻されたのは、**宣言した境界を越えて決めようとしたから**」(典拠: `docs/worklog/2026-08-21-product-data-model-design.md:165`)
- ⚠️ **候補案の 400-406 行の用途対応表には「出場区間の境界 = イベント連番 / 再計算の起点 = イベント連番」の旧文言が残っており、同じ節の 411 行と食い違っている**(典拠: 同 `:404-405` 対 `:411`)。本タスクの起草は **411 行の側を正**として扱い、この不整合を正本化タスクへ申し送る

### 4. 候補案として既に置かれている前提(矛盾を作らないよう突き合わせる)

**前置き**: `design.md` は自ら「**本書は「候補案」であり「決定」ではない**」と宣言している(典拠: `docs/features/product-data-model-design/design.md:11`)。拘束するのは要件書・ADR-003・決定記録であり、候補案は突合相手。

- **操作イベント表を正本、プレイ行を投影(materialized projection)**として持つ(典拠: 同 `:380-385`)
- 一意性: **べき等キーは一意** / **(試合, 世代, 連番) は「有効な行が 1 件」**(`WHERE 置換されていない` の部分一意インデックス)/ **下位番号の欠番・重複それ自体は拒否しない**(典拠: 同 `:534-539`)
- 操作イベントに**適用水位**を保持(典拠: 同 `:530`)
- **履歴文脈は別表を持たない** — 未取消の取消可能イベントを連番降順に並べて導出(別表は 2 つの正本になる)(典拠: 同 `:541-543`)
- **識別子 5 種**(べき等キー / イベント連番 / 記録権世代 / 一時 ID〔UUID〕/ エンティティ内部 ID)を混ぜない。一時 ID は**参照の置換**で解決し置換の記録を残す(典拠: 同 `:436-458`)
- 記録権は**世代を行として持ち、現世代は「失効していない行が 1 件」**(部分一意インデックスがサーバー側直列化の防壁)(典拠: 同 `:564-573`)
- 退避イベントは**原本を残し、取り込みは現行世代で新規採番**+取り込み先参照を持つ(典拠: 同 `:613-623`)
- 「プレイ行の論理削除」は投影側フラグで、正は墓標・改訂イベント(**フラグだけ書き換える経路を作らない**)(典拠: 同 `:417-418`)
- キャッシュ無効化のトリガー 1 = **復帰同期**で全対象範囲を無効化(典拠: 同 `:1350`)

### 5. 旧システムの実挙動(= 何が新規設計か)

- **保存方式**: 確定ごとに DB へ即時保存 + メモリ追記。DB 失敗時はメモリのみ保持し、試合終了時 `sync_missing_plays` で「DB に無い `プレイの番号` の行だけ INSERT」して回収(典拠: `docs/legacy/research/input-screen.md:25`・`docs/legacy/research/services-shell.md:130`・`:141`)
- **端末内の永続キューは Streamlit 版に無い**。保持先はセッション上のメモリミラーで、**リロードでセッション消失**(典拠: `docs/legacy/research/services-shell.md:76`・`docs/legacy/research/docs-tests-ops.md:184`)
- 別経路(FastAPI + React の新 UI)には端末内キュー + 5 秒ごと自動再送があるが、**キューに未送信が残る間は次のプレイ確定がブロックされる**(典拠: `docs/improvements-from-baseball-scoring.md:81`)→ pitchlog では**ブロックしない**方針が確定済み(要件書 `:291`)
- **順序の担い手は 88 列の `プレイの番号`(列 9)ただ 1 つ**。「試合内の通しプレイ番号(同期・重複判定キー)、初期値 0」(典拠: `docs/legacy/research/data-layer.md:161`)。**UNIQUE 制約なし**で、重複防止はアプリ側のキー比較のみ(典拠: 同 `:402`)
- **順序キーが 2 系統併存していた**: 読み出しは `プレイの番号` 順、undo は `play_data.MAX(id)` 行を削除(典拠: 同 `:285-286`)
- 行内に時刻列はあるが**順序決定に使われた記述はない**。`created_at` 列は無い(典拠: 同 `:222-224`・`:58-63`)
- **挿入(過去への割り込み)機能は該当記述なし**。訂正は既存行の UPDATE で番号は変わらない前提(典拠: `docs/legacy/research/input-screen.md:276`)
- **訂正は上書き UPDATE で履歴を残さない**。編集可能項目は 14 項目に限定(典拠: `docs/legacy/research/services-shell.md:150`・`:153`)
- **undo は物理削除**(`MAX(id)` 行を DELETE)・**直前 1 件のみ・スタック無し・確認ダイアログなし**(典拠: 同 `:144`・`:146`・`docs/legacy/research/input-screen.md:272`)
- **状態補正(回・表裏・得点・SBO・打順の手動上書き)とタイブレーク開始は DB に書かれない** — メモリのみ変更(典拠: `docs/legacy/research/services-shell.md:158`)。改善台帳は「**履歴に残らない生の上書きで、いつ・何を・どう直したかが追跡できない**」と記録(典拠: `docs/improvements-from-baseball-scoring.md:214`)
- **記録権に相当する機構は存在しない**。「1 試合の入力は同時 1 人 1 端末まで」は運用ルールのみ。認証主体が個人でなく**チーム共有パスワード**のため、2 人が同じ試合を開くことを仕組みで防げない(典拠: `docs/improvements-from-baseball-scoring.md:199`・`docs/legacy/research/services-shell.md:106`)
- **リポジトリ層にリトライが埋まっており(PG は最大 3 回・指数バックオフ)、UNIQUE がないため再送で重複挿入が起こり得る構造**だった(典拠: `docs/legacy/research/data-layer.md:266`・`:404`)
- **交代はイベントとして存在しない**(オーダー変更はスタメン JSON の上書きからしか読めない)(典拠: `docs/legacy/baseball-scoring-db-structure.md:214`)
- **旧システムに無く新規設計になるもの**: 記録権 / 操作イベント列 / API 契約上のべき等キー / 単調連番・欠番検知・墓標・世代・フェンス / クライアント側の状況計算 / 論理削除 / 多段 undo / 交代・状態補正イベント / 試合状態フラグの永続化 / 検知と終了宣言の分離 / 未送信キューの退避(典拠: `docs/improvements-from-baseball-scoring.md:82`・`:84-85`・`:202`・`docs/legacy/research/data-layer.md:404` 他)

#### 移行が同期設計に課す制約

- 88 列の読み取りは**列名ベース必須**(位置依存禁止。`owner_team_id` の列位置が環境で異なり得る)(典拠: `docs/legacy/baseball-scoring-db-structure.md:286`・`:303`)
- センチネル値(`0` / `"0"` / `""` / NULL)の**列単位変換規則**が入口に必要(典拠: 同 `:208`)
- **旧データから交代イベントは復元しない**。出場履歴・交代表記は「不明」扱いを許容(典拠: 同 `:311`)
- **先発オーダーは各試合の最初のプレイ行のスタメン JSON を正**とする(典拠: 同 `:310`)

### 6. 記録権(FR-013)との境界

- 設計書 6.3 の同期プロトコル行: 「断中記録・墓標/改訂の適用・再送・**べき等キー・記録権世代内の連番と採番の不可分性(prefix commit)**・サーバー適用の原子性と**サーバー再計算/補正**・複数タブの単一書き手競合。**記録権世代・連番を扱うコードは「記録権」と重複帰属し得る**」(典拠: `docs/development/dev-harness-design-2026-08-07.md:353`)
- 記録権行: 「付与・**世代更新とフェンシング(旧世代拒否)**・**通常引き継ぎの原子性**・**緊急引き継ぎの競合拒否**・退避経路。世代・連番の同期側実装は「同期プロトコル」と重複帰属し得る」(典拠: 同 `:355`)

- 進行中試合の修正は「**記録権を保持する端末のみ**が実行でき、かつ**未同期キューが空であること**を前提条件とする」(典拠: 同 `:240`)
