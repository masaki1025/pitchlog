# 調査メモ: 後続 γ(サーバー適用の処理段階と原子性)の射程と TSK-250 依存の切り分け

## 問い

Notion カード **TSK-321** の制約欄が「**開始条件に TSK-250(データモデル正本化)の完了を含めるかを最初に判断する — 6 章の処理段階だけならスキーマ不要で先行できる可能性がある**」と指示している。この判断に必要な事実を確定する。

副次の問い: 本タスクは Phase 4 の論理スロット 4-6 に当たるか / 旧システム側の移行制約はあるか / 何を引き継ぎ何を新規に作るか。

## 結論(要約)

1. **「スキーマ」の語が 2 種を指しており、カード本文の「スキーマ不要」は DB スキーマを指す。** TSK-250 が決めるのは「**列名・型・NULL 性・FK・索引・表分割**」(`docs/design/sync-protocol.md:1774`)。後続 β が γ へ送った宿題は「**JSON / API スキーマ**」= wire 側(`docs/features/sync-ack-contract/plan.md:246`)で、別物である。
2. **要素単位で線を引ける。** `DI1`・`DI5`・`I1` は**照合の位置・順序**の規則で 6-2 の処理段階表(`:683-693` / `:709-721`)に閉じ、DB スキーマを要さない。一方 **`B3a` は `P5 + T9`**(`:1248`)であり、**`T9` は「未使用 D5 の内容拒否原本・D5・拒否結果・理由の保存」= 永続化を伴う原子境界**(`:1201`)なので、**保存側は DB スキーマを要する**。
3. **`NFR-019(d)` の 2 項目(墓標/改訂の適用・サーバー適用の原子性)は、いずれもサーバー適用の実行を要する**。`backend/` は現状 `GET /health` の 11 行のみで、**DDL・マイグレーション・ORM が皆無**(`backend/src/pitchlog/main.py:1-11`)。**実行検証は backend なしでは閉じない。**
4. **TSK-250 の完了を開始条件にすると γ は長期停止する。** TSK-250 は承認済み(計画レビュー 5 周)だが、**開始条件 B(TSK-317)・C(TSK-271)・人間裁定 4 件が未充足**で、`docs/design/data-model.md` も新資産も **1 件も存在しない**。
5. **前例がある。** 後続 β は「**ACK 応答の消費側 + 契約の型・オラクル固定。サーバー実装は後続 γ**」で閉じた(`sync-ack-contract/plan.md:64`)。γ も同型に切れる。
6. **本タスクは Phase 4 の論理スロット 4-6 に当たらない。** 要件書 `:956` が Phase 4 完了時の合格条件から「**一致性・越境・E2E・同期故障系は実装期のため対象外**」と明示的に除外している。
7. **旧システム側の移行制約は 1 件も無い。**

## 詳細と典拠

### 1. 「スキーマ」の 2 義 — 射程裁定の中核

| 語の指す先 | 決める主体 | 典拠 |
| --- | --- | --- |
| **DB スキーマ**(列名・型・NULL 性・FK・索引・表分割) | **TSK-250** | `docs/design/sync-protocol.md:1774`(11-2 柱書)「**列名・型・NULL 性・FK・索引・表分割は決めない**(4-1)。物理構造の決定は各受け取り先が担う」 |

TSK-280 が「8 章 → 後続 γ / **TSK-250 後** / **スキーマが要る**」と書いた(`docs/features/sync-event-contract/plan.md:87`)ときの「スキーマ」は、同じ表の別行が `DI1`・`DI5`・`I1`・`B3a` を「**6 章の処理段階と A5 に依存する**」(同 `:84`)と**スキーマに言及せずに**分けていることから、**DB スキーマ**を指すと読める。

### 裁定 1 が確定させること

- **DoD は「8 章の原子性を検証する」ではなく「8 章の原子性を検証するための契約・オラクル・注入点を固定し、実行検証を送る」に限定される**
- **β が送った「JSON / API スキーマの確定」**(`sync-ack-contract/plan.md:246`)は wire 側であり **DB スキーマ(TSK-250)に依存しない**ため、射程に含められる。ただし**要件書に典拠が無い**(spec-checker 確認済み)ので、計画書では設計 v0.3 の意味上の不変条件を上位典拠として明示する
- **`B3a` は判定側(どちらに分岐するか)だけを実装し、保存側(`T9`)は送る** — `T9` は永続化を伴う原子境界(`sync-protocol.md:1201`)であり DB スキーマを要する
