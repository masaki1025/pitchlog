# 調査メモ: 付録E ゴールデンケース全表 + 終了判定ベクタ(TSK-236)

## 問い

1. 付録E は「何が」未完成で、全表を埋めるのに必要な入力(行の母集合・列の値域)は揃っているか
2. ADR-003 が既に確定した事項はどこまでで、TSK-236 が新たに決めるべきものは何か
3. リポジトリの現況(置き場・runner・CI)はどこまで出来ているか。TSK-235 との依存・順序は
4. 旧システム(Baseball_Scoring)の挙動はどこまで期待値の事実源に使えるか
5. 着手前に人間裁定が要る未決事項は何か

調査は 4 本を並列実行した(spec-checker / decision-tracer / legacy-analyst / Explore)。
報告間の食い違いは末尾「裁定した矛盾」で原典を確認して決着させた。

## 結論(要約)

- **置き場・形式・比較面・CI 検査は ADR-003 が確定済み**。残るのは「中身の作成」と、
  ADR が明示的に委任した schema の細部(ADR-003:251)。
  **ただし入力範囲(D-11)は確定済みではない** — **計画レビュー 1〜4 周目で、
  文字どおりの全列挙が実行不能であることが判明し、D-11 の改訂を本タスクの射程に入れた**
  (2026-09-24 改稿。3 節の一覧は**改訂前の ADR-003 を記述したもの**であり、
  現行の射程は [plan.md](./plan.md) 3 節と [design.md](./design.md) 1 節が正)。
- **実体はゼロから作る**。`contracts/state-transition/` は不在、ベクタ契約ファイルは 0 件、
  ベクタを消費する runner も CI ジョブも develop に存在しない。
- 着手をブロックする未決は当初 4 件。**2026-09-24 に 2 件を解消**(行の母集合の典拠 = 実測で一致を確認 /
  FR-040 = PO 了承で不採用)。残りと、計画レビューで判明した**定義の穴 8 件**は
  **本タスクの射程内で要件改訂として実施する**。
  **穴の一覧と改訂の射程は [design.md](./design.md) 7 節が正**(本メモの記述は調査時点のもの)。
- **TSK-235(PR #74)は待たない**(2026-09-24 決定)。
  **2026-09-24 のスコープ裁定で、製品 manifest 登録・実 case の両 runner 全件消費・正規化の計算投入証跡は
  段階 2 へ送った**ため、TSK-235 / TSK-455 は**本タスクの開始条件ではなくなった**
  (本メモ以下の「合流」「マージ後」の記述は改稿前のもの — 現行は [plan.md](./plan.md) 1-1 と
  [design.md](./design.md) 1 節が正)。以下は当時の記録。
  双方向の待ち合わせ(TSK-235 側は成績計上フラグの外延を待つ)
  になるため。**DoD を「契約ファイルの完成」と「`backend/domain/manifest.json` への実登録」に分割**し、
  後者を TSK-235 マージ後の合流ステップへ送る。TSK-235 は別セッションで進行中。
- 旧システムは**状態遷移の既定値の事実源としては有用**だが、規範にはできない箇所が多い
  (旧の提案テーブルは「確定前サジェスト」であり、振り逃げ分岐・タイムプレイ・X 表記・付録F は旧に無い/誤っている)。

### C. 台帳への義務(昇格条件が本タスクの着手)

運用評価台帳 `docs/development/harness-evaluation.md:1908-1912` の **候補 (10)**:

> 付録E の完成手順(典拠の選定・旧バグの仕分け)が未規定 — 完成作業で**何を典拠に拾うか**
> (旧テスト・旧 domain 挙動の扱い)と、**再現してはいけない旧バグ**を仕様と仕分けるゲートが未規定。
> **昇格条件 = 設計フェーズで付録E 完成作業を計画書化する時点**

**本計画の作成がまさにこの昇格条件に当たる**。計画書化の時点で `H-*` 採番の要否を判定する義務がある。

ADR-003 が定めたのは D-6 CI 検査 3 の「要件・状態表から独立に生成するか人間が確認する」という**出所の性質**だけで、
**典拠の優先順位・旧テスト/旧 domain 挙動の採否・旧バグの仕分け手続きは定めていない**(ADR 全文に「旧バグ」の語は無い)。

参考材料: `docs/features/nfr018-domain-calc-adr/research.md:123-127`。
**ただし「7 件すべてが旧バグ」ではない**(計画レビュー 2 周目 P2-2 の是正)—
`docs/legacy/research/domain-logic.md:170` 以下は「**既知の制約・バグ**」であり、
**1〜5 が不具合 / 6 は識別制約(走者同定が氏名文字列)/ 7 はアーキテクチャ上の推奨**。
台帳の候補 (10) も「**既知 5 件**」と数える。仕分けは design.md 8-4 が正。

### D. 完成判定の基準が無い

- 付録A には ADR-003 D-10 が**6 条件の判定基準**(判定者 = PO)を定める(:350-369)。
- **付録E・終了判定には対応する判定基準表が ADR にも要件書にも無い**。
  要件書は「完成をもって発効」としか定めない(requirements-pitchlog-2026-07-22.md:920)。
- 実効的な代替は D-11 の「入力範囲を全件覆う」+ 3 層登録漏れ検出 + 経路一致検査の要求集合差 fail(ADR-003:217, 249)。
- **誰が何をもって「完成 = 発効」と判定するか**を計画で決めるか、判定基準の新設を別途起票するかの判断が要る。

### E. 要件書が条文化していない終了判定の細部

ベクタの `expected` を書く時点で必ず具体化を迫られる:

- **コールド成立のタイミング**(回の裏の途中 / 完了時)
- **引き分け成立の具体条件**(付録F-1 の「延長上限: 上限到達で同点なら引き分け」= 同:1287 以上の規定が無い)
- **X 表記の一般規則** — 要件書は「後攻リードで最終回裏が不要」の**1 ケースのみ**(同:234)。
  サヨナラは「裏の途中で終わるため X ではなくその回の得点を表示する」と但し書きがある
- **再開(終了ロック解除)をベクタでどう表現するか** — FR-007(同:257)が
  「再開操作は FR-005 の終了条件ロックを解除する」と定める一方、**再開は断中操作イベントの Must 6 種に含まれず**
  (同:182)、FR-007 の修正はオンライン前提(同:258)。入力イベント軸に再開を入れるかの判断が要る
