## 4. 実装方針

### 重さ分類 = 通常(根拠)

`.claude/core-areas.json` の `areas[].paths` に該当 0 件(コア領域 5 つのいずれにも触れない)。**トップレベル `guard_paths`(`core-areas.json` / `ci.yml` / `core_guard.py` / `pull_request_template.md` / `pr/SKILL.md`)にも該当しない** — 本タスクが触るのは `.claude/hooks/**` で、`guard_paths` には含まれない。したがって **CI の core-guard は発火しない**。

### 確定済みの実装方針(確定ゲート 2 周目 P1-4 — 変更しない)

- **サブコマンド位置(`git` の直後)のトークンだけを動詞として判定する**(対象動詞から `push` を外すだけでは `merge` の誤認が残る)
- **`current_branch` は fail-closed へ**(docstring `:6` の宣言を正とする。**実装に合わせて docstring を弱める案は取り下げ済み**)

### A. 引用符を考慮したセグメント分割(H-10 の真因)

現在の `re.split(r"&&|\|\||\||;|\n|&", text)` は**引用符の内外を区別しない**ため、引用符内のセパレータで引用符が分断され、断片が `shlex` で解析不能になる(research.md §3)。

- **`guard_common` へ `shell_segments(command) -> list[str] | None` を新設**し、`codex_guard`・`git_guard` の両方から使う(NFR-018 — 同じ処理を 2 度書かない)
- **引用符の内側にあるセパレータでは分割しない**。実装は `shlex` を分割器として使う(`punctuation_chars` の活用)か、引用符状態を持つ手書きの走査のいずれか。**どちらでも可**だが、`shlex` を使えるなら既存の依存に揃える
- **分割そのものに失敗した場合は `None` を返し、呼び出し側が安全側へ倒す**(現行の `shell_tokens` と同じ契約)
- **認識済みの `shell -c` 本文も `shell_segments` で再帰評価する**(**計画レビュー 1 周目 P0-2**)。**これを入れないと防御が後退する** — 現行は外側の `re.split` が `bash -lc 'echo ok; codex exec x'` を**偶然**分割して遮断していたが、引用符対応後は 1 セグメントになる。再帰側(`codex_guard.py:61-84`)は `shell_tokens` を使うため `ok;` を区切りと認識できず、**生の `codex exec` を見逃す**。同型で develop 上の `bash -lc 'echo ok; git commit -m x'` も現行の遮断から許可へ変わる
- **ヒアドキュメント本文の扱いは変えない** — `effective_command`(`:42-50`)の現行契約を維持する。本文の除外は正規ラッパー呼び出しに限る(research.md §0 の 4 例目は**本タスクでは直らない**。台帳へ起票する)。**任意の heredoc を一律データ扱いにすると、展開・コマンド置換を含む実行可能本文まで隠しうる**ため、ここは緩めない(1 周目 P2 で妥当と確認)

### B. Git 呼び出しの解析と、宛先ベースの push 判定(H-2・H-11)

現在の `VERBS & set(tokens)`(`git_guard.py:94`)は**トークン集合の交差**なので、引数位置の `merge`・`push` にも反応する。

#### B-1. Git 呼び出し解析の契約を定義する(**1 周目 P1-1**)

「最初の非オプション語」だけでは `-c foo=bar` や `-C path` の**値をサブコマンドと誤認する**。次を返す解析関数を定義し、その戻り値で判定する。

- **実サブコマンド** — グローバルオプション(`-c <k=v>` / `-C <path>` / `--no-pager` / `--git-dir=<p>` など**値を取るもの・取らないものを区別**)を読み飛ばした先のサブコマンド
- **有効 cwd** — **最後の `-C` を採用**する(現行は最初の 1 つしか拾わない — `git_guard.py:95`)。相対パスの連結も考慮する
- **不明状態** — 解析できない形(未知のグローバルオプション・alias 経由など)は**不明として返し、呼び出し側は安全側へ倒す**

**alias は本タスクでは解決しない**(`git -c alias.p=push p origin HEAD:develop` のような形)。**解析が不明を返すので fail-closed に落ちる**が、**上段の宛先判定だけで絶対規則 1 を完全に満たすとは書かない** — 残余として §8 に明記する。

#### B-2. push は「宛先が非保護と証明できたときだけ許可」する(**1 周目 P0-1**)

**当初案(push をカレント判定から外す)は誤りだった。** 上段(`git_guard.py:76-85`)は**明示 refspec しか見ていない**ため、次の形で保護宛先を見出せない:

| 形 | 現状 | 当初案だと |
| --- | --- | --- |
| `git push`(引数なし) | 下段のカレント判定が develop 上で遮断 | **通ってしまう** |
| `git push origin` | 同上 | **通ってしまう** |
| `git push origin HEAD` | 同上 | **通ってしまう** |
| `git push --all origin` | 同上 | **通ってしまう** |
| `git push --mirror origin` | 同上 | **通ってしまう** |

いずれも **upstream 設定次第で develop へ反映されうる**。したがって push は次の三値で扱う。

1. **宛先が明示され、非保護と判定できる** → **許可**(例: `git push origin --delete feature/x`・`git push origin HEAD:feature/x`)。**これで H-2 は満たせる**
2. **宛先が明示され、保護ブランチ・force・`+refspec`** → **遮断**(現行の上段どおり)
3. **宛先を静的に解決できない**(引数なし・`origin` のみ・`HEAD` のみ・`--all` / `--mirror` など)→ **宛先未解決として遮断**(fail-closed)。**カレントが保護ブランチかどうかに関係なく遮断する**

#### B-3. commit / merge / rebase はカレント判定を維持する

これらは「カレント = 宛先」なので、B-1 の実サブコマンドが `commit`・`merge`・`rebase` のときだけカレント判定を行う。**引数位置の同名トークンには反応しない**(H-11 の是正)。

### C. `current_branch` の三値化と fail-closed(H-9)

現在は例外・非 0 終了のいずれも `None` を返し、`None in PROTECTED` が False になって**通る**。

**`rev-parse` の非 0 だけでは、非リポジトリ・壊れた `.git`・不存在 cwd・timeout を区別できない**(1 周目 P1-2)。したがって**三値契約**にする。

| 状態 | 判定 |
| --- | --- |
| **非リポジトリと積極的に確認できた** | **許可**(保護ブランチという概念が無い) |
| **ブランチ名を解決できた** | 従来どおり `PROTECTED` と突合 |
| **それ以外のすべての不明**(壊れた `.git` / 不存在 cwd / timeout / 例外) | **遮断**(fail-closed)。**理由をメッセージに出す** |

「非リポジトリと積極的に確認できた」の判定には `git rev-parse --is-inside-work-tree` の成功と出力内容を用いる(**手段は問わないが、積極的な確認であること**が要件 — 「失敗したから非リポジトリだろう」という推定は不可)。

**テストの作り方**(1 周目 P1-2): 現行の子プロセス起動ヘルパー(`tests/test_hooks.py:21`)では `subprocess.run` を注入できない。**既存の tmp リポジトリ fixture(`test_hooks.py:244`)を使い**、次の 2 系統を**分けて**書く。

- **プローブ成功後のブランチ解決失敗**を直接注入する単体テスト → **遮断されること**
- **存在する非リポジトリ cwd** → **許可されること**
