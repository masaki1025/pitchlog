# 調査メモ: TSK-344 の DoD を裁定 A・B に合わせて見直す

## 問い

**TSK-378 の PO 裁定 A・B(2026-09-12・山田正輝)によって、TSK-344 の DoD 6 項目のうち
どれが・どう意味を変えたか。** カードは「**4 と 6 の意味が変わる**」としているが、その前提が正しいか。

## 結論(要約)

1. **カードの前提は誤り。変わるのは 4 と 6 だけではない** — **DoD 2 と 5 も変わる**。
   DoD 3 だけが条文の明示によって**変わらない**と言える。
2. **DoD 4 は「空の要求」になる** — ただし**削除でも免除でもなく**、「対象入口なし」と**記録する義務**が残る。
3. **DoD 6 は指す先の条文が消えた** — 「解除」は正本に **0 件**(全数確認)。
   新条文では**一回性の解除という契機が存在しない**。
4. **ADR-004 の射程宣言は「TSK-344 の DoD の見直し」としか書いていない** —
   **4・6 への限定は TSK-378 側の記録にしかない**。
5. **`non-serving` の字面衝突は TSK-382 の所有** — DoD 6 の書き直しが踏み込むと**射程が衝突する**。
6. **ゲートの対象自体が広がった**(「有効化する PR」を追加)。**TSK-344 の DoD に対応する欄が無い。**

**PO 裁定(2026-09-13・山田正輝)**: **射程は DoD 全体の見直し**とする。
**DoD 6 は「条文への写像」に留め、`non-serving` の字面衝突には触らない**(TSK-382 の射程を踏まない)。

### 3. DoD 4 — 「空の要求」になる(削除ではない)

**測定経路行の逐語**(`NEW:2532`):

> [NFR-010] の測定方法が「**API 直叩き含む**」と定めるので、**アプリ経路だけの検証では通過にしない**。
> **充足条件**(裁定 B): **入口を開く PR は、同一 PR にその入口を製品の外から直接叩くテストを含む**
> (**HTTP なら API 直叩き、他のプロトコルならそのプロトコルで外から直接叩く**)。
> **入口を 1 つも開かない PR に対しては、この要求は空である** — **開いた入口が無ければ、
> 含めるべき直叩きテストも無い**。**空であることは要求の免除ではなく、要求を当てる対象が無いことである**。
> **「アプリ経路だけの検証では通過にしない」という禁止は、当該 PR が開いた入口について効く**

**TSK-344 は入口を開かない** — カードの射程が「実スキーマ適用後の再実行」であり、
**製品の HTTP 経路を新設しない**。実測では `backend/src/pitchlog/main.py` は **11 行**で
**`@app.get("/health")` 1 本だけ**(`docs/worklog/2026-09-09-pg-authz-verification-g2.md:2056-2057`)。
`/health` は境界例表で「**DB のデータへ到達しない入口** → **開かない**(条件 3 を満たさない)」(`NEW:2494`)。

**→ DoD 4 は (a) 空の要求。ただし記録義務が残る**(次項)。

**最低要求 4 件との関係も明示された**(`NEW:2531`・**新設行**):

> **最低要求 4 件はすべて DB ロール・関数 ACL・`search_path` に対する要求**であり、
> **HTTP 経路に対する要求を 1 件も含まない**。したがって **4 件は HTTP 経路を開かない PR でも判定できる**。
> **4 件の文言は変えない**(**12-7 (1) が実機確定タスクへの要求として同じ 4 件を列挙している**ため)

### 7. 新設「経路と入口の定義」— 判定の基礎

**新設小節**(`NEW:2428-2500`・73 行)。**本改訂の中核。**

| 語 | 定義(逐語) |
| --- | --- |
| **入口** | **製品の外からの要求を受け取り、DB のデータへ到達する 1 本の口**(HTTP なら **method と path の組**) |
| **経路** | **同じ経路識別子を持つ入口の集合**。**HTTP の経路識別子の正は `contracts/authz/http-route-matrix.json` の `route_id`** |

**判定・測定・記録の単位は入口である**(`NEW:2441`)。

**「開く」の 3 条件**(`NEW:2462-2464`)— **PR 前は不成立・PR 後に成立**:

1. **`e` を処理する製品コードが存在する**
2. **`e` が製品の外から到達できる**(ルーティングに載っている)
3. **`e` の処理が DB のデータを読むか書く**(直接・関数経由を問わない)

**到達性の 3 軸**: 主体(テナント・役割・付与の状態)/ 資源(表・行・列)/ 操作(読取・追加・更新・削除)。

**境界例 11 行**(`NEW:2488-2500`)。**TSK-344 に効くもの**:

| 例 | 開くか | 理由 |
| --- | --- | --- |
| **バッチ**(スケジュール実行・移行) | **開かない** | 条件 2 を満たさない。**ただし最低要求 4 件は掛かる** |
| **内部経路**(製品の外から到達できない) | **開かない** | 条件 2 を満たさない |
| **DB へ到達しない入口**(`/health`) | **開かない** | 条件 3 を満たさない |
| **ハンドラだけ足してルーティング未登録** | **開かない** | 条件 2 を満たさない |

**機械判定は射程外**(`NEW:2431-2432`): 「**本項が定めるのは人手で判定できる意味であり、
機械判定(CI での検出)は本改訂の射程外**である」→ **TSK-383**(`ADR-004:43`)。

**資産側の実測**: `http-route-matrix.json` は `asset_kind: "authz_http_route_matrix"`・
`routes` **37 件**・**JSON 全体に `method` キーも `path` キーも 0 件**。
条文の「method / path を持たず `route_id` と入口は 1 対 1 に対応しない」は**実測で裏付けられる**。

### 8. 裁定 A・B の逐語(典拠: `docs/worklog/2026-09-12-merge-gate-api-cycle.md:56-70`)

| 裁定 | 逐語 | 不採用案 |
| --- | --- | --- |
| **A** 適用単位 | **経路単位** — 12-4 のゲートは**当該 PR が開く経路について**判定する。対象横断の `NFR-019(b)` 網羅と「`NFR-010` 適合」の宣言は**リリース候補時の受入**で行う | **「対象横断のまま」**(採ると最初の 1 本が永久に条件を満たせず循環が解けない) |

ゲートが発火しない**」と判明(`ADR-004:166-170`)。

### 10. 先例 — 完全同型は無い

**「別タスクが、既存タスクの DoD を裁定に合わせて書き直した」完全同型の先例は見つからなかった。**
近い型は 3 つ:

| 型 | 内容 | 例 |
| --- | --- | --- |
| **A** | **自タスクが自分の Notion DoD を現行化** | TSK-308 / TSK-271 / TSK-342 / TSK-250 |
| **B** | 射程が動いたので**既存 DoD の該当条項だけ**を差し替え(「後続タスクで閉じる」へ) | TSK-265 の `U-1` 条項 |
| **C** | 他タスクの DoD へ**追記・登録**(書き直しではない) | TSK-250 への受取契約 / TSK-311 |

**型 A の形式**(最も件数が多い): ① **計画書 5 節と逐項照合** ② 照合結果を **3 列表**で worklog へ記録
③ **更新後の URL を併記** ④ **経緯と典拠を併記**。

**台帳の関連知見**: **`H-6`「Notion タスクの DoD と計画書 5 節の同期が一度きりで、以後の変更に追随しない」**
(`docs/development/harness-evaluation.md:410-418`)。追跡優先度は**通常**(「Notion は正本外で機械検査の射程外」)。
**本タスクはこの `H-6` が実害化した事例である。**
