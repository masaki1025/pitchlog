| **既存の 48 node の試験本体と autouse の fixture** | **38**(`ALTER ROLE "pitchlog_app"` 37 / `CREATE ROLE "pitchlog_test_role"` 1) | **`backend/tests/` は裁定 2026-09-28 で編集禁止**。**観測方法を変えて解いた**(下記) |

**PostgreSQL には「`TRUNCATE` は記録するが DDL は記録しない」設定が無い**(`mod` は `ddl` を包含する)。
**したがって statement ログで分岐を数える限り、DDL も必ず一緒に記録される。**

**解き方 — 記録をロール単位で切る**:

```
ALTER SYSTEM SET log_statement = 'all';
ALTER ROLE <管理ロール> SET log_statement = 'none';   -- 平文 DDL はすべてこの接続から出る
SELECT pg_reload_conf();
```

**所有者ロールは `NOSUPERUSER NOCREATEROLE` でパスワード DDL を打てない**ため、
**観測したい `TRUNCATE` だけが残り、平文は原理的に載らない。**

**実測(静かな窓で取得)**:

| | 是正前 | 是正後 |
| --- | --- | --- |
| **`PASSWORD '<平文>'` の出現** | **38 件** | **0 件** |
| `TRUNCATE TABLE` | 96 件 | **96 件**(観測は維持) |

**是正前に取得したログを含む検証用インスタンスは、コンテナとボリュームごと破棄した。**
**資格情報は実行ごとに生成され、そのインスタンスの外に存在しない。**

### `docker events` の観測は母集団がホスト全体に広がっている(**是正済み — 観測を拘束へ置き換えた**)

**使い捨てクラスタの名前は `pitchlog-authz-<乱数>` で、本リポジトリの全セッションが同じ形で作る**
(`backend/tests/db_fixtures.py` が `secrets.token_hex(8)` で採番する)。
**名前でも時刻窓でも、他セッションのものと区別できない。**

**実際に汚染された** — 2026-10-05 の 1 回の実行で **13 件**を拾い、**いずれも他セッションのもの**だった
(当該時刻に別タブが backend の DB 試験を走らせていた)。

**本記録の観測は、他セッションが使い捨てクラスタを作っていない時間帯に取った**
(4 セッションへ依頼し、停止の確認を得た)。**結果は 0 件。**

**この取り方は再現性が弱い** — 測定のたびに全セッションの協調が要り、
**「止め忘れが無かったこと」自体は証明できない**。**指摘は 469 タブから受けた(2026-10-05)。**

**2026-10-06 に合格条件を観測から拘束へ変えた**(**人間承認**。計画書 4-4-d 節)。
**pytest のプロセスから `docker` へ到達できないようにし、既定の分岐へ入れば必ず失敗させる。**
**本記録の証跡はその拘束の下で取った**(`docker_unreachable_during_tests: true`)。
**ホストの状態を一切見ないので、他セッションと独立に再現できる。**
`docker events` の購読は**補助**として残してある(上表)。

**協調方式の実費も測った** — 他セッションへ中断を依頼した結果、
**teardown が飛んで使い捨て DB にロールが残骸として残り**、再開後の実行が
**fail-closed で 385 errors で全滅**した。**協調に起因する増分は約 6〜7 分**
(破棄した実行 5 分 + 無駄になった再開 1 分 + 撤去の手間)。
**破棄分は中断のタイミングに依存し、全件の終盤で止めれば最大 26 分になりうる。**
**残骸は 2 面ある**(使い捨てクラスタのコンテナと、その中のロール)。

**ただし本記録の結論は、この観測が無くても別の 2 つで支えられている** —
**`TRUNCATE` 96 件 = 48 node × 2**(外部供給の分岐でしか出ない)と、
**96 件の接続観測が全件、専用インスタンスのクラスタ識別値と対象データベース名に一致**したこと。

**独立に取れていない項目を 1 つ明示する**(同節「独立に取れない観測があれば、その旨を判定記録へ書く」):

- **JUnit XML の成果物は、runner が書き出したあとに後処理している** —
  例外文と捕捉出力を消している(NFR-014。失敗時の出力に接続文字列が混ざりうるため)。
  **合否の要素(`failure` / `error` / `skipped` のタグ)は残すので判定は歪まないが、
  生の pytest 出力そのものではない。** **この 1 項目は実行側の申告を含む。**
  **さらに、後処理は書き出しの後に行われるので、生の失敗内容がいったん実行環境の一時領域へ書かれる**
  (**追記 2026-10-05・敵対レビューの指摘**)。**異常終了して後処理へ到達しなかった場合、
  接続情報を含みうる生の出力がそこに残る。** **成果物の置き場はリポジトリの外(一時ディレクトリ)で、
  リポジトリへはコミットされない**が、**実行環境には残りうる**。
  これに対し**サーバーログと `docker events` は runner が触れない経路**であり、取得の点では独立である。
