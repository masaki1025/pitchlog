## 1. 条文が定めていること / 定めていないこと

### 1-1. 7.7-4 が資産へ委任した 4 項目(`dev-harness-design-2026-08-07.md:619-622` 逐語)

1. **何を凍結するか**(凍結対象の集合)
2. **凍結対象の同一性をどの粒度・どの識別値で比べるか**
3. **宣言と実装の対応をどう保証するか**
4. **受理の単位と、直前・直後の状態の算出方法**(7.7-2)

**この 4 項目に「削除記録の置き場」「履歴アーカイブ」「履歴 ID」は含まれていない。** 7D の 3 項目は**条文の委任の外**にある。

### 1-2. ただし削除については条文が既に定めている

`:574-579`(逐語)

> **行為のあと、その基準に対応する凍結対象が 1 つも残らないときは、宣言から当該基準を取り除く。**
> **取り除いたことを表す宣言を残さない。** **記録は 7.7-2 の履歴が持つ。**
> (**宣言は「現に凍結している基準」を表すので、凍結をやめたものを宣言に残さない。** **「かつて凍結していた」は履歴の役目である。**)

`:557` / `:603` / `:605`(逐語)

> **削除も「動かす」に含む** — **含まないと、履歴を残さず基準を消す経路が開く。**
> **取り除くときも記録を要する** — **記録なしに基準を消せると、凍結そのものを黙って外せる。**
> **基準の履歴は追記のみとする。** **既存の記録を書き換える変更・削除する変更を受理しない。**

**→ 「置き場」は決まっている。tombstone 宣言は禁止。記録は履歴側。**

### 1-3. 条文が定めていないこと

- **record を一意に指す ID を要求する条項は無い**(7.7 全文走査。要求は「1 行為 = 1 記録」「追記のみ」まで)
- **履歴の大きさ・保存期間・アーカイブに関する記述は一切無い**(7.7-1/-2/-3 全文走査)

## 2. 裁定 — 2 本のエージェントの食い違い

**食い違い**: spec-checker は「**置き場は条文で決まっているので 448 が決めるのはスキーマと検査だけ**」、Explore と decision-tracer は「**履歴が資産ファイル内にあるので設計判断が要る**」。

**裁定: 両方正しく、層が違う。**

**論理的な置き場**は条文が決めている(= 履歴)。**物理的な置き場**が未決である。**実測**:

```
cache-invalidation-contract.json の history: 1 件(このファイルを消せば一緒に消える)
```

**資産を削除すると、その資産が蓄積した履歴も一緒に消える。** これは 7.7-2 `:605`「**既存の記録を削除する変更を受理しない**」に正面から抵触する。

**`research.md:272`(TSK-431)が同じ判断を既に記録している**(逐語)

> **削除された資産の履歴の置き場を条文が定めていない。** 7.7-2 `:605` と、履歴が各資産ファイル内にある現行構造が衝突する。資産を削除すれば履歴も消える。**7.7-4 の委任にも明示的には含まれない。設計判断が要る**

### 2-1. D1 が部分的に解いている

**TSK-431 の D1** により、**記録は authority(`base-allowlist.json`)に 1 件だけ**置かれる(`frozen_history.py:387` `validate_history_authority`)。

**したがって「削除という行為の記録」は authority に置けば済む。** **未決なのは「削除される資産が過去に蓄積した履歴をどうするか」**である。

**現況**: 非 authority 6 資産はいずれも **v1 記録 1 件**のみ(実測)。**失われる量は現時点では小さい**が、**将来は増える**。

**append-only 検査が位置と論理キーの二本立て**: `check_frozen_baselines.py:1330-1361` が逐語 prefix を index で検査しつつ、**件数が同じで `(acceptance_id, series)` が違えば「history の同数置換を検出した」**で別エラーにする。

### 3-3. 構造上の決定的な違い

| | `frozen-baselines.json`(TSK-421) | `contracts/tenant_boundary/*.json` |

## 7. 踏みそうな罠(3 件)

### 7-1. 「削除を受理できるようにする」が「検査を弱めた」と判定される

現行は**無条件 `ContractError`**(`frozen_history.py:295-297`)。448 はこれを緩める。

**台帳候補(TSK-440 の未マージ分)の逐語**

> **検査器の射程を動かす変更では、前版との差分比較を合格条件に入れる。「既存負例が全件赤」は必要条件であって十分条件ではない。**

**前版(develop)の検査器と新版へ同じ入力を当てる比較を、計画書の合格条件に入れること。**

**加えて TSK-431 の実装レビューで 3 周連続で出た型**(「**関数は正しいが本番経路がその結果を使っていない**」)が**同じ場所で起きる**。有効だった判定基準は「**機構を壊す変異を入れて本番経路テストが落ちるか**」で、**関数を直接呼ぶテストは 4 件をどれも捕まえられなかった**。

### 7-2. 置き場を間違えると、条文違反か母集団汚染のどちらかになる

- **`contracts/tenant_boundary/` 直下に `.json` を置くと、それ自体が保護資産として列挙される**(`check_tenant_boundary_bypass.py:3729` / `:3752-3754` — **直下 `.json` のみ・サブディレクトリは対象外**)。`retired-*.json` は**新しい資産の追加**と解釈され `baseline_set` movement を発火させる
- **tombstone「宣言」は条文が正面から禁止**(`:577`)
- **`history-snapshots/` がサブディレクトリの先例**(母集団に入らない)

### 7-3. 「安定した履歴 ID」は既存 v1 へ遡及できない

**v1 記録 7 件に `acceptance_id` が無く**、**D2 の prefix deep-equal**(`frozen_history.py:226-231`)が**既存記録への 1 バイトの追記すら拒む**。

**448 が ID 体系を定義しても、既存記録へ ID を振ることはできない。** 配列位置でしか指せない状態は、**TSK-450 の訂正経路が入るまで解けない**。

**したがって 448 の計画書は「448 の ID は新規記録にのみ適用され、既存 v1 を指す手段は TSK-450 の射程」と境界を明示すること。** **PO 判断 2026-09-25 が 450 の射程を 2 種別へ広げたのは、まさに「二度やらない」ため。**

### 7-4(付随)— 台帳への追記で必ず衝突する

**TSK-440(`fix/tenant-boundary-scope`)が未マージで、`docs/development/harness-evaluation.md` と `docs/README.md` に追記済み。** 448 も同じ 2 ファイルへ追記すると衝突する。

**PR #78 はこの衝突で 3 push 分 CI が 1 つも走らなかった。** **`gh pr view --json mergeable,mergeStateStatus` で `CONFLICTING` を確認する運用を最初から入れること。**
