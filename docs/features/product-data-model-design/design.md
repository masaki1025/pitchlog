## 3. テナント分離(論点 2・3・4・12)

### 3-0. 認可の共通述語(**本書で繰り返し使う。定義はここだけに置く**)

**同じ述語を各節で言い直すと伝播漏れが起きる**(敵対レビュー 2・3 周目で実際に 8 件発生した — 参加上限だけを
直して不変条件・制御資源・付与・招待へ反映しなかった)。**以下を唯一の定義とし、各節は参照する**。

| 述語 | 定義 | 典拠 |
| --- | --- | --- |
| **テナントが有効** | テナントが**無効化されていない**(FR-035 の無効化状態でない) | REQ:715 |
| **実効参加** | **参加行が `active`** ∧ **参加テナントが有効** | REQ:493・705・715 |
| **実効 `admin`** | **実効参加** ∧ **役割が `admin`** | REQ:488・715・716 |
| **実効グループ** | グループが **`active`**(`terminated` でない) | REQ:653・715 |
| **実効な共有文脈** | **実効グループ** ∧ **要求元の実効参加** ∧ **対象の実効参加** | REQ:597-606・653-657 |

**なぜ「参加行が `active`」だけでは足りないか**: **テナント無効化では参加レコードを維持する**
(REQ:715 — 再有効化でそのまま復帰するため)。したがって**参加行の状態だけを見ると、無効化された
テナントが生きているように見える**。REQ:705 は「無効化中は `active` でないため**計数しない**」と定めており、
**数え方は常に「参加行の状態 ∧ テナントの有効状態」**である。

**適用先(すべてこの定義を使う)**:

| 節 | 使う述語 |
| --- | --- |
| **3-5**(制御資源の RLS 述語・読み取り粒度) | **実効グループ** ∧ **実効参加** |
| **3-6**(共有関数の前提条件) | **実効な共有文脈**(6 前提の ①②③ に対応) |
| **9-1**(参加テナント上限の計数) | **実効参加**の件数 |
| **9-2**(付与の有効性) | 付与は参加行に紐づくが、**評価時は実効参加**であること |
| **9-3**(招待の受諾・役割判定) | **実効グループ** ∧ 招待者の**実効 `admin`** |
| **9-4 / 9-4-A**(不変条件・グループ終了) | **実効 `admin`** |
| **11-2**(キャッシュ無効化の対象範囲) | 無効化の波及先は**実効参加**のテナントに限る |

**グループ終了後も参加行は維持する**(監査のため)。したがって**終了済みグループの制御資源は
「参加行がある」だけでは見えてはならない** — REQ:653・655・657 は終了後をすべて **404** と定めている。
**実効グループの条件を落とすとここが漏れる**(3 周目 P1-2)。

### 3-1. 候補案: RLS を防御層として採り、アプリ層の明示条件も残す(論点 3)

**採る。** ただし**アプリ層の明示的な `tenant_id` 条件を省かない**二重構成とする。

**RLS を採れる根拠**:

- **RLS は PostgreSQL のコア機能**(9.5 で導入・拡張不要)であり、Supabase 固有ではない。要件書 REQ:976 の
  「標準 PostgreSQL の範囲で使用し、ホスティング固有機能に依存しない」に適合する(**P-04 に違反しない**)
- ポリシーがなければ **default-deny**。`SELECT` だけでなく `INSERT` / `UPDATE` / `DELETE` に適用される
  (既存行は `USING`、新規・更新後の行は `WITH CHECK`)
- 要件書 REQ:824 は「テナント分離は**初日から全機能に適用**する」、REQ:823 は越境について
  「**内容・存在を含め参照できない**」を要求する。**アプリ層だけの強制は、管理画面・バッチ・将来の
  リポジトリ層・手書き SQL で条件を落とした瞬間に隔離を失う**

**アプリ層の条件を省かない理由**:

- **索引選択と計画安定化** — ポリシー式に頼らず `WHERE tenant_id = :t` を書くことで、
  `(tenant_id, …)` を左端に持つ複合索引が確実に使われる
- **意図の明示** — クエリを読んだだけでテナント境界が見える
- **RLS のバイパス経路が実在する** — 公式が「Superusers and roles with the `BYPASSRLS` attribute always
  bypass the row security system」「**Table owners normally bypass row security as well**」と明記している。
  RLS 単独に安全性を委ねられない

**却下した案**:

| 案 | 却下理由 |
| --- | --- |
| アプリ層強制のみ(RLS を使わない) | 条件の落としが即座に越境になる。DB 境界での deny がない |
| RLS のみ(アプリ層の条件を省く) | 索引選択がポリシー式に依存し、計画が不安定になる。バイパス経路で無防備 |
| Supabase の認可機能に寄せる | REQ:976 に反する(**P-04**) |

### 3-2. 候補案: ロールを 3 つに分ける(論点 3)

**テーブル所有者は既定で RLS をバイパスする**ため、**アプリ用ロールを所有者と分ける**。

**共有経路は 3-6 節の `SECURITY DEFINER` 関数に一本化する(敵対レビュー P2-1 の是正)**: 当初のロール表は共有集計用ロールへ「専用ポリシー」を置く形で書かれていたが、**3-6 節では共有専用ロールでの再接続を却下して関数方式を採用**しており、**同じ文書内で認可経路が二重**に読めた。**採用は関数方式のみ**。ロール表もそれに合わせる — 共有集計用ロールは**関数の所有ロールとしてだけ存在**し、**越境用の RLS ポリシーは作らない**。認可境界が 1 つであることは NFR-010 の全経路検証の前提でもある(REQ:823)。

| ロール | 用途 | RLS | DDL |
| --- | --- | --- | --- |
| **マイグレーション用**(テーブル所有者) | Alembic の適用・DDL | バイパスする(所有者) | 可 |
| **アプリ用** | 通常の読み書き | **従う**(`BYPASSRLS` を付与しない) | 不可 |
| **越境関数所有用**(`NOLOGIN` + **`BYPASSRLS`**) | **`SECURITY DEFINER` 関数の所有ロール**。FR-041 の共有集計(3-6 節)と FR-035/037 の管理経路(8-2-B 節)で**用途ごとに別ロールを立てる** | **バイパスする**(`BYPASSRLS`。**絞り込みは関数本体が行う**) | 不可 |

**`SECURITY DEFINER` だけでは RLS をバイパスしない(敵対レビュー 3 周目 P1-1 の是正)**:
当初は 3-6 節で「`SECURITY DEFINER` は所有者権限で走るため RLS をバイパスする」と書いていたが、
**これは「関数所有者」と「テーブル所有者」を混同していた**。上記のとおり公式が定めるバイパス条件は
**① superuser ② `BYPASSRLS` 属性 ③ テーブル所有者(かつ `FORCE ROW LEVEL SECURITY` 無し)** の 3 つで、
**関数所有者であること自体は条件ではない**。当初案では関数所有ロールがテーブル所有者でも `BYPASSRLS` でもなく、
さらに**全テーブルへ `FORCE ROW LEVEL SECURITY` を推奨**していたため、**共有関数も管理関数も越境行を読めない**
構成になっていた(**正しい規則は本節の 1 つ上の箇条に自分で引用していた** — 文書内の自己矛盾)。

**候補案**: **越境関数の所有ロールに `BYPASSRLS` を与え、`NOLOGIN` にする**。

| 事項 | 内容 |
| --- | --- |
| **バイパス手段** | **`BYPASSRLS`**。公式が「Superusers and roles with the `BYPASSRLS` attribute **always** bypass the row security system」と定めるため、**`FORCE ROW LEVEL SECURITY` を掛けても効く**(FORCE が拘束するのは**テーブル所有者**の免除であってこの属性ではない) |
| **到達経路の限定** | ロールを **`NOLOGIN`** にし、**誰にも `GRANT` しない**。**このロールの権限に到達する経路は `SECURITY DEFINER` 関数の呼び出しだけ**になる |
| **呼び出し許可** | アプリ用ロールへ**関数の `EXECUTE` だけを付与**する。テーブルへの直接権限は与えない |
| **用途ごとに分ける** | **共有集計用**(3-6 節)と**管理経路用**(8-2-B 節)で**別ロール・別関数群**にする。片方の穴がもう片方へ広がらない |

- **「常時バイパスロールを作らない」との関係**: ロールは**バイパス属性を持つが引き受けられない**
  (`NOLOGIN` + 無 `GRANT`)。**表現を「常時バイパス経路を作らない」へ改める** — 属性は持つので経路の話として書く

**`NOLOGIN` + 無 `GRANT` だけでは呼び出し経路を限定できない(4 周目 P1-4 の是正)**: **ロール継承と関数の ACL は
別物**である。**PostgreSQL は新規関数の `EXECUTE` を既定で `PUBLIC` へ付与する**ため、
「ロールを誰にも継承させない」ことは「関数を誰も実行できない」ことを意味しない。**所有者が `BYPASSRLS` なので
誤りの影響は通常の関数より大きい**。次を候補案の契約として固定する(物理 DDL の書式は正本化時でよい):

| 契約 | 内容 |
| --- | --- |
| **既定 `EXECUTE` の剥奪** | **`REVOKE ALL ON FUNCTION ... FROM PUBLIC`** を関数作成と**同一トランザクション**で行い、そのうえでアプリ用ロールへ `EXECUTE` を `GRANT` する。**作成 → REVOKE → GRANT を分割しない**(その隙間で `PUBLIC` が実行できる) |
| **名前解決の固定** | 関数に**安全な `search_path` を設定**する(または**全オブジェクトを完全修飾**する)。公式が `SECURITY DEFINER` 関数の要件として明記している |
| **スキーマ検査** | **関数所有者 / ACL(`PUBLIC` が含まれないこと)/ `search_path` / 所有ロールの `NOLOGIN`・`BYPASSRLS` / ロール所属**を検査するテストを置く。**NFR-019(b) の越境テストとは別に、構成そのものを検査する** |
| **一時スキーマ** | 書き込み可能スキーマ・一時スキーマを `search_path` から外す |

- **これは「唯一の越境経路」を成立させる前提条件**である。ACL と名前解決を固定しないと、
  関数本体の正しさに関係なく越境できる(REQ:823・825 の「**API 直叩きを含む全経路**」に反する)
- **`core-areas.json` の `tenant-isolation` へ含める対象**は、関数本体だけでなく
  **ロール定義・ACL・`search_path` の設定を含む**
- **却下案**: **関数所有ロールをテーブル所有者にする** → `FORCE ROW LEVEL SECURITY` を全テーブルへ掛ける
  方針と両立しない(所有者も拘束されるため)。かつ DDL 権限が越境関数に付いてしまう
- **却下案**: **専用の越境 RLS ポリシーを置く**(1 周目 P2-1 で却下した形) → 認可境界が関数とポリシーの
  2 つになり、NFR-010 の全経路検証が閉じない。**ただし当初はこれを却下した際にバイパス手段を与えず、
  結果として「読めない」構成にした**のが今回の誤りである
- **残余リスク**: `BYPASSRLS` を持つロールが 2 つ増える。**`NOLOGIN` と無 `GRANT` の維持が防壁**なので、
  **ロール定義の変更をコア領域の逐行確認の対象**にする(3-6 節・8-2-B 節の関数本体と同じ扱い)

- **superuser をアプリから使わない**
- **`ALTER TABLE ... FORCE ROW LEVEL SECURITY` を全テーブルへ掛ける**ことを推奨する — 所有者がうっかり
  アプリ経路で使われた場合でもポリシーに従わせる。公式が「a table owner can choose to be subject to row
  security with `ALTER TABLE ... FORCE ROW LEVEL SECURITY`」と定めている
- 共有集計用ロールの詳細は **3-5 節**(論点 12)

### 3-3. 候補案: テナント ID はトランザクション内で `set_config(..., true)` により渡す(論点 4)

**接続方式**:

| 経路 | 方式 | 理由 |
| --- | --- | --- |
| **マイグレーション** | **direct connection** | Supabase 公式が direct を migration・`pg_dump`・backup 向けと案内。prepared statement の制約を受けない |
| **アプリ(長寿命のステートレス FastAPI)** | **session pooler を第 1 候補**、transaction pooler を許容 | REQ:975 が「サーバーはステートレス・横断状態もプロセス外」を要求。長寿命プロセスなので session pooler が素直 |

**規律(transaction pooler でも成立する形に統一する)**:

1. **明示した 1 トランザクションの最初**に `SELECT set_config('app.tenant_id', :tenant_id, true)` を発行する
2. ポリシー側は `current_setting('app.tenant_id', true)` を読む
3. **`SET app.tenant_id = …` と `set_config(…, false)` は使わない** — セッション状態になり、transaction
   pooling では物理接続が別クライアントへ再利用されるため**次の利用者へ漏れる**
4. **autocommit で `set_config` と本クエリを別トランザクションにしない** — transaction-local は
   コミット / ロールバックで戻るため成立しない
5. SQLAlchemy は**リクエストごとに `Session` / `AsyncSession` を作り、`begin()` の中で最初に発行**する。
   Session をテナント横断・リクエスト横断で共有しない(`AsyncSession` は複数 asyncio task 間で共有不可)

**第 3 引数の意味は公式で確認済み** — 「If `is_local` is `true`, the new value will only apply during the
current transaction」(`set_config(setting_name text, new_value text, is_local boolean)`)。

**この規律は検査できる**: RLS が default-deny なので、**`set_config` を発行せずにクエリすると 0 行になる**。
「テナントコンテキストを設定しないと何も見えない」ことを結合テストの前提条件にできる。

### 3-4. 候補案: 一意制約はテナント内に閉じ、FK は複合参照にする(論点 2)

**動かせない事実**(PostgreSQL 公式 `https://www.postgresql.org/docs/17/ddl-rowsecurity.html`):

> **Referential integrity checks, such as unique or primary key constraints and foreign key references,
> always bypass row security** to ensure that data integrity is maintained.

> Operations that apply to the whole table, such as `TRUNCATE` and `REFERENCES`, are not subject to row security.

つまり**一意制約と外部キーは RLS を必ず貫通する**。要件書 REQ:823 が「**内容・存在を含め参照できない**」を
要求しているため、素直に設計すると**制約違反エラーが他テナントの行の存在を漏らす**。

#### 規則 1: 一意制約はテナント内に閉じる

- **テナントに属するエンティティの一意制約は、必ず `tenant_id` を先頭に含める**
  (`UNIQUE (tenant_id, …)`)。**グローバル一意制約を置かない**
- **代理キー(主キー)は衝突しない値域を使う**ため、この規則の対象は「業務的な一意性」に限る
- **例外はテナントに属さないもの**だけ — テナント自身のテーブル・システム固定語彙・付録C の設定値
- **この規則は要件と衝突しない**: 要件が一意性を求める箇所(スタメン記憶は「チームにつき最後の 1 件」
  REQ:350 / カルテ所見は「選手 × カルテ種別」REQ:764 / 付与は「グループ × 自テナント」REQ:480)は
  **いずれもテナントかグループの内側**にある。逆に**背番号は明示的に「DB の一意制約は張らない」**
  (REQ:339 / **P-15**)ので対象外

#### 規則 2: FK は禁止しない。テナント内 FK は複合参照にする

**FK 一般の禁止は誤り** — FR-041 の制御資源(グループ・参加・付与)は**複数テナントに跨る関係を持つのが
要件**であり(REQ:824 が「記録・集計とは別のクラス」と定める)、FK を禁じると要件が表現できない。

代わりに**漏洩経路を個別に閉じる**:

| 手段 | 内容 |
| --- | --- |
| **(a) 複合参照** | テナント内の FK は `FOREIGN KEY (tenant_id, game_id) REFERENCES game (tenant_id, id)` の形にする。**参照側の `tenant_id` は自テナントに固定される**ため、他テナントの `id` を渡しても「(自テナント, その id)」という**存在しない組み合わせ**になる。エラーは「**自テナントに無い**」ことしか示さず、他テナントの存在を漏らさない |
| **(b) 事前認可** | 参照値としてアプリ層へ渡す ID は、**自テナントに属することを検証済みのものだけ**にする。検証は RLS 下の `SELECT`(= 見えなければ存在しないのと同じ)で行う |
| **(c) エラーの一律秘匿** | 制約違反の詳細(制約名・値・テーブル名)を**クライアントへ返さない**。FR-034 が「**いずれも理由コードを返さない**」(REQ:623)と定めているのと同じ扱いにする。ログには残す |
| **(d) 越境 FK は「存在が秘匿対象でない」クラスに限る** | 制御資源の参照先(グループ・参加テナント)は**当事者が既に知っている**情報であり、読み取り粒度も REQ:645-651 が定めている。詳細は 3-5 節 |

**残余リスク**: `TRUNCATE` と `REFERENCES` 権限は RLS の対象外。**アプリ用ロールに `TRUNCATE` と
`REFERENCES` を与えない**ことで運用上塞ぐ(GRANT の設計は正本化タスクで詰める)。

### 3-5. 制御資源のデータ表現(論点 12)

**制御資源は記録・集計とは別のクラス**である。要件書 REQ:824 が「これは他チームの記録・集計を参照する
権限ではなく、**参加・付与の状態そのものを扱う権限**である(制御資源は記録・集計とは別のクラス)」と
定め、管理者操作のスコープが**グループ単位に及ぶ**ことを認めている。

したがって**制御資源のテーブルはテナントに属さない**。RLS ポリシーは `app.tenant_id` 単独では書けず、
「**自テナントが実効参加を持つ実効グループの行だけ見える**」という形になる(**述語は 3-0 節が正**)。
**「参加行が `active`」だけにしてはならない** — グループ終了後も参加行は維持するため、**終了済みグループの制御資源が RLS 上は見え続ける**(3 周目 P1-2)。REQ:653・655・657 は終了後を**すべて 404** と定める。

| エンティティ | 主な属性 | 一意性 | 越境 FK |
| --- | --- | --- | --- |
| **グループ** | 状態(`active` / 終了。**終了は不可逆** REQ:704)・名称(利用者入力 → NFR-023 の対象 REQ:928) | グループ内で自明 | — |
| **参加** | グループ / テナント / 役割(`admin` / `member`)/ 状態(`active` / 離脱)/ **参加日時**(REQ:648 が「参加日時・役割は `admin` のみが見られる」と定める) | **(グループ, テナント) で 1 件と読めない**(論点 6 — 9 節で扱う) | **あり**(グループ ↔ テナント) |
| **付与** | グループ / テナント / 粒度 3 種のフラグ(`成績` / `選手個別` / `書き出し`。**既定はすべて非共有**) | **(グループ × 自テナント)で 1 件**(REQ:114・480) | **あり** |
| **招待** | グループ / **コードのハッシュ** / 有効期限 / 状態(未消費 / 消費済 / 失効)/ 発行時指定の初期役割 | — | あり |

**越境 FK を許す根拠**(3-4 節の規則 2-(d)): 参照先の**存在自体が秘匿対象でない**。参加しているグループの
一覧は当事者が読めるし(REQ:647)、メンバー一覧も同じ実効グループの実効参加テナントが読める
(REQ:648)。**参加していないグループの存在は「誰も読めない・404」**(REQ:651)なので、**FK の参照先を
知り得るのは既に参加している当事者だけ**である。

**読み取り粒度は REQ:645-651 の表に一致させる**:

| 制御資源 | 読める者 | 内容の制限 |
| --- | --- | --- |
| 自テナントが参加しているグループの一覧 | そのテナント | — |
| グループのメンバー一覧 | 同じ**実効グループ**の**実効参加**テナント(3-0 節) | **テナント名のみ**。参加日時・役割は `admin` のみ |
| 各メンバーの付与状態 | 同上 | **どの粒度を出しているかは見える**(相互性の判定に必要)。中身は認可行列に従う |
| 招待の一覧・状態 | **`admin` のみ** | **コード本体は発行時に一度だけ表示し、以後は表示しない**(ハッシュ保存) |
| 参加していないグループの存在 | **誰も読めない** | **404** |

→ **データモデル上の含意**: 参加日時・役割・招待は**同じ行に混在させても読み取り粒度で分けられる**が、
**「テナント名のみ」を返す経路と「参加日時・役割」を返す経路を別のクエリとして持つ**必要がある。
付与状態は**粒度フラグの有無が相互性の判定に必要**なので、`admin` でなくても読める。

### 3-6. 候補案: 共有集計は `SECURITY DEFINER` の制限関数を唯一の越境経路にする(論点 12)

**通常アクセスと共有アクセスの実行経路を分離する。** 3-3 節の通常経路(`app.tenant_id` 単独)では
共有集計を読めず、逆にバイパスロールを使うと既定拒否(REQ:586)を迂回してしまう。

**3 候補の評価**:

| 案 | 評価 |
| --- | --- |
| **(1) 共有専用ロールで接続し直す** | プールが分かれて接続数が増える。**ロール切替の漏れが即座に越境**になる(fail-open の方向) |
| **(2) `SECURITY DEFINER` の制限関数(採用)** | **越境の経路が関数という 1 点に集約される**。通常アクセスのポリシーは `app.tenant_id` 単独のままにできる。関数の内側で 2 層認可を明示的に検査し、**返す列を集計値に限定**すれば認可行列(REQ:625-637)と構造的に整合する |
| **(3) 追加コンテキスト(`app.shared_group_id` 等)をポリシーへ渡す** | ポリシー式が複雑化し、**アプリ用ロールが常に越境可能な状態**になる。コンテキストの設定漏れ・誤設定が越境になる(fail-open) |

**(2) を採る理由**: **境界を 1 点に集約できる**こと。**`SECURITY DEFINER` 自体は RLS をバイパスしない** —
バイパスは 3-2 節で定めた**関数所有ロールの `BYPASSRLS` 属性**による(3 周目 P1-1 の是正)。
そのロールは `NOLOGIN` で誰にも `GRANT` しないため、**バイパス権限に到達できるのは関数の中だけ**であり、関数のシグネチャが返す列を集計値に限定すれば、
「FR-020〜032 のすべてが共有グループ経由では不可(404)」(REQ:625-637)という認可行列を**物理的に**
満たせる。**生記録・カルテを返す経路を持たない**ことがコードの形として見える。

**関数が必ず検査する前提条件(要件書 REQ:597-606 の 6 項目に一致させる)**:

1. **指定されたグループが `active`**(終了していれば除外)
2. **要求元と対象テナントの参加がともに `active`**(離脱済みは除外)
3. **両テナントが無効化されていない**(FR-035 の無効化 → 除外)
4. **要求元テナントが同一の付与を、指定されたグループで出している**(**相互性 = 見るには出す**)
5. **自テナント自身が集合に含まれる場合は、付与・相互性の条件を適用しない**。ただし**同時比較表示上限には数える**
6. **要求された集合の要素数が同時比較表示上限以下**(超えていれば**要求全体を 400 で拒否**する。切り捨てない)

**前提条件だけでは足りない — 認可行列を第 2 層として検査する(敵対レビュー P0-2 の是正)**:
上記 6 項目は要件書が「**全行に掛かる前提条件**」と呼ぶもので、**その直後の認可行列(REQ:610-620)が
資源の粒度ごとに追加条件を課す**。当初案は 6 前提だけを「関数が必ず検査する前提条件」として列挙し、
**認可行列の層を落としていた**。とくに前提 ④ は「**要求元**が付与を出している」(相互性)だけなので、
**対象テナント側が付与しているかを誰も検査しない**状態になっていた。これは
「対象側が非共有でも要求元さえ付与すれば返し得る」ことを意味し、REQ:823「**内容・存在を含め
参照できない**」に反する。

**候補案**: 関数は **6 前提を満たした要素それぞれについて、要求された粒度の行を認可行列から引き、
`相手の付与 ∧ 要求元の付与` の双方を検査する**。

| 要求粒度 | 対象テナント側 | 要求元側 | 満たさないとき |
| --- | --- | --- | --- |
| **チーム集計**(打撃・投球の率指標) | `成績` を付与 | `成績` を付与 | **除外** |
| **チーム概要**(試合数・勝敗等) | `成績` を付与 | `成績` を付与 | **除外** |
| **選手個別**(実名つき) | `選手個別` ∧ `成績` を付与 | 同等を付与 | **除外** |
| ↳ **行フィルタ** | **`kind = 'self'` かつ在籍区分が現役(`active`)の選手だけ**(REQ:483「自テナント所有**かつ在籍中**」。4 周目 P1-3 の是正)。**`kind` だけでは現役と OB を区別しない** | — | OB は結果に現れない |
| ↳ **チーム集計には掛けない** | チーム集計は**OB が出場した過去試合も含める**のが正。**全共有集計へ一律に在籍フィルタを掛けてはいけない** | — | — |
| **共有集計のエクスポート** | `書き出し` ∧ 当該データ種別を付与 | 同等を付与 | **除外** |
| **1 球単位の生記録**(FR-031 の 88 列 CSV を含む) | — | — | **付与によらず 404** |
| **カルテの所見** | — | — | **付与によらず 404** |
| **第三者として記録した対戦相手データ** | — | — | **付与によらず 404**(7-1 節の `kind = 'self'` で構造的に除外) |
| **身体プロフィールの分布** | — | — | **本版では共有しない・404** |

- **粒度ごとの行を関数の内部表として持つ**。**条件を関数本体の `if` へ散らさない**
  (認可行列は要件書 REQ:610-620 が正であり、**表の形のまま写す**方が追随漏れを検出しやすい)
- **前提 ⑤ の例外は維持**する — 自テナント自身が集合に含まれる場合は付与・相互性を適用しない
  (自分のデータ)。ただし**同時比較表示上限には数える**
- **下段 4 行(404 側)は関数が「返す経路を持たない」形**にする。付与の値で分岐させない

**指定グループ以外の付与を参照させない**: 関数は **`group_id` を必須引数に取り、内部で当該
`group_id` に紐づく付与だけを見る**。他のグループの付与は関数の問い合わせ範囲に入らない。

**要求の形**: 「すべての共有リソース要求は **①グループ ②対象テナントの集合**を明示する」(REQ:597)。
関数のシグネチャもこれに合わせる(グループ + テナント集合 + 粒度)。

**エラー秘匿**(REQ:623):

- **集合要求の要素は「除外」** — 結果に現れないだけで、0 件と権限なしを応答から区別できない
- **単一リソースを名指しした要求は 404**
- **いずれも理由コードを返さない** → **関数は除外した理由を返さない**。ログには残す

**残余リスク**: **関数の実装が主要な防壁になる**(**第三者として記録した対戦相手データだけは 7-1 節の `kind = 'self'` により構造的に除外される**ため、関数の条件分岐に依存しない)。したがって ① この関数を含む変更は**コア領域の
逐行確認の対象**にすべき(`core-areas.json` の `paths` 充填時に `tenant-isolation` へ含める候補)
② **6 前提と認可行列の各行それぞれに越境テストを持つ**(NFR-019(b) の越境テスト。**とくに「対象側は非共有・要求元だけ付与」の組み合わせ** — P0-2 で落としていた経路)③ 関数の外側で越境できる
経路(バイパスロール・所有者)を運用で塞ぐ(3-2 節)。

**却下案の記録**: (1) と (3) は上表の理由で採らない。とくに (3) は「設定漏れが越境になる」方向の
失敗であり、fail-closed の原則に反する。

## 4. 永続化上の表現と識別子のライフサイクル(論点 1・9)

### 4-1. 前提(ADR-003 が固定済み — 本節は再決定しない)

- **確定イベントを持ち、現在状態・成績は導く**。契約の単位は「1 遷移」で `input` = 事前状態 + 履歴文脈 +
  次イベント 1 件(ADR-003 `:93-104`)
- **後段集計 (β) は宣言モデルから SQL 式を生成して DB 側で実行**する(Python で全行畳み込みは NFR-005 違反)
- **履歴文脈は種別 + 状態差分**を持つ。**差分を落として種別だけ持つ設計は不可**(連続 undo が実行不能 — **P-57**)
- **語彙スナップショットは対象計算の入力**として渡す。**写像テーブルに焼き込まない**(**P-40**)

**本節が決めるのは永続化上の表現だけ**である。

### 4-2. 候補案: イベント表を正とし、プレイ行を投影として持つ(論点 1)

要件は 2 方向に引いている:

| イベント側を示すもの | プレイ行という実体を要求するもの |
| --- | --- |
| 「**確定イベントは即時に DB へ永続化**」(REQ:953)/「正本は **DB の 1 系統のみ**」(REQ:147) | FR-007 が**プレイ行の論理削除・任意位置への挿入・楽観ロック**を要求(REQ:232-238) |
| 未同期キューは「**操作イベントの順序付き列**」(REQ:282。**プレイ行ではない** — **P-24**) | FR-013 が挿入位置を「**プレイ番号**」で指定(REQ:305) |
| サイドカー結合キーが「**試合ID + 記録権世代 + イベント連番**」(REQ:1182) | NFR-005 が **DB 側絞り込み・集計**を要求(毎回リプレイは全件読み込み型) |

**候補案**: **操作イベント表を正本とし、プレイ行を投影(materialized projection)として持つ**。

| 表 | 位置づけ | 主なキー |
| --- | --- | --- |
| **操作イベント** | **正本**。確定と同時に追記する。訂正は**同一連番の改訂版**、取消は**墓標イベント**(REQ:288) | (試合, 記録権世代, 連番)が一意 / べき等キーが一意 |
| **プレイ行** | **投影**。イベントから決定的に再生成できる。論理削除フラグ・楽観ロック用の版・**プレイ番号**(表示と挿入位置指定)を持つ | **行識別子**(サロゲート)。**`(試合, プレイ番号)` は一意にしない**(下記) |

- **`(試合, プレイ番号)` を一意キーにしない(敵対レビュー P1-1 の是正)**: 12-3 節で
  **旧 `プレイの番号` は非一意**であり**重複行は 2 行のまま取り込む**と決めた(REQ:755・758)。
  一方で投影表のキーを `(試合, プレイ番号)` のままにしていたため、**同じ試合・同じプレイ番号の 2 行を
  識別できず**、子の走者行からの参照も曖昧になっていた。**行識別子(サロゲート)を主キーにし、
  プレイ番号は表示・挿入位置指定の属性として持つ**
- **重複時の順序を表現できる形にする** — 移行由来の重複は**取り込み順序**(12-3 節の行識別子)で
  安定した並びを与える。**プレイ番号だけで並べない**
- **走者行など子の参照は行識別子へ向ける**(プレイ番号へ向けない)
- **論理順序と区間境界もプレイ番号に依存させない(3 周目 P1-6 の是正)**: 行識別をサロゲートにしただけでは
  足りない。**任意位置挿入**(REQ:236)は「プレイ番号」、**出場区間の境界**(6-2 節)は「イベント連番または
  プレイ番号」、**状態補正**(6-3 節)は「再計算の起点」としか書いておらず、**プレイ番号は非一意**なので
  **重複番号の間に挿入したときの前後関係と、どちらの行から再計算するかが決まらない**

| 用途 | 何で表すか |
| --- | --- |
| **操作順**(同期・undo 用) | **(記録権世代, 同期連番)**。クライアントがキュー追記時に単調増加で採番し、**欠番検知**に使う(REQ:282)。**undo は操作順の逆順**でよい(ADR-003) |
| **論理順序**(プレイ投影・交代境界用) | **同期連番とは別の順序値**を持つ。**任意位置挿入**(REQ:236)は「後から生成したイベントを過去の論理位置へ置く」操作なので、**到着順とは一致しない**。具体の順序ラベル方式(整数間隔・有理数・LexoRank 等)は **(B)** |
| **出場区間の境界** | **イベント連番**で持つ(**プレイ番号では持たない**)。REQ:272 の「どのプレイ時点で誰 → 誰」はイベント側の時点で表せる |
| **再計算の起点**(状態補正・undo) | **イベント連番**。**行識別子でもプレイ番号でもない** |
| **表示・挿入位置の指定(利用者向け)** | **プレイ番号**。**一意性を仮定しない表示用の値** |
- **操作順と論理順序を同一にしてはならない(4 周目 P1-1 の是正)**: 3 周目に「論理順序も出場区間の境界も
  再計算の起点も**イベント連番へ**」とまとめたが、**イベント連番は同期の到着順**(欠番検知のための単調増加)
  であり、**過去位置への挿入や退避イベントの取り込みでは末尾に付く**。そのまま論理順序に使うと
  **挿入したプレイが末尾に再生される**。REQ:236 は任意位置への挿入と下流再計算を要求している
- **境界と再計算の起点は「論理順序」側**を使う(出場区間の境界・状態補正の起点)。**同期連番は同期と undo に限る**


- **移行由来の重複プレイ番号でも順序が決まる** — 移行行にも**イベント連番を与える**(下記 P1-7 の是正)ため、
  同じプレイ番号の 2 行は**連番で区別され順序が付く**

- **「プレイ行の論理削除」は投影側のフラグ**であり、**正は墓標・改訂イベント**。フラグだけを書き換える
  経路を作らない(4.0-2「正本は DB の 1 系統のみ」と整合)
- **「任意位置への挿入」はプレイ番号の採番(投影側)**で表す。**イベント連番は世代内で単調増加のまま**
  動かさない。退避イベントの取り込みは「**現行世代の連番として採番し直す**」(REQ:305)ので同じ構造に乗る
- **下流再計算は投影を作り直す**。交代イベントの時点が保持されるため、再計算後も各プレイが**当時の
  出場選手**に紐づく(REQ:234)
- **投影はキャッシュではなく「常に再計算可能な導出データ」**という位置づけ(REQ:954)。**再計算不能な
  正本として持たない**(**P-07**)

**却下案**:

| 案 | 却下理由 |
| --- | --- |
| プレイ行だけを持つ(イベント表を持たない) | 墓標・改訂・べき等キー・世代内連番を置く場所がなくなり FR-012 の同期プロトコルが成立しない。**P-24** に接触 |
| イベント表だけを持つ(投影を持たない) | FR-007 の挿入位置指定・楽観ロック・論理削除の表現が持てず、集計が毎回リプレイになり **NFR-005 違反**(**P-06**) |
| 投影を「正」に格上げしてイベントを監査ログ扱いにする | REQ:147「正本は DB の 1 系統のみ」に反する。訂正の由来が追えない |

### 4-3. 候補案: 識別子を 5 種に分け、役割を混ぜない(論点 9)

| 識別子 | 生成者 | 一意性の範囲 | 役割 | 典拠 |
| --- | --- | --- | --- | --- |
| **べき等キー** | **クライアント** | 再送を同一視できる範囲 | **再送の二重適用を防ぐ**。「同じ操作か」の判定 | REQ:282 |
| **イベント連番** | **クライアント**(採番と追記が不可分) | **(試合, 記録権世代)内で単調増加** | **順序と欠落**の判定(prefix コミット)。墓標が当該連番を消費 | REQ:282-288・299 |
| **記録権世代** | **サーバー** | 試合内 | 引き継ぎのたびに更新。**正史は世代の連結** | REQ:299 |
| **一時 ID(その場登録)** | **クライアント(UUID)** | グローバル | 断中の選手登録。**同期時にサーバーが正式 ID を確定し参照を置換** | REQ:341 |
| **エンティティの内部 ID** | **サーバー** | テーブル内 | 選手 ID は**不変・内部**。名前・背番号は表示用属性 | REQ:338・342 |

**混ぜてはならない理由**:

- **べき等キーと連番は判定の目的が違う** — 前者は「同じ操作か」、後者は「順序と欠落」。1 つにまとめると
  「同じ連番の改訂版」(REQ:288)が表現できない(改訂版は**新しいべき等キー**を持ち**同じ連番**を使う)
- **連番を試合グローバルにしない**(**P-25**)。世代内スコープが正で、**世代なしでは連番が一意にならない**
- **サイドカー結合キーは (試合ID, 記録権世代, イベント連番) の合成**であり、独立した識別子を新設しない
  (**P-02** の「88 列に列を足さない」と同じ発想でキーを増やさない)

**一時 ID の置換について**:

- 置換は「**参照の置換**」であって行の作り直しではない。**置換の記録を残す**(どの一時 ID がどの正式 ID に
  解決されたか)。これは FR-035 の「**統合前の帰属を復元できる情報を保持する**」(REQ:719)と同型の要求で、
  同じ構造で扱える
- **物理型は (B) 論点 13** に送るが、**一時 ID は UUID で確定**している(REQ:341 が「クライアント生成の
  一時 ID(UUID)」と明示)

### 4-4. 履歴文脈の保存形

**取消可能な操作のスタックは (種別, 状態差分) の列**として持つ。

- NFR-019(REQ:901)が比較面に「**取消可能な操作のスタック全体 — 各要素は種別と差分。先頭 1 件だけでは
  ない**」を要求している
- **差分を落として種別だけ持つと連続 undo が実行不能**になる(ADR-003 `:29` — **P-57**)
- **実行時のスタック長に上限はない**(FR-006 の連鎖は空になるまで続く)。ADR-003 の検査上の上限 `D` は
  **保証範囲の上限にすぎない**ので、**永続化側に固定長を仮定しない**
- **undo 自身は取消可能な操作にしない**(REQ:227)。状態補正は **FR-040 が Should** なので、
  **Must 前提として構造に組み込まない**(**P-58**)

## 5. 試合・毎球データ・操作イベント(ブロック 1 ①)

**共通規則**(3 節・4 節で決めたもの): テナント内 FK は**複合参照**(`(tenant_id, …)`)/ 一意制約は
**テナント内に閉じる** / イベント表が正本でプレイ行は投影 / 識別子は 5 種を混ぜない。

### 5-1. 試合(FR-001・4.0-1)

### 5-2. 毎球データ = プレイ行(投影。FR-002 / 003 / 004)

**走者は別表に正規化する**(候補案):

| 属性 | 内容 |
| --- | --- |
| プレイ | 親(複合参照) |
| 塁 | 一塁 / 二塁 / 三塁 |
| 走者(選手 ID 参照) | **選手 ID で参照**。名前・背番号は表示用属性(**P-13**) |

| **責任投手(出塁させた投手 ID)** | **走者ごとに保持する**。「登板中に生還した走者」で導く旧方式は採らない(**P-33**) | 

- 一意性: **(プレイ, 塁)** で 1 件
- **列に 3 枠を並べない理由**: 走者は 0〜3 で可変であり、**走者ごとに責任投手を持つ**ため列が塁数 × 属性数に
  膨らむ。正規化すると「走者状況別・得点圏成績」の集計が **DB 側の GROUP BY** で書ける(NFR-005)
- 旧システムは「打順番号(0 = 不在)+ 氏名文字列 + 状況ラベル」のトリプレット×3 塁で、**衝突検出なしの
  後勝ち上書き**だった。**新設計では (プレイ, 塁) の一意性で同一塁の重複を構造的に防ぐ**

### 5-3. 操作イベント(正本。FR-012・3 章用語)

| 属性 | 内容 | 典拠 |
| --- | --- | --- |
| 試合 / **記録権世代** / **連番** | (試合, 世代)内で単調増加。**世代なしでは一意にならない** | REQ:282・299 |
| **べき等キー** | クライアント生成。再送の二重適用を防ぐ | REQ:282 |
| 種別 | **Must は 6 種**(毎球入力 / undo / 交代 / タイブレーク開始 / 試合終了宣言 / 選手のその場登録)。**状態補正は FR-040 採用時のみ**で、**Must 前提として構造に組み込まない**(**P-58**) | REQ:117・164 |
| ペイロード | 種別ごとの内容。**取消可能な操作(確定プレイ・状態補正)は状態差分を持つ**(4-4 節・**P-57**) | REQ:901 |
| **置換・墓標の状態** | **同一連番の改訂版**(新しいべき等キー)で旧版を置換 / **墓標イベントが当該連番を消費** | REQ:288 |
| 適用水位 | **連番に欠落があればそれ以降を適用しない**(prefix コミット)ため、どこまで適用済みかを保持 | REQ:284 |

**一意性の設計**(候補案):

- **べき等キーは一意**
- **(試合, 世代, 連番) は「有効な行が 1 件」** — 改訂版があると同じ 3 つ組の行が複数になるため、
  **`WHERE 置換されていない` の部分一意インデックス**で表す。**述語が固定条件なのでプランナが含意を
  認識できる**(Web 調査 6-2 節 — パラメータ化された述語では使えない場合がある)
- **下位番号の欠番・重複それ自体を拒否しない** — prefix コミットは「欠落があればそれ以降を適用しない」
  であり、**行の存在を拒否する規則ではない**

**履歴文脈は別表を持たない**(候補案): 「取消可能な操作のスタック」は**未取消の取消可能イベントを
連番降順に並べたもの**として導出できる。各要素の (種別, 差分) はイベント自身が持つ(4-4 節)。
**別表に写すと 2 つの正本ができる**(REQ:147 に反する)。

## 6. 記録権・交代・状態補正・退避・適用規則スナップショット(ブロック 1 ②)

### 6-1. 記録権は「世代」を行として持つ(FR-013)

| 属性 | 内容 | 典拠 |
| --- | --- | --- |
| 試合 / **世代番号** | (試合, 世代番号)で一意。**引き継ぎのたびに更新**。試合の正史は**世代の連結** | REQ:299 |
| 保持端末 | 1 試合につき 1 端末 | REQ:299 |
| **確定水位** | 照合は(**保持端末・世代・確定水位**)の 3 点 | REQ:301 |
| 付与 / 失効の時刻 | 失効していない行が**現世代** | REQ:299 |

- **現世代は「失効していない行が 1 件」**として表す(**`WHERE 失効していない` の部分一意インデックス**。
  5-3 節と同じ手法)。**「同時に複数の緊急引き継ぎ要求があった場合、後発は失敗する」**(REQ:302)は、
  **この一意制約がサーバー側の直列化の防壁**になる形で満たす
- **バックアップ復元後のフェンス**(REQ:819「全試合の記録権世代を無効化して新世代を発行」)は、
  **世代を行として持つことで自然に表現できる** — 現世代を一括で失効させ、新世代を発行する
- **一意制約はテナント内に閉じる**(試合がテナントに属するため複合参照で閉じる)

### 6-2. 交代はイベントとして永続化し、投影として「出場区間」を持つ(FR-011)

**旧システムは交代をイベントとして持たず、スタメン JSON の上書きと氏名列の変化からしか読み取れなかった**
(**P-27** が「オーダー表の上書きで表す」を禁止)。

| 表 | 内容 | 典拠 |
| --- | --- | --- |
| **交代イベント**(正本) | 操作イベントの種別の 1 つ。**何回・どのプレイ時点で誰 → 誰**。**DH 解除時の打順配置を明示指定**できるペイロードを持つ。**加えて出場する選手の「当時の背番号」をスナップショットとして持つ**(7-3 節・敵対レビュー P1-1 の是正) | REQ:272・275・340 |
| **出場区間**(投影) | 試合 / 打順枠または守備位置 / 選手 / **有効開始と有効終了**(イベント連番またはプレイ番号) | REQ:234 |

- **投影として「出場区間」を持つ理由**: 「下流再計算で**交代イベントの時点が保持され**、再計算後も
  各プレイが**当時の出場選手**に正しく紐づく」(REQ:234)を、**プレイ行ごとに選手を焼き込まずに**
  満たすため。区間との突合で当時の出場選手が決まる
- 一意性: **(試合, 打順枠, 有効開始)** で 1 件。区間の重なりは**アプリ層で検証**する
  (排他制約 `EXCLUDE` は範囲型が必要で、`REFERENCES` と同様に RLS の対象外になるため 3-4 節の
  漏洩経路の検討が要る。**(B) として実装時に判断**)
- **移行データでは交代を復元しない**(**P-44**)。出場区間は**移行試合では「不明」を許容**する
  (REQ:767・545)。「不明」を表せる形にする(区間が存在しないことと、区間が不明であることを区別する)

### 6-3. 状態補正は差分を持つイベント(FR-040・**Should**)

| 属性 | 内容 | 典拠 |
| --- | --- | --- |
| 対象 | 回・表裏・得点・S / B / アウト・打順・走者 | REQ:321 |
| **補正前 → 補正後の差分** | **履歴として保持**し後から追跡できる | REQ:324 |
| 位置 | 以降の再計算の起点 | REQ:323・326 |

- **操作イベントの種別の 1 つ**として持つ(別表を作らない)。4-4 節の「取消可能な操作は状態差分を持つ」に
  そのまま乗る
- **履歴に残らない直接上書きの経路を作らない**(**P-28**)。旧システムは「状況変更・タイブレークは
  メモリの `data_list` のみ変更で DB は書かない」= **履歴に残らない生の上書き**だった
- **FR-040 は Should** なので、**構造上の必須にしない**(**P-58**)。種別の語彙に含めるが、未採用なら
  その種別のイベントが発生しないだけ

### 6-4. 退避イベントは原本を残し、取り込みは新規行として採番する(FR-013・FR-035)

| 属性 | 内容 | 典拠 |
| --- | --- | --- |
| 試合 / **旧世代** / 元の連番 | どの世代のどの連番だったか | REQ:303 |
| ペイロード | **原本のまま**。破棄しない | REQ:303 |
| 状態 | 未取り込み / 取り込み済み / (取り込まないと判断した) | REQ:303-305 |
| **取り込み先** | 取り込んだ場合、**現行世代で新規採番した操作イベント**への参照 | REQ:305 |

- **取り込みは「操作者が挿入位置を指定し、現行世代の連番として採番し直す」**(REQ:305)。
  **末尾採番で自動取り込みしない**(**P-31**)
- **原本の行は消さない** — 取り込み後も退避行を残し、取り込み先への参照を持つ。物理削除しない原則
  (4.0-2)と、**管理コンソールでの閲覧・書き出しが Must**(REQ:722)であることの両方を満たす
- **「破棄されず退避」が要件**(REQ:303)。取り込まない判断をしても行は残る

### 6-5. 規則セットと適用規則スナップショット(FR-014・付録F)

| 表 | 内容 | 典拠 |
| --- | --- | --- |
| **規則セット** | 規定イニング数 / **コールド条件(段の配列 `[{点差, 適用開始回}]`)** / 延長上限 / タイブレーク(`{発動回, 走者配置, 先頭打者規則}`)/ DH 制 | 付録F-1 REQ:1231-1237 |
| **試合区分デフォルト** | システム管理者が管理(FR-037) | REQ:317・1239-1246 |
| **大会名に紐づく規則** | チームが設定可能 | REQ:312 |
| **試合単位の上書き** | 試合に持つ | REQ:312 |

- **適用優先は「試合単位の上書き > 大会名の規則 > 試合区分のデフォルト」**(REQ:312)。
  **保存時に解決してスナップショットを試合へ書く**(**参照のみにしない** — **P-30**)。
  これにより「規則マスタの事後変更は確定済み試合に遡及しない」(REQ:144)が構造で保証される
- **不正な規則値は保存できない**(REQ:316 — 「コールド適用回 > 規定イニング等の矛盾は検証エラー」)。
  **段の配列の整合は DB の `CHECK` では表現しきれない**ため、**アプリ層の検証を保存経路の必須ステップに
  する**(**(B) として実装時に、DB 側でどこまで表現するかを判断**)
- 構造化された値(段の配列・タイブレーク設定)は **JSONB を候補とする**。ただし
  **頻繁な絞り込み・結合・GROUP BY のキーは正規化列に置く**(Web 調査 6-2 節)。規則は
  **試合単位で読むだけ**で集計キーにならないため JSONB が向く

## 7. チーム・選手・在籍区分・スタメン・対戦相手チーム(ブロック 2 / 論点 5・8)

### 7-1. 候補案: 「チーム」を 2 つの表に分ける(論点 5)

要件は**テナントと対戦相手チームレコードを別概念と明言**している(REQ:391「FR-035 のチーム登録
(テナント発行)と FR-039 の相手チームレコードは**別概念**」)。さらに:

- **対戦相手チームレコードはテナント内のレコードでテナント間で共有されない**(REQ:112・392・**P-19**)
- **在籍区分は対戦相手チームレコードの選手にも適用される**(REQ:361)
- **紅白戦は先攻・後攻が同一チーム**(REQ:179)
- **自テナント自身も試合の一方の当事者**になる

| 表 | 内容 |
| --- | --- |
| **テナント** | ログイン主体。認証情報・有効/無効を持つ(8 節) |
| **チームレコード** | **テナント内のレコード**。自テナントを表す行と、対戦相手を表す行の**両方**を持つ |

**候補案**: **「試合 → チーム」の参照はすべてチームレコードを指す**。テナントは**チームレコードの
`tenant_id` として現れるだけ**で、試合から直接参照しない。

- **自テナントを表すチームレコードを 1 件持つ**(テナント作成時に生成)。これにより:
  - 紅白戦は**先攻・後攻が同じチームレコードを指す**だけで表現できる(5-1 節)
  - **在籍区分は「チームレコードに属する選手」に一律適用**でき、自チームと相手チームで分岐しない(REQ:361)
  - 試合の当事者が自テナントか相手かは、**チームレコードの `kind` で決まる**(下記)

**自他の判別は `tenant_id` ではできない(敵対レビュー P0-1 の是正)**: 自テナント行も対戦相手行も
**同じテナント配下のレコード**なので `tenant_id` は両方とも自テナントに一致する。当初案は
「`tenant_id` と自テナントを比較」と書いていたが、**この比較は全行で真になり判別できない**。
要件は判別を明確に要求している — 対戦相手チームレコードは「**FR-041 の共有をもってしても対象外**」
(REQ:112)、共有対象は「**自テナント所有かつ在籍中の選手**」に限られ「**自分が第三者として記録した
対戦相手選手のデータは共有対象外**」(REQ:483)、認可行列でも「第三者として記録した対戦相手データ =
**付与によらず不可・404**」(REQ:619)。

**候補案**: チームレコードへ **`kind`(`self` | `opponent`)を持たせる**。

| 事項 | 内容 |
| --- | --- |
| **判別** | `kind = 'self'` が自テナントのチーム。共有集計・エクスポートは**この行に属する選手のみ**を対象にする |
| **「高々 1 件」の強制** | **`UNIQUE (tenant_id) WHERE kind = 'self'` の部分一意索引**。**索引が保証するのは「2 件目を作れない」ことだけ**(敵対レビュー P1-2 の是正) |
| **「少なくとも 1 件」の維持** | **テナントと `kind = 'self'` の行を同一トランザクションで生成**する(テナント作成は Must — REQ:714)。**self 行を欠損させる遷移を作らない**(非表示化・削除の対象にしない)。**索引では 0 件を排除できない**ため、生成と遷移の側で担保する |
| **可変性** | `kind` は**不変**。対戦相手行を後から自テナント行へ昇格させない(共有範囲が遡って変わるため) |

- **却下案**: **テナント側に自チーム行への参照(`tenant.self_team_record_id`)を持つ** →
  `team_record.tenant_id → tenant` と**循環参照**になり、生成順序に遅延制約が必要。
  `kind` + 部分一意索引なら循環せずに同じ不変条件を表現できる
- **却下案**: **対戦相手を別表へ分ける** → 「試合 → チーム」の参照が非対称になり、
  紅白戦(先攻・後攻が同じ行)と在籍区分の一律適用という上記の利点を失う

**共有経路への影響**: 8 節の共有関数は、**`kind = 'self'` のチームレコードに属する選手の集計だけ**を
返す。これが REQ:619 の「付与によらず不可」を**モデルの形で**満たす経路である(関数の条件分岐に
頼らない)。
- **却下案**: 試合が「テナント参照 + 相手チーム参照」を持つ形 → **紅白戦(両方が自テナント)と
  在籍区分の一律適用の両方が表現しにくくなる**。参照の型が非対称になり、集計クエリが分岐する
- **一意制約はテナント内に閉じる** — 類似名のチームは「**重複の可能性が警告される(意図的なら登録可)**」
  (REQ:389)なので**チーム名に一意制約を置かない**
- **旧システムの `team` テーブルはテナントと対戦相手が同居**していた(`password_hash` の有無で実質区別・
  `baseball-scoring-db-structure.md:168`)。**単純な一対一の振り分けでは移行できない(敵対レビュー P1-3 の是正)**:

**旧 `team` は名前がグローバル一意で、テナント間で共有されていた**。一方、新モデルでは対戦相手は
**各テナント内のレコードでテナント間で共有されない**(REQ:387)。旧試合の所有境界は `game.owner_team_id`
(`baseball-scoring-db-structure.md:176`)なので、**ある旧チーム行は「自身のテナント」であると同時に、
別の所有テナントの試合では「対戦相手」として参照され得る**。当初案の
「`password_hash` あり → テナント / なし → 相手チームレコード」という一対一の振り分けでは、
**その相手チーム行の `tenant_id` を決められず、必要な複製も表現できない**。選手も旧チームに属するため
**同じ問題を引き継ぐ**。

**候補案(ファンアウト)**:

| 手順 | 内容 |
| --- | --- |
| 1 | **`password_hash` を持つ旧チーム行 → テナント + その `kind = 'self'` のチームレコード**(1 対 1) |
| 2 | **旧試合を `owner_team_id` で所有テナントへ割り当てる** |
| 3 | 各所有テナントについて、**その試合が参照する先攻・後攻の旧チーム行のうち自テナント以外**を、**そのテナント配下の `kind = 'opponent'` レコードとして複製**する(**同じ旧チームが N テナントから参照されれば N 行になる**) |
| 4 | **旧選手も所属旧チームごとに同じ倍率で複製**し、**複製先のチームレコードへ紐づける**(名前解決は相手チーム単位 — REQ:1191) |
| 5 | **旧試合・旧プレイの選手参照を、所有テナント側の複製行へ付け替える** |

- **複製は要件の要求**である — テナント間で共有しない(REQ:387)以上、**同じ実世界のチームでも
  テナントごとに別レコードになる**。これは重複ではなく**分離の帰結**
- **自テナントが対戦相手としても現れる場合**(旧データで A の試合に B が相手として出て、B もテナント)は、
  **B のテナント配下には `kind = 'self'` の行**があり、**A の配下には B の複製(`opponent`)**ができる。
  **両者は別レコード**で、共有集計は各自の `self` 行にだけ掛かる(7-1 節)
- **従属データも同じ倍率で複製する(3 周目 P1-8 の是正)**: 当初の 5 手順は**チーム・選手・試合・プレイ参照**
  だけを複製しており、**旧チームを所有者とする `stamem`(スタメン記憶)を扱っていなかった**。
  要件は移行対象にスタメンを含め、**何を何件移行したかと選手数の突合**を要求している(REQ:755・756)。
  **旧チームに従属するデータはすべてファンアウトの対象**とする:

| 旧の従属データ | 複製先 |
| --- | --- |
| **選手** | 複製先チームレコード配下(手順 4) |
| **`stamem`(スタメン記憶)** | **旧 `stamem` は `team` への FK しか持たず、パスワードあり(テナント相当)に限定されていない**(`data-layer.md`)。**パスワードなし旧チームに `stamem` がある場合、そのチームに `self` 行は作られない**ので、「`kind='self'` にだけ持たせる」規則では**移行先がゼロになり全件移行(REQ:755)を破る**(4 周目 P1-5 の是正)。**候補案**: 新規運用では `kind='self'` に 1 件だけ持つ(7-4 節)。**移行分は、そのチームを参照する所有テナントの対戦相手レコード配下へ「移行由来の記憶」として保全**し、**入力補助としては使わない**。所有テナントが特定できない `stamem` は**隔離領域へ**(10 節) |
| **在籍区分** | 選手に付随して複製される(相手チームの選手にも適用 — FR-017) |

- **移行レポートを 3 区分に分ける**(REQ:756 の突合を成立させるため):

| 区分 | 内容 |
| --- | --- |
| **旧原本行** | 旧 DB の実件数(複製前) |
| **生成したテナント別コピー** | ファンアウト後の件数。**「旧 1 行 → N 行」の N を記録**する |
| **隔離・未解決** | 名寄せ不能・所有テナント不明など(10 節の隔離領域へ) |

  **「移行件数」を複製後の件数だけで報告すると旧側と一致しない**。**旧原本行の件数で突合し、
  複製は別の欄で報告する**

- **SQL の詳細・名寄せの閾値は移行仕様タスクへ送る**。**論理規則(何を何倍に複製し参照をどう付け替えるか)は
  候補案で決める** — ここを決めないと論理モデルが作り直しになる
- **全件移行の要求と整合**(REQ:755)。**不整合行を弾かない**(**P-46**)

### 7-3. 候補案: 背番号の当時値は「試合参加時点のスナップショット」で持つ(論点 8)

要件は**結果だけを要求**している — 「背番号を変更しても**記録した時点の背番号で表示される**」
(REQ:340・144)。**方式は定めていない**。

**3 案の評価**:

| 案 | 評価 |
| --- | --- |
| (a) **プレイ行に背番号を非正規化** | 1 球ごとに冗長。**選手 ID 参照が正**という原則(**P-13**)から見て、表示用属性を毎球持つのは筋が悪い |
| (b) **背番号の変更履歴表**(選手 × 有効期間) | 汎用だが、**試合日時と期間の突合**が全表示経路に必要になる。期間の境界(同日の変更)が曖昧 |
| (c) **試合参加時点のスナップショット(採用)** | **スタメン・出場区間に「当時の背番号」を持たせる**。試合単位で確定するので突合が不要 |

**(c) を採る理由**: 表示が必要な単位が**試合**であること(スコアカード・当日成績・出場履歴)。

**スナップショットの正本はイベント側に置く(敵対レビュー P1-1 の是正)**: 当初案は当時の背番号を
**出場区間(投影)の行にだけ**載せていた。しかし 6-2 節で出場区間は「**常にイベントから再生成可能な
投影**」と定めており、**交代イベントのペイロードは「誰 → 誰・時点・DH 配置」だけで背番号を持たない**。
そのため**後日背番号を変更して再投影すると当時値が復元できず**、「背番号を変更しても**記録した時点の
背番号で表示される**」(REQ:340・144)を満たせなくなる。

| 保持場所 | 役割 |
| --- | --- |
| **先発**: 試合のスタメン(7-4 節) | **確定時に当時の背番号を焼き込む**。試合単位で不変 |
| **途中出場**: **交代イベントのペイロード**(6-2 節) | **正本**。出場する選手の当時の背番号を含める |
| 出場区間(投影) | 上記 2 つから**再生成する**。投影行にも背番号を持つが、**それは導出値**である |

**再投影の入力がイベント側に揃っている**ことが要点で、投影行の背番号は表示の都合の複製にすぎない。
移行データでも「最初のプレイ行のスタメン JSON」(REQ:763)から先発の当時の背番号を取れる
(**途中出場は移行では復元しない** — 12-1 節・**P-44**)。

**残余リスク**: 試合に出場していない選手の過去の背番号は復元できない。**要件が要求しているのは
「過去試合の表示」**(REQ:144)なので範囲内だが、**申し送りに記録**する(12 節)。

### 8-2-A. システム管理者の資格情報はテナントと別系統にする(敵対レビュー P1-5 の是正)

当初案は**認証情報の所有者をテナント**とし、トークンにも**テナント参照を必須**にしていた。
そのため **FR-035 のシステム管理者**(REQ:710)の資格情報とセッションを表現できなかった。
要件は分離を Must として定めている — 「**破壊的操作を一般利用と分離**」(REQ:712)、
「チーム登録 / 初期パスワードの発行」は**管理者認証済み**が前提(REQ:714)、
「**管理者自身のパスワード**の変更で**旧トークンが失効する**」(REQ:720)。

**候補案**: **主体を 2 系統にする**。`users` テーブルは作らない(**P-20** — Won't に正面衝突する)。

| 系統 | 資格情報 | セッション | 備考 |
| --- | --- | --- | --- |
| **テナント(チーム)** | 8-2 節の認証情報(テナントに紐づく) | 8-3 節のトークン(テナント参照が必須) | 一般利用 |
| **システム管理者** | **管理者資格情報**を別表に置く(ソルト付き bcrypt・**世代**・変更日時は 8-2 節と同じ形) | **管理者セッション**を別表に置く(**テナント参照を持たない**) | 破壊的操作・オンボーディング |

- **テナント参照を持たないことが要点** — 管理者セッションにテナントを持たせると「どのテナントの
  管理者か」という概念が生まれ、**要件に無いロール階層**を作ってしまう(**P-21** — ロール表・ロール列を作らない)
- **世代による失効は同じ機構**を使う(REQ:720)。管理者パスワード変更で管理者資格情報の世代を +1 し、
  **旧世代の管理者セッションを失効**させる
- **RLS との関係**: 管理者経路は**テナント文脈を持たない**ので、3-2 節の 3 ロールとは別に扱う。
  **業務データへ到達する経路は 8-2-B 節で定める**(要件が要求する管理経路がある — REQ:722・724・744)
- **却下案**: **テナント表に「管理者フラグ」を持つ** → 管理者がテナントの一種になり、
  テナント分離の前提(すべての業務行が `tenant_id` を持つ)と衝突する。**分離が Must** である以上不可

### 8-2-B. 管理者から業務データへ到達する経路を論理モデルとして定める(敵対レビュー P1-4 の是正)

8-2-A で管理者を別系統にした結果、**管理者セッションはテナント文脈を持たない**ため、
当初は「管理者が業務データを直接読む経路は作らない。必要になったら置く」と書いていた。
**これは Must を将来事項へ落としていた**。要件は管理経路を明示的に要求している:

| 要求 | 典拠 |
| --- | --- |
| **退避イベント(FR-013)を管理コンソールで閲覧・書き出し・挿入位置を指定して取り込める** | REQ:722 |
| **横断一覧・試合 CSV・操作ログは「既存の管理経路」として現行のまま維持される** | REQ:724 |
| **チーム・選手・スタメン・試合の登録状態を一覧でき、試合単位の CSV 保存ができる** | REQ:744 |

**候補案**: **第 4 の常時バイパスロールは作らない**。3-6 節の共有関数と**同じ形**で、
**管理者専用の `SECURITY DEFINER` 制限関数**を置く。

**関数を 4 クラスに分ける(3 周目 P1-5 の是正)**: 当初は「対象を必須引数に取り、対象の有効性を検証する」と
一律に書いていたが、それでは要件の管理経路が成立しない — **① 横断一覧は対象が未知のまま始まる**(REQ:744)
**② 無効テナントの確認・再有効化は「有効性」を必須にできない**(REQ:715 の可逆性)**③ 制御資源の 7 操作は
「代表するテナント + 対象グループ」が必要**(REQ:723)**④ 一覧はページングが必須**(NFR-005・REQ:795)。

| クラス | 引数 | スコープの絞り方 | 対象の状態 |
| --- | --- | --- | --- |
| **(a) 横断一覧** | **ページング(キーセット)**。対象テナントは**任意** | **返す列を登録状態の要約に限定**する(記録データ本体を返さない)。**全件読み込みを書かない**(NFR-005) | **有効・無効の両方**を含む(無効の確認が要件) |
| **(b) 対象指定の参照** | **対象テナントまたは対象試合を必須** | 当該対象の範囲だけ。試合 CSV(REQ:744)・退避イベントの閲覧(REQ:722)がここ | **有効性は要求しない**(無効テナントの確認が要件) |
| **(c) 破壊的操作** | **対象を必須**(REQ:717 が明示対象を要求するのはこの系統) | 対象 1 件ずつ。退避イベントの取り込み(挿入位置指定)を含む | 操作ごとに前提条件を定める |
| **(d) 制御資源の操作** | **代表するテナントを必須**。対象グループは**操作によって必須/不在が分かれる**(下表) | 当該グループの範囲だけ | **操作別**(下表) |

- **「明示対象が必須」は破壊的操作の規定**である(REQ:717)。**参照系まで一律に必須化すると横断一覧が始まらない**
- **管理者セッションの検証を全クラスの前提条件にする**(8-2-A の管理者資格情報の世代照合)
- **一覧は必ずページングする**(NFR-005)。**件数の上限を関数側で持ち、無制限に返さない**
**クラス (d) は 7 操作の操作別契約へ分ける(4 周目 P1-2 の是正)**: 当初は 7 操作すべてに
「代表テナント + 対象グループ必須」「実効グループ・実効参加を評価」を一律に課していたが、
**グループ作成時には対象グループも参加行も存在せず、招待受諾時には要求元がまだ参加していない**ため
成立しない。要件は**2 層判定**を操作ごとに分けている(REQ:489・723):

| 操作 | テナント側の権限 | グループ内の役割 | 対象グループ | 実効参加の要求 |
| --- | --- | --- | --- | --- |
| **作成** | 必須 | **不要** | **不在**(生成する) | **不要**(9-4-B で初期 `admin` を同時生成) |
| **参加(招待の受諾)** | 必須 | **不要** | 招待から解決 | **不要**(参加前。**招待の有効性検証**を要する) |
| **付与フラグの変更** | 必須 | **不要** | 必須 | 要求元の実効参加 |
| **離脱** | 必須 | **不要** | 必須 | 要求元の実効参加 |
| **招待の発行・失効** | 必須 | **実効 `admin`** | 必須 | 要求元の実効 `admin` |
| **役割の変更** | 必須 | **実効 `admin`** | 必須 | 同上 |
| **グループの終了** | 必須 | **実効 `admin`** | 必須 | 同上 |

- **作成・参加は共通前提の例外**である(REQ:653 — 参加前で役割が存在しないため)。
  **3-0 節の実効参加を前提条件に含めない**のはこの 2 操作だけ
- **管理者も 2 層目を免除されない**(REQ:723 — 管理者は「そのテナントを代表して」実行できるだけで、
  **役割が必要な操作では実効 `admin` であることを要する**)
- **拒否はすべて 404・理由コードなし**(REQ:659)。**テナント側権限なし / `member` による `admin` 限定操作 /
  共通前提の失敗**を応答から区別できないようにする

- **すべての呼び出しを操作ログへ記録する**(8-4 節。FR-035 の操作ログは Should だが、
  **管理経路は記録権の外側から業務データに触る唯一の経路**なので記録を必須にする)
- **共有グループ経由の閲覧とは別物**である — REQ:724 は「**管理者だから追加で見えることはない**」と
  定めており、**共有経路(3-6 節)には管理者の例外を作らない**。管理経路はそれとは**別の権限源**
- **却下案**: **管理者セッションにテナント文脈を持たせて通常のアプリ用ロールで読む** →
  「どのテナントの管理者か」という概念が生まれ、**要件に無いロール階層**になる(**P-21**)
- **却下案**: **管理者用の常時バイパスロール** → RLS を無効化した経路が常設され、
  3-1 節の「テナント分離は初日から全経路へ」(REQ:823)と衝突する

**残余リスク**: 管理経路は**記録権(6-1 節)の外側**から業務データに触る。**どの操作を許すかは
FR-035・FR-037 の受入基準が正**であり、**それを超える関数を作らない**ことを逐行確認の対象にする。

## 9. 共同分析グループ・参加・付与・招待(ブロック 4 / 論点 6)

制御資源のテーブル構成と越境経路は 3-5・3-6 節。本節は**ライフサイクルと不変条件**を決める。

### 9-1. 候補案: 参加は履歴として複数行持ち、`active` な行を 1 件に絞る(論点 6)

要件は「**離脱後の再参加は新規参加として計数する**」(REQ:487)と定めており、
**(グループ, テナント) で 1 件とは読めない**。一方で「**終了・離脱も論理削除で保持**」(REQ:947)も要求される。

**候補案**: **参加を履歴行として持ち、`active` な行が最大 1 件**(**`WHERE 状態 = active` の部分一意
インデックス**。5-3 節・6-1 節と同じ手法で 3 回目)。

- **参加テナント上限**(付録C・既定 50)の判定は「**実効参加**の件数」で行う(**述語は 3-0 節が正**)。履歴行は数えない
- **計数述語に「テナントが有効」を含める(敵対レビュー P1-7 の是正)**: 当初案は `active` な参加行だけを
  数えていたが、**テナント無効化では参加レコードを維持する**(REQ:715)ため、参加行だけを見ると
  **無効テナントが計数に残る**。要件は「無効化中は `active` でないため**計数しない**。再有効化で
  再び計数する」(REQ:705)と定めており、**計数の単位は「参加行の状態 ∧ テナントの有効状態」**である
- **設定値の不変条件**(REQ:493): **`同時比較表示上限 ≤ 参加テナント上限`**。**これを破る設定値は
  保存できない**(6-5 節の規則値と同じくアプリ層の検証を保存の必須経路に置く)
- **上限の引き下げ・再有効化で超過しても既存の参加は維持する**(REQ:493・705)。**新規参加のみ拒否**。
  → **上限検査は「参加を増やす操作」にだけ掛ける**。既存行を遡って無効化する経路を作らない
- 「**参加の確定はサーバー側で直列化し、同時受諾でも上限超過を発生させない(先着のみ成立)**」(REQ:479)は、
  **上限検査と挿入を同一トランザクションで行う**ことで満たす。部分一意インデックスは
  「同じテナントが二重に `active` にならない」ことだけを保証する(**上限は件数条件なので制約では
  表現できない** — アプリ層で検査する)
- 離脱は**行の状態遷移**(削除しない)。再参加は**新しい行**を作る

### 9-2. 候補案: 付与は「参加」に紐づける

要件は付与の単位を「**(グループ × 自テナント)**」(REQ:114・480)と定め、**既定はすべて非共有**とする。
一方**再参加時に前の付与をどう扱うかは要件に明示がない**。

**候補案**: **付与を参加行に紐づける**(グループ × テナント ではなく**参加**に紐づける)。

- 実効参加が 1 件なので、**実効的に「(グループ × 自テナント)で 1 件」になり要件と整合する**
- **再参加時は付与が既定(すべて非共有)から始まる** — 「離脱後の再参加は**新規参加として計数**」
  (REQ:487)であり、**前の付与を引き継ぐと「新規参加」の意味と矛盾する**。かつ既定は非共有(REQ:480)
- **却下案**: 付与を (グループ, テナント) に直接紐づける → 離脱・再参加をまたいで**前の付与が復活する**。
  要件が明示していない挙動を、**共有が広がる側**に倒してしまう(fail-open)
- **要件に明示がないことの記録**: 再参加時の付与の扱いは要件に書かれていない。**本案は「新規参加として
  計数する」という明文から導いた**もので、推測ではないが**正本化時に確認を仰ぐ論点**として 12 節へ記載する

### 9-3. 招待(FR-041)

| 属性 | 内容 | 典拠 |
| --- | --- | --- |
| グループ | 越境 FK(3-5 節) | — |
| **コードのハッシュ** | **ハッシュで保存**。**コード本体は発行時に一度だけ表示し以後は表示しない** | REQ:478・650 |
| 有効期限 | — | REQ:478 |
| 状態 | 未消費 / **1 回で消費** / 失効 | REQ:478 |
| 発行時指定の初期役割 | `admin` を指定できる。**受諾後の既定は `member`** | REQ:478 |

- **発行時点で参加上限を検査する**(REQ:478)。**発行と受諾の 2 時点で検査が必要**(発行後に他の
  テナントが受諾して上限に達し得るため、受諾時にも 9-1 節の上限検査が掛かる)
- **グループの終了時点で未消費の招待はすべて無効**(REQ:655)。**終了は不可逆**(REQ:704)なので、
  終了時に招待の状態を一括で失効させる(または「グループが終了していれば無効」と導出する)
- **招待の失効はキャッシュ無効化トリガーに含めない**(REQ:955 が明示 —「権限の撤回ではないため」)。
  11 節の対応表でこの除外を明記する

### 9-4. 不変条件: **実効 `admin`** が 1 名以上

「**`active` な `admin` が 1 名以上存在すること**を不変条件とし、**最後の `admin` は離脱も降格もできない**」(REQ:488 の文言。**本書ではこれを 3-0 節の実効 `admin` として読む** — テナント無効化を含めるため)
(REQ:488)。

**「実効 `admin`」の述語を定義する(敵対レビュー P1-5 の是正)**: 当初は「`active` な `admin`」とだけ書いており、
**`active` が参加行の状態だけなのか、テナントの有効状態との積なのかが未定義**だった。
**参加レコードはテナント無効化後も維持される**(REQ:715)ため、参加行だけを数えると
**無効化されたテナントの `admin` が生きているように見える**。9-1 節では参加上限について同じ問題を
既に是正しており(「参加行の状態 ∧ テナントの有効状態」)、**不変条件側へ伝播していなかった**。

**定義は 3-0 節に置いた**(実効 `admin` = 実効参加 ∧ 役割が `admin`)。**本書のすべての判定で同じ述語を使う** —
本節と 9-4-A に限らず、3-5 の RLS 述語・3-6 の共有関数・9-1 の計数・9-2 の付与・9-3 の招待・11-2 の無効化波及も同じ
(3 周目 P1-2 の是正 — 当初は「本節と 9-4-A」にしか適用すると書いており、兄弟節へ伝播していなかった)。

- **DB の `CHECK` では表現できない**(集合に対する条件)。**アプリ層の検証を離脱・降格の必須経路に置く**
  (6-5 節の規則値の検証と同じ扱い)
- 実装の選択肢(**(B) として実装時に判断**): 同一トランザクション内で**実効 `admin`** を数える /
  遅延制約 + トリガー / グループ行に**実効 `admin`** 数を持って制約を掛ける(**後者は参加行だけでなくテナントの有効状態の変化でも更新が必要**になる点に注意 — 3-0 節)
- **競合**: **実効 `admin` を減らす操作すべてを、グループ単位の同じ直列化境界に載せる**
  (3 周目 P1-4 の是正)。当初は「2 人の `admin` が同時に離脱」だけを挙げていたが、**離脱・降格・
  テナント無効化は互いに競合する**:

  > A・B が実効 `admin` のとき、Tx1 が A を無効化して「B がいるので終了不要」と判断し、
  > 並行する Tx2 が B を降格して「A がいるので最後ではない」と判断すると、
  > **両方のコミット後に `active` なグループの実効 `admin` が 0 名**になる。
  > 「無効化と終了判定を同一トランザクションで行う」だけでは**この相互競合を防げない**

  したがって **① 離脱 ② 降格 ③ テナント無効化(9-4-A の終了判定を含む)の 3 経路すべてが、
  対象グループ行を同じ順序で直列化してから実効 `admin` を数える**。具体的なロック方式は **(B)**
  として実装時に判断する(REQ:488・715・716)

### 9-4-B. グループの生成は初期 `admin` と同一トランザクションで行う(3 周目 P1-3 の是正)

不変条件(実効 `admin` が 1 名以上)の検証経路を**離脱・降格に限定していた**ため、
**「グループ行だけが存在して参加行が無い」状態を排除できていなかった**。要件は生成時の状態を定めている —
グループ作成時は「**作成者のテナントが初期 `admin` として参加した状態**」になる(REQ:477)。

**候補案**: **次の 3 行を同一トランザクションで生成する**。途中状態を作らない。

| 生成物 | 内容 |
| --- | --- |
| **グループ行** | 状態 `active` |
| **参加行** | 作成テナント / 役割 `admin` / 状態 `active`(= **実効参加**かつ**実効 `admin`**) |
| **付与行** | **既定はすべて非共有**(REQ:114・480 — 明示的に「非共有」の行を置くか、行の不在を非共有と読むかは **(B)**) |

**7-1 節の `self` 行と同じ形**である(テナントと `kind = 'self'` の行を同一トランザクションで生成)。
**「少なくとも 1 件」は生成と遷移の側で担保し、索引では 0 件を排除できない**という同じ理由による。


### 9-4-A. 唯一の `admin` の無効化はグループを不可逆終了させる(敵対レビュー P1-4 の是正)

9-4 の不変条件(**実効 `admin`** が 1 名以上)は**離脱・降格**に掛かるものであり、
**テナント無効化(FR-035)には別の規定がある**。当初案は無効化を「完全に可逆」とだけ書いており、
**唯一の `admin` を無効化した場合の遷移が無かった**。

要件は 3 点を同時に定めている(REQ:715・716):

| 事項 | 規定 |
| --- | --- |
| **無効化を拒否しない** | 「**無効化を拒否せず、また役割の移譲も要求しない**」— 管理者の無効化操作が他テナントの状態に阻まれないようにするため |
| **グループは自動終了** | 「そのテナントが**唯一の `admin` であったグループは無効化時に終了**し、**再有効化しても復活しない**」(**終了は不可逆**。再開は新規作成) |
| **残る参加者へ通知** | 「**終了したことを残る参加テナントに通知する**」 |

**候補案**:

- **グループへ終了状態を持つ**(`active` / `terminated` + 終了時刻・終了事由)。**`terminated` は不可逆**
  で、再有効化の経路を持たない(**状態遷移の形で不可逆性を表現**し、運用規律に頼らない)
- **テナント無効化と同一トランザクション**で、当該テナントが唯一の**実効 `admin`**(9-4 節の述語)である
  グループをすべて `terminated` にする。**無効化そのものは常に成功する**(拒否しない)
- **参加レコードは維持**する(REQ:715 の可逆性はデータ保全の話であり、**グループの終了とは独立**)。
  再有効化で参加は復帰するが、**`terminated` のグループは復活しない**
- **通知は永続化の要求ではない**(通知の実体は本起草の対象外)。ただし**「誰へ通知するか」を決めるには
  終了時点の**実効参加**の集合が要る**ので、**終了時刻を記録して当時の参加を引ける形**にする
- **順次無効化の経路を取りこぼさない**: `admin` が A・B の 2 名のグループで **B を無効化 → A を無効化**
  すると、B の参加行は `active` のまま残る。**参加行だけを数えると A を「唯一」と判定できず**、
  実効 `admin` が 0 名なのにグループが終了しない。**実効 `admin` の述語を使えばこの経路も終了する**
- **9-4 の不変条件との関係**: `terminated` のグループは不変条件の対象外(`admin` 0 名で終了する)。
  **「最後の `admin` は離脱も降格もできない」は `active` なグループにだけ掛ける**

## 11. 削除の 4 系統とキャッシュ無効化契約・索引設計の原則(論点 7・10)

### 11-1. 候補案: 削除は統一せず 4 系統を別のライフサイクルとして持つ(論点 7)

**共通化するのは「物理削除しない」原則だけ**(4.0-2 REQ:143)。**状態遷移まで統一しない。**

| 系統 | 対象 | 復元可否 | 認可効果 | 集計除外 |
| --- | --- | --- | --- | --- |
| **ゴミ箱** | **試合のみ** | **期限内(既定 30 日)はチーム自身が復元し「完全に元に戻る」**。期限後はチームの UI から消えるが **DB 残存**でシステム管理者がフラグ復旧 | 一覧・出力・集計のすべてから除外 | **除外**(復元で戻る) |
| **非表示** | 選手 / プレイ行 / 対戦相手チームレコード / **プレイ 0 件の試合**(ゴミ箱を経ず即時) | **要件に明示なし**(12 節へ) | 参照経路から外れる | プレイ行は集計から外れる |
| **無効化(可逆)** | **テナント**(データ全保全)/ **語彙**(削除不可・無効化のみ) | **可逆**。テナント再有効化で参加レコードもそのまま復帰 | テナント: 毎リクエストで検証・**全トークン即時失効** / 語彙: 新規選択不可・既存表示は維持 | テナント無効化は共有集計から除外 |
| **終了・離脱(不可逆)** | **グループの終了**(不可逆)/ **参加の離脱** | **グループの終了は不可逆**。離脱は**再参加が新規参加**(9-1 節) | 未消費の招待がすべて無効 / 制御資源の読み取りから外れる | 共有集計から除外 |

**選手の非表示化(FR-018)には削除可否の前提条件がある(敵対レビュー P2-3 の是正)**:
当初は「非表示」という状態だけを書いていたが、要件は 4 条件を定めている(REQ:367-370)。
**状態を持つだけでは FR-018 を満たさない**:

| 条件 | 規定 | 決める場所 |
| --- | --- | --- |
| **プレイ紐づけゼロ** | 紐づくプレイがあれば削除できず**「OB 化」へ誘導**(REQ:368) | **候補案で決める**(述語) |
| **進行中の試合が無い** | 当該チームに未終了の試合があれば削除できない — **断中端末の未同期キューが当該選手を参照しうる**ため(REQ:370) | **候補案で決める**(述語) |
| **同一トランザクション** | **紐づけ判定と削除を同一トランザクションで行い、判定後に紐づいた場合は失敗**する(REQ:369) | **候補案で決める**(不変条件) |
| **ゴミ箱を経ない** | 確認の上で非表示化する。**ゴミ箱 UI は経ない**(REQ:367) | **候補案で決める**(系統の割り当て) |

- **具体的なロック方式・SQL は実装計画へ送る**((B))。**述語と不変条件だけ今決める**
- **2 つ目の条件が要点** — サーバー側トランザクションでは断中端末のキューを検知できないため、
  **「進行中の試合が無い」はトランザクションでは代替できない**前提条件である

**`deleted_at` 一本に畳まない理由**: 上表のとおり**復元可否・認可効果・集計除外がすべて違う**。
一本にすると「復元できるのか」「トークンを失効させるのか」「集計から外すのか」を**参照する場所ごとに
分岐で書く**ことになり、FR-034 の「除外 / 404」判定とキャッシュ無効化の条件式がばらける
(計画レビュー 1 周目 P1)。

### 11-3. 索引設計の原則(論点 20 は具体形を (B) へ送るため、原則のみ)

Web 調査(`research.md` 6-2 節)で確認した公式の規則に、本設計の事情を掛けたもの:

1. **`tenant_id` を複合索引の左端に置く**。RLS のポリシー式が `tenant_id = current_setting(...)` の
   単純形なら索引が効く(3-1 節)
2. **列順は「等価条件 → 最初の範囲条件 → ソート列」**。例: `(tenant_id, occurred_at DESC, id DESC)`
3. **論理削除の除外は部分索引の候補** — `WHERE 削除されていない` は**固定条件なのでプランナが
   索引述語の含意を認識できる**(パラメータ化された述語では使えない場合がある)。
   11-1 節のとおり**全集計クエリにこの条件が乗る**ので効果が大きい。ただし
   **削除済みの割合が低い段階では容量削減効果は小さい**ため、`EXPLAIN` と実サイズで検証する
4. **母数併記は `COUNT(*) FILTER (WHERE …)` で分子分母を一度に返す**(REQ:1055 が「割合・率の表示には
   常に母数を併記」)。**各 `FILTER` のために索引を増やすより、共通の `WHERE` を狭める索引が重要**
   (分母を含む集計は基本コストが対象行数に比例する)
5. **JSONB の GIN は B-tree の代替にしない** — 頻繁な絞り込み・結合・GROUP BY のキー(チーム・試合・
   球種・結果)は**正規化列 + B-tree**。JSONB は規則セットのような**試合単位で読むだけ**の構造化値に使う
   (6-5 節)
6. **パーティショニングは初期から採らない** — 設計上限 150 万行は PostgreSQL 公式が示す「閾値は
   アプリケーション依存」の範囲。**非パーティション表 + 実クエリ別 B-tree から始め**、実測サイズ・
   VACUUM・保持年数で再判定する
7. **全件読み込みにならないクエリ形**: 既定が「全期間・全データ」の箇所(分析・カルテ・チーム分析・
   共有集計)は、**`(tenant_id, …)` で絞ってから `GROUP BY` する**形にする。**共有集計は
   「選択されていないテナントのデータを走査しない」ことが測定条件**(REQ:786)なので、
   **対象テナント集合を `WHERE` に入れてから集計する**(3-6 節の制限関数の引数がこれに対応)

**具体的な索引の列挙はしない**(論点 20 = (B))。**実クエリが 1 本も存在しない段階で確定させるのは
H-68 型**であり、原則と検証手段(`EXPLAIN (ANALYZE, BUFFERS)` を RLS 有効状態で確認する)までを決める。

### 12-4. マイグレーション方針(**推奨案** — 最終確定は正本化タスク)

**「最終確定」とは書かない。** 設計書 5.1 の「Alembic は SQLAlchemy 前提。設計フェーズで最終確定」は
**正本化タスクで同一 PR に追随させる**(計画レビュー 1 周目 P1)。

| 項目 | 推奨案 | 根拠(Web 調査 6-3・6-4 節) |
| --- | --- | --- |
| ORM | **SQLAlchemy 2.x** | 設計書 5.1 が前提としている。ADR は正本化タスクで起票を判断 |
| ドライバ | **psycopg 3 に統一**(同期・非同期のどちらか一方) | 同じ dialect で `create_engine()` と `create_async_engine()` の両方を提供。asyncpg は SQLAlchemy 側でも `prepared_statement_cache_size=0` が必要 |
| 接続方式 | **migration は direct connection**、アプリは 3-3 節 | Supabase 公式が direct を migration・`pg_dump`・backup 向けと案内 |
| pooler 対応 | transaction pooler を使う場合は **`prepare_threshold=None`** | **Supabase は transaction mode で prepared statement 非対応と明記** |
| マイグレーション | **Alembic**。**単一 head を維持**し、複数 head は `alembic merge` | 公式 |
| enum | **参照テーブル + FK を既定**(native enum は値セットが非常に安定した場合のみ) | **autogenerate は enum 値の増減を信頼して扱わない**。SQLAlchemy 自身が asyncpg の type OID / prepared statement cache が stale になり得ると警告。語彙は 3 層の DB マスタなので大半は参照テーブル(10-3 節) |
| テスト | **空の PostgreSQL に `alembic upgrade head`** を適用する。**`create_all()` でテスト DB を作らない** | `create_all()` は migration の漏れ・順序・手書き DDL を通らず **drift を隠す** |
| CI | ① 空 DB へ `upgrade head` ② `alembic current --check-heads` ③ **`alembic check`** | `alembic check` は 1.9.0 以降。**RLS policy・trigger・view・enum 値変更は検査しない**ので、それらは **migration SQL のレビュー + スキーマ検査 SQL + 専用テスト**で補う |
| データ migration | DDL と DML を統合しない。小さな初期データは `op.bulk_insert()`、大量バックフィルは段階実行 | 公式が推奨 |
| autogenerate の限界 | **rename は add + drop / 無名制約は検出不可 / sequence は未対応 / server default 比較は既定 off** | 公式が明記。**手動レビューを必須の工程にする** |
| 置き場 | **論点 15((B))** | データモデルの方式を分岐させないため実装計画で決める |

**RLS を採る影響**(3-1 節): **ポリシー・`FORCE ROW LEVEL SECURITY`・`SECURITY DEFINER` 関数はいずれも
`alembic check` の検査対象外**。→ **専用のスキーマ検査テスト**(ポリシーの存在と定義を照合する)を
CI に持つことを推奨案に含める。
