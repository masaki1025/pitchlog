## 3. テナント分離(論点 2・3・4・12)

### 3-1. 候補案: RLS を防御層として採り、アプリ層の明示条件も残す(論点 3)

**採る。** ただし**アプリ層の明示的な `tenant_id` 条件を省かない**二重構成とする。

**RLS を採れる根拠**:

- **RLS は PostgreSQL のコア機能**(9.5 で導入・拡張不要)であり、Supabase 固有ではない。要件書 REQ:976 の
  「標準 PostgreSQL の範囲で使用し、ホスティング固有機能に依存しない」に適合する(**P-04 に違反しない**)
- ポリシーがなければ **default-deny**。`SELECT` だけでなく `INSERT` / `UPDATE` / `DELETE` に適用される
  (既存行は `USING`、新規・更新後の行は `WITH CHECK`)
- 要件書 REQ:824 は「テナント分離は**初日から全機能に適用**する」、REQ:823 は越境について
  「**内容・存在を含め参照できない**」を要求する。**アプリ層だけの強制は、管理画面・バッチ・将来の
  リポジトリ層・手書き SQL で条件を落とした瞬間に隔離を失う**

**アプリ層の条件を省かない理由**:

- **索引選択と計画安定化** — ポリシー式に頼らず `WHERE tenant_id = :t` を書くことで、
  `(tenant_id, …)` を左端に持つ複合索引が確実に使われる
- **意図の明示** — クエリを読んだだけでテナント境界が見える
- **RLS のバイパス経路が実在する** — 公式が「Superusers and roles with the `BYPASSRLS` attribute always
  bypass the row security system」「**Table owners normally bypass row security as well**」と明記している。
  RLS 単独に安全性を委ねられない

**却下した案**:

| 案 | 却下理由 |
| --- | --- |
| アプリ層強制のみ(RLS を使わない) | 条件の落としが即座に越境になる。DB 境界での deny がない |
| RLS のみ(アプリ層の条件を省く) | 索引選択がポリシー式に依存し、計画が不安定になる。バイパス経路で無防備 |
| Supabase の認可機能に寄せる | REQ:976 に反する(**P-04**) |

### 3-2. 候補案: ロールを 3 つに分ける(論点 3)

**テーブル所有者は既定で RLS をバイパスする**ため、**アプリ用ロールを所有者と分ける**。

| ロール | 用途 | RLS | DDL |
| --- | --- | --- | --- |
| **マイグレーション用**(テーブル所有者) | Alembic の適用・DDL | バイパスする(所有者) | 可 |
| **アプリ用** | 通常の読み書き | **従う**(`BYPASSRLS` を付与しない) | 不可 |
| **共有集計用** | FR-041 の越境読み取り | **従う**(専用ポリシー) | 不可 |

- **superuser をアプリから使わない**
- **`ALTER TABLE ... FORCE ROW LEVEL SECURITY` を全テーブルへ掛ける**ことを推奨する — 所有者がうっかり
  アプリ経路で使われた場合でもポリシーに従わせる。公式が「a table owner can choose to be subject to row
  security with `ALTER TABLE ... FORCE ROW LEVEL SECURITY`」と定めている
- 共有集計用ロールの詳細は **3-5 節**(論点 12)

### 3-3. 候補案: テナント ID はトランザクション内で `set_config(..., true)` により渡す(論点 4)

**接続方式**:

| 経路 | 方式 | 理由 |
| --- | --- | --- |
| **マイグレーション** | **direct connection** | Supabase 公式が direct を migration・`pg_dump`・backup 向けと案内。prepared statement の制約を受けない |
| **アプリ(長寿命のステートレス FastAPI)** | **session pooler を第 1 候補**、transaction pooler を許容 | REQ:975 が「サーバーはステートレス・横断状態もプロセス外」を要求。長寿命プロセスなので session pooler が素直 |

**規律(transaction pooler でも成立する形に統一する)**:

1. **明示した 1 トランザクションの最初**に `SELECT set_config('app.tenant_id', :tenant_id, true)` を発行する
2. ポリシー側は `current_setting('app.tenant_id', true)` を読む
3. **`SET app.tenant_id = …` と `set_config(…, false)` は使わない** — セッション状態になり、transaction
   pooling では物理接続が別クライアントへ再利用されるため**次の利用者へ漏れる**
4. **autocommit で `set_config` と本クエリを別トランザクションにしない** — transaction-local は
   コミット / ロールバックで戻るため成立しない
5. SQLAlchemy は**リクエストごとに `Session` / `AsyncSession` を作り、`begin()` の中で最初に発行**する。
   Session をテナント横断・リクエスト横断で共有しない(`AsyncSession` は複数 asyncio task 間で共有不可)

**第 3 引数の意味は公式で確認済み** — 「If `is_local` is `true`, the new value will only apply during the
current transaction」(`set_config(setting_name text, new_value text, is_local boolean)`)。

**この規律は検査できる**: RLS が default-deny なので、**`set_config` を発行せずにクエリすると 0 行になる**。
「テナントコンテキストを設定しないと何も見えない」ことを結合テストの前提条件にできる。

### 3-4. 候補案: 一意制約はテナント内に閉じ、FK は複合参照にする(論点 2)

**動かせない事実**(PostgreSQL 公式 `https://www.postgresql.org/docs/17/ddl-rowsecurity.html`):

> **Referential integrity checks, such as unique or primary key constraints and foreign key references,
> always bypass row security** to ensure that data integrity is maintained.

> Operations that apply to the whole table, such as `TRUNCATE` and `REFERENCES`, are not subject to row security.

つまり**一意制約と外部キーは RLS を必ず貫通する**。要件書 REQ:823 が「**内容・存在を含め参照できない**」を
要求しているため、素直に設計すると**制約違反エラーが他テナントの行の存在を漏らす**。

#### 規則 1: 一意制約はテナント内に閉じる

- **テナントに属するエンティティの一意制約は、必ず `tenant_id` を先頭に含める**
  (`UNIQUE (tenant_id, …)`)。**グローバル一意制約を置かない**
- **代理キー(主キー)は衝突しない値域を使う**ため、この規則の対象は「業務的な一意性」に限る
- **例外はテナントに属さないもの**だけ — テナント自身のテーブル・システム固定語彙・付録C の設定値
- **この規則は要件と衝突しない**: 要件が一意性を求める箇所(スタメン記憶は「チームにつき最後の 1 件」
  REQ:350 / カルテ所見は「選手 × カルテ種別」REQ:764 / 付与は「グループ × 自テナント」REQ:480)は
  **いずれもテナントかグループの内側**にある。逆に**背番号は明示的に「DB の一意制約は張らない」**
  (REQ:339 / **P-15**)ので対象外

#### 規則 2: FK は禁止しない。テナント内 FK は複合参照にする

**FK 一般の禁止は誤り** — FR-041 の制御資源(グループ・参加・付与)は**複数テナントに跨る関係を持つのが
要件**であり(REQ:824 が「記録・集計とは別のクラス」と定める)、FK を禁じると要件が表現できない。

代わりに**漏洩経路を個別に閉じる**:

| 手段 | 内容 |
| --- | --- |
| **(a) 複合参照** | テナント内の FK は `FOREIGN KEY (tenant_id, game_id) REFERENCES game (tenant_id, id)` の形にする。**参照側の `tenant_id` は自テナントに固定される**ため、他テナントの `id` を渡しても「(自テナント, その id)」という**存在しない組み合わせ**になる。エラーは「**自テナントに無い**」ことしか示さず、他テナントの存在を漏らさない |
| **(b) 事前認可** | 参照値としてアプリ層へ渡す ID は、**自テナントに属することを検証済みのものだけ**にする。検証は RLS 下の `SELECT`(= 見えなければ存在しないのと同じ)で行う |
| **(c) エラーの一律秘匿** | 制約違反の詳細(制約名・値・テーブル名)を**クライアントへ返さない**。FR-034 が「**いずれも理由コードを返さない**」(REQ:623)と定めているのと同じ扱いにする。ログには残す |
| **(d) 越境 FK は「存在が秘匿対象でない」クラスに限る** | 制御資源の参照先(グループ・参加テナント)は**当事者が既に知っている**情報であり、読み取り粒度も REQ:645-651 が定めている。詳細は 3-5 節 |

**残余リスク**: `TRUNCATE` と `REFERENCES` 権限は RLS の対象外。**アプリ用ロールに `TRUNCATE` と
`REFERENCES` を与えない**ことで運用上塞ぐ(GRANT の設計は正本化タスクで詰める)。

### 3-5. 制御資源のデータ表現(論点 12)

**制御資源は記録・集計とは別のクラス**である。要件書 REQ:824 が「これは他チームの記録・集計を参照する
権限ではなく、**参加・付与の状態そのものを扱う権限**である(制御資源は記録・集計とは別のクラス)」と
定め、管理者操作のスコープが**グループ単位に及ぶ**ことを認めている。

したがって**制御資源のテーブルはテナントに属さない**。RLS ポリシーは `app.tenant_id` 単独では書けず、
「**自テナントが `active` な参加を持つグループの行だけ見える**」という形になる。

| エンティティ | 主な属性 | 一意性 | 越境 FK |
| --- | --- | --- | --- |
| **グループ** | 状態(`active` / 終了。**終了は不可逆** REQ:704)・名称(利用者入力 → NFR-023 の対象 REQ:928) | グループ内で自明 | — |
| **参加** | グループ / テナント / 役割(`admin` / `member`)/ 状態(`active` / 離脱)/ **参加日時**(REQ:648 が「参加日時・役割は `admin` のみが見られる」と定める) | **(グループ, テナント) で 1 件と読めない**(論点 6 — 9 節で扱う) | **あり**(グループ ↔ テナント) |
| **付与** | グループ / テナント / 粒度 3 種のフラグ(`成績` / `選手個別` / `書き出し`。**既定はすべて非共有**) | **(グループ × 自テナント)で 1 件**(REQ:114・480) | **あり** |
| **招待** | グループ / **コードのハッシュ** / 有効期限 / 状態(未消費 / 消費済 / 失効)/ 発行時指定の初期役割 | — | あり |

**越境 FK を許す根拠**(3-4 節の規則 2-(d)): 参照先の**存在自体が秘匿対象でない**。参加しているグループの
一覧は当事者が読めるし(REQ:647)、メンバー一覧も同じグループの `active` な参加テナントが読める
(REQ:648)。**参加していないグループの存在は「誰も読めない・404」**(REQ:651)なので、**FK の参照先を
知り得るのは既に参加している当事者だけ**である。

**読み取り粒度は REQ:645-651 の表に一致させる**:

| 制御資源 | 読める者 | 内容の制限 |
| --- | --- | --- |
| 自テナントが参加しているグループの一覧 | そのテナント | — |
| グループのメンバー一覧 | 同じグループの `active` な参加テナント | **テナント名のみ**。参加日時・役割は `admin` のみ |
| 各メンバーの付与状態 | 同上 | **どの粒度を出しているかは見える**(相互性の判定に必要)。中身は認可行列に従う |
| 招待の一覧・状態 | **`admin` のみ** | **コード本体は発行時に一度だけ表示し、以後は表示しない**(ハッシュ保存) |
| 参加していないグループの存在 | **誰も読めない** | **404** |

→ **データモデル上の含意**: 参加日時・役割・招待は**同じ行に混在させても読み取り粒度で分けられる**が、
**「テナント名のみ」を返す経路と「参加日時・役割」を返す経路を別のクエリとして持つ**必要がある。
付与状態は**粒度フラグの有無が相互性の判定に必要**なので、`admin` でなくても読める。

### 3-6. 候補案: 共有集計は `SECURITY DEFINER` の制限関数を唯一の越境経路にする(論点 12)

**通常アクセスと共有アクセスの実行経路を分離する。** 3-3 節の通常経路(`app.tenant_id` 単独)では
共有集計を読めず、逆にバイパスロールを使うと既定拒否(REQ:586)を迂回してしまう。

**3 候補の評価**:

| 案 | 評価 |
| --- | --- |
| **(1) 共有専用ロールで接続し直す** | プールが分かれて接続数が増える。**ロール切替の漏れが即座に越境**になる(fail-open の方向) |
| **(2) `SECURITY DEFINER` の制限関数(採用)** | **越境の経路が関数という 1 点に集約される**。通常アクセスのポリシーは `app.tenant_id` 単独のままにできる。関数の内側で 2 層認可を明示的に検査し、**返す列を集計値に限定**すれば認可行列(REQ:625-637)と構造的に整合する |
| **(3) 追加コンテキスト(`app.shared_group_id` 等)をポリシーへ渡す** | ポリシー式が複雑化し、**アプリ用ロールが常に越境可能な状態**になる。コンテキストの設定漏れ・誤設定が越境になる(fail-open) |

**(2) を採る理由**: **境界を 1 点に集約できる**こと。`SECURITY DEFINER` は所有者権限で走るため RLS を
バイパスするが、**バイパスするのは関数の中だけ**で、関数のシグネチャが返す列を集計値に限定すれば、
「FR-020〜032 のすべてが共有グループ経由では不可(404)」(REQ:625-637)という認可行列を**物理的に**
満たせる。**生記録・カルテを返す経路を持たない**ことがコードの形として見える。

**関数が必ず検査する前提条件(要件書 REQ:597-606 の 6 項目に一致させる)**:

1. **指定されたグループが `active`**(終了していれば除外)
2. **要求元と対象テナントの参加がともに `active`**(離脱済みは除外)
3. **両テナントが無効化されていない**(FR-035 の無効化 → 除外)
4. **要求元テナントが同一の付与を、指定されたグループで出している**(**相互性 = 見るには出す**)
5. **自テナント自身が集合に含まれる場合は、付与・相互性の条件を適用しない**。ただし**同時比較表示上限には数える**
6. **要求された集合の要素数が同時比較表示上限以下**(超えていれば**要求全体を 400 で拒否**する。切り捨てない)

**指定グループ以外の付与を参照させない**: 関数は **`group_id` を必須引数に取り、内部で当該
`group_id` に紐づく付与だけを見る**。他のグループの付与は関数の問い合わせ範囲に入らない。

**要求の形**: 「すべての共有リソース要求は **①グループ ②対象テナントの集合**を明示する」(REQ:597)。
関数のシグネチャもこれに合わせる(グループ + テナント集合 + 粒度)。

**エラー秘匿**(REQ:623):

- **集合要求の要素は「除外」** — 結果に現れないだけで、0 件と権限なしを応答から区別できない
- **単一リソースを名指しした要求は 404**
- **いずれも理由コードを返さない** → **関数は除外した理由を返さない**。ログには残す

**残余リスク**: **関数の実装が唯一の防壁になる**。したがって ① この関数を含む変更は**コア領域の
逐行確認の対象**にすべき(`core-areas.json` の `paths` 充填時に `tenant-isolation` へ含める候補)
② **2 層認可の 6 項目それぞれに越境テストを持つ**(NFR-019(b) の越境テスト)③ 関数の外側で越境できる
経路(バイパスロール・所有者)を運用で塞ぐ(3-2 節)。

**却下案の記録**: (1) と (3) は上表の理由で採らない。とくに (3) は「設定漏れが越境になる」方向の
失敗であり、fail-closed の原則に反する。

## 4. 永続化上の表現と識別子のライフサイクル(論点 1・9)

### 4-1. 前提(ADR-003 が固定済み — 本節は再決定しない)

- **確定イベントを持ち、現在状態・成績は導く**。契約の単位は「1 遷移」で `input` = 事前状態 + 履歴文脈 +
  次イベント 1 件(ADR-003 `:93-104`)
- **後段集計 (β) は宣言モデルから SQL 式を生成して DB 側で実行**する(Python で全行畳み込みは NFR-005 違反)
- **履歴文脈は種別 + 状態差分**を持つ。**差分を落として種別だけ持つ設計は不可**(連続 undo が実行不能 — **P-57**)
- **語彙スナップショットは対象計算の入力**として渡す。**写像テーブルに焼き込まない**(**P-40**)

**本節が決めるのは永続化上の表現だけ**である。

### 4-2. 候補案: イベント表を正とし、プレイ行を投影として持つ(論点 1)

要件は 2 方向に引いている:

| イベント側を示すもの | プレイ行という実体を要求するもの |
| --- | --- |
| 「**確定イベントは即時に DB へ永続化**」(REQ:953)/「正本は **DB の 1 系統のみ**」(REQ:147) | FR-007 が**プレイ行の論理削除・任意位置への挿入・楽観ロック**を要求(REQ:232-238) |
| 未同期キューは「**操作イベントの順序付き列**」(REQ:282。**プレイ行ではない** — **P-24**) | FR-013 が挿入位置を「**プレイ番号**」で指定(REQ:305) |
| サイドカー結合キーが「**試合ID + 記録権世代 + イベント連番**」(REQ:1182) | NFR-005 が **DB 側絞り込み・集計**を要求(毎回リプレイは全件読み込み型) |

**候補案**: **操作イベント表を正本とし、プレイ行を投影(materialized projection)として持つ**。

| 表 | 位置づけ | 主なキー |
| --- | --- | --- |
| **操作イベント** | **正本**。確定と同時に追記する。訂正は**同一連番の改訂版**、取消は**墓標イベント**(REQ:288) | (試合, 記録権世代, 連番)が一意 / べき等キーが一意 |
| **プレイ行** | **投影**。イベントから決定的に再生成できる。論理削除フラグ・楽観ロック用の版・**プレイ番号**(表示と挿入位置指定)を持つ | (試合, プレイ番号) |

- **「プレイ行の論理削除」は投影側のフラグ**であり、**正は墓標・改訂イベント**。フラグだけを書き換える
  経路を作らない(4.0-2「正本は DB の 1 系統のみ」と整合)
- **「任意位置への挿入」はプレイ番号の採番(投影側)**で表す。**イベント連番は世代内で単調増加のまま**
  動かさない。退避イベントの取り込みは「**現行世代の連番として採番し直す**」(REQ:305)ので同じ構造に乗る
- **下流再計算は投影を作り直す**。交代イベントの時点が保持されるため、再計算後も各プレイが**当時の
  出場選手**に紐づく(REQ:234)
- **投影はキャッシュではなく「常に再計算可能な導出データ」**という位置づけ(REQ:954)。**再計算不能な
  正本として持たない**(**P-07**)

**却下案**:

| 案 | 却下理由 |
| --- | --- |
| プレイ行だけを持つ(イベント表を持たない) | 墓標・改訂・べき等キー・世代内連番を置く場所がなくなり FR-012 の同期プロトコルが成立しない。**P-24** に接触 |
| イベント表だけを持つ(投影を持たない) | FR-007 の挿入位置指定・楽観ロック・論理削除の表現が持てず、集計が毎回リプレイになり **NFR-005 違反**(**P-06**) |
| 投影を「正」に格上げしてイベントを監査ログ扱いにする | REQ:147「正本は DB の 1 系統のみ」に反する。訂正の由来が追えない |

### 4-3. 候補案: 識別子を 5 種に分け、役割を混ぜない(論点 9)

| 識別子 | 生成者 | 一意性の範囲 | 役割 | 典拠 |
| --- | --- | --- | --- | --- |
| **べき等キー** | **クライアント** | 再送を同一視できる範囲 | **再送の二重適用を防ぐ**。「同じ操作か」の判定 | REQ:282 |
| **イベント連番** | **クライアント**(採番と追記が不可分) | **(試合, 記録権世代)内で単調増加** | **順序と欠落**の判定(prefix コミット)。墓標が当該連番を消費 | REQ:282-288・299 |
| **記録権世代** | **サーバー** | 試合内 | 引き継ぎのたびに更新。**正史は世代の連結** | REQ:299 |
| **一時 ID(その場登録)** | **クライアント(UUID)** | グローバル | 断中の選手登録。**同期時にサーバーが正式 ID を確定し参照を置換** | REQ:341 |
| **エンティティの内部 ID** | **サーバー** | テーブル内 | 選手 ID は**不変・内部**。名前・背番号は表示用属性 | REQ:338・342 |

**混ぜてはならない理由**:

- **べき等キーと連番は判定の目的が違う** — 前者は「同じ操作か」、後者は「順序と欠落」。1 つにまとめると
  「同じ連番の改訂版」(REQ:288)が表現できない(改訂版は**新しいべき等キー**を持ち**同じ連番**を使う)
- **連番を試合グローバルにしない**(**P-25**)。世代内スコープが正で、**世代なしでは連番が一意にならない**
- **サイドカー結合キーは (試合ID, 記録権世代, イベント連番) の合成**であり、独立した識別子を新設しない
  (**P-02** の「88 列に列を足さない」と同じ発想でキーを増やさない)

**一時 ID の置換について**:

- 置換は「**参照の置換**」であって行の作り直しではない。**置換の記録を残す**(どの一時 ID がどの正式 ID に
  解決されたか)。これは FR-035 の「**統合前の帰属を復元できる情報を保持する**」(REQ:719)と同型の要求で、
  同じ構造で扱える
- **物理型は (B) 論点 13** に送るが、**一時 ID は UUID で確定**している(REQ:341 が「クライアント生成の
  一時 ID(UUID)」と明示)

### 4-4. 履歴文脈の保存形

**取消可能な操作のスタックは (種別, 状態差分) の列**として持つ。

- NFR-019(REQ:901)が比較面に「**取消可能な操作のスタック全体 — 各要素は種別と差分。先頭 1 件だけでは
  ない**」を要求している
- **差分を落として種別だけ持つと連続 undo が実行不能**になる(ADR-003 `:29` — **P-57**)
- **実行時のスタック長に上限はない**(FR-006 の連鎖は空になるまで続く)。ADR-003 の検査上の上限 `D` は
  **保証範囲の上限にすぎない**ので、**永続化側に固定長を仮定しない**
- **undo 自身は取消可能な操作にしない**(REQ:227)。状態補正は **FR-040 が Should** なので、
  **Must 前提として構造に組み込まない**(**P-58**)

**テナント内に閉じる** / イベント表が正本でプレイ行は投影 / 識別子は 5 種を混ぜない。

| 属性 | 内容 |
| --- | --- |
| プレイ | 親(複合参照) |
| 塁 | 一塁 / 二塁 / 三塁 |

- 一意性: **(プレイ, 塁)** で 1 件

### 5-3. 操作イベント(正本。FR-012・3 章用語)

| 属性 | 内容 | 典拠 |
| --- | --- | --- |
| 試合 / **記録権世代** / **連番** | (試合, 世代)内で単調増加。**世代なしでは一意にならない** | REQ:282・299 |
| **べき等キー** | クライアント生成。再送の二重適用を防ぐ | REQ:282 |
| 種別 | **Must は 6 種**(毎球入力 / undo / 交代 / タイブレーク開始 / 試合終了宣言 / 選手のその場登録)。**状態補正は FR-040 採用時のみ**で、**Must 前提として構造に組み込まない**(**P-58**) | REQ:117・164 |
| ペイロード | 種別ごとの内容。**取消可能な操作(確定プレイ・状態補正)は状態差分を持つ**(4-4 節・**P-57**) | REQ:901 |
| **置換・墓標の状態** | **同一連番の改訂版**(新しいべき等キー)で旧版を置換 / **墓標イベントが当該連番を消費** | REQ:288 |
| 適用水位 | **連番に欠落があればそれ以降を適用しない**(prefix コミット)ため、どこまで適用済みかを保持 | REQ:284 |

**一意性の設計**(候補案):

- **べき等キーは一意**
- **(試合, 世代, 連番) は「有効な行が 1 件」** — 改訂版があると同じ 3 つ組の行が複数になるため、
  **`WHERE 置換されていない` の部分一意インデックス**で表す。**述語が固定条件なのでプランナが含意を
  認識できる**(Web 調査 6-2 節 — パラメータ化された述語では使えない場合がある)
- **下位番号の欠番・重複それ自体を拒否しない** — prefix コミットは「欠落があればそれ以降を適用しない」
  であり、**行の存在を拒否する規則ではない**

**履歴文脈は別表を持たない**(候補案): 「取消可能な操作のスタック」は**未取消の取消可能イベントを
連番降順に並べたもの**として導出できる。各要素の (種別, 差分) はイベント自身が持つ(4-4 節)。
**別表に写すと 2 つの正本ができる**(REQ:147 に反する)。

## 6. 記録権・交代・状態補正・退避・適用規則スナップショット(ブロック 1 ②)

### 6-1. 記録権は「世代」を行として持つ(FR-013)

| 属性 | 内容 | 典拠 |
| --- | --- | --- |
| 試合 / **世代番号** | (試合, 世代番号)で一意。**引き継ぎのたびに更新**。試合の正史は**世代の連結** | REQ:299 |
| 保持端末 | 1 試合につき 1 端末 | REQ:299 |
| **確定水位** | 照合は(**保持端末・世代・確定水位**)の 3 点 | REQ:301 |
| 付与 / 失効の時刻 | 失効していない行が**現世代** | REQ:299 |

- **現世代は「失効していない行が 1 件」**として表す(**`WHERE 失効していない` の部分一意インデックス**。
  5-3 節と同じ手法)。**「同時に複数の緊急引き継ぎ要求があった場合、後発は失敗する」**(REQ:302)は、
  **この一意制約がサーバー側の直列化の防壁**になる形で満たす
- **バックアップ復元後のフェンス**(REQ:819「全試合の記録権世代を無効化して新世代を発行」)は、
  **世代を行として持つことで自然に表現できる** — 現世代を一括で失効させ、新世代を発行する
- **一意制約はテナント内に閉じる**(試合がテナントに属するため複合参照で閉じる)

### 6-2. 交代はイベントとして永続化し、投影として「出場区間」を持つ(FR-011)

**旧システムは交代をイベントとして持たず、スタメン JSON の上書きと氏名列の変化からしか読み取れなかった**
(**P-27** が「オーダー表の上書きで表す」を禁止)。

| 表 | 内容 | 典拠 |
| --- | --- | --- |
| **交代イベント**(正本) | 操作イベントの種別の 1 つ。**何回・どのプレイ時点で誰 → 誰**。**DH 解除時の打順配置を明示指定**できるペイロードを持つ | REQ:272・275 |
| **出場区間**(投影) | 試合 / 打順枠または守備位置 / 選手 / **有効開始と有効終了**(イベント連番またはプレイ番号) | REQ:234 |

- **投影として「出場区間」を持つ理由**: 「下流再計算で**交代イベントの時点が保持され**、再計算後も
  各プレイが**当時の出場選手**に正しく紐づく」(REQ:234)を、**プレイ行ごとに選手を焼き込まずに**
  満たすため。区間との突合で当時の出場選手が決まる
- 一意性: **(試合, 打順枠, 有効開始)** で 1 件。区間の重なりは**アプリ層で検証**する
  (排他制約 `EXCLUDE` は範囲型が必要で、`REFERENCES` と同様に RLS の対象外になるため 3-4 節の
  漏洩経路の検討が要る。**(B) として実装時に判断**)
- **移行データでは交代を復元しない**(**P-44**)。出場区間は**移行試合では「不明」を許容**する
  (REQ:767・545)。「不明」を表せる形にする(区間が存在しないことと、区間が不明であることを区別する)

### 6-3. 状態補正は差分を持つイベント(FR-040・**Should**)

| 属性 | 内容 | 典拠 |
| --- | --- | --- |
| 対象 | 回・表裏・得点・S / B / アウト・打順・走者 | REQ:321 |
| **補正前 → 補正後の差分** | **履歴として保持**し後から追跡できる | REQ:324 |
| 位置 | 以降の再計算の起点 | REQ:323・326 |

- **操作イベントの種別の 1 つ**として持つ(別表を作らない)。4-4 節の「取消可能な操作は状態差分を持つ」に
  そのまま乗る
- **履歴に残らない直接上書きの経路を作らない**(**P-28**)。旧システムは「状況変更・タイブレークは
  メモリの `data_list` のみ変更で DB は書かない」= **履歴に残らない生の上書き**だった
- **FR-040 は Should** なので、**構造上の必須にしない**(**P-58**)。種別の語彙に含めるが、未採用なら
  その種別のイベントが発生しないだけ

### 6-4. 退避イベントは原本を残し、取り込みは新規行として採番する(FR-013・FR-035)

| 属性 | 内容 | 典拠 |
| --- | --- | --- |
| 試合 / **旧世代** / 元の連番 | どの世代のどの連番だったか | REQ:303 |
| ペイロード | **原本のまま**。破棄しない | REQ:303 |
| 状態 | 未取り込み / 取り込み済み / (取り込まないと判断した) | REQ:303-305 |
| **取り込み先** | 取り込んだ場合、**現行世代で新規採番した操作イベント**への参照 | REQ:305 |

- **取り込みは「操作者が挿入位置を指定し、現行世代の連番として採番し直す」**(REQ:305)。

  (4.0-2)と、**管理コンソールでの閲覧・書き出しが Must**(REQ:722)であることの両方を満たす
- **「破棄されず退避」が要件**(REQ:303)。取り込まない判断をしても行は残る

## 7. チーム・選手・在籍区分・スタメン・対戦相手チーム(ブロック 2 / 論点 5・8)

### 7-1. 候補案: 「チーム」を 2 つの表に分ける(論点 5)

要件は**テナントと対戦相手チームレコードを別概念と明言**している(REQ:391「FR-035 のチーム登録
(テナント発行)と FR-039 の相手チームレコードは**別概念**」)。さらに:

- **対戦相手チームレコードはテナント内のレコードでテナント間で共有されない**(REQ:112・392・**P-19**)
- **在籍区分は対戦相手チームレコードの選手にも適用される**(REQ:361)
- **紅白戦は先攻・後攻が同一チーム**(REQ:179)
- **自テナント自身も試合の一方の当事者**になる

| 表 | 内容 |
| --- | --- |
| **テナント** | ログイン主体。認証情報・有効/無効を持つ(8 節) |
| **チームレコード** | **テナント内のレコード**。自テナントを表す行と、対戦相手を表す行の**両方**を持つ |

**候補案**: **「試合 → チーム」の参照はすべてチームレコードを指す**。テナントは**チームレコードの
`tenant_id` として現れるだけ**で、試合から直接参照しない。

- **自テナントを表すチームレコードを 1 件持つ**(テナント作成時に生成)。これにより:
  - 紅白戦は**先攻・後攻が同じチームレコードを指す**だけで表現できる(5-1 節)
  - **在籍区分は「チームレコードに属する選手」に一律適用**でき、自チームと相手チームで分岐しない(REQ:361)
  - 試合の当事者が自テナントか相手かは、**チームレコードの `tenant_id` と自テナントを比較**して決まる
- **却下案**: 試合が「テナント参照 + 相手チーム参照」を持つ形 → **紅白戦(両方が自テナント)と
  在籍区分の一律適用の両方が表現しにくくなる**。参照の型が非対称になり、集計クエリが分岐する
- **一意制約はテナント内に閉じる** — 類似名のチームは「**重複の可能性が警告される(意図的なら登録可)**」
  (REQ:389)なので**チーム名に一意制約を置かない**
- **旧システムの `team` テーブルはテナントと対戦相手が同居**していた(`password_hash` の有無で実質区別)。
  移行時は**password_hash を持つ行をテナント、他を相手チームレコードへ振り分ける**(11 節)

## 9. 共同分析グループ・参加・付与・招待(ブロック 4 / 論点 6)

制御資源のテーブル構成と越境経路は 3-5・3-6 節。本節は**ライフサイクルと不変条件**を決める。

### 9-1. 候補案: 参加は履歴として複数行持ち、`active` な行を 1 件に絞る(論点 6)

要件は「**離脱後の再参加は新規参加として計数する**」(REQ:487)と定めており、
**(グループ, テナント) で 1 件とは読めない**。一方で「**終了・離脱も論理削除で保持**」(REQ:947)も要求される。

**候補案**: **参加を履歴行として持ち、`active` な行が最大 1 件**(**`WHERE 状態 = active` の部分一意
インデックス**。5-3 節・6-1 節と同じ手法で 3 回目)。

- **参加テナント上限**(付録C・既定 50)の判定は「**`active` な参加の件数**」で行う。履歴行は数えない
- 「**参加の確定はサーバー側で直列化し、同時受諾でも上限超過を発生させない(先着のみ成立)**」(REQ:479)は、
  **上限検査と挿入を同一トランザクションで行う**ことで満たす。部分一意インデックスは
  「同じテナントが二重に `active` にならない」ことだけを保証する(**上限は件数条件なので制約では
  表現できない** — アプリ層で検査する)
- 離脱は**行の状態遷移**(削除しない)。再参加は**新しい行**を作る

### 9-2. 候補案: 付与は「参加」に紐づける

要件は付与の単位を「**(グループ × 自テナント)**」(REQ:114・480)と定め、**既定はすべて非共有**とする。
一方**再参加時に前の付与をどう扱うかは要件に明示がない**。

**候補案**: **付与を参加行に紐づける**(グループ × テナント ではなく**参加**に紐づける)。

- `active` な参加が 1 件なので、**実効的に「(グループ × 自テナント)で 1 件」になり要件と整合する**
- **再参加時は付与が既定(すべて非共有)から始まる** — 「離脱後の再参加は**新規参加として計数**」
  (REQ:487)であり、**前の付与を引き継ぐと「新規参加」の意味と矛盾する**。かつ既定は非共有(REQ:480)

### 11-1. 候補案: 削除は統一せず 4 系統を別のライフサイクルとして持つ(論点 7)

### 11-3. 索引設計の原則(論点 20 は具体形を (B) へ送るため、原則のみ)

Web 調査(`research.md` 6-2 節)で確認した公式の規則に、本設計の事情を掛けたもの:

1. **`tenant_id` を複合索引の左端に置く**。RLS のポリシー式が `tenant_id = current_setting(...)` の
   単純形なら索引が効く(3-1 節)
2. **列順は「等価条件 → 最初の範囲条件 → ソート列」**。例: `(tenant_id, occurred_at DESC, id DESC)`
3. **論理削除の除外は部分索引の候補** — `WHERE 削除されていない` は**固定条件なのでプランナが
   索引述語の含意を認識できる**(パラメータ化された述語では使えない場合がある)。
   11-1 節のとおり**全集計クエリにこの条件が乗る**ので効果が大きい。ただし
   **削除済みの割合が低い段階では容量削減効果は小さい**ため、`EXPLAIN` と実サイズで検証する
4. **母数併記は `COUNT(*) FILTER (WHERE …)` で分子分母を一度に返す**(REQ:1055 が「割合・率の表示には
   常に母数を併記」)。**各 `FILTER` のために索引を増やすより、共通の `WHERE` を狭める索引が重要**
   (分母を含む集計は基本コストが対象行数に比例する)
5. **JSONB の GIN は B-tree の代替にしない** — 頻繁な絞り込み・結合・GROUP BY のキー(チーム・試合・
   球種・結果)は**正規化列 + B-tree**。JSONB は規則セットのような**試合単位で読むだけ**の構造化値に使う
   (6-5 節)
6. **パーティショニングは初期から採らない** — 設計上限 150 万行は PostgreSQL 公式が示す「閾値は
   アプリケーション依存」の範囲。**非パーティション表 + 実クエリ別 B-tree から始め**、実測サイズ・
   VACUUM・保持年数で再判定する
7. **全件読み込みにならないクエリ形**: 既定が「全期間・全データ」の箇所(分析・カルテ・チーム分析・
   共有集計)は、**`(tenant_id, …)` で絞ってから `GROUP BY` する**形にする。**共有集計は
   「選択されていないテナントのデータを走査しない」ことが測定条件**(REQ:786)なので、
   **対象テナント集合を `WHERE` に入れてから集計する**(3-6 節の制限関数の引数がこれに対応)

**具体的な索引の列挙はしない**(論点 20 = (B))。**実クエリが 1 本も存在しない段階で確定させるのは
H-68 型**であり、原則と検証手段(`EXPLAIN (ANALYZE, BUFFERS)` を RLS 有効状態で確認する)までを決める。

### 12-4. マイグレーション方針(**推奨案** — 最終確定は正本化タスク)

**「最終確定」とは書かない。** 設計書 5.1 の「Alembic は SQLAlchemy 前提。設計フェーズで最終確定」は
**正本化タスクで同一 PR に追随させる**(計画レビュー 1 周目 P1)。

| 項目 | 推奨案 | 根拠(Web 調査 6-3・6-4 節) |
| --- | --- | --- |
| ORM | **SQLAlchemy 2.x** | 設計書 5.1 が前提としている。ADR は正本化タスクで起票を判断 |
| ドライバ | **psycopg 3 に統一**(同期・非同期のどちらか一方) | 同じ dialect で `create_engine()` と `create_async_engine()` の両方を提供。asyncpg は SQLAlchemy 側でも `prepared_statement_cache_size=0` が必要 |
| 接続方式 | **migration は direct connection**、アプリは 3-3 節 | Supabase 公式が direct を migration・`pg_dump`・backup 向けと案内 |
| pooler 対応 | transaction pooler を使う場合は **`prepare_threshold=None`** | **Supabase は transaction mode で prepared statement 非対応と明記** |
| マイグレーション | **Alembic**。**単一 head を維持**し、複数 head は `alembic merge` | 公式 |
| enum | **参照テーブル + FK を既定**(native enum は値セットが非常に安定した場合のみ) | **autogenerate は enum 値の増減を信頼して扱わない**。SQLAlchemy 自身が asyncpg の type OID / prepared statement cache が stale になり得ると警告。語彙は 3 層の DB マスタなので大半は参照テーブル(10-3 節) |
| テスト | **空の PostgreSQL に `alembic upgrade head`** を適用する。**`create_all()` でテスト DB を作らない** | `create_all()` は migration の漏れ・順序・手書き DDL を通らず **drift を隠す** |
| CI | ① 空 DB へ `upgrade head` ② `alembic current --check-heads` ③ **`alembic check`** | `alembic check` は 1.9.0 以降。**RLS policy・trigger・view・enum 値変更は検査しない**ので、それらは **migration SQL のレビュー + スキーマ検査 SQL + 専用テスト**で補う |
| データ migration | DDL と DML を統合しない。小さな初期データは `op.bulk_insert()`、大量バックフィルは段階実行 | 公式が推奨 |
| autogenerate の限界 | **rename は add + drop / 無名制約は検出不可 / sequence は未対応 / server default 比較は既定 off** | 公式が明記。**手動レビューを必須の工程にする** |
| 置き場 | **論点 15((B))** | データモデルの方式を分岐させないため実装計画で決める |

**RLS を採る影響**(3-1 節): **ポリシー・`FORCE ROW LEVEL SECURITY`・`SECURITY DEFINER` 関数はいずれも
`alembic check` の検査対象外**。→ **専用のスキーマ検査テスト**(ポリシーの存在と定義を照合する)を
CI に持つことを推奨案に含める。
