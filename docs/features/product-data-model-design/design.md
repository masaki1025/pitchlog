## 3. テナント分離(論点 2・3・4・12)

### 3-1. 候補案: RLS を防御層として採り、アプリ層の明示条件も残す(論点 3)

**採る。** ただし**アプリ層の明示的な `tenant_id` 条件を省かない**二重構成とする。

**RLS を採れる根拠**:

- **RLS は PostgreSQL のコア機能**(9.5 で導入・拡張不要)であり、Supabase 固有ではない。要件書 REQ:976 の
  「標準 PostgreSQL の範囲で使用し、ホスティング固有機能に依存しない」に適合する(**P-04 に違反しない**)
- ポリシーがなければ **default-deny**。`SELECT` だけでなく `INSERT` / `UPDATE` / `DELETE` に適用される
  (既存行は `USING`、新規・更新後の行は `WITH CHECK`)
- 要件書 REQ:824 は「テナント分離は**初日から全機能に適用**する」、REQ:823 は越境について
  「**内容・存在を含め参照できない**」を要求する。**アプリ層だけの強制は、管理画面・バッチ・将来の
  リポジトリ層・手書き SQL で条件を落とした瞬間に隔離を失う**

**アプリ層の条件を省かない理由**:

- **索引選択と計画安定化** — ポリシー式に頼らず `WHERE tenant_id = :t` を書くことで、
  `(tenant_id, …)` を左端に持つ複合索引が確実に使われる
- **意図の明示** — クエリを読んだだけでテナント境界が見える
- **RLS のバイパス経路が実在する** — 公式が「Superusers and roles with the `BYPASSRLS` attribute always
  bypass the row security system」「**Table owners normally bypass row security as well**」と明記している。
  RLS 単独に安全性を委ねられない

**却下した案**:

| 案 | 却下理由 |
| --- | --- |
| アプリ層強制のみ(RLS を使わない) | 条件の落としが即座に越境になる。DB 境界での deny がない |
| RLS のみ(アプリ層の条件を省く) | 索引選択がポリシー式に依存し、計画が不安定になる。バイパス経路で無防備 |
| Supabase の認可機能に寄せる | REQ:976 に反する(**P-04**) |

### 3-2. 候補案: ロールを 3 つに分ける(論点 3)

**テーブル所有者は既定で RLS をバイパスする**ため、**アプリ用ロールを所有者と分ける**。

| ロール | 用途 | RLS | DDL |
| --- | --- | --- | --- |
| **マイグレーション用**(テーブル所有者) | Alembic の適用・DDL | バイパスする(所有者) | 可 |
| **アプリ用** | 通常の読み書き | **従う**(`BYPASSRLS` を付与しない) | 不可 |
| **共有集計用** | FR-041 の越境読み取り | **従う**(専用ポリシー) | 不可 |

- **superuser をアプリから使わない**
- **`ALTER TABLE ... FORCE ROW LEVEL SECURITY` を全テーブルへ掛ける**ことを推奨する — 所有者がうっかり
  アプリ経路で使われた場合でもポリシーに従わせる。公式が「a table owner can choose to be subject to row
  security with `ALTER TABLE ... FORCE ROW LEVEL SECURITY`」と定めている
- 共有集計用ロールの詳細は **3-5 節**(論点 12)

### 3-3. 候補案: テナント ID はトランザクション内で `set_config(..., true)` により渡す(論点 4)

**接続方式**:

| 経路 | 方式 | 理由 |
| --- | --- | --- |
| **マイグレーション** | **direct connection** | Supabase 公式が direct を migration・`pg_dump`・backup 向けと案内。prepared statement の制約を受けない |
| **アプリ(長寿命のステートレス FastAPI)** | **session pooler を第 1 候補**、transaction pooler を許容 | REQ:975 が「サーバーはステートレス・横断状態もプロセス外」を要求。長寿命プロセスなので session pooler が素直 |

**規律(transaction pooler でも成立する形に統一する)**:

1. **明示した 1 トランザクションの最初**に `SELECT set_config('app.tenant_id', :tenant_id, true)` を発行する
2. ポリシー側は `current_setting('app.tenant_id', true)` を読む
3. **`SET app.tenant_id = …` と `set_config(…, false)` は使わない** — セッション状態になり、transaction
   pooling では物理接続が別クライアントへ再利用されるため**次の利用者へ漏れる**
4. **autocommit で `set_config` と本クエリを別トランザクションにしない** — transaction-local は
   コミット / ロールバックで戻るため成立しない
5. SQLAlchemy は**リクエストごとに `Session` / `AsyncSession` を作り、`begin()` の中で最初に発行**する。
   Session をテナント横断・リクエスト横断で共有しない(`AsyncSession` は複数 asyncio task 間で共有不可)

**第 3 引数の意味は公式で確認済み** — 「If `is_local` is `true`, the new value will only apply during the
current transaction」(`set_config(setting_name text, new_value text, is_local boolean)`)。

**この規律は検査できる**: RLS が default-deny なので、**`set_config` を発行せずにクエリすると 0 行になる**。
「テナントコンテキストを設定しないと何も見えない」ことを結合テストの前提条件にできる。

### 3-4. 候補案: 一意制約はテナント内に閉じ、FK は複合参照にする(論点 2)

**動かせない事実**(PostgreSQL 公式 `https://www.postgresql.org/docs/17/ddl-rowsecurity.html`):

> **Referential integrity checks, such as unique or primary key constraints and foreign key references,
> always bypass row security** to ensure that data integrity is maintained.

> Operations that apply to the whole table, such as `TRUNCATE` and `REFERENCES`, are not subject to row security.

つまり**一意制約と外部キーは RLS を必ず貫通する**。要件書 REQ:823 が「**内容・存在を含め参照できない**」を
要求しているため、素直に設計すると**制約違反エラーが他テナントの行の存在を漏らす**。

#### 規則 1: 一意制約はテナント内に閉じる

- **テナントに属するエンティティの一意制約は、必ず `tenant_id` を先頭に含める**
  (`UNIQUE (tenant_id, …)`)。**グローバル一意制約を置かない**
- **代理キー(主キー)は衝突しない値域を使う**ため、この規則の対象は「業務的な一意性」に限る
- **例外はテナントに属さないもの**だけ — テナント自身のテーブル・システム固定語彙・付録C の設定値
- **この規則は要件と衝突しない**: 要件が一意性を求める箇所(スタメン記憶は「チームにつき最後の 1 件」
  REQ:350 / カルテ所見は「選手 × カルテ種別」REQ:764 / 付与は「グループ × 自テナント」REQ:480)は
  **いずれもテナントかグループの内側**にある。逆に**背番号は明示的に「DB の一意制約は張らない」**
  (REQ:339 / **P-15**)ので対象外

#### 規則 2: FK は禁止しない。テナント内 FK は複合参照にする

**FK 一般の禁止は誤り** — FR-041 の制御資源(グループ・参加・付与)は**複数テナントに跨る関係を持つのが
要件**であり(REQ:824 が「記録・集計とは別のクラス」と定める)、FK を禁じると要件が表現できない。

代わりに**漏洩経路を個別に閉じる**:

| 手段 | 内容 |
| --- | --- |
| **(a) 複合参照** | テナント内の FK は `FOREIGN KEY (tenant_id, game_id) REFERENCES game (tenant_id, id)` の形にする。**参照側の `tenant_id` は自テナントに固定される**ため、他テナントの `id` を渡しても「(自テナント, その id)」という**存在しない組み合わせ**になる。エラーは「**自テナントに無い**」ことしか示さず、他テナントの存在を漏らさない |
| **(b) 事前認可** | 参照値としてアプリ層へ渡す ID は、**自テナントに属することを検証済みのものだけ**にする。検証は RLS 下の `SELECT`(= 見えなければ存在しないのと同じ)で行う |
| **(c) エラーの一律秘匿** | 制約違反の詳細(制約名・値・テーブル名)を**クライアントへ返さない**。FR-034 が「**いずれも理由コードを返さない**」(REQ:623)と定めているのと同じ扱いにする。ログには残す |
| **(d) 越境 FK は「存在が秘匿対象でない」クラスに限る** | 制御資源の参照先(グループ・参加テナント)は**当事者が既に知っている**情報であり、読み取り粒度も REQ:645-651 が定めている。詳細は 3-5 節 |

**残余リスク**: `TRUNCATE` と `REFERENCES` 権限は RLS の対象外。**アプリ用ロールに `TRUNCATE` と
`REFERENCES` を与えない**ことで運用上塞ぐ(GRANT の設計は正本化タスクで詰める)。
