# 調査メモ: 製品データモデル設計の起草(論理データモデル + マイグレーション方針)

## 問い

1. 要件書はどのエンティティ・属性・制約を要求しているか(ブロック 1〜8 の全数)
2. 旧システムの 88 列データ構造と移行制約が新設計に課すものは何か
3. 過去の決定のうち「再提案してはいけない案」と「この起草で決めてよい論点」の境界はどこか
4. リポジトリに既に存在するデータ関連の実体は何か

## 結論(要約)

0. **Web 調査で設計を左右する事実が 1 件出た** — PostgreSQL 公式が「**参照整合性検査(一意制約・主キー・外部キー参照)は常に RLS をバイパスする**」と明記している(原典で確認済み)。テナント跨ぎの一意制約・FK を置くと、**RLS を有効にしても制約違反エラーから他テナントの行の存在が推測できる**。要件書 REQ:823 は「**内容・存在を含め参照できない**」を要求しているため、**一意制約をテナント内に閉じる**必要がある
1. **起草は正本の空白を埋める作業である**。`docs/design/` は未作成で、`backend/` に SQLAlchemy・Alembic・ドライバは**すべて未導入**、モデル定義・マイグレーション・`*.sql`・`CREATE TABLE` は**リポジトリに 1 行も存在しない**。これは意図的な後送り(4-2 / 4-3 の計画書が明記)
2. **要件書 6.1 の表はエンティティの網羅表ではない**。操作イベント・記録権・退避イベント・PDF 出力実績・隔離領域/移行レポート・トークン/セッション・レート制限カウンタ・事前集計・勝敗投手手動指定に 6.1 の行が無く、他条項が独立に永続化を要求している
3. **論理データモデルは意味的にコア領域 5 領域すべてに触れる**(同期プロトコル / 状況計算 / 記録権 / テナント分離 / データ移行)。6.3 は「判定に迷うコードは含む側に倒す」と定める。ただし**人間の逐行確認必須はコード PR の規定**であり、文書の起草に掛かるゲートは **7.3 の確定ゲート(正本化時)**
4. **再提案してはいけない案が 61 件**ある(3 節)。とくに「88 列を物理スキーマにする」「背番号に一意制約」「`users` テーブル・入力者識別列」「試合グローバルの単一連番」「交代をオーダー上書きで表す」は要件・決定で明示的に覆されている
5. **この起草で決めてよい論点は 15 件**(3-3 節)。ORM の選定と Alembic の最終確定もここに含まれる(設計書 `:195` が「設計フェーズで最終確定」のまま)
6. **イベント列が正本で状態は導出**、という切り分けが ADR-003 と要件書から導ける。ただし**要件書はイベントソーシングを明示していない**ため、これは起草が決める論点(5 節 論点 5)

## 調査者の裁定(エージェント間・資料間の食い違い)

### 裁定 1: 旧資料のテーブル数と `game_lineup_snapshot` の矛盾

**食い違い**: `docs/legacy/research/data-layer.md:3` は「**12 テーブル**」で `game_lineup_snapshot` を含まない。`docs/legacy/baseball-scoring-db-structure.md:17` は「**13 個**」で同テーブルを ER 図・詳細表・移行対応表に持つ。**FR-038 の先発オーダー受入基準(要件書 `:763`)はこのテーブルを前提に書かれている**。

**原典で確認した事実**:

- `db-structure.md:3` — 対象は「旧リポジトリ `Baseball_Scoring` develop(**HEAD: ed6a20f 時点**)」、作成日 2026-07-22
- `data-layer.md:11` — 対象は「`C:/develop/baseball_system/config.py`, `settings.py`, `db/` 配下全ファイル」= **別のリポジトリ/作業ツリー**
- **`db-structure.md:8` 自身が優先関係を明記している** — 「⚠ 本書より詳細な一次資料がある: 88 列の**実際の意味**・値例・移行の罠は `research/data-layer.md`(422 行の全数表つき)が**正本**。本書は構造の俯瞰図であり、**移行変換層の実装は data-layer.md を正として行う**こと」
- 要件書 `:960`(6.3)が「旧システムは本書 v1.9 の版固定アーカイブ時点から開発が継続しており**テーブル構成が増えている**ため、アーカイブ後に旧側で追加された領域が移行対象のデータ種別を増やすかどうかを FR-038 の移行仕様で判定する」と**既に未確定事項として登録している**

**裁定**:

- **88 列の意味・値例・移行の罠は `data-layer.md` が正**(`db-structure.md` 自身と要件書 `:761`・付録D-1 が同じ指定)
- **両文書は矛盾していない** — 対象の時点・リポジトリが違う。`game_lineup_snapshot` は **FastAPI 新 UI 期に追加されたテーブル**であり(`db-structure.md:310` が「Streamlit 期の試合にはスナップショット行が存在しない」「更新経路は `POST /{game_id}/lineup-change`」と記録)、要件書 `:960` が言う「アーカイブ後に追加された領域」に該当する
- **本起草はこれを解決しない**。移行対象に含めるかは FR-038 の移行仕様タスクの決定事項。**起草では「先発オーダーの正は最初のプレイ行のスタメン JSON」(要件書 `:763`)だけを制約として扱い、`game_lineup_snapshot` の保全は「移行元の最終オーダー」という別概念として置く**

### 裁定 2: 「当時の値で表示」の適用範囲(要件内の対立)

**食い違い**: 4.0-2(`:144`)は「マスタの事後変更は**確定済み試合に遡及しない**」と述べ、名指しするのは**背番号と適用規則**のみ。4.0-3(`:157`)は「**改名は表示名の変更として ID 経由で全履歴表示に反映される**」= 遡及する。NFR-019(`:905`)は FR-022 の結果表示名の比較に**語彙スナップショット**を要求する。

**裁定**: **矛盾ではなく対象が違う** — 遡及しないのは「背番号」と「適用規則スナップショット」(いずれも 4.0-2 が名指し)、遡及するのは「語彙の表示名」(4.0-3 が名指し)。**語彙スナップショットは対象計算の入力**として渡されるもので(ADR-003 `:96` が「写像テーブルに焼き込むことは禁止」と明記)、**「試合ごとに語彙スナップショットを永続化する」という要求は要件書に存在しない**(spec-checker が全走査して 1 箇所のみ = NFR-019 のテスト入力面)。→ **起草では「スナップショットする対象は背番号と規則の 2 つ」を既定とし、語彙は ID 参照のまま**とする。ただし**背番号の当時値の保持方式は未決**(5 節 論点 2)。

#### 2-2. 記録粒度

- **1 行 = 1 プレイ(原則 1 球)**。ただし**投球でないプレイも 1 行を占める**(列 40「プレイの種類」= 投球 / 牽制 / ボーク / ピッチクロック違反。旧集計は一貫して `== '投球'` で絞る)
- **データモデルはイベントソーシングではなくスナップショット型**(`domain-logic.md:31`)。各行が試合コンテキスト・スタメン・スコアボードを丸ごと持つ非正規化設計
- **打席の識別子が存在しない**。打席の同一性は「回・表裏・打順・打者氏名」の連続と列 17「打席の継続」フラグからしか復元できない
- 走者は「打順番号(0=不在)+氏名文字列+状況ラベル」のトリプレット×3 塁。進塁は状況ラベルからのマッピングで**衝突検出なしの後勝ち上書き**
- **不変条件のガードがない**(S=3 / B>3 / 同一塁走者重複 / 4 アウトを検出しない)。編集バグ由来の「幻の得点・アウト」が実在し得る
- **DB 上に試合終了フラグがない**(列 19「試合継続」にのみ現れる)。**状況変更・タイブレークは DB に書かれない**(メモリのみ)

#### 2-4. 移行がデータモデルに要求する構造

**隔離領域**(制約を満たせない行を**原本のまま保全**)/ **無検閲の取り込み保全**(不整合行を弾かず警告レポートで可視化)/ **解決レポート** / **センチネルの NULL 化と件数突合**(「新 DB の NULL 件数 = 旧 DB で `x<=0`・`球速<=0`・氏名 `'0'` に一致する行数」を**専用検証項目**とする)/ **再実行可能性**(新 DB 初期化・旧 DB は読むだけ)/ **確認ガード** / **列名ベースの読み取り**(位置依存禁止)/ **冪等キー**(旧 `プレイの番号` に UNIQUE 制約がない)。

#### 6-1. RLS(Row Level Security)の採否

**調査者が原典で確認済み**(`https://www.postgresql.org/docs/17/ddl-rowsecurity.html` を自分で参照):

- **RLS は Supabase 固有ではなく PostgreSQL のコア機能**(**9.5 で導入**・拡張不要)。公式ドキュメント第 5 章(データ定義)に記載。→ **要件の「標準 PostgreSQL の範囲で使用し、ホスティング固有機能に依存しない」に適合する**
- **バイパス経路**(原文の引用で確認): 「**Superusers and roles with the `BYPASSRLS` attribute always bypass the row security system**」/「**Table owners normally bypass row security as well**, though a table owner can choose to be subject to row security with `ALTER TABLE ... FORCE ROW LEVEL SECURITY`」→ **アプリ用ロールをテーブル所有者と分ける運用が前提**になる
- **⚠ 設計に効く追加事実**(調査者が原典で発見): 「**Referential integrity checks, such as unique or primary key constraints and foreign key references, always bypass row security** to ensure that data integrity is maintained」/「Operations that apply to the whole table, such as `TRUNCATE` and `REFERENCES`, are not subject to row security」→ **一意制約と外部キーは RLS を必ず貫通する**。テナント跨ぎの FK・グローバル一意制約を置くと、**RLS を有効にしても制約違反エラーから他テナントの行の存在が推測できる**(要件書 REQ:823 の「**内容・存在を含め参照できない**」に触れる)。**一意制約はテナント内に閉じる**設計が必要
- ポリシーがなければ **default-deny**。`SELECT` だけでなく `INSERT`/`UPDATE`/`DELETE` に適用(既存行は `USING`、新規・更新後の行は `WITH CHECK`)

**プーラーとテナント ID の受け渡し**(**この設計の最大の落とし穴**):

- transaction pooling では物理接続が**トランザクション終了時に別クライアントへ再利用**されるため、セッションレベルの `SET` は次の利用者へ漏れる
- **正しい方式**: 明示した 1 トランザクションの**最初**に `SELECT set_config('app.tenant_id', :tenant_id, true)` を発行し、ポリシー側は `current_setting('app.tenant_id', true)` を読む。**調査者が原典で確認済み**(`https://www.postgresql.org/docs/17/functions-admin.html`)— 署名は `set_config(setting_name text, new_value text, is_local boolean)` で、公式の原文は「**If `is_local` is `true`, the new value will only apply during the current transaction**」
- **`SET app.tenant_id = ...` と `set_config(..., false)` は使わない**(セッション状態になる)。**autocommit で `set_config` と本クエリを別トランザクションにすると成立しない** — 設計とテストで明示的に防ぐ
- SQLAlchemy は**リクエストごとに `Session` / `AsyncSession` を作り、`begin()` の中で最初に `set_config(..., true)`**。Session をテナント横断・リクエスト横断で共有しない(`AsyncSession` は複数 asyncio task 間で共有不可)

**性能とアプリ層強制との比較**:

- 「RLS が索引を無効化する」という一般則はない。単純な `tenant_id = current_setting(...)::uuid` なら **`tenant_id` を先頭に持つ B-tree 索引が効く**。ポリシー内の副問い合わせ・関数は行ごとのコストになる
- 「どちらが実務で多数派か」を示す**信頼できる公式の比較・統計は確認できず**
- 調査の結論: **RLS を防御層として採用し、通常クエリにも明示的な `tenant_id` 条件を残す**(安全性を RLS に委ねるのではなく、索引選択・意図の明示・計画安定化のため)

#### 6-2. 索引設計とパーティショニング

- **150 万行を理由に初期からパーティション化する必要はない**。公式は「閾値はアプリケーション依存」としており、**非パーティション表 + 実クエリに基づく索引から開始**し、表・索引サイズ・VACUUM・実測プラン・保持年数で再判定するのが合理的
- **複合 B-tree の列順**: 左端から **等価条件 → 最初の範囲条件 → ソート列**(`https://www.postgresql.org/docs/17/indexes-multicolumn.html`)。ページングの典型は `(tenant_id, occurred_at DESC, id DESC) WHERE deleted_at IS NULL`
- **`INCLUDE`** は検索・並び替えに使わないがレスポンスに必要な**狭い列**を載せて index-only scan を狙う用途。広い JSONB を含めると索引肥大。index-only scan の実効性は **visibility map と VACUUM に依存**
- **部分索引**は「論理削除の除外条件が全クエリに乗る」ケースの候補。ただし**クエリの条件が索引述語を論理的に含意するとプランナが認識できる場合だけ**使える(`deleted_at IS NULL` のような固定条件は適するが、パラメータ化された述語では使えない場合がある)。**削除済み行の割合が低い段階では容量削減効果は小さい**
- **JSONB GIN は B-tree の代替ではない**。頻繁な絞り込み・結合・GROUP BY のキー(チーム・試合・球種・結果)は**正規化列 + B-tree**、JSONB GIN は任意・低頻度・スキーマ変動属性の検索補助
- **`COUNT(*) FILTER (WHERE ...)`** は同じ入力集合から**分母と複数の分子を一度に返せる**(母数併記の要件に直接効く)。ただし分母を含む集計は**基本コストが対象行数に比例**するため、各 `FILTER` のために索引を増やすより**共通の `WHERE` を狭める索引**が重要
- **サマリ更新の選択肢**: アプリ側同一トランザクションで upsert(強整合だが全書込み経路の統制が必要)/ DB trigger(漏れにくく原子的だが書込み遅延・再集計が複雑)/ **マテリアライズドビュー**(`REFRESH` は**全体置換でリアルタイム・増分更新ではない**。`CONCURRENTLY` には**全行を覆う列のみの UNIQUE 索引と populate 済み**が必要で、同一 MV への同時 refresh は 1 本だけ)/ **バッチ・インクリメンタル集計表**(対象テナント・対象期間だけ再計算でき、無期限保持に最も運用しやすい)

#### 6-3. Alembic の運用

- **単一 head を維持**。複数 head が生じたら `alembic merge` で merge revision を作る(`down_revision` は「親」であり履歴を直線化するために書き換えるものではない)
- **autogenerate の公式な限界**: table / column の rename は **add + drop として出る** / **無名制約は検出不可** / 一部の独立した PK・EXCLUDE・CHECK の変更は未対応 / **sequence の追加削除は未対応** / 型比較は既定で有効だが型引数の片側だけが既定値の場合は比較しない / **server default 比較は既定 off**(`compare_server_default=True` にしても完全ではない)/ 現行 1.19 の名前付き CHECK は**名前ベース**で同名の式変更は差分とみなされない
- **enum**: PostgreSQL native enum は独立した schema object。**Alembic autogenerate は enum 値の増減を信頼して扱わない**。SQLAlchemy 自身が「DDL による enum 変更で **asyncpg の type OID / prepared statement cache が stale になり得る**」と警告している。→ **値が将来増減する業務区分は参照テーブル + FK か制約付き text**、値セットが非常に安定している場合だけ native enum
- **テストは `alembic upgrade head` を空の PostgreSQL に適用する**。`create_all()` だけでテスト DB を作ると **migration の漏れ・順序・手書き DDL を通らず drift を隠す**
- **CI での検査 3 段**: ① 空 DB に `upgrade head` ② `alembic current --check-heads` ③ **`alembic check`**(1.9.0 以降。「autogenerate したら pending upgrade ops が出るか」を検査)。**`alembic check` は autogenerate 非対応のもの(RLS policy・trigger・view・enum 値変更)まで検査しない** → migration SQL のレビュー・スキーマ検査 SQL・専用テストで補う
- **データ migration**: 公式は DDL と DML の統合を勧めていない。小さな初期データは `op.bulk_insert()`、大量バックフィルは「拡張 DDL → 別スクリプトで段階実行 → 制約化・旧列削除」
- **既存 DB への初回導入**: 既存 schema を正確に表す baseline revision を作成・**検証**してから `alembic stamp`(migration は実行されない)。**一致していない状態で stamp してはいけない**

#### 6-4. psycopg 3 と asyncpg

- SQLAlchemy 2.x は `psycopg2` / `psycopg`(3)/ `asyncpg` を公式サポート。**`psycopg`(3)は同じ dialect で同期 `create_engine()` と非同期 `create_async_engine()` の両方を提供**する。`postgresql://` の既定は依然 psycopg2
- **asyncpg は transaction pooling 下の prepared statement に既知の問題**(`prepared statement ... does not exist` / `already exists`)。asyncpg 公式は **`statement_cache_size=0`** と `Connection.prepare()` を使わないこと、または session pooling への切替を案内。**SQLAlchemy の asyncpg dialect は全ての文を `prepare()` で処理し既定 100 件のキャッシュを持つ**ため、**SQLAlchemy 側も `prepared_statement_cache_size=0` が必要**
- **Supabase は transaction mode で prepared statement 非対応と明記**。psycopg は `prepare_threshold=None`。psycopg 3.2 以降は PgBouncer 1.22+・`max_prepared_statements > 0`・libpq 17+ なら対応可能だが、**PgBouncer の構成要件を満たす場合だけ**
- **Supabase の接続方式 4 種**: direct(**migration・`pg_dump`・backup・長寿命 backend 向け**)/ shared session pooler(IPv4-only 環境の長寿命 backend・prepared statement 可)/ transaction pooler(serverless・短命接続・**prepared statement 不可**)/ dedicated PgBouncer transaction pooler(有料プラン)
- **同期と非同期の一般的な勝敗を示す公式ベンチマークは確認できず**。FastAPI 公式は「不明なら通常の `def`」とし混在可能とする
- 調査の結論: **長寿命のステートレス FastAPI なら psycopg 3 を同期・非同期の一方で統一するのが堅実**。transaction pooler を採る場合は上記の必須設定を置き、**migration は direct connection で実行する**
