# 調査メモ: alembic の fileConfig によるアプリロガー無効化の是正

## 問い

1. この欠陥は要件のどれを壊しているか。「NFR-015 違反」と書いてよいか
2. `disable_existing_loggers=False` は alembic 自身のログ設定を壊さないか
3. `env.py` / `alembic.ini` が現在の形になった経緯に、意図的な決定はあるか
4. コア領域判定はどうなるか。1 行修正でもゲートは重いのか
5. TSK-387 で入れた `error_logger` フィクスチャは撤去できるか

調査は 2 並列(spec-checker = 要件突合 / decision-tracer = 決定経緯)+ 自分の実測。
legacy-analyst は外した — ロギング設定は旧 Baseball_Scoring と接する面が無い。

## 結論(要約)

1. **「NFR-015 違反の是正」と書くのは過大。** 正しくは「**NFR-015 の顕在化経路のうちログ側が
   将来無効化されるのを防ぐ予防的是正**」。**アプリのプロセスは `env.py` を import しない**ため、
   現時点で製品の挙動は壊れていない。
2. **`disable_existing_loggers=False` は alembic 自身の設定を 1 つも変えない**(実測)。
3. **意図的な決定の記録は無い**。alembic テンプレート既定と同形だが、「テンプレートを採った」という
   記録すら残っていない。**アプリ側のロギング方針は未決**。
4. **コア領域で確定**。ただし「5 領域だから 5 倍重い」は誤り — core-guard は**二値判定**で、
   1 領域該当でも要求は同じ。**重いのは「コアかどうか」の 1 段だけ**。
5. **撤去の可否を判断できる記録は無い。** 撤去するなら **TSK-387 の明示的判断を上書きする決定**として
   計画書に書く必要がある(単なる後始末とは書けない)。

## 詳細と典拠

### A. 欠陥の実体(自分の実測)

**`fileConfig` を呼ぶのはリポジトリ全体で 1 箇所だけ**。`dictConfig` / `basicConfig` はゼロ。

| 箇所 | 内容 |
| --- | --- |
| `backend/migrations/env.py:16-17` | `if config.config_file_name is not None: fileConfig(config.config_file_name)` — alembic テンプレートと同形 |
| `backend/alembic.ini:6-7` | `[loggers] keys = root,sqlalchemy,alembic` — **`pitchlog` 系の qualname は無い** |

`fileConfig` の既定は `disable_existing_loggers=True` なので、**呼び出し時点で生成済みの
非列挙ロガーがすべて `disabled = True` にされる**。

**実測**(`backend/` で計測):

| 状態 | app(`pitchlog.api.errors`) | alembic | sqlalchemy.engine | root handlers |
| --- | --- | --- | --- | --- |
| 初期 | 有効 | NOTSET | NOTSET | 0 |
| **既定 `True`** | **無効化される** | INFO | WARNING | 1 |
| **`False` 指定** | **有効のまま** | INFO | WARNING | 1 |

→ **alembic 側の 3 値が完全一致**。`disable_existing_loggers=False` は
「alembic は自分の設定だけする」という最小の介入であり、alembic の意図した構成を壊さない。

### B. 要件との突合(spec-checker・原典で裏取り済み)

#### B-1. ログに関する要件の全数

| 条項 | 典拠 | 要旨 |
| --- | --- | --- |
| **NFR-015 失敗の黙殺防止**(Must) | 要件書 `:872-875` | 「保存・同期・バックアップ・出力の失敗、スキップ、自動補正は、利用者**または**管理者が気づける形(**画面通知・ログ**)で必ず顕在化する」 |
| NFR-016 死活監視(Should) | `:877-880` | 外形監視。**ログの条項ではない** |
| NFR-017 ログ保持(Should) | `:882-885` | サーバーログを 30 日以上保持。測定 = **構成確認**(運用インフラ側) |
| NFR-014 シークレット(Must) | `:867-870` | **リポジトリに含めず環境変数で管理**。**ログ出力については何も言っていない** |
| NFR-011 の測定方法 | `:855` | 「DB・コード・**ログ**のレビュー」— 測定手段の列挙であって規範条項ではない |
| FR-035 管理者操作ログ | `:743`・`:988` | **DB に記録**する破壊的操作ログ。アプリケーションログとは別資源 |

**ログの出力先・形式・水準・ロガーの構成方法を定めた条項は要件書に存在しない(規定なし)。**
改善台帳にも該当する `I-*` は無い。

→ **スコープを 1 行に締める根拠**: これを超えて formatter / level / アプリ側 logging 設定の新設へ
踏み込むと、**根拠となる条項が存在しない設計判断**になる。

#### B-2. 何を壊しているかの判定

**現時点では要件違反と言えない。** 根拠:

- NFR-015(`:874`)は顕在化手段を「画面通知・**ログ**」の**選択肢**として示し、ログを唯一の手段と定めていない
- 顕在化の対象も「**保存・同期・バックアップ・出力**の失敗・スキップ・自動補正」に限定され、
  未捕捉例外一般と完全には重ならない
- **アプリのプロセスは `env.py` を import しない**(`backend/src/` に `command.upgrade` /
  `lifespan` / `startup` の一致 0 件)。現に無効化が起きるのは **pytest プロセスの中だけ**

**過小にも言わない**: 起動時マイグレーション・移行実行器・管理コマンドを**アプリと同一プロセス**で
走らせた瞬間に `logger.exception()` が 1 件も出なくなる。喪失対象が「保存・同期・バックアップ・出力の失敗」
であれば **NFR-015 の顕在化経路のうちログ側が丸ごと失われる**。
測定方法「障害注入テストで通知を確認」(`:875`)に照らせば、ログを通知経路に数える設計を採る限り、
この欠陥は測定を通らない構成になる。

→ **計画書に書く表現**: 「NFR-015 違反の是正」ではなく
「**NFR-015 の顕在化経路のうちログ側が将来無効化されるのを防ぐ予防的是正**」。

#### B-3. 修正が新たに触れる要件 — いずれも中立

| 要件 | 判定 |
| --- | --- |
| NFR-014(`:869`) | **中立**。射程は「リポジトリに含めない」ことだけで、ログ出力の内容を規律していない |
| NFR-017(`:884`) | **中立**。保持期間の構成要件で、出力先・量・ローテーションを規定していない |
| Won't(`:96-109`) | **衝突なし** |

補足(要件由来ではない事実): SQL エコーによる接続情報漏れの懸念は、`backend/alembic.ini:20-23` が
`logger_sqlalchemy`(`qualname = sqlalchemy.engine` / `level = WARNING`)を**明示**しており、
この logger は `disable_existing_loggers` の値に関わらず ini により設定される。
**本修正で SQL エコーが有効化されることはない。**

#### B-4. FR-038 とテスト種別

- **マイグレーション実行時のログを定めた要件は無い**。FR-038(`:774-790`)が要求するのは
  **レポート**(移行結果・解決・警告・センチネル突合)であってログではない
- **意味範囲としては FR-038 の射程外** — 設計書 6.3 の境界定義表(`:390`)のデータ移行行の除外欄に
  「**旧データと接しない新スキーマ内部の通常マイグレーション — 通常レビュー + テスト**」
- **NFR-019**: 該当するのは柱書の backend pytest のみ。(a) 一致性は NFR-018 の対象計算に限定、
  (c)(d) は射程外。**(b) 越境テストは発効しない**(`:933` — 製品の外から到達できる経路を
  新設も変更もしない)。**網羅の総量は 1 件も減らない**

### C. 決定経緯(decision-tracer・原典で裏取り済み)

#### C-1. `env.py` / `alembic.ini` を意図的にそう決めた記録は無い

- 作ったのは **TSK-343**(`docs/features/orm-schema-migration/`)のステップ 2
  「Alembic の骨組み・URL 正規化・最小 revision・`target_metadata` の配線」(`plan.md:768`)
- **ステップ 2 の合格条件にロギングに関する条件は 1 つも無い**
- `docs/features/orm-schema-migration/**` を `ロギング|logging|logger|ログ` で走査して **0 ヒット**
- `構造化ログ|ログ基盤|ログ形式|ログ設定|logging.config|dictConfig|basicConfig|ログ水準|ログレベル` の
  リポジトリ全体走査で、設計・決定を述べた箇所は **0 件**

→ **テンプレート既定を採ったのか検討の末なのかは不明**(典拠が無い)。
ただし**検討した形跡が残っていない**ことは網羅走査で言える。

#### C-2. アプリ側のロギング方針は未決

- **ロギングを扱う ADR は存在しない**(ADR-001〜004 のみ)
- `backend/src/pitchlog/api/errors.py:13` の `logging.getLogger(__name__)` が**唯一のロガー取得**で、
  **アプリ起動時の logging 設定コードはリポジトリに存在しない**
- 決まっているのは **U-00 の器の中だけ** — 例外 → ログ水準の写像(`u00-api-shell/design.md:76-83`)と
  ログの規律(同 `:100-110`)

→ 計画書に「**この修正はロギング方針の決定ではなく、既存ロガーの無効化という副作用の除去である**」
と書ける。**ただし厳密には**、`disable_existing_loggers=False` は
「alembic 実行時に `[loggers]` 非列挙のロガーを生かす」という挙動変更であり、
`alembic.ini` の既存設定(`[logger_root] level = WARNING` 等)は変更されない — **この区別を明示する**。

#### C-3. `backend/migrations/*` の 5 領域登録

**TSK-343 の決定**(`docs/features/orm-schema-migration/design.md:547-581`):

- 6.3 規則②(混在ファイルはファイル全体)③(重複帰属可)④(**過剰包含は PR 単位の例外で外さず、
  モジュール分割してから狭める**)+「判定に迷うコードは**含む側に倒す**(fail-closed)」
- `:577`「**全 DDL を含む Alembic revision は混在ファイルなので 5 領域すべてへ重複登録**」
- glob(`backend/migrations/*`)にした理由 = 「後から足すファイルも自動で覆われ、
  **新規ファイルの登録漏れ(H-12 の再発型)を構造で防げる**」

**6.3:390 の除外欄をこの件に使えるか** — 使えない。
TSK-343 自身が同じ除外の適用を**明示的に撤回**している(`design.md:585-587`)。
かつ同除外は **migration revision の内容**についての意味範囲であり、
`env.py` / `alembic.ini`(ログ設定)を想定した記述ではない。両者を結びつける記録は無い。

**規則④が「軽いから外す」を明文で禁じている**(設計書 `:393`)。

#### C-4. 「5 領域だから重い」は誤り(重要な訂正)

`scripts/core_guard.py:212-226` の `matched_paths()` は
`path in guard_paths or any(fnmatch...)` の**二値判定**で、**該当領域の数を数えていない**(実測)。
台帳にも候補として記録済み(`harness-evaluation.md:1825-1847`)。

→ **1 領域該当でも 5 領域該当でも、CI の要求も人間の作業量も変わらない。**
重いのは「**コアかどうか**」の 1 段だけ。要求は敵対レビュー + **人間の逐行確認(必須)**+
実施記録行(設計書 `:372` `:378` `:380`)。

### D. 既存の構造検査はこの分岐を踏んでいない(実測)

`backend/tests/test_alembic_environment.py:52-56`:

```python
class _ConfigStub:
    """env.py のオフライン読込に必要な最小設定。"""

    config_file_name: str | None = None
```

`env.py:16` は `if config.config_file_name is not None:` なので、
**既存の構造検査は `fileConfig` の分岐に一度も入らない**。
`fileConfig` の呼び出し形を検証するテストは**現状ゼロ**。

**同ファイルは 5 領域すべての core paths**(実測 — `.claude/core-areas.json` の全 area に
`backend/tests/test_alembic_environment.py` が登録済み)。
→ **ここにテストを足してもコア射程は増えない**(既にコア)。

### E. `error_logger` フィクスチャの撤去可否

**撤去の可否に直接答える記録は無い。** あるのは位置づけだけ:

- `backend/tests/api_fixtures.py:23-25` の docstring —
  「これはテスト隔離のための手当てであり、**env.py 側の是正は別タスクの射程**である」
- `docs/worklog/2026-09-16-u00-api-shell.md:101`「**製品コードの欠陥ではなくテスト隔離の問題**」

**撤去に反対する方向の記録がある** — 同 worklog `:106-108`:
「**表明は弱めていない** — 各テストの冒頭で `assert not ...disabled` を置き、
無効化されたまま素通りしない形にした。**毒性値の否定テストも対象に含めた**
(ロガーが無効だと『毒性値が出ない』が自明に成立し、表明が空洞になるため)」

→ **撤去するなら「TSK-387 の明示的判断を上書きする決定」として計画書に明記が要る。**
単なる後始末としては書けない。

なお `backend/tests/api_fixtures.py` 自体はどの core paths にも該当しない。
ただし同一 PR に `backend/migrations/env.py` が入る以上、**PR 全体はコア判定**になる(二値)。

## 未解決・申し送り

① **テストをどこに・どう置くか** — `fileConfig` 後もアプリのロガーが `disabled` でないことを固定したい。
   既存の `test_alembic_environment.py` は `config_file_name = None` で分岐に入らない(D)。
   **【2026-09-16 訂正・敵対レビュー 1 周目 P1】** 当初ここに「`env.py` を実際に読み込ませる検査は
   DB 接続が要る」と書いたが**誤り**。既存テスト(`test_alembic_environment.py:84-97`)は
   `runpy.run_path` + `monkeypatch` で**オフライン実行しており DB 接続を必要としない**。
   したがって `config_file_name` に実 `alembic.ini` を渡すだけで `env.py:17` を直接検査できる。
   計画書の決定③がこの形を採る。

② **`error_logger` を撤去するか** — 撤去すれば根本是正が 387 のテストで直接証明される。
   残せば二重の防御になるが、不要な手当ての残存は後から読む人を誤解させる。
   **撤去するなら TSK-387 の判断を上書きする決定として明記する**(E)。

③ **`alembic.ini` に `pitchlog` ロガーを足す案との比較** — `[loggers]` に追加する手もあるが、
   **アプリのロギング方針が未決の段階で alembic.ini がアプリのログ水準を決めてしまう**。
   `disable_existing_loggers=False` のほうが介入が小さい。/plan で選択肢と根拠を書く。

④ **重さ分類は `コア領域` で確定**(C-3)。6.3:390 の除外は使えず、規則④が例外を禁じている。
   ただし「5 領域だから重い」とは書かない(C-4)。

⑤ **台帳の未処理の申し送り** — `harness-evaluation.md:2756`「昇格の可否は PO 判断事項として上げる」
   (候補「検証コマンドを人が選ぶと…」の `H-*` 採番)。**本タスクの射程ではない**が、
   同じ事象から派生しているので計画書で参照する。

⑥ **Web 調査は未実施** — `disable_existing_loggers` の既定が `True` である理由や、
   他プロジェクトでの回避の定石が要るなら /research(外部委任)を併用する。本メモはリポ内調査のみ。
