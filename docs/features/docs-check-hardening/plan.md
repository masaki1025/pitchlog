### 変更履歴表の判定条件

**見出し名に依存させない** — 変更履歴表を持つ 6 正本のうち **4 件は `## 変更履歴` 見出しを持たない**(H1 直後に表がある)。

1. frontmatter を除いた本文から走査。**`^#{2,6}\s` に一致する見出しで打ち切る**が、`^##\s+変更履歴\s*$` は打ち切らず読み飛ばす。**既存の `SECTION_HEADING_RE`(`^##\s+`)を再利用してはならない** — H2 だけに一致するため、**変更履歴表より前に H3 があると打ち切られず後続の表を誤受理する**(3 周目 P2)。新しい定数を置く
2. 最初の `|` 始まり行から表を取る。取れなければ違反
3. ヘッダは `cells[:3] == ("版", "日付", "変更内容")` かつ `len(cells) >= 4` かつ `cells[3] in {"状態", "変更者"}`
4. 各行の `cells[0]`(太字除去後に版形式)・`cells[1]`(**実在する日付**)を検証。不正セルは違反(fail-closed)。**索引の最終更新列にも同じ実日付検証を適用する**(2 周目 P2)

**日付は正規表現だけで判定しない**(1 周目 P2): `^\d{4}-\d{2}-\d{2}$` は `2026-02-31` や `2026-99-99` を受理してしまう。不正日付が最大日付として突合に入るため表現上の問題ではない。**`datetime.date.fromisoformat` 相当の実日付検証**を行い、負例を置く。

**版の比較は数値タプル**(1 周目 P1): `0.9 → 0.10 → 0.11` が実在する(`docs/development/dev-harness-design-2026-08-07.md:17-19`)。`tuple(int(part) for part in version.split("."))` で比較すれば `(0,9) < (0,10) < (0,11)` となる。**現リポの最大版は `1.4` なので文字列比較の誤実装でも統合テストが通ってしまう** — したがって `0.9 / 0.10 / 0.11` だけを持つ最小リポの正例・負例を必ず置く。

### 免除の定数 — grandfather に限る(PO 裁定 1・2 周目 P0)

**免除はパスではなく「そのパスの現在の内容」に固定する**(4 周目 P0)。パスだけの allowlist にすると、**マージ後に免除文書を編集しても変更履歴なしで通る**性質が残り、「既存内容のみの免除」という宣言と機構が一致しない。

```python
# 既存の未是正 3 件を、その「現在の内容」に限って暫定除外する(grandfather)。
# 新しい運用規則ではない — 規約(設計書 7.1-3・.claude/rules/docs.md)は
# 「正本は変更履歴表を持つ」を例外なく要求しており、本表は
# その規約違反が既に存在する事実を機械検査から外しているだけである。
#
# 内容が 1 バイトでも変われば免除は外れて違反になる(fail-closed)。
# 免除文書を編集したいなら、そのとき変更履歴表を持たせるか、
# 設計書 7.1-3 に免除区分を明記して版繰り上げ + 確定ゲートを通すこと。
#
# 将来 ADR を標準テンプレート(変更履歴表を持たない)から作ると検査が落ちる。
# それは意図した挙動 — その時点で 7.1-3 の改訂判断を強制する。
CHANGE_HISTORY_EXEMPT_DIGESTS = {
    ("docs", "adr", "ADR-001-codex-model-selection.md"): "<sha256>",
    ("docs", "adr", "ADR-002-frontend-vue.md"): "<sha256>",
    ("docs", "requirements", "requirements-draft-pitchlog.md"): "<sha256>",
}
```

ダイジェストは**実装時に計算して埋める**(改行を正規化せず、ファイルのバイト列そのものの SHA-256)。**免除パスに載っているがダイジェストが一致しない場合は違反**とし、理由に「免除は起票時点の内容に限る。**変更履歴表を持たせたうえで免除エントリを削除すること**」を出す。

| やること | やってはいけないこと |
| --- | --- |
| 免除文書を正規化するとき: **① 変更履歴表を新設する ② 同じ PR で免除エントリを削除する**。以後その文書は通常の検査対象になる | **ダイジェスト値の更新は禁止**。再計算して差し替えると**編集後の内容を再び grandfather することになり、4 周目 P0 で閉じた「履歴を残さず正本を書き換える経路」が復活する** |

**この非対称が重要**: ダイジェスト不一致は「免除の失効」を意味し、**免除表を直して黙らせるのではなく、文書側を規約に合わせて免除表から外す**のが唯一の正しい対処である。コード内コメントにもこの旨を書く。

**ディレクトリ単位の免除(`docs/adr` 全体)は採らない** — それは将来の全 ADR に及ぶ**恒久的な運用規則の変更**であり、設計書 7.1-3 の改訂 + 版繰り上げ + `/finalize-doc` を要する(2 周目 P0)。本タスクの範囲(PR レビュー)では実施できない。

**免除文書は索引の版が `—` であることを要求**する(版を持たない正本であることを機構側でも固定する)。

**免除の意味は「既存内容の未是正を機械検査から外すこと」に限る**(3 周目 P0)。上記のダイジェスト固定により、**この意味は機構側で強制される**(4 周目 P0 — 3 周目の時点では「本タスクでは編集しない」という運用側の制約だけで、マージ後の編集経路が開いたままだった)。本タスクでも免除対象 3 文書は編集しない。

**申し送り**: 「ADR 様式に変更履歴表を導入するか / 設計書 7.1-3 に免除区分を明記するか」は**未決**。台帳の `## 候補` へ起票し、次に ADR を新設するタイミングで決める。

**4 列目を許容リストにする根拠**: 規約 `.claude/rules/docs.md:9` は `状態` とするが、**要件書の実体は `変更者`**。規約側は approved 正本なので書き換えない。**この三者不一致は台帳の `## 候補` へ起票**する。

### 逆突合

**`EXCLUDED_PREFIXES` に `("docs","features")` を足してはならない** — `check_repository` が同じ `is_excluded` を `plan.md` の検査にも通しているため、足すと **`docs/features/*/plan.md` の検査が全部無効化される**。

`is_excluded` に既定引数 `prefixes` を追加(後方互換)し、`INDEX_COVERAGE_EXCLUDED_PREFIXES = EXCLUDED_PREFIXES + (("docs","features"),)` を**別定数**で持つ。`docs/README.md` 自身の除外は `INDEX_RELATIVE_PATH` 定数との一致で行う(索引が自分の行を持たないのは設計書 7.1-5 の設計どおり・台帳 H-16 が判定済み)。

**将来の落とし穴をコメントで残す**: 設計書 `:591` は `docs/ops/nfr021-acceptance/` の個々の証跡を「索引に載せない」と定めている。当該ディレクトリが生まれた時点で除外追加が必要(いま投機的に定数へ入れない)。

### 宣言突合(ステップ 7〜8)

**`check_docs_status.py` に入れず別スクリプトにする** — `git diff` + `plan.md` パースは「正本の status 検査」ではなく、`--root` だけの純粋な FS 検査という性質(テストが `tmp_path` だけで済む理由)を失う。

`scripts/check_plan_docs_sync.py`。`scripts/core_guard.py` の `GuardError` + 変更パス取得(`subprocess.run` + timeout + **fail-closed**)の書き方を踏襲する。

- **突合対象** = `docs/README.md` ∪ **base 側索引の掲載正本 ∪ HEAD 側索引の掲載正本 ∪ HEAD の FS 上の非除外 `docs/**/*.md`**(4 周目 P1 — 索引駆動だけにすると、**新設正本を索引行と 3 節の宣言の両方から落とした場合にすり抜ける**。`/pr` の契約は「**新設する正本の配置先**」も突合対象としている)。除外は `.claude/skills/pr/SKILL.md` 手順 2-2 と `docs/features/harness-evaluation/design.md` 4 節に従う
  - **和集合にする理由**(1 周目 P1): HEAD 側だけを見ると、**正本とその索引行を同じ差分で削除したときにすり抜ける** — 削除済み文書は現在の索引にも FS にも存在せず、`git diff` の削除パスが「対象外」として捨てられ、`docs/README.md` の変更だけ宣言すれば通ってしまう
  - **変更種別を保持する**: `--name-only` ではなく **`--name-status`** で取得し、**削除(`D`)・改名(`R`)を扱う**。踏襲元の `core_guard.py` はパス名しか返さないため、この点だけは踏襲せず拡張する

- **抽出は 1 行に複数マッチを許す**(1 周目 P2): 本計画書の「反映なし」行には Markdown リンクが**複数**並んでいる。**1 行につき最初のリンクだけを取る誤実装でも、差分がなければ実リポの exit 0 を通過してしまう** — したがって合格条件は「本計画書 §3 から**期待される対象集合を完全一致で検証**する」とし、1 行に複数リンクを置いた正例を必ず含める

### 本タスク自身の検証手段

- 各ステップで **`uv run pytest tests/`** と **`uv run python scripts/check_docs_status.py`**(exit 0)
- `docs-lint` の lychee(Markdown のリンク切れ。`docs/legacy` は除外)
- **負例の実効性を手で 1 度確かめる** — 索引から 1 行消して逆突合が exit 1 になること / 要件書の変更履歴表を一時的に壊して検査が exit 1 になること(確認後に `git checkout` で戻す)
- `/check` を PR 前に実行

## 7. 実装時の落とし穴

**本節は Codex への委任時に必ず渡す**(実装者が読むのはこのファイルだけであり、計画モードの検討メモは届かない)。番号順に重要度が下がるわけではない — **1 は事故の規模が段違い**。

| # | 落とし穴 | 起きること |
| --- | --- | --- |
| 1 | **`EXCLUDED_PREFIXES` に `("docs","features")` を足してはならない** | `check_repository` が同じ `is_excluded` を **`plan.md` の検査にも通している**ため、足すと **`docs/features/*/plan.md` の検査が全部無効化される**。逆突合用は `INDEX_COVERAGE_EXCLUDED_PREFIXES` を**別定数**で持ち、`is_excluded` には**既定引数**で渡す |
| 2 | **`frontmatter()` テストヘルパを先に直す** | ステップ 4(変更履歴表の検査)を入れた時点で、**「returncode == 0 を期待する既存 4 テスト」が全滅**する。ヘルパが既定で変更履歴表を含む本文を返すようにしてから検査を足す。個別テストを直す方向に走るとヘルパの意味が壊れる |
| 3 | **履歴行は日付順に並んでいない** | 台帳の実データは `2026-08-12 → 08-13 → 08-14 → 08-13`。「**最終行 = 最新**」の実装は今日は偶然通るが将来壊れる。**最大値で判定**し、その回帰テストを置く |
| 4 | **`—` は U+2014(EM DASH)** | 半角ハイフンや `-` と混同すると索引側で誤検出する |
| 5 | **版は数値タプル比較** | 設計書の版は `0.9 → 0.10 → 0.11` と進む。文字列比較だと `0.10 < 0.9` になる。**現リポの最大版は `1.4` なので誤実装でも統合テストが通ってしまう** — だから `0.9/0.10/0.11` だけを持つ最小リポのテストが必須 |
| 6 | **`**1.0**` の太字版セルが実在** | 設計書の履歴表にある。太字除去なしだと版パースが落ちる |
| 7 | **索引の最終更新は `==` でなく `>=`** | `==` にすると「履歴行を増やさない軽微な本文修正で最終更新だけ進める」正当な運用が落ちる |
| 8 | **ステップ 1 の日付を索引と揃える** | 台帳の変更履歴に追記する日付と、索引の台帳行の最終更新列を**同じ日付**にする。ずれると**ステップ 5 が自分で追加した突合で赤くなる**。※現在の台帳の履歴最大日付と索引はいずれも `2026-08-14` で整合している。**実施日が変わっている場合は両方をその日付に揃える** |
| 9 | **台帳の再編集が新しい破損を生む**(H-42 の再現) | ステップ 1 はまさにその修復である。**文字列置換ではなく節単位の移動**として行い、合格条件の `grep` 群(`^## 候補$` が 1 件・見出し行のバックティック奇数 0 件)で機械的に確認する。※ H-46 の誤挿入は「`## 候補` という文字列の最初の出現が本文中の一文だった」ことが原因 |
| 10 | **`SECTION_HEADING_RE` を変更履歴表の走査に再利用しない** | `^##\s+` は **H2 だけ**に一致する。変更履歴表より前に H3 があると打ち切られず、後続の別の表を誤受理する(§4 の判定条件) |
| 11 | **ダイジェスト不一致を「免除表の更新」で黙らせない** | §4「免除の廃止手順」を参照。**ダイジェスト値の更新は禁止**。文書側に変更履歴表を持たせ、同じ PR で免除エントリを削除する |
| 12 | **見出し破損検査はコードフェンス外に限る** | `^#{1,6}\s` かつフェンス(``` / ~~~)の外。**本計画書自身のフェンス内に `#` 始まりのコメントが 6 行ある**ため、限定しないと自分が反例になる |
