# 調査メモ: 文書検査機構の多文書対応(プロファイル化 + 不変条件 DSL)

**◎印** = 調査サブエージェントの報告のうち **Claude が原典を直接確認したもの**。
略記: `PROP` = `scripts/check_design_propagation.py` / `COV` = `scripts/check_doc_coverage.py` /
`HARNESS` = `docs/development/dev-harness-design-2026-08-07.md` /
`LEDGER` = `docs/development/harness-evaluation.md` /
`SPPLAN` = `docs/features/sync-protocol-canonical/plan.md` /
`SPLOG` = `docs/worklog/2026-08-28-sync-protocol-canonical.md`。

## 問い

TSK-269 は、同期プロトコル正本専用に書かれた文書検査機構を**二文書目(データモデル正本)にも使えるよう
一般化**するタスクである。受け渡し先の TSK-250 は本タスクのマージを開始条件としている。

1. 現在の機構は**どこが文書固有で、どこが汎用**か。一般化のコストはどこにあるか
2. TSK-250 が要求する**「機械で保証すべき 4 検査」**(`FORB` の構造判定 / 直接要件の「対象外」禁止 /
   ベースライン digest 拘束 / `WAIT`・`AUTH`・`FORB` の交差検査)は、現在の延長で表現できるか
3. この機構が**なぜこの形になったのか**。一般化が過去の決定を壊さないか
4. 既存の同期正本に対する検査結果を**変えない**ために、何を基準線にすべきか

## 結論(要約)

1. **「不変条件 DSL」は実質まだ存在しない**(◎)。JSON の `invariant` のうち判定に使われているのは
   `forbidden`(禁止 literal 走査)と、その走査範囲を決める `scope` だけで、**`positive` と `mapping` は
   読み込み時の型検査しかされていない死蔵フィールド**である。**機械欠陥 17 件のうち 16 件は
   Python の `if defect_id == ... elif` の直書き分岐**で判定されており、DSL だけで閉じているのは 1 件のみ。
   → **本タスクの「DSL 化」は既存 DSL の拡張ではなく、判定ロジックのほぼ全量を書き直すこと**を意味する。
2. **TSK-250 の契約に書いた不変条件の 5 種別では足りない**。既存分岐を型に分類すると **16 分岐中 7 件が
   5 種別のどれにも収まらず**、最低でも「行セレクタ」「行スコープの禁止」「選言」「required-exclusion」
   「条件付き禁止(含意)」「well-formedness lint」「要素の接頭辞ルックアップ」の 7 概念が要る。
3. **決定経緯に 3 つの矛盾リスク**がある(◎ 全件原文確認)。とくに **H-78 が「汎用の検査は書けない」と
   明記**し、**`SPPLAN` が「新規機構を発明しない」を確定事項としている**。前タスクの実測では
   **確定ゲート中に足した機構 3 つがいずれも欠陥を量産した**(P0 8 / 6 / 5)。
4. **CI に引数を足すと approved 正本の本文と食い違う**(◎)。ただし**スクリプト側でプロファイルを
   列挙して全文書を検査すれば、引数を増やさずに多文書化できる**(4-3 節)。
5. **帰属検査は「全件『対象外』」で通る**(◎ コードで確認)。同期正本でそれが起きないのは検査ではなく
   **テスト側のリテラル固定**が止めているだけで、**二文書目には対応する固定が無い**。
   一般化して横展開すると**二文書目は事実上ノーガード**になる。
6. **基準線**(◎ 自分で実行 — 2026-08-31): `uv run pytest tests/` = **784 passed** /
   3 検査すべて green / `ruff check` `ty check` ともクリーン。検査本体 2,331 行に対し**テストが 2,204 行**。

## 詳細と典拠

### 1. 現状の機構の実態

#### 1-1. `invariant` の 4 フィールドの実使用(◎)

| フィールド | 判定への使用 | 典拠 |
| --- | --- | --- |
| `forbidden` | **あり** — `scope` で切った本文への部分文字列走査 | `PROP:619`-`:622` |
| `scope` | **限定的** — `forbidden` の走査範囲を決めるためだけ | `PROP:619` |
| `positive` | **なし** — 読み込み時の型検査のみ | `PROP:275` |
| `mapping` | **なし** — 同上 | `PROP:272` |

`PROP:601`-`:604` の docstring が明言している:
「**`positive` と `mapping` は散文のまま評価せず、本関数から呼ぶ ID 別の構造ロジックの仕様として
実装している**」。つまり現状の JSON は**人間向けの仕様書コメント**であり、実行される規範ではない。

**機械欠陥 17 件のうち、DSL だけで閉じているのは `MT-01` の 1 件**(`_structural_reason` に分岐が無い
唯一の ID)。残り 16 件は `PROP:427`-`:593` の直書き分岐にある。

#### 1-2. 既存分岐を型へ分類した結果

`required-element` 6 / `exact-set` 主体 1 / `cross-reference` 1 / `forbidden-element` 1(冗長)/
**5 種別に収まらない 7 件**。`unique-owner` に該当する分岐は **0 件**。

**収まらない 7 件と、足りない型**:

| 欠陥 | 何が表現できないか | 必要な型 |
| --- | --- | --- |
| `SP-09` | `exact-set` + **行スコープの禁止**(`"T5" not in row`)+ **選言**(`T7 or V11`) | 行スコープ forbidden / any-of |
| `SP-12`・`SP-16` | 「**除外宣言が存在すること**」の要求(禁止の裏返し)。除外語彙が `PROP:421`-`:424` に固定 | required-exclusion(語彙の外部化つき) |
| `SP-20` | **条件付き禁止**(`P → Q`。「禁止だが明示的に否定文脈なら可」) | 含意 |
| `SP-18` | Markdown の**整形式性**(表行の `**` が偶数個) | well-formedness lint |
| `SP-08` | 要素の**接頭辞検索** + 節ごとに違う語彙辞書 + **条件付き exact-set** | 要素ルックアップ |
| `SP-13` | 「ID が表行の**識別子列**に来る」という行アンカー制約 | 行セレクタ |

行の選び方だけでも 3 種類ある(needle 包含 / 第 1 セル一致 / 識別子として出現 —
`PROP:342`・`:359`・`:865`)。

#### 1-3. 文書固有の前提(一般化で外に出すもの)

**`PROP` 側**: `DEFAULT_DOCUMENT` は `--document` で切り替えられるが、**`DEFAULT_DEFECTS` と
`DEFAULT_MANIFEST` は CLI に出ておらず `main` が無条件ロードする**(`PROP:1306`-`:1307`)。
そのほか、リンク解決の基準ディレクトリを `root/docs/design` に固定(`PROP:1089`)/ 非正本走査の開始を
`^##\s+2`(2 章)に固定(`PROP:1066`)/ 宣言表の節 `2-5`・行接頭辞 `| **R-`・**ちょうど 6 列**・列順
(`PROP:643`・`:649`・`:652`・`:655`-`:682`)/ 除外語彙(`PROP:423`)/ **節 ID の文法 `\d+(-\d+(-[A-Z])?)?`**
(`PROP:337`・`:726`)。

**`COV` 側**: 文書依存は 5 群に限られる — 対象文書パス(`COV:15`)/ 区分語彙 `ASSIGNMENT_KINDS`
(`COV:30`。「同期側で決める」が同期固有)/ 台帳の節 ID `LEDGER_SECTION_ID = "11-5"`(`COV:44`)/
**帰属表の節 `^11-3\.` が定数名なしのリテラル直書き**(`COV:429`)/ 関連するエラー文言。
**母集合 `req-universe.json` も抽出器も 8 カテゴリの正規表現群もそのまま共有できる**
(要件書からのみ導かれ、帰属先の文書に依存しないため)。

#### 1-4. 静かに検査を無効化する経路(一般化の主要リスク)

`extract_scope` は、節 ID の文法に**マッチしないトークンを黙って捨てる**(`PROP:337`-`:338` — ◎ 確認)。
`_heading_section` も**見つからなければ空文字列を返す**(`PROP:309`-`:310`)。
→ **節命名規約の違う二文書目では、scope が全脱落して `forbidden` 走査が vacuously green になる**。
誤設定が報告されないため、**「検査を載せたつもりで何も見ていない」状態が CI green のまま起きる**。

#### 1-5. **同じ型の欠陥が `codex_run.py` にもある — 見出しスコープの取り違え**(◆ 2026-08-31 に TSK-270 で実地に踏んだ)

> **訂正(2026-09-04・◎)**: 本節で `has_step_table` と書いた関数の実名は **`has_filled_step_row`**
> (`.claude/scripts/codex_run.py:62`)。2026-08-31 時点から同名で、本メモ側の誤記。行範囲は `:62-78`、
> 問題の行は `:71`。以下の本文は原文のまま残す(是正案・射程判断は有効)。

1-4 節の「静かに検査を無効化する経路」と**同型の欠陥が、文書検査機構の外(`codex_run.py`)にも存在する**。
**TSK-270 の実装委任が実際にこれで拒否され**、原因の特定に手戻りが出た。

`codex_run.py:63-78`(`has_step_table`)は、実装計画書のステップ表を**見出し単位で区切って**探す:

```python
if re.match(r"#{1,6}\s", line):
    in_section = "実装ステップ" in line
    continue
```

**見出しレベルを見ていない。** どんな深さの見出しに当たっても `in_section` を計算し直すため、

```
### 実装ステップ(コミット単位 — 設計書 6.1 段階実装)
    …散文…
#### 第 1 群: 契約と前提の凍結(1〜5)      ← ここで in_section = False
| # | ステップ | 合格条件 |                 ← 表が見えない
```

という**入れ子の見出し構成でステップ表が完全に不可視になる**。

**1-4 節との違いは「壊れ方の向き」**である:

| | `extract_scope`(1-4) | `has_step_table`(1-5) |
| --- | --- | --- |
| 誤設定時の挙動 | **黙って空になり vacuously green** | **拒否して止まる** |
| 危険度 | **高**(検査したつもりで何も見ていない) | 低(気づける) |
| 共通の根 | **文書構造の解釈が暗黙の前提に依存し、前提が外れたことを報告しない** | 同左 |

**`has_step_table` は fail-closed 側なので実害は手戻りだけ**だが、根は同じである。
**「見出しの入れ子」という Markdown では当たり前の構造を、機構が扱えない。**

**踏む条件が特殊ではない**ことが重要である。**計画を群に分割すると必ず踏む**。
TSK-270 は敵対レビューが 3 周否決したのを受けて承認範囲を第 1 群に絞ったため、
**分割は必然だった**。今後も**大きい計画ほど分割され、踏む確率が上がる**。

##### 是正案(本タスクの射程候補)

**見出しレベルを持ったスタックで判定する** — 「`###` 実装ステップ」の配下は、
**より深い見出し(`####` 以降)が来ても section 内に留まり、同レベル以上の見出しで抜ける**。

```python
# 概念: 現在の section の見出しレベルを保持し、level <= section_level で抜ける
```

**あわせて 1-4 節と同じ「前提が外れたことを報告する」規律を適用する**:
ステップ表が見つからなかったとき、**「表が無い」と「表はあるが見出しスコープの外にある」を区別して報告する**
(後者は今回のように**原因の特定に時間を食う**)。

##### 射程の判断材料

- **`codex_run.py` は文書検査機構(`scripts/check_*.py`)ではない**。本タスクの当初の射程は
  `check_design_propagation.py` の一般化であり、**`codex_run.py` は入っていない**
- しかし**欠陥の型は同一**(文書構造の解釈が暗黙の前提に依存する)であり、
  **一般化の設計をここにも適用できるかは、機構の一般性を測る良い試金石**になる
- **人間の裁定 2026-08-31: 本タスク(TSK-269)へ回す**
- **/plan で射程に含めるかを決める**。含めないと決めるなら、**独立タスクとして起票する**
  (放置すると次に計画を分割した人が同じ手戻りを踏む)

##### 暫定回避(TSK-270 で適用済み)

小見出しを **`#### 実装ステップ — 第 1 群: …`** に改題し、**語「実装ステップ」を残した**。
計画書に**機構要件である旨の注記**を入れてある(改題時に語を落とさないため)。
**これは回避であって修正ではない** — 語を含めない小見出しを書いた瞬間に再発する。

### 2. 帰属検査の穴(◎)

`check_coverage`(`COV:460`-`:502`)が参照するのは **`assignment.id` だけ**である。
`kind` は `ASSIGNMENT_KINDS` の語彙メンバシップのみ(`COV:452`-`:453`)、`destination` は**空でないこと**
のみ(`COV:450`-`:451`)。**帰属先の節が実在するかの検査も、根拠文の存在検査も無い**。

→ **帰属表を全件「対象外」で埋めても green になる。** 同期正本でそれが起きていないのは、
検査ではなく**テストのリテラル固定**(区分分布 38/84/90 — `tests/test_check_doc_coverage.py:131`-`:147`、
`tests/test_check_design_propagation.py:1515`-`:1529`)が止めているため。
**二文書目には対応する固定が存在しない。**

→ TSK-250 の契約にある「**データモデル直接要件の『対象外』禁止**」は、
**現状の延長ではなく新しい検査**として実装する必要がある。

### 3. CI 配線とテストの壊れ方

| 対象 | 固定していること | 二文書目で壊れるか |
| --- | --- | --- |
| `tests/test_ci_wiring.py:55`(◎) | `assert len(matches) == 1` — 各スクリプトを走らせる step が**ちょうど 1 件** | **壊れる**(文書ごとに step を並べる配線にすると即失敗) |
| 同 `:57` | 禁止セレクタは `--defects` / `--checks` **のみ**。`--document` は禁止に入っていない | 壊れない |
| `tests/test_core_guard.py:337`-`:340` | `guard_paths` が期待集合と**順序込みで完全一致** | **必ず壊れる**(新資産を足すたび。設計どおりの意図的な挙動) |
| 同 `:316` | 4 領域それぞれの `paths` が 2 要素と完全一致 | 二文書目を `areas[].paths` へ足すと壊れる |
| `tests/test_check_design_propagation.py`(1,709 行・収集 86 件) | 関数シグネチャ直呼びが多数(A 層 18 関数ほか)。**実 manifest / 実 defects を module scope の fixture で読む**(`:125`-`:134`) | シグネチャ変更で広範に壊れる |

**一般化の安全網として最優先で残すべき 2 本**:
`test_fixture_reports_exact_machine_defect_set`(`:707`-`:718` — 機械 17 ID の**集合完全一致**。
件数一致では通らない)と `test_fixture_default_adds_global_findings`(`:721`-`:735`)。
fixture と SHA-256 は**リファクタ前後で不変に保てる**ので、
「**12 検査 × 機械 17 件の検出集合が完全に同一**」を維持したまま内部を作り替えられる。

### 4. 決定経緯と矛盾リスク

#### 4-1. この機構が生まれた理由

- **表間伝播の検査が要る理由**: 前タスクは語彙レベルの検査 5 種を最初から入れても収束しなかった。
  「ACK の結果集合に『未処理』を足したのに境界結果表の 4 行へ写していなかった —
  **語は 1 つも変わっていないので、どの検査も反応しない**」(`LEDGER:577`)
- **oracle を実装より先に固定する理由**: 「**同じ作業で作ると共通の取りこぼしが一致して通る**」
  (`SPPLAN:292`)
- **fixture をバイト単位で固定する理由**: 「**検出器に都合よく加工された fixture を弾くため**」
  (`SPPLAN:286`)
- **計画レビュー 16 周で 3 度作り直した**(`SPPLAN:33`-`:42`)。とくに 9 周目に
  **人間照合欠陥の機械化を断念**している —「**意味の判断は機械化できず、機械化すると第二の正本になる**」

#### 4-2. 矛盾リスク 3 件(◎ 全件原文確認)

| # | 原文 | 本タスクへの含意 |
| --- | --- | --- |
| ① | 「**汎用の検査は書けない**(文書ごとに対応関係が違う)ため、**『その文書のための検査を書くこと』自体を起草の成果物に含める**形が要る」(`LEDGER:583`) | **エンジンを汎用化し、文書固有の宣言(マニフェスト/プロファイル)は保つ**限り整合する。**宣言を薄める方向へ一般化すると H-78 が名指しで否定した形になる** |
| ② | 「**(5) 新規機構を発明しない。** ベースライン ratchet は 5 周目に廃止した。**セレクタと累積実行という単純な列挙**で閉じる」(`SPPLAN:294`) | **「不変条件 DSL」は定義上まさに新機構**。前タスクの実測では**確定ゲート中に足した機構 3 つがいずれも欠陥を量産**(P0 8 / 6 / 5 — `SPLOG:233`)。**既存分岐の抽出に留めるか、新しい記述言語を作るかは計画で正面から決める** |
| ③ | 「**4 と 5 は CI の `docs-lint` で引数なしで強制される**(ハーネス設計書 10.1 が正)。**引数を付けると選択実行になり一部しか回らない**」(`docs/design/sync-protocol.md:2426` — **approved 正本の本文**) | CI へ `--document` を足すと**この一文が事実と食い違う**。設計正本の本文変更は 7.3 の確定ゲート対象になり得る。**回避策は 4-3 節** |

#### 4-3. 「引数なし」を保ったまま多文書化する案(Claude の設計提案 — 検証はしていない)

CI の引数を増やすのではなく、**スクリプトが `scripts/design_relations/` 配下のプロファイルを列挙して
全文書を検査する**形にすれば、次の 3 つを**すべて保ったまま**多文書化できる:

- `HARNESS:623` の「引数なし」という配線の規範
- `docs/design/sync-protocol.md:2426`(approved 正本)の記述
- `tests/test_ci_wiring.py` の意図(**選択実行の禁止**。禁止セレクタは `--defects` / `--checks`)

**ただし `test_ci_wiring.py:55` の「step はちょうど 1 件」は温存できる**(step を増やさないため)。
この案の当否は /plan で判断する。**推測を含む提案であり、当時の決定を代弁するものではない**。

#### 4-4. oracle を「後から変更しない」規律

「**絶対に触らない**」ではなく「**黙って触らない — 正当な改訂として、承認済みの独立ステップで触る**」が
原文の趣旨(`SPPLAN:350`・`req-universe.json:2`「**抽出器の出力に合わせて書き換えてはならない**」)。
実際に例外を通した唯一の記録は `SPPLAN:344`(ステップ 41)で、理由は
「**反映周で oracle を黙って更新すると、検査が正本を検証するのではなく検査が正本に合わせられる**」
(`SPLOG:283`)。

#### 4-5. `guard_paths` と重さ分類

`guard_paths` は**完全一致集合で glob が効かない**(`SPLOG:178`)。**既存の `PROP` を 1 行でも触れば
core-guard が発火**し、PR 本文の逐行確認チェックが必須になる。
**重さ分類の前例**: 検査ツールを作った `nfr021-evidence-verifier` は `重さ分類: 通常`、
