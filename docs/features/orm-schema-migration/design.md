## 1. models の型境界(裁定 `Q-2` の具体化)

### 1-1. 問題

**「型を損失なく受け取る境界」という表現は正本のどこにも定義がない**(research.md 4-4 節)。
また **88 列由来の属性の SQL 型は `data-model.md` で 1 つも確定していない**(確定は `D1`〜`D4` = `bigint`、
一時 ID = `uuid` の 5 つだけ)。一方でセンチネル変換の**値**の決定は TSK-250 の所有(裁定 `R-9`)。
→ **値を決めずに型だけを決める**必要がある。

### 1-2. 層を 3 つに分ける(レビュー 1 周目 `P0-1` → 2 周目 `P0-1` の是正)

**当初案は「恒等写像で保持する」を 88 列全体へ一般化していた**(1 周目 `P0-1` で否認)。
**2 層に分けたが、それでも「移行イベントの原本ペイロード」という層が抜けていた**(2 周目 `P0-1`)。

正本の定め:

- **移行イベントのペイロードが持つ「原本事実」は「センチネル判定後の値」である**(`data-model.md:2326`)。
  **導出可能な列はイベントに入れない**
- **88 列の行き先は 7 区分**で、**`導出`** / **`保持のみ`**(**88 列互換出力のために保持**し新スキーマの
  意味づけはしない — 例: 列 72「入力経路の識別値。互換出力のため」`:2256`)/ **`移行時に使用`**
  (名寄せ等に使い**新スキーマには残さない**)を含む(`:2208-2210`)
- **移行変換では実際の意味に従って読み替える。列名どおりに変換しない**(`P-43` — `:2204-2206`)

**したがって層は 3 つである:**

| 層 | 内容 | 恒等写像 | 本タスクの射程 |
| --- | --- | --- | --- |
| **(i) 隔離領域**(10-6 節 `:1969-1971`) | 88 列の**生の行**を raw ペイロードとして保持。**raw 内容へ意味制約・FK・CHECK を掛けない** | **正解** | **作る**(表 + raw ペイロード列 + 技術的 PK — 1-6 節) |
| **(ii) 移行イベントの原本ペイロード**(12-3 節 `:2326`) | **センチネル判定後の値**を持つ。**`保持のみ` の列はここに保存先を持つ**。**`導出` の列は入れない** | **正解ではない** | **ペイロードの器と行き先区分との対応を作る。値の変換は作らない** |
| **(iii) 正規スキーマの原本事実列 / 解決列** | **正本が明示した列だけ**。**必須ペアは列 47・55 のみ**(`:2242,2264-2272`)。移行元最終オーダーの解決列は**任意**(`:2380`「解決結果を**持ちたい場合は**別の nullable 列として足す」) | **正解ではない** | **列を作る。型と NULL 性を決める。値は埋めない** |

**層外の処理**(層番号を持たない — レビュー 3 周目 `P2-2` の是正): **変換ロジックと写像の値**
(フィールド別センチネル変換 / 88 列写像の値 / 座標正規化 / 球速の扱い)は **TSK-250 の所有**であり
**本タスクでは作らない**(裁定 `R-9`)。層は **(i)〜(iii) の 3 つ**である。

**2 周目の是正点**:

- **層 (ii) を新設した**。`保持のみ` の列は「**原本事実列を作らない**」だけでは不十分で、
  **互換出力のために保存先が要る**。→ **移行イベントのペイロードが保存先**であり、
  **行き先区分(`:2208-2210`)との exact-set 照合**で保存先の有無を検査する。
- **層 (iii) の必須ペアを列 47・55 に限定した**。**移行元最終オーダーの解決列は本タスクで作らない**
  (`:2380` が任意としているため、作ると裁定なしに射程を広げる)。

### 1-3. 型を決める規則(層 (i)〜(iii))

**規則**: **旧側の保存型が損失なく入る型を選ぶ。意味が数値であっても旧側が TEXT なら TEXT にする。**

| 旧側の保存型 | 選ぶ型 | 根拠 |
| --- | --- | --- |
| TEXT | **`text`** | `0` / `"0"` / `""` / NULL が同居する(`data-layer.md:144,400`)。数値型にすると**センチネル判定より前にドライバのキャストが壊れる**か暗黙変換で情報が消える |
| REAL | **`double precision`** | 座標 4 列・球速の 5 本(`data-layer.md:194-208`) |
| INTEGER | **`bigint`** | 桁あふれの余裕を取る |
| TEXT(JSON 文字列) | **`text`** | 旧は JSON/JSONB 型ではなく TEXT(`data-layer.md:144`)。**配列長が非対称なので固定長を仮定しない**(`:2261`) |

**層 (iii) の必須対象**: 列 47(捕球選手 = 守備番号)/ 列 55(実体はエラー選手の守備番号)。
`:2242,2264-2272` が「守備位置番号を原本事実として保持 + 解決済み選手 ID は別の nullable 列」
「番号自体は NULL 化しない — センチネルのみ NULL」と定めている。

**やらないこと**: 旧 TEXT 列を新側で `integer` / `numeric` として宣言すること。

### 1-4. NULL 性の既定

**`C12`(`:800-802`)が定める範囲に従う。** 88 列由来の原本事実列は**既定で nullable**
(旧側は制約なし・全列 NULL 可 — `data-layer.md:63`)。
旧側の事実により初回スキーマで `NOT NULL` にできない列がある(試合の所有チーム列 / プレイと選手の紐づけ)。
**実データ未確認**(research.md 4-6 節)。

### 1-5. exact-set テストの形(裁定 `Q-3` の具体化) — **3 層**

#### A. 隔離領域(層 (i))— **恒等写像が正解の層**

| # | 落とす欠陥 | 検査 |
| --- | --- | --- |
| A1 | **全消去** | 4 形態 + 境界値の入力表に対し**期待出力表と exact-set 一致**。NULL を返す行は入力が NULL の行だけ |
| A2 | **部分潰し**(`""` と NULL、`0` と `"0"` が同一化) | 4 形態が往復後も**相互に区別できる** |
| A3 | **型変換による情報喪失** | 桁の大きい数値文字列・先頭ゼロ・前後空白・全角数字が**バイト同値**で戻る |

#### B. 移行イベントのペイロード(層 (ii))— **保存先の網羅を検査する層**

| # | 検査 | 水準 |
| --- | --- | --- |
| B1 | **行き先区分表(`:2208-2210`)をパースし、`保持のみ` に分類された列の集合がペイロードの区分定義と一致する** | **機械**(区分の集合まで) |
| B2 | **`導出` の列がペイロードの区分定義に入っていない**(`:2326`「導出可能な列はイベントに入れない」) | **機械** |
| B3 | **`移行時に使用` の列が新スキーマに残っていない** | **機械** |
| B4 | **ペイロードの型が 1-3 節の規則どおり**(センチネル判定後の値を損失なく持てる) | **機械** |
| B5 | **列単位の保存先の網羅**(88 列の各列が実際にどのペイロードキーへ入るか) | **機械では閉じない** → 10 節 |

**水準を「区分の集合まで」に弱めた**(レビュー 3 周目 `P1-1`・収束方針 — plan.md 4-11 節):
**列単位の写像は TSK-250 が値を確定するまで決まらない**(裁定 `R-9`)ので、
**本タスクで列単位の exact-set を要求すると、確定していない値を先取りするか、空の検査になる**。
→ **区分の集合の一致までを機械で閉じ、列単位の網羅は TSK-250 の写像確定後へ送る**(10 節に明示)。

**値の変換の正しさは検査しない**(TSK-250 の所有)。

#### C. 正規スキーマの原本/解決列(層 (iii))

| # | 検査 |
| --- | --- |
| C1 | **列 47・55 について原本列と解決列が別の列として存在する** |
| C2 | 原本列の型が 1-3 節の規則どおり(旧 TEXT 由来が数値型で宣言されていない) |
| C3 | 解決列が **nullable で既定値を持たない**(埋めていないことを構造で示す) |
| C4 | **移行元最終オーダーに解決列を作っていない**(`:2380` の任意規定 — 作るなら別途裁定) |

**負例で red になることを同時に検査する**(判定を純関数へ抽出し、壊した実装を渡して red を確認する)。

### 1-6. 隔離領域の識別子(レビュー 2 周目 `P2-2` の是正)

正本は「**新スキーマの制約を掛けず、この表だけは正規化しない**」(`:1969-1971`)とするが、
**Declarative ORM は行識別のため mapped primary key を要求する**。

→ **線引き**: **「raw ペイロードの内容へ意味制約・FK・CHECK を掛けない」**と読む。
**取り込み単位の識別子(取り込みバッチ識別子 + 読み出し順序)と技術的 PK は許す** —
これは `:2312-2313` が移行の行識別子として既に要求しているものと同じであり、
**raw 内容への制約ではない**。

## 3. スキーマ契約 manifest

### 3-1. なぜ必要か

**「存在する models だけを走査するテスト」は、表そのものの作り忘れを検出できない。**
1 周目のレビューが **`data-model.md` の必須実体 7 群の欠落**を実測した:
一時 ID→正式 ID 写像表(`:763`)/ 規則セットと適用規則スナップショット(6-5 節)/
試合のスタメンと背番号スナップショット(`:1436-`)/ 管理者資格情報・管理者セッション・通常トークン(8-2-A)/
管理者操作ログ・選手統合イベント・移動記録・レート制限表(8-4)/
カルテ所見の変更履歴・PDF 出力実績(10-1)/ 移行結果・解決・警告レポート(10-6)。

### 3-2. 自己循環を部分的に断つ — **「全数オラクル」とは主張しない**

**2 周目の指摘**: manifest と実スキーマの相互比較は、**同じ表を両方から落とすと green** になる。
人手転記が manifest と実装で共有されているため、自己循環が残る。

**3 周目**でも「**正本に対する独立した全数集合がまだ作れていない**」と再指摘された。

→ **収束方針(plan.md 4-11 節)に従い、要求水準を実現可能な線まで弱める。**
**manifest は「全数オラクル」ではなく「カタログで表現可能な構造の期待値 + 正本への追跡可能性」である。**

| 機構 | 内容 | 何が閉じるか |
| --- | --- | --- |
| **要求 ID と正本節の保持** | manifest の各要素が **`正本節` と `要求 ID`**(`M01`〜 / `C11`〜 / `RQ-` / `D` / `V` 等)を持つ。**解決できない参照があれば red** | **追跡可能性**(逐行確認の足場)。全数性は閉じない |
| **正本の blob SHA 束縛** | manifest に **`data-model.md` の blob SHA** を記録し、**変われば `stale` として red**(既存慣行と同型 — `scripts/design_relations/fixture-sha256-data-model.txt`) | **正本が動いたことの検出**。**正本改訂時に manifest の見直しを強制する** |
| **正本 2 表のパース照合** | **業務的一意性全数表(`:359-387`)と行き先区分表(`:2208-2210`)は機械可読に近い表形式**なので、**パースして manifest の該当集合と exact-set 照合する**。**実 DB を経由しない独立経路** | **この 2 表が定める範囲の全数性**(一意制約 27 行 / 88 列の行き先区分) |
| **表の全数性** | **機械では閉じない** | → **10 節の受入証跡で閉じる** |

**「表の全数性を機械で閉じる」ことは本タスクの射程から外す**(レビュー 3 周目 `P1-1` の是正 —
ただし**指摘の求めた方向とは逆に、要求を弱めることで閉じる**)。**理由**:

- **正本の表定義は節ごとの散文と表の混在**であり、**2 表のような機械可読な形になっていない**。
  機械可読ブロックを正本へ新設するのは **`data-model.md` の改訂**であり、
  **本タスクのやらないこと**(TSK-348 が版を動かしている)
- **正本から生成する期待集合を本タスクで作ると、その生成器自体が人手転記になる** — 自己循環が
  1 段深いところへ移るだけで、**輪が閉じない**(運用評価台帳の「検査層が欠陥源になる輪」)

**manifest は実スキーマから自動生成しない** — 「観測値を後から期待値にする」形になり
設計書 `:695` が禁じた型に当たる。

### 3-3. 一意制約の役割タグ — **非排他的にする**(レビュー 2 周目 `P1-3` の是正)

**1 周目で導入した「業務的一意 / 代理キー / FK 支援」の排他的 3 分類は破れていた。**
**イベントスロットの `PRIMARY KEY (tenant_id, 試合, D4, D1)`(`:371`)は同時に
① 業務的一意性全数表の 1 行 ② 主キー ③ `M07` の FK 参照先**であり、排他分類では所属が定まらない。

→ **是正**: **物理制約 1 件に対して非排他的な役割タグを付ける。**

| タグ | 意味 | 照合先 |
| --- | --- | --- |
| **`business_unique`** | `data-model.md:359-387` の 27 行のどれか | **同表と exact-set 一致**(`➖` 4 行がテナント外) |
| **`primary_key`** | 主キー | manifest |
| **`fk_target`** | FK の参照先にするために必要な完全な一意制約 | manifest |

**イベントスロットの PK は `business_unique` + `primary_key` + `fk_target` の 3 タグを持つ。**
**`D5` 台帳の `(tenant_id, D5, 種別)` は `fk_target` のみ**(業務的一意 27 行には入らない)。
**27 行照合では `business_unique` タグを持つ集合を使う** — タグが非排他なので余剰も欠落も出ない。

### 3-4. ライフサイクルは判別共用体にする(レビュー 2 周目 `P0-2` の是正)

**1 周目で「全表に 4 削除系統のいずれかを要求する」としたが、これは正本と衝突していた。**
**管理者操作ログは「保持は無期限」「追記のみ(論理削除の対象にしない)」**(`:1642-1643`)。

→ **是正**: manifest のライフサイクル欄を**3 つの独立した軸**にする
(レビュー 4 周目 `P1-3` の是正 — **1 つの判別共用体では表せなかった**)。

**なぜ 1 軸では表せないか**: **`D5` 台帳は退役状態を更新でき、退役後も「消費済み」として残る**
(`:2361`「**`D5` は退役で解放しない**。やり直しは新しいバッチ識別子と新しい `D5` で行う」)。
これは**削除 4 系統のどれでもなく、追記専用でもない**。

| 軸 | 値 | 典拠 |
| --- | --- | --- |
| **軸 1: 業務オブジェクトの削除系統** | `ゴミ箱` / `非表示` / `無効化` / `終了・離脱` / **`対象外`** / **`親に従う`**(親オブジェクトの系統に従う投影・付随表) | 削除 4 系統(`:2005-2010`)+ 本計画が足した 2 値 |
| **軸 2: 追記専用性** | `追記専用`(**`UPDATE`/`DELETE` を拒否**)/ `更新可` | **`:1642-1643`**(管理者操作ログ) |
| **軸 3: 移行バッチ退役** | `退役述語を持つ` / `持たない` | **`:2362`** の 7 件の全数 |

**`追記専用` の表には削除列を持たせない**(持たせると論理削除できる形になり監査の不変性が壊れる)。
**拒否は 5 節の不変列マトリクスと同じ機構(トリガ)で実現し、構造・挙動・downgrade を検査する。**

**軸 1 の割り当ての正しさは機械で全数確認できない**(10 節 `N4`)。
**理由(4 周目 `P1-3` で訂正)**: **`:2005-2010` は「業務オブジェクトへの系統の割り当て表」であり、
物理表の全数との写像を持たない**(投影表・付随表・台帳は同表に現れない)。
→ **`N4` の突合は `:2005-2010` が挙げる業務オブジェクトに対応する表だけを対象とし、
それ以外の表は「正本に直接割当なし」として個別典拠を添えて人間が判定する。**

### 3-5. manifest が持つ項目

表ごと: テーブル名 / **正本節と要求 ID** / 列(名・型・NULL 性・既定値)/ **ライフサイクルの 3 フィールド**(**削除系統** / **追記専用性** / **移行バッチ退役** — 3-4 節。**`削除対象外・追記専用` という複合値は使わない**)/
FK(参照先・構成列・**`MATCH`**・**削除動作**・複合か越境か)/ CHECK / 一意制約(**役割タグ**・**述語の全文**)/
索引(**列順**・範囲/ソート用の別)/ **禁止列**(`V12`・入力者識別列・`created_by` 相当)/
**不変列マトリクス**(保護列・許可更新列 — 5 節)。

**照合は exact-set**(manifest に無い実体が実スキーマにあれば red、逆も red)。
**負例**: manifest から 1 行落とすと red / 実スキーマに 1 表足すと red /
**正本の blob SHA を変えると `stale` で red**。

## 4. `D5` 台帳の「経路と種別の一致」の強制機構(`:1032,2757` の受け取り)

### 4-1. 正本が定めていること / 実装が選ぶこと

正本が定めるのは **「1 対 1 であること」と「経路と種別が一致すること」**まで。
機構は `CHECK` / 種別ごとの部分一意 / 参照の分割の**いずれかを実装が選ぶ**(`:2757`)。

前提(`:1027-1031`): **`D5` 台帳が `(tenant_id, D5)` の一意性を持つ唯一の表**。
操作イベント表・拒否原本表・退避原本表は**それぞれ台帳への FK を持ち、3 表すべてに `UNIQUE (tenant_id, D5)`**。

### 4-2. 3 択の評価

| 案 | 判定 | 理由 |
| --- | --- | --- |
| **参照の分割** | **不可** | `D5` の一意性は **試合・世代を跨ぐ**(`:361`)。3 表に分けると `(tenant_id, D5)` の唯一性が壊れる |
| **種別ごとの部分一意** | **不可** | **PostgreSQL の FK は部分索引を参照できない**(`:761` が `V10` で同じ制約を根拠にしているのと同型) |
| **`CHECK` + 種別を含む複合 FK** | **採用** | 下記。**計画レビュー 2 周目で「閉鎖」と評価された** |

### 4-3. 採用する形

1. 台帳に **`種別` 列**を置く。**`NOT NULL`** かつ **3 値だけを許す `CHECK`**。
2. 台帳に **`UNIQUE (tenant_id, D5, 種別)` の完全な(部分でない)一意制約**を追加する
   (`UNIQUE (tenant_id, D5)` があるので自動的に一意)。**これを FK の参照先にする**。
   **manifest の役割タグは `fk_target` のみ**(3-3 節)。
3. 参照元 3 表それぞれに **`種別` 列**を置き、**`NOT NULL`** + **`CHECK (種別 = '<自分の種別>')`** で固定する。
4. 参照元 3 表の FK を
   **`FOREIGN KEY (tenant_id, D5, 種別) REFERENCES d5_ledger (tenant_id, D5, 種別) MATCH FULL`** にする。

#### なぜ `NOT NULL` と `MATCH FULL` が必須か

- **`CHECK (種別 = 'x')` は式が NULL のとき「満たされた」扱いになる**(SQL の三値論理 — 制約は
  結果が FALSE のときだけ違反)。→ `種別 = NULL` は CHECK を通る
- **既定の `MATCH SIMPLE` の複合 FK は、構成列のいずれかが NULL なら参照先の照合を要求しない**。
  → `種別 = NULL` なら **台帳に対応行が無くても子行を挿入できる**
- **`DEFAULT` は明示的な NULL 挿入を防がない**

**負例 4 種を実 DB で検査する**: ① `種別 = NULL` ② 不正な種別値 ③ 台帳に対応行が無い ④ **他種別の台帳行を参照**。

### 4-4. 保証できる範囲の正確な記述

**子側の FK + `UNIQUE (tenant_id, D5)` が構造で保証するのは「台帳 1 行に対し子は 0 または 1 件」= 高々 1 件**であり、
**厳密な 1 対 1 ではない**(台帳だけの孤児行は作れる)。

**本タスクの立場**: **「高々 1 件」までを構造で保証する。**
「ちょうど 1 件」を DB で強制するには**コミット時に評価する遅延制約トリガ**が必要になるが、
**正本は機構を実装の選択に委ねており、遅延トリガまでは要求していない**(`:2757`)。
→ **台帳行と原本行の原子書き込みの責務はアプリ層**(原子境界 `T1`〜`T9` の所有 = 同期・記録権の実装タスク)。

## 5. 不変列マトリクス(レビュー 2 周目 `P1-7` の是正)

**1 周目までは `D3` の後退禁止だけを機構として設計していたが、正本は他にも不変性を要求している。**

**注意**: **全更新を拒否する誤実装にすると移行の退役等を阻害する**ので、

**この 5 表は「本計画が拾う範囲」であり、正本が不変性を要求している列の全数であるとは主張しない**

**機械可読な全数表を持たない**。**全数性の担保は 10 節の受入証跡で閉じる** —
**逐行確認で「不変」「変えない」「昇格させない」等の語を拾い、マトリクスとの差分を人間が確認する**。
**追加が見つかればマトリクスへ足す**(実装期・レビューで拾う)。

### 5-1. 機構と補償テスト

**機構は `BEFORE UPDATE`(および追記専用表は `BEFORE UPDATE OR DELETE`)トリガ。**

| 案 | 評価 |
| --- | --- |
| 条件付き `UPDATE` | **不採用**。**アプリ側の全経路が正しく書くことに依存**し、1 経路の漏れで不変条件が破れる。**更新 0 行を成功と誤読する経路**も生まれる(NFR-015「失敗の黙殺防止」と逆行) |

**構造**: `pg_get_triggerdef` の全文 / **対象表と対象列** / **`tgenabled`(有効であること)** / 関数定義。
**挙動**: ① **保護列の更新を拒否** ② **許可更新列の更新を通す** ③ **`D3` は同値許可・前進許可・後退拒否**
④ **追記専用表は `UPDATE` と `DELETE` の両方を拒否し `INSERT` を通す**。

## 7. 接続 URL・接続方式・設定契約

### 7-1. 解く問題

設定正本テンプレートの 9 行目が裸の `postgresql://...` で、
**SQLAlchemy 2.0.48 はこれを `PGDialect_psycopg2` / driver=psycopg2 と解釈する**(Notion タスクの実測)。
**psycopg2 は未導入**なので Alembic が落ちる。

### 7-2. 触ってはいけない範囲(research.md 4-3 節の裁定 — 2 周目とも「維持してよい」と評価)

**`postgresql+psycopg://` は SQLAlchemy の URL 形式であり libpq の conninfo ではない。**
`backend/tests/db/conftest.py` は DSN を **`psycopg.connect()` へ直接渡し**(`:81,116,207`)、
**`conninfo_to_dict()` / `make_conninfo()` で解析している**(`:17,65,257`)。
→ **テスト用 DSN を `postgresql+psycopg://` にしてはいけない**。

**次の 3 資産には触らない**: `tests/test_ci_wiring.py:395-397` /
`.github/workflows/ci.yml` の job env の DSN / `backend/tests/db/environment-expectations.json:197,205`。

### 7-3. 設定契約 — 3 つのキーに分ける(2 つの URL + pooler フラグ)

**1 周目で「Alembic 用 direct URL とアプリ用 URL を別設定にする」と決めたが、
キー名・消費者・fallback 禁止を確定しておらず、同じ設定を両方が読む実装でも受入可能だった。**

→ **確定する**:

| 設定キー | 消費者 | 未設定時 | 内容 |
| --- | --- | --- | --- |
| **`PITCHLOG_DATABASE_URL`** | **アプリの engine のみ** | **起動を失敗させる**(既定値を持たない) | pooler 経由でもよい |
| **`PITCHLOG_DATABASE_POOLED`** | **アプリの engine のみ** | **起動を失敗させる**(既定値を持たない) | **`true` / `false` を明示する**。`true` なら engine に **`prepare_threshold=None`** を付ける |
| **`PITCHLOG_MIGRATION_DATABASE_URL`** | **Alembic の `env.py` のみ** | **`alembic` の実行を失敗させる** | **direct connection のみ**(`:2400`) |

**pooler かどうかを URL から自動判定しない**(レビュー 3 周目 `P1-4` の是正 — 収束方針)。
**理由**: pooler の判定は**ホスト名やポートの慣行に依存**し、環境が変われば静かに誤判定する。
**設定で明示させ、未設定は失敗させる**ほうが NFR-015(失敗の黙殺防止)に沿う。

**相互 fallback を禁止する** — 一方が未設定のとき他方の値を使わない。
**理由**: fallback を許すと **Alembic が pooler URL を消費する経路**ができ、`:2400-2401` の
「migration は direct connection」を満たせなくなる。

**正例**(レビュー 4 周目 `P1-6` の是正): **`PITCHLOG_DATABASE_POOLED=false` で
アプリと Alembic が同一の direct URL を使う構成は契約上有効である。**
**当初案の「2 URL キーが同値なら red」は誤りだった** — アプリ URL は
「**pooler 経由でもよい**」= direct も許されるので、**同値は pooler 使用の証拠にならない**。

**負例**(3 種): ① **片方を未設定にして他方へ fallback させる** ② **`PITCHLOG_DATABASE_POOLED` を未設定にする**
③ **`PITCHLOG_DATABASE_POOLED=true` なのに engine に `prepare_threshold=None` が無い**。

**migration の direct 性は「CI の明示 URL」と「運用設定の確認」で担保する**
(URL の形からは判定できないため)。

**CI への供給**(レビュー 3 周目 `P0-2` の是正): **`alembic` を CI で動かすには
`PITCHLOG_MIGRATION_DATABASE_URL` が job env に必要**である。
**`.github/workflows/ci.yml` の `backend` ジョブへ追加する**(既存の `PITCHLOG_TEST_*_DSN` とは別のキー)。
**当初案は 3 段のコマンド追加だけで、URL の供給が抜けていた。**

### 7-4. 正規化の形

**`backend/src/pitchlog/db/url.py` に正規化関数を 1 本置き、SQLAlchemy が URL を受け取る経路すべてが通す。**

- 裸の `postgresql://` → **スキームだけを `postgresql+psycopg://` へ書き換える**(他の要素は変えない)
- 既に `postgresql+psycopg://` → **そのまま**

- 通す経路は **`env.py`** と **engine 生成**の 2 箇所だけ。**他に URL の解釈を書かない**

### 7-5. 検査

- `create_engine(正規化後).dialect.driver == "psycopg"` / **実接続**(`requires_db`)
- 裸 → `postgresql+psycopg://` / 既に正しい形は不変 / **別ドライバ明示は拒否**
- **負例**: 正規化を外すと `dialect.driver` が `psycopg2` になり red

### 10-1. 突合シートの判定区分と是正遷移(レビュー 4 周目 `P0-1` の是正)

**当初案は完了条件が「未判定行が残っていない」だけで、差分が出たときの処理が無かった。**
**人間が欠落を見つけても「確認済み」にして `D18` を通せる形だった。**

→ **是正**:

| 事項 | 規定 |
| --- | --- |
| **判定区分** | 各行を **`一致` / `差分` / `対象外`** のいずれかに固定する。**`対象外` は理由と典拠(ファイル:行)を必須**にする |
| **区分の適格条件**(レビュー 5 周目 — **`対象外` を欠落の隠れ場所にしないため**) | **`一致`** = **正本側の項目と、対応する manifest / 実装側の項目を両方特定できる**(片方しか挙げられないなら `一致` にできない)/ **`差分`** = **欠落・余剰・内容不一致のいずれか** / **`対象外`** = **当該 `N` の「対象・範囲」の外にある生成候補だけ**。**対象内の欠落に `対象外` を使うことを禁じる** |
| **完了条件** | **未判定 0 かつ未解消の `差分` 0 かつ不適格な `対象外` 0**(`D18`) |
| **是正遷移** | **`差分` が出たら、実装ステップ表の末尾へ番号付きの是正ステップを追加する**(`/<N>` を付けていないので追加できる)。**是正後に突合シートを再生成し、再度判定する** |
| **シートの位置** | `docs/features/orm-schema-migration/acceptance-sheets/`。**生成は機械・判定は人間**(6.3 の実施記録行の形式で対象・範囲・方法を書く — 設計書 `:355`) |
| **横断 audit との関係** | **ステップ 23〜25 の横断 audit は「追加修正を行わない検査」に限る**。**是正はステップ 27 以降の是正ステップで行う** |

**この表は「逃げ」ではなく射程の宣言である** — **機械で閉じる範囲(manifest ↔ 実スキーマ ↔ 正本 2 表)と
閉じない範囲を分けて書き、閉じない範囲には受入証跡の形と受け取り先を必ず与えている**。
**`N1`・`N3`・`N4` は突合シートを機械生成する**(人間の目視を数十件以上の逐行に晒さない)。
**`N2`・`N5`・`N6` はシートを作らず受け取り先で閉じる**(`N5` は承認前条件・`N6` は運用証跡)。
