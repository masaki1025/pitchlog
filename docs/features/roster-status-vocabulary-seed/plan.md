## 4. 実装方針

### 4-1. キーの名前空間の衝突(**本タスクの中核**)

【実測】`system_vocabularies` の**主キーは `key` 単独**で `category` を含まない
(`backend/src/pitchlog/db/tenant_isolation/models.py:1120-1124`・`data-model.md:396`「`UNIQUE (キー名)`」)。
一方、要件書 `:171` は**試合区分にも在籍区分にも「その他」**を置いている。

**→ 2 つの「その他」に同じキーは振れない。**

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **甲** | **在籍区分を無接頭辞で採る** — `active` / `other` / `ob`。試合区分側の「その他」が別キーを採る | `active` の既存典拠 4 箇所と整合。区分内で表記が揃う。**ただし名前空間を先に取り、試合区分側へ「その他だけ別名」という不揃いを押し付ける** |
| 乙 | **両区分に接頭辞** — `roster_active` / … と `game_official` / … | 対称で衝突しない。**しかし `active` を名乗る既存典拠 4 箇所と食い違う**。変えるなら要件改訂ゲート |
| 丙 | **在籍区分の「その他」だけ修飾** — `active` / `roster_other` / `ob` | 衝突は解けるが**区分内で表記が不揃い**。読む側が規則を導けない |
| **丁(推奨・1 周目 `P1-3` で追加)** | **在籍区分は無接頭辞のまま、試合区分の全キーに接頭辞** — `active`/`other`/`ob` と `game_official`/`game_semi_official`/…/`game_other` | **`active` を維持しつつ、どちらの区分内でも表記が揃う。** 甲の「試合区分側だけ不揃い」を解消する。**規則が 1 文で言える**(「システム固定語彙は在籍区分が無接頭辞、試合区分が `game_` 接頭辞」)。**制約は試合区分側の全キーに及ぶ**ので裁定は要る |
| 戊(1 周目 `P1-3` で追加) | **`UNIQUE (key, category)` へ変え、参照 FK を複合にする** | **衝突が構造的に消え、§4-5 の誤参照も同時に解ける。** ただし `system_vocabularies` の主キーと `players` / `games` / `game_type_rule_defaults` の FK を変えるため**重い**(`data-model.md:396` の「`UNIQUE (キー名)`」の改訂も要る) |

**`CHECK` 制約だけでは主キー衝突は解けない。** `CHECK` は §4-5 の**誤参照**への対策であって、
**同じ `key` を 2 行置けるようにはしない。** 両者は別の問題である(1 周目 `P1-3`)。

**【過去案の記録】当初の当方推奨は丁だった。** 根拠は ① `active` の既存典拠 4 箇所を動かさない(乙を落とす)
② **どちらの区分内でも表記が揃う**(甲・丙を落とす)③ 規則が 1 文で言える。
**戊は最も堅いが、主キーと 3 つの FK を変えるため本タスクには重い** — ただし §4-5 を同時に解くので、
**裁定次第では戊が最良になりうる。**

> **【裁定 2026-10-03・山田正輝 / 2 周目 `P1-4` で縮小】**
> **本タスクが決めるのは在籍区分の 3 キー(`active` / `other` / `ob`)だけ。**
> **試合区分の命名は決めない。** 丁が示した `game_` 接頭辞は、**拘束力のない推奨**として
> 別タスク(試合区分の seed)のカードへ送る。
>
> **理由**: **未実装の他単位の命名を正本で固定すると「新しい共通設計規則」になり、
> 7.6-3 の「実装追随」では扱えず 7.3 の確定ゲートへ入る。** 本タスクはそこへ入らない。
>
> **衝突回避は事実から従う** — 在籍区分が `other` を取る以上、試合区分の「その他」は別キーを採るしかない。
> **規則を作らなくても衝突しない。** **戊(スキーマ変更)は ② の裁定により採らない。**

### 4-3. seed の形式と、DML 禁止検査への限定許可(**1 周目 `P1-1` で全面改稿**)

#### 初稿の誤り

初稿は「migration に `INSERT` を直書き」としていた。**これは二重に誤りだった**:

| | 典拠 |
| --- | --- |
| **既存テストが全 revision の DML を禁止している** | `backend/tests/test_migration_hygiene.py` の `test_all_migration_revisions_contain_only_schema_ddl`。`_FORBIDDEN_SQL` が `INSERT INTO` / `UPDATE … SET` / `DELETE FROM` を、`_FORBIDDEN_CALLS` が `bulk_insert` / `create_all` を拒否する |
| **正本は `op.bulk_insert()` を指定している** | `docs/design/data-model.md:2421`「**DDL と DML を統合しない。小さな初期データは `op.bulk_insert()`**、大量バックフィルは段階実行」 |

**計画段階で `backend/tests/` を読まずに方式を決めたために起きた。**

#### 採る形

| 層 | 実体 |
| --- | --- |
| **シード(正)** | **リポジトリに JSON 資産**(キー・`category`・表示名) |
| **投入** | **seed 専用 revision が `op.bulk_insert()` で投入**(正本 `:2421` に合わせる)。**値は revision 内に直書き**し、実行時に外部ファイルを読まない |
| **一致の担保** | **テストがシード資産と revision の投入値の exact-set 一致を検査** |

**実行時に外部ファイルを読まない理由**: シード資産を後から変更すると、
**適用済み revision の意味が後から変わる**(再現性が壊れる)。**直書き + 一致検査**なら、
シードを正にしたまま再現性を保てる。**1 周目のレビュアもこの理由づけは妥当と認めた。**

#### DML 禁止検査への限定許可(**緩和を機械的に封じる**)

**現在の禁止集合は「権限 DDL」と「DML」を 1 つの検査に束ねている**
(`CREATE POLICY` / `CREATE ROLE` / `ALTER ROLE` と `INSERT` / `UPDATE` / `DELETE` / `bulk_insert` / `create_all`)。
**seed 専用 revision が必要とするのは DML の一部だけで、権限 DDL は一切要らない。**
したがって**許可は次の 6 項目で絞る**(**うち DML の絞りは 1〜4、5 は残存禁止、6 は宣言の置き方**):

| # | 絞り | 内容 |
| --- | --- | --- |
| 1 | **対象ファイル** | **許可するのは `seed_allowlist` に列挙した revision だけ**。他は従来どおり全面禁止 |
| 2 | **操作** | **`upgrade()` は `op.bulk_insert()` のみ**(生の `INSERT INTO` 文字列は許可対象でも拒否)。**`downgrade()` は seed した 3 キーに限定した削除のみ**(**2 周目 `P1-1` の是正** — 初稿は `DELETE` を一律拒否しており、自分のステップ 4・7 と矛盾していた) |
| 3 | **対象表**(**2 周目 `P1-2`**) | **許可する DML の対象表を `system_vocabularies` 1 つに固定する。** 他表への `bulk_insert` は許可対象ファイルでも拒否 |
| 4 | **呼び出し件数と投入行**(**2 周目 `P1-2`**) | **`upgrade()` 内の `bulk_insert` 呼び出しは 1 回ちょうど。投入行は 3 行ちょうどで、`category` が全行 `roster_status`。** 2 つ目の呼び出し・4 行目・別 category はいずれも拒否 |
| 5 | **残る禁止** | 許可対象でも**権限 DDL(`CREATE POLICY` / `CREATE ROLE` / `ALTER ROLE`)・`UPDATE … SET`・`create_all`** は従来どおり拒否 |
| 6 | **allowlist 自体の置き方** | **宣言資産へ置き、検査器へ直書きしない**(設計書 7.7-1)。**動かしたら 7.7-2 の記録を追記する** |

#### allowlist は凍結基準なので 7.7 に従って置く(**6 周目 `P1-2` の是正**)

**5 周目に採った「素の exact-set `assert` を検査器ソースに置く」形は、設計書 7.7 に適合しない。**

【実測】設計書 7.7 の逐語:

> **7.7-1 凍結基準の外出し**: 凍結の基準を**新たに置くとき**、または現に置かれている基準を動かすとき、**次の両方を満たす。**
> 1. **宣言**: … **機械可読な宣言として資産側へ置く。**
> 2. **直書きの禁止**: … **検査器のソースへ直書きしない。**
