# 調査メモ: 在籍区分キーの値と `system_vocabularies` の seed(TSK-475)

**基準**: `develop` = `0492b9af18010e73e948c70fe28bc96d2ad1d9f8`(PR #74 マージ後)。
**調査**: 調査サブエージェント 3 本(spec-checker / legacy-analyst / decision-tracer)+ 当方の原典実測。
**凡例**: 【実測】= 当方が原典で直接確認 / 【報告】= エージェントの報告で当方未確認 / 【解釈】= 推論。

## 問い

在籍区分 3 値(現役 / その他 / OB)のキー文字列を決め、`system_vocabularies` へ seed する。
その前に **①キーの典拠 ②射程(試合区分を含めるか)③隣接タスクとの境界 ④重さ分類**を確定する。

## 結論(要約)

1. **本タスクは「キーを決めて入れる」だけでは済まない。設計判断が 1 つ要る** —
   `system_vocabularies` の**主キーは `key` 単独**(`category` を含まない)なのに、
   **試合区分と在籍区分の両方に「その他」がある**。**同じキー文字列は使えない。**
2. **正本が定めているキーは `active` 1 つだけ。** 「その他」と「OB」の綴りは**どこにも無い**。
   したがって**本タスクが 2 値を新たに決める**。
3. **旧システムに在籍区分は無い**ので、移行の写像は不要。必要なのは初期値 1 つ(現役)だけ。
4. **試合区分は射程外が妥当** — 所有単位が U-M1 と異なり(U-G1 / U-X1 / U-A2 / U-X5)、
   かつ**旧 `Kind` 12 値 → 新 5 区分の対応が未決**(付録 D-5 は例 3 件のみ)。
   **ただしキーの名前空間は共有するので、衝突しない命名規則は本タスクで決める。**
5. **重さ分類は再検討の余地がある**(§6)。`backend/migrations/*` は 5 領域すべての `paths` だが、
   **設計書 6.3 の境界定義表は「旧データと接しない新スキーマ内部の通常マイグレーション」を
   `データ移行` の対象外(通常レビュー + テスト)としている。**
6. **U-M1 を止めている理由は構造として裏付けられた** — `players.roster_status_key` は
   `nullable=False` + `system_vocabularies.key` への FK・既定値なし。**seed が無いと選手を 1 行も作れない。**

## 詳細と典拠

### 1. 最大の論点 — キーの名前空間が区分をまたいで 1 つ

【実測】`backend/src/pitchlog/db/tenant_isolation/models.py:1114-1126`:

```python
__table_args__ = (
    CheckConstraint("category IN ('game_type', 'roster_status')"),
    PrimaryKeyConstraint("key", name="pk_system_vocabularies", ...),
)
```

【実測】`models.py:155-162` — 選手側の FK は **`key` だけ**を参照し `category` を拘束しない:

```python
ForeignKeyConstraint(
    ["roster_status_key"], ["system_vocabularies.key"],
    name="fk_players_roster_status", match="SIMPLE", ondelete="NO ACTION", ...
)
```

【実測】要件書 `:171` — **試合区分にも在籍区分にも「その他」がある**:

> | システム固定 | 試合区分(公式戦/準公式戦/オープン戦/紅白戦/**その他**)、在籍区分(現役/**その他**/OB) | 変更しない |

【報告・spec-checker / decision-tracer が独立に指摘】`docs/design/data-model.md:396` も
システム固定層の一意性を **`UNIQUE (キー名)`**(category を含まない)と定めている。

**→ 帰結 2 つ**:

| | |
| --- | --- |
| **(a)** | **2 つの「その他」に同じキー(例 `other`)を振れない。** 片方に別名が要る |
| **(b)** | **FK は `category` を見ないので、選手の `roster_status_key` に試合区分のキーが入っても DB は止めない** |

**(b) は本タスクが作る欠陥ではなく既存の構造**だが、**キーを入れた瞬間に実害が発生しうる**
(`official` を `roster_status_key` に入れても通る)。**本タスクで扱うか別タスクへ送るかは計画段階の判断。**

### 2. キー文字列の典拠

【実測】正本で在籍区分のキー綴りが出るのは **`active` の 3 箇所だけ**で、いずれも括弧書きの言い換え:

| 箇所 | 逐語 |
| --- | --- |
| 要件書 `:505`(FR-041) | 「在籍中(`active`)の選手」 |
| 要件書 `:996`(6.2) | 「在籍中(`active`)」 |
| 要件書 `:1177`(付録 A-5) | 「選手個別を `active` に限る」 |
| `data-model.md:526` | 「`kind = 'self'` かつ在籍区分が現役(`active`)の選手だけ」 |

**【当方の初稿の誤り】** 本タスクの Notion カードに `data-model.md:524` と書いたが、**実際は `:526`**。

【報告・decision-tracer】**`active` の綴りを決めた決定(D-* / ADR / 裁定 / 変更履歴の行)は見つからなかった。**
D-22(在籍ステータス)は日本語 3 区分だけを定め、綴りに触れていない
(`docs/requirements/requirements-draft-pitchlog.md:172-176`)。
**文書上の最古の出現は v2.0 の作業文書**(`docs/features/req-v2-legacy-parity/design.md:296`)。
【解釈・decision-tracer】**決定を経ずに書かれた可能性が高い。** 旧システムの列名(旧の在籍は `active`/`inactive` の 2 値 —
`docs/features/legacy-frontend-coverage/research.md:233`)を説明的に借りた表記に見える。

【報告・spec-checker】**「その他」「OB」のキー文字列の典拠は正本のどこにも無い。**
**試合区分 5 値のキー文字列の典拠も無い。**

【報告・legacy-analyst】テストには `active` / `inactive` / `official` / `roster-active` 等が現れるが、
**いずれも各テスト関数内の INSERT でテスト専用**。**`ob` / `other` はテストにも無い。**
表示名も「在籍」「退団」で要件の 3 区分と一致しない。

**→ 本タスクは `active` を追認し、残り 2 値を新たに決める。**

### 3. 命名の慣行(規約は無い)

【報告・decision-tracer】**列挙値の大文字小文字・記法を定めた条文は、正本のどこにも無い。**
近いのは `ADR-003` D-12(`:296`)だが、これは `contracts/` の**ファイル名**の規約。

【報告・decision-tracer の計数】**DB の CHECK 値は 50 出現・46 種類がすべて小文字スネーク(大文字 0・ケバブ 0)。**
`check_authz_catalog.py:328-349` の閉じた集合 9 個・24 値もすべて小文字スネーク。

**【解釈】小文字スネークが支配的な慣行。規約ではないので、本タスクは「慣行に従う」と明記して採る。**

### 4. 旧システムと移行

【報告・legacy-analyst】**旧 `player` は `id / チーム_id / 背番号 / 名前 / 左右` の 5 列だけで、在籍に当たる列は無い**
(`docs/legacy/research/data-layer.md:31-39`・`docs/legacy/baseball-scoring-db-structure.md:169`)。
改善台帳 I-13 も「在籍ステータスの概念がなく … 整理する手段は物理削除しかない」
(`docs/improvements-from-baseball-scoring.md:125`)。

【報告・legacy-analyst】要件書 `:790`「取り込み時の割り当て: 選手=在籍区分「現役」」は、
**「旧に無いので全員現役」の意味**と原典から判断できる(`baseball-scoring-db-structure.md:309` が
「在籍ステータスなし」と「全員現役」を同じ行に書いている)。

**→ 移行の写像規則は不要。必要なのは現役キー 1 つ。**

### 5. 試合区分を射程に入れるか — **入れない**

| 根拠 | 典拠 |
| --- | --- |
| **所有単位が違う** — 在籍区分(FR-017)= **U-M1** / 試合区分 = FR-001 **U-G1**・FR-014 **U-X1**・FR-037 **U-A2**・FR-038 **U-X5** | 【報告・spec-checker】`docs/features/product-impl-unit-split/design.md:73-80` |
| **旧 `Kind` → 新 5 区分の対応が未決** — 旧の選択肢は **12 個 + 自由入力**。付録 D-5 が定めるのは**例 3 件だけ**(リーグ戦 / A オープン戦 / 部内リーグ) | 【報告・legacy-analyst】`docs/legacy/research/services-shell.md:175`・要件書 `:1242` |
| **語彙 seed を所有する単位は帰属表上「空席」** | 【報告・spec-checker / decision-tracer が一致】 |

**【解釈】試合区分を含めると、要件側の穴(12→5 の対応)を本タスクが引き受けることになる。**
**在籍区分は 3 値が閉じているので、分けるのが妥当。別タスクの起票を DoD に入れる。**

**ただし §1 の名前空間は共有する**ので、**試合区分のキーと衝突しない命名規則は本タスクで決める。**

### 6. 重さ分類 — **再検討の余地がある**

【実測】`.claude/core-areas.json` — `backend/migrations/*` は **5 領域すべての `paths`** に入っている。
→ **core-guard は必ず発火する。**

【実測】しかし設計書 6.3 の**境界定義表 `データ移行` 行の右列(対象外)**(`:398`)に逐語:

> **旧データと接しない新スキーマ内部の通常マイグレーション — 通常レビュー + テスト**

**【裁定】decision-tracer は「設計書 6.3:398 が通常レビューとしている」と報告したが、
これは一般規則ではなく `データ移行` 行の対象外列である。** 他 4 領域の意味範囲からも外れるかは**別途の判断**。

【実測】同 6.3 は「**判定に迷うコードは含む側に倒す(fail-closed)**」とも定めている。

**【解釈・未確定】** 本 seed は旧データに接しない新スキーマ内部の migration なので
`データ移行` の意味範囲からは外れる。他 4 領域(同期プロトコル・状況計算・記録権・テナント分離)の
意味範囲に入るかは、本調査では確定できない。**fail-closed の原則からは `コア領域` が安全側。**
**計画段階で人間の判断を仰ぐ。**

**いずれにせよ core-guard は発火するので、PR には逐行確認のチェックと実施記録が要る。**

### 7. 隣接タスクとの境界

#### TSK-410(ラベル語彙のチーム拡張)— **行単位で分かれる**

【実測】要件書 `:171` = **システム固定**(本タスク)/ `:173` = **チーム拡張可**(TSK-410):

> `:173` | チーム拡張可 | ラベル語彙: 球種・作戦・大会名・**在籍ステータスラベル**(自チーム内のみ有効) | 各チーム |

【報告・spec-checker】**表も別** — 在籍区分 = `system_vocabularies`(テナント列なし)/
在籍ラベル = **`tenant_vocabularies`**(category `roster_label`・主キー `(tenant_id, key)`・`models.py:1178-1200`)。
`players` は両方を別々の FK で持つ。

**【当方の初稿の誤り】** 本タスクの Notion カードに「`admin_vocabularies`」と書いたが、**正しくは `tenant_vocabularies`**。
`admin_vocabularies` は打撃結果・打球情報・シーズンで**在籍とは無関係**。

**→ 重なりは無い。行単位・表単位で分かれる。**

#### TSK-343(ORM 導入・完了)からの送り先

【報告・decision-tracer】TSK-343 の計画書「やらないこと」に
「**enum・参照テーブルの値**(とくに列 44 球種)→ 受け取り先 **TSK-334 / TSK-250**」
(`docs/features/orm-schema-migration/plan.md:101`)。ステップ 14 の合格条件に
「**参照テーブルに値を入れていない**」(同 `:781`)。

【実測】Notion で確認(2026-10-03):

| | 状態 | 名前 |
| --- | --- | --- |
| **TSK-343** | **完了** | ORM の導入と models・migration |
| **TSK-334** | 未着手 | **88 列と旧資料矛盾の裁定セッション**(TSK-271 の判定 22 件の採否) |
| **TSK-250** | 進行中 | **データモデル設計の正本化** |

**【裁定】どちらも「システム固定語彙を seed する」タスクではない。**
TSK-343 が値を送った**理由は列 44 球種の値域衝突**であり、TSK-334 はその裁定セッション。
**本タスクは重複ではない。** ただし**関係を計画書に明記する**(TSK-343 が「器まで」と線を引いた、その先が本タスク)。

### 8. seed の形式 — 「二段構成」の条文がある

【報告・decision-tracer】`data-model.md:1946-1947` 逐語:

> **語彙の初期値はリポジトリのシードが正で、それを DB へ投入する二段構成。シードを DB の正本にしない。**

要件書 `:1235`(付録 D-4)「機械可読なシードデータとしてリポジトリに収載し、それを正とする」。
要件書 `:178`(4.0-3)「語彙の初期値は付録 D-4 の一覧を投入する」。

【報告・decision-tracer の限界】**付録 D-4 が名指しするのは球種・打撃結果・作戦・打球情報**で、
**システム固定語彙(試合区分・在籍区分)には触れていない**。
システム固定層にまで別ファイルのシードを要求する条文かは**判断できない(不明)**。

**【解釈・要判断】migration に `INSERT` を直書きするだけだと「シード(投入元)」と「投入」の二段が分かれない。**
**本タスクがどちらの形を採るかは計画段階の判断**(① migration 直書き ② `contracts/` 等にシード資産を置き migration が読む)。

### 9. seed 後の変更経路 — 要件に穴がある

【報告・spec-checker】

| 事実 | 典拠 |
| --- | --- |
| 要件書 `:171` システム固定は「**変更しない**」 | 要件書 |
| 要件書 `:175`「**全層共通**の保全規律: 使用実績のある語彙は削除不可・**無効化のみ**」 | 要件書 |
| `data-model.md:2095` は「**システム固定語彙の変更**」を管理者操作として前提にしている | `data-model.md` |
| `models.py:1135` は `DeletionLifecycle.DISABLED` を宣言 | `models.py` |
| **実装は `display_name` と `disabled` を含む全列の UPDATE をトリガで拒否** | `0010_vocabularies_settings.py:160-177` |

**【報告・spec-checker の結論】宣言された無効化経路が、実装では実行できない。**
**システム固定層の `disabled` が何に使われるかを定めた正本は無い。**

**【解釈】本タスクは seed するだけなら触らずに済むが、「入れたら直せない」ことを承知の上で入れることになる。**
**射程に入れるか別タスクへ送るかは計画段階の判断。**
