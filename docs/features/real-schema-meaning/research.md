# 調査メモ: 12-4 の「実スキーマ」の意味と、SP-06・non-serving 宣言・受け取り先表の字面衝突(TSK-382)

典拠の行番号は、特記のないかぎり develop `f2dc9f9b` の時点のもの。

**【344wt】** は TSK-344 のブランチ `feature/product-rls-boundary-tests` にだけ在るファイルを指す。develop には未マージ。

調査は次の 3 本を並列に回し、主要な典拠は原典で抜き取って確認した。
- spec-checker: 要件との突合
- decision-tracer: 決定経緯
- Explore: 正本の現行文言の洗い出し

## 問い

1. **論点 A(カードの射程)** — `docs/design/data-model.md` の 3 者が字面のうえで衝突している。
   - SP-06 の行は「RLS を初日から全テーブルに掛ける」で、判定は「遵守」
   - 12-4 の non-serving 宣言は「RLS のポリシーとロールの DDL は本書の射程外」とする
   - 12-6 の受け取り先表は、RLS の DDL を実機確定タスクへ送っている

   決めることは次の 3 つ。
   - 「遵守」は何に対する遵守か
   - 判定はいつの時点で行うか
   - 3 者のどれを直すか
2. **論点 B(後から積まれた射程)** — 12-4 の通過条件にある「実スキーマ」は、正本の上で何を指すか。
   - TSK-344 が求めているのは可否 1 つ。「compose の専用 Postgres インスタンス上の、名前の付いた 1 DB」が実スキーマに当たるかどうかが、条文から一意に決まることである
   - この DB は毎回作り直し、既存データを持たず、製品コードの入口 1 つで適用する

## 結論(要約)

- **「実スキーマ」は正本のどこにも定義されていない。要件書と改善台帳には、この語も RLS も出てこない。**
  - 要件が課すのは「越境させないこと」「API を直接叩くテストを CI に常設すること」「経路ごとの発効」「リリース時の網羅」の 4 つで、どの DB インスタンスで確かめるかは指定していない。
  - TSK-344 の対象が持つ 4 性質は、どれも要件上「言及なし」である。
- **用語の変遷からは、「使い捨てクラスタ」と「実スキーマ」を別物として扱う二分が、承認済みの正本(12-8 `:2925`)にすでに入っている。**
  - そのため、使い捨てクラスタを含める定義(候補 b)は既存の決定と衝突する。
  - 本番に限る定義(候補 d)は、要件 NFR-021(`REQ:962`・開発 DB で (b) の成功を求める)、NFR-019 の柱書(PR ごとの CI)、ADR-004 が却下した「現状維持」による停止と衝突する。
  - **衝突する確定決定が見当たらないのは候補 (c)「使い捨てでない専用インスタンス上で、製品 migration と製品適用器で作った DB」だけ**である。ただし「使い捨て」を何で区切るか(クラスタの寿命か、DB の作り直しか)は定義が要る。
- **論点 A は字面だけの問題で、要件との矛盾ではない。**
  - SP-06 の出所は D-4①「テナント分離は初日から実装(後付けは困難なため)」で、要件側の原文は RLS もテーブルも指していない。
  - SP-06 を「後付けできない構造という作り方の方針」として読み直し、文言を直す案は、既存の決定と衝突しない。
  - 12-6 の TSK-317 行は、12-8 `:2925` に追随していない(古い)。
- **前提の訂正**: data-model.md に 12-9 節は存在しない(節は 12-1〜12-8)。SP-06 の行は **12-6 節**(`:2778`)にある。「12-9」という誤った表記は `product-authz-surface/design.md:661` から写されて広がった。

### 4. SP-06 の出所と「初日から」の意味

出所は次のようにたどれる。
1. SP-06(`data-model.md:2778`)は P-22 を判定している
2. P-22 は同期プロトコル設計 8-6 から送られた(`docs/design/sync-protocol.md:217`)
3. P-22 の典拠は決定記録 D-4①(`docs/features/product-data-model-design/research.md:213`)
4. D-4① の原文は「マルチテナント分離(team_id 分離・認証)は初日から実装(後付けは困難なため)」(`docs/requirements/requirements-draft-pitchlog.md:57`)

同じ根を持つものが 2 つある。
- 改善台帳 I-2「最初から実装する(利用が 1 チームの段階から組み込む)」。理由は「後付け・後追い是正では漏れが構造的に生まれる」(`improvements-from-baseball-scoring.md:32-36`)
- NFR-010「初日から全機能に適用する」(`REQ:848`)

要件側の原文は、どれも「テナント分離」「team_id 分離」を対象にしている。**RLS と「全テーブル」は data-model.md が足した語**で、3-1 節自身も「この採否は要件から導出されない — 本書の設計判断である」と書いている(`:146-156`)。
- 典拠に書かれた理由は、一貫して「後付けが困難」である。作り方の方針として読むことを支える典拠がある
- 「初日」の時点で RLS が稼働していることを求める文言はない
- 要件は、データに届く経路がまだない期間を自ら許容している(発効は経路ごと `REQ:933`、Phase 4 は越境を対象外 `REQ:961`)
