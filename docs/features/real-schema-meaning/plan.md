## 4. 実装方針

### 重さ分類: コア領域

**根拠**:
- `docs/design/data-model.md` は、`.claude/core-areas.json` の **5 領域すべての `paths`** に入っている(2026-10-05 実測)
- 加えて、改訂は `contracts/authz/shared-preconditions.json`(`tenant-isolation`)と `contracts/db/schema-manifest.json`(5 領域)の追随を**機構として強制する**
- #93 は計画時に「通常」と判定し、`/pr` で前提が崩れた(同計画書の「重さ分類」節)。本書は**最初からコア領域**とする
- したがって、計画レビューは敵対レビュー(`review adversarial`)、正本は `/finalize-doc`(敵対レビュー + 人間承認)、PR は人間の逐行確認を要する

**執筆の主体**: 変更は文書と digest の追随だけなので、**Claude が書く**(CLAUDE.md の役割分担 — ドキュメントは Claude)。
- 実装コードは書かない
- Codex は計画レビュー・確定ゲートの敵対レビューに使う

**派生資産**: `data-model.md` を 1 行でも変えると、次の追随が機構で強制される。
- `shared-preconditions.json` の `git_blob_digest`(git blob)
- `schema-manifest.json` の `canonical_source.sha256`(ファイル内容の SHA-256)
- N1 シート(5〜12 章の全見出しが対象 — 新しい小見出しで 1 行増える)と N3 シートの行番号参照、その件数を直書きした `tests/test_orm_acceptance_sheets.py`

確定ゲートの各周で正本が変わるので、**派生資産の追随は確定後に 1 回だけ行う**(#93 の前例 `f68bf0c7`)。それまでの CI の赤(digest 不一致)は想定内とし、worklog に記録する。

**版の取り合い**: #93(v0.5)と U-A1 β(#96 — 3-4・8-1・12-8 節の実装追随・版は上げない)は着地済みで、develop を取り込み済み(`906d219c`)。ほかに `data-model.md` を改訂中の PR があれば、確定ゲートの前に develop を取り込み直す。
