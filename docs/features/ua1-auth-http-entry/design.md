# 詳細設計: U-A1 δ 認証の HTTP の入口

本書の 1〜4 節が、`docs/design/data-model.md` 8-6 節が要求する
**「人間が承認した暫定設計」**である。調査の典拠は [research.md](research.md)。

> 入口を開く前に、要件書 10 章の相談で決まった具体設計か、**人間が承認した暫定設計を持ち**、
> それが下の不変条件を満たすことを確かめる(`docs/design/data-model.md:1787`)

**本書は敵対レビュー 3 周で否決された 3 案を差し替えた 4 案目である。** 経緯は 5 節(とくに 5-2-b)。

## 1. レート制限の暫定設計

| # | 決めること | 暫定設計 |
| --- | --- | --- |
| 1 | **カウント単位** | **試行元のみ**(`src:<正規化した試行元>`)。**チーム名を鍵に含めない** |
| 2 | **ロックの効き方** | **照合を先に済ませ、成功はロックを一切取らずに抜ける。失敗だけが試行元の予約票(`next_allowed_at`)を取り、その時刻まで待ってから応答する** |
| 3 | **閾値** | 遅延の開始 = **5 回 / ウィンドウ** |
| 4 | **ウィンドウと間隔** | ウィンドウ **300 秒** / 失敗の応答間隔は **250ms → 500ms → 1000ms** の 3 段 / **1 回の待ちの上限 2000ms** |
| 5 | **未登録名による行の累積の抑え方** | **構造的に発生しない**(鍵が試行元のみで、利用者の入力文字列が鍵にならない) |

### 1-1. 正しい資格情報だけが、制限の外に出る

FR-033(`docs/requirements/requirements-pitchlog-2026-07-22.md:596`)は**相反する 2 つ**を求める。

> Given ログイン失敗の連続 / When レート制限発動 / Then **試行が制限される**。ただしログイン済みの
> 既存セッションはロック中も有効であり、**正規利用者の締め出し(第三者の故意の失敗連打による
> 試合中の妨害)に使えない設計**とする

**第三者が制御できる属性(チーム名・試行元)で全試行を一律に制限すると、必ず後段に反する。**
拒否すれば止まり、遅らせても順番待ちで止まる。**2 周の敵対レビューがこの 2 つを順に否決した。**

**正規利用者だけが持っていて、第三者が持っていないものは「正しいパスワード」である。**
したがって**制限を失敗にだけ掛ける**。

**不変条件 ② は、これを条文として許している。**

> ② 失敗した試行について、計数・ロックの判定・失敗の応答は、チーム名の存在とパスワードの
> 誤り方によって変わらない。**正しい資格情報による成功は対象外**(`data-model.md:1790`)

② が一様性を求めるのは**失敗どうしの間**であり、**成功を失敗と同じ速さにすることは求めていない**。
成功が速いことから攻撃者が得る情報は「このパスワードは正しい」だけで、**それは応答そのもの
(セッションが開くこと)から既に分かる**。新しい漏洩はない。

### 1-2. 試行元の定義

| 入力 | 正規化後 |
| --- | --- |
| IPv4 | そのアドレス |
| IPv6 | **/64 プレフィクス**(単一ホストが多数のアドレスを持つため) |
| 取得できない | 固定の値 `src:unknown` へ寄せる |

プロキシ経由の配備では、信頼できる転送ヘッダの設定が前提になる。**誤設定で全要求が 1 つの
試行元に見えても、成功は制限の外なので正規利用者は止まらない**(失敗だけが遅くなる)。

### 1-3. 処理の流れ

```
受信 → 試行元を正規化 → authn.login_attempt(name, password, source) を 1 回呼ぶ

  [トランザクション内]
  a. 資格情報を照合する(ロックを取らない。常に bcrypt コスト 12 を 1 回・ダミーハッシュで一様化)
  b-成功: 計数も予約票も触らず、トークン行を作って token_id を返しコミット
          → 成功は勧告ロックを一度も取らない。待ち行列にも接続の奪い合いにも入らない
  c-失敗: ここで初めて試行元の勧告ロックを取り、
          c1. 現ウィンドウ + 直前ウィンドウの失敗数を読む
          c2. 失敗数から応答間隔を決める
          c3. 予約票 next_allowed_at を max(now, 既存値) + 間隔 へ進め、
              待ち時間 = 既存値 - now(負なら 0・上限 2000ms)を算出する
          c4. 計数を 1 増やす
          c5. NULL と待ち時間を返してコミット         ← ロックはここで解放
  → アプリ側で待ち時間だけ待ってから失敗を応答する(DB 接続は保持しない)
```

**要点は 3 つ。**

1. **照合がロックの前にある。** 成功は勧告ロックを一度も取らないので、**先行する失敗が
   何件積まれていても待たされない**(3 周目 P0-1 の是正)
2. **待つのは DB の外。** ロックもトランザクションも保持しないので、**失敗が接続プールを
   占有しない**(3 周目 P0-2 の是正)
3. **予約票が律速の実体。** 遅延をコミット後に置くだけでは並行できて律速しないが、
   **`next_allowed_at` を進めてから待つ**と、同一試行元の失敗の応答は
   **間隔あたり 1 件に揃う**(2 周目 P0-1 の是正)

**勧告ロックの鍵はウィンドウを含めず試行元のみ**にする。ウィンドウを含めると境界の前後に
届いた 2 件が別鍵を取って並行する(2 周目 P0-3)。

**`next_allowed_at` の置き場**は `rate_limit_counters` の現ウィンドウ行とする。
同表は `id` / `scope_key` / `window_start` の更新を不変トリガが禁じているが、
**`attempt_count` と `locked_until` は更新できる**(`0013_player_merge_rate_limits.py:186-210`)。
**`locked_until` を予約票として用いる** — 「この時刻までは応答しない」という意味で、
拒否ではない。列を増やさずに済む。

### 1-4. 応答間隔の段(失敗にのみ適用)

| 現ウィンドウ + 直前ウィンドウの失敗数 | 失敗の応答間隔 |
| --- | --- |
| 0〜5 | なし |
| 6〜10 | 250ms |
| 11〜20 | 500ms |
| 21 以上 | **1000ms(上限)** |

**待ちは DB の外で消費するので、接続もロックも保持しない。** 1 回の待ちには上限 2000ms を置き、
予約票がそれ以上先にある場合も 2000ms で打ち切って応答する(待ちが無制限に伸びない)。

**値はすべて `system_settings` から読む**(不変条件 ⑤)。キーは
`auth.team_login.window_seconds` / `.throttle_threshold` / `.throttle_step_ms` / `.throttle_max_ms`。
**4 件のいずれかが未設定・不正ならログインを拒否する** — 条文の逐語どおり
(`data-model.md:1793`)。**2 案目はここを「最も強い段へ倒す」と読み替えて P0-4 で否決された。**

### 1-5. 値の根拠

| 値 | 根拠 |
| --- | --- |
| 遅延開始 5 回 | 試合中のスコアラーが 5 分で 5 回打ち間違えるのは起こりうる。そこまでは遅延 0 |
| 1 回の待ちの上限 2000ms | 待ちが無制限に伸びないための打ち切り。正規利用者はそもそも待たない |
| ウィンドウ 300 秒 | 既存の器が `floor(epoch/window)*window` で切る実装に合わせる |

3 つとも**付録C の受け皿(`requirements:1222`)で変更できる値**として扱い、
**本書は既定値を提案するだけで、付録C には書かない**(3 節 E)。

## 2. 不変条件 ①〜⑥ への適合

| # | 不変条件 | 本設計がどう満たすか |
| --- | --- | --- |
| **①** | 第三者の故意の失敗連打で、正規利用者を締め出せない | **成功は勧告ロックを一度も取らず、予約票にも触れない**(1-3 の a→b)。第三者がどれだけ失敗を積んでも、正規利用者の待ち時間は**照合 1 回ぶん(約 250ms)で一定**。**待ちは DB の外で消費するので接続プールも奪われない。** 発行済みトークンの検証は `authn.verify_token` がカウンタを参照しないので無影響 |
| **②** | 失敗した試行について、計数・ロックの判定・失敗の応答は、チーム名の存在とパスワードの誤り方によって変わらない。**成功は対象外** | 鍵に名前が入らないので計数と遅延の判定は名前と独立。照合は**常に bcrypt コスト 12 を 1 回**。**失敗どうしの間では、遅延も応答も一様**。**成功を速く返すことは条文が明示的に対象外としている** |
| **③** | 失敗の計数は、失敗を返すのと同じコミットで確定する | 照合・予約票の更新・計数を 1 トランザクションに収める。**待ちはコミットの後**だが、**計数はコミット済み**なので「失敗を返すのと同じコミットで確定」を満たす |
| **④** | 同じカウント単位への並行した試行は直列化する(**同時の失敗を数え落とさない**) | **失敗はすべて勧告ロックの内側で計数する**ので、同時の失敗を数え落とさない。鍵は試行元のみでウィンドウを含めないため境界でも外れない。**成功をロックの外へ出す**のは、括弧書きが示す条文の目的(失敗の数え落とし)が成功には当たらないため — **この読みは人間の裁定を得た(2026-10-09・山田正輝)** |
| **⑤** | カウンタの読み書きは認証関数の内側。閾値は関数が設定値から自分で読み、**未設定なら拒否する** | **計数の読み書きも閾値の読み出しも認証関数の内側**(アプリ用ロールはカウンタの表を直接触れない)。**4 キーのいずれかが未設定・不正ならログインを拒否する**(逐語どおり)。**待ちの消費だけが関数の外側**だが、⑤ が内側を求めているのは**計数と閾値の読み出し**であって待ちの消費ではない(`data-model.md:1793` の逐語)。外へ出すのは 3 周目 P0-2 の是正である |
| **⑥** | 物理削除しない | 行を消す処理を一切書かない。**鍵が試行元なので、利用者の入力で行を増やせない** |

| 案 | 内容 | 却下の理由 |

## 4. 残余リスク(承認の対象)

| # | リスク | 評価と緩和 |
| --- | --- | --- |
| **R1** | **パスワードを忘れた正規利用者は、失敗の制限を受ける** | 正しいパスワードを持たない以上、攻撃者と区別できない。忘失時は管理者がリセットする(FR-036 `:757`)。**セッションが既に開いていれば影響しない**(FR-033 の既存セッション保護) |
| **R2** | **分散した試行元からの推測は制限されない** | 本機構の保証外。パスワードポリシー(FR-036 `:756`)と 10 章の相談で扱う。**本書は「制限する」と主張しない** |
| **R3** | **照合そのものは制限できない** | 成功を先に通すため、**照合(bcrypt コスト 12)はロックの前**にある。攻撃者の試行は毎回 CPU を使う。**制限できるのは応答の速度であって計算資源の消費ではない**。R2 と同じく 10 章の相談で扱う |
| **R4** | **成功が速いことから「このパスワードは正しい」と分かる** | **応答そのもの(セッションが開くこと)から既に分かる**ので、新しい漏洩はない。② が成功を対象外としている理由でもある |
| **R5** | **新しい入口が外から到達可能になる** | 12-4 のマージゲートの対象。同一 PR で直叩きテストを含める |

### 5-1. 敵対レビューで否決された 2 案

| 周 | 案 | 否決の理由(逐語の要約) |
| --- | --- | --- |
| 1 | **試行元を単位にしたハードロック**(閾値 20・ロック 300 秒)。会場の NAT による巻き込みを「残余リスク」として承認を求めた | **P0**: 攻撃者が被害チーム名を選べなくても、**試合中の利用者を妨害できる点は同じ**。FR-033 と ① に「名前を狙った場合」という限定はない |
| 2 | **全試行を直列化し、コミット後に逓増遅延**(上限 2000ms) | **P0**: コミット後の待機は**並行できる**ので定常状態の試行速度が下がらない / **順番待ちで「最大 2000ms」が成立しない**(100 件先行で約 25 秒) |

### 5-2. 判断いただきたい 1 点

**「試行が制限される」を「失敗した試行の速度に上限が掛かること」と読む**(1-1)。
正しい資格情報による試行は制限を受けない。

**この読みを認めない場合、FR-033 の 2 つの要求は両立しない。** 第三者が制御できる属性で
全試行を一律に制限する機構は、拒否でも遅延でも後段(締め出しに使えない)に反することが、
2 周の敵対レビューで実証された。その場合は**要件書 10 章の相談で、どちらを優先するかを
決めていただく**必要がある。

### 5-2-a. 3 周目で残った P0 3 件(上限に達したため人間の裁定へ)

**レビュー回数は設計書 6.3 の上限(3 周)に達した。** 残った指摘と、こちらの採否は次のとおり。

| # | 指摘 | 採否 |
| --- | --- | --- |
| 1 | **成功は順番待ちの外に出ていない。** 勧告ロックを照合より前に取るので、先行する失敗が遅延中なら後着の成功も待つ。**トランザクション単位の勧告ロックはコミットまで保持される**ので「照合の直後に解放」は誤り | **採用**(事実誤認はこちらにあった) |
| 2 | **失敗の待ち行列が DB 接続を占有する。** ロック待ちの要求もそれぞれ接続を保持し、既定のプール上限(SQLAlchemy 既定で約 15)を埋めれば、正しい資格情報も接続の取得で待つ | **採用** |
| 3 | **テスト計画が ⑤ の修正を打ち消していた**(6 節に「拒否ではなく上限の遅延」が残っていた) | **採用・反映済み** |

### 5-2-b. 4 案目を採った(2026-10-09・山田正輝の裁定)

**3 周の上限に達した後の案なので、敵対レビューを通していない。** 人間が直接判断した。
**1 節が本案で書き直されている**(本節は経緯の記録)。

レビュー側の案は「照合を先に済ませ、失敗だけがロックを取る」までで、
**失敗の待ちが接続を占有する問題(3 周目 P0-2)の解き方は『容量を隔離するか非ブロッキング取得』と
選択肢を示すにとどまっていた**。本書はそこを**予約票(`next_allowed_at`)**で解いた —
**待ちを DB の外へ出し、ロックもトランザクションも保持しない**(1-3)。

**この案には、人間の裁定が要る論点が 1 つある。**

**不変条件 ④「同じカウント単位への並行した試行は直列化する」の逐語は「試行」と書いており、
成功をロックの外に出すとその逐語から外れる。** ただし ④ の括弧書きは
**「(同時の失敗を数え落とさない)」**(`data-model.md:1792`)で、**成功は計数の対象ではない**ため、
**条文の目的は損なわれない**と読める。**この読みの可否が裁定の対象である。**

**同じ型の裁定が本書には既に 1 つある** — ② の「成功は対象外」を根拠に成功を速く返す読み(1-1)。
**④ も同じ向きに読んでよい、という裁定を得た(2026-10-09・山田正輝)。**

## 6. 実装上の制約

### 6-1. `authn.login` は置き換える

**`authn.login(text, text)` を `authn.login_attempt(text, text, text)` へ置き換え、
旧 2 引数版は除去する**(残すと制限の効かない入口が並存する)。

**トークンの識別子は `token_id uuid`**(失敗は `NULL`)。**`tenant_id` ではない** —
現行 `login` は `public.tenant_tokens` の行 ID を返し、署名器 `TokenPresentation` も
その ID を受ける(`FUNCTION:authn:login(text, text).sql:68-75`・
`backend/src/pitchlog/authz/token_presentation.py`)。

**戻り値は `token_id` と待ち時間の 2 値**とし、`OUT` 引数で返す
(`login_attempt(p_team_name text, p_password text, p_source text,
OUT token_id uuid, OUT wait_ms integer)`)。PostgreSQL の関数識別子は IN 引数だけで決まるので、
要素 ID は `FUNCTION:authn:login_attempt(text, text, text)` のままである。

**待ちは関数の内側で消費しない。** 1-3 の c5 のとおり待ち時間を返してコミットし、
**アプリ側がコミット後に待つ**。関数の内側で待つと、3 周目 P0-2(待ちが DB 接続と勧告ロックを
占有する)へ戻ってしまう。

旧署名が固定されている先: `contracts/authz/product/function-bodies/` の SQL manifest /
`contracts/authz/product/probe-product-map.json` / `backend/src/pitchlog/authz/runtime_contract.py` の
`PROTECTED_FUNCTIONS` と生成モジュール / `backend/tests/db/test_product_authz_authn_app.py` /
**`backend/tests/test_product_authz_catalog.py`(削除予定の SQL ファイルを直接読む)** /
**`backend/tests/test_product_authz_probe_product_map.py`(旧関数 atom を期待する)**。

### 6-2. Cookie を読む経路は U-M1 に依存する

**ログアウトと PW 変更は、要求から提示値を取り出さないと叩けない。** その処理は

### 6-3. Cookie の期限とスライディング延長

トークンの有効期限はスライディング延長(付録C `requirements:1220`)だが、`Set-Cookie` を
ログイン時にだけ出すと、**DB 側が延長されてもブラウザは元の期限で破棄する**。
**延長が起きた要求で `Set-Cookie` を出し直す**責務を δ が持つ。
