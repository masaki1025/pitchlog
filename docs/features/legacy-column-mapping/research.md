## 結論(要約)

**すべての結論に共通する射程の限界(先に読むこと)**: `docs/legacy/research/` の 9 本は
**Streamlit 版の解剖**である。旧システムにはもう 1 つの書き込み経路 — **Tsukuba PSS 内製の
FastAPI + React SPA** — があり、**その時期に書かれた行の挙動は 9 本のどこにも記述がない**(0 節)。
したがって以下の結論、とくに**センチネル定義(2 節)と先発オーダー判定(5 節)は Streamlit 期に
限って成立する**。FastAPI 期の実データ確認は**移行仕様タスクの射程**(送り先の正は
[plan.md](plan.md) 2 節の表)。

1. **`DM-LG-01`〜`DM-LG-16` / `DM-LX-01`〜`DM-LX-06` の ID 対応表はリポジトリのどこにも存在しない。**
   台帳には**件数(16 / 6)と所有ステップだけ**があり、内容は TSK-250 の調査メモに無番号の散文で載る。
   **本タスクの最初の作業は ID の割り当てそのもの**であり、TSK-250 が件数を exact-set で機械検査する
   ため **16 件・6 件は変えられない**(1 節・7-4)。
2. **座標の視点と左右反転は既決。人間裁定に上げる論点ではない。** Notion の DoD は「移行変換が恒等か
   左右反転かを旧資料だけでは確定できない」とするが、答えは旧資料から出るものではない —
   **要件書 付録 B-2/B-3 が「捕手視点・左打者をミラー保存しない」を確定し、B-5 が変換式を「(確定)」と
   明記**(`x_norm = x_old/263` = **x は恒等**、`y_norm = (263−y_old)/263` = **y のみ反転**)。
   旧側の視点も**改善台帳 I-17 が旧コード全経路の実査結果として記録済み**(4 節)。
3. **`DM-LG-03`(列 63-71 を新スキーマに残さない)は過去決定で片が付いていない、かつ「捨てる」は
   approved 3 本と衝突する。** FR-031(Must)・付録 D-3・改善台帳 I-5 が 88 列本体の不変を要求し、
   「不明」許容の射程は交代表記・出場履歴に限られて **88 列 CSV は射程外**。移行と互換出力は
   **設計書 6.3 の同一コア領域**なので「別領域だから」で逃げられない。**「保持のみ」へ倒せば要件改訂は
   不要**、「捨てる」を通すには要件書の改訂ゲートが必要で本タスクの射程外(7-5)。
4. **センチネルを列単位で 88 列全数について記録した(2 節)。ただし 20 列は「旧資料に記述なし」で
   確定していない**(加えて **列 33 は "両" 登録投手の場合に限り記述が無い**という条件付きの欠落 — 2 節)。
   `T250R` が未言及とした 10 列のうち 6 列は実は `DL` に記述があり、逆に `T250R` が挙げていない
   12 列が記述なし・不完全だった。とくに **列 53・54 は「該当イベントがない行の値」が不明**で、
   `FR-038` の NULL 件数突合の前提が立たない。**残りは本番 Supabase の実データ確認**を要する。
5. **`DM-LX-*` は `DL` vs `DB` ではなかった。** 6 件中 4 件は衝突相手が `IS`/`DOM`/`AR`/`DT` であり、
   `T250R` の切り分けが誤り。**`DL` precedence の射程は「88 列の意味・センチネル値・列名の罠」に
   限られる**ため、`DM-LX-03`(列 44 球種)・`DM-LX-04`(列 86-87 末尾 4)・`DM-LX-06`(座標の保存形式)は
   射程内で解けるが、**`DM-LX-01`(テーブル数)・`DM-LX-02`(接続プール)は射程外で未決** — 裁定権限を与えた
   決定が無く、設計書は「**優先順位を定めず「不明」と報告**」と定める(3 節・7-2)。
6. **`T250R` の「裏が取れない 5 件」のうち `DM-LG-04`(列 86-87 の情報喪失)は `T250R` 側が誤り。**
   `DOM:177` に明記があり、**情報喪失は取消経路限定**で通常系では 0 点の回(`0`)と未消化(`""`)を
   区別できる(1-3)。
7. **成果物の形は 3 つの要求集合の和で満たす必要がある。** 要件書 付録 D-1 の意味欄 4 項目と
   TSK-250 の受け渡し 4 項目は**同じ「4」でも集合が違い、調停した決定が無い**。置き場は
   `contracts/README.md` が「88列スキーマ定義」の収載を既に宣言し、`contracts/authz/oracle-seal.lock.json`
   が **元 commit・blob digest の完全な先例**を与える(8 節)。
8. **要件側の矛盾を 1 件検出 — `RQ-A`(P0 相当)。** 負値座標の扱いが付録 B-5(クランプ)と
   `FR-038`(`x<=0` を NULL 件数に算入)で食い違い、**負値が 1 行でも存在すると V2 の件数突合が
   構造的に不一致となり 8 章 DoD⑤ を満たせない**(6-5)。

#### 8-2. 写像 JSON の項目 — **3 つの要求集合を和で満たす**

| 出所 | 要求する項目 | 身分 |
| --- | --- | --- |
| **要件書 付録 D-1** `付録D-1` | **列名・順序・型** + 意味欄 4 項目(**実際の中身 / 旧コードの参照箇所 / 新スキーマの行き先 / 変換規則**) | **approved(最上位)** |
| **TSK-250 受け渡し契約** TSK-250 計画 1 節「射程の決定」 | `column_index = 0..87` をキー + **保存元 / 変換 / 欠損時規則 / 逆変換可能性** + スキーマ版・安定 ID・**共通正規化 ID**・元 commit・blob digest | 承認済み計画(2026-09-04) |
| **`FR-038`** | **列単位のセンチネル規則**(= 欠損時規則)。かつ `P1-9` により **「センチネル由来の NULL」と「解決不能由来の NULL」を別欄に分ける** | approved + 候補案 |

**両者の 4 項目は同じ「4」でも集合が違う**(「実際の中身」「旧コードの参照箇所」が TSK-250 側に無く、
「欠損時規則」「逆変換可能性」が要件側に無い)。**この差を調停した決定は存在しない**(7-6 #12)。

→ **和集合(下記 9 項目)を各列に持たせるのが安全**。どちらの検査にも落ちない:

`column_index`(0..87)/ `column_name`(`COLUMN_NAMES` の固定コピー)/ `type` /
`actual_meaning`(実際の中身)/ `legacy_code_ref`(旧コードの参照箇所)/ `target`(新スキーマの行き先)/
`transform`(変換規則 = 保存元 + 変換)/ `missing_rule`(欠損時規則 — センチネル由来と解決不能由来を分離)/
`reverse_mappable`(逆変換可能性)。加えてファイル単位で
`version` / `schemaVersion` / `stable_ids` / `normalized_ids`(**該当なしは明示的な空集合 + 理由**)/
`source_commit` / `blob_digest`。
