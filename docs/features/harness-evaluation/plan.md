## 4. 実装方針

### 重さ分類の根拠:**通常**(ただし検査経路に触れる)

- **コア領域(同期プロトコル / 状況計算 / 記録権 / テナント分離 / データ移行)に触れない**。`.claude/core-areas.json` の `areas[].paths` はすべて空(Phase 4 で定義予定)
- **ただし `guard_paths` の `.claude/skills/pr/SKILL.md` に触れる**。`/pr` の判定規則どおり「**guard_paths のみ該当 → 逐行確認チェックのみ有効化**」であり、**敵対レビューは不要・重さ分類は「通常」のまま**(コア領域該当時のみ adversarial + 逐行確認)。→ 計画レビューは `review normal`、PR 本文に **`- [x] コア領域/検査経路の変更: 人間による逐行確認を実施した`** を付ける
- 「軽微」ではない理由: **正本の新設**であり確定ゲートを通すため
- 「機械的軽作業」ではない理由: 様式の設計判断と起票内容の取捨選択を伴うため

### 様式(確定事項)

**変更履歴表を持たせる。ただし版は「様式の版」と定義する**(人間の裁定 2026-08-12)。

- **H-\* の追記では版を上げない** — 変更履歴表に 1 行追記する。この追記は「**様式・運用規則を変えない台帳内容の追加**」であり、7.6-3 前段(PR レビュー)として扱う
- **記載要素・運用規則・分類を変えるときだけ版繰り上げ + 確定ゲート**
- **同一版で複数行になること自体**は要件書 v1.8(`docs/requirements/requirements-pitchlog-2026-07-22.md:18-19`)に先例がある。ただし**先例は「版列が一意キーでない」ことの例に限る** — v1.8 の 2 行目は「frontmatter 追加・**本文の内容変更なし**」で、H-* 追記(実質的な内容追加)とは性質が異なる(計画レビュー 1 周目 P2-1)。**この違いは運用規則に明記する**
- これにより 7.1-3(正本は変更履歴表を持つ)に準拠しつつ、追記を軽く保てる。改善台帳のように**規約違反を新規に増やさない**

**構造**(改善台帳 `docs/improvements-from-baseball-scoring.md:1-11` の骨格を流用):

1. frontmatter — **厳格 3 行**(`status:` のみ。追加キー・行末コメント不可 — `check_docs_status.py:274-301`)
2. タイトル
3. **変更履歴表**(版・日付・変更内容・状態)
4. **運用規則の blockquote** — 目的 / **`H-*` は harness evaluation の項番であることの定義**(`P0/P1/P2` や `P-1` と紛らわしいため。改善台帳には記号の定義文がない)/ **番号は追記のみ・振り直しなし・欠番も再利用しない** / **版 = 様式の版**である旨と「H-* 追記は 7.6-3 前段」/ 追記導線
5. 分類ごとの節 → `### H-N: <一文タイトル>` をフラットに並べる
6. 末尾に **`## 候補`** 節(まだ傾向として確定していない単発事象の受け皿。改善台帳 `:218` の `## 追記候補` と同じ役割)

**各項目の記載要素**(改善台帳の 5 点を写像し 2 点追加):

| 要素 | 内容 |
| --- | --- |
| `**分類**` | プロセス設計 / 機構の穴 / 機能した点 |
| `**検出日**` | 出典を括弧で併記(worklog の `ファイル:行`・レビュー周回・PR 番号)|
| `**事象**` | 何が起きたか(改善台帳の「現行」に相当)。**典拠必須** |
| `**再発**` | N 件(横断で数えられるもののみ。単発は「1 件」)|
| `**なぜ問題か / なぜ効いたか**` | **機能した点は「観測事実・根拠・限界」を併記**する(「有効性の証明」と書かない — 計画レビュー 1 周目 P2-2)|
| `**追跡優先度**` | **高 / 通常**(`候補` は H-* を与えず `## 候補` 節へ)。`高` は `対応案` に **F-ID + worklog への相対リンク、または日付つき PO 見送り裁定が必須** |
| `**対応案**` | 改善台帳の「pitchlog」に相当。**別タスク化するものはそう書く**。**Notion URL は書かない**(7.4 `:351` — URL は worklog 側)|
| `**状態**` | 未対応 / 対応中 / 対応済み / **見送り**(見送りは理由と裁定日を必須)|

**`追跡優先度` の判定条件・3 分割の定義は台帳の「追跡優先度の判定条件」節が唯一の正**(確定ゲート 5〜6 周目 P1-4/P1-1 — 非正本の feature 文書を正にできない。本節へも複製しない = 7.1-1)。**起案時 19 件の割り当て導出記録**は [design.md](design.md) 2 節。本計画が受け入れ条件として要求するのは次の 3 点のみ。

- **判定が排他的である**こと(`候補` / `高` / `通常` のいずれか 1 つに一意に決まる)
- **起案時 19 件が design.md 2 節の対応表どおり**に割り当てられていること(**高 10 / 通常 8 / 候補 1**)。**確定ゲート中に追加した H-41 を含む現行の集計は 高 11 / 通常 30 / 候補 4**
- **将来追加される項目は台帳「追跡優先度の判定条件」節で判定**すること(design.md 2 節の対応表は起案時の集合に限る — 項目を固定すると腐る)

**状態欄は改善台帳に前例がない新設要素**。必要な理由: 本台帳には既に「見送り」判断が発生している(`deleteBranchOnMerge` の有効化 — `docs/worklog/2026-08-12-harness-evaluation.md:16`)。

### 追記導線(計画レビュー 1 周目 P1-2 で是正)

**主経路 = `/pr` のクローズ処理**。`/pr` の手順 1 は **worktree 側・feature ブランチ上**で走り、「この変更を最後のコミットとして PR に含める」ことを目的にしている(`.claude/skills/pr/SKILL.md:11`)。台帳追記をここに置けば**同一 PR で正本を運ぶ**規約(7.6-2)と整合する。

**「検討する」では誰がいつ判断するかが決まらない**(2 周目 P1-1)。次のとおり主体・時点・記録を固定する。

- **判断主体・時点**: **PR 作成者が、クローズ処理の最終コミットを作る前に判断する**(手順 1 の中)
- **該当する場合**: 同一 PR で **① 計画書 3 節へ宣言を先に追記 → ② 台帳へ H-* を追記 ③ 台帳の変更履歴表に 1 行追記 ④ 索引の最終更新日を現行化**(②〜④ は同一コミット)。**宣言を先に置く順序は `/sync-docs` の規律と揃える**(`sync-docs/SKILL.md:13-24` — 3 周目 P1-2)
- **該当しない場合**: **「台帳への追記なし」と理由を worklog に残す**(判断したことを記録に残し、忘れたのか判断したのかを区別できるようにする)
