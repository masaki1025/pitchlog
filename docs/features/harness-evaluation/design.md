# 詳細設計: 追跡優先度の割り当てと follow-up タスクの束ね方

`plan.md` 4 節から参照される詳細設計。**計画レビュー 3 周目 P1-3** の指摘「`追跡優先度` の基準は research.md 5 節の全 19 件へ一意に適用できない(N-11 は制御目的の典拠自体が未確認)」に対応し、**既知の 19 件については判定を対応表で固定**する。**時点注記(確定ゲート 5〜6 周目)**: 将来追加される項目の判定は **台帳 `../../development/harness-evaluation.md` の「追跡優先度の判定条件」節**に従う(本書は approved 後は履歴)。**本書 2 節の対応表は起案時 19 件に限る**(項目を固定すると腐るため)。

## 1. 判定条件(2 条件の同時成立)

> **時点注記(確定ゲート 5 周目 P1-4)**: 本節は**起案・確定時に使用した設計**。**approved 後の判定条件の正は台帳 `../../development/harness-evaluation.md` の「追跡優先度の判定条件」節**(`docs/features/` は活動中のみ意味を持つ一時ディレクトリ — 設計書 7.2 `:329`・7.6-4 `:370`)。本節は 2 節の割り当て導出記録として保存する。

2 つの条件で**排他的に 3 分割**する(4 周目 P1-2 — 「どちらか欠ける = 通常」と「典拠が未確認 = 候補」は重複しており、`候補` が `通常` にも該当してしまうため)。

- **条件 ①(制御目的の典拠)**: その機構が「何を止める / 何を検査する」ことになっているかが、リポジトリ内の記述(docstring・スキル本文・規約・設計書)で示せる
- **条件 ②(誤った振る舞いの実証)**: 現行で **(a) 正しい操作を止める**(誤検知)/ **(b) 止めるべき操作を通す**(fail-open・空回り・検査漏れ)のいずれかが起きることを実ファイル・実測で示せる
  - **② は「既存の機構が」誤った振る舞いをしていることを要する**(確定ゲート 1 周目 P1-3 で明文化)。**そもそも機構が存在しない**(未実装・未着手)ものは ② に該当しない — 振る舞う主体がないため。この線引きが **H-4 と H-20 の非対称を説明する**: H-4 は `/pr` 手順 2-2 という**既存の機構に穴があった**(片方向だった)ので `高`、H-20 は**波及チェックの機構がそもそも存在しない**ので `通常`
  - **適用範囲は `分類: 機構の穴` に限る**。条件 ①② はいずれも「機構が何を止める / 検査するか」を前提に書かれており、**`プロセス設計` と `機能した点` には適用しない**(両者は常に `通常`)
- **`プロセス設計` の歯止め**(`追跡優先度` の代わり): **`再発` が 3 件以上のものは `対応案` に「何を変えるか」を具体的に書く**(「未対応」だけで放流しない)。follow-up タスクまでは要求しない — 多くは運用規律の変更でコード修正を伴わないため。※ 該当は H-19(5 件)・H-20(9 件)・H-21(8 件)・H-22(5 件)・H-23(4 件)・H-24(3 件)・**H-25(7 タスク — 観測指標であり「変えるべきこと」は収束コストの低減。対応案に 2 案を明記済み)**

| 判定 | 条件 | 扱い |
| --- | --- | --- |
| **候補** | **① なし**(② の評価自体ができない) | `## 候補` 節へ置き **H-* 番号を与えない**。典拠が確認できた時点で `高` / `通常` へ昇格 |
| **高** | **① あり かつ ② あり** | H-* を与える。`対応案` に **F-ID + worklog への相対リンク、または日付つき PO 見送り裁定が必須** |
| **通常** | **① あり かつ ② なし** | H-* を与える。follow-up の必須要件はかからない |

`通常` は「重要でない」ではなく「**放置しても誤った振る舞いは起きない**」の意。記録すること自体が成果物である。

## 4. `/pr` 手順 2-2 の双方向突合 — 対象範囲と処理順

**双方向化の必要**(**ステップ 5 以前の状態**): 「宣言済みで未反映」だけを中断していたため、**正本を更新したのに計画書 3 節へ宣言し忘れると素通りした**。**現在(ステップ 5 以降)は `pr/SKILL.md` の「2. 突合」節が双方向**になっている(ただし**自然言語の手順であり機械化は未対応** — 機構化は F2)(実例 = `docs/worklog/2026-08-11-req-v1-9-nfr021-wsl2.md:110`)。

**対象範囲**(全 `diff --name-only` を逆突合すると、この PR 自身に含まれる feature 文書・worklog・スキルで**誤中断する** — 計画レビュー 3 周目 P1-2):

- **突合対象**: `docs/README.md` / **索引に掲載されている正本** / **新設する正本の配置先**
- **除外**: `docs/features/**`・`docs/worklog/**`・`docs/legacy/**`・`docs/development/templates/**`・`.claude/**`・リポジトリ直下の規約ファイル(`AGENTS.md`・`CLAUDE.md`・`README.md`)
  - 除外の根拠: これらは索引に載らない = 正本ではない(設計書 7.2 `:330` 「worklog は記録であり正本ではない」/ `check_docs_status.py:15-19` の除外リスト)。正本外だが同一 PR で運ぶファイルは**計画書 3 節の別枠(「正本体系外だが同一 PR で更新するもの」)**で宣言する運用を維持する

**処理順**(`/sync-docs` の規律 = 宣言を先に更新、と揃える — `sync-docs/SKILL.md:13-24`):

1. **計画書 3 節の宣言を先に更新**する
2. **正本・変更履歴表・索引を同一コミットで更新**する
3. **双方向突合**を行う(宣言済み未反映 / 差分にあるのに未宣言 の両方を中断対象)

**fast path は現行どおり別規則**(`pr/SKILL.md` の fast path 分岐では 2-2 を「正本への影響がない」ことの差分確認に置換する)。双方向突合はこの置換後の確認にも同じ対象範囲を適用する。
