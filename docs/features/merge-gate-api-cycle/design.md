# 詳細設計: マージゲートと API の循環 — 選択肢の比較

**本書は選択肢の比較と 12-4 の条文判定を持つ。** 調査の事実と典拠は
[research.md](research.md) が正で、本書は内容を複製しない(設計書 7.1-1)。

## 1. 「確定ゲート数」の数え方(柱書)

比較表の「確定ゲート」列は、**設計書 7.3 の確定ゲート(敵対レビュー → 人間承認)を
何回起こすか**を数える。数え方は次の 2 条による。

| 条 | 内容 | 典拠 |
| --- | --- | --- |
| **置き場ごとの要否** | `docs/requirements/`・`docs/design/`・`docs/development/`・`docs/ops/` は**必須**。`docs/adr/` は**必須(軽量版可)**。`docs/worklog/` は**不要**(記録であり正本ではない)。`docs/features/` は**計画レビューのみ**(正本ではない) | 設計書 7.2 の表 |
| **approved の再変更** | 「**approved 済み正本の再変更は新しい版として同じゲートを通す**(軽微な誤字等は人間判断で省略可、ただし変更履歴には残す)」 | 設計書 `dev-harness-design-2026-08-07.md:435` |

したがって:

- **`data-model.md` 12-4 の改訂は 1 ゲート**(approved 済み正本の再変更)。
  ただし**通過条件の変更は「軽微な誤字等」に当たらない**ので省略できない
- **ADR の新設は 1 ゲート。ただし軽量版が使える**(7.2 の表)ため、
  `docs/design/` の全文ゲートより**レビュー面が小さい**
- **worklog への裁定の記録は 0 ゲート**
- **`docs/features/` の `design.md`(本書)は 0 ゲート**

**「人間の手番」列**は PO の裁定・承認の回数を数える。
**全案に共通する本計画の承認 1 回は除く。**

**注意**: ゲート数が少ない案が常に良いわけではない。
**0 ゲートの案は「条文に残らない」という別のコストを持つ**(7.3-5 の終結は当該ゲート内で
のみ有効で、別文書の全文レビュー周には効かない)。**表の「依存」列と併せて読むこと。**

### 推奨の組

> **⑧ で即時解除 → ⑦ で条文化 → 中身は ⑤。**

**合計 確定ゲート 1 回・PO の手番 2〜3 回。** ⑥ 単独(実質 2 ゲート)より安く、
かつ循環が実際に解ける。

**⑧ を単独で終わらせない理由**: 条文に残らないと、TSK-317 の計画書が書いた
「本タスクの成果を『NFR-010 適合』と主張しない」(`pg-authz-verification-g2/plan.md:157`)
との緊張が条文上に残り、**別文書の全文レビュー周で再燃する**。

## 3. 12-4 の条文判定

### 3-1. 12-4 は 3 つを重ねているが、どこまで揃えれば通過なのかを書いていない

`data-model.md:2437-2444` の 6 行のうち、通過に関わるのは 3 つある。

| 行 | 条文(逐語) | 性質 |
| --- | --- | --- |
| **通過条件** | 「① RLS のポリシーとロールの DDL が実スキーマへ適用されている ② **その実スキーマに対して越境テストが green である**(NFR-019(b) の越境テスト)」 | **通過の定義** |
| **越境テストの最低要求** | 「① アプリ用ロールが関数を経由せず他テナント行を読めないこと ② `PUBLIC` が越境関数を実行できないこと ③ `search_path` の乗っ取りが効かないこと ④ 対象側が非共有なら要求元が付与していても返らないこと」 | **下限** |
| **測定経路** | 「NFR-010 の測定方法が『**API 直叩き含む**』と定めるので、**アプリ経路だけの検証では通過にしない**」 | **禁止** |

**条文はこの 3 つの関係を書いていない。** 「最低要求 4 件を満たせば通過」なのか、
「最低要求は下限にすぎず NFR-019(b) の網羅が要る」のか、
「さらに測定経路の条件も同時に満たす必要がある」のかが決まらない。

### 3-2. 最低要求 4 件は全件がアプリ経路ではない(逐語)

上表の最低要求 4 件を逐語で読むと、**参照している主体は次のとおり**である。

| # | 主体 | 層 |
| --- | --- | --- |
| ① | **アプリ用ロール**が**関数を経由せず**他テナント行を読めないこと | **DB ロール** |
| ② | **`PUBLIC`** が越境関数を**実行**できないこと | **関数 ACL** |
| ③ | **`search_path`** の乗っ取りが効かないこと | **セッション設定** |
| ④ | **対象側が非共有なら要求元が付与していても返らない**こと | **関数の返却契約** |

**HTTP に対する要求は 1 件も無い。** そして 12-7(1)(`:2672-2675`)は
「**実 PostgreSQL 上で**越境テストを書いてから確定する」と要求している。

**したがって最低要求 4 件は、HTTP API が 1 本も存在しない現在でも実行できる。**
実行主体は TSK-317(作成)と TSK-344(実スキーマでの再実行)である。

### 3-3. 「アプリ経路」の定義が無く、2 通りに読める

**`data-model.md` にも要件書にも「アプリ経路」の定義は無い。** そして
**同じ文書の中で「API 直叩き」の用法が割れている。**

| 箇所 | 逐語 | 読める意味 |
| --- | --- | --- |
| `:161-163` | 「NFR-010 の測定方法は『越境アクセスの自動テスト(API 直叩き含む…)』である。**DB 側に既定拒否があれば、経路を足したときのテスト追加漏れが構造的に塞がる**(アプリ層のみだと『新しい経路を書いたがテストを書き忘れた』が越境そのものになる)」 | **読み ①**: アプリ層のみの**強制/検証を否定**する語。DB 側既定拒否の根拠として使われている |
| `:246` | 「関数本体の正しさに関係なく越境できる(NFR-010 の『**API 直叩きを含む全経路**』に反する)」 | **読み ②**: **全経路の網羅**を要求する語。API 直叩きはその 1 つ |

**読み ① を採ると**、最低要求 4 件は全件が DB 層なので**禁止に触れず、現在でも通過し得る**。

**読み ② を採ると**、HTTP 経路を含む全経路の網羅が要るので、**API が無い現在は通過できない**。

**この分岐が「テスト専用エンドポイントで足りるか」「API が無くても通過できるか」の
答えを逆転させる。** 条文だけでは決まらない。

**どちらでも変わらない部分**もある。**通過条件①(RLS の DDL が実スキーマへ適用)は
どちらの読みでも未充足**であり、**律速は TSK-317** である
(`backend/migrations/` に `CREATE POLICY` / `CREATE ROLE` / `ROW LEVEL SECURITY` は 0 件)。
**読みの分岐が効くのは、①が充足した後**である。

### 3-4. 経路を決めるのは NFR-010、合否と網羅を決めるのは NFR-019(b)

| | 定めているもの | 典拠(逐語) |
| --- | --- | --- |
| **NFR-010 測定方法** | **経路**と常設先 | 「越境アクセスの自動テスト(**API直叩き含む**。CIに常設 → NFR-019)」(要件書 `:846`) |
| **NFR-019(b)** | **合否判定基準**と**網羅すべき組合せ** | 「越境アクセステスト — **合否は『越境が1件でもあれば fail』ではなく『FR-034 の認可行列どおりに通り、行列外はすべて404』で判定する**。網羅すべき組合せは: 付与の粒度3種の組合せ × 相互性 / グループ終了後・離脱後・付与撤回後・テナント無効化後 / 複数グループへの同時参加 / 資源種別ごと …」(要件書 `:928`) |

**`NFR-019(b)` の本文は経路を一切名指ししていない**(`:928` を全文確認)。
したがって **12-4 が通過条件②で `NFR-019(b)` を、測定経路で `NFR-010` を引いている分担は、
要件書自身の分担と一致する。**

**この分担から出る帰結**: **測定経路の一次典拠は `NFR-010`(`:846`)だけである。**
`NFR-019(b)` にも `NFR-021` にも経路の規定は無く、**代替典拠にならない。**
特に `NFR-021` は Phase 4 完了時に越境を対象外としており(`:956`)、
**時点の説明には使えても経路の根拠にはならない。**

### 3-5. per-PR の判定と対象横断の判定は分けられるか

**要件書は 2 つの時点を分けている。**

| 時点 | 条文(逐語) | 典拠 |
| --- | --- | --- |
| **Phase 4 完了時** | 「ハーネスの pytest・backend の pytest・frontend の Vitest が成功し、開発 DB へ接続でき、backend/frontend が起動して疎通確認できること(**一致性・越境・E2E・同期故障系は実装期のため対象外**)」 | 要件書 `:956` |
| **リリース候補時** | 「**NFR-019 の全ランナー**(pytest・Vitest・Playwright)**および同項の (a)〜(d) がすべて成功すること**、および NFR-018(b) の機械検査が成功すること」 | 要件書 `:957` |

**「越境テストが全部通っていること」を要求しているのはリリース候補時**であって、
Phase 4 完了時ではない。

**ADR-003 が同型の分け方を確立している。**

> **その変更は、当該対象について全検査が緑であることをマージの条件**とする
> (要件書 NFR-018 の「正解ベクタは完成をもって発効する」= **未完成のあいだ適合と判定しない**
> であって、**実装を禁じるものではない**)
> — `docs/adr/ADR-003-domain-calc-method.md:389`

ADR-003 はさらに、**この分け方を採った理由が本件とまったく同じ**だと書いている。

> **循環しない形で定める** — 検査は生成物・**製品入口**・変異対象が存在しないと緑にできないため、
> 「緑になってからコードを追加する」とは書けない
> — 同 `:387`

**ただし ADR-003 型の一般則は `NFR-018` に限定されている。**
ハーネス設計書 `:897` は「**ただし `NFR-018` の対象計算に触れる実装は**」と対象を絞っており、
**`NFR-010` / 12-4 には対応する条項が無い。**

### 3-6. 反証 — 越境テストの作成者自身が「NFR-010 適合と主張しない」と書いている

**この判定に不利な材料を明示する。**

> HTTP 経路の判定(`404` / `400` / 存在秘匿の同値性)と `NFR-019`(b) の 13 クラスのうち残り 12
> → **TSK-217**。`NFR-010` の測定方法が「**API 直叩き含む**」と定める。DB 層は「0 行」と
> 「権限拒否」を区別してしまう。**本タスクの成果を「`NFR-010` 適合」と主張しない**
> — `docs/features/pg-authz-verification-g2/plan.md:157`

**越境テストを作る当人が、DB 層だけでは `NFR-010` 適合と主張しないと宣言している。**
読み ① を採っても、**DB 層の green が `NFR-010` 適合を意味しないことは動かない。**

**ただしこれは「適合の主張」の話である。** ADR-003 `:389` が
「**未完成のあいだ適合と判定しない**であって、**実装を禁じるものではない**」と分けたのは、
まさにこの区別である。**「per-PR のマージゲートを通す」と「NFR-010 適合を宣言する」を
別物として運用できるかどうか**が、裁定 A の争点になる。

**分担の裏づけは要件書自身にもある**(上表 3-5 の 2 時点)。
`NFR-010` 適合の宣言はリリース候補時の受入(`:957`)で行えばよく、
per-PR のマージゲートと同じ時点である必要は条文上どこにも書かれていない。

### 3-7. まとめ — 条文から出ること・出ないこと

| | 判定 |
| --- | --- |
| **条文から出ること** | 最低要求 4 件は全件が DB 層で HTTP を要求しない / 経路を決めるのは `NFR-010` だけ / 要件書は「Phase 4 完了時」と「リリース候補時」を分けている / 通過条件①が未充足で律速は TSK-317 |
| **条文から出ないこと** | 3 条件のどこまでを揃えれば通過か / 「アプリ経路」が何を指すか / per-PR と対象横断を分けてよいか / 「製品機能」の規範的定義 |

**「条文から出ないこと」の 4 件が、そのまま裁定の対象**である。

## 4. PO 裁定 3 件

**3 件は独立に否決できる。** どれか 1 件を否決しても残る 2 件は意味を持つ
(独立性の確かめ方は 4-4 節)。

### 裁定 A — 適用単位

**問い**: 12-4 のゲートは **何を単位に**判定するか。

| | 内容 |
| --- | --- |
| **推奨** | **当該 PR が開く経路について**判定する。対象横断の `NFR-019(b)` 網羅と「`NFR-010` 適合」の宣言は、**リリース候補時の受入**で行う |
| **典拠** | ADR-003 `:389`「**未完成のあいだ適合と判定しない**であって、**実装を禁じるものではない**」/ 同 `:387`「検査は生成物・**製品入口**・変異対象が存在しないと緑にできないため『緑になってからコードを追加する』とは書けない」/ 要件書 `:956`(Phase 4 完了時は越境を対象外)・`:957`(リリース候補時に `NFR-019` の (a)〜(d) がすべて成功) |
| **対立案** | 12-4 の通過条件②は「越境テストが green」であり、`NFR-019(b)` は**対象横断の集合**を網羅すべき組合せとして列挙している(要件書 `:928`)。**per-target 構造は 12-4 にも `NFR-019(b)` にも書かれていない** |
| **弱点** | ADR-003 型の一般則は **`NFR-018` に限定**されている(ハーネス設計書 `:897` の「ただし `NFR-018` の対象計算に触れる実装は」)。`NFR-010` / 12-4 に転移させるには**明示の裁定が要る** |
| **反映先** | `data-model.md` 12-4(条文化タスクへ) |
| **裁定しないと何が止まるか** | **FR の実装 PR が 1 本も通せない。** 対象横断の網羅を per-PR で求める限り、最初の 1 本は永久に条件を満たせない |

### 裁定 B — 測定経路

**問い**: 「**アプリ経路だけの検証では通過にしない**」を**どう充足**したことにするか。

| | 内容 |
| --- | --- |
| **推奨** | **当該 PR が HTTP 経路を開く場合は、その経路の HTTP 直叩きテストを同一 PR に含める**ことをもって充足とする。**HTTP 経路を開かない PR には空の要求として掛かる** |
| **典拠** | 12-4 の測定経路行の規範文は**禁止**である(`:2442`)。越境テストの最低要求 4 件は**全件が DB ロール・関数 ACL・セッション設定・関数の返却契約**への要求で、**HTTP への要求は 1 件も無い**(`:2441`) |
| **対立案** | `data-model.md:246` は「`NFR-010` の『**API 直叩きを含む全経路**』に反する」と書いており、**全経路の網羅を要求する語**として使っている。この読みなら **API が無い現在は通過できない** |
| **弱点** | **同じ文書の中で用法が割れている**(`:161-163` は読み ①・`:246` は読み ②)。**条文だけでは決着しない**。加えて TSK-317 の計画書が「**本タスクの成果を『`NFR-010` 適合』と主張しない**」(`pg-authz-verification-g2/plan.md:157`)と書いている |
| **反映先** | `data-model.md` 12-4(条文化タスクへ) |
| **裁定しないと何が止まるか** | **裁定 A が通っても最初の API PR が通せない。** A は「単位」を決めるだけで、「その単位で何を測れば足りるか」は B が決める |

### 裁定 C — 所有者

**問い**: **「製品 HTTP 経路(API)の実装」を誰が持つか。**

| | 内容 |
| --- | --- |
| **推奨** | **各 FR の実装タスクが、自経路の HTTP 越境テストごと持つ**(裁定 A の per-PR と揃う)。TSK-217 は**対象横断の判定とハーネス**の所有者として残し、**前提「FR-041 の実装が先。実装がないと構成できない」を「FR-041 の実装 PR と同一変更」へ訂正**する |
| **典拠** | TSK-367 の候補 3 に「**製品機能の各実装タスク**(機能固有の判定)」が既に挙がっている / `contracts/authz/http-route-matrix.json` に **37 経路が FR 番号で凍結済み**(全件 `test_owner = TSK-217` の `planned`)なので、**FR ごとの割り当ての母集団は既にある** |
| **対立案** | 単一の「API 実装タスク」を立てて 37 経路をまとめて持たせる。**利点** = 契約の一貫性を 1 タスクで担保できる。**欠点** = そのタスク自身が最初のゲート通過の当事者になり、A・B が否決されると詰まる |
| **弱点** | **TSK-367 が「`contract_only` 158 行の受取先を決める」タスクとして既に存在する。** 同じ問いを 2 箇所で決めないよう、**起票の前に TSK-367 と突合する必要がある** |
| **反映先** | **正本ではない。** Notion のタスク定義(TSK-217 の前提の訂正・新規起票)。**設計書 7.4 のとおり作業管理面なので確定ゲート不要**。**A・B と違い反映先の正本の節を持たない** |
| **裁定しないと何が止まるか** | **A・B が通っても着手する人がいない。** 現に「製品 HTTP 経路の実装」の所有者は不在で、TSK-317 が「新規起票」として送った先が空手形になっている |

### 4-1. 条文化の乗り物(裁定 A・B を採った場合のみ)

裁定 A・B を採るなら、**条文に残す必要がある**(0 ゲートのままだと
`pg-authz-verification-g2/plan.md:157` との緊張が条文上に残り、
**別文書の全文レビュー周で再燃する**)。乗り物は 2 案。

| 案 | 中身 | ゲート |
| --- | --- | --- |
| **⑦(推奨)** | **ADR-004 を新設し、同一の確定ゲートで 12-4 を追随改訂する。** 先例は ADR-003 の「本 ADR と**同一の確定ゲート**で要件書 v2.2 として改訂する」(`:387`・`:152`)。ADR は 7.2 の表で「必須(**軽量版可**)」なので `data-model.md` 側を 1〜2 行に抑えればレビュー面が最小 | **1** |
| **②** | `data-model.md` 12-4 の単独改訂 | **1**。ただし実績コストが高い(v0.2 は契約表 4 行の是正に確定ゲートのレビュー実行 10 回・PO 裁定 4 回) |

**どちらでも `S-4` の「12-4 節冒頭の旧文言の現況化」を同乗させる**
(⑩ の却下で受け取り手が無いことが判明したため)。

### 4-2. 裁定しない選択(①)の帰結

**FR の実装 PR が 1 本も通せない状態が続く。** ハーネス設計書 v1.13 が同型の詰まりを
「Phase 表が Phase 5 で終わることにより製品実装の位置づけが**規範上不明**で、
**それが着手を止めていた**」(`:64`)と記録しており、**同じ状態の再現**になる。

### 4-3. 律速は裁定ではない — TSK-317

**裁定 A・B・C がすべて通っても、通過条件①(RLS のポリシーとロールの DDL が
実スキーマへ適用されている)が未充足なら誰も通過できない**
(`backend/migrations/` に `CREATE POLICY` / `CREATE ROLE` / `ROW LEVEL SECURITY` は **0 件**)。

**①の産出者は TSK-317(進行中)である。** 裁定は**①が充足した直後に詰まらないための先回り**
であって、**今すぐ何かが動き出すわけではない。**

### 4-4. 独立性の確かめ方

**3 通りすべてで、残る 2 件が意味を持つことを確かめる。**

| 否決するもの | 残る 2 件がどう意味を持つか |
| --- | --- |
| **A を否決** | ゲートは対象横断のまま。**B は「対象横断の網羅に HTTP 経路を含めるか」の問いとして残り**、**C は「誰が対象横断のテストを作るか」の問いとして残る** |
| **B を否決** | 測定経路は「全経路の網羅」のまま。**A は「その網羅をいつ判定するか(per-PR かリリース候補時か)」の問いとして残り**、**C は所有者の問いとしてそのまま残る** |
| **C を否決** | 所有者は別途決める。**A・B は条文の読み方の問いとして完全に成立する**(誰がやるかと、何を満たせば通過かは別) |
