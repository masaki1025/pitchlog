## 4. 実装方針

### 重さ分類の根拠 — **コア領域**

**コード変更 0 行の文書タスクだが、意味範囲としてコア領域(テナント分離)に該当する。**
設計書 6.3 の境界定義表のテナント分離の行が、含む側に
「**全出力経路の越境**(管理者画面・共有画面・エクスポート・CSV・PDF・**API 直叩き**・
キャッシュ無効化)+ **NFR-010 の越境防止**」を挙げている。本タスクの裁定 A・B は
**まさにその「API 直叩き」と NFR-010 の測定経路の解釈を決める**。

同表は「**判定に迷うコードは含む側に倒す**(fail-closed — 誤って強化レビューする方が、
誤って外すより安全)」と定める。**先例**: コード 0 行の文書タスクを意味範囲で
コア領域と判定した `../data-model-handoff-revision/plan.md` の重さ分類。

**したがって敵対レビューと人間の逐行確認を行う。**

**機械検知は発火しない**(変更するのは `docs/development/harness-evaluation.md`・
`docs/README.md`・`docs/features/` 配下・`docs/worklog/` だけで、いずれも
`.claude/core-areas.json` の `paths` にも `guard_paths` にも該当しない)。
**CLAUDE.md が「意味範囲の正は設計書 6.3 の境界定義表 / paths〔機械可読〕の正は
`core-areas.json`」と分けている**とおり、**発火しないことは該当しないことを意味しない**。
`/pr` ではチェック項目を手で有効化する。

**本タスクの成果物は PO 裁定の入力**であり、裁定は正本の改訂へ波及する。
**判断材料の正確さが成果物の品質そのもの**なので、典拠のない主張を 1 件も置かない。

## 6. テスト計画

**NFR-019 のテスト種別に足すものは無い。** 製品コードを書かないため。

代わりに**文書の内部整合と既存の機械検査**で担保する。

| 種別 | 何を回すか |
| --- | --- |
| 既存の機械検査 | `uv run ruff check .` / `uv run ty check` / `uv run pytest tests/`(ルート)。**新設した文書が既存の文書検査を壊さないこと** |

**人が読んで確かめること**(機械化できない部分):
