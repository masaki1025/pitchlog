# 調査メモ: マージゲートと API の循環

## 問い

`data-model.md` 12-4 節のマージゲートは、越境テストを「API 直叩きを含む経路」で測定しないと
通過にしない。しかし API を作ること自体が「DB を利用する製品機能」の実装 PR なので
ゲート対象になる。**API の最初の 1 本をどう通すか。**

## 結論(要約)

1. **ゲートの例外規定は正本のどこにも存在しない**(全数走査で不在)
2. **「製品 HTTP 経路(API)の実装」に所有者がいない**(Notion 精査で確認)。TSK-217 は
   越境テストの実装のみで API を作らず、TSK-367 は「受取先を**決める**」タスク。
   **循環は実在する** — FR-041 の実装 → 12-4 のゲート → 越境テスト(TSK-217)→ FR-041 の実装
3. **同型の問題を ADR-003 が既に決着させている** — 「ゲート = 未完成のあいだ適合と判定しない
   であって、実装を禁じるものではない」。解き方は**適用単位を対象 1 件ごとに落とし、
   検査を同一変更として追加する**
4. **「API 直叩き」は旧要件書からの継承文言**で、旧システムはそれを一度も満たしていなかった
5. **12-4 は 3 つの条件を重ねているが、どこまで揃えれば通過なのかを書いていない**。
   越境テストの最低要求 4 件は **HTTP API が 1 本も無くても実行できる**

**Notion カードの前提 2 件がリポジトリで裏付けられない**(下記 6 節)。

### 5. ADR-003 の先例 — 同型の循環を決着済み

`docs/adr/ADR-003-domain-calc-method.md:387-390`(approved):

> **ただし着手できる範囲には順序がある**(**循環しない形で定める** — 検査は生成物・製品入口・
> 変異対象が存在しないと緑にできないため、「緑になってからコードを追加する」とは書けない):
> 1. **ベクタの schema と検査基盤を先に確定する**(この段階では対象計算のコードを追加しない)
> 2. **対象計算 1 件ごとに、正本・生成物・製品経路の呼び出し部・その対象の 3 層検査を
>    「同一の変更」として追加**する(片側だけのコミットを作らない)
> 3. **その変更は、当該対象について全検査が緑であることをマージの条件**とする
>    (**未完成のあいだ適合と判定しない**であって、**実装を禁じるものではない**)
> 4. **対象横断の判定は、対象すべての契約が完成してから**行う

**ADR-003 は「検査は製品入口が存在しないと緑にできない」という本件と同一の構造を認識し、
適用単位を落とすことで解いている。**

**ただし 12-4 の文言は ADR-003 より強い。** 12-4 の 2 項は「マージ**または有効化**しない」と
書いており、ADR-003 の「実装を禁じるものではない」がそのまま転移するとは限らない。
**この読みが通るかは条文解釈であり、PO 裁定を要する**(推論)。

### 10. 12-4 の内部的な緊張(条文の不備)

12-4 は通過条件として **3 つを重ねているが、どこまで揃えれば通過なのかを明示していない**:

- 通過条件② 「越境テストが green」
- **越境テストの最低要求 4 件** — すべて DB ロール / 関数 ACL / `search_path` に対する要求で、
  **HTTP に対する要求は 1 件もない**。12-7(1)(`:2672-2675`)も「**実 PostgreSQL 上で**
  越境テストを書いてから確定する」と要求
- 測定経路 「API 直叩き含む」

**最低要求 4 件は HTTP API が 1 本も無くても実行できる。** spec-checker と legacy-analyst が
独立に同じ結論に達している。

また **「アプリ経路」の定義が 12-4 にも要件書にも無い**(不明)。2 通りに読める:
① 画面操作経由の検証だけでは不可(API を直に叩け)/ ② アプリ層を通した検証だけでは不可
(DB ロール直の検証も要る — 3-1 節 `:153-163` の「アプリ層のみの強制」批判と同系)。
**どちらを採るかで「テスト専用エンドポイントで足りるか」の答えが逆転する。**

### 12. 射程解釈の仮説の判定

**仮説**(Claude が立てた): 越境テスト専用で製品機能を提供しないエンドポイントは
「製品機能」に当たらず 12-4 の対象外ではないか。

**判定: 条文からは成立も不成立も出ない。**

- **「製品機能」の規範的定義がどこにもない**。要件書 3 章の用語定義 8 語(`:124-132`)にも、
  `data-model.md` 1-1 節の定義の所在表 13 行(`:49-64`)にも無い。同表 `:66` は
  「この表に無い事項を後から複数節へ書くときは、まず定義節を決めて行を足す」と定めており、
  **12-4 の「製品機能」は定義節を持たないまま使われている**
- **弱い支持**: `data-model.md:532`(3-6 節)が「**probe と製品は別の層として扱う**」と
  非製品(検証専用)を別扱いした前例。ただし対象は DB の `SECURITY DEFINER` 関数であって
  API ではなく、同じ文が「**製品の返却契約を緩めるものではない**」と釘を刺している。
  `probe` の語は 12-4 節に 0 件
- **不利な材料**: non-serving 宣言①「利用経路を開かない」。テスト専用でも本番到達可能な
  HTTP 入口を足せば「利用経路」に当たるかは正本に判定基準なし
- **外延的な手がかり 1 件**: ハーネス設計書 `:894`「**要件書の FR が定める製品機能**の実装は、
  本章の Phase の対象外とする」。「製品機能 ≒ FR が定めるもの」と読めるが、
  12-4 のゲート対象を定義する条項ではない

**解釈で通す対象ではなく、裁定として記録する対象**(推論)。
