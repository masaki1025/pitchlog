# MVP 規則選択トラック: 画面上の7回/9回・延長上限

## 実装した利用者操作

試合作成画面で「適用する規則」を選べる。

- `試合区分の既定規則を使う`（既定）: 現在の段階A解決結果をそのまま保存する。
- `規定回と延長上限を選ぶ`: 規定回 `7` / `9`、延長上限 `7` / `9` / `12`
  （延長上限は「行える最終回の番号」）を選ぶ。

選択値は `POST /games` の `rule_choice` として送り、作成serviceが段階Aの既定
snapshotへ一度だけ適用して `games.applied_rules` へ保存する。以後の開始・記録・
終了・再読込は保存済み6-key snapshotだけを読む。

## 実装境界

- 単一codec `decode_applied_rules` / `encode_applied_rules` を変更せず再利用する。
- 差し替えるのは `regulationInnings` と `extensionLimit` だけ。コールド条件とDHは
  既定規則から引き継ぐ。
- タイブレークは新設・移動しない。既定の開始回が規定回以下、または延長上限を
  超える場合は到達不能として `null` にする。到達可能なら既定値をそのまま残す。
- 値が変わらない選択（例: 公式戦の9回・12回）は既定の `ruleSetId` と5値を
  そのまま返し、IDを増やさない。
- 値が変わる選択は固定名前空間の UUIDv5 で派生 `ruleSetId` を作る。これは
  画面presetの安定IDであり、DB `rule_sets` の行ではない。
- SQL関数・認可資産・新しい規則計算エンジンは追加していない（NFR-018）。

## 形式上の残課題（formal follow-up）

1. 派生preset IDと値を `rule_sets` に実在させる正式なデータ配置migration。
   現状は `games.applied_rules` 内だけの派生IDで、段階A resolverの出所証明
   （`resolve_stage_a_rule` が返す `ruleSetId`）の範囲外である。
2. FR-014 の適用優先「試合単位の上書き > 大会名の規則 > 試合区分のデフォルト」の
   段階B実装。今回は既定規則への部分上書きであり、大会割当・規則管理UI・
   タイブレーク開始回の再設定は未実装。
3. 7回選択時に既定タイブレークが到達不能なら外す動作は暫定である。7回制の
   タイブレーク開始回（例: 8回）を要件として確定する場合は、要件・契約の
   正式ゲートが必要。
4. 延長上限はMVPの閉じた3値（7・9・12）だけを公開する。連盟差の任意値や
   「上限なし」は今回の画面選択に含めない。

## 検証

- backend: 作成serviceが選択後の6-keyを1回だけ保存し、開始経路の
  `_saved_start_rule_wire` が同じ7回・9回を読むことを単体で確認する。
- frontend: 7回・7回/9回/12回の終了条件核、作成画面の `rule_choice`、
  詳細再読込が同じ `applied_rules` を返すこと、開始画面が同じ規定回・延長を
  表示することをVitestで確認する。
- 実ブラウザの create→start→record→end→reload E2E は本トラックでは未実行。
