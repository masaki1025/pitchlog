# 詳細設計: 凍結資産の更新経路と digest 連鎖の短縮

**本書は設計の中身を持つ。** 調査の事実と典拠は [research.md](research.md) が正で、
本書は内容を複製しない(設計書 7.1-1)。**契約(射程・ステップ表・DoD)は
[plan.md](plan.md) が持つ。**

**計画レビュー 6 周で収束した**(`P1` 7 / 6 / 6 / 6 / 3 / **0**。6 周目 `可決 P0 0 / P1 0 / P2 2`)。
**1 周目で ① 宣言の置き場 ② 承認の機械的検証 ③ 上げ忘れの検出 を作り直し、**
**2 周目で「この設計が機械的に保証しないこと」を明示した**(3-4 の表)。
**全周の誤りを全件 8 節に残す。**

## 1. 解くべきこと — 3 つの層

| 層 | 現状 | 望む状態 |
| --- | --- | --- |
| **規範** | **正本に条文が 1 つも無い**。凍結の規律は資産と検査器の中だけの宣言 | **ハーネス設計書に「凍結基準の更新経路」の条文がある** |
| **機構** | **コミット SHA を検査器へ直書き**(`check_authz_catalog.py:107`)。更新は**検査器の編集** | **検査器は SHA を持たない**。基準は**追記のみの台帳**から読む |
| **連鎖** | **母集合 → 派生 3 資産が blob digest を 6 値**持つ(**資産全体を指す digest 辺は `contracts/` 全体で 21 本** — 実測) | **版参照 3 値**へ。**辺は 21 → 16 本**(派生 −6 / 台帳 +1)。**手で計算する digest が 6 → 1** |

**3 層は独立に失敗しうる。**

## 2. 規範 — ハーネス設計書へ何を書くか

### 2-1. 置き場と版

**7 章の末尾へ `7.7 凍結基準の更新経路` を新設する。** **版は `v1.14 → v1.15`**。
**合否条件を新設するので 7.6-3 後段(版繰り上げ + 7.3 の確定ゲート)を通す**
(先例: ハーネス設計書 `:720` の v1.14・裁定 `Q-1`)。

### 2-2. 条文の骨子

1. **凍結基準の外出し**: ある資産集合の不変性を検査で強制するとき、
   **その基準(コミット・版・digest)は機械可読な宣言として資産側へ置く**。
   **検査器のソースへ基準の値を直書きしない。**
2. **更新経路の必置**: **凍結を謳う検査は、正当な更新経路をちょうど 1 本、
   宣言の中に持たなければならない。** 経路を持たない凍結は置けない。
3. **追記のみ**: **基準の履歴は追記のみとする。** 既存の記録を書き換える変更を検査は受理しない。
4. **更新の記録**: 基準を動かすとき、**動かした事実・理由・承認者・承認日・直前の基準**を
   新しい記録として追記する。**直前の基準が履歴の末尾と一致しない追記を受理しない。**
5. **fail-closed**: 基準の妥当性を確かめられないとき(参照先が解決できない等)、
   **検査は緑にしてはならない。**
6. **本節が定めるのは 1〜5 まで**であり、**何を凍結するか・どの粒度で比べるかは
   各資産の宣言と実装が定める**(`data-model.md:244` と同型の委任)。

**3 と 4 が `P1-2` の反映**である。**追記のみ + 直前基準の連鎖**によって、
**「記録を残さずに基準を動かす」経路と「既存の記録を書き換えて誤魔化す」経路を塞ぐ。**

**「承認そのものの真正性」は塞がない**(**3 周目 `P1-5`** — 初版・2 周目とも
「使い回す経路を機械で塞ぐ」と書いていたが、**3-4 の表と矛盾していた**。
**承認欄をコピーした新規追記は通る**)。

**5 は本タスクで実際に踏んだ欠陥**(`check_authz_catalog.py:4798` の fail-open)から来ている。

### 2-3. 適用範囲の明示(`P1-3` の反映)

**リポジトリに現存する凍結基準の直書きは 4 つ**(**2 周目 `P1-6` で 1 件の見落としが判明**。実測):

### 2-4. allow-list 走査の仕様(**3 周目 `P1-3` の反映** — 2 周目は方式名しか書いていなかった)

**「凍結基準かどうか」を字面から機械判定することはできない**(40 桁 OID には fixture・ダミー・
別領域の基準が混ざる)。**そこで allow-list 方式を採る。** **仕様を確定させる**:

| 項目 | 定め |
| --- | --- |
| **走査対象** | **`scripts/**/*.py`・`tests/**/*.py`・`backend/**/*.py`** の**ソース本文**を `(?<![0-9a-f])[0-9a-f]{40}(?![0-9a-f])` で走査する。**AST の文字列リテラル完全一致ではない**(**4 周目 `P1-5`** — 完全一致だと **10 出現**しか見えず、**より長い文字列に埋め込まれた 4 出現**〔`test_verify_nfr021_evidence.py:675-678`〕を見落とす。**埋め込みを見逃さない側が fail-closed**) |
| **識別単位** | **`(リポジトリ相対パス, 値)` の組**。**値単位ではない** — **値単位だと既存の値を別ファイルへ足しても通る**(3 周目 `P1-3`) |
| **allow-list の置き場** | **`scripts/frozen-baseline-scan-allowlist.json`**。**台帳とは別ファイル**(台帳は「凍結基準」、本表は「凍結基準ではないことの宣言」— 別のもの) |
| **各件の内容** | `path` / `value` / `reason`(**なぜ凍結基準ではないか**)/ **`pending_removal`(真偽)** |
| **`pending_removal`** | **`true` は、台帳が base に存在しないときにのみ許される**(= **移行 PR に限る**。`F-7` と同じ条件)。**それ以外の PR に `true` が 1 件でもあれば red**(**5 周目 `P1-2`** — 4 周目は「ステップ 7 の合格条件 = 0 件」としたが**本 PR 限りの確認**であり、**後続 PR で `true` を足して残し続けても CI を通せた**)。**ステップ 5 で走査を有効にした時点では `56c281c…` の 3 出現がまだ残る**(除去はステップ 7)ための一時枠であり、**機械が期限を持つ** |
| **判定** | **走査で見つかった組が allow-list に無ければ red**(**未登録の出現**)。**allow-list にあって走査で見つからない組があっても red**(**古くなった宣言** — `N12` が固定する)|

**実測(反映時点・部分一致方式)**: **出現 14 件 / 相異なる値 6 件。**
**本タスク完了後、`56c281c…` と `0cf994f4…` の 4 出現は消える**ので、**残るのは
`test_verify_nfr021_evidence.py` と `test_nfr021_append_only.py` のダミー値 10 出現**である。
**AST 完全一致方式だと 10 → 6** になる — **どちらの数を DoD に置くかは方式で決まる。部分一致を採る。**

**「母集団を人が列挙する検査」ではあるが、台帳が記録している失敗型とは向きが違う** —
**あの型は「射程が動くと黙って古くなる」**もので、**本方式は両方向に fail-closed である**
(未登録の出現も、消えた登録も red)。**古くなる方向には倒れない。**

**`contracts/authz/function-bodies/manifest.json` の `source_commit` は射程外**
(関数本体スナップショットの基準で、oracle 封印とは別の資産群)。**申し送りにする。**

## 3. 機構 — 追記のみの基準台帳

### 3-1. 置き場(`P1-1` の反映)

**`contracts/authz/frozen-baselines.json` を新設する。**

**初版では `oracle-seal.lock.json` の中へ置こうとしたが、これは誤りだった。**
**seal 自身が backend の意味本文比較の対象**であり(`_oracle_seal_meaning_body`)、
**キーを 1 つ足すだけで `verify_frozen_oracle_unchanged` が落ちる**。
**基準を、その基準で検査される資産の中に置くのは自己言及である。**

**要件は「連鎖の外」ではなく「連鎖の入口を持たない」である**(**4 周目 `P1-6` の反映**)。

**初版から 3 周目まで「誰の digest も持たず、誰からも digest で参照されない」と書いていたが、
これは 4-3 の `corpus_versions[].canonical_sha256` と正面から矛盾していた。**
**3 周目には「台帳側で辺が 1 本増える」と自分で数えながら、この文を直していない。**

**正しい要件は片方向である**:

| 向き | 可否 | 理由 |
| --- | --- | --- |
| **台帳 → 他資産**(台帳が他資産の digest を持つ) | **可**(**anchor に必要**) | **不動の側が可動の側を指すのが anchor である。** 逆向きにすると anchor にならない |
| **他資産 → 台帳**(誰かが台帳の digest を持つ) | **不可** | **台帳が seal の入力になると、基準を動かすたびに再封印が要り、鶏と卵になる**。**`input_assets`・`sealed_assets` に入れない**のはこのため |

**初版の `oracle-seal.lock.json` 案が誤りだったのは「連鎖の中にある」からではなく、
「台帳が、その台帳で検査される資産の一部になる」から**である。
**`frozen-baselines.json` は oracle 意味本文比較や digest 封印の入力にならないので、
他資産の digest を持ってよい**(**5 周目 `P2`** — 「誰にも検査されない」は誤り。**`F-2`〜`F-4` が検査する**)。

### 3-3. 系列の型と述語の適用範囲(**4 周目 `P1-1` の反映**)

**4 系列は同じ型ではない。** **3 周目まで「4 系列に `F-1`〜`F-7`」と書いていたが、
`corpus_versions` の記録は `commit` を持たない**ので、`F-1`・`F-5`・`F-6`・`F-7` は適用できない。

| 系列 | 記録の型 | 適用される述語 |
| --- | --- | --- |
| `oracle_input` / `oracle_meaning` / `core_areas_guard` | **commit 型** — `commit` / `supersedes` / 承認 3 項目 | **`F-1`〜`F-7` 全部** |
| `corpus_versions` | **version 型** — `version` / `canonical_sha256` / **`supersedes`(直前の `version`。先頭は `null`)** / 承認 3 項目 | **共通述語 `F-2`・`F-3`・`F-4`** + **`G-1`〜`G-5`**。**`F-1`・`F-5`〜`F-7` は適用しない**(commit を持たないため)|

**共通述語**(全系列に掛かる): **`F-2`(`supersedes` の連鎖)・`F-3`(承認 3 項目が非空)・
`F-4`(追記のみ)** の 3 つ。

**`supersedes` は全系列が持つ。** **`F-2` の比較対象は系列の型による** —
**commit 型は直前の `commit`、version 型は直前の `version`。**

**確定ゲート 5 周目 `P1-1` は「仕様が 3 通りに割れている」という指摘だった**
(3-3 は「直前の `version`」/ `F-2` の本文は「直前の `commit`」/ 4-3 の構造例には無い)。
**そのとき私は「落とす」方向で割れを解消したが、これは誤りだった**
(**PR #63 の敵対レビュー `P0`**)— **条文 7.7-4 は「直前の基準の識別値」を
系列の型で場合分けせずに要求している。** **落とすのではなく 1 つに決めるべきだった。**
**割れを解消する方向が逆だった。**

**`F-8` は系列に掛からない**(**自己点検** — `F-8` は **CI の結線に掛かる述語**であり、
台帳の記録を見ない。**上表の「`F-1`〜`F-7` 全部」に `F-8` は含まれない**)。

**空の系列は置かない。** **系列は最低 1 記録を持つ**(記録の無い系列があると `[-1]` が未定義)。
**ステップ 4 が commit 型 3 系列 + 共通述語 + `F-1`〜`F-7` を作り、
ステップ 8 が `corpus_versions` 系列 + `G-1`〜`G-5` を足す**(**両ステップの分担を確定させた**)。

### 3-4. 検査(`P1-2` の反映)

| # | 述語 | 何を防ぐか |
| --- | --- | --- |
| F-1 | 各系列の**末尾の `commit`** が、対応する検査の基準として使われる | 基準の一元化 |
| F-2 | **全系列で** **`記録[i].supersedes == 記録[i-1]` の識別値**、先頭は `null`。**識別値は commit 型が `commit`、version 型が `version`** | 履歴の連鎖 |
| F-3 | **`approved_by` / `approved_at` / `reason` が空でない**。`approved_at` は ISO 日付 | 空の記録 |
| F-4 | **追記のみ** — **PR の base に存在した記録が 1 件も書き換わっていない・削除されていない** | **既存記録の改ざん**(**使い回しは防がない** — 3 周目 `P1-5`) |
| F-5 | **`commit` が実在し、かつ現在の `HEAD` から到達可能**。**実在の確認は `git cat-file -e`、到達可能性の確認は `git merge-base --is-ancestor <commit> HEAD`。どちらかが失敗したら red** | **fail-open** / **dangling commit を基準にすること** |
| F-6 | 同一系列に**同じ `commit` が 2 度現れない** | 巻き戻し |

**`.git` が無い実行経路を fail-open にしない**(**PR #63 の敵対レビュー `P0`**):
**`validate_oracle_seal` は `.git` が無いと履歴照合を丸ごと省略し、正例テストがその緑を固定している。**
**正当な履歴なし用途を維持するなら、凍結検査とは別の契約に分ける** —
**「履歴照合を省略した」ことを出力で明示し、省略した実行を凍結の保証の対象外と宣言する。**
**黙って通さない。**

**`F-5` は 2 つの確認を要する**(**PR #63 の敵対レビュー `P0`**): **`git cat-file -e` は
オブジェクトの実在しか見ない。** **到達不能な dangling commit を受理してしまう** —
**実測**: `72802003ba0c3863f374325e90be2bc8490131aa` は `cat-file -e` を通るが、
`merge-base --is-ancestor ... HEAD` は exit 1、**含む ref は 0 件**だった。
**dangling commit は gc で消えるので、基準として使うと後から黙って壊れる。**
**初版は「実在し、到達可能(`git cat-file -e`)」と、要求と誤った機構を同じセルに書いていた。**
**実装は仕様に忠実だった。仕様が嘘をついていた。**

**`F-4` の先例がある** — `scripts/check_nfr021_append_only.py` が
**PR の base と HEAD を比べて既存レコードの不変を検査**している(同 `:397` `validate_existing_record_history`)。
**同じ型を使う。**

#### この検査が保証すること・しないこと(**2 周目 `P1-2`・`P1-3` の反映**)

**初版は「承認記録の使い回しを機械で塞ぐ」と書いたが、これは過大主張だった。**

| 保証する | 保証しない |
| --- | --- |
| **基準を動かすには新しい記録の追記が要る**(**全系列で `F-2`・`F-3`・`F-4`**。commit 型はさらに `F-1`・`F-5`〜`F-7`、version 型はさらに `G-1`〜`G-5`) | **`approved_by` / `approved_at` / `reason` を前回からコピーした追記は通る**。**非空しか見ていない** |
| **既存記録の書き換えが PR の差分で red になる**(`F-4`) | **ブランチ保護が無いので直接 push で base ごと書き換えられる**。以後の PR は改ざん済みの base を正とする |
| **記録なしに基準だけ動かせない** | **同一 base の複数 PR に分ければ個別には green になる** |
| **改ざんが差分として見える** | **HEAD 側で検査器自身を弱める経路**(既知の循環参照) |

**典拠**: `docs/development/github-setup.md:35-39` —
「**`NFR-019` の『全グリーンでないとマージ不可』のリモート強制は未達**」
「**機械的強制ではなく、所有者が遵守する管理手続**である。…**人間の端末・別 clone・
GitHub UI/API からの操作は遮断しない(過信しない)**」。

**したがって本設計が達成するのは次の 3 つに限られる**:

1. **凍結基準がソースコードからデータへ出る** → **要件書を改訂するたびに検査器を編集する運用が終わる**
   (**これが TSK-386 の目的そのもの**)
2. **基準を動かした痕跡が、理由つきで残る**(自己申告だが**追記の形で残る**)
3. **既存記録の書き換えが差分として見える**

**「実際に人間が承認したか」も「悪意ある改ざんの阻止」も達成しない。**

### 3-4-2. 委任 3 指定の宣言(**PR #63 の敵対レビュー `P0` の反映**)

**7.7-6 は委任先 3 つを宣言が持ち、実装が宣言から導出することを要求している。**

| 現状(違反) | 変更後 |
| --- | --- |

### 3-4-2-B. 宣言を「使わせる」ための作り直し(**PR #63 敵対レビュー 2 周目 `P0` — 方針の見直し**)

**3-4-2 の初版は失敗した。** **宣言を足しただけで、実装がそれを使う形になっていなかった。**

**実測した 2 つの失敗**:

| 失敗 | 実測 |
| --- | --- |
| **宣言が守られていない** | **`corpus_versions.frozen_targets` から 1 資産を外すと全検査 exit 0** |
| **宣言が使われていない** | **`identity` / `granularity` をでたらめな文字列にしても全検査 exit 0** |

**`frozen-declaration-used=` は「使った証跡」ではなく「読んだ宣言のエコー」だった。**
**`identity` と `granularity` は、実装の挙動を*説明するラベル*として設計してしまった。**
**条文が要求しているのは、実装の挙動を*選択する入力*である。**

**部分修正を重ねても同じ形の `P0` が出る**と判断し、**方針を作り直す**(PO 判断 2026-09-16)。

#### R-1 宣言が挙動を選択する(dispatch)

**`(identity, granularity)` の組が、比較戦略を選ぶ鍵になる。**

- **実装は戦略のレジストリを持ち、宣言が名指しした戦略へ dispatch する**
- **宣言が名指しした組が登録に無ければ red**(fail-closed)
- **登録にあってどの宣言からも名指しされない戦略があれば red**(死んだ戦略を残さない)

**これで `identity` を変えると挙動が変わる。** **変えて何も起きないなら、それは使われていない。**

#### R-2 出力は「実行の記録」であって「宣言の写し」ではない

**比較戦略が実行中に、自分が実際に比較した対象と使った鍵を記録する。**
**出力はその記録である。** **宣言から組み立て直さない。**

**テストは「実行の記録」と「宣言」の完全一致を見る。**
**宣言をコピーして出力する実装では、記録が空になるので落ちる。**

#### R-3 宣言の変更は基準の追記を伴う

**`declarations` が base と HEAD で違うなら、当該系列に新しい記録が追記されていなければ red。**

**根拠**: **凍結対象を変えることは、基準が何に適用されるかを変えることである。**
**それは基準を動かすのと同じ重さを持つ**(7.7-2 の受理条件・7.7-4 の記録)。
**「追記のみ」を `declarations` へそのまま課すのではなく、「変更には基準の追記を伴う」**とする
(宣言は履歴ではなく現在の状態なので、追記のみは形が合わない)。

#### R-4 宣言の凍結対象を独立な出どころと突合する(**最重要**)

**`frozen_targets` を宣言だけで持つと、狭めても誰も気づかない。**
**宣言とは別の場所から同じ集合を導出し、完全一致を要求する。**

**実測で 4 系列すべてに独立な出どころがあることを確認した**:

| 系列 | 独立な出どころ | 実測 |
| --- | --- | --- |
| `oracle_input` | **seal の `input_assets` のパス集合** | **8 = 8・完全一致** |
| `oracle_meaning` | **seal の `sealed_assets` のパス集合 + seal 自身** | **6 + 1 = 7・完全一致** |
| `corpus_versions` | **母集合 ∪ {`input_manifest` が母集合を名指しする資産}** | **1 + 3 = 4・完全一致** |
| `core_areas_guard` | **`core_guard` が現に読むパス** | 1 件 |

**これで「宣言を狭める」と独立な出どころと食い違って red になる。**
**両方を同時に狭めるには、seal や派生資産の構造自体を変える必要があり、それは差分として大きく出る。**

#### R-5 `.git` 無しは別契約にする

**警告を出して続行し正常値を返すのは fail-open のままである。**

- **履歴照合を省略した実行は、成功と区別できる状態を返す**
- **呼び出し側は「省略」を「検証済み」として扱わない**
- **既定では非ゼロ終了**。**履歴なしを許す用途は明示のフラグで宣言する**
- **`.git` 無しの正例テストは「省略された」ことを検査する**(成功を固定しない)

#### R-6 固定集合をテストへ移さない

**`oracle_meaning` の確定集合は実装から消えたが、リポジトリの正例テストへ残っている。**
**テストも基準から導出する。** **固定値の置き場を変えただけでは、更新経路は開通しない。**

### 3-4-3. `oracle_meaning` の更新経路の開通(**PR #63 の敵対レビュー `P1` の反映**)

**`STEP2_CHANGED_CANONICAL_ASSET_PATHS` が固定の 2 件で、正当な更新経路を塞いでいる。**

**実測**: 台帳の `oracle_meaning` 末尾を現在へ進めると、**意味本文が変わった資産の集合は空になる**が、
**検査は旧来の 2 資産をそのまま要求する** → `意味本文が変わった資産がステップ2の確定集合と不一致: ()`。

**これは 7.7-2 違反**である。**基準を動かす正当な経路が、実装の固定値で閉塞している。**
**ステップ 11 で直した digest 辺の固定期待値と同じ型**であり、**同じ PR 内で 2 回踏んだ。**

**直し方**: **「確定集合」を固定値で持たず、`基準 → HEAD` の差分から導出する。**
**基準を進めれば集合は空になり、空であることが正しい状態になる。**

**固定値で持ってよいのは「宣言が定める凍結対象」だけ**(3-4-2)であり、
**「その基準時点で変わっていた資産の集合」は基準に従属する派生量**である。
**派生量を固定値で持つと、基準を動かした瞬間に嘘になる。**

## 4. 連鎖 — `H-85` 対応案②

### 4-1. 何を「段」と数えるか(`P1-5` の反映)

**初版は「4 段 → 3 段」と書いたが、これは測れない主張だった。** 依存の段は減らない。
**測れる形へ言い直す。**

**定義**: **digest 辺** = 資産 X が**資産 Y の全体の内容 digest**を**自分の中に保持している**関係。
**「全体の」が要**である — **`contracts/` の digest らしきキーを全部数えると 5241 件**あり(実測)、
**その大半は資産内の 1 項目ごとの digest**(`claims[i].*_digest` 等)で、**資産間の連鎖ではない**。
**±5 の変化を 5241 の中で示しても何も証明できない。**

**測り方**: `contracts/**/*.json` を走査し、**ルート直下の
`input_manifest` / `input_assets` / `sealed_assets` / `oracle_context` / **`baselines`** の配下**にある
`digest|sha256|checksum` キーで値が 40 or 64 桁 hex のものを全数列挙する。

**`baselines` を含めるのは、新設する台帳の `corpus_versions[].canonical_sha256` を
数え落とさないため**である(**自己点検で発見** — 含めないと結果は `21 → 15` になり、
**「台帳側で 1 本増える」を計上しないまま「純減 5 本」と主張する**ことになる)。
**定義変更は既存の実測値 21 を動かさない**(現行の `contracts/` に ルート `baselines` を持つ資産は無い — 実測)。

**実測(反映時点)= 21 本**:

| 資産 | 本数 |
| --- | --- |
| `oracle-seal.lock.json` `input_assets[0..7].git_blob_digest` | 8 |
| `oracle-seal.lock.json` `sealed_assets[0..5].canonical_sha256` | 6 |
| **派生 3 資産 `input_manifest.requirement_claims_{,lock_}blob_digest`** | **6** |
| `requirement-claims.json` `input_manifest.source_blob_digest` | 1 |

### 4-2. 変える辺

| 現在 | 変更後 |
| --- | --- |
| 派生 3 資産が `requirement_claims_blob_digest` と `requirement_claims_lock_blob_digest` を各自持つ = **6 辺** | 派生 3 資産が **`corpus_version` を 1 つ持つ = 0 辺**(版参照は digest 辺ではない) |

**ただし台帳が `corpus_versions[].canonical_sha256` を持つので、辺が 1 本増える**
(**2 周目 `P1-1`** — 初版は「6 本減」と書いたが、**同じ文書の中で自己矛盾していた**)。

**期待値**: **21 → 16 本。** 派生側で 6 本減り、台帳側で 1 本増える。**純減 5 本。**
**手で計算する digest は 6 → 1**(台帳の `canonical_sha256` が残る)。
**これが DoD の測定対象である**(「段数」でも「5241 のうちの 5」でもない)。

**増える 1 本を受け入れる理由**: **`G-2` の上げ忘れ検出に必要**である。
**digest を持たない版番号だけでは、内容が変わったことを検出できない。**

### 4-3. 上げ忘れの検出(`P1-4` の反映)

**初版は「母集合が版と canonical digest を対で持つ」としたが、これでは防げない。**
**同じ可変資産に両方があり、両方を再封印すれば自己整合する。**

**台帳を使う。** `frozen-baselines.json` へ 4 系列目を足す:

```
"corpus_versions": [
  { "version": 1, "canonical_sha256": "<母集合の digest>", "supersedes": null,
    "approved_by": …, "approved_at": …, "reason": … },
  …
]
```

**検査**:

| # | 述語 |
| --- | --- |
| G-1 | 母集合の `corpus_version` == 台帳の `corpus_versions[-1].version` |
| G-2 | 母集合の現在の canonical digest == 台帳の `corpus_versions[-1].canonical_sha256` |
| G-3 | **追記のみ**(`F-4` と同じ機構) |
| G-4 | `version` は 1 から連番・重複なし |
| **G-5** | **派生 3 資産の `corpus_version` が、母集合の `corpus_version` と一致する**(**2 周目 `P1-5`** — これが無いと**母集合だけ版を上げて派生を放置**しても全述語が通る) |

**上げ忘れは `G-2` で落ちる**: 母集合を変えると digest が変わり、**台帳の末尾と一致しなくなる**。
**台帳を書き換えて合わせようとすると `G-3` で落ちる**(追記のみ)。
**追記すれば `G-1` が版の不一致で落ちる**ので、**母集合の版も上げるしかない。**

**独立した anchor は「追記のみ」が与える。** これが初版に欠けていた。

**`N8`(派生の追随漏れ)は `G-5` が捕まえる**(初版は「`G-1` 経由」と書いたが**実装不能だった**)。
