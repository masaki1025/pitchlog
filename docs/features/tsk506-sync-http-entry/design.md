# TSK-506 同期 HTTP 入口: 接続案（未承認）

## 境界と先行範囲

E-1/E-2 は認証済みの `TenantContext` と JSON 本文を `SyncRequest.from_payload` へ渡し、S-1 をゲーム参照の前に確定する。入口は [U-S1 公開関数](../../../backend/src/pitchlog/sync/apply.py) に**登録済みの本物のポート**を注入し、その `AckResult` / `ChangeResult` / B6・B7 を [wire 設計](../sync-wire-schema/design.md) 4 節へ写す。内部 transaction を外側で再実装せず、HTTP が D5 の採番・台帳書込・状態投影を直に行わない。

新規 `frontend/src/lib/sync/wireCodec.ts`・`httpTransport.ts` と `apiRequest` の接続は core paths の宣言・登録後のステップ 3 で行う。X-5 の形式検査と X-6 の構造一致は新 codec が持ち、既存受け取り側には足さない。E-1/E-2 を稼働入口として開くステップは、U-R1 の V12/D4・RG1 本物ポート、U-X1/U-G2 の検証/投影ポート、登録・呼出境界、E-1 の経路選択とルート登録を受領してから完了させる。実 DB の RLS/ACL 越境証跡は後続の検証・PR ゲートで取得する。未接続のまま `200` を返す仮実装や別の保存経路は認めない。

| --- | --- | --- |
| U-S1 / TSK-391 後続の維持担当 | 正本 8-1 により 1球は P2。E-1 の P1/P2 混在バッチを単一 ACK・D1 順・部分成功のまま公開関数へ渡す方法、P4 の判定時点、P5 を内部拒否として扱う境界を**型/関数名で受理**する。`registrations`/`targets` の生成元、同じ D5 の再掲・異内容拒否も確認。U-S1 全体完了ではなくこの公開境界だけを確認 | 実呼出の型検査と同じ適用核を経る隔離 DB 試験。HTTP で要求を経路別に分割して別 ACK にしない |
| U-R1 / TSK-392 と U-G1 / TSK-395 | V12/D4/復旧世代の発行・格納・失効と `RecordingRightsPort` 登録、③-a/⑧ の RG1、試合開始時の初期記録権、試合行→記録権世代行の lock 順 | 進行中 1球の認可、失効/越境/復元調整中の拒否、ACK 消失再送と衝突試験。U-R1 所有ファイルは編集しない |

## 1球の受入経路

1. U-G1 の開始済み試合と U-R1 の現記録権を、使い捨ての RLS 適用済み DB に作る。実際の HTTP 認証 Cookie・CSRF を通す。
2. U-F8 後続が採番済み D1 と固定 D5 を端末キューへ永続追記して E-1 へ送る。まず TSK-506 の直叩き試験でも同じ wire を送る。
3. U-S1 適用核が既存の台帳・slot・原本と投影を同じイベント transaction で確定し ACK を返す。接続が欠ける時は試験を未達と明示する。
4. 同じ D5/同じ内容を再送し、台帳/原本が 1 件のままで既存結果が再掲される。別内容の同 D5 は拒否し、ACK 消失・401・通信断で端末キューを失わない。
5. 別の HTTP 読取経路（所有と契約を受理してから）で再読込し、DB 原本と同じ球を画面に表示する。**DB への SELECT だけでは「画面で再読込」を完了と呼ばない**。読取 API が未整備なら TSK-506 の API/DB 証跡と、画面接続の残課題を分けて記録する。API 越境の正式ゲートは、さらに実行間で存続する検証専用クラスタで別途判定する。

他テナント試合と自テナント不存在は E-1/E-2 それぞれで同一 404（status/header/body）。S-1 はそれらの試合 ID に依存しない 422。RG1 が閉じている時は D5 未消費で B7/B10、書込直前の閉鎖で全取消。V12 を本文や例外ログへ記録しない。E-2 は P3 の 1 件要求を独立の 409/200 結果として扱う。ステータス解釈不能や認証切替は元のキュー・D5 を保持する。

ステップ 4 に必要なのは**受理済みの callable 契約**であり、ステップ 5 で初めて得る DB 実行結果ではない。ただし本物のポートが未登録ならステップ 4 を完了扱いにせず、仮ポートで入口を開けない。U-X1 の計算核が凍結中なら `play_input` の投影を誰がどの承認済み単位で供給するかを PO と担当へ照会し、TSK-506 にコピー実装を作らない。

## 検証専用クラスタの提供条件（候補、環境未作成）

- 用途は data-model 12-4 の E-1/E-2 直叩き判定だけ。機能・故障系の使い捨て DB と分け、**独立したローカル PostgreSQL クラスタ**を第一候補にする。環境管理者が既存マシンの資源と別クラスタ実体を確認するまで作成しない。共有・本番 DB は対象にしない。
- 期間は初回 preflight から**少なくとも異なる 2 実行を経て最終 PR-head の判定・人間確認が終わるまで**同じクラスタを保持する。DB の作り直しは承認済み [運用手順](../../ops/product-rls-real-schema.md) に従ってよいが、クラスタ自体を試験ごとに捨てない。終了後の撤去は管理者が別に判断する。
- 権限は、環境管理者だけが対象確認・DB/ロールの撤去作成・製品 authz DDL の管理操作を持つ。migration は既存の専用 owner 経路、HTTP 試験は通常製品ロールで行い、製品利用ロールに DDL・越境権限を与えない。運用手順の authz DDL に必要な管理権限と、製品 migration/利用時の権限を混同しない。接続情報は環境変数だけに置き、リポジトリ・PR に載せない。
- 実行ごとに対象要約・クラスタ/DB の同一性、作り直し世代、migration/DDL の版、開始/終了、同対象の全実行の出典と非重複比較を残す。運用手順で必要な 0 接続確認と失敗時停止を守る。
- **費用**: 既存ローカル計算資源で独立クラスタを供給できれば新規クラウド請求は 0 円。CPU・メモリ・ディスク・電力の追加消費と管理工数は未測定で、管理者が確保量を提示する。既存資源が使えず有料環境を要する場合は、提供者・月額/従量上限・保持期間の見積りを PO に別途提示し、承認前に作成しない。
