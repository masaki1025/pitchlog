# 実装計画案: TSK-506 同期の HTTP 入口

## 1. 背景・目的

[正式カード](https://app.notion.com/p/3f493b75e68781629ed8eec9c8338dcd)の E-1/E-2 と [FR-012](../../requirements/requirements-pitchlog-2026-07-22.md#FR-012) を実現する。MVP の利用経路は「記録画面から 1 球送信→実 DB へ保存→再読込」である。現基線と不足の根拠は [research.md](research.md)、担当別の接続案は [design.md](design.md)。計画承認と U-R1 の guard 編集所有解除を受け、最新 `develop` を基線にステップ 1〜3 を実装した。ステップ 4 の接続契約受理は別条件として維持する。

## 2. スコープ

### やること

- E-1/E-2 の HTTP 入口、S-1 と共通認証、U-S1 適用核への接続、wire 結果写像。別の適用核・直接 SQL の保存経路は作らない。
- TSK-331 の X-1〜X-6 に沿うクライアント codec/通信層。既存 `apiRequest`、端末キュー、同一 D5 の再送を利用する。
- EP-1〜EP-11、実 HTTP/隔離 DB の越境・再送・失効・原子性試験。N-1/N-2/N-4 は性能測定で値または導入見送りを判断し、必要な実装と再検証まで行う。N-15 の route_id/越境ゲート、N-18 の U-S1 型↔wire キー対応も同じ入口 PR に記録する。
- 391・U-R1・U-F8 と読取経路の引渡し。実画面までの残部を TSK-506 の API 完了と混同しない。

### やらないこと

- U-S1 適用核、共有実行器 A、C1、U-R1、U-F8 画面の所有ファイルの並行編集。未登録ポート・仮 V12・仮の保存経路。
- 要件/正本の意味変更、未承認の認可緩和、既存 DB への migration 適用、正本凍結資産の独断更新。
- この計画コミットでの製品実装、push、PR 作成、マージ。

## 4. 実装方針

同期・記録権・テナント分離の入口なので **コア領域**。既存の `require_tenant_access`、`SyncRequest.from_payload`、`apply_sync_request`、登録済みポートと [wire 設計](../sync-wire-schema/design.md) 4 節を再利用する。HTTP は適用核の transaction を包み直さない。先行できる codec と、真のポート/認可が要る稼働入口を分ける。EP-1〜EP-11 は入口を開く**同一 PR**で満たす。

**開始条件**: 全ステップに人間の計画承認が必要。ステップ 1・2 はコア paths/共有認可資産の編集所有と順序の受理が必要。登録後のステップ 3 は frontend 所有境界に重複が無ければ実ポート完成前に先行できる。ステップ 4 の**着手前**には TSK-391 の公開境界（**毎球入力=P2、P1/P2 混在バッチを単一 ACK・D1 順・部分成功で処理する型/関数と P4/P5 内部分岐**）、U-R1 の V12/D4/RG1、U-X1/U-G2 の `play_input` 検証・投影について、担当・公開型/関数・失敗境界・注入元を受理する。実ポートの登録と本物の DB 経路はステップ 4 の**完了条件**であって、ステップ 3 の着手条件ではない。実 HTTP/DB 試験、専用クラスタでの越境・非重複証跡、性能値、EP-11 の PR 記録はステップ 5/PR の**完了証跡**であり、実装前には要求しない。現行 `SyncRequest.path` の単一値を HTTP が独自に分割して埋めない。各ステップは別指示で 1 つずつ実装・検証・コミットする。

## 8. 新停止結果の限定計画追補（2026-10-19・承認済み）

**対象は未着手のステップ 4・5 とその DoD・試験だけ**とし、完了済みステップ 1〜3、5 ステップの番号、既存の承認・レビュー履歴を維持する。2026-10-19 の PO4 方針採用と本節の計画承認は別の判断であり、本節の承認を正本確定、結果 ID・wire 形・公開理由の承認へ流用しない。未確定の接続契約を要する製品実装は、各担当の受理まで開始しない。

ステップ 4 では、U-S1 の 7.3 正本と TSK-331 の wire 設計で確定した**専用停止結果**だけを、HTTP status 単独に頼らない型付き応答として扱う。対象理由は、原本 0 行（RLS 不可視を含む）、未使用 D5 が参照する不変の拒否原本の不整合、DB 読取・接続障害、明示的な DB 権限エラー、D-2c 前の墓標 `"8"` とする。既存 D5 の台帳・再掲結果破損は現行 B7 に残し、通常 5xx→B7/B10、W2→B3a/T9、DI2、S-1 の外形拒否を変更しない。U-S1 が提供する原wire入力と codec 版の専用指紋を受け、既存 DTO 経路・保存済み指紋の意味を HTTP で変えない。混在バッチを HTTP 側で分割しない。

端末側は新停止を ACK 成功・B3 内容拒否・送信済みへ写さず、同一 `(game,D4)` の要求と停止理由・再開条件を耐久保存して自動再送を止める。前方のサーバー確定は維持するが、端末では要求全体を未確認として保持し、後続は未処理とする。対象イベントの取引取消がサーバーで確定した場合だけ対象 D5 を未消費と判定し、**commit 結果不明なら取消・未消費を推定せず、自動再送と内容訂正を禁止して耐久的な結果照会まで停止する**。**送信前に対象要求の未解決送信印を耐久化し、停止応答の保存前にブラウザが失われても再起動時の自動送信を抑止する。** 照会時に結果が「まだ無い」だけでは通常 B7 と確定しない。旧 HTTP 要求が遅延中でも、同一 scope の適用取引と直列化したサーバー側の耐久的な試行遮断・結果照会によって旧試行の後着適用と新停止が起きないと証明できた場合だけ、通常 B7 の自動再送へ戻す。成立しなければ結果不明として保留する。試行識別子やwire変更が必要なら TSK-331 と U-S1 の正式ゲートへ出し、506単独で追加しない。この事前印・照会・遮断の所有と原子境界をキュー所有側・U-S1 の正式契約で受理するまで、通信層は実装しない。停止情報の保存失敗・応答受信直後のブラウザ喪失を、成功や安全な再送と扱わない。

明示再開は、サーバーが同一テナントの原本・権限・DB・D-2c 対応を確認した後に限り、保持した同じ D1・D5・内容・codec 版で行う。**確認と適用の間に前提が失われても、適用取引内の再確認で安全に拒否できる契約**を U-S1 から受け取る。前方確定分は DI2 再掲で端末が確認し、二重適用しない。内容訂正は、旧要求を端末に保全したまま送信対象から外し、同一 D1 スロットの新 D5・訂正内容へ不可分に置換する。ただし、**旧 D5 の未適用・取消を耐久的に確認し、遅延した旧要求が後から適用されないサーバー側の制御**が正本・実 Port・隔離 DB 試験で成立するまでは、訂正 API・UI を提供しない。commit 不明時の置換は禁止する。端末側の送信停止だけを旧要求の無効化証跡としない。

ステップ 4 の追加着手条件は、U-S1 の正本 7.3 確定、結果 ID・wire 形・非機密の公開理由とサーバー再開確認口の型・認可・再確認点の受理、キュー所有側と U-F8 の項目別受理、TSK-506 の本計画 6.1 レビュー・人間承認である。旧 D5 の安全な置換に必要なサーバー側制御が現行契約にない場合は、U-S1 主担当へ正式追補を提示し、その経路の実装を止める。既存の実 Port・共有 route/API 資産の受理条件も維持する。

ステップ 5 の追加合格条件は、Vitest・pytest・使い捨て隔離 DB・実 HTTP で、(1) 通常 B7 と新停止の非衝突、(2) 指紋の正規化・同一性と原本可視性/復旧に対する不変、(3) 取消確定と commit 不明の区別、(4) 前方確定・対象取消・後続未処理と DI2 再掲、(5) 再読込後も自動再送 0、(6) 再開確認直後の前提喪失による安全な拒否、(7) 旧要求の遅延到着と訂正の競合、(8) 停止応答の保存失敗・応答受信直後のブラウザ終了・再起動で自動送信 0、旧試行遅延中の結果照会ではB7確定不可、耐久的な旧試行遮断と結果確定後にだけ通常B7の自動再送へ復帰、(9) RLS 非開示、を実証すること。結果 ID・wire 形が未確定の試験は正式値の確定後に作成し、仮の成功値でゲートを通さない。実 HTTP/DB の証跡は着手前条件に置かず、ステップ 5 の完了条件とする。
