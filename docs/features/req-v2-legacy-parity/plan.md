## 1. 背景・目的

Notion タスク: [要件書 v2.0 改訂](https://app.notion.com/p/3bb93b75e687819485e5f7f2aa79fa64)

旧システム `shogo0303/Baseball_Scoring` が pitchlog の版固定アーカイブ時点(`ed6a20f`)から **30 コミット先行**していることが判明し(現在 `dd03160`・DB スキーマ 13 → 33 テーブル)、**PO 決定(2026-08-13)でこの追加分を踏襲する**ことになった。

踏襲対象のうち**最も重く、後付けが最も高い**のがテナント間データ共有である。認可モデルが「所有」から「所有 ∨ 付与」へ変わり、コア領域(テナント分離)に正面から触れる。本タスクはここに絞る。

**撤回のハードルは記録上低い**([research.md](research.md) §7): Won't の一次記録は「データ所有権制御の帰結」としての演繹で、**共有の是非を評価した記録がない**。撤回は「過去の評価を覆す」ではなく「保留していた検討を実施する」に該当する。

## 4. 実装方針

### 重さ分類 = コア領域(根拠)

CLAUDE.md が列挙するコア領域 5 つのうち**テナント分離**に正面から触れる。認可判定が単一の不変条件から「所有 ∨ 付与」という条件付きの規則へ変わり、越境テストの性質も「一切漏れない」から「認可行列どおりに通る」へ変わる。したがって計画レビューは `codex_run.py review adversarial`、PR は人間の逐行確認を適用する(設計書 6.3)。

**機構が発火しない点と代替統制**: `areas[].paths` が Phase 4 まで空のため CI の `core-guard` は本 PR で発火せず、`guard_paths` にも触れない。代替として**最新 HEAD の全差分を PO が逐行確認し、実施者名と対象 HEAD の SHA を PR 本文へ記録する**。

### 実装委任は行わない

正本ドキュメントの起草は Claude の役割(設計書 3 章)。Codex へは `review adversarial` のみ委任する。下表は `/implement` の実行対象ではなく、**Claude が自ら実施するコミット単位の計画**であり `feature_status.py` の進捗導出に使われる。

### ステップ設計の方針

- **PO 裁定は起草前に取得済み**。ステップ内の未決事項として残さない
- **依存順**: 概念を定義する FR(2・3)→ それを参照する認可モデル(4)→ 波及(5〜7)
- **Won't の削除と対応要件の新設は同一ステップ**。分離すると中間コミットが不完全な要件書になる
- **確定ゲートはステップ表に載せない**。`/finalize-doc` が実行し、周回は `確定ゲート周回` キーで追跡する
- **合格条件は design.md の該当節を参照する形で書く**。仕様を本書に複製しない(改訂 5 の構造変更)
