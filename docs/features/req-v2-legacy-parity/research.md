# 調査メモ: 旧システム Baseball_Scoring の現状と pitchlog 要件との差分

## 問い

Phase 4 着手前の確認として「旧リポジトリが変わっていないか」を確かめ、変わっていた場合に **pitchlog 要件書 v1.9 との機能差**と、**踏襲する場合の要件書への影響範囲**を特定する。あわせて `/investigate`(2026-08-13・4 本並列)で次を検証した — ① 自責点判定の規則準拠 ② 公式記録ワークフローと既存 FR の重複 ③ テナント分離 Won't の決定経緯 ④ 改善台帳の未確認 11 件。

## 結論(要約)

1. 旧リポ `shogo0303/Baseball_Scoring` の origin/develop は、pitchlog の版固定アーカイブ時点(`ed6a20f`・2026-07-24 取り込み)から **30 コミット先行**(現在 `dd03160`・2026-08-11)。DB スキーマは **13 → 33 テーブル**
2. ただし **`play_data`(88 列)の定義と `config.py` の 88 列契約は無変更**(blob SHA 一致)。**移行(FR-038)の中核契約は無傷**で、増えたのはすべて周辺
3. 旧の新機能の**大半は pitchlog 要件書が既に規定済み**。旧リポに pitchlog への言及が一切ないため、追随ではなく**同一課題への独立実装**
4. **改善台帳 27 項目のうち「完全解消」と判定できたものは 0 件**(§4)。pitchlog の再構築価値の中核(全件読み込み集計・2UI 併存・88 列の役割降格・PostgreSQL 一本化)は 4 点とも未解消。**旧が追いついたのは「機能」であって「構造」ではない**
5. **自責点は踏襲の前提が成立していない**(§5) — 旧の永続化 API はフロントから呼ばれておらず(`frontend/src` 全体で 0 件)、`ENGINE_VERSION = "manual-api/1"`、9.16(g)(h) のロジックは本番から未接続(呼び出し元はテストのみ)、ERA は非算出。**pitchlog 付録A-2 の既存規定のほうが旧実装より進んでいる**
6. **公式記録ワークフローは新規 FR が必要**(§6) — 15 要素中 12 要素が該当 FR なし。ただし**稼働しているのは読み取り専用のレビュー表示のみ**で、永続化・版管理・承認・指紋・陳腐化は本番未接続
7. **テナント分離 Won't の撤回ハードルは記録上低い**(§7) — 一次記録は「データ所有権制御の帰結」としての演繹で、**共有の是非を評価した記録がない**。撤回は「過去の評価を覆す」ではなく「保留していた検討を実施する」に該当。ただし改訂箇所は当初見積の 6 箇所より多く、**4 箇所が未捕捉だった**
8. 上記 5・6 を受けた PO 判断(2026-08-13)により、**自責点は Won't 維持**が確定。公式記録の判定の永続化・版管理・承認・指紋・陳腐化も踏襲対象外(本番未接続)。**ただし稼働している読み取り専用のレビュー表示の扱いは PO 裁定事項として未決**([design.md](design.md) §7 の v2.1)
9. テナント関連の改訂箇所は当初見積の 6 箇所から**大幅に増加**(計画レビュー 1〜2 周目で FR-033・FR-039・FR-017・6.1・6.2・6.4・NFR-003・NFR-005・2.1・R-9 等の漏れを指摘された)。加えて**改善台帳(I-2・I-27)の同時改訂**が必要で、同台帳には**変更履歴表がない**ため改訂の記録方法を先に決める必要がある(前例なし)
10. **計画の敵対レビューが 2 周で収束しなかったため、要件書の一括改訂を分割した(3 周目の指摘で臨時代走をさらに分離し**現在 4 本**)**(2026-08-14 PO 判断 — 末尾「タスク分割」)

| 失策・捕逸による出塁を非自責とする | ある | する |
| イニング再構成(失策抜きの状態再現) | **アウト数のみ整数カウンタで近似**。走者状態の再構成なし | 部分的 |
| 救援が引き継いだ走者の帰属(9.16(i) 相当) | ある(`HalfInningEarnedState.change_pitcher` が実アウト数から時計開始) | する |
| **フォースアウトの責任枠継承(9.16(g))** | domain にある | **しない**(該当ケースを検知して `unknown` に倒す) |
| **打席途中交代の帰属(9.16(h))** | domain にある。`_FORMER_PITCHER_WALK_COUNTS = {(2,0),(2,1),(3,0),(3,1),(3,2)}` は **`req:846` の規定と一致** | **しない** |
| タイブレーク走者の非自責 | ある | する(ただし `inning < 10` のハードコードで ruleset に非連動) |

**非対称の注意点**: ワイルドピッチ・ボークは非自責原因に**含まれない**(捕逸のみ)。失策機会カウントは 1 行あたり最大 +1 固定で、1 つの失策で 2 アウト分を失った場合を表現できない。PB・妨害には「失策がなくても得点したはず」の救済が適用されない(条件が `cause == ERROR` のみ)。

**したがって**: `req:846` が既に規定している 9.16(g)・9.16(h) の処理は、**旧システムでは自動化されていない**。旧が自動でできていたのは「責任投手の履歴逆走査による推定」と「仮想アウト時計による非自責の検出」までで、それ以外は人間へのエスカレーション。**pitchlog 要件書のほうが到達点が先にある。**

**踏襲の動機との関係**: 踏襲の理由は「旧に機能があり利用者が使っているので pitchlog に無いと乗り換えられない」。自責点はこれに該当しない(導線なし・ERA なし・88 列に列なし)。

**調査資料の空白**: 版固定の [`docs/legacy/research/`](../../legacy/research/) 9 本には `scoring_adjudication` / `official_scoring_*` の記述が**一切ない**(取り込み元が `ed6a20f` 時点のため)。公式記録エンジンはそれより後に旧へ入った。**この件について版固定資料は正本にならない。**

### 6. 公式記録ワークフローと既存 FR の突合

旧のワークフローを 15 要素に分解した結果、**12 要素が該当 FR なし / 3 要素が既存 FR の拡張で足りる / 3 要素が既にカバー済み**(重複計上あり)。

**新規 FR が必要(12)**: レビュー画面 / 判定の永続化(当時値スナップショット付き)/ **版管理 + `supersedes_id`** / 状態機械(`draft`・`review_required`・`final`・`stale`。半イニング 1 `final`)/ **人間レビューの承認** / **元データ指紋**(半イニング単位・プレイ+選手リンク+状態イベントの正規化 SHA-256)/ **自動陳腐化検出** / 判定理由コード / 判定エンジン版 / 判定保留(`review`)状態 / 判定入力の参照整合性検証 / 打点を記録員判断とする扱い

**既存 FR の拡張で足りる(3)**: 自責点の指標定義(付録A-2 の改訂)/ ruleset のスナップショット(FR-014 の拡張)/ FR-007・FR-011 への「判定の無効化」連動追加

**既にカバー済み(3)**: テナント分離(NFR-010 + NFR-019(b))/ 走者ごとの責任投手データの保持(`req:715`)/ 責任投手の帰属規則(`req:846`)

**設計思想が正面から異なる**: pitchlog は元データが変わったら「**再計算**」(FR-007 `req:223`・FR-011 `req:262`・付録C `req:901` が一貫)。旧は「**無効化して人間に再判定させる**」(`db/official_scoring_repo.py:339-358` が指紋不一致で `stale` 化、確定は 409 で拒否)。人間の判断を含む派生物は機械的に再計算できないため、この差は必然。pitchlog 側に「人間判断の永続化」という前提がないため、対応する要求も存在しない。

**稼働/未稼働の切り分け**(踏襲範囲の判断に直結)

- **稼働している** — ハーフイニング単位のレビュー表示。`GET /games/{id}/scoring-review`(`api/routers/games.py:536-552`、`services/half_inning_scoring.py:80` が `"persisted": False` を明示)→ `frontend/src/components/game/OfficialScoringReviewSheet.tsx`(読み取り専用 `:244,287`)
- **稼働していない** — 判定の永続化・版管理・人間承認・指紋・陳腐化。**新規 FR 12 要素の中核がこちら側**

**個別の重要判定**

- **FR-007 は版管理をカバーしない**。受け入れ基準 7 行(`req:220-227`)はすべて「修正 → 下流再計算 → 再集計」の系。履歴性に触れるのは `req:225` の論理削除のみで、これは「行を消さない」であって「前版を保持して新版を作る」ではない。差分プレビューは**実行前**の確認
- **FR-040 は `official_scoring_revision` とは別物**。FR-040 の対象は試合進行状態(回・表裏・得点・S/B/アウト・打順・走者 — `req:309`)、判定の対象は記録員の判断値。旧の FR-040 相当物は `game_state_event`(`state_override`)で、改善台帳 I-26 が FR-040 の出所を「旧 `render_manual_state_change_expander` の後継」と明記。旧では **`game_state_event` が公式記録判定の入力**(指紋の材料)
- **`source_fingerprint` 相当の要求は要件書に存在しない**
- **操作イベント 7 種には加えない**。「操作イベント」の定義は `req:106` で**断中キューの単位**。`req:153`(4.0-4)が断中可能な操作を完全列挙し「これ以外(過去プレイの修正・分析・カルテ編集・試合開始)はオンライン前提」と明記。公式記録の判定・改訂は旧でもオンライン前提(サーバ側トランザクション+試合単位ロック必須)なので 7 種の外。**追記すべきは用語定義**であって操作イベントの種別ではない。ただし**同期プロトコル(コア領域)への影響は別途規定が必要** — 断中に積まれたプレイが復帰同期で適用されると当該半イニングの判定が `stale` になる(`db/official_scoring_write_integration.py:269-294` がプレイ書き込みと同一トランザクションで refresh)
- **`reviewed_by` はチーム名**(`api/deps.py:168-171` で個人名を破棄)。2.2 Won't「個人アカウント・入力者の識別」(`req:70`)との衝突はないが、**「誰が承認したか」は原理的に記録できない**

### 7. テナント分離 Won't の決定経緯

**「テナント分離が価値の核」の一次記録は `req:77` の Won't 行 1 行だけ**で、この表現を導いた対話決定(D-\*)は**記録なし**([`requirements-draft-pitchlog.md`](../../requirements/requirements-draft-pitchlog.md) 全文に該当語なし)。記録上の根拠は一貫して旧 NFR-007 由来の**「スカウティング優位性の保護」**(pitchlog の NFR-010 は目的紐づけ 1.1(b) を継承 — `req:635`)。

**テナント分離を前提に据えた決定**: D-1(2026-07-20・外部チーム提供を視野)/ D-2(共有クラウド 1 インスタンス SaaS)/ D-4①(分離は初日から。「後付けは困難なため」)/ **I-2**(理由が最も明確 — 「記録データはスカウティング情報であり、他チームへの漏えいは製品の信頼を一発で失う」「後付け・後追い是正では漏れが構造的に生まれる」)/ D-31。

**Won't の一次記録**: 決定記録の「機能要件の横断精査 ③」(2026-07-21、D 番号なし)。根拠は「**7-2(データ所有権制御)の帰結**」であり、**共有の是非を検討・比較した記述はない**。同じ一文の中で「対戦相手データの突合・共有は将来検討として未決事項へ」と送られ、**D-36(2026-07-22)で未決事項に正式登録**。旧要件書には同種の Won't は存在せず、**pitchlog 側で新設されたもの**。

**したがって撤回の位置づけ**: 「共有を想定した上で是非を評価して否定した」記録は**ない**。あるのは「共有の可能性を認識し、所有権制御の帰結として非共有を確定し、検討は将来へ送った」という記録。**撤回は「過去の評価を覆す」ではなく「保留していた検討を実施する」に該当する。**

**過去に共有系の提案が却下された記録**: **なし**(全レビュー回の却下・棄却リストを確認)。ただし **D-44 で「記録権引き継ぎの認可」が共有アカウントモデル(D-3)と衝突して棄却**されており、**認可の粒度を増やす提案は共有アカウントと衝突する**という構造が記録上明確。データ共有は「1 チーム数十名が PW 共有」(`req:98`)の共有アカウントに**対外開示の権限を渡す**設計になるため同系統。**「共有フラグと共有アカウントの相性」を論じた記録は存在しない = 撤回時に新規で潰すべき論点。**

**見落としやすい依存**: D-15 改訂(2026-07-21)で語彙のチーム拡張が緩和された理由が「**テナント分離により集計は自チーム内で閉じるため安全**」。テナント間で成績・球種割合を突き合わせるとこの安全性の論拠が失われる(R-9 の表記ゆれリスクは「チーム内運用規律に委ねる」で受容 — `req:796`)。**この理由づけは決定記録側にのみ存在し、要件書 4.0-3 には残っていない。**

### 8. 分析ワークスペース(チーム間データ共有)の仕組み

- **共有の単位**: `analysis_data_grant` の主キーが `(workspace_id, team_id)` = **自チームがワークスペース単位で何を出すかを決める**。相手チームごとの出し分けは同一ワークスペース内では不可能(ワークスペースを分ければ実現可能)
