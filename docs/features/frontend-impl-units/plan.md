# 実装計画書: frontend の実装単位を定義する

## 1. 背景・目的

**Notion**: [frontend の実装単位を定義する](https://app.notion.com/p/3f493b75e68781cb8274c82fa427a317)
**調査メモ**: [research.md](research.md) — **典拠集**(正本ではない)。本書が事実を述べるときは正本か実測を直接引く。

**着手の足場が定義されていない。** 実装単位の表(`../product-impl-unit-split/`)の **23 単位はすべてサーバ側**で、`frontend` / `画面` / `Vue` / `クライアント` の語が `plan.md` と `design.md` の全文で **0 件**である(実測)。**単位が無いので、計画書の置き場も FR の帰属もコア領域判定も存在しない。** `frontend/src/screens` `stores` `api` `layouts` が**実体 0 件**(`.gitkeep` のみ)なのは人手の問題ではなく、ここに起因する。

**リリース判定③**(要件書 8 章)が「**実試合 1 試合をフル記録し、記録者は開発者以外・利用ガイドのみを頼りに完走**」を求めており、**画面は必須**である。

**対象 FR/NFR**: 主所有は動かさない(2 節)。**分担として面を足す対象は FR-001〜042 のうち画面側の責務を持つ 41 件**([research.md](research.md) 1 節)。**単位の DoD へ入る横断要求**は `NFR-005` / `NFR-018` / `NFR-019` / `NFR-023` / 要件書 4.0-2 と、`NFR-001` / `003` / `004` / `006` / `007` / `015` / `020`(同)。

### 13 章の射程宣言との関係(**先に片づける**)

**設計書 13 章の射程宣言は「実装単位の数・名称・境界・PR 分割・着手順・見積もり」を「実装時(各実装単位のタスク)で確定する範囲」としている。** TSK-363 はこれに 2 周続けて `P0` を受け、**PO 裁定(2026-09-13・山田正輝)**を取った:

> **厳密に読むと循環する** — **「各実装単位のタスク」は単位が定義されないと存在できない**のに、**単位の定義が「各実装単位のタスク」の仕事**とされている。**誰も最初の 1 歩を踏めない。**
> **裁定**: カードを優先する。**13 章の射程宣言は循環するので、最初の 1 回だけメタタスクが単位を定義してよい。** **正本は改訂しない**(確定ゲートを払わない)。

**本タスクは 2 回目のメタタスクである。** 「最初の 1 回だけ」の文言をそのまま読むと本タスクは射程宣言に触れたままになる。**人間の決定(2026-10-09・山田正輝)により、この裁定を frontend へも拡張する。** **正本を改訂しない点は TSK-363 と同じ**で、**衝突は記録として残す**(13 章の改訂が要ると判断されたら、それは別タスクの確定ゲートである)。

**`H-68`(実機のない段階で細部まで確定させると確定ゲートが閉じた輪に入る)について。** **本タスクは正本を触らないので 7.3 の確定ゲートを通らない。そこまでは言える。** **ただし「失敗形そのものが不在」とは言わない** — 台帳には**計画レビュー段階で同型が出た例**があり、TSK-272 の取り下げ記録も「13 章改訂を外した後もなお `H-68` 型だった」と記している。**したがって本タスクが引き受けるのは「確定ゲートの輪に入らない」ことだけで、計画レビューが輪に入る可能性は残る。** その手当ては**射程の縮小**(2 節の「やらないこと」)と**導出の `design.md` への分離**(4 節)であり、**TSK-363 が 3 周の `P0` を経て採った形をそのまま踏襲する**。補強として、**TSK-272 が否決した対象のうち「13 章に群を書く」経路は、13 章 v1.13 自身が閉じている**(「**本節は製品機能の実装について順序・群・段階を定めない**」)。**ただし TSK-272 の否決が「13 章への条文化」だけだったとは言えない** — 取り下げ記録には**13 章改訂を外した後もなお同型の指摘が残った**とあり、**作業ツリーに逐語が無いため何を否決したかは確定できない**([research.md](research.md) 3 節)。より確かな補強は、**TSK-363 が同じ条件 — 当時も製品コード 0 行 — で通っている**ことである。

**着手可否の判定権**は 13 章 v1.13 が「**着手可否は 6.1 の計画書ゲート〔人間承認〕で判断する**」と明言している。**「API / UI 設計が 0 行だから着手できない」と判定する権限は条文のどこにも無い。**

## 2. スコープ

### やること

1. **frontend の実装単位を定義する** — 数・名称・境界・**コア領域判定**・依存関係。**着手順は非拘束の推奨に留める**
2. **各単位が担う「面」を、既存 23 単位への分担行として書く** — **主所有は 1 件も動かさない**(契約 1)。**分担には面の名前を必ず書く**(契約 2)
3. **どの単位にも属さないクライアント側の要求を拾う** — 要件書 4.0-4 の断中動作 / `NFR-006` の鮮度表示 / `NFR-007` の E4 / `NFR-019` の E5 / `NFR-020` の単一書き手 6 前提と不成立時の表示。**契約 5 に従い各単位の DoD へ入れるのか、分担行を立てるのかを決める**
4. **コア領域に触れる面と触れない面の境界を引く** — 非コアで回せるのは `src/screens` `src/stores` `src/api` `src/layouts` と `src/components`(`zone/` を除く)の本体だけで、**`src/lib/sync` の 61 ファイル・`components/zone`・`src/lib/generated/*` は全部コア**([research.md](research.md) 5 節)
5. **Notion カードを起票する**(単位ごと)
6. **帰属の導出は [design.md](design.md) に書く**(本書は契約を持つ)

## 4. 実装方針

**重さ分類 = 通常**。根拠: 本タスクの成果物は **`docs/features/` 配下の文書と Notion カードだけ**で、`.claude/core-areas.json` の `paths` にも `guard_paths` にも当たらない(実測。`frontend/` 配下のコードを 1 行も書かない)。**コア領域の判定を「記録する」ことと、コア領域のコードを「変更する」ことは別である。**

**導出は [design.md](design.md) が正**(本書は契約を持つ)。**TSK-363 は計画書の中で 42 FR × 5 領域 = 210 セルの帰属の完全性を証明しようとして 3 周とも `P0` を出し、`design.md` へ分離して 4 周目に収束した。** 同じ轍を踏まない。

### 単位の境界を引く材料(実測。詳細は [research.md](research.md) 2 節)

- **共有部品は `ui/` だけが全画面で共有**。zone・field・diamond・pads・scoreboard の利用者は **GameScreen とその配下だけ**
