# 調査メモ: frontend の実装単位を定義する

## 問い

1. **どの FR が frontend 側に主所有を持つべきか**(要件の側からの帰属)
2. **移植元が実際にどう面を切っているか**(独立に作れる面と、まとめて作るしかない面)
3. **単位分割の契約と、過去の否決の経緯**(同じ轍を踏まないため)
4. **コア領域の境界**(非コアで回せる面はどこまでか)

## 結論(要約)

- **主所有の空きが無い。** 要件書の FR は **42 件**で、**既存 23 単位が 42 件すべてを主所有**している(検算: 延べ 42 / 一意 42 / 多重度 max 1)。**frontend の単位は「面の名前つきの分担」としてしか契約に入れない**
- **画面の集合は要件から導けない。** 要件書に「画面一覧」「画面構成」「画面遷移」は**全文 0 件**。**単位の境界は旧 frontend の構造から導く**ことになる
- **「最初の 1 回だけ」という PO 裁定がある。** 13 章の射程宣言との循環を避けるため、**メタタスクが単位を定義してよいのは 1 回だけ**とされ、TSK-363 がそれを使った。**本タスクは 2 回目であり、裁定の拡張が要る**(人間の決定 2026-10-09 = 拡張する)
- **非コアで回せるのは画面・ストア・API クライアントの本体だけ。** `src/lib/sync/`(61 ファイル)・`components/zone/`・`src/lib/generated/*` ほかは**すべてコア領域**
- **移植元の基準が 2 つの記録で食い違っており、実物も読めていない**(未解決)
