### 射程を大幅に絞った理由(計画レビュー 1 周目 P0-2・P0-3・P0-4 を採用)

**当初計画は「FR 42 件を群へ割り当て、13 章へ製品実装フェーズを新設する」だった。これは否決された。**

- **P0-2**: **API / UI 設計が 0 行の段階で「群」を最終確定するのは H-68 の型そのもの**である。
  スタブの方向・API・状態所有者・失敗時の扱いは実体が無ければ決められず、
  **文字列の「スタブ宣言」は何も保証しない**。**H-68 の 1 例目は「Phase 4 の分割」であり、
  同じ 13 章・同じ種類の改訂で既に 18 周の閉じた輪に入っている**
- **P0-3**: 新フェーズを Phase 5 の後ろに置くと、**13 章冒頭の「この順に develop へ」により
  Phase 5 の完了後でなければ開始できない**。しかも **Phase 5 の完了条件は「個別判断」**である。
  さらに計画が頼った「第 4 号以降」は **`Phase 4 完了時受入の前提 PR` の第 4 号以降**であって、
  **新しい複数 PR フェーズの手続ではない**(**計画の読み違いだった**)
- **P0-4**: 「3 つ目の全数表は作らない」と言いながら **JSON と 13 章の群→FR 表という二重の全数表**を
  新設していた。かつ典拠に使おうとした `product-data-model-design/design.md` は
  **自ら「候補案であり決定ではない」と明記する一時文書**であり、**approved な 13 章の規範根拠にできない**

→ **本タスクは「要件が直接強制する束ねの下限」だけを固定する。**
**群の確定と 13 章の改訂は別タスクへ送る**(前例 P5 = 要件解釈から独立した前提整備だけを完結させる /
P6 = 正本化を別タスクにしてその起票を DoD に入れる)。

### なぜこれが「実装に移る」ことに寄与するか

**実装開始に 13 章の改訂は必要ない。**必要なのは**承認済みの実装計画書**(絶対規則 5)である。

本タスクが固定するのは、**どんな群分けであっても満たさなければならない要件由来の下限**である。
これがあれば:

- **縦切り 1 本目のタスクが、下限に照らして安全かを機械で確かめられる**
- **13 章改訂タスクが、18 周ではなく短い周回で通る**(論点が (A)/(B) に分かれ、伝播表がある)

### 要件 FR/NFR との関係

本タスクは**個別の FR を実装しない**。**要件が束ねに課している制約を機械可読に固定する**ことが成果物で、
根拠は次の 3 条:

- **`NFR-019(a)`**(`REQ:917-921`)— 一致性テストの比較単位が**束ねの下限**を決める
- **`NFR-018`**(`REQ:884-885`)— (α)/(β) 区分が**実行の所在**で FR を切り分ける
- **`NFR-019(b)`**・**`FR-034`**(`REQ:638-651`)— 出力経路の認可が**横断制約**になる

## 2. スコープ

### やること

1. **論点の (A)/(B) 分類を固定する** — **(A) = 要件が直接強制するので実体なしでも決まる** /
   **(B) = 実体が無いと決められない**。**(B) は `決定時点` / `解除条件` / `必要な Git 上の成果物` /
   `再計画トリガー` で表す**(**タスク ID を必須にしない** — 計画レビュー 1 周目 P1-11)
2. **要件が強制する束ねの下限を機械可読に固定する** — 一致性比較単位 / 明示順序 / 相互依存の存在 /
   (α)(β) 区分 / 横断制約 / 前提。**群の数・名称・PR 分割は決めない**
3. **下限の全数被覆検査器** — `req-universe.json` の FR 42 件に対し、
   **各 FR がどの制約に関与するかを全数記録**する(未記録 0)。**群への割り当てではない**
4. **13 章改訂のための伝播表** — `Phase 5` / `P4-後` / `この順に develop` / `1 PR` / 前提 PR を
   **全件列挙**し、各箇所を **`改訂` / `不変` / `歴史記録`** へ判定する(計画レビュー 1 周目 P1-5)
5. **後続タスクの起票** — 13 章改訂タスク / 要件書 `FR-035` の矛盾是正タスク

## 4. 実装方針

### 重さ分類の根拠 — **通常**

**コア領域(同期プロトコル / 状況計算 / 記録権 / テナント分離 / データ移行)に触れない。**
成果物は機械可読資産と検査器で、`.claude/core-areas.json` の `paths` にも該当しない。

**正本への反映が 0 件になったため、本タスクは確定ゲート(7.3)の対象外**である
(**当初計画は対象だった** — 13 章の改訂を別タスクへ送った結果)。
**13 章改訂タスクが 7.6-3 後段(版繰り上げ + 7.3 確定ゲート)を通す。**

### (A) に残すもの — 要件が直接強制する下限だけ

**実体が無くても要件書から一意に決まるもの**に限る(計画レビュー 1 周目 P0-2 の是正案)。

| 制約種別 | 内容 | 典拠 |
| --- | --- | --- |
| **一致性比較単位** | `FR-005`・`006`・`020`・`021`・`022`・`023` + **付録 E-1 の成績計上フラグ全欄**が **1 つの比較単位**。**分けると一致性テストを構成できない** | `REQ:917-921` |
| **実行区分** | **(α)/(β)** が実行の所在で FR を切る。**`FR-021`・`FR-022` は両方に現れる** | `REQ:884-885` |
| **明示順序** | `FR-042 → FR-041` / `FR-039 → FR-001` の **2 件のみ** | `REQ:513` / `REQ:397` |

**前提は「Git 上の成果物が approved であること」で書く。タスク ID を書かない**(P0-1)。

### (B) へ落とすもの

**群の数・名称・PR 分割 / API・UI 境界 / スタブの有無と契約 / frontend・backend の担当順 /
旧 frontend の再利用 / 見積もり / 新フェーズと Phase 5 の関係。**

**(B) の表現形式**(P1-11 の是正案):

| 列 | 意味 |
| --- | --- |
| `決定時点` | いつ決まるか |
| `解除条件` | 何が揃えば決められるか |
| `必要な Git 上の成果物` | 何が approved になれば足りるか(**タスク ID ではない**) |
| `再計画トリガー` | 何が起きたら本タスクへ戻るか(例: **TSK-226 の完了 → 群数・境界の再レビュー**) |

### FR-021 / FR-022 の二重所属の扱い(計画レビュー 1 周目 P0-7 を採用)

**「FR の一意な被覆」と「実行区分」を別関係にする。**

- **被覆関係**: `FR → 関与する制約の集合`。**FR 42 件が全数現れ、未記録 0 件**
- **実行区分関係**: `(FR, 実行区分)` の組。**`FR-021`・`FR-022` は (α) と (β) の 2 行を持つ**

**exact-set の「重複 0」は被覆関係にのみ課す。**実行区分関係は組で一意とする。
**付録 E-1 を一致性比較単位の必須メンバーとして検査対象に含める**(当初計画は落としていた)。

### 機械化禁止との境界(計画レビュー 1 周目 P0-1 を採用)

設計書 `:847` が禁じるのは **「論理スロットと Notion タスクの対応の機械化」**で、理由は
**「起票する行為そのものは誰も検査できない」**である。

**本タスクは境界に近づかない形に変える**:

- **成果物のスキーマから `task_id` / Notion URL / タスク状態 / 起票数 / 群名由来のタスク名を禁止し、
  テストで拒否する**
- **群を作らない**(群は (B))。したがって **FR → 群 → タスク の対応が生まれる経路が無い**
- **前提は Git 上の成果物条件で書く**(「approved なベクタ」「88 列対応表」)

### 合格条件の書き方(計画レビュー 1 周目 P1-6 を採用)

**有限集合・許容値・比較対象ファイルが定義できるものだけを機械合格条件に残す。**
それ以外は **「人間レビューで判定」と明記し、機械 green を意味的合格として扱わない**。
