# 調査メモ: 実装ロードマップの作成(FR 42 件の束ね + Phase 表への製品実装フェーズ追加)

凡例: **◎** = Claude が原典を直接確認した / **◆** = Claude 自身が実行して確認した /
無印 = サブエージェントの報告(典拠つき)

## 問い

1. FR 42 件を実装単位へ束ねるとき、**順序と依存はどこまで要件書から決まるのか**
2. **設計書 13 章へ製品実装フェーズを足す**のに、どのゲートを通り、射程をどこまでに絞れば通るのか
3. **既に何があるのか**(重複起票・二重設計を避けるため)
4. **取りこぼし 0 件を機械で示す**手段は既にあるか

## 結論(要約)

1. **束ねの主要な制約は「ブロック分けを実装単位にできない」ことである。**
   **NFR-019(a) の一致性テストが 1 つの比較単位に FR-005・006・020・021・022・023 + 付録E-1 を束ねる**
   ため、**ブロック 1(試合記録)と ブロック 3(リアルタイム成績)を別々に実装すると、この一致性テストを
   構成できない**。NFR-018 の (α)/(β) 区分もブロック境界と一致せず、**FR-021・FR-022 は (α) と (β) に
   分割される**。
2. **順序では解けない相互依存が 3 組ある** — `FR-012 ⇄ FR-013`(記録権世代と連番)/
   `FR-034 ⇄ FR-041`(認可の正は 034 側、経路は 041 側)/ `FR-006 ⇄ FR-040`(undo 対象)。
   **同一実装単位に入れるか、片方をスタブで先行させるしかない。**
3. **要件書自身が「未実装だと成立しない」と書いている順序制約は 2 件だけ** —
   `FR-042 → FR-041`(`REQ:513`)と `FR-039 → FR-001`(`REQ:397`)。**残りは設計判断である。**
4. **ロードマップが approved 決定と正面衝突しうる箇所が 1 つある**(◎)。設計書 `:847` は
   **「論理スロットと Notion タスクの対応の機械化は行わない」**を v1.9 で approved 済みとしている
   (9〜15 周目に 7 案を起案して全否決。「**起票する行為そのものは誰も検査できない**」という同じ限界)。
   → **ロードマップに進捗の機械判定・タスク対応の機械化を同梱してはならない。**
5. **Phase 4 は設計書上「完了」として記録されていない**(◎)。完了証跡は `P4-後` が 13 章へ記録する規定
   (`:827`・`:842`・`:851`)だが**その記録が無く、`P4-後` の worklog も存在しない**。
   そして `:850` が「**`P4-後` のマージを ① Phase 5 への着手 ② Phase 4 展開タスクのクローズ
   ③ プロダクトリリースの開始 の前提とする**」と定めている。
   → **規範上、プロダクトリリースの開始は開いていない。TSK-263 が先行する。**
6. **H-68 の 1 例目は「Phase 4 の分割」そのものである**。同じ 13 章・同じ種類の改訂で**既に一度
   18 周の閉じた輪に入っている**。18 周のうち **9 周分は「実体のない機構の机上設計」**に費やされた。
7. **取りこぼし 0 件の機構は既にある**が、**単一文書にハードコードされている**。
   `check_doc_coverage.py:15` の `--document` 既定値が `docs/design/sync-protocol.md` で、
   **CI は引数なしで走る**(設計書 `:623`)。**別文書の帰属表は現状の CI 配線では検査されない** —
   これは **TSK-269(文書検査の多文書対応)の射程そのもの**である。
8. **要件書に矛盾 1 件を発見した**(§7)。**FR-035 の操作ログの優先度が 3 箇所で不一致**。
   v1.7 で Must へ昇格した事実が受入基準と変更履歴には反映され、**条見出しと 6.1 のデータ表には
   反映されていない**。**要件書側の是正が必要**。

## 詳細と典拠

### 1. 束ねの制約(要件側)

#### 1-1. ブロック分けは実装単位にならない — 決定的な材料

**NFR-019(a) の比較単位**(`REQ:917-921`)は 1 つのテスト対象に
**FR-005・FR-006・FR-020・FR-021・FR-022・FR-023 + 付録E-1 の成績計上フラグ全欄**を束ねる。
→ **ブロック 1 と ブロック 3 を分けて実装すると、この一致性テストを構成できない。**

**NFR-018 の (α)/(β) 区分**(`REQ:884-885`)は「実行の所在」で切る:

- **(α)** = 状況判定・入力表示の座標変換・捕球選手推定・終了判定 +
  **断中にクライアントで実行する成績集計の前処理(FR-020〜023)** → **ブロック 1 と 3 が同一区分**
- **(β)** = ①FR-025/026/027 ②FR-028/029 ③**FR-021/022 のシーズン通算欄** ④FR-041 ⑤FR-042
  ⑥FR-038 座標変換 ⑦打球方向導出 ⑧FR-038 責任投手導出
- → **FR-021・FR-022 は (α) と (β) に分割される**

**FR-042 の補足**(`REQ:522`)が「NFR-019(a) の一致性テストは**拡張しない**…
**バックエンド集計の契約と単体テスト**を別建てで置く」と明示 → **検証経路の分岐 = (α)/(β) 境界**。

**「ブロック分けをそのまま実装単位にできるか」は要件書に記載がない**。ブロックは 2.1 の分類
(`REQ:77`「以下8機能ブロック(詳細は4章)」)であり、実装単位の宣言ではない。

#### 1-2. 順序では解けない相互依存 3 組

| 組 | 内容 | 典拠 |
| --- | --- | --- |
| **FR-012 ⇄ FR-013** | 連番は記録権世代ごとに採番され、正史は「世代の連結」/ 記録権拒否は内容の編集で解決できず退避へ誘導 | `REQ:291`・`:312`・`:319`・`:301` |
| **FR-034 ⇄ FR-041** | FR-034 が FR-041 の認可行列を受入基準に含み、判定の全条件は FR-034 側が正 | `REQ:488`・`:498`・`:599` |

**同一実装単位に入れるか、片方をスタブで先行させる以外に解けない。**

#### 1-3. 要件書が明示する順序制約は 2 件だけ

- **`FR-042 → FR-041`**(`REQ:513`): 「A-5 を定める本FR(FR-042)が**未実装だと FR-041 が成立しない**」

**残りの順序はすべて設計判断**であり、**ロードマップが決める部分**である。

### 2. ゲートと射程(決定経緯)

#### 2-1. ゲート区分は 7.6-3 後段(版繰り上げ + 7.3 確定ゲート)

13 章の Phase 表に関わる改訂 **13 件**のうち、**版を上げなかったのは 2 件だけ**で、いずれも
「件数の参照化」「別名の置換」= **規範条件を変えない同期**。
**規範条件・完了条件・PR 本数に触れた改訂はすべて 7.3 確定ゲート**である。

直接の前例(`docs/features/frontend-skeleton/plan.md:29`):
「**設計書 13 章の改訂は確定ゲートを先に通す**(計画レビュー 1 周目 P1-4)」
→ 同 `:33`「**4 により本タスクは 2 段構成**になる — 設計書 13 章の改訂 → **確定ゲート** → 骨格の実装」

台帳 **H-19** は「実装追随の節更新 = PR レビュー」で起案した判定が**連続 5 件確定ゲートへ覆っている**
ことを記録している(前段で通った実例は 1 件のみ)。

#### 2-2. 「18 周」の内訳と原因(◎ 出典 2 本で一致)

出典: 設計書変更履歴 v1.7 行(`:43`)と `docs/worklog/2026-08-16-frontend-skeleton.md:97-99`。
**周回の数え方は ① 両文書の明記 ② `反映1周目`〜`反映18周目` の各 1 コミット**(設計書 6.1 の反映周
コミット規定)の 2 系統で裏づけられている。

| 周 | 内容 |
| --- | --- |
| 1・2・6 周目 | **P0 3 件** — いずれも「**受入合格の確定前にリリース経路が開く**」同型 |
| 9〜15 周目 | **実体のない機構の机上設計。7 案を起案して全否決**。12〜15 周目の P1 は **11 件中 11 件が直前の周の修正への指摘**(閉じた輪) |
| 16 周目以降 | スコープ縮小の後片付け。**新しい設計論点は出ていない** |

**縮小後の 16 周目に出た指摘 1 件は「縮小と無関係の既存の矛盾で、15 周かけて誰も気づかなかった」**
— **範囲を絞ったことで見えるようになった**、と worklog が記録している。

**含意**: 新フェーズを Phase 表へ 1 行足すだけなら系統②の因子は原理的に発生しない。
**新フェーズの運用機構(タスク対応の機械化・進捗の機械検査・完了条件の機械判定)を同梱すると、
7 案全否決と同じ経路に入る。**

### 4. 取りこぼし 0 件を機械で示す手段

#### 4-2. `requirement-claims.json`(TSK-270 の資産)の流用可否

| 論点 | 事実 |
| --- | --- |
