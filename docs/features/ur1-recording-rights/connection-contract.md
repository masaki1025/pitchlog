# U-R1 ステップ 1: U-G1・U-S1 接続契約案

2026-10-14 作成。**物理資産・D4 発行部分は未承認の案**であり、製品実装・DB migration・認可/凍結資産の変更を許可しない。U-G1 の preparing 作成側と U-S1 の RG1 Port 接続面は項目別受理済み。意味の正は FR-013、data-model 5-3/6-1、sync-protocol 2-1/4-3/6-2/9-5 と、承認済み U-S1 R-16/R-17。物理方式の未決事項を仮値で埋めない。

U-G1 が作成側だけを受理するための短い参照は [RG1 受理シート](rg1-preparing-acceptance.md)、D4 方式と運用の PO 判断材料は [D4 裁定案](d4-decision-proposal.md)。後者は未承認で、前者の受理条件ではない。

**2026-10-15 の新4物理接続追補**: RG1内部operationの公開署名とU-G1/U-S1の呼出位置は維持する。DB読取関数2件だけを各`(uuid)`へ変更し、Aの固定関数実行器が検証済みscopeの`tenant_id`を唯一のbindとして注入する。呼出側がtenantを指定する引数・tokenフィールドは追加しない。DB関数内で引数と`app.tenant_id`の一致を検査し、不一致・欠損・不正はfail-closedにする。関数の戻りと直前`FOR SHARE NOWAIT`、B7/P3 B10の全取消は従前どおり。列ACLは`singleton_id`の同一行に`SELECT`と`UPDATE`を束ね、指定RG1表・列・owner・commit-check関数以外のUPDATEを拒否する。A統合後の実関数登録と凍結資産の値は7.7正式受理前の候補として別途照合する。

## 2. U-R1 から提示する関数・型（担当合意待ち）

これらは**提案する Python の接続面**である。実装名・引数形・結果型は U-G1/U-S1 の項目別受理まで確定しない。`_TenantTransaction` は既存 `tenant_transaction_scope` が渡す不透明なハンドルを意味し、Session を外へ出さない。

```python
@dataclass(frozen=True, slots=True)
class InitialRecordingRight:
    game_id: UUID
    generation: int                 # DB の D4、wire では不透明な str
    issuance_order: int
    holder_device: str              # 信頼できる端末識別の出所は要合意
    recovery_generation: str       # wire の不透明値
    recording_right_proof: str      # V12。応答で保持端末にだけ渡す

def read_rg1_open(scope: _TenantTransaction, *, game_id: UUID | None) -> None: ...
def assert_rg1_open_before_commit(
    scope: _TenantTransaction, *, game_id: UUID | None
) -> None: ...
def issue_initial_recording_right(
    scope: _TenantTransaction, *, game_id: UUID, holder_device: str
) -> InitialRecordingRight: ...
```

- RG1 は**二つの operation**に分ける。`read_rg1_open` は認可後・D5 の前に永続状態を**ロックせず**読む。`assert_rg1_open_before_commit` は同じ transaction のコミット直前に同じ状態行を共有ロックして再読し、そのロックを commit/rollback まで保持する。先の読み取り後に復元調整へ移行した場合は後者が検出して全取消。後者のロック取得後の移行は待機し、通常書き込みの確定が直列化順で先行する。初回から共有ロックを保持すると「事前検査後に移行→直前検査で全取消」の競合を実現できないため、その方式は採らない。`game_id=None` は試合作成前の共通ゲート、ID ありは認可済み試合の作成後変更。状態行の欠損・不明・読取失敗・調整中は再試行可能な例外（U-G1 で B7 相当、U-S1 の P3 は B10 へ写像）を返し、成功時は `None`。例外型・HTTP 写像は担当合意待ち。
- `issue_initial_recording_right` は、U-G1 が認可し試合行を `FOR UPDATE` した同じ scope 内でだけ呼ぶ。対象が自テナントの `preparing` 試合で、通常現世代が存在しないことを検査し、初期通常世代 1 行を挿入する。戻り値は**コミット前の仮結果**であり、U-G1 は scope の正常終了後にだけ証明値を利用者へ返す。二重開始・不在・越境では追加発行しない。例外結果の詳細は担当合意待ち。
- U-S1 向けには PortWriter の token 経由で現 D4/保持端末/V12、復旧世代と RG1 を判定する実装を U-R1 が提供する。U-S1 が独自に D4/V12/RG1 の規則を持たない。RG1 Port は `read_rg1_before_d5(writer: PortWriter) -> bool` と `check_rg1_before_commit(writer: PortWriter) -> bool` の 2 口を U-S1 が受理済み。後者だけが同一 RG1 行を `FOR SHARE` で再読する。`PortWriter.run_function(token)` は exact 固定関数 token を同一 scope の実行器へ渡す条件で受理済み。U-R1 が本物の port を登録する段階は承認済み計画の**新ステップ 8**であり、**U-S1 全体の完成は本接続契約の受理条件ではない**。

## 3. 操作別の成功境界とロック順案

| 経路 | U-R1 に必要なもの | 成功/失敗境界・順序案 |
| --- | --- | --- |
| `preparing` 作成 | `read_rg1_open(scope, game_id=None)` の事前判定と `assert_rg1_open_before_commit(scope, game_id=None)` の直前判定だけ。D4/端末/V12/復旧世代の発行契約は不要 | U-G1 の作成 transaction と同じ scope。事前判定後に移行が確定したら直前判定で B7 相当・全未確定。RG1 中/不明も同様。**開始時発行の未決事項を作成契約の受理条件にしない**。U-X1 の規則解決は別依存 |
| スタメン確定・開始 | 認可済み試合、信頼できる保持端末識別、初期発行、RG1 事前/直前検査 | 事前 RG1 読取はロックなし。U-G1 が `games` 行 `FOR UPDATE` → 自チーム行（必要な双方の安定順）→選手行 UUID 昇順 → U-M2 記憶 → `recording_generations` 行/追加 → コミット直前の RG1 状態行共有ロック、の順を候補とする。ゲーム・両側スタメン・記憶・初期権・開始時刻/状態は U-G1 scope の正常終了で全確定、途中失敗は全取消。既存 U-S1 の「ゲーム行→世代行」および U-M2 の「チーム行→選手行」は満たすが、**他チーム行を含む全順・記憶保存と発行の細かな順は U-G1/U-S1 受理待ち** |
| U-S1 同期 | 認可後の RG1、現世代/V12/復旧世代照合、直前再照合 | ③-a はロックなしで状態を読み、D5 の前に停止。既存 U-S1 イベント transaction はゲーム行→世代行。⑧ ではゲーム/世代行取得後に RG1 状態行の共有ロックを取って再照合し、commit まで保持する案。U-S1 の R-16 で定めたゲーム行→世代行の順は保つ。イベント適用/退避の所有は U-S1 |
| 復元調整への移行 | RG1 の直列化点と全ゲームの後続フェンス | **状態行だけを先に排他的にロックして調整中へ移し確定**、その後に通常経路と同じゲーム行→世代行で失効処理する案。移行 transaction は状態ロックを保持したままゲーム行を待たない。開始・同期と逆順を作らず、移行確定前の通常処理は直列化順で先行し、確定後の処理は RG1 で拒否する。状態の永続化/起動時 fail-closed と復旧世代切替は物理契約/PO ゲート待ち |

RG1 状態行への**直前検査の共有ロック**と、移行時の排他ロックをコミットまで保持する案である。`preparing` 作成はゲーム行がないので状態を先に非ロックで読み、後で状態を共有ロックする。開始・同期はゲーム行→（U-G1 だけチーム/選手）→世代行→RG1 状態行を基本候補とし、U-S1 R-16 の冒頭ゲーム行ロックと矛盾しないことを担当に確認する。**移行側の最初の transaction は状態行だけをロックし、ゲーム/世代行を待たない**ので逆順の待ちサイクルを作らない。全ロック順を受理するまでは製品の成功経路にしない。

## 4. 物理方式と判断の所在

| 項目 | 案・現時点の不足 | 判断 |
| --- | --- | --- |
| D4 の非再利用採番 | `recording_generations.generation bigint` が既存の保存先。通常の PostgreSQL sequence は transaction rollback 後の非再利用には使えるが、**バックアップ復元で sequence も巻き戻る**。厳密案はアプリ DB の復元範囲外にある耐久的な単調 `bigint` 発行源から一度だけ取得し、使用済み番号は失敗/取消後も戻さず、発行源が不明・不能なら fail-closed とする。初回 D4 や発行順に仮値を置かない | **PO/正本・運用ゲート**: 発行源の所有・障害/復元手順・追加資産を裁定。アプリ DB だけの sequence は採らない。nonce 案なら再衝突の残余リスクを別に評価・承認する |
| 復旧世代と RG1 状態 | 現行 ORM に永続列/表がない。復旧世代は復元後も再利用禁止。状態不明時 fail-closed、起動時読取、直列化ロック用の永続状態が必要 | **PO/7.6・凍結ゲート**: 新しい制御資源の形・所有・復元時の保存境界。U-S1/U-G1 は接続面を受理できる |
| 保持端末と V12 | `holder_device` 列はあるが、端末 ID の信頼できる発行/認証元、V12 の秘密値・寿命・保存先・失効/再発行・端末内格納先は未定。wire は不透明文字列、V12 は現 D4+復旧世代+保持端末に結合 | **U-G1/U-S1 担当合意**: 認証済み端末識別の入力元と応答/port DTO。**PO 裁定**: 秘密値・寿命・端末格納方式など意味に影響する選択 |
| 初回 `issuance_order` | 列と試合内一意・単調増加は既存契約。初回の具体値は正本未指定 | U-R1 の物理案を U-G1 と合意。値をここでは仮置きしない |
| 認可・凍結資産 | U-S1 Draft #132 が共有資産を作業中。U-R1 の新 operation と状態表が確定していないため差分・revision はまだ固定不可 | U-S1 統合後の基線で候補を作り、別の人間承認・7.7 受理。#132 は変更しない |

**所有の正確な読み**: TSK-250 は data-model 正本化タスクであり、同書 12-6 は D4 非再利用の**保証機構を本書に持たず、後続の実装で確定する**と明記する。後続の承認済み TSK-363 単位分割（2026-09-13）は U-R1 に記録権の付与・世代更新とフェンシングを割り当て、U-S1 R-17 も物理 D4・復旧世代・RG1 を U-R1 側へ送る。よって TSK-250 と U-R1 の所有衝突はない。復元外発行源や RG1 の新しい永続資源の**具体的な方式・認可/凍結資産・運用条件**は、計画の後続実装ゲートで別途提示・承認する。現段階で資産は変更しない。

## 5. D4 非再利用の推奨方式と復元手順（PO 判断用、未採用）

**推奨: 復元する業務 DB の外に、原子的な予約ができる耐久的な発行台帳を置く。** `bigint` の D4 を試合全体で単調に予約し、予約を永続化してから U-R1 に値を返す。予約は失敗・transaction rollback・引き継ぎ中断でも戻さない。業務 DB の `recording_generations.generation` と `issuance_order` は従来どおり別列であり、D4 値順を正史の並びに使わない。発行台帳の具体的な製品・API/ACL・配置は未選定で、**存在するものとして実装しない**。

| 観点 | 推奨候補の具体条件 |
| --- | --- |
| 永続資産 | ① 業務 DB のバックアップ・復元範囲に入らない発行台帳（次に予約する正の `bigint`、発行済み上限、予約履歴、復旧世代の非再利用識別、障害/復元 epoch）。② 業務 DB 内の RG1 状態行（状態・epoch・更新時刻。通常 transaction の直前検査で共有ロック、移行では排他ロック）。③ epoch の一致を確認する起動/再接続ゲート。表名・列名・ACL は候補ゲートで確定 |
| 開始・引き継ぎ | 発行台帳で一つの D4 を**先に永続予約**し、その値をテナント束縛済み transaction 内の世代行 INSERT に使う。業務 transaction の失敗時にも予約は失効済みとして残す。DB 側はテナント・試合・現世代の一意性と発行順を別に検査。台帳が応答不明なら再予約前に予約結果を識別できる契約が必要。重複使用の可能性があれば fail-closed |
| バックアップ復元 | ① 通常書き込みを停止し、発行台帳/復元制御で復元 epoch を新しく確定。② 業務 DB の過去 snapshot を復元。③ 起動ゲートが台帳 epoch と DB 内状態の不一致を検出し、通常経路を閉じる。④ RG1 調整中の状態を確定し全旧世代をフェンス、端末保持分を回収・退避し、未回収 0 と閲覧/書き出しを確認。⑤ 台帳から新 D4 と非再利用の復旧世代を予約し、RG1 解除と新世代 D3=0 の開始を業務 DB 内で不可分に確定。⑥ epoch 一致と健康状態を確認して通常経路を開く。これは NFR-009/DoD ⑥ の意味契約に従う**案**で、運用手順そのものの承認を代替しない |
| 障害時 | 発行台帳が読めない・予約が永続化したか不明・上限枯渇・epoch 不一致なら D4 を発行せず fail-closed。RG1 状態が読めない場合は**開始・同期だけでなく preparing 作成も** B7 相当で停止。既存の保持端末に「発行できた」と返さず、管理者ログ/通知へ理由を残す |
| RG1 との依存 | `preparing` 作成には D4 予約 API は不要。ただし安全な復元状態の読取と起動/再接続 epoch 照合が必要なので、**RG1 制御資源が未着地なら作成成功は不可**。発行台帳と RG1 の epoch を共通にするなら台帳障害が作成にも波及する。この可用性上の結合は PO が採否を決める。開始・引き継ぎは D4 台帳と RG1 の両方が必要 |

**代替案 A**: 復元対象外の別の PostgreSQL データベース/クラスタで sequence と予約履歴を管理する。既存の SQL 運用を再利用しやすいが、別接続の認証・ACL・障害監視と原子的な予約結果の確認が必要。業務 DB と同じ backup/restore をしてしまえば保証を失うため、別保全・復元手順は必須。

**代替案 B**: D4 を暗号学的乱数の nonce から発行する。バックアップ巻き戻しとは独立しやすいが、既存 `bigint` に収めると衝突可能性をゼロにできず、復元で失った履歴との照合もできない。128-bit UUID へ拡張するなら既存 DB/イベント/FK/契約の変更が広い。**いずれも「過去値を再利用しない」を無条件に証明する方式としては採らず**、残余リスクまたは正本の変更を PO が明示承認する場合だけ再検討する。

**PO に必要な裁定**: 復元対象外の耐久発行台帳を新設するか、代替の残余リスク/構造変更を受けるか。推奨案を採る場合は台帳の運用所有、復元時の epoch・高水位の保全、障害時 fail-closed と可用性影響、RG1 状態資源と startup gate の認可/凍結/7.6 対象を確定する。これらは本ステップで資産を変更しない。

### PO 裁定用の短い比較（外部台帳は未承認）

| 論点 | 確認結果と未決条件 |
| --- | --- |
| 正本の要求 | [sync-protocol 2-1](../../design/sync-protocol.md) の D4 はバックアップ巻き戻し後も**一度発行した値を再利用しない**。[data-model 5-3](../../design/data-model.md) は保存型を `bigint` とし、**単調増加を要求するのは別列の試合内 `issuance_order`**。D4 の数値順は正史の順序ではない。したがって外部の単調カウンタは保証を実現する一候補であり、D4 自体の単調性は正本の要件ではない。[NFR-009](../../requirements/requirements-pitchlog-2026-07-22.md) は過去の日次バックアップからの復元と全旧世代のフェンス・新世代発行を要求する |
| 外部台帳候補の配置と耐久性 | 具体候補は**業務 DB と別ホスト・別ストレージの PostgreSQL クラスタ**に、原子的な発行上限と予約履歴を置く方式。発行成功を返す前に同期永続化し、業務 DB の日次 export/restore へ含めない。別クラスタも古い snapshot に戻せば保証を失うため、**最後に成功応答した予約を失わない同期複製または同等の保全**と、台帳自身の復旧手順が必要。現行 MVP の `docker-compose.yml` は業務 DB と検査用 DB だけで、この台帳・複製先・バックアップ境界は存在しない。具体配置、耐久障害モデル、保管先は PO/運用承認待ち |
| MVP 追加資産・担当・復旧 | 採る場合は U-R1 が予約 operation/永続 schema/障害時 fail-closed を実装し、DB 管理側が別クラスタ・同期保全・監視・資格情報・復元 runbook・演習を用意する必要がある。既存日次 export だけを別クラスタへ複製しても、前日以降の予約を失うので不十分。復元時は台帳の最新上限を確認できるまで開始/引き継ぎを閉じ、業務 DB を復元、RG1 で全旧世代をフェンスし、非再利用値で新世代を発行する。運用担当・配置先・費用・RTO は未合意 |
| 別 DB / nonce | **別 DB** は業務 DB の restore 対象から外れ、最後の成功予約まで独立に保全できる場合のみ既存保証を満たし得る。同じホスト/backup の別 database は不十分。**乱数 nonce** は `bigint` の範囲で衝突確率を 0 にできず、失われた発行履歴を照合できないため既存の厳密保証を満たさない。UUID 等へ型を広げても確率的方式単独なら同じ。nonce の採用には非再利用保証の明示的な正本改訂・残余リスク承認、UUID 型変更にはさらに DB/wire/参照契約の改訂が必要 |
| 台帳障害の停止範囲 | **D4 専用の独立台帳**なら `preparing` 作成は D4 を発行しないため停止対象ではない。ただし RG1 状態を読めない/不明なら作成は B7 相当で停止。開始・引き継ぎ・復元後の新世代開始は D4 予約不能時に停止。既存保持端末の記録継続・同期は、既存 D4/V12/復旧世代と RG1 を独立に検証できる限り継続可能。台帳を RG1 epoch/毎要求検証と共用する設計なら作成と同期も止まるため、その結合は別の PO 裁定が必要。復元調整中は台帳の有無にかかわらず通常書き込みを停止 |

### preparing 作成側 RG1 の実測と受理境界

使い捨て PostgreSQL 17 の二接続で、提案する非ロック事前読取→`FOR SHARE` 直前再読と、復元側の同一行 `UPDATE` を検証した。復元側が先に確定した場合、直前検査が調整中を検出して例外となり、同一 transaction で挿入した試合行は **0 件**に rollback。作成側が先に共有ロックを取得した場合、復元側の更新は作成 commit まで **1.42 秒待機**し、作成→復元の順で確定した。これはロック機構の独立プローブであり、U-G1 の実 transaction/認可経路での結合試験と、関数・例外の担当受理はまだ必要。復元移行の transaction が RG1 行の排他更新だけで確定し、ゲーム行を待たないことがデッドロック回避の前提。

### ③-a・⑧ Port 確定照会（2026-10-14）

U-S1 へ `read_rg1_before_d5(writer: PortWriter) -> bool` と `check_rg1_before_commit(writer: PortWriter) -> bool` の候補を提示し、認可後/D5前とゲーム行→世代行 `FOR UPDATE` 後/commit前の各呼出位置、`PortWriter` の発行時点、終了後 P3 と内部配信の位置を項目別に照会した（Notion `3f993b75-e687-8127-93e3-001db36235ba`）。RG1 は global singleton のため `game_id` を Port 引数から外す案であり、現行 `is_restoration_active(game_id, writer)` からの変更は**担当回答待ち**。上記 U-G1 作成用 `read_rg1_open` / `assert_rg1_open_before_commit` は `None`/例外のサービス接続案、U-S1 Port は bool/失敗の内部候補で、型・変換を受理前に混同しない。

現行 `PortWriter.run` は表 DML の `_TenantTransaction.run` にしか到達しない。TSK-550 と共通の `run_function` を RG1 Port から同一 scope で呼ぶ閉じた口、その発行・失効を U-S1 へ追加照会した（同 `3f993b75-e687-81d8-ae7c-001d2afae493`）。**U-S1 所有 PortWriter の製品変更と実入口接合は承認済み計画の新ステップ6**とし、新ステップ2で行うのは署名合意と RG1 operation/DB 試験まで。U-S1 の返答を得る前に受理済みとはしない。
