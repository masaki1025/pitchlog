# 新5の data-model 改訂候補と 7.3 審査境界

状態: **正本未反映・正式 7.3 未開始**。`docs/design/data-model.md` は approved v0.11 のまま。以下を同書 6-1 の追補候補とし、正本の版繰り上げ・in-review 化、全文敵対レビュー、指摘採否、PO 承認を 7.3 の順に行う。候補の DDL・owner名・関数本文・JSON・7.7 実値をここで確定しない。

## 本改訂で確定したい範囲

1. 初期通常世代は試合**開始**時に U-G1 の開始 transaction と同じ業務DB transactionで作る。準備中の試合作成では発行しない。世代/配達の片方だけを確定しない。この変更は現行 sync-protocol 9-5 の「試合作成に初期記録権を含む」行と衝突する。U-S1 R-17に従い、同正本を作成と開始の2行へ分け、作成は試合行だけ・開始は初期世代/証明を含めてRG1停止時に全取消とする改訂を、U-G1統合より先に別ゲートで確定する。
2. D4 は業務DBの復元範囲外に置く同期保全の発行源で予約し、成功の耐久証明が取れないと発行停止する。予約IDはテナント・試合・開始要求へ束縛し、再照会は同じID/owner tupleに限定する。claimは一度だけ成功し、取消や復元後も番号を再利用しない。D4の値順は発行順を意味しない。
3. 復旧世代の現値は同じ復元外発行源で管理し、業務DB内のRG1状態に記録した世代と毎書込で照合する。不明/不一致では、既存記録権による書込も止める。外部epoch行の共有fenceを業務DBのcommit結果が確定するまで保持する。復元開始の最初のtransactionはRG1状態行だけを閉じて確定し、外部epochの更新はその後に行う。
4. V12の再交付値・digest・復旧世代は、既存世代表へ秘密列を足さず、世代へテナント付き複合参照を持つ別の `function_only` 表に置く。平文V12を業務DB・ログに保存しない。現権利・同一開始要求・同一の認証済み有効端末・同一復旧世代の照合が成功した時だけ暗号文から同じ値を再交付する。失効、鍵不明、端末不一致で再交付しない。
5. 端末IDの自己申告は権利の証拠にしない。認証に束縛された端末資格を内部operationでも再照合し、資格行の共有ロックを業務DB commitまで保持して失効と直列化する。新表はFORCE RLSと専用関数経路に限定し、既存世代表のapp権限を広げない。

## 実装時・別ゲートに残す範囲

具体的な表/列/制約/owner/関数/ACL/鍵管理/端末資格の物理資産、migration番号、固定operationと凍結契約、外部台帳の実配置と運用・費用、7.7の実revision/digest/snapshot、U-G1/U-S1の公開DTOとPort署名/呼出位置は別受理。運用上のRG1 open/復元開始の製品関数は新7、本物の `RecordingRightsPort` とHTTP実入口の結合は新8。本改訂でそれらを実装済みと記録しない。

## 既存正本との照合が要る箇所

| 箇所 | 審査質問 |
| --- | --- |
| data-model 5-3 `M04` / 6-1 | D4非再利用と発行順の分離を保ち、世代表の既存app ACLへ秘密が漏れないか |
| data-model 3-2 / 3-5 | 新しい配達表の function_only、FORCE RLS、専用ownerがRG1既承認の最小権限と衝突しないか |
| data-model 5-4 `WAIT-06` | 「P経路のT要素は同一業務DB」の規定と、Pの前に行う外部D4予約/claimを混同しないか。外部予約は業務DBのT要素へ含めず、業務DB commit失敗時のD4空番を許す |
| data-model 8-3 / ops key-rotation | 認証用HMAC署名鍵の旧鍵破棄規律をV12暗号鍵へ誤って流用しないか |
| sync-protocol 9-5、U-S1 R-17 | **現行9-5の作成行は変更対象**。作成/開始を分離する別の正本ゲートが先に成立し、RG1閉鎖の全取消、D5未消費、復元開始の先行閉鎖とロック順を保つか |

**7.3 の実施順**: canonical `data-model.md` の現行版と他担当の編集所有を確認 → 差分を正本に `in-review` で起案し、変更履歴に本書で確定/実装時に確定の射程を記す → 適用する7.3版と条文コミットをworklogへ記録 → 独立した敵対レビュー1回目(全文) → 指摘の採否・反映と必要な2回目(反映差分+影響節) → POへ最終本文/採否/未再レビュー差分を提示。未承認の段階で `approved` へはしない。
