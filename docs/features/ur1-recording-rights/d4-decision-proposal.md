# D4 復元後非再利用: PO 裁定案（未承認）

2026-10-14。**方式選定の提案であり、外部台帳の採用・資産追加・実装を許可しない**。`preparing` 作成の RG1 受理とは別ゲート。[sync-protocol 2-1](../../design/sync-protocol.md) はバックアップ巻き戻し後も発行済み D4 の再利用を禁止し、[data-model 5-3](../../design/data-model.md) は D4 を `bigint`、発行順を別の試合内単調増加列とする。[NFR-009](../../requirements/requirements-pitchlog-2026-07-22.md) は業務 DB の過去バックアップからの復元を前提とする。D4 数値自体の単調性は正本の要求ではない。

## 推奨する一案: 独立した同期複製 PostgreSQL 予約台帳

**一つの採否対象**は、業務 DB の復元範囲外に置く D4 専用 PostgreSQL primary と、別故障領域の同期 standby の組。D4 予約が両側の耐久ログへ記録された後だけ成功を返し、その予約上限を業務 DB の日次復元で巻き戻さない。これは `bigint` D4 の非再利用を保つための候補であり、RG1 の状態資源とは独立させる。同期 standby を失ったときに非同期運転へ降格しない。可用性より非再利用を優先し、最後の成功予約を証明できなければ新規発行を停止する。

| 項目 | 裁定候補と成立条件 |
| --- | --- |
| 配置 | 業務 DB の `docker-compose.yml` の volume・日次 export・復元範囲**外**に、D4 専用 PostgreSQL 17 primary を別ホスト/別ストレージで配置し、さらに別故障領域の同期 standby を置く。台帳の単一高水位と予約履歴だけを持ち、アプリからは予約 operation のみ許可。業務テナント表への横断 SELECT 権は付けない。ホスト/保管先/資格情報の実値は未指定 |
| 最後の成功予約の保全 | primary と standby の WAL 永続化を確認してから予約成功を返す。PostgreSQL では `synchronous_standby_names` を設定し、予約 transaction を `synchronous_commit=on`、`fsync=on` で運用する候補（[PostgreSQL 17 同期複製](https://www.postgresql.org/docs/17/warm-standby.html#SYNCHRONOUS-REPLICATION)）。standby 不達なら非同期へ自動降格せず、新規 D4 発行を停止。昇格時は最後の成功予約を含む standby だけを候補とし、旧 primary を必ずフェンスして二重発行を防ぐ。**両保全先を同時に失い最新高水位を証明できない場合は、古いバックアップからの発行再開を禁止**する。日次コピーだけでは非再利用を証明できない |
| 予約と業務 transaction | U-R1 は正の `bigint` を台帳で原子的に予約し、成功応答後に業務 DB の同一 `tenant_transaction_scope` 内で世代行へ使う。業務 transaction が rollback しても予約番号は戻さない。台帳の応答不明・値域上限・二重 primary の疑いでは fail-closed。予約自体の重複応答を識別するキーと、既存世代の再送判定は実装前に契約化する。`issuance_order` は試合内の別列として維持する |
| 復旧手順 | ① RG1 を調整中に固定し通常書き込みを停止。② 台帳の primary/standby から最新の成功予約上限を照合し、失われていれば再開しない。③ 業務 DB の過去バックアップを復元するが台帳は巻き戻さない。④ 旧世代を全フェンスし、端末保持分を回収・突合・退避する。⑤ 台帳から新しい D4 と非再利用の復旧世代を確保し、RG1 解除と新世代開始を不可分に確定する。⑥ 監査・再開判定を記録する。復旧世代の物理保全と epoch の設計は別途具体化が必要 |
| 実装・運用担当 | U-R1 は予約 API/DB operation、異常時 fail-closed、世代行との結合試験を担当する候補。**台帳クラスタ・同期複製・資格情報・監視・フェイルオーバー/復元 runbook の運用担当は未指名**で、PO が引受主体を決める必要がある。U-G1 は開始 transaction で U-R1 operation を呼ぶ担当、U-S1 は既存世代の同期判定担当。#132 の共有凍結資産の変更は本裁定案に含めない |
| MVP 準備と停止範囲 | 現行環境には専用クラスタ/standby がない。採用するなら**追加 PostgreSQL 2 インスタンス、独立ホスト/永続ストレージ 2 組、複製経路、監視/アラート、資格情報、migration、復旧 runbook と演習、障害注入/凍結契約検査**が要る。費用はホスト・ストレージ・複製通信・監視/保守の継続費と初期構築/演習工数。配置先と見積単価が未定なので金額は算定していない。D4 専用台帳が停止すると**開始・引き継ぎ・復元後の新世代開始**は停止。RG1 が独立して健全なら `preparing` 作成と既存世代の記録/同期は D4 予約障害だけでは停止しない。RG1 と台帳 epoch を毎要求で共用するなら停止範囲が広がり、別裁定が必要 |

## PO に決めてほしい項目

| 判断 | 現在地 |
| --- | --- |
| 上記の**二台・同期複製・障害時発行停止**を MVP の D4 方式として採用するか | 未承認。これを承認しても具体的な schema/認可/凍結契約の差分承認は別に必要 |
| primary と standby の配置先、別故障領域、永続ストレージ/複製通信の提供主体 | 未指定。こちらでクラウド/機器/契約先を推定しない |
| クラスタ/監視/秘密情報/復旧演習の**運用責任者**と障害時の連絡・昇格権限 | 未指名。U-R1 は製品 operation の候補担当であり、インフラ運用を自動引受けしない |
| 初期構築と月額費用の見積取得、MVP 日程への組込み、台帳停止中の開始/引き継ぎ不可を受け入れるか | 金額・所要期間は未確定。配置/担当が決まってから見積とリハーサル日程を固定する |
| 両保全先を失い最新予約上限を証明できない場合の運用 | 本案では**新規 D4 発行停止**。古い台帳 backup からの無条件再開は認めない。停止を解除するには発行済み集合を失っていないことの証拠、または別の正式契約改訂が要る |

採用時は具体的な DB/認可/凍結/運用差分を再提示し、規約のゲートを通す。別 DB でも最新予約の独立保全がなければ不適合。乱数 nonce は衝突可能性が残り、厳密保証を満たさないため、採用するなら正本の明示的改訂と残余リスク承認が必要。**保証の弱体化を既定案にしない**。
