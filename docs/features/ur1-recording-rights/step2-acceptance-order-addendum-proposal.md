# U-R1 新ステップ2: 候補作成と7.7受理の順序追補案（計画レビュー待ち）

2026-10-15。POは[作業ログの循環整理](../../worklog/2026-10-15-ur1-recording-rights.md)に示した、**正式受理前にローカル候補を作成する順序方針**を承認した。本書は[承認済み計画](plan.md)の新2開始条件と7.7受理順だけを追補する候補であり、計画レビューと最終人間承認は未了。RG1のowner・FORCE RLS・EXECUTE・FOR SHARE NOWAIT・隔離正常系は[既存の個別承認資料](rg1-individual-approval-packet.md)で項目別採否を受ける。本書は5項目の採否、正確なDDL/JSON、7.7実値の受理を兼ねない。

## 変更する開始条件

現行計画§4は7.7正式受理を新2の製品実装開始条件とする一方、同節は製品operation、凍結資産、snapshot、単一未マージ受理記録のafterを同じステップコミットに入れ、受理単位をPR最終headとする。候補がなければ実after・snapshotは確定できない。**新2を次の二段階に分ける。**

| 段階 | 着手条件 | 許す作業と止める境界 |
| --- | --- | --- |
| ローカル候補作成 | TSK-550共有実行器Aのdevelop統合。A統合後の最新developでbefore revision/digest/snapshotと既受理履歴を固定。5項目の項目別採否、具体的DDL/認可/必要正本の個別承認、候補作成範囲の明示許可 | **許可済み範囲だけ**専用worktreeで製品コード・試験・凍結資産の候補差分を作る。正式台帳の受理済み履歴・before側・PR #72のPENDING_ACCEPTANCEは変更しない。候補は「受理待ち」と明記し、承認者・承認日を仮記入しない。候補の検査が赤なら、差分を修正して再提示する |
| 正式受理とステップコミット | 候補の完全差分、実after revision/digest/snapshot、入力blob、movement_fact/reason、正式PR番号、独立レビュー・検査結果を人間へ提示し、7.7の個別受理を得る | 実承認記録から承認者・承認日を転記し、単一未マージ受理記録のafter、派生資産、archiveを候補と整合させる。製品operation/SQL許可・snapshot・記録afterを**同じ新2ステップコミット**に含め、凍結履歴/archive/契約・DB/認可検査を緑にする。中間コミットは受理単位にしない |

## A統合後の具体的な順序

1. Aの統合コミットと受理済み最終headを照合し、最新developを後続worktreeの基点にする。そこからCのbefore revision・canonical digest・参照blob/snapshot、履歴authorityと比較元、共有実行器の登録形式を読み取って固定する。旧試算値は使わない。
2. [個別承認資料](rg1-individual-approval-packet.md)の5項目を採否し、具体的なDDL/認可/必要正本と**ローカル候補作成だけ**の人間許可を得る。A/B/C分割承認や本順序方針を、5項目・資産差分の承認に流用しない。
3. 許可された候補をローカルで作り、試験で生成SQL・権限・固定2登録・常閉/隔離競合を確認する。正式台帳の受理済み履歴には触れない。snapshotがコミット済みblob等を要して、ステップコミット前に識別値を作れない場合は**中間コミットの例外と対象を先に提示**し、追加許可まで停止する。
4. 実before/after、全変更ファイル、revision/digest、snapshot/blob、単一未マージPR記録のafter候補、movement_fact/reason、検査と独立レビュー結果を人間へ提示する。承認者・承認日は資料上「受理待ち」で、正式台帳にはまだ書かない。既存Draft PR番号を使い、番号がなければ番号取得用push/Draft作成の別許可を得るまで停止する。
5. 7.7の個別受理後、実承認者・承認日を記録から転記する。`history_authority: true`の`base-allowlist.json`にある同一PRの**単一未マージ記録のafter側**だけを実状態へ更新し、既受理履歴とbefore側を固定する。派生資産・archiveを追随させ、新2の同一コミットを作る。snapshot除去は全参照を調べ、未マージ・比較元に不在・参照が外れたものだけに限る。
6. 最終headと受理済み候補が一致することを検査する。候補からの逸脱、新しい認可拡張、参照/識別値の変化、検査不能があればコミットまたは先のステップへ進まず差分を再提示し、必要な受理を取り直す。PR最終headでの単一受理記録の照合は既存計画の新9にも維持する。

## 不変の境界

- 新2の製品関数は常閉。開状態fixtureの直接SQLロック試験と製品関数の常閉試験を分ける。製品open成功・復元開始関数は新5、U-S1/U-G1実経路の結合試験は新6、D4方式は別ゲート。
- 7.7-2の記録は**実際の受理が作った一つの遷移に一件**とし、承認前の候補を受理済み履歴として書かない。7.7-3の参照不能・比較不能は不合格。履歴の改変や基準の無断緩和を認めない。
- 本追補が承認されるまで現行の新2製品実装開始条件は維持する。さらに本追補の承認後も、A統合・個別資産承認・候補作成の明示許可が成立するまでは候補実装を開始しない。push・Draft作成・マージの許可は本追補に含めない。
