# U-R1 新ステップ2: 候補作成と7.7受理の順序追補案（再レビュー候補）

2026-10-15。POは正式受理前のローカル候補作成という**方針**とRG1資産5項目の**設計方針**を承認した。本追補の最終承認、具体的資産、候補実装の開始、7.7実値の正式受理は別ゲート。前候補`b0168ef9`の独立レビューP0=1/P1=1を採用し、[現行計画](plan.md)§4のPR単位・新2/9の関係だけを次のように改める。既存の[新2最小追補](step2-minimal-addendum-proposal.md)の試験境界とステップ表は変えない。

## P0の解消: 新2を独立した受理単位のPRにする

現行§4は新2〜6を同じPRの単一未マージ記録へ積み、各ステップの記録afterを更新しながら、7.7の正式受理をPR最終HEADの1回とする。この形では新2時点でそのPRの最終HEADが存在しない。**新2を独立PRの最終製品ステップ**とし、後続の新3〜9は別PRへ分ける計画変更を提案する。新2PRの変更集合を固定してから人間が**そのPRの最終候補状態を1回だけ正式受理**し、同じPRに製品operation・凍結資産・snapshot・単一受理記録を置く。新2を受理したPRには後続ステップの製品変更を追加しない。新3以降はそれぞれ実際のPR境界に対して新たなbefore・PR番号・記録を決め、過去PRの受理履歴を変更しない。

これは**計画のPR分割と開始条件の変更**であり、`base-allowlist.json`の`acceptance_unit: single_review_acceptance`、`frozen_history.py`、7.7条文を変更する案ではない。PR分割により後続PRの作成・レビュー作業は増える。新9はU-R1全体の最終検査を維持し、新2PR固有の最終HEAD・履歴照合も新2の完了条件に追加する。仮に新2PRの受理後にコード・凍結射影・比較元が変われば、最終HEADを新たな候補として再提示し、同じ記録を人間の再受理なしに更新しない。

## ローカル候補から正式反映まで

| 時点 | 許される操作・確認 | 停止点 |
| --- | --- | --- |
| A統合後のbefore固定 | `git fetch`で最新`origin/develop`、Aの統合・正式受理・実契約を確認する。専用worktreeを最新develop基点へ追随させ、7資産のrevision・digest・snapshot/blob・既受理履歴を記録する | A未統合なら実値を確定しない。beforeや既受理記録を書き換えない |
| PR番号の取得 | 新2独立PRに番号が必要。計画・作業ログだけの準備コミットをpushしてDraftを作る場合は、その**Git操作の明示許可**を得る | 許可前にpush/Draft作成しない。PR番号を仮置きしない |
| ローカル候補 | 5設計方針に対応する**正確な**DDL/JSON/必要正本を人間が個別承認し、候補作成開始を明示許可した後、許可範囲の製品・試験・凍結候補を作業ツリーに作る。before・既受理履歴・PR #72のmarkerを保持する | 候補は「受理待ち」。正式台帳へ承認者・日付を仮記入しない。snapshot算出に中間コミットが不可欠なら、その例外と対象を先に提示して停止する |
| 候補検査・提示 | DB/認可/固定登録/SQL束縛/常閉・隔離ロック試験と、候補revision/digest/snapshot・完全差分・movement_fact/reason・PR番号・独立レビュー結果を提示する。凍結履歴検査は**記録未反映に起因する不合格を予期どおりの未受理状態として記録**し、それ以外の不合格と分ける | 7.7-3の不合格をgreen/skip/保留と呼ばない。未受理のままステップコミット・push・PR公開を完了扱いしない |
| PR最終候補の正式受理 | 対象PRの変更集合とafterを固定して、7.7の**単一レビュー受理**を人間から取得する。承認者・承認日はその実記録を使う。`history_authority: true`の`base-allowlist.json`へ当該PRの受理記録1件を追記し、派生資産・archive・snapshotを整合させる | 受理がない間は台帳に記入しない。before・既受理済み履歴は不変。候補との差異があれば再提示・再受理 |
| 完了コミット・最終検査 | 製品・契約・受理記録を同一の新2ステップコミットに含める。凍結履歴/archive/契約、DB/認可、pytest/ruff/ty等の必要ゲートを**ここで緑にする**。必要なコアレビューと人間逐行確認、PR最終HEADの実状態と単一記録の照合を行う | 確認後の差分、CI赤、比較元の変化は再照合。Draft解除・mergeは別判断。後続ステップのコードをこのPRへ加えない |

ローカル候補期間の凍結履歴不合格は[7.7-3](../../development/dev-harness-design-2026-08-07.md)を緩和しない。**検査が赤い間は受入不可**であり、記録を正式反映した後の緑を新2の合格条件とする。候補中に履歴検査をskip・モック・allowlistで迂回しない。予期した履歴末尾不一致以外のエラーは候補の欠陥として修正する。

## 変えない境界

- 新2の製品2関数は常閉。隔離DBの試験用open行への直接`FOR SHARE`と製品関数の常閉拒否を分ける。製品open成功・復元開始関数は新5、U-S1/U-G1の実経路結合は新6、D4方式は別ゲート。
- TSK-550 A統合前のrevision/digest/snapshot試算は承認値にしない。A統合後の実値、正確な資産差分、正式PR番号を用いる。
- 本追補の最終承認前は承認済み計画§4が有効。A統合・具体資産承認・候補作成の明示許可・7.7正式受理・push/Draft許可・merge判断を、この順序方針や5項目の設計承認から推定しない。
