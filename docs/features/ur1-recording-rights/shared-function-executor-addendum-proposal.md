## 先行範囲と統合順

TSK-550の承認済み計画はステップ3で段階A制限関数・認可・配置、ステップ4で固定関数operationの登録経路を実装し、ステップ5以降で公開resolver等を扱う。受理済み契約は既存DMLの`OperationRegistration` / `_TenantTransaction.run`を緩めず、別の`FunctionOperationRegistration` / 同一scopeの`run_function`を設け、**最初の製品登録を段階Aの1件**とする。U-R1はこの共有実行器を複製しない。

| 順序 | 所有・PR単位の提案 | 範囲と合格条件 |
| --- | --- | --- |
| A | TSK-550担当が現行ステップ3・4を先行PRとして所有 | 段階A制限関数と必要なDDL/ACL、sealed固定関数登録、同一scopeの`run_function`、起動時の関数identity/固定SQL/bind/戻り値検査、DMLとのID・型衝突拒否、scope失効/偽造token/任意SQL/Session拒否。**段階Aの1件を最初の製品登録**として実DB試験。ステップ3・4は各1コミット、7.7は先行PRの最終headで1受理単位とする |
| B | U-R1担当がA統合後のdevelopを基点に別PR | 新ステップ2のRG1専用`RG1PrecheckToken` / `RG1CommitCheckToken`と対応する固定関数2件、RG1だけのDDL/認可/分類/凍結契約、起動時既定閉鎖とDB競合試験。U-S1 PortWriter実接合はU-R1新ステップ6。7.7はBの最終headで別受理単位とする |

この案はTSK-550の**ステップ3→4順序と最初の段階A登録を維持**し、既存計画の「1 PR」を「先行ステップ3・4のPR + 後続ステップのPR」に改める必要がある。中間コミットを7.7受理済みheadと扱わない。Aの製品関数登録0件だけを先に別PRへ出す旧案は撤回する。

**TSK-550担当に求める受理**: (1) ステップ3・4を先行PRとして統合できるか、(2) 所有worktree・PR・各コミットの担当、(3) 後続ステップ5以降との共有ファイル所有と統合順、(4) 先行PR最終headでの7.7受理単位を「受理／修正が必要／PO裁定が必要」で回答すること。不可なら現行の1 PRでステップ4まで統合後にU-R1が続く代案とし、TSK-550全体の完了は待たない。

**必要なゲート**: 先行PRへの分割はTSK-550担当の正式計画追補、コア計画の独立査読、人間承認が要る。TSK-550先行PRとU-R1 PRのDDL・認可・repository契約・派生資産・7.7履歴はそれぞれの実差分で個別承認する。実revision/digestは先行PR統合後の基線から計算する。受理済み履歴や他担当worktreeは変更しない。
