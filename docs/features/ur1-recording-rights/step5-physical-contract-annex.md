# U-R1 新5の物理契約差分案（2026-10-18）

**状態: 判断候補。製品コード・DDL・認可・凍結資産の変更許可ではない。** [承認済み計画](plan.md)のステップ表は維持する。[一枚判断資料](step5-decision-sheet.md)の未決部分だけを具体化する。POは 2026-10-18 に、D4を業務DBの復元範囲外・別故障領域の専用PostgreSQL primary＋同期standbyで保全し、旧primaryをフェンスし、耐久性を証明できなければ新規発行を停止する**設計方針**を採用した。実配置、運用責任、有料資源、以下の物理契約は未承認。

## 1. 正本・現物との差分

| 契約 | 現行の確定事項・実装 | この候補で追加する事項 |
| --- | --- | --- |
| V12 | sync-protocol 2-1 のVF1〜VF6。現D4・現復旧世代・保持端末の結合。進行中P3まで必須、終了後P3は不要。現行世代行に照合値なし | 発行・検証値・応答消失後の同一値再交付・失効の物理方式 |
| 端末 | `recording_generations.holder_device` はある。認証の `verify_tenant_id` はtenantと期限しか返さず、`TenantContext`にも端末はない | 端末資格の発行、認証との結合、製品内部まで検証結果を運ぶ型と保存先 |
| 復旧世代 | sync-protocolは復元ごとの非再利用と旧要求拒否を要求。RG1行は`singleton_id,state`だけ | 復元外の発行源、業務DB側の比較値、照合時点と台帳障害時の停止範囲 |
| U-S1 Port | `holds_recording_right(game_id,d4,v12,writer)`に端末引数がない。`PortWriter`も端末を持たない | 検証済み端末を同期の照合位置へ届ける最小の署名変更。U-S1受理待ち |
| U-G1 開始 | 同一tenant scopeで開始と初期付与を確定する意味は受理済み。開始HTTPの実装はU-G1 | 再送識別、具体DTO、失敗型、外部予約位置と全ロック順。U-G1受理待ち |

この追加は既存の意味契約を弱めない。正本本文を物理方式に合わせて変える必要があるかは7.6で判定する。特に復旧世代の毎書込照合を採る場合は停止範囲の変化を正本・計画へ明示してから確定する。

## 2. V12: 応答消失でも同じ権利を再取得する候補

**推奨A: サーバー発行値の暗号化再交付。** U-R1が暗号学的乱数256 bitのV12を生成し、世代行には`SHA-256(V12)`の32 byteだけを置く。照合はdigestを一定時間比較し、同じscopeで試合・現D4・現復旧世代・有効な保持端末を必ず再照合する。V12原文はイベント・監査表・アクセスログ・例外・SQL束縛値ログへ記録しない。端末は暗号化されたローカル永続領域へ保存し、再同期で提示する。端末内保存手段はTSK-506/クライアント担当の受理待ち。

再交付に必要な原文だけを、業務DBの**同じ開始transaction**内でアプリ管理のAEAD鍵により暗号化して保存する候補とする。候補表`recording_right_deliveries`は`tenant_id,game_id,generation,start_request_id,device_id,key_id,nonce,ciphertext,revoked_at`を持ち、`(tenant_id,game_id,start_request_id)`を一意にする。世代行には`v12_digest BYTEA NOT NULL`と`recovery_generation BIGINT NOT NULL`を追加する候補。暗号鍵は業務DBとは別の秘密管理境界に置き、業務DBやrepository契約へ原文・鍵を保存しない。鍵の実保管先、運用者、ローテーション・保持期間は未指定であり、決定前に製品正常系を確定しない。行は物理削除せず、失効時は`revoked_at`を立てる。保管期間と旧鍵の廃止条件は別途承認を要する。

U-G1は開始要求にサーバーが検証する`start_request_id: UUID`を持たせる候補。端末は要求送信前にこのIDを永続化し、同一開始の再試行では同じIDを送る。最初の開始がcommit済みでHTTP応答だけ失われたときは、**同じテナント・認証済み端末・start_request_id・現世代/復旧世代で、deliveryが未失効**なら同じV12を復号して返す。新D4を予約しない。IDだけ、別端末、別要求、失効済み権利では返さない。二重要求の同時実行は試合行のロックと一意制約で直列化する。鍵欠損・復号失敗・状態不明は秘密値を再生成せず閉鎖失敗とし、明示的な引き継ぎ/復旧経路へ送る。

外部台帳のD4予約は業務DBのcommitと原子的でない。予約の応答が不明なら台帳の同じ予約IDを照会し、成功/未成功を証明できるまで新予約へ進まない。**業務DBが取消された予約D4は消費済みのまま**とする。同じ`start_request_id`による新たな試行は別の予約attempt IDを採り、旧D4を再挿入しない。応答消失の「commit済み再交付」と「rollback済み再試行」をDBの実状態で区別する。

**選択肢B: 再交付せず、明示的な引き継ぎで新D4/V12を発行。** 暗号化保管と鍵管理は不要だが、応答消失だけで引き継ぎ工程が必要になり、RG1中やD4台帳停止時は回復できない。MVPで安全な再取得を求める今回の条件に対してAを推奨する。Aの鍵・保管先・寿命を仮決めしない。

## 3. 信頼済み端末ID: 発行と偽装拒否の候補

**推奨: 認証済みチームセッションに結合したサーバー発行の端末資格。** 認証境界がランダムな端末資格と不変の`device_id: UUID`を発行し、保存先の候補`trusted_devices(tenant_id,device_id,credential_digest,revoked_at,...)`にdigestだけを置く。提示された資格とチーム認証cookieのtenantを同時検証し、該当tenantの有効行を読み、`VerifiedDeviceContext(tenant_id,device_id,auth_session_binding)`を内部で発行する。要求body・任意headerの裸の端末ID、U-G1の文字列引数、D4/V12だけからの端末推定は信頼しない。U-R1 operationは同一tenant scope内で有効資格のDB行を再照合し、内部token直接呼出しでも偽装値を拒否する。型だけを信頼境界にしない。

再ログイン時は同じ端末資格と新しいチーム認証の両方を確認する。紛失/変更は旧端末資格を失効し、明示的な通常・緊急引き継ぎで新D4/V12と新holderを作る。旧V12・旧端末資格はその直後から拒否する。単なる「同一チームの別端末」は保持端末にならない。端末資格と認証cookieを共に複製された場合の耐性はこの方式だけでは証明できない。秘密鍵による端末の所有証明を要するなら、WebCrypto等の追加クライアント契約・正本/資産ゲートが必要な別案となる。

**担当境界の未受理**: 認証/TSK-506側が端末資格の発行・検証・HTTPからの導出を持つか、U-R1が永続行と検証operationだけ持つかを項目別に確定する。U-G1は検証済み文脈だけを開始へ渡す。U-S1はP1/P2/P4と進行中P3のV12照合時に検証済み端末をPortへ渡す。終了後P3にはV12/端末を要求しない。保存済みD5の再掲は同期正本のD1分岐を維持し、新資格の有無で保存結果を書き換えない。資格失効時の既保存結果の閲覧可否は入口の認可契約としてTSK-506が受理する。

## 4. 復旧世代: 非再利用と停止範囲の選択

外部D4台帳に**D4とは別の単調な正の`bigint`復旧世代系列**を置き、発行結果を両保全先へ耐久記録する候補。業務DBにはRG1 singleton行の`recovery_generation`列と各記録権世代の同名列を置く。wireは不透明な文字列とし、D4の数値順や試合内`issuance_order`と混ぜない。新5開始時は外部の現復旧世代とRG1側が一致し、RG1が開いている場合だけ初期世代へ束縛する。復元では通常書込を閉じ、外部で新しい復旧世代を耐久発行してから、失効/回収を終え、新7の解除・新D4開始を不可分にする。旧backup内の値を現値として採用しない。復元開始・製品openの実装は新7に残す。

| 選択 | 照合点・停止範囲 | 推奨 |
| --- | --- | --- |
| A: 通常書込のコミット直前にも外部現値を照合 | 台帳現値が不明/不一致ならRG1を閉じているものとして、試合作成・開始・同期・通常引き継ぎ・状態変更内部ジョブを全取消する。発行台帳の故障が**既存世代の書込も停止**させる。復元の証明は強いが、既存の「D4障害だけなら既存世代の書込継続」という一枚資料の候補から停止範囲が拡大する。外部現値の読取とRG1ロックとの競合直列化方式はU-S1/U-G1の受理とDB試験が必要 | **安全優先の推奨**。停止範囲変更を7.6・PO判断へ明示する。外部読取だけでは途中のepoch切替に対する原子性を保証しないため、復元制御側の閉鎖・フェンスを先に確定する |
| B: 管理された復元停止と起動/再接続時だけ外部照合 | 台帳単独障害でも既存書込を継続できるが、稼働中の業務DBを外から復元する操作や検査を迂回した再接続を禁止し、運用・起動フェンスの実証が必須。証明できなければ通常書込を全停止 | 可用性重視の代案。厳格な復元手順・担当・起動条件の承認なしにAと同等の保証と扱わない |

どちらも外部現値が不明・不一致のまま新D4を発行しない。RG1新4の製品関数は常閉であり、試験fixtureの開状態を運用open承認に転用しない。A/Bいずれでも新5の隔離試験は可能だが、製品の通常成功を運用で実現するには配置・復元手順・新7が別に必要。

## 5. 担当へ提示する公開契約とロック順（未回答は未受理）

候補署名は`issue_initial_recording_right(scope, *, game_id: UUID, verified_device: VerifiedDeviceContext, start_request_id: UUID) -> InitialRecordingRight`。内部operationであり、HTTPの公開書込APIをU-R1に増やさない。DTO候補は`game_id: UUID, generation: int, issuance_order: int, holder_device_id: UUID, recovery_generation: str, recording_right_proof: str`。D4は内部`bigint`、wireは不透明文字列。V12はcommit成功後の同端末への応答だけへ露出し、ログ・通常一覧へ載せない。具体的な初回`issuance_order`、DTO名、HTTP statusはU-G1/U-S1受理待ち。

| 結果分類 | U-R1内部結果の候補 | U-G1 HTTP / U-S1同期側の判断 |
| --- | --- | --- |
| 新規成功 | 1世代を挿入、D3/適用prefix=0。業務scopeはU-G1だけがcommit | 開始+両側スタメン+U-M2記憶+初期権+deliveryを一括確定。返却前にcommit成功を確認 |
| 同一開始の応答消失 | 同じ要求ID・同じ有効端末・現世代なら既存deliveryを再交付。D4追加なし | U-G1が再交付入口・結果を受理するまでHTTP仕様未確定 |
| 越境・欠損・二重開始・別端末 | 成功なし。越境で試合/権利の存在を漏らさない | 404/409等の具体写像はU-G1未回答 |
| RG1閉鎖/不明、台帳/鍵/復旧世代不明 | fail-closed、業務scope全取消。予約済みD4だけ消費済み | RG1はB7、進行中P3はB10、同期ではD5未消費。開始HTTPのstatusと再試行可否はU-G1未回答 |
| U-S1のV12・端末不一致 | 旧世代・別端末・digest不一致を拒否 | P1/P2/P4はB4、進行中P3はB9、終了後P3はV12不要。実Portは新8 |

**候補の全順**: 認証・テナント/端末資格検証 → RG1非ロック事前読取 → 対象試合の権限を非ロック読取 → 外部D4予約と復旧世代の事前確認（この時点で業務DBの行ロックは持たない） → **外部復旧世代行の共有fence取得 → そのロック下で外部現値を読み業務DB内の世代と照合** → 同一業務scopeで試合行`FOR UPDATE` → 双方チーム行をUUID昇順 → 対象選手行をUUID昇順 → U-M2記憶のロック/保存 → 現世代行の照合/初期INSERT → delivery行の一意照合/保存 → RG1行`FOR SHARE NOWAIT`と復旧世代の再照合 → 業務DBのcommit/rollback結果確定まで外部fenceと業務DBロックを保持。**外部fence前の読取は最終判定に使わない**。認可・試合状態・端末資格・RG1はロック取得後に**同じ確定値で再照合**する。予約後に不適合が見つかればD4を消費して業務DBは全取消。外部D4台帳の予約トランザクションは業務DBの行ロックを保持したまま待たない。U-M2の実ロック順（チーム→選手UUID昇順）とU-S1のゲーム→世代は維持する。復元開始はRG1閉鎖を先に確定してから外部世代を排他更新し、外部共有fenceを待つ同一transactionで試合・世代行を取りに行かない。両チーム・記憶・deliveryを含む順序と再照合位置、同期/復元経路との逆順がないことはU-G1/U-S1の**項目別受理待ち**であり、ここで確定しない。

**U-S1への最小差分**: 現Portは検証済み端末を受けない。P1/P2/P4・進行中P3の未保存イベントの`holds_recording_right`呼出しへ`VerifiedDeviceContext`を渡すか、同一scopeの固定取得operationで検証済み値を読み出す必要がある。TSK-506はHTTPで端末資格を検証してU-S1核へ渡す。Port実装・登録はU-R1新8で提供する。終了後P3およびD1の保存済みD5再掲は既存正本に従う。署名・呼出位置・失敗写像はU-S1受理待ちで、仮Portを製品実装としない。

## 7. 読取だけの配置調査と次の承認単位

`docker-compose.yml`の`db`と`product-rls-db`は同じ開発compose内の独立した単体サービスで、同期standbyでも別故障領域でもない。`docs/ops/deployment.md`は実配備先確認を未実施としている。現在のローカルDocker contextに見えるコンテナは隔離試験用途で、実配置の提供証拠にならない。既存権限で見える範囲には転用可能な2配置先・提供者・運用当番・単価/日程の証拠がない。実配備先・接続資格情報を推定しない。

**最小計画追補案**: 新5の着手条件を「D4設計方針採用済み」と「V12/端末/復旧世代/開始Port契約と、必要な正本・具体資産の個別承認」に分ける。ステップ表は変えず、新5の隔離実装・試験は実配置前に先行できると明記する。ただし運用成功/安全なopenは新7と実配置・復旧演習を要する。新8の本物のPort・実入口結合は移動しない。承認後、正本7.6判定→必要な7.3→exact DDL/JSON/認可/7.7提示→新5製品候補/隔離DB試験→独立レビュー/本人逐行確認の順で進む。

**一括で必要な人間判断**: (1) V12の暗号化再交付と鍵/保持/端末保存の管理責任、(2) 端末資格の発行・検証・失効の所有、(3) 復旧世代照合A/Bと台帳障害時の通常書込停止範囲、(4) U-G1/U-S1の候補署名・DTO・失敗・全ロック順の項目別受理、(5) 隔離実装を許す最小追補とexact資産候補化の許可。配置候補・運用責任・見積日程・有料資源利用・運用open・共有DB適用は別判断。担当未回答は受理済みとしない。
