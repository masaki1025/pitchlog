# 実装計画書: U-R1 記録権核

## 1. 背景・目的

[TSK-392](https://app.notion.com/p/3da93b75e6878176a132ee9f25e9430a) は帯1・FR-013 主所有、U-S1 依存、着手可。初期付与、世代更新とフェンシング、通常・緊急引き継ぎ、退避経路を実装する。正本は [FR-013](../../requirements/requirements-pitchlog-2026-07-22.md#fr-013)、[data-model 5-3・6-1](../../design/data-model.md)、[sync-protocol 6-2・9-5](../../design/sync-protocol.md)。当初の基点は PR #126 統合後の `origin/develop` `157cd858`。2026-10-14 の実装前再照合で最新 `origin/develop` `c0ad63e0` を fast-forward 取り込み済み。U-R1 の既存 worktree・進行中 PR・別担当着手は見つからなかった。他担当の U-S1/U-G1 worktree は読取のみ。

## 2. スコープ

### やること

- U-G1 の開始 transaction から呼べる初期記録権付与 operation と現世代・保持端末の判定。
- 保持端末・世代・確定水位の比較に基づく通常引き継ぎ、警告確認を伴う緊急引き継ぎ、旧世代フェンス、並行要求の後発拒否。
- 旧世代イベントを適用・物理削除せず退避し、管理者が対象を指定して閲覧・書き出す Must 経路。管理者用の制限関数と実利用入口の所有をステップ1で確定する。
- RG1 の事前停止とコミット直前再確認を、U-G1 の作成・開始を含む通常書き込みと U-S1 の同期に接続する。復元調整の起動時 fail-closed、回収・退避、解除と新 D4 の不可分性も扱う。

### やらないこと

| 対象 | 所有・理由 |
| --- | --- |
| 試合作成・スタメン確定・開始 HTTP | U-G1。U-R1 は内部 operation を提供する |
| D1/D3 イベント適用・D5 判定・終了イベント、P4/T8 の唯一の書き手 | U-S1 と同期入口。U-R1 は本物の `RecordingRightsPort` を登録し、T8 との接合を検証する |
| 状態計算・スタメン記憶 | U-X1・U-M2 |
| 退避イベントの取り込み（Should） | FR-013 Must の退避・閲覧・書き出しと分離 |
| D4/V12/保持端末/復旧世代の仮値 | 担当受理と必要なゲートまで製品へ入れない |

## 4. 実装方針

**コア領域**。記録権・同期プロトコル・テナント分離へ重複帰属。計画は敵対レビューと人間承認、実装 PR は独立敵対レビューと人間逐行確認を経る。既存 `recording_generations` の `(tenant_id, game_id, generation)`、通常現世代の部分一意、試合内発行順一意、D3 初期 0 と後退禁止を使う。D4 値順は発行順ではない。

### U-S1・U-G1 接続の受理判定

| 提示事項 | 判定 | 根拠・残る確認 |
| --- | --- | --- |
| 初期権は試合開始時に付与 | **意味として受理** | FR-013 と一致。`preparing` 作成では発行せず U-G1 開始 operation の同一 transaction から呼ぶ。物理発行方式・返却 DTO は未確定 |
| `games` 行→記録権世代行の順でロック | **U-S1 の承認済み R-16 を受理** | U-S1 design 3 節は認可・試合存在確認後、イベント transaction の冒頭で全 P1〜P5 に適用と明記。U-R1 の付与・引き継ぎも同順。U-S1 実コードとの結合検査は未了 |
| RG1 中の通常書き込み・内部ジョブ・通常/緊急引き継ぎ停止 | **正本どおり受理** | sync-protocol 9-5: 認可後・D5 前、B7/B10、D5 非消費、コミット直前再検証、起動時 fail-closed、解除と新 D4 の不可分。状態読取・直列化点は担当確認待ち |

U-G1 に必要な最小 U-R1 成果は、**開始 transaction に参加する初期付与 operation、作成・開始の双方から使う RG1 判定とコミット直前再検証、ゲーム行→世代行の取得順、発行結果契約、失敗時全取消**。作成中の RG1 停止では試合行も残さない。U-G1 は HTTP・スタメン・試合状態を所有する。U-X1 の規則解決と紅白戦側識別は別依存として残る。

**未確定**: D4 のロールバック後非再利用を満たす採番源、V12 の物理形式・発行/検証/失効、保持端末識別子、復旧世代の読取/更新と返却形、RG1 状態の直列化点、管理者入口と復旧制御面の実所有。正本の値域だけから具体値を作らない。担当受理、R-17 正本改訂の確定・統合、必要な凍結契約ゲートを該当実装ステップの開始条件とする。

**ステップ単位の凍結受理**: ステップ 1 の計画・契約準備だけで Draft PR を作り、正式な PR 番号を取得する（この手続自体は計画承認後の別の実行指示を要する）。新ステップ 2～6 で DB operation/SQL 許可を増やすときは、各ステップの同じコミットに repository capability/token、許可シンボル、生成物、一致試験、snapshot と**同じ PR 番号の単一未マージ受理記録の after 側**を含める。before 側と既存受理済み履歴は固定し、after 側はその時点の実状態から再計算する。snapshot を取り除く前に archive と全資産の参照を確認し、after の更新で参照が外れた **未マージかつ比較元に存在しない snapshot** だけを同じステップコミットで取り除く。受理済み履歴、before が参照する snapshot、比較元にある snapshot は保持する。各ステップの候補差分を人間へ示し、実際に承認された候補だけについて承認者・日時を実記録から転記する。未承認候補を承認済みとして書かない。ステップごとに凍結履歴・archive・契約検査を緑にし、検査不能ならコミット前に止める。**7.7 の正式受理単位は中間コミットではなく、この PR の最終 head への 1 回のレビュー受理**とし、新ステップ 9 で単一記録の after を最終 head と照合する。候補範囲が承認を超えれば別途承認を受ける。

### ステップ 1 の接続契約再提示と D4 方式候補

[connection-contract.md](connection-contract.md) 2・3 節の RG1 初版案は、事前から状態行の共有ロックを保持すると事前通過後の移行をコミット直前で検出する競合を作れないため**修正が必要**と判定した。作成側には `read_rg1_open`（認可後の非ロック読取）と `assert_rg1_open_before_commit`（同一 scope のコミット直前に共有ロックして再読）を別 operation として提示。状態不明・欠損・読取失敗・調整中は B7 相当で全取消。開始時 D4/V12 とは分けて U-G1 に受理を依頼した（Notion コメント `3f993b75-e687-8150-bae2-001df35c2b52`）。U-S1 には ③-a/⑧、R-16 とのロック順、P3 の B10 を別途照合依頼した（`3f993b75-e687-812c-b0ca-001db583d32e`）。**担当返信は未確認**であり、項目別受理を代記しない。

D4 非再利用は業務 DB の復元範囲外の耐久的な原子予約台帳を**推奨候補**とする。予約失敗・取消後も番号を戻さず、業務 DB の snapshot 復元前に通常経路を止め、台帳 epoch との不一致は fail-closed、RG1 中の回収・退避後に非再利用 D4 と復旧世代を確保して解除と新世代開始を不可分に行う。必要資産、バックアップ復元手順、障害時、別 DB/クラスタと乱数 nonce の代替案を同書 5 節に示した。**依頼者は外部台帳の現時点での採用を承認していない**。別ホスト・別保全の候補を含む短い比較は接続契約 5 節に追記した。D4 自体の単調性は正本要件ではなく、単調なのは試合内発行順列。方式の採用は PO・7.6/7.7・認可ゲート待ち。RG1 の安全な状態読取は `preparing` 作成にも必要だが、D4 予約 API は不要。台帳と RG1 epoch を共通にする場合の可用性上の結合は PO 裁定候補。#132 の共有凍結資産は変更しない。

**作成側 RG1 の優先確認**: 使い捨て PostgreSQL 17 の二接続で、事前読取後に復元開始の状態更新が先に確定すると直前の `FOR SHARE` 再検査が拒否し、挿入済み試合行が 0 件に rollback されることを実測した。作成側の共有ロックが先なら復元開始の更新は作成 commit まで待機した。これは DB ロック機構の確認であり、U-G1 実経路の項目別受理・結合試験ではない。U-G1 へ Notion コメント `3f993b75-e687-8128-99ee-001ddb5005af` で、二段階 operation、B7 相当、全取消、開始側 D4 契約との分離について受理を再依頼した。担当の返信は未確認。D4 の裁定を preparing 作成側受理の条件にしない。
