## 4. 実装方針

### 重さ分類の根拠 — **コア領域**

**同期プロトコル**(設計書 6.3)。ADR-001 により **`sol` / effort `xhigh`** を自動適用。**敵対レビュー必須・人間の逐行確認必須**。
**design.md は作らない**(4 章の内容は正本にあり、本書へ再掲しない — H-44)。

### 設計の中核判断

| # | 判断 | 根拠 |
| --- | --- | --- |
| **1** | **スロットの型は `unknown`。物理型を 1 つも選ばない。値の形式(長さ・文字種・UUID らしさ)を検査しない。** 例外は正本が構造を決めた **V5** と **V10(3 要素の合成)** のみ | 正本 `:222`「型・NULL 性は決めない」/ (B) 論点 17・26 は D5 の長さと D2 の数値型を未決のまま実装計画と TSK-250 へ送っている。**形式検査を入れると D5 の形式を実質決定してしまう**(P1-6) |
| **2** | **種別ごとの判別可能 union を作らない。** 封筒は単一形、**必須性は表引き** | `:433-436`(**P-58** — 採用状態は集合の要素の有無で表し、種別ごとの分岐を構造の前提にしない) |
| **3** | **ID は正本 ID をそのまま使う**(`'V9'`・`'8'`)。英語スラグは表の注記に留め、**ロジックから参照しない** | 英語スラグを ID にすると「正本 ID ↔ 英語名」の**第二の正本**ができる(**H-61**)。**2-3 の別名問題を翻訳ごと持ち込まない**(P1-5) |
| **4** | **ID リテラルの locus を 1 ファイルずつに限定**し、raw 走査で機械検査する | **H-78**(規則は 1 箇所へ集約し、残存を検出する機械検査を別に置く) |
| **5** | **オラクルのパーサは未知トークンで fail-closed に落ちる** | 期待集合は JSON 側からだけ来る(裁定 3)。**v0.2 が正本語を変えると red になり手戻りが顕在化する** |
| **6** | **V8 は不透明ペイロードとして「存在すること」だけを検査する** | V8 の中身は**状況判定(NFR-018 の対象計算)の出力**(`:259`・ADR-003 D-6)。踏み込むと **P0** |
| **7** | **単一の規則表から `EventSlotId`(V1〜V11)と `RequestOnlyId`(V12)を導出**し、**封筒は前者だけ**を受け付ける | V12 は**要求レベル**であり、復旧世代とともに**イベント値ではない**(`:263`・`:344`)。型レベルで分離しないと「V12 を封筒に置けない」を機械で言えない(P1-2) |
| **8** | **文脈依存の必須性は注入した resolver で解く。** `#9 改訂版` は**元イベントの参加区分を継承**するため、元の参加区分と取消可能性を返す resolver を検査器へ注入する。**本タスクは resolver の入出力契約だけを定義し、キューや永続化は持ち込まない** | `:583`(改訂版は元イベントの参加区分を継承する)。2 表の総称ループだけでは #9 の V6 要否が決まらない(P1-1) |

**本実装の TypeScript 型は、正本の型決定ではない。** (B) 論点 17・18・26 は判断 1 によりいずれも選ばない。TSK-250 が物理型を決めた時点で追随する。
