## 4. 実装方針

**重さ分類 = コア領域の根拠**: 裁定対象に同期プロトコル(B-5・B-6)・テナント分離(B-4)・データ移行の隣接(A-10・A-11)を含む文書判断であり、文書のみのタスクでもコア領域該当となった TSK-226 と同型(「文書タスクだから」は分類を落とす根拠にならない — `docs/features/legacy-frontend-coverage/plan.md:114`、運用評価台帳 H-12 再発補記 `docs/development/harness-evaluation.md:66`)。

**機構が発火しない点と代替統制(H-12)**: 本タスクは `.claude/core-areas.json` の paths を変更しないため CI の core-guard は発火しない。代替統制は次の 4 点を**ステップ・合格条件に落として**適用する:

1. **計画・成果物の両方を敵対レビューに掛ける** — 計画書(本書・実施中)と、**ステップ 7 で成果物**(裁定結果表 20 行・開発運用系の反映・後続タスクへの合流補記)。**台帳 v1.2 はステップ 4 の /finalize-doc の敵対レビューが担い、ステップ 7 の対象外**(approved 後の再レビューは新版ゲートを要するため二重に掛けない)。指摘反映後に収束確認周を回し、**最終周 P0/P1 = 0 で収束**させる
2. **人間の逐行確認** — 対象は **裁定結果表の全 20 行**(裁定・正本化先・ゲート・合流先)と**台帳 v1.2 の追記全行**。ステップ 2(裁定セッション自体が逐行確認を兼ねる)とステップ 4(/finalize-doc の人間承認)で実施し、worklog に実施記録を残す
3. **必須チェック行の手動付与** — /pr で PR 本文に必須チェック行(文言の正 = `scripts/core_guard.py` の REQUIRED_CHECK_TEXT)+ 設計書 6.3 の実施記録行(`対象=/範囲=/方法=`)を手動で置く
4. **典拠の照合可能化** — 裁定結果表の各行に decision-sheet の行 ID と正本化先のアンカー(ファイル・節 or 行)を付け、レビュー側が機械的に照合できる形にする

方針の骨子(PO 確認済み 3 点 — 2026-09-02):

1. **裁定方式** = 推奨一括 + 争点のみ対話。争点は B-1(個人アカウント — 全面踏襲の射程解釈)・B-2(公式記録レビュー表示)・群 A の明文化要否(要件化 = 7.3 ゲート案件になるため 1 行ずつ確認)。**B-2 は二段階で裁定する**: ①表示のみ踏襲 / 破棄、②(①が踏襲なら)REQ:91 の Won't を撤回するか限定改訂するかの要否 — 2 項目を裁定結果表に別項目で記録する。送り先版番号は繰り下げ済みで「v2.1」表記の読み替えが必要(research.md §5)
2. **正本化範囲** = 改善台帳・開発運用系は本タスクで完結、要件書系は割り当てと起票まで。**全 20 行の裁定は次のいずれかに終着させる**(worklog のみを終着にしない — 7.6-4): (a) 既存正本の具体的アンカーが既に裁定内容を支えている(行 ID とアンカーを対で記録) / (b) 本タスクの PR 内で正本へ反映 / (c) **正本パス・節・ゲートを DoD に持つ起票済み後続タスク**へ割り当て
3. **dd03160 照合** = 裁定前に 3 点のみ(理由と各点の裁定への影響は research.md §6)。**照合結果が「確認不能」の行は、その旨を PO 提示資料に明示し、「条件付き裁定」(事実の確定を合流先タスクまたは実装タスクの DoD に含め、事実が覆った場合の再裁定条件を付す)として必ず裁定する — 保留(未裁定)経路は置かない**(DoD 1 点目「全行を PO が裁定」と整合させる)。B-8 は照合結果次第で裁定事項自体が変わり得るため、変わった場合は提示資料の行を書き換えてから裁定する

**PO 提示資料には research.md で判明した既知のずれを反映してから提示する**: A-4 の典拠ずれ(REQ:1062 → 1066)・A-9 の「FR-028 は分析画面からの編集のみを規定」という解釈相違(正: 経路を未規定)・A-2 の項目名脱落(「出典」)・B-4 の根拠補強(REQ:636 ほか)— research.md §1・§4・§6。

**逸脱条件(実装を止めて計画改訂 + PO 裁定に戻すケース)**:
- 裁定の結果、**要件書の実改訂**が本タスクのスコープに入る場合
- 裁定が**絶対規則・現行正本と矛盾**する場合(例: B-3 で裁定優先 = 物理削除を選ぶ — AGENTS.md 絶対規則・4.0-2 と衝突)
- **正本化先・ゲートの割り当てが 3 節の宣言から変わる**場合(例: A-1 で版固定ディレクトリの新設を選ぶ — 開発文書の構造変更となり 7.6-3 後段へ繰り上がる)

裁定・正本化の判断材料はすべて [research.md](research.md) に集約済み(§2 正本化先とゲートの決定表 / §3 群 B の裁定材料 / §4 群 A の受け皿 / §5 Won't 衝突 3 件 / §6 旧実装事実の検証)。A-5 を TSK-306 へ合流する場合は「再割当機能が G-2〔対象キー・略号の未定義〕の射程外に落ちないか」を合流補記に明記する(§4)。
