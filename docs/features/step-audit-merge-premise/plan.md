# 実装計画書: ステップ履歴監査が develop で必ず赤になる問題の是正

## Context — なぜやるか

PR #74(TSK-235)をマージした直後、**develop の `consistency` ジョブが赤になった**。

```
tests/test_step_history_audit.py::test_real_repository_artifacts_exist_at_each_completed_step_commit
AuditViolation: 実装ステップコミットを第一親履歴から取得できない   (:500)
```

**PR では緑で、マージした瞬間に真偽が反転する。** TSK-440 / TSK-460 で直したのと同じ家族だが、
**直し方が違う型**である(下記「2 つの型」)。

- `consistency` は**必須チェックではない**(実機 ruleset `protect-main-develop` の必須 10 件に
  `consistency` と `mutation` は含まれない — 本セッションと TSK-448 が独立に実測)
- → **誰のマージもブロックされない。** 実害は **CI の赤が出続け、レビューする人が別の問題と
  誤認する**こと

## 原因(実測 2026-10-03)

### 直接の原因

`_implementation_commits`(`tests/test_step_history_audit.py:437`)が
`git log --first-parent {base_ref}..{selected_head}` でステップコミットを集め、
**`:500` の `if not records:` で 0 件を違反**とする。`base_ref` の既定は **`origin/develop`**。

**develop 上では HEAD == origin/develop なので範囲が空**になり、必ず 0 件になる。

| | 実測 |
| --- | --- |
| develop の第一親履歴のステップコミット | **0 件** |
| 全履歴なら | **816 件** |

### より広い原因

```
STEPS_PATH = ROOT / "docs/features/domain-calc-dsl/steps.json"   (:27)
```

**この検査は TSK-235 の feature 固有のステップ台帳に束縛されているのに、
全ブランチと develop で走る。** したがって develop だけでなく、
**ステップコミットを持たないブランチ(計画段階・他 feature・本修正ブランチ自身)でも落ちる。**

### 2 つの型(台帳の分類に提案済み)

| | 中身 | 直し方 |
| --- | --- | --- |
| (a) 比較元が動く | `merge_base(origin/develop, HEAD)` などの可変参照 → マージで差分が空 | **比較元の固定**(TSK-460 がアンカーを資産へ宣言) |
| **(b) 母集団が空になる** | 比較元は固定なのに、その上に立つと範囲が空(**本件**) | **「対象が無い」と「対象があるのに不足」を分ける** |

**TSK-460 で (a) を直した直後に (b) を入れた。** 「アンカーを固定したから大丈夫」は成り立たない。

## 方針(2026-10-03 改訂 — 敵対レビュー 1 周目の P1 2 件を反映)

**「審査対象が存在しない状況を違反と呼ぶのが誤り」という芯は変えない。**
**ただし「対象が存在しない」の判定を改める。**

### 初版の誤りと、なぜ崩れたか

初版は「**範囲に実装ステップコミットが無いとき**」を「対象なし」とした。**2 つの理由で成立しない。**

**(1) 無記法の実装コミットが素通りする(P1-2)。** `:478` の抽出は記法に一致しない件名を
**読み飛ばす**。したがって「対象 feature のコードを記法なしでコミットした」場合も 0 件になり、
早期 return で緑になる。**従来は `:500` で赤だった。**
初版の「失うものは無い」という根拠(`feature_status.py` がコミットから導出するので
主張と実体が食い違う状態を作れない)は**原典と一致しない** — `scripts/feature_status.py:981` は
その場合を「実装前」ではなく **`kind="unknown"` / `note="無記法の実装コミット混在"`** と判定し、
**この検査の失敗を代替しない。**

**(2) 本タスク自身の PR が赤になる(P1-1)。** 監査は範囲内のステップ記法を
**feature 名で絞らず**収集し、`/N` を **`domain-calc-dsl` の台帳(total=60)**と照合する
(`:27` の `STEPS_PATH`)。本タスクが `(ステップ k/3)` でコミットすると、
**別 feature の総数検査に入って赤になる。**
さらに `tests/test_step_history_audit.py` は **`domain-calc-dsl` の宣言済み artifact** である
(`steps.json` の artifact 60 件に含まれる・実測)。**artifact で絞る案も本タスクを救わない。**

→ **申し送り 1(feature への束縛)は先送りできない。本タスクの範囲に含める。**

### 改訂後の設計

**監査は「このブランチが当該 feature を実装している」ときにだけ適用する。**

判定は **feature 側の計画書の `branch:` 宣言**で行う。`/task-start` が設定し
`codex_run.py` も読む既存の欄である。

**★ 宣言は比較元(`origin/develop`)側から読む(2 周目 P1-1)。**
HEAD 側から読むと、**同じ PR で `branch:` を書き換えるだけで自分の監査を無効化できる**。

```
declared_base = git show origin/develop:docs/features/domain-calc-dsl/plan.md の branch:
declared_head = HEAD 側の同じ欄
current       = PR イベントの head.ref(PR 外は git rev-parse --abbrev-ref HEAD)

declared_head != declared_base          → 違反(宣言の書き換えそのものを赤にする)
current == declared_base                → 監査する(従来どおり全判定)
それ以外                                 → 対象外(監査しない)
```

**宣言の食い違い自体を失敗にする**ので、書き換えによる迂回が成立しない。
**比較元側の値は PR からは変えられない。**

| 状況 | 判定 | 根拠 |
| --- | --- | --- |
| **develop** | 対象外 | ブランチが比較元の宣言と一致しない |
| **`feature/domain-calc-dsl`** | **対象。従来どおり全判定**(0 件なら赤のまま) | 一致する |
| 他 feature のブランチ(**本タスクを含む**) | 対象外 | 一致しない |
| **宣言を書き換えた PR** | **違反** | `declared_head != declared_base` |

**`:500` の「0 件は違反」を残したまま、適用条件だけを明示する。**
**所有ブランチ上で、ステップコミットが 1 件も無いまま実装コミットがある場合は、従来どおり赤**になる。
**1 件以上ある後の無記法コミットは従来から通り抜ける** — 本改訂が作る穴ではない(申し送り 4)。

**PR の checkout は合成 merge commit になる**ため、ブランチ名は
`_history_head_revision`(`:408`)と同じ経路で **PR イベントの `head.ref`** から取る。
PR 外ではローカルの `git rev-parse --abbrev-ref HEAD` を使う。

**却下した代替案**: `--first-parent` を外して全履歴を見る案は採らない。
**理由は「範囲が空のままで解決しないから」**(実測: `origin/develop..origin/develop` は
**0 件**。develop で 816 件になるわけではない — 初版の却下理由は誤りだったので訂正する)。

## 通り抜けるもの(DoD と PR 本文へ明記する)

**1. 非所有ブランチでの総数不一致の検出を失う(2 周目 P2-1)。**
従来は非所有ブランチの `(ステップ k/3)` が `:487` の総数判定で**明示的に赤**になった。
改訂後は監査自体を飛ばすので**この失敗も失う**。
*判断*: その赤は「別 feature の記法が混ざった」という意味ではなく**総数不一致としか言わない**。
**原因を示さない赤**であり、かつ**正当な作業を止めていた**。射程を狭める判断として受け入れる。
**PR 本文へ明記する。**

**2. 有効なステップコミットが 1 件以上ある後の、無記法コミットは通り抜ける(2 周目 P1-2)。**
`:478` の抽出は無記法の件名を読み飛ばし、既存の 1 件があるので `:500` の 0 件違反は発火しない。
成果物検査(`:564`)も**完了コミット時点**の存在を見るので、その後の無記法変更は見ない。
*判断*: **これは本改訂が作る穴ではなく、従来からある穴である**(実測で確認)。
**本タスクでは塞がない**(射程外)。**申し送り 4 へ残す。**
→ したがって**「無記法の実装コミットは赤」とは書けない。** 正確には
**「所有ブランチで、ステップコミットが 1 件も無いまま実装コミットがある場合は赤」**である。

**所有ブランチ上で、改訂によって失う検出は無い**(0 件違反・重複・昇順・`/N`・成果物はすべて不変)。
