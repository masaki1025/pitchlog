# 調査メモ: NFR-021 予約レコード監査 PR(10.1 ブートストラップ ①)

## 問い

1. 予約レコード(phase4 ゲート seq001)に正本が課す形式・内容は何か。要件書と設計書 10.1・`docs/ops/nfr021-acceptance/README.md` のどこが正本か
2. 索引カバレッジ除外規則を `scripts/check_docs_status.py` にどう実装すべきか。受入条件(正例・負例)は何か
3. この PR で**やってはならないこと**(否決済みの案・他スロットの責務・別タスク指定の台帳項目)は何か
4. 「4-4 の確定ゲート完了 → 予約レコード監査 PR → 4-4 のマージ」という順序規範に対し、実際には 4-4 が先にマージされた。この逸脱をどう扱うか

## 結論(要約)

- **予約レコードの正本は 2 層**: 5 項目の存在規範は設計書 10.1(`docs/development/dev-harness-design-2026-08-07.md:635`)、命名文法・`attempt_id` 生成規則・対応契約は `docs/ops/nfr021-acceptance/README.md`(v1.0 approved)。**要件書 NFR-021 は「予約」に一切言及しない** — 証跡の必須項目 11 件はすべて結果証跡側の要求(`docs/requirements/requirements-pitchlog-2026-07-22.md:923`)
- **除外規則は既存の接頭辞機構では実装できない**。`is_excluded` はパス構成要素の前方一致しか表現せず(`scripts/check_docs_status.py:122-141`)、当該ディレクトリを `INDEX_COVERAGE_EXCLUDED_PREFIXES` に足す実装は README:115-116 に正面から違反する。**直下判定 + 正規形の述語**という別機構が必要
- **fail-closed の対象は `.md` に限る**(README:117)。非 `.md` の未知ツリー項目は 4-5 の検証器・統合時検査の責務(README:42・150)。統合時の受入検査 4 項目も全部 4-5(README:132-134・162)
- **順序逸脱の実害はない**。「未確定形式の予約は救済不能」(設計書:813)の目的は 4-4 が approved 済みで達成済み。「docs-lint の循環」(同:636)は前提の並びが崩れたが**結論は生きている**(4-4 は D-7 により実装を意図的に含めていないため、develop にいま除外規則が無い)。v1.8 ③ の許可条件は「初回のブートストラップに限り」であって「4-4 のマージ前に限り」ではないので、許可は依然この PR に適用される
- ただし **「ディレクトリ自体の新設」の帰属先が消滅した** — 設計書:636・801・812、README:180 はいずれも新設を監査 PR に割り当てているが、4-4 が README とテンプレートを入れた時点でディレクトリは develop に生まれている。この PR は新設を行わない

### 4. 順序逸脱の扱い

**規範**: 設計書:812「4-1 が先行 → 4-2 / 4-3 は相互任意 → **4-4 の確定ゲート完了** → **予約レコード監査 PR** → **4-4 のマージ** → 4-5 → 4-6 → マージ後検査 → `P4-後`」。4-4 で確定ゲートとマージを分ける理由は同:813、循環回避は同:636(v1.8 ③)。

**観測**: develop 先端は `de9670f`(PR #21 = 4-4)。`docs/ops/nfr021-acceptance/` には正本 4 件のみで予約レコードは 0 件。`scripts/check_docs_status.py` の除外定数は未変更。CI は develop 上で全ジョブ緑。

**2 つの理由の現在の成否**:

- **「未確定形式の予約は救済不能」(:813)— 守るべき利益は損なわれていない**。README・テンプレートは v1.0 approved で既に develop 上にあり、「確定した blob に準拠して書く」条件(:812)は**より強く**満たせる
- **「docs-lint の循環」(:636)— 文言の前提は偽になったが結論は生きている**。4-4 は D-7 により実装を意図的に含めなかったため develop にいま除外規則が無い。v1.8 ③ の許可条件は「**初回のブートストラップに限り**」であって「4-4 のマージ前に限り」ではないので、許可は依然この PR に適用される
- 10.1 が要求する実質(「予約は受入前に `develop` へ統合済み」:635 / 受入は 4-6 のみ:636)は、いま監査 PR を入れれば引き続き満たせる。残りの並び(監査 PR → 4-5 → 4-6)は保存される

**帰属の消滅(実務上の要対応)**: 設計書:636・801・812 と README:180 は「ディレクトリ自体の新設」を監査 PR に割り当てているが、4-4 のマージで既に新設済み。**この PR は新設を行わない**ことを計画書に明示しないと、受入条件と実物が食い違って読める。

**7.6 適合(規範改訂をしない選択)**: worklog は正本でないためゲート不要(設計書:382・407-411)。台帳への `H-*` 追記は版を上げず 7.6-3 前段(PR レビュー)で足りる(`docs/development/harness-evaluation.md:33`、設計書:421)。7.6-3 は「版繰り上げを伴う構造的変更は確定ゲート」と定めるだけで逸脱の事後追認を要求していないため、13 章:812 を改訂しない選択も 7.6 と矛盾しない。**裏返しとして :812 の順序は現行規範として残る**。

**台帳の分類は `## 候補` ではなく `H-*`**: 候補の受け皿は「**制御目的の典拠が示せず追跡優先度を判定できないもの**」(`docs/development/harness-evaluation.md:40`・「追跡優先度の判定条件」節)。今回の逸脱は設計書:812 という明示の典拠を持ち、`分類: プロセス設計`(文書・ゲート区分・レビュー運用の設計に起因し機構の実体を伴わない)であれば**追跡優先度は通常固定で `H-*` を与える**扱いになる。制御目的の典拠があるものを候補へ下げるのは分類規則に反するとして `H-50` を採番した前例がある(設計書:37)。
