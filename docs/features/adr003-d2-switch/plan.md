# 実装計画書: ADR-003 改訂 — 見直しトリガー第 1 項の発火(D-1 から D-2 への切り替えの判定)

## 1. 背景・目的

Notion: [TSK-509](https://app.notion.com/p/3f493b75e68781f09701fab2fc8a7c99)(優先度 高)

TSK-405(U-X1)が、U-X1 の 13 FR について宣言モデルで書けない計算の候補 28 件を判定し、
**表現不能 5 件**(C3 出力値の導出式 / C4 履歴の読み出し / C10 可変長の出力 /
C12 行リストの出力 / C13 閉じない列挙)を特定した。これが
[ADR-003](../../adr/ADR-003-domain-calc-method.md) の**見直しトリガー第 1 項**に該当する。
PO が 2026-10-09 に発火を決定した。

要件の典拠(5 件すべてに要求条文がある — [research.md](research.md) 4 節):
FR-006(`:258`・`:259`・`:261`)/ FR-020(`:442`・`:452`)/ FR-021(`:470`)/
FR-022(`:479-481`)/ FR-023(`:490`)/ 4.0-3(`:175`)/ NFR-019(a)(`:971`・`:975`)/
付録A-2(`:1174`・`:1184`・`:1193`)/ 付録F-1(`:1632`)。

**なぜ急ぐか**: リハーサル最小集合 26 FR のうち **13 件を U-X1 が持つ**。
U-X1 は本 ADR の方式決定を待っている。**本タスクが製品コードの律速**である。

**発火の根拠の受領状態**(重要): PO が受領して発火を決めたのは **TSK-405 の初回提出**である。
その後**ステップ 8 の敵対レビューで 4 値の内訳が是正**され(`表現可能 10 → 0` / `未確定 6 → 16`)、
**更新版は PO 受領「未 — 判断待ち」**(`ux1-game-state-core/research.md:681-683`)。
**本計画は更新後の内訳を確定した前提として用いない。** 発火の根拠である**表現不能 5 件は是正の前後で不変**であり
(同 `:659`)、本計画が依存するのはこの 5 件だけである。内訳の受領は本タスクの前提条件ではない。

**下調べの結論**([research.md](research.md)): **D-1 の実行経路は存在しない**
(生成器 3 言語がすべて固定スタブ — 本タスクが全文を追試)。したがって
「D-1 拡張」と「D-2 切替」は**どちらも実行経路をこれから作る**点で同じ土俵にあり、
捨てる資産の差は小さい。

### D-2 を採る場合の追加範囲(計画レビュー 1 周目 P0-4・P0-6 の反映)

**D-2 を採ると、後送できないものが 2 種類ある。**

1. **ADR 自身の内部矛盾**(P0-6)— 現 ADR には D-1 を前提にした規定が広く散らばっている。
   **D-3**(生成器と生成物の同期規則)・**D-11**((α) の Python / TypeScript 生成物の比較)・
   **D-1-d**((β)①〜⑤ の DB 側集計の SQL 式生成)に加え、**D-8 の表示対応**(対象集合の正を
   **宣言モデル schema の閉包**とする)と**帰結の実装順序**(宣言モデルの生成物を前提にする)も含まれる
   (計画レビュー 2 周目 P0-2 の反映)。D-2 を採ってこれらをそのまま approved にすると、
   **同一文書内で方式が食い違う**。
   → **ADR 全体の D-1 依存箇所を棚卸しし**(ステップ 6)、**発効前後それぞれの適用規則を確定する**
   (ADR-003 の 1 正本内なので射程宣言は保たれる)。
   **(β) の DB 側集計経路は NFR-005(要件書 `:855`)が方式と無関係に要求する**ため、
   **実行場所(DB 側)を維持する形だけでなく、正本から SQL 式を得る経路**も確定する。
2. **要件書の規範との矛盾**(P0-4)— 付録A-1(`:1169`)は「**対象集合の正 = 宣言モデル schema の閉包**」と定め、10 章(`:1129`)は方式を名指しする。**D-1 を廃すとこれらが偽になる。**
   → **要件書の規範改訂は本 PR で行わない**(確定ゲートが別に要るため)。代わりに
   **「決定」と「発効」を分ける**。具体的には ADR の条文として次の 3 つを置く(計画レビュー 2 周目 P0-1 の反映):
   **① D-2 の規則に発効条件を付ける**(要件書の規範追随の完了をもって発効)/
   **② D-1 の規則を発効日まで明示的に存続させる**(「発効までは D-1 が現行」と書くだけでなく、
   **D-1 の各規定が発効日まで有効であることを条文に残す**)/
   **③ 発効後に D-1 前提の規定が無条件で残らないようにする**(発効と同時に失効する規定を名指しする)。
   **先例**: 要件書 `BOOT-ACTIVATION`「**本書が approved となることは発効ではない**」(`:962`)。
   **射程の変更に当たるため、この形を採るかは PO 裁定を仰ぐ**(設計書 7.3-6・7.3-7)。

## 4. 実装方針

### 射程宣言(設計書 7.3-7)

**本改訂で確定する範囲**(確定ゲートの対象 — **ゲート対象は ADR-003 の 1 正本に限る**):

1. **整数符号化の許否**と、`ADR-003:103`「条件分岐…は引き続き書けない」の射程(表示規則に掛かるか DSL 全体か)
2. **NFR-018 (b)③ と採った方式の関係**(ADR 側で判定できる範囲。要件書の条文解釈が割れる場合は **PO 裁定へ上げて停止**する)
3. **D-1 / D-2 の採否**と、その理由(v0.2 の 3 理由への応答を含む)
4. **D-2 を採る場合のみ**: **ADR 全体の D-1 依存箇所**(D-3・D-11・D-1-d に加え **D-8 の表示対応**・
   **帰結の実装順序**)の**発効前後それぞれの適用規則**と、**決定と発効の分離**の条文
   ((β) は実行場所だけでなく**正本から SQL 式を得る経路**も)
5. **式の文法の帰属**(ADR の射程の範囲内か、本改訂で初めて決めるか)
6. **TSK-235 の資産の扱い**(残す / 置き換える / 保留)
7. **見直しトリガー発火後の手続き**を ADR に持つか
8. **Q1 の帰属**(要件側の穴か ADR 側の穴か)**の裁定のみ**

**実装時(後続タスク)に確定する範囲**:

- 採った方式の**実行基盤の実装**(生成器 / JS ランタイムの配線)
- **D-2 の費用の本格的な実測と製品実装**(本タスクのスパイクは**採否の判定に要る最小限**に限る)
- **要件書の規範改訂**(付録A-1 `:1169` ほか)。**D-2 の発効条件**
- **Q1 が要件側と出た場合の要件書改訂**
- D-6 / D-12 の追随(TSK-338 / TSK-275)

**射程が変わった場合**(とくにステップ 2 で PO 裁定へ上げた場合、および D-2 採用で
「決定と発効の分離」を採る場合)は、**変更範囲と理由を ADR の変更履歴と worklog に記録し、
次周の範囲を PO 裁定で指定する**(設計書 7.3-6・7.3-7)。

**重さ分類 = コア領域。** 根拠: ADR-003 が決めるのは**状況計算**の実現方式であり、
CLAUDE.md の列挙(同期プロトコル / **状況計算** / 記録権 / テナント分離 / データ移行)に直接当たる。
設計書 6.3 の境界定義表は状況計算と下流再計算を含む(計画レビュー 1 周目で確認)。
→ レビューは `codex_run.py review adversarial`、人間の逐行確認が必須。

**進め方の原則**: **安い関門を先に置き、高い作業を後ろへ回す。**
ステップ 2 で D-2 が (b)③ に抵触すれば、費用の検討(ステップ 4)は丸ごと不要になる。
ステップ 3 で D-1 拡張が 5 件を書けると分かれば、同じく不要になる。

**判断の材料はすべて [research.md](research.md) にある。** 本計画では複製しない。
