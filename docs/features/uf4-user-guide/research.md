# 調査メモ: U-F4 利用ガイド画面 — 判定③ の「利用ガイド」は何か、逐語移植で足りるか

## 問い

1. リリース判定③(要件書 `:1085`)が言う「利用ガイド」は、アプリ内の画面(HelpScreen)か、文書としての「利用チーム向けガイド」か、両方か
2. 移植元 `dd03160:frontend/src/screens/HelpScreen.tsx` は実在するか。逐語移植で画面として成立するか
3. 利用ガイド(文書)の所有者は決まっているか

調査サブエージェント 3 本(spec-checker / legacy-analyst / decision-tracer)に並列委任し、**報告が食い違った箇所と判定の分かれ目になる箇所は、すべて原典をこちらで読み直して裁定した**。裁定の結果は本文に「**裁定**」として明示する。

## 結論(要約)

1. **判定③ の「利用ガイド」は文書を指す蓋然性が高い。** 決定記録 D-35 DoD精査②(`requirements-draft-pitchlog.md:399`・approved)が「実スコアラー部員が利用ガイドのみで完走=**ドキュメントの実地検証を兼ねる**」と定義している。**したがって U-F4(画面)はリリース判定③ の律速ではない。** ただし要件書本文へは引き継がれていないので、最終判定は PO。
2. **U-F4 の FR 典拠は要件書に無い。** FR-012 に利用者へ説明する条文は 1 件も無く、FR-002 は補足 **Could** 1 件(`:216`)だけで、しかもその対象は「**記録画面**の入力補助」= U-F8 の面である。`frontend-impl-units/design.md:311` の「FR-002 の入力操作と FR-012 の断中操作を利用者へ説明する補助面」は、**要件側に典拠を持たない**(同書は feature 作業文書であり正本ではない)。
3. **移植元は実在する(124 行)が、逐語移植すると I-28 と衝突する。** 本文 `:112` が「**AI分析**」を説明しており、これは I-28 が「実体のない機能」として**唯一確定した該当(旧 AI 分析タブ・破棄)**である。移植対象外と裁定された機能の説明文が画面に載る。
4. **利用ガイド(文書)の所有者は空席。** 要件は「書くこと」と記載事項 3 点を定めるが、担当・置き場・時期の裁定は無く、`docs/ops/` に席も無い。
5. **旧システムには、ガイドの文言を実挙動に固定する試験があった**(`dd03160:tests/test_frontend_help_foundation.py`・49 行)。本単位の NFR-019 テスト設計の先例になる。

## 詳細と典拠

### 1. 判定③ の「利用ガイド」は何を指すか

**要件書の条文だけでは決まらない。**

| 典拠 | 逐語 | 性質 |
| --- | --- | --- |
| `requirements-pitchlog-2026-07-22.md:1085`(判定③) | 「**記録者は開発者以外**(実際にスコアラーを務める部員)とし、利用ガイドのみを頼りに完走できること」 | **定義なし**。「利用ガイド」の語は要件書全文でこの 1 箇所のみ |
| 同 `:1089`(判定⑦) | 「**ドキュメント**: README(…)・approved かつ現行化された開発者セットアップ手順(`docs/development/onboarding.md`)・運用文書(…)・**利用チーム向けガイド(紛失時PW変更含む)**が現行化されている」 | 「ドキュメント」の列挙に入る = **文書** |
| 同 `:1052`(6.4) | 「**運用ガイド**に「端末紛失時はただちにチームパスワードを変更する」を明記」 | 「運用ガイド」の定義も無い。内容は ⑦ の括弧と一致するが、同一と明記した箇所は無い |

**③ と ⑦ が同じものだと明記した条文は要件書に無い。**

**裁定(原典をこちらで確認)**: 決定記録に手がかりが 1 つある。

> **DoD精査②③(2026-07-22採用)**: ②リハーサル記録者は開発者以外(実スコアラー部員が利用ガイドのみで完走=**ドキュメントの実地検証を兼ねる**) ③…
> — `docs/requirements/requirements-draft-pitchlog.md:399`

この文書は **`status: approved`** で、索引に「要件対話の決定記録(D-1〜D-44)/ approved(記録)」として載る(`docs/README.md:11`)。

**「ドキュメントの実地検証を兼ねる」と書かれている以上、判定③ の「利用ガイド」は判定⑦ の文書を指していると読むのが自然である。** リハーサルは文書の検証を兼ねる場であって、画面の検証を課した記録ではない。

**ただし、この定義は要件書本文へ引き継がれていない。** `:1085` は精査②の前半(記録者は開発者以外)だけを取り込み、「ドキュメントの実地検証を兼ねる」を落としている。したがって**条文のレベルでは未決**であり、確定は PO 裁定による。

**本調査が否定できたこと**: 「**U-F4 の画面を作らないとリリース判定③ が動かない**」という理解には、要件書にも決定記録にも典拠が無い。むしろ決定記録は逆(文書)を示唆する。

### 2. U-F4 が担うとされる FR の面

`docs/features/frontend-impl-units/design.md:311` は U-F4 を「**FR-002 の入力操作と FR-012 の断中操作を利用者へ説明する補助面**」と定義する。要件側を当たると次のとおり。

- **FR-012**(`:311-331`): **利用者へ説明する条文は 1 件も無い。** あるのは状態の表示・通知・警告のみ — `:315`「未送信件数が常時表示される」/ `:317`「どの試合の何球分が送信されたかが操作者に通知される」/ `:324` E3「記録できないことと、記録中のタブを終了する導線を明示する」/ `:330`「キューが消され得る旨の警告が表示される」。いずれも**記録画面側の表示**であって、ガイド画面の要求ではない
- **FR-002**: 受入基準(`:212-215`)に説明表示は無い。唯一のものは補足で、**優先度が Could**:

> - **補足(Could)**: **記録画面の入力補助**——球種等のキーボードショートカットと、略号選択肢(PB/WP/K3等)の説明表示。PCでの記録速度・誤選択防止に効く現行機能の継承
> — `requirements-pitchlog-2026-07-22.md:216`

**裁定**: `:216` の対象は「**記録画面**の入力補助」であり、独立したガイド画面を要求していない。この面を担うのは記録画面を持つ **U-F8** である(`design.md:315` が `components/game/**` を U-F8 に置く。ショートカット一覧 `components/game/CheatSheet.tsx` も U-F8 — `design.md:92,315`)。

**結論**: **U-F4 の存在根拠は要件書に無い。** 旧実装に画面があったこと(逐語移植の対象)が根拠である。これは本単位の射程と DoD に直接効くので、計画段階で PO へ上げる。
