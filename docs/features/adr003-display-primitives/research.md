# 調査: ADR-003 D-1 への数値表示 primitive の追加

調査サブエージェント **3 本**を並列で実施(要件突合 / 決定追跡 / 旧システム事実)。
**重い指摘は Claude が原典で直接確認した(◎印)**。

**行番号の注意**: 調査 3 本が挙げた `ADR-003` の行番号は**いずれも 1〜2 行ずれていた**。
本書は Claude が文字列検索で再取得した行番号を使う。

## 0. 結論(先出し)

### ◎ 0-1. 改訂は `ADR-003` だけで閉じる(要件書に触らない)

**要件書 `NFR-018`(878〜911 行)に「表示規則」「写像テーブル」「プレースホルダ」は 0 件**(Claude が実測)。

→ **「表示規則は 2 種だけ」は `ADR-003` D-1(正本の射程)だけの決定**(v0.2 改訂前の記述 — ステップ 8 で行番号参照を決定 ID へ置換)であり、要件書は表示規則の種類を制約していない。
**人間の裁定(甲 = ADR だけで閉じる)は妥当。**

### ◎ 0-2. 「なぜ 2 種に限定したのか」の理由は、どこにも書かれていない

25 周の変更履歴・本文・worklog・計画書・評価台帳を当たって **不明**。

- 16 周目 `:26` の「**表示の都合が正本へ流れ込むことを防ぐ**」は**全面除外の理由**であり、
  **17 周目 `:27` に取り込みへ反転**している(「表示規則を正本の外に置くと、利用者が見る値が単一実装の外へ出る」)
- → **2 種限定そのものの理由は残っていない**

**代わりに射程制限一般の理由が `:359` にある**(逐語):

> 生成は**正本の射程を制約する**ことで成立する。射程を「状態遷移 + 有限の算術」に限れば、
> **生成器は小さく保て、生成物の検査(型・範囲・丸め・到達不能)も生成時に機械化できる**

→ **有限で型付きの primitive はこの論拠に抵触しない**(「生成時に機械検査できる有限な構成物」という同じ形)。
**改訂の根拠として使える。**

### ◎ 0-3. ADR が記録した「次点」は射程拡張ではない — 敵対レビューで必ず問われる

`:395`(見直しトリガー・逐語):

> **DSL の射程で表せないドメイン計算が現れたとき** — D-1 の正本の射程(状態遷移 + 有限の算術)に
> 収まらない計算が要件に入った場合。**次点は D-2 の「TS 正本 → 同一 JS artifact を QuickJS / 常駐 Node で実行」**

**本改訂(射程拡張)は ADR が記録した帰結と異なる。**
→ **計画で「なぜ D-2 へ切り替えないのか」に先に答える。**

D-2 の内容(`:115`):

> **TS 正本 → 同一 JS artifact を QuickJS / 常駐 Node で実行** | タブレット負担は最小で同一由来性も hash で示せる**次点の候補**。
> ただし**バックエンドに JS ランタイム・境界の直列化・timeout・クラッシュ処理**…

**Claude の見立て**: 数値書式のためだけに **JS ランタイムをバックエンドへ持ち込む**のは対価が過大。
ただし**これは判断であり、ADR にそう書かれてはいない**。

### ◎ 0-4. 「逃げ道」条項はあるが、通ると要件書の改訂に当たる

`:97` にこの条項がある(逐語):

> **表示規則を持たない項目**(例: 責任投手の氏名)**は対象計算の出力ではない**(比較面にも入らない)

これを使えば「投球回の表示値は対象計算の出力ではない」と宣言でき、**射程を広げずに整合が取れる**ように見える。

**しかし `NFR-019(a):915` が塞いでいる**(逐語):

> **比較する出力は、当該計算の結果を利用者へ見せる条項が定める全項目**とし、
> **一部だけを比較面に採ることはできない**(**項目を除外するには本書の改訂を要する**)

→ **比較面から落とすには要件書の改訂**が要り、**台帳 `H-85` の 8 資産連鎖**に当たる。
**射程を広げるほうが安い。**

### ◎ 0-5. ADR は改訂前から「2 種」を破っている

`:97`(D-1 の射程)は同じ行の中で:

- 「表示規則として許すのは **2 種だけ**…**数値整形ロジックは書けない**」
- 「**0 除算時は構造化値 `null` + 表示値「−」**(**表示規則で対応づける** — 比較器で吸収しない)」

そして `:252`(D-6)と `:346`(D-10)が **「0除算時の構造化値 `null` と表示値「−」(D-1 の表示規則)」**と参照する。

**`null` → 「−」は 2 種のどちらにも収まらない**:

| 種別 | なぜ収まらないか |
| --- | --- |
| ①写像テーブル | `:97` は写像を「**enum から表示名への写像テーブル**」と定義。`null` は同じ行で「**nullable**(値なしを表す型)」と**別の型機能**として列挙されている |
| ②テンプレート | 「**プレースホルダの差し込みだけ**」で「**条件分岐は書けない**」。`null` のときだけ切り替えるのは条件分岐 |

→ **本改訂は「拡張」ではなく「既存の破れの是正 + 拡張」である。** 確定ゲートでの説明はこの形にする。

### 0-6. 版繰り上げは PO 裁定事項(成文規則が無い)

| 前例 | 運用 |
| --- | --- |
| **ADR-001 / ADR-002** | **新設時から 1.0**。様式の正規化(決定内容の変更なし)でも **1.0 据え置き** |
| **ハーネス設計書** | 0.1〜0.17 が draft/in-review、**確定ゲート通過時に 1.0**、以後 1.1〜1.11 |
| **ADR-003** | **新設 0.1(draft)→ 確定ゲート通過後も 0.1 のまま approved** |

**「確定ゲート通過 = 1.0」の慣行から見ると、ADR-003 が 0.1 のまま approved なのは前例からの逸脱**(理由の記録は**存在しない**)。

**Claude の推奨**: **`0.2`**。1.0 への正規化は**他の ADR との整合を取り直す別の話**であり、本改訂に混ぜると射程が広がる。

## 2. ADR-003 の決定経緯と波及範囲(decision-tracer + Claude の確認)

### 2-1. 表示規則に触れた 6 周の変遷

| 周 | 変更 |
| --- | --- |
| **16** | **nullable と enum→表示名の写像テーブルを射程に追加し、文字列の合成・整形を射程から除外**(0 除算は `null` を返し「−」は**表示層** / 責任投手は選手 ID を返し氏名解決は**表示層**)。理由 = 「**表示の都合が正本へ流れ込むことを防ぐ**」 |
| **17** | **反転**。**表示規則を射程へ取り込み、構造化値と表示値の両方を返す**ことに確定。理由 = 「表示規則を正本の外に置くと、**利用者が見る値が単一実装の外へ出る**」。**許すのは 2 種**と明記(条件分岐・部分文字列操作・数値整形は書けない) |
| **18** | **管理者管理の語彙の表示名は写像テーブルに持たず ID によるデータ参照**(4.0-3 の保全規律と衝突するため)。**写像テーブルの対象は安定した enum に限る**。**データ参照による名称解決は対象計算の出力ではない(比較面にも入らない)** |
| **19** | **語彙スナップショット(ID → 表示名)を対象計算の入力に含める**。改名を入力の差し替えとして反映し、**完成した表示値のまま比較面に載せられる** |
| **20** | 語彙スナップショットを「**断中の成績集計の前処理**」の入力へも追加 |
| **21** | **状況判定の入力から語彙スナップショットを外す**(状況判定の出力は表示名を含まないため)。**取るのは前処理だけ** |

### 2-4. `propertyCatalog` の列挙の非対称

- `:206`(D-11 プロパティ層)と変更履歴 `:20` に **`propertyCatalog` がある**
- **`:232`(宣言の正)の列挙には無い**

**判断材料**: `:232` は「**対象計算ごとに**」持つフィールドの列挙。
`:206` の `propertyCatalog` は「カタログ **1 本**」を指す構造なので、
**マニフェスト直下のトップレベル・キー**と読めば**矛盾ではなく記載階層の違い**になる。
**ただしその階層区別を明言した記述はどこにもない(不明)。**

**扱い**: **記載漏れの補完**なら追随的な明確化。
**階層と `properties[]` との対応を新たに決める**なら決定の追加。
なお `:238` の PO 裁定が「schema のフィールドレベルの細部は**ベクタ整備・検査基盤タスクで実機とともに確定**」と
定めており、**送り出し範囲に該当し得る**。

## 3. 旧システムの表示整形(legacy-analyst)

### 3-1. ◎ 新旧の書式が一致しない

| 新要件書の要求 | 旧の実挙動 | |

| 投球回「**5回2/3**」(スラッシュ) | **`1⅓`**(Unicode 分数記号)+ `1.1` + `1.333` の 3 表現 | **不一致** |

| 「割合・率には**常に母数を併記**」 | **該当規定なし**(近いのはヘッダの「打数-安打」のみ) | **旧に前例なし** |
| 0 除算は「**−**」 | **規定なし**。`"--"` は**行種別マスクで別物** | **不一致** |

→ **primitive を足すだけでは足りず、書式そのものを新規に定義する必要がある。**

### 3-2. ◎ 旧では表示整形が 6 層に分散していた

| 層 | 例 |
| --- | --- |
| **domain** | 投球回 3 表現(`pitching_innings.py`)・球速合成(`pitch_speed.py`)・スコア枠の `""`→`0` |
| **services** | 打席結果の合成(`derive_plate_result`)・経過時間 |

| **analytics** | コース 13 分割の閾値着色 |
| **reports** | スコアカードの記号・カルテ HTML |
| **UI** | `format_batter_status` の読み替え・カウントドット・「打数-安打」 |

**同じ投球回が層ごとに別書式**だった:

| 層 | 書式 |
| --- | --- |
| `charts` の総合スタッツ表 | `1.2` 形式 |
| `reports` のスコアカード | **`⅓` 表記** |

**画面と帳票で書式が違っていた実例。** `ADR-003` が 17 周目に「表示規則を正本に取り込む」と決めたのは

### 3-3. ◎ 条件分岐が必要だった整形 — 13 件

**数値表示 primitive を足しても、これらは解けない。**

| # | 箇所 | 分岐の条件 |
| --- | --- | --- |
| C1 | `prepare_overall_stats_table` の `"--"` マスク | **平均値行か × カウント系列か**の二次元条件 |
| C2 | 打者状況の読み替え(長打時「走塁死」→「二塁アウト」) | **打撃結果が長打か** |
| C3 | 打席結果の合成 `derive_plate_result` | **結果種別**で 3 通りに切り替え |
| C4 | 球速合成 `compose_pitch_speed` | **値域**(`00` / `01-64` / `65-99`)+ フラグ |
| C5〜C7 | スコアカードの「×」・得点イニング赤字・ヒット赤/四死球青/犠打緑 | 消化済みか / 得点 > 0 か / 結果種別 |
| C8 | コース別打率の赤/青/灰着色 | 打率の**閾値** |
| C9 | スコア枠の `""` → `0` 確定 | 3 アウト到達 |

**扱いの選択(改訂で決める)**:

- **(a) 構造化値の側で分岐を済ませてから表示規則に渡す**(`null` を返す / 読み替え後の enum を返す)
- **(b) 表示規則の外(UI 層)に置く**

**17 周目の決定(「利用者が見る値が単一実装の外へ出る」を防ぐ)と逆行する。**

## 4. primitive の候補 — 2 本の調査で見立てが割れている

| 調査 | 数 | 導出元 |

| 要件突合 | **6 種** | 要件書が現に要求している表示値 |
