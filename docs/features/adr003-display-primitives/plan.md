# 実装計画書: 数値表示の確定 — ADR-003 D-1 の改訂と要件書への書式 binding

## 1. 背景・目的

**Notion タスク**: [TSK-278](https://app.notion.com/p/3ce93b75e68781c0967ccd269ee0c5dd)(高 / **見積り要再検討** — §4-(11))

### なぜやるか — 見直しトリガーが発火した

**要件書が要求する完成表示値を、現行の D-1 の射程では表現できない。**

| 要件書 | 要求 |
| --- | --- |
| A-2 投球回行 | 投球回は「1/3回単位で保持し**「5回2/3」形式で表示**」 |
| FR-023(球種割合 — 本改訂で行が移動するため行番号では参照しない) | 球種割合は**割合+球数の併記**(「**スライダー 40%(12球)**」) |

一方 D-1 の射程は表示規則を **2 種**(enum→表示名の写像 / プレースホルダ差し込み)に限り、
「**条件分岐・部分文字列操作・数値整形ロジックは書けない**」と定める。
`ADR-003` 自身が「**表せないものが出たら D-1 の見直しトリガー**」と定めており、本タスクはその正規の経路。

### ◎ 射程を「甲」へ拡大した(敵対レビュー 1 周目 P0-1・人間の裁定 2026-09-01)

**当初計画は「ADR は primitive の型だけを定め、各指標の実引数は要件側へ送る」だった。これは否決された。**

> **型シグネチャだけでは「5回2/3」を生成できず、少なくとも分母、単位、剰余 0 時の省略規則を与えた
> witness が必要**である。…**本タスクだけで TSK-235 の再開条件が満たされるとしており、両立しない**

**人間の裁定 = 甲**: **要件書を同時改訂**し、**対象出力ごとの primitive binding・丸め・scale・符号・
剰余 0・文字種を確定する**。→ **TSK-235 が完全再開できる。**

### ◎ 前提 — 甲は `H-85` の連鎖に当たる(承認時に順序の裁定が要る)

**要件書を変更すると TSK-270 の要件主張母集合の凍結が発火する**(台帳 `H-85`)。

**その理由は今も生きている。**

### ◎ ステップ順序の機構的制約(2 周目 P0-1 の是正 — 本計画の順序の正)

**「正本を編集してから in-review 化する」順序は 7.3 の状態遷移と逆であり、
「確定ゲート前に母集合を追随する」と確定ゲートで要件書の版・変更履歴・status が変わるため blob digest が必ず古くなる。**
本計画は次の順序を固定する(ステップ表はこの順序で構成済み):

1. **両正本(ADR-003・要件書)を先に `in-review` へ**(適用版の worklog 暫定記録と同一コミット — 7.3-1)
2. **改訂と敵対レビューを完了する**(反映周)
3. **人間承認後に、版・変更履歴・索引を確定したコミット**を作る
4. **その最終コミットの要件書 blob に対して母集合を追随する**(甲-2 を採る場合はこの追随を TSK-270 へ送る)
5. **全 checker green を確認して閉じる**

## 4. 実装方針

**改訂案の骨子(詳細設計)は [design.md](design.md) へ分離**(ステップ 2 の成果物 — primitive の型・DisplayAtom・複合 target の証跡スキーマ・同値分割・D-2 の 3 理由・16 周目への回答・決定の空白の埋め方)。本節には方針の骨格だけを置き、内容を複製しない(7.1-1)。

### (1) 重さ分類の根拠 — コア領域

**D-1 は状況計算の実現方式そのもの**を定める(設計書 6.3 の境界定義表)。
`ADR-003` 自体の確定ゲートも **`sol xhigh` で 25 周**。
→ **敵対レビュー + 人間の逐行確認必須。** ゲートは **7.3 + 版繰り上げ**(7.6-3 後段)。**要件書も同じ。**

### (2) ◎ D-2(QuickJS / 常駐 Node)を採らない理由 — 3 点に絞る(レビュー P1-5)

**当初の 4 理由のうち理由 4 は成立しなかった。**

> **理由 4 は成立しない。NFR-005 が要求するのは DB 側の絞り込み・集計であり、
> 最終表示文字列まで SQL で作れとは言っていない**

**残す 3 理由**:

| # | 理由 |
| --- | --- |
| 1 | **D-2 の対価が過大**。ADR 自身が「**バックエンドに JS ランタイム・境界の直列化・timeout・クラッシュ処理**」を挙げる。**数値書式のためだけに払うコストではない** |
| 2 | **D-2 は「射程で表せない計算」全般への代替**であって表示規則固有の対処ではない。**状態遷移・有限の算術という中核の射程は現行のまま足りている** |
| 3 | **D-2 へ切り替えても書式の正が生まれない**。要件書に書式が無い問題は方式に依存せず残る(だから甲で要件書を改訂する) |

**この 3 点を ADR 本文の「採らなかった案」節へ書く。**

### (3) ◎ `(β)` の生成先を ADR で確定する(レビュー P0-2)

**送り先の判断が誤っていた。**

> `(β)` の primitive 生成先は**フィールドレベルの細部ではなく ADR の実現方式そのもの**。
> 表示整形を SQL に含めるか、生成された Python 受け口で行うかによって、
> **生成物、hash、`directTargets[]`、経路一致、変異対象が変わる**

**採る規定**(レビューの是正案):

> **`(β)` は SQL が構造化数値を DB 集計し、同じ宣言モデルから生成された Python 受け口が完成表示値を作る。**

**帰結として追随が要る**: **Python 表示生成物を `generated[]`・`directTargets[]`・hash・変異対象へ追加する。**

**◎ 証跡モデルの再定義(2 周目 P0-2 の是正)**: SQL target は構造化数値まで・Python target は DB 集計経路を通らないため、**製品経路の「SQL → Python 表示」全体と一致する直接 target が存在しない**。是正として:

- **`(β)`①〜⑤ の direct target を「生成 SQL → 型付き受け口 → 生成 formatter までを実行する 1 つの複合 target」として D-11 で再定義する**(**計画改訂〔PO 裁定 2026-09-03〕: `(β)⑦` も 2 段 composite〔sql → 写像①適用の受け口〕として証跡拘束する — composite は段数可変の一般定義**)
- **`directTargets[]` を単数参照から順序付き複数参照へ変更する**(構成要素を順序つきで列挙し、複合 target が経路全体を証跡として拘束する)
- **証跡スキーマの指針(再開 1 周目 P0-5・段数可変化はゲート中 PO 裁定 2026-09-03)**: 複合 target は **1 つの `directTargets[]` 要素**であり、その要素が**順序付きの構成生成物リスト(各生成物に hash。段数は対象による — `(β)①〜⑤` = 3 段〔SQL → 受け口 → formatter〕/ `(β)⑦` = 2 段〔SQL → 写像①適用の受け口〕)**を持つ。**要素を段数分に分けない**(証跡直積の軸は従来どおり `directTargetId` 単位 — 「1 target」と証跡直積を両立させる)。具体スキーマは design.md(ステップ 2)で確定し、ステップ 6 で D-11 へ規定する
- **D-7(property layer)への波及(再開 1 周目 P0-4・対象の限定は再開 2 周目 P0-2)**: 現行 D-7 の `(β)` 比較は生成 SQL と Python reference の比較であり最終表示結果を含まない。**数値 formatter の拡張対象は `(β)①〜⑤`**(**`(β)⑦` は写像①適用後の表示名まで比較〔2 段 composite — ゲート中 PO 裁定〕**・`(β)⑥⑧` は現行のまま)とし、`(β)①〜⑤` の property 比較を「SQL → 受け口 → formatter」の**最終表示文字列**まで拡張する。**比較の相手 = 参照実装(Python reference)も同じ宣言モデルから表示までを生成し、最終表示文字列同士を比較する**(具体は design.md〔ステップ 2〕で確定し、ステップ 6 で D-7 へ規定する)。NFR-018 の「生成された各実行本体間の同値性」に formatter を含める

### (4) ◎ `NumericValue → DisplayAtom` の型付き変換(レビュー P1-4)

既存テンプレートは「**プレースホルダの差し込みだけ**」であり、
**数値を渡す際の文字列化が未定義**だった。**言語既定の `str()` / `String()` を使うと
Python・TypeScript・SQL に暗黙の重複実装が生じる**(NFR-018 違反)。

**規定**:

- **`NumericValue → DisplayAtom` を生成対象の型付き変換として明示する**
- **template が受け取れるのは `DisplayAtom` のみ**
- **暗黙の言語既定文字列化を禁止する**
- **整数表示は固定小数の `scale=0` に統一する**(独立 primitive を増やさない)

### (5) ◎ primitive の集合 — 要件由来の 9 条項を 4 分類し直す(レビュー P1-3)

| 条項 | 分類 |
| --- | --- |
| #1 投球回「5回2/3」 | **新 primitive**(混合分数)。**剰余 0 時の規則を要件書で決める** |
| #2・#3 球種割合「40%(12球)」 | **新 primitive**(百分率)+ 既存テンプレート。**丸めと文字種を要件書で決める** |
| #4 0 除算「−」 | **独立 primitive(P4 null 代替)で確定**(§4-(7) — binding 確定後の最終判定・design §8。既存規則①の拡張は不採用) |
| #5 母数併記 | **新 primitive ではない**。#2/#3 + 既存テンプレートの合成 |

### 機械条件の判定方法(ステップ表の `[機械]` の正 — 再開 2 周目 P1-6)
