# 実装計画書: U-F8 記録画面の独立部品（表示・入力下書き）

## 1. 背景・目的

U-F8 の担当範囲は [実装単位の定義](../frontend-impl-units/design.md) 5.3 節にあり、試合開始・記録・再開・修正を含む。要件書の FR-002（1 球入力）と FR-020（記録中のスコア表示）に向け、現時点の API 契約や同期の受理処理に依存しない部品を先に作る。**この分割は利用者が開ける製品画面を完成させない**。本計画は U-F8 全体の完了計画ではなく、入口接続・実データ供給・記録の成立を含む残部には別計画と承認を要する。

2026-10-13 の最新 `origin/develop` は `9114a5a6`。U-F6 は PR #120 で API クライアントを作業中、U-A1 の HTTP 入口は PR #119、U-M2 は PR #121 にあり、試合・プレイ API は U-F6 のスコープ外である。ADR-003 のランタイム作業も別 worktree で進行中。U-F8 の Notion カードはリンクが既存文書にあるが、現在の連携権限では取得できなかった。承認時にカードの担当・DoD と本書の分割範囲を人間が照合する。

**着手前提**: 正式カードの担当・DoD と本分割の整合を確認し、人間が本計画と開始する実装ステップを承認する。パス登録の先行マージは不要。U-F6 PR #120 が所有する `.claude/core-areas.json`・`scripts/core_guard.py`・`tests/test_core_guard.py` はその統合まで変更せず、ステップ 1・2 の独立した画面コードだけ先に進められる。登録は U-F6 統合後に `origin/develop` を取り込んで、本 PR の別コミットで行う。

## 2. スコープ

### やること

- `frontend/src/screens/GameScreen.vue` に、試合名・回表裏・得点・アウト・走者・カウント・打者・投手の **受け取った表示値** と記録入力の下書き領域を置く。欠けた値は未取得と表示する。画面専用 view model の数値表示欄は `string | null` とし、生の `number` を受けない。対象計算の数値からこの文字列を供給する後続の呼出元は ADR-003 D-1 の **生成 formatter** を必ず通す。この PR は formatter への接続を実装しないため、実データを表示できる完成画面とは判定しない。
- 球種、球速、コース、結果の選択を画面内の下書きに保持し、選択・訂正・クリアを操作できるようにする。球種・結果の候補は呼出元が `{id, displayName, enabled}` の配列で渡す。画面は有効候補の ID を保持し、表示名を固定しない。候補の取得と登録済み判定は後続の API 接続で行う。コースは既存 `StrikeZone.vue` の選択値を下書きに保持する。保存座標の新たな変換、カウント進行、打席結果判定、イベント生成はしない。下書きは画面の再マウント時に消えることを表示する。
- 記録確定は有効化しない。記録権・同期キュー・サーバー受理の接続ができる後続計画で、永続追記成立と成功表示を結ぶ。利用者に保存成功と誤認させる表示を出さない。
- 画面の描画・下書き操作・未取得表示・非保存を Vitest で確認する。

### やらないこと

| 項目 | 理由・送り先 |
| --- | --- |
| `App.vue`・`main.ts` のルート接続 | U-F13 の所有。画面は後続の入口から配置する |
| `api/**`・`lib/sync/**`・`src/domain/**` | U-F6・U-F7・ADR-003 の作業と競合し、API・計算契約を先取りするため |
| 保存・送信・再送・記録権・undo・再開・修正・試合削除 | U-F8 残部。U-F7 と各 API 契約の着地後に別計画で扱う |
| 得点・アウト・走者・打順・カウント・終了条件の計算 | NFR-018 に従い ADR-003 の単一実装を待つ。画面にコピー実装を作らない |
| ユーザーへ操作できる本番導線の追加 | U-F13 の入口とサーバー契約が未着地。コンポーネント単体の操作を先に完成させる。**PR と DoD に「製品画面として利用不可」と明記する** |

## 4. 実装方針

重さ分類は **コア領域**。U-F8 は [実装単位の定義](../frontend-impl-units/design.md) 5.4 節で 5 領域すべてに該当する。今回の下書きは保存イベントへ変換しないが、記録操作と誤認される表示が安全性を損なうため敵対レビューを適用する。表示値は呼出元から受け、画面でドメイン計算をしない。利用者入力は Vue の通常のテキスト描画を使い、生 HTML を挿入しない。

現行の `.claude/core-areas.json` の paths は予定の新規画面パスに一致しない。設計書 6.3 の落とし込み規則 ①・③・⑤に従い、本 PR 内で `frontend/src/screens/GameScreen*` を U-F8 の 5 領域の paths に登録する。U-F2・U-F6 と同じく、先に `AREA_PATH_ADDITIONS` とテストを変更し、次の別コミットで JSON に追加する。追加層はその時点の develop を基線とし、U-F6 の宣言を取り込み済みの登録へ置き換える。登録は PR 作成・レビュー依頼前に終え、head 側 `core_guard.py` で全予定パスが検出され、必須チェックが発火することを実測する。`/pr` の base 側判定が新規パスを見落とす場合は PR 本文にコア領域の敵対レビューと人間逐行確認の項目を明示して補う。コア領域の敵対レビューと人間逐行確認を必須とする。

### 実装ステップ（コミット単位）

| # | ステップ | 合格条件 |
| --- | --- | --- |
| 1 | `GameScreen.vue` に読み取り専用の試合状態表示と明確な未取得表示を作る。画面専用 view model の数値表示欄は `string | null` として props で受け、生数値の差し込みを拒む | Vitest で試合名・整形済みスコア文字列・カウント文字列・未取得・利用者文字列のエスケープを確認。`vue-tsc`・ESLint・Prettier が緑 |
| 2 | 画面内に球種・球速・コース・結果の入力下書きを置き、訂正とクリアを可能にする。球種・結果の候補は外部から受け、有効 ID だけを保持する。非保存を明示し、確定操作を置かない | Vitest で候補の改名・無効化、入力・訂正・クリア、再マウント後の消去、保存成功表示が無いことを確認。frontend の品質ゲート 4 種と build が緑 |
| 3 | U-F6 統合後の develop を取り込み、`AREA_PATH_ADDITIONS` を本単位の `GameScreen*` 追加へ更新し、対応する guard テストを更新する | U-F6 の登録が基線にある。宣言のみのコミットで `tests/test_core_guard.py` が緑 |
| 4 | `.claude/core-areas.json` の 5 領域に `GameScreen*` を追加する | ステップ 3 と別コミット。`verify_area_path_baseline` が通り、画面と spec が core-guard の検出対象になる |

ステップ 1・2 は U-F6 の共有ファイルに触れない。ステップ 3・4 の前に U-F6 の統合と共有ファイルの所有解除を確認する。ステップ間と完了時に、画面が API・同期・計算の既存所有ファイルへ依存していないことを確認する。**承認後も実装は指示されたステップで止め、各ステップを別コミットにする。**

## 5. DoD（受け入れ基準）

- [ ] 呼出元が与えた表示値を画面に表示でき、欠けた値を推測せず未取得として示す。生数値を表示欄に渡せない
- [ ] 球種・球速・コース・結果を下書きとして操作でき、消去できる
- [ ] 下書きは未保存と分かり、記録成功・保存成功を示す操作や表示がない
- [ ] API DTO、同期イベント、記録権、ドメイン計算を独自に定義しない
- [ ] `GameScreen` のテストと frontend の品質ゲートが緑
- [ ] PR に「この分割は利用者が開ける製品画面ではない」と明記し、入口・実データ・記録成立の後続計画へ受け渡す
- [ ] 本 PR 内の宣言・登録を別コミットで行い、PR head の core-guard が画面と spec を検出して必須チェックを機械強制する。コア領域の敵対レビューと人間逐行確認を実施する

## 6. テスト計画

| NFR-019 の種別 | 今回の試験 |
| --- | --- |
| 単体 | 整形済み文字列 props の表示、未取得表示、下書きの選択・訂正・クリア。候補 ID は維持し、表示名の改名と無効化に追従 |
| 越境 | 利用者の試合名を文字列として描画し、生 HTML が実行・挿入されないこと |
| 故障系 | 欠損 props の表示と、再マウントによる下書き消去。永続化に失敗したかのような成功表示を作らないこと |
| 一致性・E2E | 本分割は状態計算・API・入口を持たないため対象なし。U-F8 残部で ADR-003 とサーバー契約を受けて追加する |

検証は `frontend/` で `pnpm exec prettier --check .`、`pnpm exec eslint .`、`pnpm exec vue-tsc --noEmit`、`pnpm test`、`pnpm run build`。パス登録については root で `uv run pytest tests/test_core_guard.py` を実行する。backend の全試験は本分割の直接の合格条件にしない。
