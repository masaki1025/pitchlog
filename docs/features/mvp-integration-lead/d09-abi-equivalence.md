- **同等以上(機構の面)**: 業務scopeの外側でのfence保持、commit前の再照合、結果不明時の隔離(成功も解放も推測しない)、writer と nonce の偽造防止(binding と frame の範囲)。α の broker lease・PG側 admission・4値の観測は、旧 `fenced_transaction` が合成試験で示した性質を、実PGの同一トップレベルTXへ結び付けている(G8〜G11)。
- **同等性を示せない(省略不可・追加実装が必要)**: 次の9項目(G 番号では G1、G2、G4、G5、G6、G7、G12、G14、G17、G18、G20 の11)。
  - 検証済み端末文脈を公開入口で必須にすること(G1)
  - 全経路へ伝えること(G2。多TX構造は G19)
  - 端末資格の真正性の照合を core が強制すること(G4)
  - Port から現権利を照合する閉じた口(G5、G6)
  - 照合不能と不保持を B7/B10、B5、B4 へ写すこと(G7)
  - 登録 Port から α 内部への到達の遮断(G12。P1-3)
  - 停止契約3口(G17。P1-1)と E-1 バッチ口(G18。P1-2)
  - 配信入口(G14)
  - **確定した拒否(要求内容に起因)を、結果不明の隔離から区別して、その要求だけの拒否にすること(G20。反映2で新設。反映3で設計案が主担当判断により採用された〔§6.5〕が、実装は未了)。現行は同 phase の再 publish・同 attempt_id の付替えで authority 全体が停止し、再起動でも回復しない(合成で再現)**
- **1 phase = 生涯1 binding と多TX構造(G19)** は α の範囲内の実装選択である(PO採用の範囲外へ出ない)。**主担当判断(PO委任。人間の逐行確認ではない)で (i) F1 に限り1要求1 bound TX が採用された**。ただし実装も実PG検証(T-20)も未了で、**G19 は担保ではない**。(i) を採ったときに何が担保され何が残るかは §6.4。
- WB では端末資格の照合 `bind_device` と現権利の照合 `check_current_right` は SQL の部品として存在するだけである。製品コードからの呼出元は0件で、試験が手で呼んでいるにすぎない(`backend/tests/db/test_sync_writer_binding.py:268-279`)。
- **現在の閉鎖は「未接続」によるもの**: WB では `PORT_IMPLEMENTATIONS` が空(`backend/src/pitchlog/sync/ports.py:134`)、`bind_writer` の製品呼出元が0件(grep で確認)、HTTP 入口が無い、という理由で書込経路が開かない。これは「端末文脈の欠落を拒否している」のではなく**接続されていないから閉じている**だけである。接続した時点で、G1・G2・G4・G5・G12 の拒否が無いまま開くおそれがある。

## 6. G19(1 phase = 生涯1 binding と多TX構造)の3案比較(P1-4)と主担当判断(反映2)

- 6.1 前提となる事実 / 6.2 3案比較 / **6.3 主担当判断済み: (i) 採用** / **6.4 (i) を採ったときの担保と未担保の残り** / **6.5 G20 の最小設計案** / 6.6 (i) で先に決める点

### 6.1 前提となる事実

**前提となる事実**(静的読取。出典は §2 の G19 と補足の表):
- binding は (tenant, attempt, phase) ごとに生涯1回(PK + 不変 trigger + `INTO STRICT`)。binding には実 TX の xid が入り(`binding_control.py:617-619` → publish の `transaction_id`)、`assert_writer_binding` は `r.transaction_id<>own_xid` を拒否する(`writer-binding-functions.sql:88`)。つまり1つの binding は**1つの top-level TX に1回だけ**結び付く。
- 初球の1要求は、受理・B4 で Port を呼ぶ TX が2つ、T9 で3つ(§2 G19 の補足)。T9 は局所 TX の rollback の後に拒否 TX が開く。コードに自動の TX 再試行ループは無い(`retry`・`40001`・`40P01` の grep が `sync/` と `transaction.py` で0件)。
- UA の印は、bind を行った**同じ top-level TX** で、`admission` が `xmin = top-level xid の低32bit`、binding の `transaction_id = own_xid`、状態が `right_verified`(device→right の順序付き遷移)であることを PlayRow の INSERT trigger が確かめ、**1 phase につき1回だけ** `consumed` にする(UA 反映2 `first_ball_write_stamp.py:25-29,77-165`。印の表は PK (tenant, attempt, phase) で、`sync_fence.writer_bindings` の同じ3列へ FK を張る=0038 候補 `fk_first_ball_write_admission_binding`)。nested の consume は xmin 不一致で拒否される(:163-165)。
- 制御 DB の `event_phases` は PK (tenant, attempt, phase_id) と UNIQUE (…phase_id, d1, d5, event_fingerprint) を持ち、(attempt, position) の一意制約は無い(`control-phase-schema.sql:56-72`。同じ位置に複数 phase を置くこと自体は DB が許す。ただしこのファイルの先頭コメントは「F2制御9表の構造候補。別PG専用。role/固定保存器/正式受理は未提供」と述べており、**正式受理された構造ではない**)。`register_first_ball_phase` は `ON CONFLICT DO NOTHING` と全値の一致確認で冪等(`writer-binding-control.sql:26-37`)。
- 物理再試行は新 attempt_id(sync-protocol :914)なので、「rollback 後に同じ (attempt, phase) を再 bind する」経路は通常起きない。**要求の内部の TX 間**が問題である。
