# 実装計画書: ADR-003 D-14 の発効条件を満たす(TSK-541)

## 1. 背景・目的

Notion: [TSK-541](https://app.notion.com/p/3f593b75e68781f3a3a6cd98788120ea)(優先度 高)

**ADR-003 は v0.5 で approved だが発効していない。** D-14-f:

> **発効日が記録されるまで本決定は発効していない — 記録が唯一の発効の印である**
> **発効まで: D-1 の規定が現行である。本改訂で失効する規定は無い**

**発効しない限り D-2(TS 正本 → 同一 JS artifact)は正本の方式にならない。**

**本タスクは発効条件のうち (i)(ii)(iii) と要件書の規範改訂を満たす。**
**(iv) は満たさない**(3 周目 P0 — **案 A を前提に書いた計画なら、到達点もそれに合わせる**)。
**理由**: **(iv) は「段階 2 が定める部分集合に収まるかを発効前に判定せよ」と要求するが、
その部分集合の具体は段階 2(TSK-538)が定める**(`ADR:793`)。**条文自身が循環している**(4 節の難所 (7))。

**したがって本タスクの完了時点で発効はできない。** **発効は (iv) が段階 2 の後に閉じてからになる。**
**本タスクが作るのは「(iv) 以外が揃い、残るのが (iv) と PO の記録行為だけ」という状態である。**
**PO 裁定(2026-10-11)で案 A を採ったため、この到達点が確定である。**

**最長工程である。** U-X1(リハーサル必須 26 FR のうち 13 件)の実装までの連鎖は「段階① の完了 + 発効」で、
**発効側は確定ゲートを含む**。ADR-003 v0.1 は敵対レビュー 25 周、要件書 v2.2 も同じゲートで通した。

**律速に直結する条件がある** — `docs/features/ux1-state-calc/design.md:72` の P-4 が
**「発効条件 (i) が未確定だと PR-1 を緑にできない」**と書いている。**(i) を最初に書く。**

関係する要件: **NFR-018**(`:928`〜 ドメイン計算の単一実装)/ **NFR-019・NFR-019(a)**(`:969`)/
**NFR-005**(`:857-858` DB 側集計)。調査の結論は [research.md](research.md) が正。

## 4. 実装方針

### 重さ分類の根拠: コア領域

**`docs/adr/ADR-003-domain-calc-method.md` が `.claude/core-areas.json` の `paths` に該当する。**
したがって **ADR-001 のモデル・effort をラッパーが固定**し、**計画書の段階から敵対レビュー**、
**PR も敵対レビュー + 人間の逐行確認**が要る(設計書 6.3)。

**`contracts/authz/**` も同じ判定に入る**(ステップ 8)。

### 本タスク固有の難所

**(1) (i) は「比較相手を定める」だけでは閉じない。**

[research.md](research.md) §1-2 のとおり、**比較相手の表は機械可読に実在する**
(`backend/src/pitchlog/domaincheck/runners/equivalence.py:39-50`)が、
**2 つの実行体を実際に走らせて突き合わせる経路はリポジトリに 1 行も無い**。
**`properties.py:1-6` の docstring が「等価性は完走証跡の存在だけを確認し、比較そのものは行わない」と明記している。**

**この層は過去に実際に取り逃がしている** — 生成 formatter の Python / TypeScript の値ずれを、
**TS を実行する試験が 1 件・1 値しか無かったため検出できなかった**。

→ **(i) の条文は、比較相手に加えて「誰が・どの経路で実行するか」と「何をもって実行されたと判定するか」を定める。**
**定めないと「文言は直したが実効がない」(台帳 `H-21`)になる。**

**(2) (i) の論拠が明文で存在しない。**

「なぜその 2 つを比較するのか」を述べた文は ADR にも worklog にも無い([research.md](research.md) §1-4)。
**条文化は書き写しではなく、根拠を初めて書く作業になる。**
**`ADR:269` がこの層の限界(製品経路の別実装は捕まえられない)を書いている**ので、それと矛盾しない範囲で書く。

**(3) 要件書 `:1129` に触ると凍結資産の連鎖が動く。**

**TSK-509 が同じ行を変えて `contracts/authz/` の凍結入力が 5 段の連鎖で red になり、
9 ファイル再封印したところで止めて PO 裁定で取り下げた**(`docs/worklog/2026-10-09-adr003-d2-switch.md:1373-1417`)。
**その費用を本タスクが払う。** 連鎖は次の順:

```
要件書の git blob digest
  → contracts/authz/requirement-claims.json の input_manifest(commit + source_blob_digest)
  → 当該行の source_text / source_text_digest / decision_digest
  → requirement-claims.lock.json
  → 派生 3 資産(route-registry / auth-catalog / http-route-matrix)+ 各 lock
  → oracle-seal.lock.json の oracle_commit
  → oracle_commit を固定する 7 資産
```

**`--reseal` は原文 digest 不一致で止まる** — **自動再封印しない設計**で、
**原文が変われば分類を見直させる**ためである。**分類の見直しを飛ばさない。**

**(4) ゲート投入は 4 点を同時に含める。**

全正本の frontmatter を `in-review` / 各変更履歴へ起案行 / 索引の 3 列 / worklog へ適用版
(**7.3 の版数 + 条文コミット SHA**。3 正本の条文 SHA を書く誤りが先例にある)。
**索引の検査は 2 段階で落ちる。**

**(5) 版番号は暫定にする。** **`v2.5` が TSK-267 の先約**で埋まっている。
**先例どおり版のセルは暫定にし、承認時に PO が裁定する。**

**(7) (iv) の循環を解く(敵対レビュー 1 周目 P0)。**

**現行の (iv) は、そのままでは本タスクで満たせない。** 逐語(`ADR:735-736`):

> **要件書ブロック 4 が定める必須集計の全件について、D-14-i 1 の「変換可能な部分集合」に収まるかを判定し、
> 変換不能と判定されたものの扱いを定める。**

**一方 `ADR:793` は「どの構文・どの演算を許すかの具体は段階 2 で定める」としている。**
**存在しない集合への包含は判定できない** — **(iv) の充足が段階 2 の成果に依存し、循環する。**

**1 周目では「包絡の確定をもって (iv) の充足とし、照合は段階 2 の入口ゲートへ移す」案を書いたが、
2 周目 P0 で「それでは変換可否が未判定のまま発効できる」と指摘され、撤回した。**
**`D-14-i 5` が「発効までに判定する」と定めている以上、照合を後ろへ送ることは発効条件を弱めることになる。**

**これは本タスクだけでは決められない。** **選択肢は 3 つで、どれも PO 裁定を要する**(PO 判断④):

| 案 | 内容 | 帰結 |
| --- | --- | --- |
| **A** | **(iv) をそのまま満たす** — 段階 2(TSK-538)が部分集合を定めるのを待ち、全件照合してから発効条件を閉じる | **本タスクでは (iv) を満たせない。発効は段階 2 の完了後**になる。本タスクは (i)(ii)(iii) + 要件書の追随までで閉じ、**(iv) だけが残る** |
| **B** | **部分集合の具体を本タスクで定める** — `ADR:793` が段階 2 へ送っている射程を本タスクへ引き取る | **射程の移動**。重さが増え、段階 2 の設計を文書だけで先に決めることになる |
| **C** | **包絡の確定をもって充足とし、照合を段階 2 の入口ゲートへ移す**(1 周目の案) | **発効条件が弱まる**(2 周目 P0)。**採るなら「弱める」ことを明示して PO が裁定する** |

**本タスクの推奨は A** — **(iv) の充足を段階 2 の後に残し、(i)(ii)(iii) と要件書の追随を先に閉じる**。
**理由**: (i) が U-X1 の律速(`ux1-state-calc/design.md:72`)であり、**(iv) を待つと (i) も止まる**。
**A なら (i)(ii)(iii) が先に approved になり、発効だけが (iv) 待ちで残る。**

**PO 裁定(2026-10-11・山田正輝)で A を採った。** 本計画は A の前提で確定している。

**(6) 「同じ論旨を別の箇所・別の言い方で述べた部分」を取り残さない。**
v2.9 のゲートでこの型が **4 回**繰り返した。**最終周で「変更しない範囲」が基準版と HEAD で
SHA-256 同一であることを機械的に確認**して閉じた先例に倣う(ステップ 9)。
