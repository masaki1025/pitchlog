## 4. 実装方針

**重さ分類 = 通常** の根拠: 変更は**設計書の別名の現況化・結果証跡・feature 配下**のみで、`backend/`・`frontend/`・`contracts/` に触れない。CLAUDE.md が列挙するコア領域のコードにも触れない(`.claude/core-areas.json` の各領域 `paths` は全域空・`guard_paths` にも該当しない)。

**`/implement`(Codex 委任)は使わない。** 実機受入は判定者(人間)が行い、Claude の作業は記録の起草と検査の実行に限られる。**ステップ 3・6・7 は人間の作業**である。

### 進行順序の機構的制約(research.md §4・§5 が典拠)

1. **`T` を採ったら allowlist 3 系統以外を一切触らない** — 失効判定は `T..E` の**各コミットの変更パスの和集合**(2 点差分ではない)
2. **検証器は候補 SHA を checkout した作業ツリーからしか通らない** — 自己同一性検査が、実行中の `scripts/verify_nfr021_evidence.py` と `.claude/nfr021-invalidating-paths.json` の blob を候補ツリーと突き合わせる
3. **detached HEAD は使わない** — `git_guard` の `current_branch` は detached 時に文字列 `HEAD` を返し `PROTECTED` にも `UNKNOWN` にも該当せず**ガードが発火しない**ため、onboarding 6 章の負例試験が落ちる。**`git switch -C develop <T の 40 桁 OID>`** でブランチ名を `develop` に保つ(onboarding 2-1 節)
4. **`E` は「結果証跡・3 節の実パス宣言・計画書 status・worklog の締め」を含む単一のクローズ処理コミット**であり、**PR の最終コミット**である(計画レビュー 1 周目 P0)。**証跡を別コミットにしない** — `/pr` のクローズ処理が後から HEAD を動かすと `gh pr merge --match-head-commit <E>` の前提(remote head = `E`)が崩れる。**`/pr` は受入完走後に 1 回だけ**実行する
5. **CI は「全ジョブ緑」では成立しない** — **success 必須 7 本**(`secrets` / `docs-lint` / `core-guard` / `harness` / `nfr021-append-only` / `frontend-changes` / `backend-changes`)、**skipped 許容は `frontend`・`backend` の 2 本のみ**
6. **push は宛先を明示**(`git push -u origin feature/phase4-6-gate`)。**`git -C` にシェル変数を渡さない** — フックは生のコマンド文字列を字句解析するため変数を展開できず、ブランチ解決に失敗して遮断する(台帳 `## 候補` (13))
7. **証跡の 6 ラベルは `; ` 区切りの 1 物理行** — 改行や `<br>` を入れると完全性検査 ⑩ の表抽出が打ち切られ、**当該欄と後続の「判定者」欄が欠落扱い**になる(前提 PR 第 3 号の確定ゲート 3 周目で実測)
8. **`phase4_base_sha` を証跡に書かない** — 未知キーとして拒否される。置き場は判定者の手元と PR コメント
9. **達成不能な合格条件を書かない** — 自己参照(そのコミット自身の OID を条件にする)は不可。`T`・`E`・`M` はいずれも**確定後に取得して記録する**

### 運用手順(コミットを作らない作業 — 上表の外)

**A. ステップ 1 の後 — `T` の固定と push**

1. `T` = ステップ 1 のコミット。`rev-parse HEAD` と `rev-parse HEAD:docs/development/onboarding.md` の 2 値を取得する
2. `git push -u origin feature/phase4-6-gate` で **remote head = `T`** にする
3. 2 値は**未コミットの worklog へ書く**(ステップ 2 の `E` に含まれる)。**以降 allowlist 3 系統以外を触らない**

**B. 【人間】実機受入の完走**(判定者)

1. `git fetch origin feature/phase4-6-gate` → `git switch -C develop <T の 40 桁 OID>` → `branch --show-current` が `develop`・`rev-parse HEAD` が `T` であることを確認(**detached にしない**)
2. onboarding **2-2 節**のブロックを実行し、**6 ラベルと `適合: arch=<arch>`・終了コード 0** を得る。**不適合なら受入を続行せず、下記「C. 判定」で `failed` へ進む**
3. onboarding 0〜8 章を逐語実行し、**合格 5 項目**(ハーネス pytest / backend pytest / frontend Vitest / 開発 DB 接続 / backend・frontend の起動疎通)の実測値を採る

**C. 【人間】人手確認と判定**(判定者の専権。**Claude は草案の作成と値の転記のみ**)

1. 受入証跡 README「証跡本文の完全性」の**人手確認項目**(6 ラベルの実在と値の適合)を確認する
2. **判定者が `passed` / `failed` を決める**。Claude はその値を証跡の `result` へ転記する
3. **`passed` の場合、この時点で `phase4_base_sha`(= 判定時点の `origin/develop`)を完全 OID で固定し、人手で記録する**(計画レビュー 3 周目 P1 — 10.1 は「**判定時点**の `origin/develop`」と定めており、F で初めて採ると「判定時点の値」であることを証明できない)
4. **途中失敗(2-2 の不適合・章の途中で完走不能)でも証跡は作る** — **到達済みの実測値と失敗理由を記録**し、**未実施の必須欄には非空の理由値**(例: `未実施(2-2 で不適合のため中断)`)を入れて完全性検査 ⑩ を通す。`result: failed` として**経路 A** へ分岐する

**D. ステップ 2 の直前 — `/check`**

- **`/check` を本セッションで成功させる**(`/pr` は「`/check` が未実行または失敗なら中断」する)。証跡の起草と 3 節の実パス置換を終えた後、`/pr` の直前に実行する

**E. 【人間】検証器の実行**

- `E` を checkout した状態で `uv run python scripts/verify_nfr021_evidence.py --root "$(pwd)" --gate-kind phase4 --candidate-sha <E> --evidence-path docs/ops/nfr021-acceptance/<証跡>.md`
- **終了コード 0 かつ stdout / stderr がいずれも空**であること。**判定は C で済んでいる**(ここで再判定はしない)

**F. 【人間】排他区間 → マージ → マージ後検査**

1. **排他区間の開始を PR コメントへ**記録する(`main`・`develop` を進めるあらゆる操作を停止 — GitHub UI / API からの他 PR のマージも含む)。**C-3 で固定した `phase4_base_sha` もここに記録**する
2. **3 つの判定値を GitHub API で再照合し、いずれも一致することを PR コメントへ記録する**(計画レビュー 3 周目 P1):
   - `.head.sha` == **`E`**
   - `.base.sha` == **C-3 で固定した `phase4_base_sha`**
   - **`E` に対する CI が success 必須 7 本で成功している**(最新の実行を見る)
3. **一致しない場合・排他区間が時間切れになった場合・`gh pr merge` が拒否された場合は、マージしない** — **中断理由を PR コメントへ記録 → 排他区間を解除 → 受入からやり直す**(`T` を採り直すかは原因により判断する。10.1「時間切れ・照合不一致なら排他を解除して受入からやり直す」)
4. `gh pr merge --merge --match-head-commit <E>` でマージする
5. `M` の**第 1 親 = `phase4_base_sha` / 第 2 親 = `E` / ツリー = `E` のツリー**を検査する
6. **記録 4 項目**(`M` の完全 OID・実施日・合否・確認者)を PR コメントへ(**合否どちらでも**)→ **排他区間の解除を PR コメントへ**

**G. `passed` 後に `/check`・`/pr` 突合・CI・検証器のいずれかが失敗した場合の復旧**(計画レビュー 3 周目 P1)

**`E` は未統合なので書き換えてよい。** 「状態戻しコミット + 修正コミット」を積むと **`E` = 唯一の `(ステップ 2/2)`** という契約が壊れるため、**通常の差し戻し手順(`status` を `active` へ戻す往復)は使わない**。

- **`E` の中身だけの修正**(証跡の記入漏れ・3 節の宣言のずれ・worklog の不足など): **`E` を `git commit --amend` で書き換え**、`(ステップ 2/2)` を **1 個のまま維持**する → force push ではなく**未 push のうちに直す**か、push 済みなら**同一ブランチへの再 push が必要**になるため、**`/pr` の実行前に `/check`・突合・`append_only` 検査をローカルで通しておく**(運用手順 D の目的)
- **`T` を変える必要がある修正**(設計書の現況化に誤りがあった等): **旧 `E` を履歴から外し、`T` を作り直して運用手順 B から実機受入をやり直す**。`T` が変われば `tested_commit_sha` と `short_sha` も変わるため、**証跡のファイル名も作り直す**
- **検証器が不合格の場合**: 決定表のとおり**マージしない**。**同一 `attempt_id` のまま**証跡を直す(未統合なので改変できる)

### 決定表(どの結果でどこへ進むか — 計画レビュー 2 周目 P1)

| 結果 | 次にすること |
| --- | --- |
| **C で `failed`** | **経路 A**。本 PR はマージしない。`/task-done` は使わない |
| **C で `passed` かつ E で検証器が合格** | **4-6 マージ前条件を満たす** → F へ進む |
| **C で `passed` だが E で検証器が不合格** | **マージしない**。原因を直して**同じ `attempt_id` のまま証跡を作り直す**(証跡は未統合なので改変できる)。`T` を触る修正が必要なら `T` から採り直す |
| **F でマージ後検査が不合格** | **経路 B**。Phase 4 未完了。`/task-done` の不合格分岐へ |
| **F でマージ後検査が合格** | **正式受入が成立**(= Phase 4 完了)。`/task-done` の合格分岐で `P4-後` を起票 |

### 不合格の 2 経路(いずれも到達可能な形で定める — 計画レビュー 1・2 周目 P0)

**経路 A: 判定者が `failed` と判定した場合**(C の時点)

1. **本ブランチの PR は作成しない**(作成済みなら**マージしない**)。**`/task-done` は使えない**(PR が MERGED でなければ中断する)。本タスクの Notion は `差し戻し` へ。**元 worktree は除去せず保持**する(未コミットの証跡草案・worklog・`T` の記録が入っているため)
2. **別タスク・別 worktree・承認済み計画書**で「**結果証跡だけの監査 PR**」を作り、同一 `attempt_id` の **`result: failed`** を追記して予約を閉じ、`develop` へマージする(設計書 `:653`)。**元ブランチで `/pr` を実行してはならない** — ステップ 1 の設計書・索引変更が混ざり「証跡だけの監査 PR」にならないため
3. 監査 PR へは、元 worktree から **`T` の完全 OID・onboarding の blob OID・到達済みの実測値・失敗理由**を転記する
4. **ステップ 1(設計書の別名の現況化)は受入の合否と独立**なので、**別タスクの通常 PR として切り出してマージしてよい**(正本の現況化を受入の失敗に巻き込まない)。**そのまま `cherry-pick` してはならない** — 件名の `(ステップ 1/2)` が新タスクのステップ表の総数と一致せず `feature_status.py` の突合が不整合になる(計画レビュー 3 周目 P2)。**`git cherry-pick -n` で内容だけ移して新タスクのステップ表に対応する新しい件名でコミットする**
5. **次の試行の予約**を、**既存のすべての予約より厳密に大きい `attempt_seq`** で**別 PR として先に `develop` へマージ**する(検証器の合格条件 ⑧ が「同一ゲートキーの予約がすべて閉じている」ことを要求するため、**2 を先に済ませないと新規予約が排他規則と矛盾する**)
6. 再受入は**新しいタスク・新しいブランチ**で行う

**経路 B: マージ後検査が不合格だった場合**(F の時点。4-6 はすでにマージ済み)

1. **Phase 4 未完了**とし、**`M` を新たな試験対象 `T` として再受入**する(設計書 `:659`)
2. 本タスクは**マージ済みなので `/task-done` で閉じる** — その**不合格分岐で「Phase 4-6 再試行」タスクを起票**する(必須 3 項目: タスク名に `Phase 4-6 再試行` を含める / 担当者を引き継ぐ / DoD に「`M` を新たな `T` として受入をやり直し、マージ後検査に合格すること」)
3. **再試行タスクの順序を再試行タスクの DoD に明記する**: `seq001` は `passed` の結果証跡で既に閉じており**同一試行へ結果を追加できない**。したがって **① より大きい `attempt_seq` の予約 PR を先にマージ → ② `M` を `T` として受入 → ③ 結果証跡の PR** の順で行う

### 並行タスクへの制約(受入開始前に通知する)

並行して `sync-protocol-design`(同期プロトコル設計の起草)が走っている。**PO 判断 2026-08-27 で 4-6 を先に閉じる**方針とし、同タスクには次を課す:

- 変更は `docs/features/sync-protocol-design/**` と `docs/worklog/**` に限定する(正本・索引・台帳・`.claude/**`・`scripts/**` に触れない — allowlist 配下なので受入証跡を失効させない)
- **台帳への追記もしない**(H-77 の番号衝突回避 + 失効回避)
- `git push` は可(`develop` を進めないため排他区間に触れない)。**PR 作成とマージは 4-6 のマージ後**
- 4-6 の**排他区間中**(受入完走 → マージ後検査の完了まで)は、GitHub UI からの操作も含めて `develop` を進めない
