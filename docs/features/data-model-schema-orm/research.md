# 調査メモ: データモデルのスキーマ本体と ORM 導入(TSK-342)

## 問い

1. **ORM の矛盾はどう成立したのか。** 設計書 10.1(approved)が「ORM は入れない」と定め機械検査まで置いている一方、TSK-250 の承認済み計画が「ORM = SQLAlchemy 2.x を確定」とする。どちらが先で、調停した決定はあるか
2. **「RLS を防御層とする」は要件から導出されるのか。** 導出されないなら、本タスクが自分で決める設計判断になる
3. **要件書はスキーマ本体に何を課しているか。** とくに `FR-015`「DB の一意制約は張らない」は候補案 3-4 の一意制約と衝突するのか
4. **旧システム側の物理形が新スキーマ・models に課す制約は何か**
5. **本タスクが壊してはいけない過去の決定は何か。** 同期プロトコル正本が送っている `WAIT-01`〜`WAIT-08` は誰の射程か

## 結論(要約)

1. **ORM の矛盾は「同じ日に別タスクが逆向きに決めた」もので、後の決定が先の決定を打ち消していた。** `2026-08-31 01:00` に TSK-250 が 3 値を固定し、**同日 13:19 に検査が実装され、23:19 に 10.1 の箇条が入った**(実測)。**TSK-270 側に TSK-250 の裁定を認識した記録は無い。** 調停した決定は存在しない
2. **「RLS を防御層とする」は要件から導出されない。** 要件書・改善台帳に `RLS` は **0 hits**(独立に再確認)。`NFR-010` は結果・適用範囲・検証だけを課し実現層を指定しない。**本タスクが決める設計判断**である
3. **`FR-015` との衝突は成立しない。** 候補案 3-4 の一意制約 18 件 + 複合 FK 6 件を突合し、`FR-015` の禁止範囲と対象が重なるのは**背番号 1 件のみで、候補案の結論も「張らない」= 要件と同じ**
4. **`WAIT-01`〜`WAIT-08` の全 8 件が本タスクの射程**(TSK-335 裁定 `R-1`)。ただし機械可読定義 `waiting-data-model.json` は**未作成**で、定義が読めるのは T250P 履歴節の逐語だけ
5. **人間の裁定が要る論点が 4 件**(申し送り)。うち 2 件は本タスクの成否に直結する(**`game_lineup_snapshot` の存否**・**越境テスト再実行ゲートの所有者**)

### 2. RLS は要件から導出されない設計判断

#### 2-1. 実測(独立再確認)

| 走査対象 | 語 | 結果 |
| --- | --- | --- |
| 要件書 | `RLS` / `Row Level` / `行レベル` / `防御層` / `DBロール` / `GRANT` / `ロール分離` / `アプリ層` | **0 hits**(`防御` の 3 hits はすべて「**防御率**」と `NFR-011` の「総当たり試行への防御」) |
| 改善台帳 | `RLS` / `ROW LEVEL` / `防御層` / `ORM` / `SQLAlchemy` | **0 hits** |

→ **TSK-335 の調査 §2 の実測と一致**(独立に再確認済み)。

#### 2-2. `NFR-010` と `I-2` が課しているもの

**`NFR-010`(Must)が課すのは 3 つだけ**:

- **結果** — 「それ以外の他チームのデータ資源は**内容・存在を含め参照できない**」
- **適用範囲** — 「**テナント分離は初日から全機能に適用する**」
- **検証手段** — 「越境アクセスの自動テスト(API 直叩き含む。CI に常設 → `NFR-019`)」

→ **実現層(DB / アプリ)を指定していない。「防御層」という概念語も出てこない。**

**改善台帳 `I-2` が指名する手段は `team_id` による分離**であり、RLS・DB ロール・関数 ACL は書かれていない。
**`team_id` という識別子自体も要件書には現れない。**

#### 2-3. RLS 以外の手段を要件が許すか — 許す(禁じる条項が無い)

| 条項 | 含意 |
| --- | --- |
| 要件書 7.1「**DB は標準 PostgreSQL の範囲で使用**し、ホスティング固有機能に依存しない」 | RLS は PostgreSQL コア機能なので**採ってもよい**。同時に**要求もしない** |
| `FR-033` 補足「認証は**アプリの 1 層のみ**」 | 唯一「層」を語る条項だが対象は**認証**。認可・テナント分離ではない |
| `FR-034` 受入基準 | 経路の網羅を要求するが**どの層で塞ぐかは指定していない** |
| `NFR-012` | 分離は**認証の系統**の話で DB ロールを要求しない |

→ **アプリ層のみでの実現を禁じる条項も、DB 側での実現を要求する条項も存在しない。**

#### 2-4. 候補案 3-1 の根拠の内訳 — 半分は候補案自身の推論

候補案 3-1 が挙げる根拠は 3 種類だけ(先行する決定記録 `D-*`・`I-*`・ADR を根拠にしていない):

1. **要件条項** — 7.1 / `NFR-010` / `FR-034`(= **事実**)
2. **PostgreSQL 公式ドキュメント**(RLS は 9.5 のコア機能・default-deny・バイパス経路の列挙)
3. **却下案 3 件の消去**(アプリ層強制のみ / RLS のみ / **Supabase の認可機能に寄せる** ← 禁止事項 `P-04` 違反)

そして「**アプリ層だけの強制は、管理画面・バッチ・将来のリポジトリ層・手書き SQL で条件を落とした瞬間に隔離を失う**」は
**要件書の条文ではなく候補案の技術的推論**である。

→ **「RLS を防御層とする」は候補案が自前で立てた設計判断であり、正本化されていない。**
論点の起源は TSK-248 計画書の**論点 3「RLS の採否とロール分離」= (A) 分類**。

#### 2-5. ただし「RLS を採る」と決めた瞬間にテーブル制約が従属する

候補案 3-4 冒頭の「動かせない事実」(PostgreSQL 17 公式 `ddl-rowsecurity.html` の逐語):

> Referential integrity checks, such as unique or primary key constraints and foreign key references, **always bypass row security**

→ **一意制約と外部キーは RLS を必ず貫通する。** `NFR-010` が「内容・存在を含め参照できない」を要求するため、
素直に設計すると**制約違反エラーが他テナントの行の存在を漏らす**。
そこから **規則 1(一意制約は `tenant_id` を先頭に含める)**・**規則 2(テナント内 FK は複合参照)**・
(b) 事前認可 / (c) 制約違反詳細の一律秘匿 / (d) 越境 FK は存在秘匿対象外のクラスに限る、が導かれる。

**同じ導出は 2 つの一次記録にも残る**: `docs/worklog/2026-08-21-product-data-model-design.md`「Web 調査で設計を左右した事実」節 /
TSK-248 計画書 2 節 論点 2 行「参照整合性が RLS を貫通するため。**FK 一般の禁止ではない**(レビュー 1 周目 P0 で是正)」。

→ **「テナント内一意 + 複合 FK」は `NFR-010` と「RLS を採る」の"組"から導かれる。要件単独からは導かれない。**
TSK-335 の裁定 `R-1`「外すと複合 FK を選ぶ理由が消える」はこの構造を指している。

### 3. `FR-015` との衝突は成立しない

#### 3-1. `FR-015` の禁止範囲

要件書 `FR-015` 受入基準 第 2 項の逐語:

> Given 同じ背番号の現役選手が存在 / When 同番号で登録 / Then 警告が表示される
> (意図的なら登録可。**DBの一意制約は張らない**。OB選手の番号は再利用可)

Given / When が「**同じ背番号の現役選手**」「**同番号で登録**」に限定されているため、
**禁止の対象は `背番号` 属性に対する一意制約**である。条文が排除する挙動は 3 つ:

| 禁止されている挙動 | 典拠 |
| --- | --- |
| 同番号の**現役**選手が併存できないこと | `FR-015` 第 2 項 |
| **OB 選手の番号を再利用できない**こと | 同項 |
| 背番号が**必須**であること | `FR-015` 第 1 項「**背番号は任意**(B戦の番号なし選手も登録可)」 |

**補強**: 改善台帳 `I-12` は旧システムに「**DB は「チーム内で背番号一意」制約のため、卒業生の背番号を新入生が引き継げない**」があったことを記録し、pitchlog 側の改善を「**OB の背番号再利用も普通にできる**」と定めている。
→ **禁止対象が `UNIQUE(チーム, 背番号)` であることは台帳側からも一致して読める。**
→ **5-1 のとおり、旧 `player` にこの制約が実在する。`FR-015` はそれを外す決定である。**

#### 3-2. 候補案 3-4 の一意制約 18 件・複合 FK 6 件の突合結果

**重なるのは 1 件のみ**(背番号・`design.md:769`・`:826`・`:1814`)で、**候補案の結論も「張らない」= 要件と同じ**。
候補案自身が明記している(`design.md:222-225`):

> **この規則は要件と衝突しない**: 要件が一意性を求める箇所…は**いずれもテナントかグループの内側**にある。
> 逆に**背番号は明示的に「DB の一意制約は張らない」**ので対象外

**残り 23 件は `FR-015` と対象が重ならない**(操作イベントのべき等キー / `(試合, 世代番号)` / 出場区間 / 自チームレコードの部分一意 / 参加の `WHERE active` 部分一意 / 付与 `(グループ × 自テナント)` / カルテ所見 `(選手, カルテ種別)` / 語彙・設定値・規則セット / テナント内 FK の複合参照 6 件 ほか)。

**前タスクの §12 は「衝突している」と書いていなかった** — 「**踏むな**」という**遵守条件**として挙げていた
(合格条件 `B-5`「`FR-015`「DB の一意制約は張らない」を踏まないこと」)。→ **要件改訂は不要。**
