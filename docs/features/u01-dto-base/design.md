## 2. 共通基底モデル

**現状**: `schemas/base.py` の 5 クラスが**すべて `pydantic.BaseModel` を直接継承**し、
**`ConfigDict` は `backend/src` に 0 件**([research.md](research.md) 3-1)。

### 置くもの — 基底 2 本

| 型 | 設定 | 用途 |
| --- | --- | --- |
| **`BaseSchema(BaseModel)`** | `extra="forbid"` | **すべての DTO の根**。要求・応答の別を問わない |
| **`ReadSchema(BaseSchema)`** | `from_attributes=True` を追加 | **読み取り応答**。葉が ORM の行から組み立てる |

**基底を 2 本に分ける理由**(**(B)**): `from_attributes` を根に置くと**要求 DTO にも属性読みが効く**。
要求は外から来る JSON だけを受けるべきなので、**読み取り側にだけ付ける**。
1 本にすると葉が毎回 `ConfigDict` を書くことになり、**設定の重複**が生まれる。

### `extra="forbid"` を既定にする理由(**(B)**)

**未知のフィールドを黙って捨てない。** 捨てると、**クライアントの綴り誤りが「無視された」形で通り**、
`FR-002`「**不足項目が明示されて確定できない**」(要件書 `:207`)の趣旨と逆向きになる。
拒否すれば `RequestValidationError` → **器が 422 + `fields` へ写す**(既存経路)。

**後方互換への影響**: 既存 5 クラス(`ErrorField` / `ErrorDetail` / `ErrorEnvelope` /
`HealthResponse` / `VersionResponse`)は**いずれも未知フィールドを受け取らない**ので、
**基底の差し替えで外形は変わらない**。**ステップ 1 の合格条件で機械的に確認する。**

### 採らなかった設定

| 案 | 採らない理由 |
| --- | --- |
| `frozen=True` | **不変にする根拠が無い**。葉が組み立て途中で書き換える形を先に禁じることになる |
| `alias_generator`(camelCase 化) | **DTO のフィールド命名を定めた決定が存在しない**([research.md](research.md) 1-2)。**camelCase を採るのは根拠の無い先決**。Python 既定の snake_case のままにする |
| `populate_by_name` | 別名を持たないので効かない |

## 3. ID の共通型

### 置くもの

**`EntityId`** — サロゲート ID の型別名。**実体は `uuid.UUID`。**

### 根拠の層(**(B) 実装事実に合わせた判断**)

- **UUID のサロゲート ID に限れば**、ORM は例外なく `Uuid(as_uuid=True)`。
  **自然キー(`intent_id` は `Mapped[str]`、`game_type_key` / `tournament_key` / `key` は `Text`)と
  同期系の `D1`〜`D4`(数値)は別系統**であり、`EntityId` の対象外(**1 周目 `P2`**)
- **しかしこれを固定した正本条文は無い**([research.md](research.md) 1-2)。
  **型まで固定された正本の ID は「断中の一時 ID = `uuid`」の 1 件だけ**(要件書 `:363`)
- **`ULID` の語は `docs/` に 1 件も無い**

→ **「正本の帰結」ではなく「実装事実に合わせた」と明記する。**

### 直列化(**(B)**)

**JSON では文字列。** pydantic の既定に従い、独自の直列化を書かない。

### **非目標 — この型は資源を一意に指さない**(**重要**)

**テナント所有表の大半が `(tenant_id, id)` 複合主キー**である([research.md](research.md) 3-2)。
**`EntityId` が表すのは複合キーの `id` 側だけ**で、**テナント文脈は含まない。**

**したがって `EntityId` を認可判定に使ってはならない**(**(B) の判断**)。
テナント文脈は **`set_config('app.tenant_id', …, true)` でトランザクション側に束ねる**のが正本
(`data-model.md:308-332`。RLS が default-deny なので未設定なら 0 行 — `:331`)。

**ただしこれは DB トランザクションの RLS 文脈についての規律であって、DTO の禁止ではない**
(**3 周目 `P0` で是正**)。**管理関数の引数は逐語では (b) 対象テナント**または**対象試合 / (c) 対象 / (d) 代表するテナント**
(同 `:1573-1575`。**4 周目 `P0` で逐語へ是正**)。**いずれも DTO のテナント識別子を禁じる条文ではない。**
**base 型に載せないのは `NFR-010` の帰結でも原典の具体化でもなく、カード由来の DoD を受けた (B) の判断**である。

**この非目標を型の docstring に明記する。** 後続の葉が `EntityId` をそのまま資源 ID に流用して
**分離の担保が DTO 層で消える**ことを防ぐため。

### 採番しない

**ORM の ID 列に既定値が無く(`default=` / `server_default` / `Identity` が 0 件)、アプリ層が採番して渡す前提**
だが、**採番そのものは `U-01` の射程外**(サービス層の責務)。**型だけを置く。**

## 4. 時刻の共通型

### 置くもの

**`Timestamp`** — **タイムゾーンつき日時**の型別名。**naive な日時を拒否する。**

### 根拠の層

| 層 | 内容 |
| --- | --- |
| **(A)** | **日時は JST 基準で扱う**(年度 4/1 判定・試合日の基準 — `D-33 ①`・要件書 `:1019`) |
| **(A)** | **多言語・タイムゾーン対応は Won't**(`NFR-022` 要件書 `:109`,`:972`) |
| **(B)** | **aware を要求する**(naive を拒否)— ORM が `DateTime(timezone=True)` 39 箇所すべてで揃っている実装事実に合わせる |

### 決めないこと

| 項目 | 理由 |
| --- | --- |
| **精度(秒・ミリ秒・マイクロ秒)・丸め** | **決定が存在しない**([research.md](research.md) 1-3)。**型は精度を強制しない** |
| **どのエンティティが時刻属性を持つか** | **イベントが時刻属性を持つかを定めた条文が要件書に無い**(`TSK-327` へ送済・未反映) |
| **年度・試合日の境界判定** | **`U-01` は判定を書かない。** 型だけを置く。境界判定はドメイン計算側 |

**`NFR-022` との関係**: **任意タイムゾーンを DTO で受ける抽象(tz 名を受けるフィールド等)を作らない。**
`Timestamp` が要求するのは「offset を持つこと」までで、**タイムゾーンの選択肢を表に出さない。**

## 5. ページング型

### 決める範囲(**PO 判断 2026-09-17**)

**形だけ決め、値は決めない。** [plan.md](plan.md) 2 節。

### 置くもの

**契約として確定する(1 周目 `P1`)。** フィールド名・必須性・「継続なし」の表し方まで決める。

| 型 | フィールド | 必須 | 「なし」の表し方 |
| --- | --- | --- | --- |
| **`PageRequest`** | `limit: int` | **必須**(**既定値を持たない**) | — |
| | `cursor: str \| None` | 省略可 | **`None`**。**空文字列は受け付けない** |
| **`Page[T]`**(ジェネリック) | `items: list[T]` | 必須 | 空配列 |
| | `next_cursor: str \| None` | 省略可 | **`None`**(次ページが無い)。**空文字列は受け付けない**(**2 周目 `P1`**) |

**`limit` に置く制約は下限だけ** — **1 以上**。`0` と負数は一覧として意味を持たないため。
**上限は置かない。既定値も置かない。**

**`cursor` / `next_cursor` の中身は不透明**で、**書式は `U-01` で決めない**(葉と `TSK-346` の判断)。
**`cursor` と `next_cursor` の双方で空文字列を拒否する**のは、「継続なし」の表し方を `None` の 1 通りに閉じるため
(**2 通りあると葉ごとに解釈が割れる**)。**当初 `next_cursor` 側が漏れていた**(**2 周目 `P1`**)。

### 位置を「不透明な文字列」にする理由(**(B)**)

**方式を offset に固定しないため。**

`data-model.md:1572` は**管理コンソールの横断一覧について「キーセット方式」**を定めている。
**要求型に `offset` を置くと `U-A2`(管理経路)で食い違う。**
**不透明な文字列にしておけば、キーセットでもオフセットでも実装側が選べる。**

**中身の書式は `U-01` で決めない**(葉と `TSK-346` の判断)。

### **既定値・上限定数・clamp を持たない**(**検査できる形へ言い換えた — 1 周目 `P1`**)

当初「型に数値を持たない」と書いたが、**件数フィールド自体が数値なので検査できない**。
**次の 3 つが無いこと**で言い換える。

**判定仕様まで決める。** **構成の列挙をやめ、振る舞いで見る(3 周目 `P1` — 列挙は必ず抜ける)。**

**2 周目に置いた 4 判定は破綻していた**: 「モジュール名前空間に callable が無い」は
**モデルクラス自体が callable なので必ず失敗**し、型を除外しても
**`Annotated[..., AfterValidator(...)]` / `__init__` / `model_post_init` / インライン lambda** が抜ける。

**上限も clamp も、どう実装しても「拒否する」か「値を変える」かのどちらかになる。** そこを見る。

| # | 検査(**振る舞い**) | 何を覆うか |
| --- | --- | --- |
| **1** | `PageRequest.model_fields["limit"].is_required()` が真。**かつ**未指定の構築が `ValidationError` | **既定値** |
| **2** | **標本値を素通しする** — `limit` が `10**3` / `10**6` / `10**9` / `2**63-1` のいずれでも `ValidationError` にならず、**`.limit` が入力値と等しい** | **上限制約・clamp・検証器・`model_post_init`・lambda・別名/import 経由**を、**標本の範囲で**捕まえる |
| **3** | `limit=0` と `limit=-1` が `ValidationError` | **下限が効いている** |
| **4** | `limit=1` が通り `.limit == 1` | **下限の境界が 1 ちょうど**(**個数ではなく値を固定する** — 3 周目 `P1`) |
| **5**(補助) | `model_fields["limit"].metadata` に `Le` / `Lt` が無い | **早期に気づくための構造検査**。**本体は 2** |

**2 が本体**である。**構成を列挙しないので、将来の書き方にも効く。**

#### **この検査は網羅ではない(限界の明示 — 4 周目 `P1`)**

**有限個の標本で「上限が無い」ことは証明できない。** 例えば **`AfterValidator` で `2**63-1` 以下だけを通せば、
標本 4 値と補助検査 5 をすべて抜けて、それより大きい値だけを拒否できる。**
**当初「すべてを覆う」と書いたのは成立しない主張だった。**

**したがって本検査は「上限を課す実装が無いことの証明」ではなく、
「よくある上限の置き方を標本で捕まえる」ものである。**
**上限を課さないことは規律として守り、検査はその部分的な証拠にとどまる。**
**`schemas/base.py` は小さく、レビューで読み切れる大きさに保つ**ことを併せて守る。

**既定件数・上限件数の値は各葉の単位か設定値の正本が持つ。**

**理由**: **実クエリが 1 本も無い段階で数値を固定するのは根拠の無い固定になる**
(同期プロトコルが「バッチサイズ・バックオフ定数」を実装計画へ送った前例 — `sync-protocol.md:1552` 論点 18)。

### 上限超過の規約(**(B)**)

**`U-01` は件数を黙って詰める補助関数を置かない。** 上限の判定と拒否は葉の責務であることを型の docstring に書く。

**根拠の範囲を限定する(1 周目 `P0`)**: 要件書 `:508`(`FR-041`)/ `:628`(`FR-034`)の
「**同時比較表示上限を超える集合の要求は要求全体を 400 で拒否する(切り捨てない)**」は
**比較対象テナント集合についての規則**であり、**`PageRequest` の件数上限一般へ直接は及ばない**。
**当初これを (A) として一般化して書いたのは誤りだった。**

**clamp を置かない判断は (B) の設計判断**である。理由は**同型の規則が要件書に 1 つ存在する以上、
基盤が逆向き(黙って詰める)の既定を与えるのは筋が悪い**というものであって、条文の帰結ではない。

### `total`(総件数)を持たない理由(**(B)**)

**共通封筒がすべての一覧に総件数クエリを強いる形にしない。** 必要な画面が出てきたら、その葉が自分の応答型に足す。

**`NFR-005` を根拠にしない(1 周目 `P0`)**: **SQL の `COUNT` は `NFR-005` が禁じる「全件読み込み型の集計」ではない** —
同条は「**DB 側絞り込み・集計(WHERE / GROUP BY + インデックス)を基本規律とする**」と述べており、
**`COUNT` はむしろ同条が是とする側**である。**当初「`total` は `NFR-005` と衝突する」と書いたのは誤りだった。**

**キーセット方式と総件数は相性が悪い**(次ページの位置が分かっても総数は別クエリになる)という
**設計上の理由**で置かない。**(B) の判断**であり、条文の帰結ではない。

### 語彙の制約

**`generation` を使わない。** 既存の規約テストが `api/**` の全文連結に対して部分一致を掛けるため、
**docstring とコメントにも書けない**([plan.md](plan.md) 4 節)。
ページ位置の語彙には `cursor` 系を使う(**禁止語に含まれない** — 実測)。

## 6. バリデーション写像

### `U-00` から送られたもの

**フィールド単位の検証規則・DTO 側の写像**(`u00-api-shell/plan.md:62`)と、
**`fields` の `location` 書式のうち配列添字の扱い**(同 `design.md:182-183` — 「経路が生えてから確定でよい」)。

### 確定する書式(**(B)**)

**`loc` タプルを `.` で連結する。配列添字も同じく `.` で連結する。**

```
body.player_name            スカラー
body.players.0.name         配列添字を含む
```

**これは現在の実装がすでに出す形**(`errors.py:57` の `".".join(str(item) for item in error["loc"])`)。
**`U-01` は書式を確定してテストで固定するだけで、`errors.py` を変更しない。**

**角括弧形式(`body.players[0].name`)を採らない理由**: **現行実装の出力を変えることになり、
器のコードを触る必要が出る。** 射程が器へ戻るのを避ける。**利得は読みやすさだけ**で、
**`TSK-346` が別の形を定めたらどのみち従う**(暫定規約)。

### 守る制約(**層を正した — 1 周目 `P0`**)

**当初これらをすべて (A) と書いたが、`U-00` 自身が (B) としているものが混ざっていた。**

| 層 | 制約 | 典拠 |
| --- | --- | --- |
| **(B)** | **`fields` に `input`(入力値)と pydantic の内部メッセージを載せない** | `u00-api-shell/design.md:67`。**`U-00` が (B) として置いた安全側規約**。**`NFR-023` を根拠にしない**(同条の対象経路に API の JSON 応答は含まれない — 要件書 `:967`) |
| **(B)** | **エラー封筒に `code` を足さない** | 同 `:65`。**`U-00` が (B) として置いた規約**(`TSK-346` 従属)。既存の規約テストが機械的に検査 |
| **(B)** | **422 を 400 に読み替えない** | 同 `:97-98`。**400 が業務規則である**ことは (A) だが、**422 を採るという選択自体は `U-00` の規約** |
| **規約由来**(**要件の帰結ではない** — **2 周目 `P0`**) | **シークレット・認証情報をログに出さない** | **`AGENTS.md` の Code Review Rules**。**`NFR-014`(要件書 `:867-870`)は「リポジトリに含めず環境変数で管理する」であり、ログの規定ではない**(実測)。**`NFR-015`(同 `:872-875`)の対象も「データ保存・同期・バックアップ・出力の失敗」に限定** |

**入力値の扱いは 3 つに分けて書く(1 周目 `P1`)** — **pydantic の `ValidationError` は内部に `input` を保持しうる**ので、
「例外へ入力値を載せない」は**そのままでは成立しない**。

| # | 禁じる面 | 層 | 検査 |
| --- | --- | --- | --- |
| 1 | **応答本文に入力値が現れない** | **(B)** `u00-api-shell/design.md:67` | 否定テスト(`U-00` の `test_api_errors.py:110` を継承) |
| 2 | **`U-01` が書くログに入力値を出さない** | **(B)** `U-00` の申し送り(同 `:110`,`:186`) | `U-01` はログを書かない(`schemas/` に logger を置かない)ことで満たす |
| 3 | **`U-01` が定義する独自の例外・検証メッセージに入力値を埋め込まない** | **(B)** 同上 | メッセージ文字列に値を差し込む書き方をしない |

**pydantic が内部に持つ `input` そのものは禁止対象にしない** — **器が `loc` だけを取り出して写す**ので応答には出ない。

### 検証の当て方

**`U-01` は経路を登録できない**(述語 4)ので、**ボディを持つ一時アプリをテスト側に組んで実測する。**
**`U-00` の前例**: `backend/tests/api_fixtures.py` の `create_error_test_app()`。
**同じファイルへ、配列を含むボディを受ける一時アプリを足す。**

**`ROUTERS` を経由しないので述語 4(経路ちょうど 2 本)には当たらない。**

## 7. 検討して採らなかった案

| 案 | 採らない理由 |
| --- | --- |
| **`ResponseValidationError` を 422 系へ写す** | **塞ぐには `errors.py` を触ることになり射程が器へ戻る。別タスクへ送る**([plan.md](plan.md) 7 節)。**「踏まない」とは書かない(1 周目 `P0`)** — **`/health` `/version` には既に `response_model` があり、`U-01` はその基底を差し替える**。**`U-01` が足さないのは「新規の本番経路」と「新規の応答モデル束縛」**であって、応答検証の経路が無いわけではない |
| **camelCase のフィールド別名** | **命名を定めた決定が存在しない**。採ると根拠の無い先決になる |
| **`total`(総件数)を封筒に持つ** | **キーセット方式と相性が悪く、共通封筒がすべての一覧に総件数クエリを強いる形になる**(5 節)。**`NFR-005` を根拠にしない** — **`COUNT` は同条が禁じる「全件読み込み型」ではない**(**2 周目 `P0`**) |
| **offset 方式の要求型** | `data-model.md:1572` のキーセット方式と `U-A2` で食い違う(5 節) |
