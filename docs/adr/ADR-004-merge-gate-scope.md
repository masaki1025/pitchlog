## 文脈

`data-model.md` 12-4 節の**越境テスト再実行ゲート**は、「**DB を利用する製品機能**の実装 PR」を対象に
**越境テストが green** であることを通過条件とし、測定経路を「**アプリ経路だけの検証では通過にしない**」と
定めていた。**この条文は具体的なタスク依存の輪を作っていた。**

```
FR の実装(= DB を利用する製品機能の PR)
  → 12-4 のゲートの対象
  → 通過には越境テストの green(NFR-010 の測定方法が「API直叩き含む」と定める)
  → その越境テストの所有者は TSK-217
  → TSK-217 の前提は「FR-041 の実装が先。実装がないと構成できない」
  → 振り出し
```

**これを解かない限り、製品機能の PR は 1 本も通せない。** 調査は TSK-378 で行い、
事実と典拠は [`docs/features/merge-gate-api-cycle/research.md`](../features/merge-gate-api-cycle/research.md)、
選択肢の比較は同 [`design.md`](../features/merge-gate-api-cycle/design.md) が持つ。**本 ADR は内容を複製しない**(設計書 7.1-1)。

**条文だけでは決着しなかった。** 12-4 の測定経路の規範文は禁止の形だが、
`data-model.md` 内で「API 直叩き」の用法が 2 つに割れていた —
アプリ層のみの検証を否定する語としての用法と、全経路の網羅を要求する語としての用法である。
**同一文書の中で引っ張り合っており、字面の読みだけでは決まらない。** そのため PO 裁定を求めた。

## 理由

### なぜ「当該 PR が開く経路」で切ったか(D-1)

**先例が同型の輪を同じ形で解いている。** ADR-003 は、検査は生成物・製品入口・変異対象が
存在しないと緑にできないので「**緑になってからコードを追加する**」とは書けないとし
(`ADR-003` `:387`)、`NFR-018` の発効条項を「**未完成のあいだ適合と判定しない**であって、
実装を禁じるものではない」と読んだ(同 `:390`)。**本件は対象が `NFR-010` に替わっただけで、
輪の形は同じである。**

**要件書自身が 2 つの時点を分けている。** **主典拠は 8 章のリリース判定基準**である —
**基準 1** が Must 要件の受入基準充足を、**基準 2** が `NFR-019` の (a)〜(d) すべての成功を、
**リリース可の判定条件**として置いている。**対象横断の網羅の成立を求めているのはこの時点である**、
というのがこの箇所を主典拠に置いた理由である。
**個々の PR について `NFR-019` の柱書が求めているのは「その時点で走るテストが全グリーンであること」**であり、
**網羅の成立ではない**。**この 2 つの区別が条文に書かれていなかった**ことが `D-3` の起点である
(**発効済みのテストは個々の PR でも全グリーンでなければならない** — 本決定はそこを緩めていない)。
`NFR-021` の測定方法も「Phase 4 完了時」と
「リリース候補時」を分けているが、**同項は開発環境の受入プロファイルの条項であって
`NFR-010` に一言も言及していない**ので、**従たる傍証として扱う**。

**ADR-003 型の一般則が `NFR-018` に限定されている**ことが弱点だった
(ハーネス設計書 `:897` の「ただし `NFR-018` の対象計算に触れる実装は」)。
**`NFR-010` / 12-4 へ転移させるには明示の裁定が要る** — それが本 ADR の存在理由である。

### なぜ「同一 PR に直叩きテストを含む」で充足としたか(D-2)

**これは現行条文の読みではなく、条文化を要する新しい適用規則である。**

**根拠にしなかったものを明示する。** `data-model.md` の「アプリ層のみだと『新しい経路を書いたが
テストを書き忘れた』が越境そのものになる」という記述は、**DB 側に既定拒否を置く理由**を述べた箇所であり、
**API 直叩きという測定経路を DB 層のテストで代替できるとは言っていない**。**裁定 B の根拠にしていない。**

**支えたのは条文の形と最低要求の中身である。** 測定経路行の規範文は**禁止**の形であり、
**越境テストの最低要求 4 件は全件が DB ロール・関数 ACL・`search_path`・関数の返却契約への要求で、
HTTP への要求を 1 件も含まない**。**したがって禁止を「開いた経路について効く」と読む余地があった。**
**ただし最低要求 4 件を満たすことは下限の充足にすぎず、`NFR-010` の「API直叩き含む」を
充足する根拠にはならない** — だから**開く PR の側に直叩きテストを課す**形にした。

### なぜ要件書を触ったか(D-3)

**当初の計画は「要件書は反映なし」だった。これは成立しない。**

`NFR-019` の柱書は「**PRごとにCIで自動実行、全グリーンでないとマージ不可とする**」(逐語)と
**その CI に `(b)` 越境アクセステストを含めること**を、同じ要件文で結んでいる。
`(b)` は網羅すべき組合せを列挙しているが、**`NFR-018` の正解ベクタ条項
(「**完成をもって正解ベクタとして発効する。完成前にNFR-019(a)を合格と判定してはならない**」— 逐語)に
当たる条項を持たない**。
**12-4 は下位文書なので上位の義務を解除できない。**

**決め手は成立可能性である。** 柱書が PR ごとに網羅の完成を要求すると読むなら、
**`(b)` を実装する PR 自身を含めてどの PR もマージできず、要件が成立しない**。
したがって **`(b)` 側に発効条項を置くほかない。**

**`NFR-018` と同型だが向きは逆である。** `NFR-018` は「**完成前にNFR-019(a)を合格と判定してはならない**」
(未整備を適合と偽らないため)、`NFR-019(b)` は「**発効前の経路に係る組合せを理由に本項(b)を
不合格と判定してはならない**」(実装が存在しない経路の越境テストは書けないため)。**いずれも逐語。** **同型なのは「実体が無いものについて判定を下さない」
という原則の方**で、**禁止の向きは実体が無いことの帰結が逆だから逆になる。**

### 採らなかった案

| 案 | 却下・不採用の理由 |
| --- | --- |
| **現状維持(裁定しない)** | **FR の実装 PR が 1 本も通せない状態が続く。** ハーネス設計書は同型の詰まりを「Phase 表が Phase 5 で終わることにより製品実装の位置づけが規範上不明で、**それが着手を止めていた**」(`:64`)と記録している |
| **`NFR-010` を改訂する** | ① **具体的な文案が無い状態で上位正本の改訂を選ぶと射程が定まらない** ② 改訂すれば `NFR-019(b)`・`FR-034` の受入基準まで波及面が広がる ③ **D-1・D-2 で足りる** |
| **例外規定(初回免除)を 12-4 へ新設する** | 上と同じ理由に加え、**旧システムの失敗モードの再現に向かう**(アプリ層のみの分離で `owner_team_id` がオプショナル引数、省略すると全データにアクセス可能 — `docs/legacy/research/data-layer.md:397`) |
| **TSK-346(API 契約の正本)へ 12-4 の解釈を畳む** | **射程侵犯。** 12-8 節が「越境テスト再実行ゲートの定義(12-4 節)」を `data-model.md` の確定範囲と宣言し、射程変更を 7.3-6 の PO 裁定に限定している。加えて設計書 7.1-1「**1 テーマ 1 正本 — 内容を複製しない**」・7.6 柱書「**同じ規則を別文書で再定義しない**」に反する |
| **常時 404 を返す deny 経路を先に入れる** | **何も証明せず、実装が入った瞬間に測り直しになる。** 設計書 7.3-3 の P1 の定義「**「文言は直したが実効がない」型を含む**」に当たる |
| **裁定だけ取り、条文を変えずに運用する** | **正本を変えずに新しい規範は効かない。** 条文に残らないと、TSK-317 の計画書が書いた「本タスクの成果を『`NFR-010` 適合』と主張しない」との緊張が条文上に残り、**別文書の全文レビュー周で再燃する** |
| **`data-model.md` 12-4 の単独改訂**(ADR を作らない) | **確定ゲートの回数では差が付かない**(一括検証は単一のゲート — 設計書 `:437`)。**レビュー面はむしろ増える。** それでも ADR を採ったのは、**裁定の理由の残り方**が違うからである — 単独改訂では**変更履歴の 1 行**にしか残らないが、本件は「条文が二読可能で、どちらを採るかを決めた」という**争点そのものが後から参照される**性質を持つ |

## 帰結

- **本 ADR がマージされるまで、製品機能 PR に効くのは現行の 12-4 である。**
  TSK-378 は裁定を取り条文化の受け皿を作っただけで、**ゲートを解除していない**
- **律速は本 ADR ではない。** 12-4 の通過条件①(RLS のポリシーとロールの DDL が実スキーマへ適用)が
  未充足であるかぎり誰も通過できず、**その産出者は TSK-317 である**。本決定は
  **①が充足した直後に詰まらないための先回り**である
- **裁定は「経路」単位で下されたが、条文では「入口」単位になった。** `route_id` は
  `contracts/authz/http-route-matrix.json` の論理経路の識別子で、**HTTP の method / path と
  1 対 1 に対応しない**。経路単位のままだと、**既存の `route_id` へ 2 本目の入口を足す PR が、
  新しい外部入口を作るのにゲートも直叩きテストも発火しない**(確定ゲート 3 周目 `P1`)。
  **判定が細かくなる方向の精密化であり、裁定 A の意図を緩めていない。**
  **「入口」と「経路」の定義は 12-4 節「経路と入口の定義」が持つ**
- **判定の記録の項目が 1 つ増えた** — 「**どの入口について判定したか**」(`route_id` と入口の両方 —
  12-4 節のゲート表「判定の記録」行)。**`route_id` だけでは、同じ経路の別の入口を既存の証跡で
  通したのかどうかが区別できない**からである
- **`contracts/authz/http-route-matrix.json` が経路識別子の正になった**(12-4 節「経路の定義」)。
  **識別子を持たない入口を開いた場合の扱いも同節が定めている** — 本 ADR は定めない
- **`NFR-019(b)` の網羅すべき組合せは 1 件も減っていない。** D-3 が変えたのは**判定の時点だけ**であり、
  合否の基準・網羅すべき組合せ・製品が満たすべき挙動は変えていない
- **設計書 v1.14 が TSK-353 の射程と宣言していた「12-4 節冒頭の現況化」を、本改訂が先に履行した。**
  TSK-353 の側にこの項目が空手形として残るため、同タスクへ申し送った
- **本 ADR が受け取り先を実 ID で持つのは 2 件である** — **[TSK-382](https://app.notion.com/p/3d993b75e68781c094f9caf50fbceeab)**(`SP-06` との字面衝突)と
  **[TSK-383](https://app.notion.com/p/3d993b75e68781ad8663dce3ac2484a2)**(「経路を開く」の機械判定)。
  **どちらも受領範囲を先方の本文に書いた** — 台帳の「送り先が空手形になる」型を自分で再生産しないためである
