## 文脈

### なぜこの決定が必要か

要件定義書 **NFR-018「ドメインロジックの単一実装」**が、実現手段と検査方式の決定を設計フェーズの ADR へ委任している。委任の範囲は要件書 v2.1(2026-08-18 approved)の申し送りと 10 章未決事項表が定める:

| # | 委任項目 | 典拠 |
| --- | --- | --- |
| ① | **実現手段**の選択(共有ランタイム / WebAssembly / コード生成 等) | [要件書](../requirements/requirements-pitchlog-2026-07-22.md) NFR-018 の申し送り・10 章 |
| ② | **達成条件 (b)② の検査方式**(探索対象の閉域の具体化・実行入口の定義・生成物の識別・動的ロード等の禁止規則・到達性検査の方式) | 同上 |
| ③ | **正解ベクタと比較面の整備**(付録A 固定ベクタ・付録E 全表・FR-022 の当日打席結果の列定義) | 同上 |
| ④ | **「実現不能」と結論する判断そのもの** | 同 NFR-018 達成条件 (b)・10 章 |

**要件が既に固定しており本 ADR で緩められない制約**: (α) は「クライアント・サーバーの双方が同一のコードに由来する実行体を用いる」/ (β) は「サーバー内で人手保守する実装が 1 系統」/ 対象の列挙は NFR-018 が正(実装判断で対象から外せない)/ (b)② の 3 不変条件(**検査対象は本番に到達可能なソース・生成物・実行入口の全域** / **未分類・判定不能は fail-closed** / **対象範囲を縮小して満たしたことにはできない**)/ 正解ベクタは完成をもって発効し完成前に NFR-019(a) を合格と判定しない / **(α)(β) の区分をコア領域の境界に用いない**。

### 発火点と、期限が一度失効していた事実

本 ADR の発火点の**正は要件書 NFR-018 の申し送りと 10 章未決事項表**であり、本 ADR は複製せず参照する。

**この申し送りの期限は一度失効している。** 当初は「Phase 4 着手前に ADR で確定する」と定められていたが(要件書 v1.8・開発ハーネス設計書 4 章)、**Phase 4-1(frontend 骨格)と Phase 4-3(docker-compose + contracts 雛形)が先に実施され、期限を過ぎた状態が続いた**。さらに要件書 v2.1 の確定ゲートで、**再設定した「対象コードを最初に作成する前」も既に遵守不能**であることが判明した — `frontend/src/lib/courseInputView.ts` の座標変換が既に存在し、`frontend/src/components/zone/StrikeZone.vue` の実行経路から呼ばれていたためである。**現行の発火点は要件書 v2.1 が現況から到達可能な形へ再設定したもの**で、既存の対象コードは本 ADR の確定まで現状維持のみ許容される。

### 本 ADR が属する位置

**本 ADR は開発ハーネス設計書 13 章の Phase 4 のどのスロットにも属さない**(4-1〜4-6 + `P4-後` のいずれにも ADR を担当する行が無く、Phase 4 の範囲は 4-1〜4-6 で閉じている)。実態としては **Phase 4-3 の積み残しの受け皿**であり、同スロットが意図的に空けた項目(付録E マトリクス・付録A 固定ベクタ・付録B-6 領域シード・付録D スキーマの中身、および `contracts/` 内の形式・命名規約)を引き取る。

### 旧システムが示した事実

**旧システムは同趣旨の要件(旧 NFR-011・Should)を持ちながら、1 年以上多重実装を解消できなかった。** 重要なのは「共有物が無かったから失敗した」のではないことである — 共有モジュール(`domain/out_statuses.py`・`domain/batting_results.py`)と共有契約ファイル(`shared/display_geometry_263_v1.json`)は**実在していた**。版固定資料の結論は「**定義は domain/ 共有だがロジックは別コード**」(`../legacy/research/analytics-reports.md`)である。

旧に実在した「固定する機構」は 3 種類で、いずれも本 ADR の設計に流用できる:

| 先例 | 入力 | 出力 | 比較単位 | 固定方法 |
| --- | --- | --- | --- | --- |
| 88 列契約 | `config.COLUMN_NAMES` / `IDX` | 列数・列名・整数インデックス | スカラ等値 | テスト内の直値アサート |
| **2 DDL 同期**(唯一の実装横断固定) | SQLite DDL と PostgreSQL DDL | テーブル集合・インデックス集合 | 集合の包含 | 別実装間の突合テスト |
| リプレイ恒等式 | `[(play_id, 88列リスト)]` 全行 | 不一致の全件リスト | **行 × フィールド**(11 項目)+ カウント上限違反 | 先頭行を種に全再計算し保存値と突合 |

**一方で「複数実装が同じ指標値を返すことを固定する機構」は旧に存在しない。** 同一指標の二重実装(被打率・投球回)が明記されている一方、実装間の値一致を機械が固定するテストの記載が全資料に無い。**本 ADR が設計する一致性の担保は、旧に前例がない領域である。**

さらに、旧では**指標値が計算式ではなく入力側の前処理に左右されていた** — 派生列の付与(`コースYadj = 263 − コースY` 等)、`球速>0` や `タイムの種類.isin([1..9])` のような個別除外、未クリック座標の `(0,0)` センチネル。**固定ベクタは入力の正規化規則まで含めて固定しないと成立しない。**

## 決定

### D-1: 実現手段 — 制約された宣言モデル(DSL)を正本とし、Python と TypeScript を生成する

| 項目 | 決定 |
| --- | --- |
| **正本** | **制約された型付きの宣言モデル**(状態遷移・成績計上・座標変換の規則を宣言で書く)。人手で保守するのはこのモデルだけ |
| **正本の射程** | 状態 / イベント / ガード / 次状態 / **整数・boolean・enum** / 四則・比較・min・max / **明示的な丸め** / 有限の reducer(集計) / 入出力の型・範囲・単位・scale。**これ以外の計算を正本に書かない**(表せないものが出たら D-1 の見直しトリガー) |
| **生成物** | Python 実行コードと TypeScript 実行コード。**いずれも派生物であり人手で編集しない**(要件書 NFR-018 達成条件 (a)) |
| **生成器が生成前に検査すること** | 遷移の**重複・欠落・到達不能** / 演算の型と整数範囲 / 除算・丸め規則の指定漏れ |
| **生成物に埋め込むこと** | 生成元の位置(モデル上の識別子)/ **正本の内容 hash と生成器のバージョン**(達成条件 (b)① の乖離検出に使う) |
| **置き場** | 正本と生成器は **`backend/` 配下**。生成物は backend 側と **`frontend/src/lib/generated/`**。**`contracts/` には置かない**(下記 D-1-b) |

**D-1-b: `contracts/` には正本・生成器・生成物を置かない。** 開発ハーネス設計書 4 章が `contracts/` を「**NFR-019(a) のゴールデンベクタの置き場**であって **NFR-018 の実現方式そのものではない**」と限定しているため、ここに実現方式の中核を置くと同章の改訂(版繰り上げ + 確定ゲート)を誘発する。本 ADR は同章に触れない。

**D-1-c: 状態テーブルを両言語の手書き interpreter で読む方式は採らない。** その場合 **interpreter 自体が 2 つの人手保守実装**となり、達成条件 (a)(人手で保守する実装は 1 系統)を満たさない。生成器から**両方の実行コードを派生させる**。

### D-2: 却下した方式と理由

| 方式 | 却下の理由 |
| --- | --- |
| **Pyodide**(Python 正本をブラウザで実行) | 技術的には成立するが、**未圧縮で WASM 約 9MB + 標準ライブラリ約 2.4MB + JS 約 1MB** の固定ランタイムコストが、数 KB〜数十 KB 規模のテーブル駆動の状態遷移に対して過大。タブレット実機での 2026 年時点の実測資料も不足しており、断中の初回起動を賭けられない |
| **Rust + WASM**(Rust 正本を PyO3 と wasm-bindgen で両側へ) | 実行体の同一由来性は最も強く WASM も小さくできるが、**主コストは性能ではなく第三言語・FFI 型変換・wheel matrix・WASM glue・エラー表現・リリース同期**。本番事例でも PyO3 用と wasm-bindgen 用の変換・ラッパー差分が報告されている。**1 名開発体制で両輪を維持する妥当性が、現在のドメイン(テーブル駆動の状態遷移 + 単純な算術集計)では立たない** |
| **TS 正本 → 同一 JS artifact を QuickJS / 常駐 Node で実行** | タブレット負担は最小で同一由来性も hash で示せる**次点の候補**。ただし**バックエンドに JS ランタイム・境界の直列化・timeout・クラッシュ処理・デプロイ依存**が増える。DSL で表せないロジックが増えた場合の**代替案として保持**する(D-1 の見直しトリガー) |
| **一般 Python ↔ TypeScript のトランスパイル** | **意味を保存する成熟した手段が確認できない**。片方向・双方向とも長期の正本にできない |

### D-3: 正本の版と生成物の同期規則

- 生成物は**生成器の実行結果のみ**をコミットする。**手で直した生成物は (b)① が検出して CI を失敗させる**
- 正本を変更した PR は**生成物の再生成を同一コミットに含める**(生成物だけ・正本だけの片側コミットを作らない)
- 生成器のバージョンを上げた PR も同様に**全生成物を再生成する**

### D-4: 達成条件 (b)② は、要件書 **v2.1** の定義のままでは実現不能である

**結論の対象を版で固定する** — 本決定が「実現不能」と述べるのは、**要件書 v2.1 の NFR-018 達成条件 (b)② とその 3 不変条件**である。本 ADR と同一の確定ゲートで成立する**要件書 v2.2 の再定義後の条文を指すものではない**。

#### 不変条件ごとの判定

| 要件書 v2.1 が課す不変条件 | 現行定義での達成可否 | 未達の理由 |
| --- | --- | --- |
| ②「**宣言外の実装が混入していないこと**」を CI が機械的に判定できること | **未達** | 「実装」を**対象ドメイン計算を実現する任意のコード**と読む限り、判定は**プログラム同値性の判定**に帰着する。これは一般に決定不能であり、**方式の選択で解決できる問題ではない** |
| 検査対象の範囲は**本番に到達可能なソース・生成物・実行入口の全域** | **部分的に達成可能** | モジュール・チャンク・実行入口・生成物の**集合**は列挙できる(Rollup のビルドグラフ、Vite の manifest、Python の import グラフ)。しかし**「ソースの全域」に対して「そこに再実装が書かれていないこと」を判定する**ことは上記により不能。**集合を閉じることと、集合の内側の意味を判定することは別である** |
| **未分類・判定不能は合格としない**(fail-closed) | **達成可能だが空振りする** | 未宣言のモジュール・入口・動的機構は fail-closed にできる。しかし**宣言済みモジュールの内側に書かれた再実装は「未分類」として現れない**ため、この規則では捕まらない |
| **対象範囲を縮小して②を満たしたことにはできない** | **この禁止に抵触する** | 実現可能な検査(下記 D-5)は、判定面を「モジュール・入口・生成物の集合」へ**縮小している**。要件書 v2.1 はこの縮小を明示的に禁じているため、**D-5 をもって②を満たしたと宣言することはできない** |

#### 必須の帰結(要件書 v2.1 が定めるもの)

| 項目 | 内容 |
| --- | --- |
| **実装の扱い** | **実装を開始しない**(要件書 v2.1 NFR-018 達成条件 (b) の 3 つ目の不変条件・10 章未決事項表) |
| **要件書の扱い** | **`in-review` へ戻して再改訂する**。本 ADR と**同一の確定ゲート**で **v2.2** として再定義する(逆遷移ではなく**新しい版としての改訂** — 開発ハーネス設計書 7.3) |
| **本 ADR の他の決定** | D-1〜D-3(実現手段)と D-6〜D-8(ベクタ・比較面・判定基準)は**②の帰結に影響されない**。v2.2 の確定をもって実装の発火点が満たされる |

#### 結論の根拠(3 点)

1. **プログラム同値性は決定不能** — 「同じ計算を別の書き方で実装したコードが存在しないこと」の一般判定は不可能。これは実装技術の不足ではなく**計算可能性の限界**である
2. **到達可能性検査が閉じられるのは「集合」であって「意味」ではない** — バンドラのモジュールグラフ・import グラフが与えるのは**どのモジュールが本番に含まれるか**であり、**そのモジュールの内側で何が計算されているか**ではない
3. **単一のツールでは fail-closed にならない**(原典で確認済み)— esbuild は解析できない import を**バンドルせずそのまま出力に残す**(「Other forms of import paths are not bundled, and are instead preserved verbatim in the generated output」)。ESLint の `no-eval` は**間接 eval を検出できない**(「This rule cannot catch renaming the global object.」)。したがって閉域は**複数の検査を重ねて初めて**成立し、その場合も上記 1・2 の限界は残る

### D-5: 要件書 v2.2 の再定義に用いる材料

**本節は材料の提示であり、要件文ではない。** 新しい合格条件・実装許可・規範文はここに書かない(要件文は要件書 v2.2 側で書く)。

#### (a) 実現可能な検査 — アーキテクチャ完全性検査

| 検査 | 内容 | 手段の例 |
| --- | --- | --- |
| **A-1 入口の全列挙** | 本番に到達可能な入力を宣言し、宣言外の入口を拒否する。**メイン画面だけでなく Web Worker・Service Worker・別 HTML・`public/` 配下の実行可能ファイルを含める** | Vite の production input の宣言と突合 |
| **A-2 モジュール集合の照合** | ビルド後に実際に含まれるモジュール・チャンクを採取し、宣言マニフェストと突合する | Rollup の `generateBundle`(`moduleIds` / `renderedExports` / `dynamicImports`)/ Vite manifest / esbuild metafile |
| **A-3 動的機構の禁止と検出** | 動的コード生成・非リテラル import・外部スクリプトを**禁止**し、違反を検出する。**単一ツールでは漏れる**ため複数を重ね、実行時の CSP も併用する | dependency-cruiser(dynamic / exotic / **unknown・undetermined dependency を error に**)+ lint + CSP |
| **A-4 Python 側の閉域** | import グラフでモジュール集合を閉じ、`importlib`・`getattr`・エントリポイント経由の動的読み込みを禁止・検出する | import グラフ解析 + 契約検査 |
| **A-5 生成物の由来** | 生成物に埋め込んだ**正本の hash と生成器バージョン**を照合し、乖離を検出する(達成条件 (b)① と同一機構) | 再生成して差分ゼロを確認 |

#### (b) この検査でも残る検出不能範囲

- **宣言済みモジュールの内側に手書きされた再実装**。これは旧システムが実際に陥った形(「定義は共有・ロジックは別コード」)と**同一の失敗モード**である
- **ドメイン計算の結果を、正本を経由せずに構成するコード**(例: 画面コンポーネント内でアウト数を直接加算する)
- 上記はいずれも**出力が偶然一致する間は一致性テストでも検出されない**

#### (c) 残余を狭めうる補助手段(要件で採るかは v2.2 の判断)

- ドメイン計算の結果型を**生成物からのみ構築可能**にする(型で外部での構築を禁じる)
- 手書き実装を置けるディレクトリを限定し、**それ以外での対象計算の定義を lint で拒否**する
- 対象ドメインの語彙・定数・演算パターンを**ドメイン層の外で禁じる**

**いずれも完全性は保証しない。** v2.2 は「どこまでを要求し、どの残余を明示的に受容するか」を決める必要がある。

## 理由

- **要件が (α) に「双方が同一のコードに由来する実行体」を課している**以上、人手保守の実装は 1 つでなければならない。Python と TypeScript という**言語境界をまたぐ**以上、選択肢は「片方の言語で書いて他方でも動かす(ランタイム持ち込み)」か「共通の正本から両方を作る(生成)」しかない
- ランタイム持ち込み(Pyodide / Rust+WASM / JS ランタイム)は**実行環境そのものを製品に抱え込む**。本ドメインの計算は**テーブル駆動の状態遷移と単純な算術集計**であり、抱え込む固定費に対して得るものが小さい
- 生成は**正本の射程を制約する**ことで成立する。射程を「状態遷移 + 有限の算術」に限れば、生成器は小さく保て、**生成物の検査(型・範囲・丸め・到達不能)も生成時に機械化できる**
- **旧システムの教訓に直接応える** — 旧は共有物(定数・語彙・契約ファイル)を持ちながら「定義は共有・ロジックは別コード」で失敗した。**ロジックそのものを生成物にすれば、片側だけ書き換わる経路が閉じる**

**D-4(実現不能の結論)について**:

- 要件書 v2.1 の (b)② は、**旧 NFR-011 の失敗モードを二度と許さない**という明確な意図で書かれている(条文の括弧書きが「旧システムは共有モジュールを持ちながら『定義は共有・ロジックは別コード』の状態が解消しなかった」と名指ししている)。**その意図は正しい**
- しかし**意図を実現する手段が、汎用言語(Python / TypeScript)の上では存在しない**。判定は決定不能な問題に帰着する
- ここで「実現可能な近似(D-5(a))をもって②を満たした」と宣言することは、**要件書 v2.1 が明示的に禁じている「対象範囲の縮小」そのもの**である。したがって**近似を採るなら要件側の再定義が要る**
- **緩い側へ倒して着手しない** — 要件書 v2.1 はこの状況のために差し戻し経路を用意している。本 ADR はその経路を使う
