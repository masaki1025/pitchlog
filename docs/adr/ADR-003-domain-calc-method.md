**要件が既に固定しており本 ADR で緩められない制約**: (α) は「クライアント・サーバーの双方が同一のコードに由来する実行体を用いる」/ (β) は「サーバー内で人手保守する実装が 1 系統」/ 対象の列挙は NFR-018 が正(実装判断で対象から外せない)/ **(b)② の 3 不変条件**(**検査対象は本番に到達可能なソース・生成物・実行入口の全域** / **未分類・判定不能は fail-closed** / **対象範囲を縮小して満たしたことにはできない**)— これは**起案時点の要件書 v2.1 の条文**であり、**本 ADR は D-4 でこの形の (b)② を実現不能と結論し、同一の確定ゲートで成立する要件書 v2.2 が②の目的を「差分が必ず検出されること」へ再定義した**。**したがって現行の制約は v2.2 の条文**(保証する対象・入力範囲・強さ〔3 層〕・範囲外の 4 点)であり、**fail-closed と「対象範囲の縮小で満たしたことにできない」は v2.2 でも維持されている**が、**「本番到達可能な全域を探索して再実装の不在を示す」という要求は v2.2 には無い**(①乖離検出と③構成の完全性が全域探索を担う)/ 正解ベクタは完成をもって発効し完成前に NFR-019(a) を合格と判定しない / **(α)(β) の区分をコア領域の境界に用いない**。

### 旧システムが示した事実

**旧システムは同趣旨の要件(旧 NFR-011・Should)を持ちながら、1 年以上多重実装を解消できなかった。** 重要なのは「共有物が無かったから失敗した」のではないことである — 共有モジュール(`domain/out_statuses.py`・`domain/batting_results.py`)と共有契約ファイル(`shared/display_geometry_263_v1.json`)は**実在していた**。版固定資料の結論は「**定義は domain/ 共有だがロジックは別コード**」(`../legacy/research/analytics-reports.md`)である。

旧に実在した「固定する機構」は 3 種類で、いずれも本 ADR の設計に流用できる:

| 先例 | 入力 | 出力 | 比較単位 | 固定方法 |
| --- | --- | --- | --- | --- |
| 88 列契約 | `config.COLUMN_NAMES` / `IDX` | 列数・列名・整数インデックス | スカラ等値 | テスト内の直値アサート |
| **2 DDL 同期**(唯一の実装横断固定) | SQLite DDL と PostgreSQL DDL | テーブル集合・インデックス集合 | 集合の包含 | 別実装間の突合テスト |
| リプレイ恒等式 | `[(play_id, 88列リスト)]` 全行 | 不一致の全件リスト | **行 × フィールド**(11 項目)+ カウント上限違反 | 先頭行を種に全再計算し保存値と突合 |

**一方で「複数実装が同じ指標値を返すことを固定する機構」は旧に存在しない。** 同一指標の二重実装(被打率・投球回)が明記されている一方、実装間の値一致を機械が固定するテストの記載が全資料に無い。**本 ADR が設計する一致性の担保は、旧に前例がない領域である。**

さらに、旧では**指標値が計算式ではなく入力側の前処理に左右されていた** — 派生列の付与(`コースYadj = 263 − コースY` 等)、`球速>0` や `タイムの種類.isin([1..9])` のような個別除外、未クリック座標の `(0,0)` センチネル。**固定ベクタは入力の正規化規則まで含めて固定しないと成立しない。**

### D-1: 実現手段 — 制約された宣言モデル(DSL)を正本とし、Python と TypeScript を生成する

| 項目 | 決定 |
| --- | --- |
| **正本** | **制約された型付きの宣言モデル**(状態遷移・成績計上・座標変換の規則を宣言で書く)。人手で保守するのはこのモデルだけ |
| **正本の射程** | 状態 / イベント / ガード / 次状態 / **整数・boolean・enum** / 四則・比較・min・max / **明示的な丸め** / 有限の reducer(集計) / 入出力の型・範囲・単位・scale。**nullable**(値なしを表す型)/ **enum から表示名への写像テーブル**。**これ以外の計算を正本に書かない**(表せないものが出たら D-1 の見直しトリガー)。**自由な文字列処理は正本の射程に含めない**が、**宣言的な表示規則は含める** — **対象計算は「①構造化値」と「②宣言された表示規則を適用した表示値」の両方を返し、`expected` と比較面はその双方を持つ**(**表示規則を正本の外に置くと、利用者が見る値〔FR-022 の結果表示名など〕が単一実装の外へ出てしまう**ため)。**表示規則として許すのは次の 3 類だけ**(v0.2 仮改訂 — TSK-278): **①enum → 表示名の写像テーブル** / **②プレースホルダの差し込みだけを行う宣言的テンプレート**(例: `{捕球選手}{打球タイプ}`)/ **③数値表示 primitive(有限の 4 種・パラメータはすべて宣言時固定)** — **固定小数**(scale 0..3・丸め・先頭 0 の有無・負値の符号。**scale=0 で整数表示を含む** — 独立の整数/符号付き整数 primitive は作らない)/ **百分率**(scale 0..2・丸め・**先頭 0 の有無**〔scale ≥ 1 で 1% 未満の値の `0.5%` / `.5%` を一意化〕・記号)/ **混合分数**(分母・整数部の助数詞・剰余 0 の形・分数の体裁)/ **null 代替**(代替文字列 — **値部分のみを担当**する。併記の件数・母数は常に構造化値として存在する〔全欠損なら 0〕ため、**通常と同じ fixed-decimal(scale=0)+ テンプレート②で合成し、null 時専用の分岐・別テンプレートは作らない** — 例 `−(0球)` = null 代替「−」+ 件数 0 の合成〔併記を持つ書式の場合。併記を持たない書式〔球速等〕は「−」単独 — 併記の有無は通常書式の規定に従い null 時に変えない〕。v0.2)。**書式の実引数の正は要件書 付録A の「表示書式」列(binding)**であり、正本の宣言は binding の値を参照する(表示の都合ではなく要件として与えられる)。**型領域の定義(v0.2)**: `NumericValue` = 対象計算が返す構造化数値の総称(**整数・decimal・有理数〔分子/分母〕とそれらの nullable** — これ以外の数値表現を表示経路に持ち込まない)/ `DisplayAtom` = 表示文字列の最小単位となる**不透明型**(テンプレート差し込み以外の操作を持たない)。**`DisplayAtom` の供給源は 3 つに閉じる**: ①写像テーブルの結果 / ③数値表示 primitive の結果 / **語彙スナップショットから ID で解決した表示名**(型付きの参照解決であり自由な文字列操作は挟めない — v0.2 で経路を明示)。**数値の文字列化は `NumericValue → DisplayAtom` の型付き変換として必ず ③ を経由**し、**テンプレート②が受け取れるのは `DisplayAtom` と①の結果のみ**(`NumericValue` の直接差し込みは生成前検査で fail)。**言語既定の文字列化(Python `str()` / TS `String()` / SQL `CAST(... AS TEXT)` 等)を生成物に出さない**(暗黙の重複実装の禁止 — NFR-018)。**本規定の射程は NFR-018 の対象計算の生成物に限る**(対象計算の出力でない利用者可視数値〔管理コンソールの設定値表示等〕は D-1 の射程外 — 対象列挙を広げない。付録A-1 の表外既定表示も対象計算の出力に限る)。**条件分岐・部分文字列操作・③の宣言の外の数値整形ロジックは引き続き書けない**。**①の写像テーブルは「管理者管理でない安定した enum」に限る** — **管理者が改名できる語彙(打撃結果・打球情報・シーズン — 要件書 4.0-3)の表示名は写像テーブルに焼き込まない**(改名が ID 経由で全履歴表示へ即時反映されるという 4.0-3 の保全規律を、生成時に固定する写像テーブルでは満たせない)。**代わりに「語彙スナップショット(ID → 表示名の対応)を対象計算の入力に含める**」 — こうすると、**改名は入力の差し替えとして反映され**、かつ **FR-022 の「結果表示名」と NFR-019(a) の「利用者へ見せる全項目」を、完成した表示値のまま比較面に載せられる**(合成規則が単一実装の外へ出ない)。**「構造化値 + 表示値」を返すのは、宣言的表示規則を持つ計算・出力項目だけ**であり、**表示規則を持たない項目(例: 責任投手の氏名)は対象計算の出力ではない**(比較面にも入らない)。**表外既定(要件書 A-1)で scale=0 の書式を与えられる数値(スコアボードの得点・カウント等)は表示規則を持つが、例外として対象計算の出力とベクタ比較面は構造化値のまま**とする(表示値を返さない) — 表示は製品表示呼出箇所が同一の生成 formatter を通し、担保は生成前検査・構成検査・変異検査(D-8・D-11。要件書 NFR-019(a) の例外と対 — PO 裁定 2026-09-03)。具体的には **「結果表示名」は enum の結果コード(構造化値)+ 語彙スナップショット経由の表示名とテンプレート(表示値 — 打撃結果は管理者管理語彙〔4.0-3〕のため写像テーブルに焼き込まない。v0.2 で本行内の旧例示の矛盾を是正)** / **0 除算時は構造化値 `null` + 率・割合の値の位置の表示値「−」(MINUS SIGN U+2212。母数併記は付録A-1 のとおり維持 — 完成表示値の例 `−(0打数)`・`−(0球)`)** — **③の null 代替 primitive が値部分を対応づける**(率・割合の両形式に適用)(v0.2 仮改訂で帰属を明示。従来この対応づけは①②のどちらにも収まっていなかった。比較器で吸収しない)/ **責任投手は選手 ID(または `null`)を返し、氏名の解決は正本の射程外**(比較面も選手 ID。氏名は FR-038 の移行突合で見る)— **選手名は表示規則の対象ではなく、利用者へ見せる条項〔FR-022〕が列に持たないため**。**写像テーブルとテンプレートも生成対象**であり、**(b)① の乖離検出・直接呼び出し対象・変異テストの対象に含まれる** |
| **生成物(target matrix)** | 対象の区分ごとに生成先を分ける。**いずれも派生物であり人手で編集しない**(要件書 NFR-018 達成条件 (a)):<br>・**(α)** = Python 実行コード + TypeScript 実行コード<br>・**(β)①〜⑤**(DB 側集計が必須・**表示 primitive を持つ**)= **SQL 式** + それを呼ぶ **Python の型付き受け口** + **同じ宣言モデルから生成した表示 formatter(Python)**(v0.2 仮改訂 — 完成表示値までを生成物で閉じる。direct target はこの 3 生成物の**複合 target** — D-11)。**TypeScript の生成物は作らない**<br>・**(β)⑦**(DB 側集計が必須・**数値表示 primitive は持たないが写像①〔打球方向の区分 → 表示名〕を持つ**)= **SQL 式** + **写像①を適用する Python の型付き受け口**(**受け口が写像適用後の区分表示名までを出力とし、ベクタ期待値・property 比較・direct target の比較面に表示名を含め、写像を変異対象に含める**。direct target は **2 段の composite**〔sql → typed-receiver。数値 formatter は追加しない = 3 段化しない〕 — v0.2・最終全文確認周の PO 裁定で確定)。**TypeScript の生成物は作らない**<br>・**(β)⑥・⑧**(移行時のみ動作)= **Python 実行コードのみ**<br>**全生成先に共通で** hash の埋め込み・再生成差分の検出・結果型の構築規則を適用する |
| **生成器が生成前に検査すること** | 遷移の**重複・欠落・到達不能** / 演算の型と整数範囲 / 除算・丸め規則の指定漏れ / **表示 primitive の全パラメータの指定漏れ**(固定小数 = scale・丸め・先頭 0・符号 / 百分率 = scale・丸め・先頭 0・記号 / 混合分数 = 分母・整数部の助数詞・剰余 0 の形・分数の体裁 / null 代替 = 代替文字列 — **1 つでも欠けた宣言は fail**) / **`NumericValue` をテンプレートへ直接差し込む宣言**(DisplayAtom 変換の欠落 — v0.2 仮改訂) |
| **生成物に埋め込むこと** | 生成元の位置(モデル上の識別子)/ **正本の内容 hash と生成器のバージョン**(達成条件 (b)① の乖離検出に使う) |
| **置き場** | 正本と生成器は **`backend/` 配下**。生成物は backend 側と **`frontend/src/lib/generated/`**。**`contracts/` には置かない**(下記 D-1-b) |

**D-1-b: `contracts/` には正本・生成器・生成物を置かない。** 開発ハーネス設計書 4 章が `contracts/` を「**NFR-019(a) のゴールデンベクタの置き場**であって **NFR-018 の実現方式そのものではない**」と限定しているため、ここに実現方式の中核を置くと同章の改訂(版繰り上げ + 確定ゲート)を誘発する。本 ADR は同章に触れない。

**D-1-d: 区分(β)①〜⑤・⑦ の集計は、宣言モデルから **DB 側集計の式**(SQL 式)を生成する。** ブロック4の共通規則と NFR-005 が **DB 側集計(WHERE / GROUP BY + インデックス)**を必須とし、全件読み込み型の集計を禁じているため、(β) の生成物を「取得した全行を Python で畳み込むコード」にすると NFR-005 違反になる。**宣言モデルの有限 reducer から SQL 式を生成**し、実行は DB 側で行う。**(β) には TypeScript の生成物を作らない**(クライアントで実行しないため)。

**D-1-c: 状態テーブルを両言語の手書き interpreter で読む方式は採らない。** その場合 **interpreter 自体が 2 つの人手保守実装**となり、達成条件 (a)(人手で保守する実装は 1 系統)を満たさない。生成器から**両方の実行コードを派生させる**。

### D-2: 却下した方式と理由

| 方式 | 却下の理由 |
| --- | --- |
| **Pyodide**(Python 正本をブラウザで実行) | 技術的には成立するが、**未圧縮で WASM 約 9MB + 標準ライブラリ約 2.4MB + JS 約 1MB** の固定ランタイムコストが、数 KB〜数十 KB 規模のテーブル駆動の状態遷移に対して過大。タブレット実機での 2026 年時点の実測資料も不足しており、断中の初回起動を賭けられない |
| **Rust + WASM**(Rust 正本を PyO3 と wasm-bindgen で両側へ) | 実行体の同一由来性は最も強く WASM も小さくできるが、**主コストは性能ではなく第三言語・FFI 型変換・wheel matrix・WASM glue・エラー表現・リリース同期**。本番事例でも PyO3 用と wasm-bindgen 用の変換・ラッパー差分が報告されている。**1 名開発体制で両輪を維持する妥当性が、現在のドメイン(テーブル駆動の状態遷移 + 単純な算術集計)では立たない** |
| **TS 正本 → 同一 JS artifact を QuickJS / 常駐 Node で実行** | タブレット負担は最小で同一由来性も hash で示せる**次点の候補**。ただし**バックエンドに JS ランタイム・境界の直列化・timeout・クラッシュ処理・デプロイ依存**が増える。DSL で表せないロジックが増えた場合の**代替案として保持**する(D-1 の見直しトリガー) |
| **一般 Python ↔ TypeScript のトランスパイル** | **意味を保存する成熟した手段が確認できない**。片方向・双方向とも長期の正本にできない |

**v0.2 仮改訂(TSK-278)の再評価 — 数値表示 primitive の追加にあたり、次点の D-2(QuickJS / 常駐 Node)へ切り替えない 3 理由**:

1. **対価が過大** — 本表が挙げるとおり D-2 は「バックエンドに JS ランタイム・境界の直列化・timeout・クラッシュ処理」を伴う。**数値書式のためだけに払うコストではない**
2. **D-2 は「射程で表せない計算」全般への代替**であって表示規則固有の対処ではない — **状態遷移・有限の算術という中核の射程は現行のまま足りており**、見直しトリガーが要求するのは表示の末端だけである
3. **D-2 へ切り替えても書式の正は生まれない** — 要件書に書式が無いという問題は実現方式に依存せず残る(だから本改訂は要件書 付録A の書式 binding を対で改訂した)

数値表示 primitive は**有限・型付き・宣言時固定・生成時に機械検査可能**であり、D-1 の射程制限の論拠(「射程を制約することで生成器は小さく保て、生成物の検査を生成時に機械化できる」)と同じ形を保つ — **射程の意味を変えずに端を広げる最小の改訂**として、方式切替(D-2)より優先する。

### D-3: 正本の版と生成物の同期規則

- 生成物は**生成器の実行結果のみ**をコミットする。**手で直した生成物は (b)① が検出して CI を失敗させる**
- 正本を変更した PR は**生成物の再生成を同一コミットに含める**(生成物だけ・正本だけの片側コミットを作らない)
- 生成器のバージョンを上げた PR も同様に**全生成物を再生成する**

### D-4: 達成条件 (b)② は、要件書 **v2.1** の定義のままでは実現不能である

**結論の対象を版で固定する** — 本決定が「実現不能」と述べるのは、**要件書 v2.1 の NFR-018 達成条件 (b)② とその 3 不変条件**である。本 ADR と同一の確定ゲートで成立する**要件書 v2.2 の再定義後の条文を指すものではない**。

#### 不変条件ごとの判定

| 要件書 v2.1 が課す不変条件 | 現行定義での達成可否 | 未達の理由 |
| --- | --- | --- |
| ②「**宣言外の実装が混入していないこと**」を CI が機械的に判定できること | **未達** | 「実装」を**対象ドメイン計算を実現する任意のコード**と読む限り、判定は**プログラム同値性の判定**に帰着する。これは一般に決定不能であり、**方式の選択で解決できる問題ではない** |
| 検査対象の範囲は**本番に到達可能なソース・生成物・実行入口の全域** | **部分的に達成可能** | モジュール・チャンク・実行入口・生成物の**集合**は列挙できる(Rollup のビルドグラフ、Vite の manifest、Python の import グラフ)。しかし**「ソースの全域」に対して「そこに再実装が書かれていないこと」を判定する**ことは上記により不能。**集合を閉じることと、集合の内側の意味を判定することは別である** |
| **未分類・判定不能は合格としない**(fail-closed) | **達成可能だが空振りする** | 未宣言のモジュール・入口・動的機構は fail-closed にできる。しかし**宣言済みモジュールの内側に書かれた再実装は「未分類」として現れない**ため、この規則では捕まらない |
| **対象範囲を縮小して②を満たしたことにはできない** | **この禁止に抵触する** | 実現可能な検査(下記 D-5)は、判定面を「モジュール・入口・生成物の集合」へ**縮小している**。要件書 v2.1 はこの縮小を明示的に禁じているため、**D-5 をもって②を満たしたと宣言することはできない** |

| 項目 | 内容 |
| --- | --- |

| **要件書の扱い** | **`in-review` へ戻して再改訂する**。本 ADR と**同一の確定ゲート**で **v2.2** として再定義する(逆遷移ではなく**新しい版としての改訂** — 開発ハーネス設計書 7.3) |

#### 結論の根拠(3 点)

1. **プログラム同値性は決定不能** — 「同じ計算を別の書き方で実装したコードが存在しないこと」の一般判定は不可能。これは実装技術の不足ではなく**計算可能性の限界**である
2. **到達可能性検査が閉じられるのは「集合」であって「意味」ではない** — バンドラのモジュールグラフ・import グラフが与えるのは**どのモジュールが本番に含まれるか**であり、**そのモジュールの内側で何が計算されているか**ではない
3. **単一のツールでは fail-closed にならない**(原典で確認済み)— esbuild は解析できない import を**バンドルせずそのまま出力に残す**(「Other forms of import paths are not bundled, and are instead preserved verbatim in the generated output」)。ESLint の `no-eval` は**間接 eval を検出できない**(「This rule cannot catch renaming the global object.」)。したがって閉域は**複数の検査を重ねて初めて**成立し、その場合も上記 1・2 の限界は残る

### D-5: 要件書 v2.2 の再定義に用いる材料

**本節は材料の提示であり、要件文ではない。** 新しい合格条件・実装許可・規範文はここに書かない(要件文は要件書 v2.2 側で書く)。

#### (a) 実現可能な検査 — アーキテクチャ完全性検査

| 検査 | 内容 | 手段の例 |
| --- | --- | --- |
| **A-1 入口の全列挙** | 本番に到達可能な入力を宣言し、宣言外の入口を拒否する。**メイン画面だけでなく Web Worker・Service Worker・別 HTML・`public/` 配下の実行可能ファイルを含める** | Vite の production input の宣言と突合 |
| **A-2 モジュール集合の照合** | ビルド後に実際に含まれるモジュール・チャンクを採取し、宣言マニフェストと突合する | Rollup の `generateBundle`(`moduleIds` / `renderedExports` / `dynamicImports`)/ Vite manifest / esbuild metafile |
| **A-3 動的機構の禁止と検出** | 動的コード生成・非リテラル import・外部スクリプトを**禁止**し、違反を検出する。**単一ツールでは漏れる**ため複数を重ね、実行時の CSP も併用する | dependency-cruiser(dynamic / exotic / **unknown・undetermined dependency を error に**)+ lint + CSP |
| **A-4 Python 側の閉域** | import グラフでモジュール集合を閉じ、`importlib`・`getattr`・エントリポイント経由の動的読み込みを禁止・検出する | import グラフ解析 + 契約検査 |
| **A-5 生成物の由来** | 生成物に埋め込んだ**正本の hash と生成器バージョン**を照合し、乖離を検出する(達成条件 (b)① と同一機構) | 再生成して差分ゼロを確認 |

#### (b) この検査でも残る検出不能範囲

- **宣言済みモジュールの内側に手書きされた再実装**。これは旧システムが実際に陥った形(「定義は共有・ロジックは別コード」)と**同一の失敗モード**である
- **ドメイン計算の結果を、正本を経由せずに構成するコード**(例: 画面コンポーネント内でアウト数を直接加算する)
- 上記はいずれも**出力が偶然一致する間は一致性テストでも検出されない**

#### (c) 残余を狭めうる補助手段(要件で採るかは v2.2 の判断)

- ドメイン計算の結果型を**生成物からのみ構築可能**にする(型で外部での構築を禁じる)
- 手書き実装を置けるディレクトリを限定し、**それ以外での対象計算の定義を lint で拒否**する
- 対象ドメインの語彙・定数・演算パターンを**ドメイン層の外で禁じる**

**いずれも完全性は保証しない。** v2.2 は「どこまでを要求し、どの残余を明示的に受容するか」を決める必要がある。

### D-11: (b) の検査設計(**決定** — 要件書 v2.2 の再定義後の条文に対する具体化)

要件書 v2.2 は (b) を ①**乖離の検出** ②**差分の検出可能性** ③**宣言された構成の完全性** に再構成した。**②は「再実装が存在しないことの証明」ではなく「再実装があって値がずれたら必ず落ちること」の担保**である(強制点を 3 度提案し 3 度とも意味判定へ帰着したため、確定ゲートで目的そのものを変更した)。本 ADR はその具体的方式を確定する。

#### ② 差分の検出可能性(**保証範囲を閉じたうえで、その範囲では取りこぼしを許さない**)

**保証する対象**: **宣言された実行入口を通した**対象計算の出力。**生成物を直接呼ぶだけの検査にはしない** — 旧システムの事故(責任投手モデルを新設したのに表示される失点は旧方式のまま)は**製品経路が別の実装を使っていた**形であり、生成物を直接叩く検査では捕まらない。

**保証する入力の範囲**(要件書 v2.2 が課す「閉じた集合」の具体化):

| 対象 | 入力範囲の作り方 |
| --- | --- |
| 状況判定 | **事前状態 × イベント × 主要フラグの全列挙 ×(履歴文脈の境界値・等価分割)**(**全列挙するのは有限な軸だけ** — 履歴文脈は有限にならないため下段の規則で固定する。**主要フラグの閉包は宣言モデルの schema が定める** — 回・表裏・得点・S/B・アウト・打順・走者・タイブレーク中・試合終了済みの各フィールドの値域)。付録E の「1 行 = 結果 × 前提条件」を展開の軸にし、**イベント種別は断中操作イベントの全種(毎球入力・undo・選手交代・タイブレーク開始・試合終了宣言・その場登録の Must の 6 種 + **FR-040 を採用した場合のみ状態補正**)を軸に含める**。**補正**(FR-040 採用時のみ)は「補正で設定しうる状態の代表集合(各フィールドの境界値)」、**undo** は「**履歴文脈の各種別(確定プレイの各種別 + FR-040 採用時は状態補正)** × 補正を跨ぐ場合」を固定する(**履歴文脈が空 = 取り消す対象が無い場合も 1 件置く**) |

| **(β)⑥ 移行時の座標変換** | 付録B-5 が定める**変換前後の具体値の組**(旧263px の端点・範囲外のクランプ点・**センチネル(`0`/空/`"0"`)** を全件) |

**3 層の内容**:

| 層 | 決定 | 対象 | CI |
| --- | --- | --- | --- |
| **網羅的な正解ベクタ + 経路一致検査** | 上記の入力範囲を**全件覆う**。**同一の case を ①製品の実行入口を通して と ②正本生成物を直接呼んで の双方で実行し、「①=期待値」「②=期待値」に加えて「①=②」を検査する**(**経路一致検査**)。**①=②が破れた時点で fail** — 期待値と一致していても fail とする | (α)(β) 全対象 | **PR 必須** |
| **プロパティテスト** | ①**不変条件**(**カタログは要件・付録から導出した独立の規範述語**とし、**対象計算の計算規則から導出しない**。**製品側の生成器がこのカタログを実装の生成に用いることを禁止**し〔同じ値を両者が読むと oracle が循環する〕、各述語には**典拠(要件 ID・付録の節)を必須記録**する。カタログは宣言モデルとは**別ファイル**で保持し、**マニフェストの `propertyCatalog`(パス・schema・述語ごとの典拠)として登録**する(**`propertyCatalog` はマニフェストのトップレベル・キー**であり、対象計算ごとの `properties[]` とは階層が異なる — v0.2 仮改訂で記載階層を明記)。**独立性の機械検査**: 生成器の入力を **allowlist で宣言**(正本の宣言モデルのみ)し、**生成の実行中のファイルアクセス証跡と突合**して allowlist 外の読み取りを fail とする。あわせて**生成器の依存グラフにカタログが現れないこと**を静的に検査する — 状況判定/終了判定 = S≤2 / B≤3 / アウト≤2 / 同一塁の走者重複なし / **通常の前進プレイに限った**得点の単調性〔**状態補正・undo は現在状態を直接書き換えるため対象外** — FR-040〕/ 座標変換 = 定義域内で全射・単調・クランプの冪等性 / 捕球選手推定 = 出力が守備位置の閉じた集合に属し、**タイブレーク規則を適用した後の帰属が一意**(**多角形の共有境界そのものは「重なり」として扱わない** — 付録B-6 が境界線上の点に「先に定義された領域が優先」というタイブレークを定めているため。禁じるのは**内部の重複**) / 集計 = **分母 0 または集計対象 0 件(全欠損)で構造化値 `null`・完成表示値は値の位置に「−」+ 併記の有無は通常書式の規定に従う**(併記を持つ率・割合 = `−(0打数)`・`−(0球)` で併記維持〔「−」だけ・`0%` は違反〕/ **併記を持たない書式〔球速等〕= 「−」単独が正** — 付録A-1。`0` やエラーを返す実装は違反。D-1 ③の null 代替 primitive — v0.2)/ **計数と率の非負性**(打数・安打・奪三振などの**計数**と、打率・出塁率などの**割合**は非負。**FIP・wRAA など負値を取り得る指標には課さない** — 付録A の指標ごとに成立条件を宣言する)/ 部分和の総和一致 / 移行導出 = 出力が入力の値域に閉じ NULL 条件が排他)②**正本から生成した実行体どうしの等価性** — **(α)** = Python 生成物と TypeScript 生成物 / **(β)①〜⑤** = **複合 target(生成 SQL → 型付き受け口 → 生成 formatter)の最終表示文字列**と、**同じ宣言モデルから表示まで生成したテスト専用の Python 参照実装**の結果(**構造化数値段の比較も従来どおり保持する — 置換ではなく終端の延長**。v0.2 仮改訂)/ **(β)⑦** = **受け口が写像①を適用した区分の表示名まで**と、**同じ宣言モデルから表示名まで生成した参照実装**の結果(数値 formatter は持たないが写像①の適用までを比較面に含める — v0.2)(**参照実装は生成物であり手書きではない。製品経路には載せない**)/ **(β)⑥⑧** = 生成 Python と同参照実装 | (α)(β) 全対象 | **PR 必須**(seed 固定)+ 夜間(拡大) |
| **変異テスト** | 上位 2 層の**実効性そのものを測定**。**非等価変異の生存を認めない(生存 0 が合否基準)** | 生成物 + **製品経路上の対象計算の呼び出し部** | **PR 必須**(変更対象)+ 夜間(全面) |

**変異テストの運用規則**(合否を機械的に一意にするため):

| 項目 | 決定 |
| --- | --- |
| **言語別の変異演算子** | Python / TypeScript = 算術演算子の置換・比較演算子の境界移動・真偽値の反転・定数の増減・条件分岐の除去。**SQL 式** = 集計関数の置換・`WHERE` 述語の反転・`GROUP BY` キーの欠落・`JOIN` 条件の緩和。**表示系(v0.2)** = 文字列リテラルの置換・テンプレート placeholder の削除と入替・写像テーブルの値と順序の変異・**表示 primitive のパラメータ変異**(scale・丸め・先頭 0・記号・剰余 0 の形)・**formatter 呼出しの削除と言語既定の文字列化への置換**(v0.2 — 製品表示呼出箇所を対象。**書式差が出力に現れる対象〔scale≥1・先頭 0 なし・負号・剰余表記・記号等〕で kill を判定**する。**scale=0 の整数表示では出力が同一になり得るため等価変異の規則〔人手判定・記録必須〕で扱い、表外既定の非経由経路の検出は構成検査〔(b)③ の表示対応の突合〕が担う**)— **表示生成物(formatter・写像・テンプレート)を変異対象に持つ対象計算は表示系演算子を 1 種以上適用する**(数値系演算子だけで非ゼロ条件を満たして表示層を素通りさせない) |
| **等価変異の扱い** | **人手で等価と判定したものだけを分母から除外**し、**除外の理由と判定者を記録**する(記録のないものは非等価として扱う) |
| **未対応変異** | **対象計算ごとに「未対応箇所 0」または承認済みのカスタム変異への置換**を合格条件とする。**未対応のまま残る箇所が 1 件でもあれば fail**(分母から外して合格にしない)。**生成された変異数が 0 の対象計算も fail**(変異層が実質不存在のまま「生存 0」で通る false green を防ぐ)。未対応箇所の一覧は毎回出力する |
| **判定の単位** | **対象計算ごとに判定**する(全体集約にしない — 小規模な対象の生存を他の対象で希釈させない) |
| **PR での対象** | **その PR で変更された対象計算 + それに依存する対象計算**。全面は夜間。ただし**次のいずれかを変更した PR は全面を PR 必須**とする(対象計算のファイルを 1 つも触らない PR で必須範囲が空集合になり、上の fail 条件が一度も評価されないのを防ぐ): **宣言マニフェスト / 生成器 / 正本の宣言モデル / 変異器の設定 / 等価変異台帳 / 正解ベクタ・プロパティテストの基盤 / 実行入口の構成**。**影響範囲を逆引きできない変更も全面**とする(fail-closed) |
| **kill 要因の記録** | **各変異について、上位 2 層のどの検査が kill したかを必須記録**とする。**対象計算ごとに、プロパティ層が非等価変異を 1 件以上 kill していること**を合格条件に加える(**プロパティ層の kill が 0 件の対象計算は fail** — 恒真な述語を 1 件置いただけで層を満たしたことにできない)。**(b)① の乖離検出(正本 hash・再生成差分)による kill は分子に数えない**(生成物を変異させると hash 検査だけで kill され、網羅ベクタ・プロパティテストが差分を観測していなくても「生存 0」になるため) |
| **等価変異の記録** | **`backend/domain/mutation-equivalents.json`** に、変異の識別子・等価と判断した理由・判定者・判定日を記録する。**判定者は本 ADR の改訂権者(PO)**とし、**追加はレビューで確認**する(記録のないものは非等価として扱う) |
| **実行時間の上限** | **PR 必須分の合計で 10 分**を上限とし、**超過はタイムアウト = fail**。**「対象を絞る」は必須範囲(変更された対象計算 + 依存先)を削らない** — 収まらない場合は**変異器の高速化・並列化・CI ランナーの増強**で対処し、**必須範囲の縮小でも夜間への移送でも対処しない**(夜間枠は補助検査に限る — D-7)。**全面が発火した PR は上限を 30 分**とする(差分実行より対象が桁で多いため。それでも超える場合は上限の見直し自体を本 ADR の改訂ゲートで行い、**上限を超えたまま暫定でマージする経路は設けない**)。上限そのものは Phase 4 で実測して見直す |

**保証の範囲外**(要件書 v2.2 と同じ): ①入力範囲の外側 ②**製品側が正しい出力を誤って選択・抑止・改変する誤り**(FR の受け入れ基準と NFR-019(c) の E2E が**主要分岐を覆う**が、**全対象計算・全表示経路・全選択条件を閉じるものではない — 残余リスク**)③正本と常に同一の値を返す再実装が存在する事実(**上位要件と (a) には違反する**ため (a) とレビューで抑止)。

**経路一致検査を独立した合否条件とする理由**: 正解ベクタ・プロパティテスト・変異テストの 3 層は、**製品経路が正本生成物とは別の実装を使っていても、その別実装が期待値と一致する限り全層を通過し得る**(ベクタ層は別実装を通して成功し、プロパティ層は正本由来の実行体どうしを比較して成功し、変異はいずれかの層が kill する)。**(b)③ の構成の完全性が本来これを構成的に排除する**が、③ の解析が及ばない経路(未知の入口・解析器の限界)に対しては空振りするため、**値の面でも直接突き合わせる層を必須にする**。

**3 層の登録漏れの検出**(層ごとに「対象計算の集合との差」を取る): CI は **① マニフェストの `calculation` の集合**と **② 各層が実際に実行した対象計算の集合**を突合し、**差が 1 件でもあれば fail** とする。すなわち **正解ベクタ層** = 消費されたベクタファイルが覆う対象計算。**さらに経路一致検査の要求集合を `(calculation, vector, case, runner, entrypointId, directTargetId)` の直積**とし、**その各要素について「①実行済み・②実行済み・①=expected・②=expected・①=②」の 5 判定を機械可読な証跡として出力する。**証跡はアダプタの自己申告ではなく、CI 側の独立した収集器が生成する** — 収集器はアダプタから**生の出力・実行した artifact の hash・(β) では実際に発行された SQL 文または AST**、**さらに composite target((β)①〜⑤ = 3 段・(β)⑦ = 2 段)では各段の入力と出力(SQL 結果集合・受け口の入力と型付き出力・〔3 段では〕formatter の入力と最終文字列)**を受け取り、**等値判定(composite では値の連鎖検証を含む)は収集器が計算する**(アダプタが `true` を 5 個返すだけで通る経路を閉じる。保証範囲は D-11 の複合 target 規定のとおり — v0.2)。**受け取った hash が `generated[]` の現在の hash と一致しない場合も fail**。要求集合と証跡集合の差が 1 件でもあれば fail / 5 判定のいずれかが不成立でも fail** とする(**製品経路だけを実行した case で「実行済み」にできない** — 経路一致検査が空振りするため。**入口が 2 つあり片方だけを実行した場合も差分として検出される**)。**`entrypoints[]` と `directTargets[]` も空を許さない** / **プロパティ層** = **ランナーが出力した機械可読の実行証跡**(pytest = JUnit XML 等 / Vitest = reporter の JSON)から集計した、**実際に完走したテスト**が宣言する対象計算。**skip・xfail・todo・0 ケース生成は「実行済み」に数えない**。さらに**対象計算ごとに ①不変条件のテストと ②実行体どうしの等価性のテストの双方が 1 件以上完走し、生成ケース数が 1 以上であること**を条件とする(**いずれかが 0 なら fail**。宣言だけの no-op テストで層を満たしたことにできない)。**証跡のスキーマを固定する** — 各テストは `calculation` / `propertyId` / `propertyKind` / `generatedCases` / `status` を機械可読に出力する。**出力方法**は runner ごとにアダプタで揃える(pytest = プロパティ用フィクスチャが JUnit XML の `properties` へ書く / Vitest = reporter が JSON へ書く)。**この 5 項目を出力しないテストは「実行済み」に数えない**/ **変異層** = 変異が生成・実行された対象計算(**生成変異数 0 は fail** — 上表)。**他対象の成功で欠落対象を覆い隠せない**(判定は対象計算ごと)。

**本 ADR が確定する範囲と、実装へ送り出す範囲**(確定ゲート 19 周目・PO 裁定 2026-08-19): **本 ADR が確定するのは「方式」** — 制約 DSL からの生成 / 3 層 + 経路一致検査 / 契約の 2 分類・置き場・CI 配線 / 対象と契約の 1 対 1 対応 / 入力範囲の閉じ方 / 比較面 / (b)①③ の検査方式 / 実装の着手順序。**契約 schema のフィールドレベルの細部**(履歴文脈の上限 `D` の値・語彙スナップショットの粒度・正規化規則の識別子体系・証跡ファイルの具体形式など)は、**ベクタ整備タスクと検査基盤の実装タスクで、実機とともに確定する**。**理由**: 検証機構もベクタも 1 行も存在しない段階でフィールド設計まで机上で閉じようとすると、是正が次の穴を生む閉じた輪になる(**ハーネス設計書 v1.7 の確定ゲート 12〜15 周目で実測済みの失敗パターン**)。**送り出しても方式は分岐しない** — 上記の細部はいずれも「schema が定める範囲を保証範囲とし、範囲外は (b)② の保証範囲外として明示する」という本 ADR の規則の下で決まるため。**見直しトリガー**: 細部の確定が本 ADR の決定(特に D-1 の射程・D-6 の契約分類・D-11 の 3 層と経路一致検査)と両立しないと判明した時点で、本 ADR を改訂ゲートへ戻す。

**判定不能の扱い**: 解析器が「解析できない」と報告した箇所は**合格にしない**。解析不能な構文は動的機構の禁止規則で先に落ちるため、**残る判定不能は解析器の限界を意味し、CI を失敗させて人が判断する**。

**採らなかった方式と理由**(確定ゲートで否定されたもの): **結果型の構築点の限定**(branded type / 型の封印)は、**既存の結果値を展開して一部を差し替える構築**と **`any` 相当への降格**で迂回でき、**結果の受け口の閉包(sink 閉包)**は、**手書きの判定で正規の結果 A・B のどちらを表示するかを選ぶ制御フロー**を止められない(結果値をプリミティブで渡さないため)。**いずれも任意コードの意味判定に帰着する**。

2. **正規化規則をテストが実際に通ること** — runner は **①生値へ生成済みの正規化規則を適用し ②正規化後の期待値と突合し ③その実値を計算へ渡す**。**正規化後の値を入力としてそのまま与え、規則の実装を素通りさせてはならない**(素通りすると旧システムの事故層〔前処理の差異〕が固定されない)
3. **期待値を正本実装から自動生成しない** — 重要ベクタは**要件・状態表から独立に生成するか人間が確認する**(正本から生成すると oracle が循環し、正本の誤りをそのまま固定してしまう)
4. **数値の扱い** — カウント・得点・アウトは狭い整数範囲を schema で固定 / 座標は**固定小数点整数**(単位と scale をフィールド名か schema に持たせる)/ **NaN・Infinity・-0・暗黙の丸めを禁止** / 除算は「切り捨て・0 方向・四捨五入・ties-to-even」のいずれかを**ベクタごとに明記** / 2^53−1 を超え得る値は decimal string

### D-10: 開発ハーネス設計書 6.3 の「付録A 契約の実装完了」の判定基準

設計書 6.3 は、確定済みイベント事実から付録A 指標を算出する**後段集計をコア領域から条件付き除外**とし、その**発効を「付録A 契約(固定ベクタ + CI 強制)の実装完了後」と定め、発効判断を本 ADR に委任**している。判定基準・判定者・手続きは未規定であったため、本 ADR が定める。

**「実装完了」の判定基準(下表の 6 条件〔1・2・3・3-b・4・5〕を**すべて**満たしたときに限り完了とする。1 つでも欠ければ完了としない)**:

| # | 条件 | 確認方法 |
| --- | --- | --- |
| 1 | **付録A 固定ベクタが D-6 の形式で存在する** | ファイルの存在と schema 検証 |
| 2 | **付録A の全指標が少なくとも 1 件のベクタで覆われている** | 付録A-2 / A-2b / A-3 / A-3b / A-4 / A-5 の各行に対応する `calculation` があること |
| 3 | **分岐がベクタで区別されている** | 付録A が明示する分岐(投球回の振り逃げ・奪三振の 5 系統・与四球の申告敬遠算入・WHIP の与死球除外・FIP の定数・失点の責任投手帰属とフォースアウト引き継ぎ・**打数の定義が控除する全項目**〔犠打・犠飛・四球・死球・打撃妨害/走塁妨害による出塁〕・出塁率の分母・エンドランの 3 値)がそれぞれ別 case で存在すること |
| 3-b | **付録A-1 の共通規則がベクタで固定されている** | ゴミ箱除外・結果球ベースの紐付け・**割合と率への母数併記**(**率・母数の 2 構造化値 + テンプレート②の合成** — v0.2)・対左右分類・欠損球速の除外・0除算時および**集計対象 0 件(全欠損)時**の**構造化値 `null` と、値の位置に「−」+ 併記を維持した完成表示値(例 `−(0打数)`・`−(0球)`)**(D-1 ③の null 代替 primitive — v0.2)・**「表示書式」列どおりの完成表示値**(v0.2 仮改訂)・シーズン通算の年度境界・**サヨナラ時の得点計上**の**それぞれに、規則の適用有無で結果が変わる case が存在すること**(旧システムの事故はこの層で起きた) |
| 4 | **CI で強制されている** | D-7 の「**網羅的な正解ベクタ = PR 必須**」に配線され、**失敗時にマージ不可**であること |
| 5 | **期待値が正本実装から自動生成されていない** | ベクタの由来(要件・状態表からの独立生成、または人間確認)が記録されていること |

**判定者**: PO(山田正輝)。**手続き**: 上記 **6 条件それぞれ**の確認結果を、判定を行う PR に記録する。

**本 ADR は発効を宣言しない。** 発効条件は「実装完了**後**」であり、本 ADR の承認時点で付録A 固定ベクタは存在しない。設計書 6.3 が「契約が存在しない間は含む」と定めるとおり、**後段集計は当面コア領域に含まれ続ける**。

**`core-areas.json` の paths は本 ADR では変更しない。** 設計書 6.3-⑤ が「paths の追加・削除・縮小は敵対レビュー + 人間承認の対象」と定めており、**発効の判定と paths の縮小は別の手続き**である(評価台帳 H-12)。

## 理由

- **要件が (α) に「双方が同一のコードに由来する実行体」を課している**以上、人手保守の実装は 1 つでなければならない。Python と TypeScript という**言語境界をまたぐ**以上、選択肢は「片方の言語で書いて他方でも動かす(ランタイム持ち込み)」か「共通の正本から両方を作る(生成)」しかない
- ランタイム持ち込み(Pyodide / Rust+WASM / JS ランタイム)は**実行環境そのものを製品に抱え込む**。本ドメインの計算は**テーブル駆動の状態遷移と単純な算術集計**であり、抱え込む固定費に対して得るものが小さい
- 生成は**正本の射程を制約する**ことで成立する。射程を「状態遷移 + 有限の算術」に限れば、生成器は小さく保て、**生成物の検査(型・範囲・丸め・到達不能)も生成時に機械化できる**
- **旧システムの教訓に直接応える** — 旧は共有物(定数・語彙・契約ファイル)を持ちながら「定義は共有・ロジックは別コード」で失敗した。**ロジックそのものを生成物にすれば、片側だけ書き換わる経路が閉じる**

**D-4(実現不能の結論)について**:

- 要件書 v2.1 の (b)② は、**旧 NFR-011 の失敗モードを二度と許さない**という明確な意図で書かれている(条文の括弧書きが「旧システムは共有モジュールを持ちながら『定義は共有・ロジックは別コード』の状態が解消しなかった」と名指ししている)。**その意図は正しい**
- しかし**意図を実現する手段が、汎用言語(Python / TypeScript)の上では存在しない**。判定は決定不能な問題に帰着する
- ここで「実現可能な近似(D-5(a))をもって②を満たした」と宣言することは、**要件書 v2.1 が明示的に禁じている「対象範囲の縮小」そのもの**である。したがって**近似を採るなら要件側の再定義が要る**
- **緩い側へ倒して着手しない** — 要件書 v2.1 はこの状況のために差し戻し経路を用意している。本 ADR はその経路を使う

## 帰結

### 何が変わるか

1. **要件書 NFR-018 (b)② が再定義される** — 本 ADR と**同一の確定ゲート**で要件書 **v2.2** として改訂する(逆遷移ではなく新しい版としての改訂 — 設計書 7.3)。**v2.2 の確定をもって ADR の発火点(「対象のドメイン計算コードを新規に追加または変更する最初の変更の前に ADR で確定する」)が満たされる**。**ただし着手できる範囲には順序がある**(**循環しない形で定める** — 検査は生成物・製品入口・変異対象が存在しないと緑にできないため、「緑になってからコードを追加する」とは書けない):
   1. **ベクタの schema と独立に確認した期待値**、および**検査基盤(生成器・マニフェスト・収集器・CI 配線)** を先に確定する(この段階では対象計算のコードを追加しない)
   2. **対象計算 1 件ごとに、宣言モデルの正本・生成物・製品経路の呼び出し部・その対象の 3 層検査を「同一の変更」として追加**する(片側だけのコミットを作らない)
   3. **その変更は、当該対象について全検査が緑であることをマージの条件**とする(要件書 NFR-018 の「正解ベクタは完成をもって発効する」= **未完成のあいだ適合と判定しない**であって、実装を禁じるものではない)
   4. **対象横断の判定(NFR-019(a) の合格・(b)② を満たしたという判定)は、対象すべての契約が完成してから**行う
2. **FR-022 に当日打席結果の列定義が入る**(D-9 の案を v2.2 で反映)。これにより NFR-019(a) の比較面の fail-closed が解ける
3. **ドメイン計算は宣言モデルの生成物になる** — 手書きの Python / TypeScript でドメイン計算を書く経路が閉じる。既存の `frontend/src/lib/courseInputView.ts` の座標変換は、逐語移植の受入条件を解く時点で生成物へ移行する(要件書 NFR-018 達成条件 (c) の例外表の卒業)
4. **`contracts/` の役割と内部規約が確定する** — NFR-019(a) のゴールデンベクタ((α) が参照するもの)の置き場。**実現方式の中核(正本・生成器・生成物)は置かない**。**ディレクトリ構造・命名規則・形式・バージョニングは D-12 が正**とし、`contracts/README.md` は索引に徹する(approved の本 ADR へ追随させる)
5. **後段集計のコア領域からの除外は、当面発効しない** — 付録A 契約が未実装のため(D-10)

### 見直しトリガー

- **DSL の射程で表せないドメイン計算が現れたとき** — D-1 の正本の射程(状態遷移 + 有限の算術)に収まらない計算が要件に入った場合。次点は D-2 の「TS 正本 → 同一 JS artifact を QuickJS / 常駐 Node で実行」
- **生成器の保守コストが実測で見合わなくなったとき** — 1 名開発体制で維持できないと判断された場合
- **要件書 v2.2 の (b)② が再び改訂されたとき** — 検査方式の前提が変わるため D-5 を見直す

- **対象技術の世代交代** — Pyodide / WASM / JS ランタイムの運用コストが大きく変わり、D-2 の却下理由が成立しなくなった場合
