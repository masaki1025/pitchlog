## 決定事項

### D-1: 製品版の射程 = 外部チーム提供を視野（2026-07-20）
- 自チーム（筑波）運用を軸に、他大学・他チームにも使ってもらえる品質・テナント分離で作る
- 課金・契約・利用規約は今回は要件化しない（必要になったら追補）
- 旧成功指標G-1〜G-3は自チーム運用前提 → 外部提供を視野に入れた指標へ見直し対象

### D-2: 提供形態 = 共有クラウド1インスタンスのSaaS型（2026-07-20）
- 全チームが同一インスタンスを利用し、テナント分離はソフトウェアで担保（旧NFR-007の考え方を継承）
- 運用主体は開発者（山田さん）。障害対応も開発者が担う（属人性リスクは継承 → リスク章で管理）

### D-3: アカウントモデル = チーム共有アカウント継続（2026-07-20）
- チーム名+パスワードの共有アカウント。個人アカウント・入力者識別は引き続きWon't
- 卒部時のアクセス権更新はパスワード変更+旧トークン失効（旧FR-030を継承、今回は全経路で最初から実装）
- 将来の個人アカウント化を妨げないID設計（利用者テーブルを追加できる余地）だけ制約として残す

### D-4: 想定規模 = 1チームで開始、必要時に拡張可能な構成（2026-07-20 確定）
- 当面の利用は自チーム（筑波）1チームのみ。外部チーム追加は「必要になったら」
- 具体化（ユーザー承認済み）:
  - ① マルチテナント分離（team_id分離・認証）は初日から実装（後付けは困難なため）
  - ② 性能の保証・実測は 1チーム×5年 ≈ 15万プレイ規模で行う（多チーム規模の性能試験は今回しない）
  - ③ 集計はDB側絞り込み・集計（WHERE/GROUP BY + インデックス）を基本規律として非機能要件化。
    毎球参照される画面（リアルタイム成績等）に限り事前集計テーブルを採用可。一覧系画面はページングを設計ルールとする
  - チーム数増加時はインフラ増強+性能要件の改定で対応

### D-5: UI構成・技術スタック = 単一Web UI、FastAPI + React + TypeScript を継承（2026-07-20）
- Streamlit版は作らない。UIは1本（旧2.3の併存・置換問題は消滅）
- スタックは現行新UIで検証済みの FastAPI + React + TS + Python を継承（コードは新規に書き直す）
- **タブレット・PC両対応を明示要件とする**（ユーザー強調）: 記録画面はタッチ最適化、分析・管理画面はPC操作でも快適に使える
- ドメインロジック（状況判定・座標変換・集計等）は単一実装に集約（旧NFR-011の多重実装問題を構造的に解消）

### D-6: データ契約 = 内部スキーマは再設計、88列は入出力互換形式として維持（2026-07-20）
- DBスキーマは製品版として正規化・再設計する（選手はID参照、走者状況等は正規化。項目追加が局所変更で済む形）
- 88列「1プレイ=1行」は**入出力の互換フォーマット**に役割変更: CSV出力・既存データ取り込みは88列形式で行う
- 既存の記録資産・Excel分析ワークフローは互換維持（新旧の変換層を1枚実装する）

### D-7: DB構成 = PostgreSQL一本化（2026-07-20）
- 本番: Supabase PostgreSQL を継承。開発: PostgreSQL（Windowsネイティブ版 or Docker、セットアップ手順はWindowsで完結させる）
- SQLiteは廃止。開発と本番の差異ゼロ、スキーマ乖離の監視テスト・二重スキーマ保守を不要にする

### D-8: 既存データ = 全件移行する（2026-07-20）
- 現行の毎球データ・チーム・選手・スタメン・試合情報・カルテ所見を全件 pitchlog へ移行
- 移行はD-6の変換層（88列→新スキーマ）を使用。件数・代表集計値の新旧突合を移行の受け入れ基準に含める
- 現行移行スクリプトの既知不具合（毎球データ移行失敗・監査P2-1）の轍を踏まない検証付き移行とする

### D-9: 機能スコープ = 既存8ブロックをそのまま継承（2026-07-20）
- ①試合記録 ②チーム・選手管理 ③リアルタイム成績 ④分析 ⑤カルテ ⑥帳票・出力 ⑦認証・マルチテナント ⑧データ管理
- 旧ブロック9（新UI）はD-5により「UIそのもの」となり消滅
- 新機能追加は初回リリース後に回す（スコープ肥大の防止）。旧正本の〔新規〕要件（在籍ステータス管理・誤登録選手セルフ削除）は含む
- 旧FR-032（SQLite→Supabase移行）はD-8「既存データの検証付き移行」に置き換え
- 旧FR-033（新UIフルフロー）は消滅（単一UIの各機能要件に吸収）

### D-10: オフライン耐性 = 通信断中も入力継続（レベルB）（2026-07-20）
- 試合開始（スタメン設定・試合作成）はオンライン必須。**開始後は通信断が試合終了まで続いても毎球入力を継続できる**。復帰後にまとめて自動同期（client_keyべき等で二重登録なし）
- 端末内キューは1試合分（350プレイ以上）を保持できること
- 断中に使える操作: 毎球入力＋直前取り消し（undo）。過去プレイの修正・分析・カルテはオンライン前提（レビュー時に要確認）
- **設計上の含意**: スコア・アウト・走者・打順の状況計算をクライアント側で実行できる必要がある（現行はサーバー側のみ＝断中は次の入力がブロックされる実装だった）。D-5の単一実装原則と両立させる配置（状況遷移ロジックを1箇所に書き両側から使う等）は設計フェーズの必須課題として申し送る
- 完全オフライン（試合開始からオフライン）は引き続きWon't

### D-11: 要件の再基線化はブロック単位でユーザーと逐次確認（2026-07-20）
- 一括変換ではなく、8ブロック+非機能要件を1ブロックずつ提示→確認→確定で進める
- 確認済みブロックはこの下書きに「確定」として記録する

### D-12: FR「選手交代の記録」を新設（2026-07-20）※旧正本の拾い漏れ
- 投手交代・代打・代走・守備交代（複数同時・位置入れ替え含む）を記録できる（Must）
- 交代後のプレイは新選手に紐づき、成績表示が切り替わる。9ポジション過不足の検証（警告、ブロックはしない）
- 未登録選手の途中出場は試合画面を離れずその場登録（旧FR-011連動）
- **交代はイベントとして永続化**し「何回・どのプレイ時点で誰→誰」を追跡可能に（スコアカード・出場履歴の基盤。現行はオーダー表上書きで履歴が残らない）
- 交代は通信断中（D-10）も記録できる
- 境界: DH解除・同一枠への再交代・交代の取り消し。連盟規定にない交代は対象外

### D-13: 断中同期の正 = サーバーを正とする（2026-07-20）
- 復帰同期時はサーバーがプレイ列を再計算・検証したものが確定記録。クライアント表示と差異があればサーバー結果で補正し、操作者に通知（黙って直さない）
- 「同一のプレイ入力列からクライアント・サーバーが同一状況を導く」一致性テストをCIに置く（受け入れ基準化）
- 正本はDBの1系統のみ、という原則の明文化

### D-14: 未同期キュー = 操作イベントの列として設計（2026-07-20）
- キューはプレイ行でなく「操作イベント（プレイ確定・undo・交代）」の順序付き列
- 断中の未送信プレイのundo → キューから除去（サーバーへ送られない）。同期済みプレイのundo → 取り消しイベントをキューに積み復帰後適用
- 復帰同期は入力順を厳守。途中の1件が拒否されたら後続を停止し、どこで止まったか操作者に明示（黙って飛ばさない）

### D-15: 語彙管理 = DBマスタ化＋「試合区分/大会名」の2層化（2026-07-20）
- 打撃結果・球種・作戦・打球情報・シーズン等の語彙はDBマスタで管理。初期値は現行config.pyと同一内容（88列互換維持）
- プレイの意味に関わる語彙の変更は**システム管理者のみ**（チーム別カスタム語彙はWon't）
- 大会は2層に分離: **試合区分**（共通固定: 公式戦/準公式戦/オープン戦/紅白戦/その他 — 分析・指標の軸）＋**大会名**（チーム自由登録: 関東大会、新人戦…）
- 既存データ移行時は現行Kind値を「区分＋大会名」へ機械的にマッピング

### D-17: 試合規則マスタ（2026-07-20）
- 規則セット（規定イニング・コールド条件・タイブレーク規則・DH有無・延長上限）を**大会名に紐づけてチームが自由に設定**できる
- 適用優先順位: 試合単位の上書き ＞ 大会名の規則 ＞ 試合区分のデフォルト（システム共通初期値）
- 試合終了判定・コールド・サヨナラ・タイブレーク開始は適用規則に従う
- **途中回での終了宣言**（日没・時間切れ・雨天）はいつでも可能で、その時点のスコアで確定（旧FR-010の受け入れ基準に追加）
- 既存データ移行時は現行コードの判定ロジック相当を初期規則として割り当て

### D-18: 試合終了後の修正を正式要件化（2026-07-20）
- 終了済み試合への過去プレイ修正は終了状態のまま可能（編集→下流再計算→差分プレビュー）
- プレイの追記が必要な場合（入れ忘れ等）は進行中に戻して追記→再終了できる
- 修正・追記後は成績・カルテ・帳票の再集計が自動で走る（事前集計テーブルとの整合、D-4③連動）
- 期限・権限の制限は設けない（チーム共有アカウントでは実効性が薄いため）。乱用は成功指標「終了後修正5行以下」で運用監視

### D-19: 断中の端末故障リスク = 受容（2026-07-20）
- D-10により未同期キューは最大1試合分に膨らみ、断中の端末故障で失う量は現行より増え得る
- ただしD-10なしでは断中プレイはそもそもデジタルに存在しない（最悪ケース=従来の通常ケース）ため、受容が合理的（ユーザー判断）
- 緩和策: ①未同期件数の常時表示（Must・旧FR-034継承） ②端末内キューのローカル書き出しと復旧後取り込み（Could・非常口）
- リスク章に「受容済み・対応しない理由」込みで登録する

### D-20: ブロック2-1 選手登録 = 選手ID管理を正とする（2026-07-20）
- 選手の同一性は選手ID（内部・不変）で管理。プレイ行は選手IDを参照し、名前・背番号は表示用属性（現行の「名前文字列が正+後付けlinkテーブル」を反転）
- 登録項目: 名前・投打（投:右/左、打:右/左/両を別項目）。**背番号は任意**（B戦の番号なし選手対応）
- 背番号の重複は現役同士なら警告のみ、ブロックしない。DBの一意制約は張らない。OB選手の背番号は当然再利用可
- 過去試合は「記録した時点の背番号」で表示（スタメン・プレイ記録に当時の番号を保存）
- 入部年度・学年は入れない（ユーザー判断）
- 試合中のその場登録（旧FR-011）・チーム名の汎用化（D-16-b）を継承

### D-21: ブロック2-2 スタメン記憶・復元 = 最後の1件方式を継承（2026-07-20）
- 前回確定スタメンをチーム選択時に自動復元（打順・守備位置・選手）。複数パターン記憶はしない
- OB選手を含む枠は自動採用せず差し替えを促す（継承）
- 復元は名前でなく選手IDで行う（D-20連動。現行stamemは名前・背番号の文字列保存 → I-12に記録済み）

### D-22: ブロック2-3 在籍ステータス = 3区分固定＋ラベル自由（2026-07-20）
- 区分（固定・挙動を決める）: **現役**=候補に出る／**その他**=初期表示では候補に出ないが明示操作で選択可・所属のまま／**OB**=候補から完全除外・過去データ保全
- 全ステータス可逆。物理削除しない。移行時は既存選手全員「現役」
- 区分ごとにチームが自由な名前のラベルを付けられる（怪我・休部・卒業…、初期ラベル同梱）。ラベルは表示用で挙動に影響しない
- 優先度: **区分3つ=Must**（後からの区分追加は移行を伴うため先に固定）、**ラベル自由化=Should**（なくてもリリース可）

### D-23: ブロック2-4 削除の権限構造（2026-07-20）
- **誤登録選手のセルフ削除**: プレイ紐づけゼロの選手のみチームで削除可。紐づけ判定と削除は同一トランザクション。紐づく選手はOB化へ誘導（旧FR-014継承、選手ID化で判定確実化）
- **試合の削除 = ゴミ箱方式（仮置き）**: 記録済み試合もチームアカウントで削除可。ただしソフトデリートで30日間ゴミ箱に保管、チーム自身で復元可能。30日後に完全削除
- **プレイ0件の試合**はゴミ箱を経ず即時削除可（失うものがないため）
- **システム管理者**（運用者専用アカウント1つ）: チーム登録（手動オンボーディング。セルフサインアップはWon't）・チーム無効化・ゴミ箱期限後の復旧対応・選手統合（二重登録の合体、レア）・DB保守
- チーム管理者ロールは今回作らない
- **未決事項に登録**: チーム管理者（ユーザー管理者）ロールの導入検討。導入する場合は削除系操作の担当をチーム管理者に移し、一般チームアカウントからは外す（ゴミ箱方式の位置づけも再検討）

- **P1-2 断中のその場登録**: 「選手のその場登録」を断中可能操作の6つ目に追加。クライアント生成の一時ID（UUID）で記録し、同期時にサーバーが正式IDを確定・イベント列内の参照を置換
- **P2の確定（12件）**:
  1. 同期拒否イベントは操作者が「編集して再送/破棄」を選択して再開できる
  2. 全操作イベント（交代・終了宣言等含む）にクライアント生成のべき等キーを付与
  3. 同期済みイベントも端末に24時間保持（日次バックアップ前のDB障害時の再送出所）。残余リスクはリスク章へ
  4. 打球情報の語彙は「管理者管理」層（D-15改訂の3層に追記）
  5. プレイ0件エンティティも論理削除に統一（ゴミ箱UIを経ず即非表示。物理削除は管理者保守のみ）
  6. 試合開始時プリフェッチに適用規則スナップショットを含める（断中のクライアント終了判定用）
  7. **基線11本は旧FR-001〜010の受け入れ基準を継承し、変更点のみ上書き**と明文化（幻の得点是正・捕球選手の座標自動推定・プレイ修正の楽観ロック・DH10人目構造・紅白戦・球速欠損可等は旧基準のまま生きる）
  8. 同期成功時の通知内容「どの試合の何球分」を継承（旧FR-034）
  9. 書面化時に全NFRへ測定方法を付す（P-1は実戦リハ250球以上でp95算出）
