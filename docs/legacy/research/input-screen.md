# 調査レポート: input-screen

## 要約

Tsukuba PSSのメイン入力画面（app/pages/game_input.py 約1,680行）を完全解剖した。入力は「構え→ゾーン画像クリック→球種→打撃結果カテゴリ→詳細結果→（打球時）フィールドクリック+打球情報→球速→確定」という段階的開示型のフローで、1球あたり最低8〜10回のウィジェット操作が必要であり、その各操作がStreamlitの全script再実行を引き起こす。走者状況は打撃結果からdomain/runner_advancement.pyが自動提案し、確定後はdomain/game_state.update_list()がカウント・アウト・イニング・打順・走者配置を自動遷移させる。座標はストライクゾーン・フィールドとも0〜263スケールのfloatで保存され、React製カスタムコンポーネント（クリック毎rerun回避用）は存在するがビルド成果物が無く実際には未稼働で、streamlit_image_coordinatesフォールバック（クリック毎に実質2回rerun）が使われている。取り消しは「↩戻る」ボタン1タップでDB削除+メモリpop+得点逆算を行うが確認ダイアログが無い。

## 2. 1球の入力フロー（時系列）

通常の1球（例: 外角低めストレートを打ってセンター前ヒット）の操作列。**各ステップでStreamlitの全script rerunが発生**する点に注意。

1. （両打ち打者のみ）打席左右 radio を選択 …rerun
2. 「構え」大分類 radio を選択（例: 1低）…rerun → ゾーン番号 radio が出現、番号選択 …rerun（計2タップ）
3. ストライクゾーン画像（右打者=Plate_R.png / 左打者=Plate_L.png）をクリック → コースX/Y 確定 …クリックで1 rerun＋打点ドット再描画のための遅延rerunが1回（`coordinate_click.py` の pending フラグをページ末尾 `consume_coordinate_rerun` で消費）
4. 「球種」radio（構え入力後に初めて出現）を選択 …rerun
5. 「打撃結果」カテゴリ radio（球種入力後に初めて出現）で `hits` を選択 …rerun → 詳細 radio で「単打」を選択 …rerun
6. この時点で走者状況 selectbox 群が自動提案値（打者=出塁、走者は各1進塁）で表示される。必要なら手動上書き
7. フィールド画像をクリックして打球位置を入力 …rerun×2 → **捕球選手が座標から自動推定**され radio に反映
8. 「打球」G/L/F、「強度」A/B/C を選択 …各rerun
9. 球速を十の位・一の位 radio で入力（例: 3,5 → 135km/h）…各rerun。作戦があれば作戦系 radio 入力
10. 「確定」ボタン押下 → バリデーション → 二重登録チェック（`last_confirmed_play_key`）→ 88列の行を構築（`build_confirmed_play_row`）→ **DB即時insert＋メモリ追記**（`record_confirmed_play`）→ スコアボード加算（`apply_scoreboard_event`）→ 次プレイ状態の自動生成（`update_list`、§3-3）→ イニング交代時は守備ポジション欠落チェック → 入力状態リセット（`reset_confirm_input_state`＝打撃結果/エラー選手/走者状況/捕球選手などのsession keyを削除、`reset_flag`で構え・牽制radioを次周期リセット）→ 両画像キャンバスをクリア（counter increment）→ rerun

**最小操作数**: 見逃しストライク1球でも「構え大分類→ゾーン→ゾーンクリック→球種→カテゴリ(continue)→見逃し→球速2つ→確定」で約8〜9タップ。インプレーだと12〜14タップ。牽制のみなら「牽制radio→結果radio→確定」の3タップ。

### 3-1. 確定前の走者状況自動提案（`domain/runner_advancement.suggest_runner_states`）

| トリガー | 打者状況 | 走者状況 |
|---|---|---|
| 打撃結果2 = PB/WP | 現状維持 | 全走者1進塁（二進/三進/本進） |
| 打撃結果2 = ボーク | 現状維持 | 全走者1進塁、プレイの種類=ボーク |
| 牽制アウト | 継続 | 該当塁走者=投手牽制死 |
| 牽制エラー | 継続 | 全走者1進塁 |
| 盗塁/エンドラン 成功・盗塁成功 | 現状維持 | Wスチール=全走者進塁、それ以外=先頭走者のみ進塁 |
| 盗塁/エンドラン 失敗 | 現状維持 | 先頭走者=盗塁死（走者なしなら警告） |
| 三振ゲッツー | アウト | 先頭走者=盗塁死（走者なし警告） |
| ライナー併殺 | アウト | 先頭走者=封殺、打球タイプ=Lを自動セット |

| 見逃し三振/空振り三振/K3/凡打死/ファールフライ | アウト | 現状維持 |
| 犠飛 | アウト | 三走のみ本進 |
| 犠打 | アウト | 全走者1進塁 |

提案は「入力シグネチャ（打撃結果・打撃結果2・牽制・作戦・走者面子・アウト数のタプル）」が変化した時だけ session_state に書き込まれるため、**スコアラーの手動上書きはrerunをまたいで保持される**（game_input.py:1204-1230）。

### 3-2. カウント連動の自動昇格（`_resolve_continue_batting_result`）

- S=2 で「見逃し」→「見逃し三振」、「空振り」→「空振り三振」
- B=3 で「ボール」→「四球」
- B=3 で無投球ピッチクロック違反 →「四球」
- 打席の継続: `continue` カテゴリかつ結果が三振/四球/申告敬遠でない →「打席継続」、それ以外「打席完了」

### 3-3. 確定後の状態遷移（`domain/game_state.update_list`）

- **得点**: 打者/一走/二走/三走の状況が「本進」の数だけ攻撃側得点に加算。`apply_scoreboard_event` がイニング別スコア・H（安打）・E（エラー、守備側）・K（三振）・B（四球死球）カウンタも加減算（direction=±1 で確定/取り消し両用）。
- **アウト**: 打者状況∈{アウト,封殺,投手牽制死,捕手牽制死,盗塁死,走塁死}、走者状況∈{封殺,投手牽制死,捕手牽制死,盗塁死,走塁死} を合算。3アウト到達で: カウント・走者クリア、表→裏 or 裏→次回表、次打者を打順リストから自動選出（打席途中の3アウトなら同打者が次イニング先頭に再登場するよう打順を戻す）。
- **走者再配置**: 打者状況=出塁→一走に、二進→二走に、三進→三走に打者を配置。各走者の「継続/二進/三進」に応じて塁を移動。
- **S/B更新**: 見逃し/空振り→S+1、ファール→S<2のときのみS+1、ボール or ピッチクロック違反→B+1。打席完了・チェンジで0リセット。上限 S=2, B=3 にクランプ。
- **試合終了判定**: `should_finish_game`（コールド等、Kind依存）。終了時は「試合終了」状態になり確定ボタン非表示。
- **打席結果の自動合成**（打席完了時、game_input.py:1516-1535）: 見三振/空三振/三振併/振逃/邪飛/`{捕球選手}{打球タイプ}併`/`{捕球選手}ライナー併`/`{捕球選手}{打球タイプ}`（凡打死・凡打出塁）/それ以外は打撃結果をそのまま。
- **警告（非ブロッキング）**: 第3アウトがフォース/打者アウトなのに得点が記録されている場合、サヨナラで決勝点超過の場合に `st.warning`（`domain/scoring_rules.py`）。
- **守備ポジション検査**: イニング交代時・選手交代直後に守備番号2〜9の欠落を検出して警告。

### 3-4. 捕球選手の自動推定（`_infer_fielder_from_batted_ball`、helpers:54-89）

263スケール座標で: y≥205→捕手(2)、x≥155&y≥165→一塁手(3)、x≤75&y≥165→三塁手(5)、105≤x<145&140≤y≤190→投手(1)、それ以外は9守備位置アンカー座標への最近傍。推定は座標シグネチャが変わった時のみ `fielder` radio に反映され、手動変更は保持される。

## 4. 座標系（画像クリック）

### 4-1. ストライクゾーン（plate.py）

- 素材: `assets/Plate_R.png` / `Plate_L.png`（各401×401px）。**右打者用/左打者用を打席左右で切替**（両打ちは打席ごとの選択値で切替）。

- 座標変換: クリック点→パディング除去→**400×400のソース空間**（`_PLATE_COORD_SIZE=400`）→ 保存時 `x = 263 * px / 400`。**保存形式は 0〜263 の float**（列 `コースX`, `コースY`）。未クリックは (0,0)。
- クリック取得: `streamlit_image_coordinates`（v0.4.0）。クリック毎にコンポーネントがrerunを発生させ、さらに `remember_coordinate_click` が pending フラグを立て、ページ末尾の `consume_coordinate_rerun` で**2度目のrerun**（ドット描画反映）。確定/取り消し時は `image_clicker_key_counter` をインクリメントしてコンポーネントを作り直しリセット。
- **Reactカスタムコンポーネント**（`components/plate_component/`）: 「クリック時はJS内で座標を保持し、コンポーネント内の確定ボタン押下時のみPythonへ返す＝クリック毎rerunを消す」設計（PlateComponent.jsx）。返り値は自然画像ピクセルで、`263 * x / 400` に換算。**ただし `frontend/build` も `frontend/dist` も存在せず**（src/vite.config.jsのみ）、`plate_component_available()` が False → **現在は必ずフォールバック（streamlit_image_coordinates）が動いている**。
- 修正モード（直前/過去修正）では `use_js_component=False` を明示し、保存済みの263値を `initial_point_263` として初期ドット表示。

### 4-2. フィールド（field.py）

- 素材: `assets/Field3.png`（421×421px、RGBA、`st.cache_resource`）。表示344×344px、パディング6px。
- 描画: 守備選手名8名（表裏に応じ守備側チームの names[10..17]）をPILで座標焼き込み、走者のいる塁に赤「◇」、直前クリック点に半径6pxの黒丸。

## 5. その他タブ・統計表示・取り消しの仕組み

### 5-1. データ入力タブ内の常時統計表示（毎rerunで再計算）

- **カウント表示**: B（緑・3個）/ S（黄・2個）/ O（赤・2個）のドットHTML。
- **ヘッダテーブル**: 日付・経過時間・投手（球数/左右/背番号）・打者（打順/左右/背番号/シーズン打率・打数-安打）。
- **投手カード**: 今日の投球回・最速・ストレート平均球速・被安打/奪三振/与四球/失点、シーズンOAV・vsR・vsL・投球回・WHIP・FIP、相手投手の球数（`analytics/cal_stats.cal_stats`、27要素リスト）。
- **打者カード**: 現打者と次打者の「Today（今日の打席結果列挙）/ Season打率 / vsR / vsL / HR」。
- **球種割合 円グラフ**: 当該投手の全投球の球種分布（Plotly Pie、球種別固定カラー、高さ100px）。
- **スコアボード**: 1〜12回+R/H/E/K/B のHTMLテーブル（H/E/K/Bは `calc_hekb` で毎回集計）。
- 統計の元データ: DBの全試合プレイ（チームIDでキャッシュ）＋当日セッション分を `試合日時+プレイの番号` で重複排除して結合（`df_for_season`、all_list長が変わった時のみ再構築）。ただし **`cal_stats` 自体は毎rerun実行**。

### 5-2. スコアブックタブ

スコア表・先攻/後攻のスコアブック（打者×イニングの打席結果マトリクス）・投手スコアを `st.dataframe` 表示（`reports/score_card.py` の `_score_df`/`_scorebook_df`/`_pitcher_df` を利用）。「PDF生成」ボタン→スピナー→「PDFダウンロード」`st.download_button` の2段階。

### 5-3. データ一覧タブ

直近150件を全列 `astype(str)` で `st.dataframe(height=400)` 表示（全件数もキャプション表示）。閲覧専用・編集不可。

### 5-4. メニュータブ

①**試合開始ボタン**（開始時刻記録、未押下だと赤エラー表示。確定バリデーションの第1関門）②試合日付修正（date_input＋確認checkbox＋反映ボタンの3段構え。DB上の全プレイの試合日時を更新）③**DBに同期**（未送信プレイのみをSupabaseへ再送）④CSV保存（`st.download_button`、UTF-8 BOM）⑤画面再表示 ⑥**入力終了**（未送信分を同期→結果表示→「スタートへ戻る/キャンセル」の2段階確認）。

### 5-5. 取り消し（1つ前に戻す = `↩戻る`）

処理列（game_input.py:505-573）: ①DBの最終プレイをdelete（失敗時はメモリを触らず中断・エラー表示）②`all_list` から最終行 pop ③その行の打者/走者状況・打撃結果・エラー選手から `apply_scoreboard_event(direction=-1)` で得点・H/E/K/Bを逆算減算 ④残った最終行（全削除時はテンプレ行にスコアを反映）を基に `update_list` で「次プレイ状態」を再構築 ⑤入力セッション状態リセット・両キャンバスクリア・rerun。**確認ダイアログなしの即時実行**。連続で押せば何プレイでも遡れる（1回につき1プレイ）。

### 5-6. 修正機能（削除せずに直す）

- **✏️直前修正モード**: DBの最終プレイとセッション最終プレイの番号一致を検認後、通常入力と同じ盤面（球種/球速/打撃結果/打撃結果2/捕球選手/打球タイプ/打者・走者状況の selectbox 群＋プレート・フィールド画像）で1行だけ修正。修正前後の差分テーブルを確認して保存。**後続プレイの再計算はしない**。
- **🔎過去修正モード**: 回/表裏/打者/投手のselectboxフィルタで対象プレイを検索→同じ盤面で修正→保存範囲を「この1行だけ」/「このプレイ以降を再計算して更新」から選択（後者は再計算プレビュー差分を表示）→確認checkbox→保存。

## 6. 現行UIの問題点（UI刷新の論点）

### 6-1. 操作数が多い
1. **1球あたり最低8〜9タップ、インプレーで12〜14タップ**。段階的開示（構え→球種→打撃結果カテゴリ→詳細…）が直列依存になっており、構えを入れないと球種すら表示されない。構え入力は「大分類→ゾーン番号」の2段radio＋別途ゾーン画像クリックと**実質3回同じ場所を指定**している（構えとコースは別概念だが操作としては重複感が強い）。
2. **球速入力が radio 0-9 ×2列＋checkbox**。数字20個の縦radioは面積も大きくタップ精度も要求される。101-164への自動+100規則は暗黙知。
3. 打撃結果が「英字カテゴリ→日本語詳細」の2段選択。カテゴリ名（continue/K/BB/outs/hits/miss/sacrifice）が英語で学習コストがある。
4. ファールでも打球位置クリック＋打球タイプが必須（`_needs_batted_ball_details`）。頻発イベントに対して操作が重い。
5. PDF出力が「生成→ダウンロード」の2ボタン、試合日付修正が「date選択→checkbox→ボタン」の3操作。

### 6-2. Streamlit rerun による遅さ
6. **全ウィジェット操作が85KBのscript全体を再実行**。しかも毎rerunで `cal_stats`（シーズン全打席の集計）・`calc_hekb`・Plotly円グラフ生成・PILによるプレート/フィールド画像の再合成＋base64転送が走る。キャッシュは DataFrame 構築（件数キー）と背景画像のみで、**統計計算はキャッシュされていない**。
7. **画像クリックは1クリックで実質2回rerun**（コンポーネントのrerun＋ドット描画反映の遅延rerun）。
8. rerun毎リセットを防ぐための複雑な状態管理（`reset_flag`、key counter インクリメント、走者提案の「シグネチャ比較」、`_quick_action` の2周期処理、初回 `already_rerun` 強制rerun）が多数あり、刷新時の移植難度・バグ源。
9. **rerun削減の切り札だったReactコンポーネントが未ビルドで死んでいる**（`components/plate_component/frontend/` に build/dist なし → 常にフォールバック）。設計意図（クリックはJS内で保持し確定時のみ返す）は刷新時にそのまま活かせる。

### 6-3. タブレットでの使いにくさ
10. 固定サイズ画像（プレート360px・フィールド344px）と5列カラム（構え/画像/牽制、E選手/打者/1R/2R/3R など）前提のレイアウト。狭幅では Streamlit がカラムを縦積みにし、入力順とスクロール位置が噛み合わなくなる。
11. 縦並びradioの選択肢が多く（打撃結果詳細6件、球種11件、走者状況11件）、タップターゲットが小さい。selectbox はタブレットだとドロップダウン展開が必要で1操作あたり2タップ。
12. `div:has(...) ~ div[data-testid="stHorizontalBlock"]` や `div.stButton > button:first-child` など **StreamlitのDOM内部構造に依存したCSSハック**が多用され、確定ボタンのスタイルが全ボタンに波及。Streamlitバージョン更新で崩れるリスクが高い。確定ボタンのラベルも `'.　　　確定　　　.'` という空白詰めハック。
13. フォント12〜14pxの自前HTMLテーブル（スコアボード・ヘッダ）はタブレットで視認性が低い。

### 6-4. 安全性・整合性
14. **「↩戻る」に確認ダイアログがない**。DB削除＋メモリpopが即時実行される（誤タップで1プレイ消失。復元手段は再入力のみ）。
15. `牽制の種類` 変数が投手牽制（`一塁牽制`）と捕手牽制（`1塁牽制`）で**上書き共有され表記も不統一**。データ分析側の分岐リスク。
16. 二重登録防止は `last_confirmed_play_key`（直前キー比較）のみで、ダブルクリックには効くが複数端末同時入力には無力。
17. 経過時間は Tag ボタンか確定時にしか更新されず、リアルタイムでない。
18. 修正系が「戻る（削除）」「直前修正」「過去修正」「状況変更」「タイブレーク」と5系統に分散しており、導線整理の余地が大きい。

### 6-5. 刷新時に維持すべき資産（ドメインロジックはUIから分離済み）
- `domain/`（runner_advancement, game_state.update_list, input_validation, scoreboard, scoring_rules, pitch_speed, player_side）と `services/play_recording.py` は**純粋関数/薄いサービス層として切り出し済み**で、UIを差し替えてもそのまま再利用できる。88列スキーマ（`config.COLUMN_NAMES`/`IDX`）と263スケール座標が外部（DB・分析・スコアカードPDF）との契約点。
