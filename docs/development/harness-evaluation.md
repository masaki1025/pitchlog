# pitchlog ハーネス運用評価台帳 — 開発ハーネスを実際に回して分かったこと

| 版 | 日付 | 変更内容 | 状態 |
| --- | --- | --- | --- |
| 1.0 | 2026-08-12 | **新設(起案)**: 様式の確定(`H-*` 連番・記載要素 8 点・分類 3 種・`追跡優先度` の 3 分割)+ 運用規則 + 追記導線。起票内容は本タスクのステップ 2〜5 で記入する。計画: `../features/harness-evaluation/plan.md` | draft |

> **目的**: 本プロジェクトで開発ハーネス(`dev-harness-design-2026-08-07.md`)を実際に回して分かった**摩擦点と、機能した点**を蓄積する台帳。**1 タスクの worklog には詳細が残るが、横断的な傾向は残らない** — どのゲートが空振りし、どこで周回が伸び、どの機構が実際に効いたかは複数タスクを並べないと見えない。
> **改善台帳(`../improvements-from-baseball-scoring.md`)との違い**: あちらは**プロダクト**が旧システムから何を改善するかの台帳(I-1〜I-27 のすべてがプロダクト事項)。本書は**ハーネス自身**を対象とする(7.1-1「1 テーマ 1 正本」)。
> **項番 `H-*`**: harness evaluation の項番。レビュー重大度の `P0/P1/P2` や非機能要件の `P-1`・`A-1` 等とは無関係の別体系。
> **番号は追記のみ** — 振り直さない。**欠番も再利用しない**。他文書に `H-1〜H-N` の上限を書かない(追記で腐るため。設計書 v1.4 で `decision-tracer` の番号上限を撤去したのと同じ規律)。
> **版は「様式の版」**: 本書の版は**記載要素・運用規則・分類の版**を表す。**`H-*` の追記では版を上げず**、変更履歴表に 1 行追記する(**7.6-3 前段 = PR レビューで足りる**)。**記載要素・運用規則・分類そのものを変えるときだけ版を繰り上げ、7.3 の確定ゲートを通す**。※ 同一版に複数行が並ぶこと自体は要件書 v1.8(`../requirements/requirements-pitchlog-2026-07-22.md`)に先例があるが、**あの先例は「版列が一意キーでない」ことの例に限る** — v1.8 の 2 行目は「frontmatter 追加・本文の内容変更なし」であり、`H-*` 追記(実質的な内容追加)とは性質が異なる。
> **追記導線(2 経路 — 実装は `.claude/skills/pr/SKILL.md` 手順 1-3 と `.claude/skills/task-done/SKILL.md` 手順 5)**:
> - **主経路 = `/pr` のクローズ処理**。**PR 作成者**が、クローズ処理の**最終コミットを作る前**に追記の有無を判断する。該当するなら同一 PR で **① 計画書 3 節へ宣言を先に追記 → ② 本書へ `H-*` を追記 ③ 本書の変更履歴表に 1 行 ④ 索引の最終更新日を現行化**(②〜④ は同一コミット)。**該当しないなら「台帳への追記なし」と理由を worklog に残す**(忘れたのか判断したのかを区別できるようにする)。※ ① の宣言漏れは **`/pr` 手順 2-2 の双方向突合**が捕まえる(「差分にあるのに未宣言の正本」も中断対象)。
> - **`/task-done` では本書を編集しない**。`/task-done` は PR マージ後に develop 上で走るため、そこから正本を編集すると絶対規則 1(main/develop へ直接コミットしない)に反する。**マージ後に気づいた知見は follow-up タスクを起票**し、次の `/task-start` で別 feature/PR として追記する。
> **`分類` の境界**(確定ゲート 1 周目 P2-1 で明文化): **`機構の穴`** = **機構の実体またはその設定**(hooks / scripts / skills / `settings.json` / `core-areas.json` / CI ワークフロー)に起因するもの。**手順の欠落・一度きりの同期・設定と記述の齟齬も含む**(H-3・H-6・H-18)。**`プロセス設計`** = **文書・ゲート区分・レビュー運用の設計**に起因するもので、機構の実体を伴わないもの(H-19 のゲート区分・H-29 の設計書記述の齟齬)。**`機能した点`** = 機構または運用が実際に誤りを捕捉した / 期待どおり働いた事例。
> **記載要素**(8 点・全項目必須): `分類` / `検出日`(出典を括弧で併記) / `事象`(**典拠必須** — `ファイル:行`) / `再発`(下記の単位で数える) /
> **`再発` の集計単位**(確定ゲート 2 周目 P1-3 で固定 — 単位が混ざると母集団が矛盾する): **`N 件(具体的事象)`** を既定とし、**1 件 = 典拠つきで特定できる 1 つの事象**とする。周回やタスクを単位にする場合は **`N 周`・`N タスク`と単位を明記**する。**「1 件」と書きながら本文で「全タスクで発生」と述べるような母集団の混在を作らない** — 全体傾向は `なぜ問題か` に書き、`再発` には**検証できた事象数**だけを入れる。 `なぜ問題か`(**機能した点は「観測事実・根拠・限界」を併記**し「有効性の証明」と書かない) / `追跡優先度` / `対応案` / `状態`。
> **`追跡優先度`**: **高 / 通常**の 2 値。**判定条件は下記「追跡優先度の判定条件」節が唯一の正**(確定ゲート 5 周目 P1-4 — 従来は非正本の `../features/harness-evaluation/design.md` を正としていたが、`docs/features/` は**活動中のみ意味を持つ一時ディレクトリ**〔設計書 7.2 `:329`・7.6-4 `:370`〕であり、approved 後も使う運用規則の正を履歴文書に置けない)。**高 / 通常の判定条件を適用するのは `分類: 機構の穴` だけ**。`プロセス設計` と `機能した点` は**比較判定せず `通常` 固定**(記載自体は 8 要素の統一性のため必須)。**高** は `対応案` に **follow-up の F-ID + worklog への相対リンク、または日付つき PO 見送り裁定が必須**(「未対応」と書くだけで放流しない)。判定条件が評価できないもの(**制御目的の典拠が示せないもの**)は `H-*` を与えず末尾の `## 候補` へ置く。**判定条件は下記「追跡優先度の判定条件」節を正とする**。
> **`プロセス設計` の歯止め**: `追跡優先度` で差を付けない代わりに、**`再発` が 3 件以上のものは `対応案` に「何を変えるか」を具体的に書く**(「未対応」だけで放流しない)。follow-up タスクまでは要求しない — 多くは運用規律の変更でコード修正を伴わないため。
> **`対応案` に Notion URL を書かない**(設計書 7.4「正本は Notion を参照しない — Git 単独で完結」)。**URL は非正本の worklog 側**に記録し、本書からは **F-ID と worklog への相対リンク**だけを張る。
> **`状態`**: 未対応 / 対応中 / 対応済み / **見送り**(見送りは**理由と裁定日**を必須)。
> **番号は追記順に採番する — 節ごとの連番にはならない**。分類は節で表すため、追記が進むと各節の `H-*` は不連続になる(これは正常)。**節内を連番に揃えるための振り直しはしない**。


## 追跡優先度の判定条件

> **本節が `追跡優先度` の唯一の正**(確定ゲート 5 周目 P1-4 で feature 文書から移設)。**起案時の 19 件(`機構の穴` のうち `research.md` 5 節で検証したもの)の割り当て導出記録**は `../features/harness-evaluation/design.md` 2 節にあるが、あちらは**活動中のみ意味を持つ一時ディレクトリ**の文書であり **approved 後は履歴**。**現行の判定は本節だけに従う**(H-19〜H-41 のように起案後に追加した項目も本節で判定した)。

2 つの条件で**排他的に 3 分割**する。

- **条件 ①(制御目的の典拠)**: その機構が「何を止める / 何を検査する」ことになっているかが、リポジトリ内の記述(docstring・スキル本文・規約・設計書)で示せる
- **条件 ②(誤った振る舞いの実証)**: 現行で **(a) 正しい操作を止める**(誤検知)/ **(b) 止めるべき操作を通す**(fail-open・空回り・検査漏れ)のいずれかが起きることを実ファイル・実測で示せる
  - **② は「既存の機構が」誤った振る舞いをしていることを要する**。**そもそも機構が存在しない**(未実装・未着手)ものは ② に該当しない — 振る舞う主体がないため。この線引きが **H-4 と H-20 の非対称を説明する**: H-4 は `/pr` 手順 2-2 という**既存の機構に穴があった**ので `高`、H-20 は**波及チェックの機構がそもそも存在しない**ので `通常`

| 判定 | 条件 | 扱い |
| --- | --- | --- |
| **候補** | **① なし**(② の評価自体ができない) | `## 候補` 節へ置き **`H-*` 番号を与えない**。典拠が確認できた時点で `高` / `通常` へ昇格 |
| **高** | **① あり かつ ② あり** | `H-*` を与える。`対応案` に **F-ID + worklog への相対リンク、または日付つき PO 見送り裁定が必須** |
| **通常** | **① あり かつ ② なし** | `H-*` を与える。follow-up の必須要件はかからない |

`通常` は「重要でない」ではなく「**放置しても誤った振る舞いは起きない**」の意。記録すること自体が成果物である。
