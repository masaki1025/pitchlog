## 1. DB のログ設定

### 前提

**束縛値(バインドパラメータ)を DB のログへ出さない。** パスワードとトークンの提示値は
束縛値として渡るため、ログに出ると NFR-014 に反する。

| 設定 | 値 | 理由 |
| --- | --- | --- |
| `log_parameter_max_length` | `0` | 通常文のログから束縛値を落とす |
| `log_parameter_max_length_on_error` | `0` | **エラー文のログからも**束縛値を落とす |

**2 つある。** `log_parameter_max_length` だけを 0 にしても、
**エラーのときは `log_parameter_max_length_on_error` の側が効く**ので束縛値が残る。

### 実測(使い捨て PostgreSQL)

`backend/tests/db/test_product_authz_authn_security.py::test_bound_password_is_absent_from_database_logs`
が、使い捨てクラスタに対して次を実際に行う。

1. 上の 2 設定を `0` に、`log_statement = 'all'` と `log_min_error_statement = 'error'` を設定する
2. `authn.login_attempt` を**正常に 1 回**、**エラーを起こして 1 回**呼ぶ
3. **コンテナのログを読み**、通常文とエラー文の両方が出ていることを確かめたうえで、
   **パスワードの平文がログに現れないこと**を表明する

**2026-10-10 時点で緑。**

**この実測が示していない範囲**: 上の試験は**単一セッションで `SET` してから `SET ROLE` する**形で、
**そのセッションに効いた設定**を確かめている。**配備先では、アプリ用ロールが張る接続に
実際に効いている設定**でなければ意味がない。`SET` はセッション限りで、
`ALTER ROLE` / `ALTER DATABASE` / `postgresql.conf` のどこで設定されたかによって、
**管理用接続とアプリ接続で実効値が違いうる**。

### 配備先での確認

**管理用接続で実効値を見ても、アプリ接続の設定を確かめたことにならない。**
**アプリ用ロールの接続から**確かめること。

- [ ] 2 設定が**永続設定**として入っていること(`postgresql.conf` / `ALTER SYSTEM` /
      `ALTER DATABASE` / `ALTER ROLE` のどれで入れたかを記録する。セッションの `SET` は再起動で消える)
- [ ] **アプリ用ロールの接続から** `current_setting('log_parameter_max_length')` と
      `current_setting('log_parameter_max_length_on_error')` がいずれも `0` であること
- [ ] その接続で**通常文を 1 回・エラーを起こす文を 1 回**実行し、
      **配備先のログに束縛値が出ていないこと**(両方)

## 2. DB 接続の経路

### 前提

**アプリと DB の接続は、同一ホストに閉じるか、証明書検証付きの TLS であること。**
`backend/src/pitchlog/authz/database_transport.py` の `require_database_transport` がこれを検査する。
同一ホストと認めるのは**絶対パスの UNIX ドメインソケット**・**IPv4 の 127.0.0.0/8**・
**IPv6 の ::1** だけで、**`localhost` は名前解決に依存するので含めない**。

**検査が走るのは起動時ではない。** `create_app()` が起動時に検査するのは**署名鍵だけ**で、
DB の接続資源は**最初のログイン要求のときに作られ、そこで初めて経路が検査される**
(`backend/src/pitchlog/authz/team_login.py` の `get_login_connection`)。

**つまり「アプリが起動した」ことは、DB 接続の前提が満たされている証拠にならない。**
**配備の確認は、実際にログインを 1 回通してから行う。**

### ループバック TCP の扱い(δ の裁定)

`data-model.md` 8-2 節は「ローカル接続 = UNIX ドメインソケット」と書いているが、
開発用の `docker-compose.yml` は `127.0.0.1:5432` を公開する。
**δ はこの食い違いを締めない方を採った**(計画書 1 節の裁定 5)。

**8-2 節が求めているのは配備先の接続の性質であり、開発と CI の接続形態は別の問題である。**
したがって:

- **開発と CI**: ループバック TCP を許す。`require_database_transport` も 127.0.0.0/8 を通す
- **配備先**: 下の確認欄で、UNIX ドメインソケットか証明書検証付き TLS のどちらかであることを確かめる

### 配備先での確認

- [ ] 接続が UNIX ドメインソケット、または証明書検証付きの TLS であること
- [ ] TLS の場合、**証明書の検証が有効**であること(検証なしの TLS は前提を満たさない)

## 3. レート制限と有効期限の設定値の投入

### 投入するキー

**いずれも `public.system_settings` へ JSON の整数で入れる。**
**値の妥当条件は全キー共通で 1 以上 2,147,483,647 以下**(欠落・文字列・0 以下・小数・上限超えは不正値)。
キーの一覧の正は [`docs/features/ua1-auth-db-layer/design.md`](../features/ua1-auth-db-layer/design.md) 6 節。

| キー | 意味 | 提案する既定値 |
| --- | --- | --- |
| `auth.token_ttl_seconds` | トークンの有効期限(スライディング延長) | 604800(付録C の 7 日) |
| `auth.team_login.window_seconds` | 失敗を数える窓の幅 | 300 |
| `auth.team_login.throttle_threshold` | 遅延を始める失敗数 | 5 |
| `auth.team_login.throttle_step_ms` | 応答間隔の最小段 | 250 |
| `auth.team_login.throttle_max_ms` | 1 回の待ちの上限 | 2000 |

**上の既定値は提案であって、要件書の付録C には書かれていない。**
付録C の「レート制限の閾値・ロック時間」は**未決(10 章)**のままである
([design.md](../features/ua1-auth-http-entry/design.md) 3 節 E)。
**値を確定させるのは要件書 10 章の相談**であり、本書はそれまでの運用値を示すにとどまる。

### fail-closed

**`auth.team_login.*` の 4 キーのいずれかが未設定・不正ならログインを拒否する。**
正しい資格情報でも発行しない(`data-model.md:1793` の逐語)。
**つまり設定の投入は配備の必須手順であり、忘れるとログインが一切通らない。**

`auth.token_ttl_seconds` も同じく未設定なら発行と延長を拒否する。

### 旧キーの扱い

`auth.team_login.max_failures` と `auth.team_login.lock_seconds` は、
**δ 以降チームのログイン経路では読まれない**。既存の投入物が参照しうるのでキー自体は残す。
管理者側の `auth.admin_login.*` は別のキーで、**無関係**である。

### 投入の手順

**実行する主体**: `public.system_settings` へ書ける権限を持つ接続
(アプリ用ロールではない。表の所有側か DB 管理者)。**アプリ用ロールに書き込み権限を足さない。**

**既存行がありうるので、投入は冪等にする。** 同表は `key` の更新を不変トリガが禁じているため、
**`key` は変えず `value` だけを更新する**形にする。

```sql
INSERT INTO public.system_settings (key, value) VALUES
  ('auth.token_ttl_seconds',              '604800'::jsonb),
  ('auth.team_login.window_seconds',      '300'::jsonb),
  ('auth.team_login.throttle_threshold',  '5'::jsonb),
  ('auth.team_login.throttle_step_ms',    '250'::jsonb),
  ('auth.team_login.throttle_max_ms',     '2000'::jsonb)
ON CONFLICT (key) DO UPDATE
  SET value = EXCLUDED.value, updated_at = CURRENT_TIMESTAMP;
```

**`updated_at` を明示して更新する。** 列には既定値があるが、それが効くのは `INSERT` のときだけで、
`DO UPDATE` の側では更新されない。

**投入したら読み戻して確かめる。**

```sql
SELECT key, value FROM public.system_settings
 WHERE key = 'auth.token_ttl_seconds' OR key LIKE 'auth.team_login.%'
 ORDER BY key;
```

**表の形**(`0010_vocabularies_settings.py:85-96`): `key` が主キーの `text`、`value` が `jsonb`(NOT NULL)、`updated_at` が `timestamptz`(既定値あり)。**`key` の更新は不変トリガが禁じている**ので、上の形(`key` は変えず `value` を更新)しか通らない。

### 確認の順序(fail-closed の検証を先に置く)

**5 キーを投入した後に「1 キーを欠く」状態を作ってはいけない。**
配備先で行を消すのは本番データの破壊であり、**物理削除しない原則にも反する**。

**順序は次のとおり。**

1. **投入前**(または使い捨ての検証先)で、**キーが無い状態のままログインを 1 回試み、
   拒否されることを確かめる**
2. そのうえで上の投入を行う
3. 読み戻しで 5 キーが揃っていることを確かめる
4. ログインが通ることを 1 回確かめる

**1 を飛ばしたなら「未確認」と記録する。** 投入後に作り直して確かめない。

### 配備先での確認

- [ ] 手順 1(未投入の状態でログインが拒否される)を確かめた、または**未確認と記録した**
- [ ] 5 キーを投入し、読み戻しで揃っていることを確かめた
- [ ] 投入後にログインが 1 回通った(**= DB 接続の経路の検査もここで初めて走る** — 2 節)
- 実施記録: 実施者= 実施日= 対象= 手順 1 の実施可否= 結果=

## 4. カウンタの累積量の監視

`authn.observe_rate_limit_counters()` が、**現ウィンドウ外の行数**と
**カウンタ鍵(`scope_key`)の種類数**を返す。

**「試行元の種類数」ではない。** 本関数は鍵の前置きで絞らず**表全体**を数えるので、
ログインの `src:` だけでなく、β 由来の `team:` や管理者側の鍵も含む。
累積量の監視なので総量を見るのが目的である。

### 誰がこの値を取るか

**`EXECUTE` の付与先は管理関数所有用ロール(`pitchlog_management_fn_owner`)だけである。**
ただし**このロールは `NOLOGIN`** なので、**このロールとして接続して呼ぶことはできない**。
付与がこの形になっているのは、**アプリ用ロールへ広げないため**と、
将来この関数を呼ぶ管理関数が同じ所有側に置かれるためである。

**したがって、いま値を取れる経路は DB 管理者の接続だけである**(superuser は `EXECUTE` の
検査を迂回する)。**配備担当者は管理者の接続で呼ぶ。**

```sql
SELECT * FROM authn.observe_rate_limit_counters();
```

**管理コンソールなどから取れる経路は、まだ無い。** 必要になった時点で、
管理関数を 1 本足してそこから呼ぶ(付与先を広げるのではなく)。

**物理削除はしない**(要件書 4.0-2・不変条件 ⑥)。本関数は読むだけである。

**未測定の点**: 種類数は性質上すべての鍵を見る必要がある。索引
`ix_rate_limit_counters_window (scope_key, window_start DESC, id)` の先頭列でまとめる形にしてあるが、
**実 DB の実行計画は未測定**で、プランナが索引走査を選ぶ保証はない。
