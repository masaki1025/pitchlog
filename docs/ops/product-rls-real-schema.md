# 製品 RLS の実スキーマ適用と再実行の運用

## 位置づけ

`docs/design/data-model.md` **12-4 節**の越境テスト再実行ゲートを実行するときの、**実環境側の運用手順**である。
ゲートの定義・通過条件・判定の記録様式は同節が正であり、本書は**複製しない**。

本書が定めるのは**誰が・どの対象に対して・どの順で操作し、失敗したらどうするか**だけである。

### 射程宣言

**本書で確定する範囲**:

1. **適用主体**の要件(何を満たす主体が適用してよいか)
2. **対象の識別**(何を対象と認めるか)と**撤去・作り直し**の順序
3. **既存接続 0 件**の確かめ方
4. **失敗時に serving へ戻さない**扱い

**本書で確定しない範囲**:

- **12-4 の「実スキーマ」の正本上の意味** — **TSK-382 の射程**。本書は「本手順が対象とする運用上の対象」を定めるだけで、条文の意味を定めない
- **接続先の実値・資格情報** — **書かない**(NFR-014)。本書は識別子の**種別**だけを定め、値は設定資産が持つ
- **本番配備への適用・災害復旧・複数環境の運用** — 本書は対象が 1 つである前提で書く。増えたら改訂する
- **適用器の実装・越境テストの中身** — `contracts/authz/product/` と `backend/` が持つ
- **自動化の実装**(runner の構造・観測の手段)— 実装時に決める

## 1. 適用主体

**適用してよい主体の要件**:

| # | 要件 |
| --- | --- |
| 1 | **superuser であること** |
| 2 | **アプリケーション用ロールでないこと** |
| 3 | **対象データベースの所有者ロールが、適用の開始時点で存在していること** |

要件 1・2 は**適用器が接続時の通知から機械で検査する**ので、人が確認する必要はない。
満たさない主体で適用しようとすると適用器が拒否する。

要件 3 は**適用器が検査しない**。所有者ロールの資産は作成を含まず変更だけを行うため、
**存在しなければ適用が失敗する**。**撤去・作り直しの手順(2 節)に所有者ロールの作成を含める。**

**秘密情報は本書に書かない。** 主体の識別と、資格情報をどこが保持するかだけを運用で固定する。

## 2. 対象の識別と撤去・作り直し

### 2-1. 対象と認める条件

次をすべて満たすものだけを対象とする。**1 つでも判定できなければ中止する**(判定不能を成功にしない)。

| # | 条件 | 確かめ方 |
| --- | --- | --- |
| 1 | **専用のデータベースサーバーであること** | 接続したサーバーの識別値を、配備定義の実体と**独立に突き合わせる**。設定値どうしの自己照合にしない |
| 2 | 接続先が**設定資産の指す先と一致する**こと | ホスト・ポートの識別子を照合する |
| 3 | 対象データベース名が**承認された名前と完全に一致する**こと | 部分一致・前方一致で通さない |
| 4 | **共有の開発用データベースでないこと** | 名前とポートのいずれも一致しないことを確かめる |

### 2-2. 撤去・作り直しの順序

**毎回この順で行う。** 途中から再開しない。

1. **対象と認める条件(2-1)をすべて確かめる** — 通らなければ**ここで中止し、以降を実行しない**
2. **既存接続が 0 件であることを確かめる**(3 節)
3. **撤去** — 対象データベースと、手順が作る権限ロールを取り除く
4. **作り直し** — 所有者ロールを作り、対象データベースを作り、スキーマ移行を適用する
5. **適用** — 製品 authz DDL を適用する
6. **再実行** — 越境テストを実行する
7. **記録** — 12-4 の判定記録を書く(様式は `data-model.md` 12-4 が正)

**3 以降は 1 回の連続した実行として行う。** 分けて実行すると、5 で適用した対象が
次の実行の 3 で消えるため、6 が「5 で適用した対象を検査した」ことにならない。

**同名の対象を作り直す前後は、実行ごとに採番する識別値で区別する。**
適用・再実行・判定記録の 3 者が同じ採番を指していることを確かめる。

### 2-3. 作り直しが前提であることの明示

本手順は**状態を保持しない**。対象は毎回まっさらになる。

**したがって、既存のデータを持つ対象への適用は本手順では検証していない。**
この限界を**判定記録へ明記する**。

## 3. 既存接続 0 件の確かめ方

**排出の対象は「アプリケーションの接続」だけではない。対象へ到達できるすべての主体の接続である。**

1. **新しい接続を止める**
2. 対象へ到達できる接続が **0 件**であることを確かめる
3. 0 件でなければ**待つか中止する**。強制切断で 0 件にしたときは、**切断した事実を判定記録へ書く**

**この区間の始期**は、撤去を始める前に 1・2 を満たした時点である。
**終期**は、適用の後に検査と越境テストがすべて通った時点である。

## 4. 失敗時に serving へ戻さない扱い

**撤去・作り直し・適用・再実行のいずれで失敗しても、対象を serving へ戻さない。**

- **部分的に再開しない。** 失敗後は 2-2 の 1 からやり直し、**新しい採番を採る**
- **弱化した状態を次回へ持ち越さない。** 復元ではなく**再構築**で回復する
- **中断したまま放置しない。** 再構築するか、対象を落としたままにするかのいずれかにする

本手順は**維持用の錠(maintenance latch)を置かない**。錠は「弱化した状態のまま serving へ戻さない」ための
機構だが、本手順は**再構築で閉じる**ので、弱化状態を跨いで保持する必要がない。

## 付記: 本書が扱わない対象が増えたとき

対象が 2 つ以上になる、本番配備へ適用する、既存データを保持したまま適用する、のいずれかが必要になったら、
**本書を改訂する**。現行の 4 節は**対象が 1 つで、毎回まっさらにする**前提でのみ成立する。
