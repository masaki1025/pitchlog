# 署名鍵の入れ替え手順

**状態: approved(v1.0)。** 確定ゲート(/finalize-doc)を 2026-10-10 に通過した(敵対レビュー 2 回 → PO 承認・山田正輝)。

トークンの提示値に付く HMAC-SHA256 署名の鍵を入れ替える手順を書く。
条文の正は [`docs/design/data-model.md`](../design/data-model.md) 8-3 節。


## 0. 射程宣言(設計書 7.3-7)

1. **署名鍵の条件** — 生成・長さ・符号化・供給する環境変数名
2. **入れ替えの手順** — 11 段と、完了の定義(全実行系を指紋で 1 つずつ照合し、**旧鍵を破棄するまで**完了としない)。**受付を止めてから入れ替える**こと(混在禁止)
3. **入れ替えが何をするか** — 全トークンの失効と同じ効果であること、新旧の並行受付ができないこと、**旧鍵を再投入すると失効が取り消されること**

## 1. 入れ替えが何をするか

> **署名鍵の入れ替えは全トークンの失効と同じ効果を持つ**(鍵の版を持つ設計は採らない —
> 必要が実測で示された時点で本節を改訂)。**この効果は、提示値を検証するすべての実行系が
> 新しい鍵へ切り替わった時点で成立する**。入れ替えの手順は全実行系の切り替えの完了を
> 確かめてから完了とする(`data-model.md:1704`)

**鍵の版を持たない**ので、**新旧を並行して受け付ける期間は作れない**。
入れ替えた瞬間に、**既存の利用者は全員ログインし直すことになる**。

**「全実行系」が要点である。** 1 つでも古い鍵を持つ実行系が残っていると、
そこだけ古い提示値を通し続けるので、**失効は成立していない**。

### 失効は「鍵を使わないこと」で保たれる(取り消せる)

**トークン行は鍵の入れ替えで変わらない。** 署名の照合はアプリ側の HMAC だけで行い、
`authn.verify_token` は署名鍵を見ない(`FUNCTION:authn:verify_token(uuid).sql`)。

**したがって旧鍵を再投入すると、期限内の旧提示値は再び通る。**
「全トークンの失効と同じ効果」は、**旧鍵を二度と使わない限りにおいて**成立する。

- **旧鍵は破棄する。** 切り戻しのために取っておかない
- **切り替えに失敗したときは、旧鍵へ戻さず新鍵で前進させる**(手順 3 の再実行)。
  旧鍵へ戻すと、失効させたはずの提示値が全部復活する
- **本当に旧鍵へ戻さざるを得ない場合**は、**失効が取り消されたものとして扱い**、
  戻した事実と影響範囲を記録して、改めて入れ替えをやり直す

## 2. 鍵の条件

`backend/src/pitchlog/authz/signing_key_config.py` の
`require_signing_key_configuration` が起動時に検査する。

| 条件 | 内容 |
| --- | --- |
| 生成 | **CSPRNG 由来の乱数** |
| 長さ | **32 バイト以上**(復号後) |
| 符号化 | **標準 Base64 の padding 付き正規形**。別表記は受け付けない |
| 供給 | 環境変数 `PITCHLOG_TOKEN_SIGNING_KEY_B64` |

**条件を満たさない値ではアプリが起動しない**(`create_app()` が例外で止まる)。
欠落・形式不正・短すぎのいずれも拒否する。

鍵の生成の例:

```
python -c "import base64,secrets; print(base64.b64encode(secrets.token_bytes(32)).decode())"
```

**生成した鍵をリポジトリへ置かない。** 設定の正本は環境変数であり、
キー名の一覧は設定例ファイルが持つ(NFR-014)。

## 3. 手順

### 先に:順次再起動をしてはいけない

**鍵の版を持たないので、旧鍵の実行系と新鍵の実行系が同時に受け付けている時間を作ってはいけない。**
混在させると、**同じ提示値が当たった実行系によって通ったり拒否されたりする**。
利用者から見ると、再読み込みのたびにログイン状態が入れ替わる。

**負荷分散の下でローリング再起動をすると、必ずこの状態になる。**
下の手順は**受付を止めてから入れ替える**形にしてある。

### 鍵の指紋(手順 6 で使う)

**鍵そのものを見せずに、どの鍵が入っているかを突き合わせるために指紋を使う。**
指紋 = **設定値(Base64 の文字列)の SHA-256**。

```
printf '%s' "$PITCHLOG_TOKEN_SIGNING_KEY_B64" | sha256sum
```

**鍵の値は出力されない。** 新しい鍵を作ったときに指紋を 1 度計算し、
それを**期待値**として手順 6 で各系の出力と突き合わせる。

**起動に成功したことは、新しい鍵が入っている証拠にならない。**
起動時の検査(`signing_key_config.py`)が見るのは**形式と長さだけ**で、
旧鍵も同じく通る。

### 手順

1. **新しい鍵を生成し、その指紋を控える**(上の条件と指紋)
2. **提示値を検証するすべての実行系を数え上げ、一覧にする。**
   **この一覧が手順 7 の照合表になる**ので、各系を一意に指せる名前で書く
3. **切り替え前に有効な提示値を 1 件取っておく**(手順 9 で使う)。
   **受付を止めた後では旧鍵で発行できない**ので、ここで取る。
   **取得した提示値は確認が終わったら破棄する**
4. **受付を止める。** 負荷分散から全実行系を外すか、入口を停止する。
   **ここから手順 8 までの間、利用者の要求を受け付けない**
5. **一覧のすべての実行系の環境変数を新しい鍵へ差し替える**
6. **一覧のすべての実行系を再起動する**
7. **一覧の 1 つずつについて、その系で指紋を計算し、手順 1 の期待値と一致することを
   確かめ、一覧に照合結果を書き込む。**
   **負荷分散を経由せず、各系へ直接到達して確かめる**(どの系に当たったかを
   呼び出し側から決められないため)。
   **1 件でも未確認・不一致が残っているあいだは次へ進まない。**
   **「どれか 1 つで旧提示値が拒否された」ことをもって全系の確認に代えない**
8. **受付を再開する**
9. **手順 3 で取っておいた提示値が拒否されることを確かめる**
10. **利用者が再ログインできることを 1 件確かめる**
11. **旧鍵を破棄する。** 保管場所・設定・控えのすべてから消し、消したことを記録する

**手順 7 の照合が全件そろい、かつ手順 11 の破棄が済むまで、入れ替えは完了していない。**

**手順 11 を飛ばすと失効は保たれない。** 旧鍵が残っている限り、
再投入すれば期限内の旧提示値が全部復活する(1 節)。

**受付を止められない配備形態の場合**は、本手順は使えない。
**鍵の版を持つ設計が要る**ことになるので、`docs/design/data-model.md` 8-3 節の改訂へ上げる
(同節は「必要が実測で示された時点で本節を改訂」と書いている)。

## 4. 実地確認の記録

**本書の手順のうち、「鍵を替えると旧提示値が通らなくなる」ことだけを 1 回確かめた。**
**手順 1〜11 を通したわけではない。**

- **実施日**: 2026-10-10
- **実施者**: Claude(U-A1 δ・TSK-470)
- **対象**: `TokenPresentation` と `require_signing_key_configuration`(配備先ではない)
- **方法**: 旧鍵で提示値を発行 → 新鍵へ入れ替え → 同じ提示値を新鍵で検証

```
入れ替え前の提示値を旧鍵で検証: True
入れ替え後の新鍵で旧提示値を検証: 拒否 -> 提示値の形式または署名が不正です
新鍵で発行した提示値を新鍵で検証: True
旧提示値と新提示値が異なる: True
31 バイト鍵の拒否: 署名鍵の設定が短すぎます
```

**確かめたのは「鍵を替えると旧提示値が通らなくなること」と「短い鍵が拒否されること」である。**

**確かめていないこと**(手順のほとんどが未検証である):

- **受付の停止と再開**(手順 4・8)
- **全実行系の数え上げと、指紋による 1 系ずつの照合**(手順 2・7)。
  上の確認は**単一の署名器**に対するもので、複数の実行系を使っていない
- **実行系の再起動**(手順 6)
- **旧鍵の破棄**(手順 11)
- **入れ替え中の利用者の影響**(同時接続がある状態での挙動)

## 5. 入れ替えが要る場面

- **鍵が漏れた、または漏れた疑いがある**
- **全トークンを失効させたい**(鍵の版を持たないので、これが唯一の全失効手段である)

**定期的な入れ替えの要否は本書では決めない。** 全利用者の再ログインを伴うため、
運用の判断になる。
