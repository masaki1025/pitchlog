## 1. 入れ替えが何をするか

> **署名鍵の入れ替えは全トークンの失効と同じ効果を持つ**(鍵の版を持つ設計は採らない —
> 必要が実測で示された時点で本節を改訂)。**この効果は、提示値を検証するすべての実行系が
> 新しい鍵へ切り替わった時点で成立する**。入れ替えの手順は全実行系の切り替えの完了を
> 確かめてから完了とする(`data-model.md:1704`)

**鍵の版を持たない**ので、**新旧を並行して受け付ける期間は作れない**。
入れ替えた瞬間に、**既存の利用者は全員ログインし直すことになる**。

**「全実行系」が要点である。** 1 つでも古い鍵を持つ実行系が残っていると、
そこだけ古い提示値を通し続けるので、**失効は成立していない**。

### 失効は「鍵を使わないこと」で保たれる(取り消せる)

**トークン行は鍵の入れ替えで変わらない。** 署名の照合はアプリ側の HMAC だけで行い、
`authn.verify_token` は署名鍵を見ない(`FUNCTION:authn:verify_token(uuid).sql`)。

**したがって旧鍵を再投入すると、期限内の旧提示値は再び通る。**
「全トークンの失効と同じ効果」は、**旧鍵を二度と使わない限りにおいて**成立する。

- **旧鍵は破棄する。** 切り戻しのために取っておかない
- **切り替えに失敗したときは、旧鍵へ戻さず新鍵で前進させる**(手順 3 の再実行)。
  旧鍵へ戻すと、失効させたはずの提示値が全部復活する
- **本当に旧鍵へ戻さざるを得ない場合**は、**失効が取り消されたものとして扱い**、
  戻した事実と影響範囲を記録して、改めて入れ替えをやり直す

## 2. 鍵の条件

`backend/src/pitchlog/authz/signing_key_config.py` の
`require_signing_key_configuration` が起動時に検査する。

| 条件 | 内容 |
| --- | --- |
| 生成 | **CSPRNG 由来の乱数** |
| 長さ | **32 バイト以上**(復号後) |
| 符号化 | **標準 Base64 の padding 付き正規形**。別表記は受け付けない |
| 供給 | 環境変数 `PITCHLOG_TOKEN_SIGNING_KEY_B64` |

**条件を満たさない値ではアプリが起動しない**(`create_app()` が例外で止まる)。
欠落・形式不正・短すぎのいずれも拒否する。

鍵の生成の例:

```
python -c "import base64,secrets; print(base64.b64encode(secrets.token_bytes(32)).decode())"
```

**生成した鍵をリポジトリへ置かない。** 設定の正本は環境変数であり、
キー名の一覧は設定例ファイルが持つ(NFR-014)。

## 3. 手順

### 先に:順次再起動をしてはいけない

**鍵の版を持たないので、旧鍵の実行系と新鍵の実行系が同時に受け付けている時間を作ってはいけない。**
混在させると、**同じ提示値が当たった実行系によって通ったり拒否されたりする**。
利用者から見ると、再読み込みのたびにログイン状態が入れ替わる。

**負荷分散の下でローリング再起動をすると、必ずこの状態になる。**
下の手順は**受付を止めてから入れ替える**形にしてある。

### 手順

1. **新しい鍵を生成する**(上の条件)
2. **提示値を検証するすべての実行系を数え上げ、一覧にする。**
   **この一覧が手順 6 の照合表になる**ので、各系を一意に指せる名前で書く
3. **受付を止める。** 負荷分散から全実行系を外すか、入口を停止する。
   **ここから手順 7 までの間、利用者の要求を受け付けない**
4. **一覧のすべての実行系の環境変数を新しい鍵へ差し替える**
5. **一覧のすべての実行系を再起動する**
6. **一覧の 1 つずつについて、新しい鍵で起動したことを確かめ、一覧に照合結果を書き込む。**
   **1 件でも未確認・不一致が残っているあいだは次へ進まない。**
   **「どれか 1 つで旧提示値が拒否された」ことをもって全系の確認に代えない** —
   負荷分散の下では、どの系に当たったかを呼び出し側から決められない
7. **受付を再開する**
8. **古い提示値が拒否されることを 1 件確かめる**
9. **利用者が再ログインできることを 1 件確かめる**

**手順 6 の照合が全件そろうまで、入れ替えは完了していない。**

**受付を止められない配備形態の場合**は、本手順は使えない。
**鍵の版を持つ設計が要る**ことになるので、`docs/design/data-model.md` 8-3 節の改訂へ上げる
(同節は「必要が実測で示された時点で本節を改訂」と書いている)。

## 5. 入れ替えが要る場面

- **鍵が漏れた、または漏れた疑いがある**
- **全トークンを失効させたい**(鍵の版を持たないので、これが唯一の全失効手段である)

**定期的な入れ替えの要否は本書では決めない。** 全利用者の再ログインを伴うため、
運用の判断になる。
