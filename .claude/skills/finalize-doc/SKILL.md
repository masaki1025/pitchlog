# 正本確定ゲート(設計書 7.3)

**敵対レビューを経ずに approved にする経路は存在しない。** 規範(適用版・収束条件と終端遷移・重大度定義・レビュー範囲・依頼文規約・エスカレーション・残余リスク)の正は**設計書 7.3(7.3-1〜7.3-8)** — 本書は手順だけを定め、内容を複製しない。**適用する規則は、その時点で approved の 7.3**(7.3-1)。**7.3 自身の改訂ゲートでは、適用版 = 対象の in-review 化の直前に approved であった版**とし、**版数と当該版の条文を含むコミット SHA を worklog へ記録して、手順 1 の in-review 化と同一コミットにする**(証跡)。以後の運用は**記録した適用版の条文**に従う — 本書の手順と適用版の条文が食い違う場合は**条文が優先**する(節番号の存否で判定しない。スキルを先に改訂しても未承認規則は自己適用されない — v1.13 以降も同じ)。

## 手順

0. **射程宣言の確認**(7.3-7): 射程宣言(「本書で確定する範囲/実装時に確定する範囲」)があることを確認する — **新設の正本は文書内の節・既存正本の改訂は当該改訂の変更履歴行(in-review)に記載**。なければ追加してから開始する
1. 対象の変更履歴表/frontmatter を `in-review` に更新し、**適用版(7.3 の版数+条文コミット SHA)の worklog 記録を同一コミットに含める**(7.3-1 — すべてのゲートで記録し、当該ゲートは記録した版で最後まで運用する。ゲート中に 7.3 の新版が approved になっても切り替えない)
2. 敵対レビューを実行する: `python .claude/scripts/codex_run.py review adversarial -`(モデルはラッパーが ADR-001 どおり sol xhigh に固定)。依頼文は **7.3-5 の規約**に従う:
   - **冒頭に命令文**「実際にレビューを実施し、次周の依頼文を作らず、判定を返すこと」を置く
   - **7.3-3 の重大度定義**を毎回組み込む
   - 対象は **初周・最終全文確認周・射程変更(縮小・拡大)直後の周 = 全文**、それ以外 = **反映差分と影響節の指定のみ**(前周指摘の全文並記をしない — 7.3-4)
   - 応答様式(各指摘に `P0|P1|P2` + `起因|非起因` + `(A)|(B)`、最終行に判定行)を明記する。**判定行のない応答は周として数えず、同一周を再依頼する**
3. 指摘を「採用(反映内容)/不採用(理由)」に分類し、**採否記録を worklog へ周ごとに追記して当該周のコミットに含める**(7.3-2 の定義: 要旨・重大度・起因・(A)/(B)・採否と理由・(B) の送り先 — 中断時にも 2 周連続判定と申し送りを復元できるようにする)。処理は **7.3-2 の終端遷移表に従う**(P0/P1 ゼロ周での P2 一括反映・(B) の送り先記録・全件不採用の扱い・最終全文確認周の分岐を含む)
4. **収束(7.3-2)まで 2〜3 を繰り返す**。**採用反映を伴う** 1 周ごとに、**実行中 feature の plan.md** の frontmatter `確定ゲート周回` を +1 する(指摘なし・全件不採用の周は数えない。更新先 = 実行時 worktree の `docs/features/*/plan.md` で status が active|in-review かつ branch が worktree と一致するもの。一意に解決できなければ人間に確認 — 黙って省略しない。キーが無い旧 plan は `0` を追記してから更新する)
   - **反映周ごとに 1 コミットを作る**(設計書 6.1)。件名に **`反映<r>周目`**(`<r>` は 1 始まり)を含め、**ステップ記法を付けない**。例: `docs: 確定ゲート 反映3周目 — 指摘 4 件を反映`。**`確定ゲート` を含むだけの件名は反映周コミットとみなされない**
   - **6 周警告**(7.3-6): `確定ゲート周回` が 6 に達したら、周回・重大度推移・起因比の一覧を PO へ提示する(判断を求めるが強制打ち切りはしない)
   - **エスカレーション**(7.3-6): 前周修正**起因**の指摘が 2 周連続で過半になったら(算式は 7.3-6)、PO スコープ裁定へ上げる。裁定(射程縮小/範囲確定/続行指示)後の編集・カウンタ・次周は 7.3-6 の表に従う。**射程が変わった場合(縮小・拡大とも)は変更範囲と理由を変更履歴と worklog に記録し、次周は全文レビュー**
5. 採用/不採用の一覧を提示して**人間の承認を明示的に求める**(曖昧な同意で進めない)
6. 承認後: 状態を `approved`・版数確定・変更履歴表に追記・`docs/README.md` 索引を現行化する
7. レビュー往復の要点(重要指摘と対応・警告/エスカレーションの発動有無)を worklog に記録する

- 判定行・起因フラグ・警告・エスカレーション検知は**運用規律であり機械検証されない**(7.3-8 — 欠けても CI は green になり得る。手順で守る)
- 指摘反映で**コード修正**が必要になり、かつ実行中 feature の plan が `in-review`(PR 段階)の場合は、先に /pr の「差し戻しが発生したら」手順で `status: active` へ戻してから /implement する(`codex_run.py implement` は `active` 以外を拒否する — 設計書 6.1 差し戻しの往復)
