# タスク完了(設計書 6.1 / 12.1)

worklog の締めと計画書の status 更新は **/pr が PR 内で実施済み**(マージ後の develop を直接編集しない)。本スキルはリポジトリ外の後片付けだけを行う。

## 前提

`gh pr view <branch> --json state` で PR が **MERGED** であることを確認する(branch は計画書 frontmatter の `branch` — `feature/*`・`fix/*` 両対応。未マージなら中断してレビュー状況を報告)。

## 手順

1. メインツリーで `git switch develop` → `git pull --ff-only`(最新化。fast-forward 不可なら**中断**して状況を報告 — 保護ブランチにマージコミットを作らない)。**worktree の有無にかかわらず必ず実施する**
2. **worktree の存在を判定する**(**再実行の起点** — v1.6・確定ゲート 9・10 周目 P1)。**不在なら worktree に依存する手順(3 と 5)を完了済みとして扱い、それ以外の手順は通常どおり実行する**
3. 【worktree があるときだけ】worktree に未コミット変更が残っていないか確認(残っていれば内容を見せてユーザーに確認してから)
4. **【Phase 4 の論理スロット 4-6 を閉じる場合のみ】必須の後続処理を起票する**(設計書 13 章 — v1.6)。**worktree 除去より前に行う**(除去後だと中断時の再実行が成立しないため)
   - **対象の識別は人間に確認する** — 「このタスクは Phase 4 の 4-6(NFR-021 受入判定を担う PR)か」を問う。**機械的な識別は Phase 4-4 / 4-5 へ送った**(設計書 13 章「本改訂で意図的に定めなかったもの」— PO 裁定 2026-08-16)
   - **判定**: **10.1 のマージ後検査(`M` の両親・ツリー)の結果を 4-6 の PR コメントの記録から読む**(記録項目 = `M` の完全 OID・実施日・合否・確認者 — 13 章)。**3 分岐で扱う**: **① 記録が無い・判定不能なら中断**して人間に報告する / **② 合格なら下記「合格のとき」** / **③ 不合格なら下記「不合格のとき」**(**②③ を「前提」でまとめると不合格経路が到達不能になる** — 確定ゲート 16 周目 P1)
   - **合格のとき**: ① `P4-後` を Notion へ起票(タスク名に `P4-後` を含める)→ ② **4-6 のタスクと相互にリンク**(**`URL` プロパティは使わない** — 同欄は `/pr` が GitHub PR URL を記録する専用欄。**コメント**で相互に記録する)
   - **不合格のとき**: **`P4-後` は起票せず、「Phase 4-6 再試行」タスクを起票**して相互リンクする(設計書 13 章)。**最小の必須事項は 3 つ**: **タスク名に `Phase 4-6 再試行` を含める / 担当者は元タスクを引き継ぐ / DoD に「`M` を新たな `T` として 10.1 の受入をやり直し、マージ後検査に合格すること」を書く**。**本タスクはそのまま手順 5 以降で閉じる** — **元 PR はマージ済みで worktree も回収すべき**
   - **再実行契約(冪等)**: 起票対象のタスクが**既に存在すれば照合して再利用**し、重複起票しない。**リンクが片側だけ済んでいれば残りだけを補う**
   - **`P4-後` のタスクが「Phase 4 展開」の終端**であり、4-6 のタスクを閉じても Phase 4 展開は閉じない
5. 【worktree があるときだけ】`git worktree remove ../pitchlog-worktrees/<worktree名>` → `git worktree prune`
6. Notion ステータスを `完了` へ・完了日 = マージ日を記録(綴りの正: `.claude/notion-map.json` — 推測しない)。残件があれば新しい Notion タスクとして起票を提案する
7. **マージ後に気づいたハーネス運用上の知見は follow-up タスクとして Notion に起票する**(または既存タスクへリンクする)。**本スキルから評価台帳(`docs/development/harness-evaluation.md`)を編集しない** — 本スキルは develop 上で走るため、正本を直接編集すると絶対規則 1(main/develop へ直接コミットしない)に反する。**台帳への追記は次の `/task-start` で別 feature/PR として行う**(追記の主経路は /pr のクローズ処理 — `pr/SKILL.md` 手順 1)

## 報告

完了サマリ: マージされた PR / 更新された正本 / 残件(あれば)。
※ 完了状態の正は「PR merged + Notion Done + worktree 不在」の組(計画書の frontmatter は in-review のまま残る — 設計書 6.1)。
