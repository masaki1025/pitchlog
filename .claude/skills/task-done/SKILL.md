# タスク完了(設計書 6.1 / 12.1)

worklog の締めと計画書の status 更新は **/pr が PR 内で実施済み**(マージ後の develop を直接編集しない)。本スキルはリポジトリ外の後片付けだけを行う。

## 前提

`gh pr view <branch> --json state` で PR が **MERGED** であることを確認する(branch は計画書 frontmatter の `branch` — `feature/*`・`fix/*` 両対応。未マージなら中断してレビュー状況を報告)。

## 手順

1. メインツリーで `git switch develop` → `git pull --ff-only`(最新化。fast-forward 不可なら**中断**して状況を報告 — 保護ブランチにマージコミットを作らない)。**worktree の有無にかかわらず必ず実施する**
2. **worktree の存在を判定する**(**再実行の起点** — v1.6・確定ゲート 9・10 周目 P1)。**不在なら worktree に依存する手順(3 と 5)を完了済みとして扱い、それ以外の手順は通常どおり実行する**
3. 【worktree があるときだけ】worktree に未コミット変更が残っていないか確認(残っていれば内容を見せてユーザーに確認してから)
4. **計画書 frontmatter の `Phase4スロット` で分岐する**(設計書 13 章 — v1.6)
   - **欠落・空値・列挙外の値は中断**して人間に報告する(**本キーは既定値を持たない** — 設計書 6.1・確定ゲート 12 周目 P1)。**`Phase4スロット` を持たない v1.6 以前の計画書も中断対象**であり、**人間が `対象外` を明示して再実行する**(同 11 周目 P2)。**値は `/task-start` で人間が 8 択から選んだもの**であり、**タスク名からの推定で補わない**(同 12 周目 P1 — 推定は `/task-start` と同じ規則の再読にすぎず独立照合にならない)
   - **`対象外` / `4-1`〜`4-5` / `P4-後`**: 後続処理なし。**手順 5 へ**
   - **`4-6`**: 下記のマージ後検査と後続処理を行う。**worktree 除去より前に行う**(除去後だと中断時の再実行が成立しないため)
   - **① マージ後検査(期待値は `E` の中から取る — v1.6・確定ゲート 13 周目 P1)**: `gh pr view <branch> --json mergeCommit,headRefOid` で **`M`(マージコミット)と `E`(PR head)** を取得し、**(a) `git rev-parse <M>^2` == `E`** / **(b) `git rev-parse <M>^{tree}` == `git rev-parse <E>^{tree}`** / **(c) `git rev-parse <M>^1` == 証跡の `phase4_base_sha`**(完全一致)を確認する。**証跡は検証器へ `evidence_path` として名指しした 1 ファイル**を指す(`E` には複数試行の証跡が収録されうるため — 確定ゲート 14 周目 P1)。**その `evidence_path` は 4-6 の PR コメントの記録項目に含まれている**ので、そこから復元する(記録が無ければ**復元不能として中断**する — 同 15 周目 P1)。**証跡は `E` の Git ツリーに収録されるため不変**であり、書き換えれば `E` 自体が変わって受入をやり直すことになる。**12 周目に置いた `merge-base` による代替(第 1 親が `E` の祖先)は撤回した** — **排他区間中に develop を `E` の祖先の一つへ fast-forward すると条件が成立してしまい、手続きの保証にならない**。**Git オブジェクトを解決できないとき・証跡に `phase4_base_sha` が無いときは判定不能として中断**する(fail-closed)
   - **② 人間の判定記録**: 4-6 の PR コメントに合格判定が記録されていることを確認する(記録項目は 13 章。10.1 が判定者による合格判定を必須としているため)。**①の合格条件を②で代替しない** — **PR コメントは編集・削除できる可変媒体**であり、**期待値を記録から取ると、base が動いた後に記録を書き換えるだけで検査が通る**(同 12 周目 P1)
   - **①②が揃ったときだけ合格**とする。**未記録・不合格・食い違いは Phase 4 未完了**
   - **合格のとき**: ① `P4-後` を Notion へ起票(タスク名に `P4-後` を含める)→ ② **4-6 のタスクと相互にリンク**(**`URL` プロパティは使わない** — 同欄は `/pr` が GitHub PR URL を記録する専用欄。**コメント**で相互に記録する)→ ③ **①の実測値(`M`・`E`・両者のツリー・第 1 親)と②の記録項目を `P4-後` のタスクへ転記**する(完了証跡へ Git 管理下で引き継ぐため — 13 章)→ ④ DoD へ**機械可読マーカー行 `Phase4スロット: P4-後`** を書く(**行全体の完全一致・DoD 欄にちょうど 1 行**。`/task-start` がこれと人間の選択を突合し、食い違えば中断する — 設計書 13 章・確定ゲート 13・14 周目 P1)→ ⑤ **起票した子タスクの URL を 4-6 のタスクへコメントで記録**する(`/task-start` が同名タスクの重複起票を検出するのに使う — 同 14 周目 P1)
   - **不合格のとき**: **`P4-後` は起票せず、「Phase 4-6 再試行」タスクを起票**して相互リンクする(設計書 13 章)。**初期化は Notion タスクの範囲だけで行う**(v1.6・確定ゲート 12 周目 P1 — **計画書・ブランチ・worktree を作るのは後続の `/task-start` の責務**であり、本スキルで計画書まで作るとステータスが `進行中` になり「開始は `未着手`」と両立しないため): **タスク名に `Phase 4-6 再試行` を含める / 担当者・優先度は元タスクを引き継ぐ / ステータスは `未着手` / DoD へ**機械可読マーカー行 `Phase4スロット: 4-6`**(**行全体の完全一致・DoD 欄にちょうど 1 行**。`/task-start` が人間の選択と突合する — 同 13・14 周目 P1)と「`M` を新たな `T` として 10.1 の受入をやり直し、マージ後検査に合格すること」/ 完遂責任者は元タスクの担当者**。**初期化まで済ませてから**本タスクを手順 5 以降で閉じる — **元 PR はマージ済みで worktree も回収すべき**(同 10 周目 P1)
   - **再実行契約(冪等)**: 起票対象のタスクが**既に存在すれば照合して再利用**し、重複起票しない。**リンクが片側だけ済んでいれば残りだけを補う**
   - **`P4-後` のタスクが「Phase 4 展開」の終端**であり、4-6 のタスクを閉じても Phase 4 展開は閉じない
5. 【worktree があるときだけ】`git worktree remove ../pitchlog-worktrees/<worktree名>` → `git worktree prune`
6. Notion ステータスを `完了` へ・完了日 = マージ日を記録(綴りの正: `.claude/notion-map.json` — 推測しない)。残件があれば新しい Notion タスクとして起票を提案する
7. **マージ後に気づいたハーネス運用上の知見は follow-up タスクとして Notion に起票する**(または既存タスクへリンクする)。**本スキルから評価台帳(`docs/development/harness-evaluation.md`)を編集しない** — 本スキルは develop 上で走るため、正本を直接編集すると絶対規則 1(main/develop へ直接コミットしない)に反する。**台帳への追記は次の `/task-start` で別 feature/PR として行う**(追記の主経路は /pr のクローズ処理 — `pr/SKILL.md` 手順 1)

## 報告

完了サマリ: マージされた PR / 更新された正本 / 残件(あれば)。
※ 完了状態の正は「PR merged + Notion Done + worktree 不在」の組(計画書の frontmatter は in-review のまま残る — 設計書 6.1)。
