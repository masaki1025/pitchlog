# タスク完了(設計書 6.1 / 12.1)

worklog の締めと計画書の status 更新は **/pr が PR 内で実施済み**(マージ後の develop を直接編集しない)。本スキルはリポジトリ外の後片付けだけを行う。

## 前提

`gh pr view <branch> --json state` で PR が **MERGED** であることを確認する(branch は計画書 frontmatter の `branch` — `feature/*`・`fix/*` 両対応。未マージなら中断してレビュー状況を報告)。

## 手順

1. メインツリーで `git switch develop` → `git pull --ff-only`(最新化。fast-forward 不可なら**中断**して状況を報告 — 保護ブランチにマージコミットを作らない)。**worktree の有無にかかわらず必ず実施する**
2. **worktree の存在を判定する**(**再実行の起点** — v1.6・確定ゲート 9・10 周目 P1)。**不在なら worktree に依存する手順(3 と 5)を完了済みとして扱い、それ以外の手順は通常どおり実行する**
3. 【worktree があるときだけ】worktree に未コミット変更が残っていないか確認(残っていれば内容を見せてユーザーに確認してから)
4. **計画書 frontmatter の `Phase4スロット` で分岐する**(設計書 13 章 — v1.6)
   - **キーの欠落・空値・列挙外の値は中断**して人間に報告する(v1.6・確定ゲート 10 周目 P1 — **任意キーにすると 4-6 で書き忘れたときに後続処理を落としたまま完了まで進む**)。**`Phase4スロット` を持たない v1.6 以前の計画書も中断対象**であり、**人間が `対象外` を明示して再実行する**(同 11 周目 P2)
   - **独立照合(必須)**: **Notion タスク名とスロット値を突合する**(v1.6・確定ゲート 11 周目 P1)。タスク名に `Phase 4-<n>` / `Phase 4-6 再試行` / `P4-後` を含むのに `Phase4スロット` が対応しない、またはその逆なら**中断**する — **テンプレの既定値 `対象外` を書き換え忘れても「欠落」にはならない**ため、値の存在検査だけでは 4-6 の記入漏れを塞げない
   - **`対象外` / `4-1`〜`4-5` / `P4-後`**: 後続処理なし。**手順 5 へ**
   - **`4-6`**: 下記のマージ後検査と後続処理を行う。**worktree 除去より前に行う**(除去後だと中断時の再実行が成立しないため)
   - **① Git からの実測**: `gh pr view <branch> --json mergeCommit,headRefOid` で **`M`(マージコミット)と `E`(PR head)** を取得し、**`git rev-parse <M>^2` == `E`** かつ **`git rev-parse <M>^{tree}` == `git rev-parse <E>^{tree}`** を Git オブジェクトで独立に再検査する。**Git オブジェクトを解決できないときは判定不能として中断**する(fail-closed)
   - **② 第 1 親の照合**(v1.6・確定ゲート 11 周目 P1 — **10 周目に「要らない」と書いたのは誤りで撤回した**): **`git rev-parse <M>^1` == 記録された `phase4_base_sha`** を確認する。**第 1 親は「排他区間中に base が動いていないか」という手続きを検査**しており、第 2 親・ツリー(統合結果の内容)では代替できない — **`develop` に変更とその revert が入るとツリーは判定時点へ戻るため、①だけでは base が動いた事実を検出できない**。**期待値 `phase4_base_sha` は Git から実測できない**ので③の記録から取る
   - **③ 人間の判定記録**: 4-6 の PR コメントに合格判定が記録されていることを確認する(記録項目は 13 章 — `M` の完全 OID / 期待した両親とツリー / 実測した両親とツリー / 実施日 / 合否 / 確認者)
   - **①②③がすべて揃ったときだけ合格**とする。**③だけを根拠にしない**(PR コメントは編集・削除できる)。**未記録・不合格・食い違いは Phase 4 未完了**
   - **合格のとき**: ① `P4-後` を Notion へ起票(タスク名に `P4-後` を含める。計画書には `Phase4スロット: P4-後` を書く)→ ② **4-6 のタスクと相互にリンク**(**`URL` プロパティは使わない** — 同欄は `/pr` が GitHub PR URL を記録する専用欄。**コメント**で相互に記録する)→ ③ **①②の実測値と③の記録項目を `P4-後` のタスクへ転記**する(完了証跡へ Git 管理下で引き継ぐため — 13 章)
   - **不合格のとき**: **`P4-後` は起票せず、「Phase 4-6 再試行」タスクを起票**して相互リンクする(設計書 13 章)。**後継責務として初期化する**(v1.6・確定ゲート 11 周目 P1 — 名称とリンクだけでは再試行が未着手のまま放置できる): **タスク名に `Phase 4-6 再試行` を含める / 計画書に `Phase4スロット: 4-6` / 担当者・優先度は元タスクを引き継ぐ / 開始ステータスは `未着手` / DoD に「`M` を新たな `T` として 10.1 の受入をやり直し、マージ後検査に合格すること」/ 完遂責任者は元タスクの担当者**。**初期化まで済ませてから**本タスクを手順 5 以降で閉じる — **元 PR はマージ済みで worktree も回収すべき**(同 10 周目 P1)
   - **再実行契約(冪等)**: 起票対象のタスクが**既に存在すれば照合して再利用**し、重複起票しない。**リンクが片側だけ済んでいれば残りだけを補う**
   - **`P4-後` のタスクが「Phase 4 展開」の終端**であり、4-6 のタスクを閉じても Phase 4 展開は閉じない
5. 【worktree があるときだけ】`git worktree remove ../pitchlog-worktrees/<worktree名>` → `git worktree prune`
6. Notion ステータスを `完了` へ・完了日 = マージ日を記録(綴りの正: `.claude/notion-map.json` — 推測しない)。残件があれば新しい Notion タスクとして起票を提案する
7. **マージ後に気づいたハーネス運用上の知見は follow-up タスクとして Notion に起票する**(または既存タスクへリンクする)。**本スキルから評価台帳(`docs/development/harness-evaluation.md`)を編集しない** — 本スキルは develop 上で走るため、正本を直接編集すると絶対規則 1(main/develop へ直接コミットしない)に反する。**台帳への追記は次の `/task-start` で別 feature/PR として行う**(追記の主経路は /pr のクローズ処理 — `pr/SKILL.md` 手順 1)

## 報告

完了サマリ: マージされた PR / 更新された正本 / 残件(あれば)。
※ 完了状態の正は「PR merged + Notion Done + worktree 不在」の組(計画書の frontmatter は in-review のまま残る — 設計書 6.1)。
